Part 2 — Modeling  ::  Chapter 12

2.8 System Knowledge: Models as a System

The six preceding chapters each drew a different model of the same product. It would be natural to read them as six views onto one large model that holds structure, behavior, ownership, policy, measurement, and provenance together. DocAble has no such model. Nor does MAGE require one. What it has is a family of structured models, each built for a different engineering question, joined where a join earns its keep. System knowledge is not a seventh class of model. It is the substrate that lets the six classes work as a system.

2.8.1 A Layered Modeling Substrate

DocAble's models differ in shape on purpose. Some are registries of components and their relations. Some represent state transitions. Some encode contracts or decisions. Some capture quantitative relationships. They share identities, derivations, query surfaces, and traceability where those help, but nothing forces them into a single representation. Read the collection as a modeling substrate, not as one system-knowledge graph.

The substrate is concrete, and it is larger than any one chapter. In DocAble it holds on the order of ninety structured model modules plus several data dialects, organized in layers: a component-identity layer names what exists; a per-component metadata layer annotates each one; orthogonal meta-files sit across the top for deployment topology, inter-service edges, data flow, required environment, state machines, and the governance graph itself. One rule governs all of it — the models are data, not code, and nothing in the substrate imports the system it describes. That decoupling is the point. A model that is the implementation cannot drift from it, and cannot be checked against it either. Holding the map separate from the territory is what makes reconciliation mean something. Figure 2.8-1 draws the layers and the shared spine that joins them.

The unity that matters is semantic, not syntactic. A service named in a structural registry is the same service a flow model references. A work item in an ownership view resolves to the lifecycle and the measurements for that work. A provenance event identifies the operation whose effect it records. Nothing demands the models share a file format or a metamodel; they need only agree on who is who.

That agreement follows one discipline: derive and join; do not repeat. A model joins to its neighbours on a shared key, and it never keeps a second copy of a neighbour's facts. The service-flow model is the endpoint list the access policy is generated from and the call graph is checked against; it holds no private duplicate of the endpoints. A journey model joins to those endpoints by call site rather than copying them. Restate a fact in two models and you own two copies to reconcile by hand — the exact cost the substrate exists to remove. Derivation and join are the cure.

Semantic unity buys a way in. An agent — or an engineer — enters the substrate through the object its task names and traverses outward, following identities across models rather than loading everything. A canonical query surface makes the traversal a query instead of a grep: name a component and ask what it owns, what it depends on, which flow reaches it, what its lifecycle looks like. The agent does not need the whole model. It needs the connected slice that answers the engineering question in front of it. Figure 2.8-2 draws that entry and outward walk.

The substrate even models itself. DocAble's structured models self-classify into a few families keyed by the failure they guard against: state-machine models of async lifecycles, whose failure mode is a race or bad interleaving; structural-registry models of components and topology, whose failure mode is model-to-code drift; contract/decision models of an option space and a selection function, whose failure mode is an incomplete option set or a stale measurement. Each family carries its own verification discipline. The diversity is not untidiness to be resolved into one graph — it is the system knowledge. Different questions want different reductions, and the substrate lets each have the one it needs.

2.8.2 Purpose and Representation Shape

A model sits on two independent axes, and separating them prevents a common confusion. The purpose axis is the engineering question a model answers — the six classes of this Part: structure, behavior, ownership, decision, measurement, provenance. The representation-form axis is the shape the model takes on the page — a registry, a state machine, a contract, a quantitative relation, a table. Purpose and shape do not line up one-to-one, as Figure 2.8-3 shows.

A state machine is not important because "state machine" ranks among some fundamental kinds of knowledge. It earns its place when state and legal transition are the right reduction for the question at hand. The same runs the other way: a file of structured YAML does not become a model merely by being structured. Purpose comes first. Representation follows. Choose the shape that fits the question, and let the question, not the notation, decide.

Leading with purpose keeps MAGE deliberately lighter than a comprehensive model-based-systems-engineering methodology. It borrows the model-based instinct — represent the concern, then reason and check over the representation — without the commitment that every engineering concern inhabit one metamodel or one notation. The substrate takes the model-driven pattern and stops where the pattern stops paying: at the first shape that answers the question.

2.8.3 Keeping the Models Connected to the System

A family of models raises an obvious danger: a second system of record that quietly diverges from the first. The answer is not "never model." It is to engineer the relationship between map and territory so divergence is caught rather than assumed away. Which machinery you reach for depends on which side is authoritative.

A model and the system stay equal by derivation, and derivation runs in one of two directions. Name the direction up front, because the machinery that holds each honest is different. Figure 2.8-4 lays the three cases side by side.

  • Where the implementation is authoritative, derive the model. The code is the truth; the model is a projection of it, reconciled at build time. A component-zone registry reads the real directory tree; a journey's dependency list is induced from its real call sites. The drift check is a reconciler — it re-derives the model from the code and fails on divergence. This is the usual case for a codebase that pre-dated its models, which most of Part II's do.
  • Where the model is authoritative, generate the downstream artifact. The model is the truth; code, configuration, or documentation are emitted from it. The access policy, the service catalog, and the wire-contract types are generated from the service-flow model. The drift check is a freshness and provenance check — the generated artifact carries a header, and a hand-edit or a stale regeneration is a finding.

Where neither side can be fully derived from the other, the move is traceability plus drift checking. Relate each model element to the implementation that realizes it, then check the correspondences a machine can decide. Keep that relation live: resolve the target against current code when the check runs, rather than storing a line number or a symbol name that is itself another snapshot able to drift. A deleted target then surfaces as a finding instead of a stale green edge. In DocAble a traceability gate resolves each model-to-code anchor through a language-aware resolver — one for each source language — and reports every anchor that no longer resolves. Before it existed, most such drifts had no mechanical detection at all; a rename anywhere could silently strand a model's citation.

No single check covers the whole relationship, so read it as two layers. The mechanical layer handles claims a machine can re-derive or test: an anchor still resolves, a declared edge still exists, an observed dependency still belongs to the permitted set. The judgment layer handles the semantics no predicate yet captures: prose whose meaning has quietly moved, an architectural distinction the schema cannot express, an obligation whose reading stays contextual. A human, or another probabilistic reasoner, can inspect the second layer — but that inspection is not deterministic coverage.

Two gaps survive the net, and both mark where judgment is filling in for representation. A semantic miss is a mechanical relation that still resolves while its meaning has changed — the pointer is live, the intent is not. An unmodeled region has no relation to check at all. A recurring gap is a candidate for governance conversion later: add a model, refine the abstraction, or promote the recurring judgment to a check once retiring it is worth the cost. Figure 2.8-5 draws the net and the two ways through it.

This is why an executable model is best read as its schema plus its checked predicates. The schema gives the entities, fields, edges, and states. The predicates state what must remain true over that structure, each named by a stable id and held true at its declared cadence by a checker. Draw the schema and stop, and it can rot the first time the code moves past it. The predicates are not invented for neatness — they come from failures the system actually met. In the DocAble build, the gaps the models caught were violated-but-unstated invariants: a property the system had always needed, never written down, promoted to a checked predicate the moment it broke. Figure 2.8-6 draws that relationship.

Inset — What is an invariant?

An invariant is a property intended to hold over a defined model domain. In a behavioral state machine, it is often a predicate that must hold in every reachable state; in a structural model, that every observed dependency lies in a permitted set; in a measurement model, that a quantity stays below a bound. State both the property and the domain the checker claims to establish it over.

Take a behavioral illustration. A job carries two fields at once — a status of free, leased, or done, and a lease_owner that names the holding worker or is empty. Different steps write the two fields, so they can fall out of agreement, which is exactly why you write the invariant down. "A job is leased if and only if it has an owner" is a predicate over the pair: (status == "leased") == (lease_owner is not None). A free status with a lingering lease_owner is a stale lease; a leased status with no owner is a lost lease. Both become reachable the moment the two writes separate, and both break the predicate. What makes this more than a comment is that the predicate is checked, exhaustively, by a tool:

STATES = product({"free", "leased", "done"}, {None, "worker-1", "worker-2"})
def invariant(s):                                    # leased iff owned
    return (s.status == "leased") == (s.lease_owner is not None)
assert all(invariant(s) for s in reachable_states())  # check every reachable state

None of this proves the model right. No synchronization mechanism establishes universal semantic correctness. A model can be structurally in sync and still express the wrong architecture. A pointer can resolve while its meaning has changed. A schema and its generated client can agree while a live producer emits something else. The guarantee the machinery offers is narrower, and worth stating plainly:

For the surface the model claims, check the correspondence that can actually be decided.

That boundary returns in Part III, where agreement and correctness part company. Synchronization buys agreement between map and territory over a decidable surface. It does not buy correctness of the map's claims. Holding the two apart is what keeps the substrate honest about what it has, and has not, earned. Figure 2.8-7 draws the whole: heterogeneous models joined on a stable identity, not fused into one graph.

2.8.4 Modeling Creates Surfaces for Alignment

A model does not govern the system merely by existing. The structural model can name a forbidden dependency without preventing it. The recovery model can name an illegal transition without rejecting it. The measurement model can represent a budget without stopping the work that exceeds it. The provenance model can specify the evidence an operation should leave without requiring the operation to leave it. Each class makes a property explicit; none, by itself, gives that property force.

The separation is deliberate. Modeling makes an engineering property explicit. Alignment gives selected properties consequence. A property, once represented, becomes a surface something can act on: a constraint that forbids the violation, a sensor that reports it, a validator whose gate blocks on it. The model supplies the property; Alignment decides which properties carry weight and by which mechanism. Figure 2.8-8 draws the whole path, from territory to consequence.

The richer the representation, the richer the properties available to govern. A local static check can constrain a local, syntactic property with almost no explicit modeling. Architectural boundaries, temporal obligations, distributed ownership, provenance requirements, and end-to-end policies each need more semantics on the table before they can be judged at all. This is why the Part's rhythm ran from architecture through time, ownership, permission, quantity, and history to composition: each class put a harder property within reach of a check.

2.8.5 The Handoff to Alignment

Can Alignment exist without explicit models? Yes. A sandbox can forbid network access. A compiler can reject an illegal construct. A test can block a regression against observed behavior. A reviewer can adjudicate a system-level obligation no tool can currently express. These are real forms of authority, and useful systems are built on them. Their limit is what the environment can state and observe without reconstructing the missing semantics each time.

That is the claim this Part has earned. Models enlarge the engineering questions we can reason about and the properties we can make explicit. As representation grows richer, more judgment becomes eligible for analysis and for deterministic enforcement; what stays outside the representation stays probabilistic, human, or both.

The models need not wait for enforcement to be worth their cost. They already pay in reasoning, prediction, composition, and traceability. Part III opens on the separate question of authority — which obligations the environment should hold, by which mechanisms, and with what evidence — and it begins exactly at the boundary this chapter drew: the difference between a map that agrees with its territory and a map that is right.
