# The Book's Language

## Glossary

Agentic software engineering is a fast-evolving topic, and it seems that many concepts have been given overlapping or contradictory names.
Part of the purpose of this book is to articulate coherent vocabulary for the field.
The glossary is divided into four parts: the core ideas of the book, the vocabulary for coding agents and their accompanying phenomena, the terms for the governed engineering environment that stabilizes them, and a few terms from the case study that grounds the book.

## The core ideas

The ideas the whole argument turns on — the two theses, the conversion that grows the environment, the governing metaphor, and the vocabulary of models underneath them.

<!-- index-def: commodity-intelligence -->
**Commodity intelligence.** Machine intelligence that has become abundant, inexpensive, and broadly available. Once intelligence is no longer scarce, engineering reorganizes around judgment, representations, evidence, authority, and governance.

**Governance.** The engineering discipline of encoding judgment into durable mechanisms that autonomous systems inherit automatically. In MAGE, governance includes models, constraints, validators, policies, workflows, and other executable or machine-interpretable artifacts; it is not synonymous with management or compliance.

**Model.** A structured approximation of a system that engineers and agents can reason through instead of reasoning directly over the implementation.

<!-- index-def: model-as-map -->
**Map and territory.** A model is a map, not the running system. Its value comes from omitting detail while preserving the properties needed for reasoning.

**Modeling Thesis.** Externalize engineering knowledge and intent into explicit, structured models so engineers and agents share a compact representation to reason through.

**Alignment Thesis.** Encode engineering obligations into deterministic mechanisms that constrain actions, sense violations, validate evidence, and control admission.

**Governance Conversion.** Converting a recurring failure into a durable engineering mechanism that permanently retires that class of failure.

<!-- index-def: compounding -->
**Compounding.** The accumulation of engineering capital as recurring judgment is converted into durable mechanisms that lower the future cost of change.

**Engineering capital.** The stock of durable engineering mechanisms that reduce the recurring cost of change. Engineering capital grows through governance conversion and depreciates when it no longer fits the system.

**The Printer.** The book's governing metaphor: treat a coding agent like a 3D printer. It builds almost anything you specify — and only what you specify.

**Middle-range theory.** After Merton, a theory intended to explain a bounded class of phenomena rather than universal laws. MAGE is offered in this sense.

## How coding agents work (and fail)

What a fleet of coding agents is, and the ways it comes apart.

**Churn.** The agent-fleet form of velocity decay: an increasing share of effort spent rediscovering context, undoing recent changes, repairing regressions, or reconciling inconsistencies rather than advancing the system.

**Context Window.** The bounded amount of prior conversation and code an agent can hold at once. Fixed the moment you choose the model, it is the sharpest driver of churn when the work outgrows it.

**Foundation model.** The trained model at the bottom of the agent stack. Choosing it fixes the context window and the reasoning ceiling every layer above works within.

**Agentic harness.** The runtime wrapped around the foundation model — Claude Code, OpenCode, and their kin — that feeds it prompts, manages the context window, and hosts the hook, skill, and tool mechanism points.

**Skill.** A reusable body of guidance, with trigger conditions, for a recurring class of agent work.

**Tool.** A deterministic capability exposed to an agent through code or an interface, allowing it to perform an action instead of approximating one through reasoning.

**Fleet.** The set of coding agents working the codebase — the agentic-era workforce this book governs, in place of a team of human engineers.

**Reasoning horizon.** The amount of intermediate reasoning state a task requires held at once to carry it to a correct result. It is a property of the task, not of who reasons — human, agent, or a later architecture.

**Long-horizon task.** A task whose required reasoning state cannot be held losslessly within the available working memory, so completing it forces compression and reconstruction of that state, at some cost in fidelity. A context window instantiates the limit today; the term does not depend on one.

**One-shot Scripting.** The task mode for a small, unsubtle job: describe the process once, get it back in a single pass, no supervision loop.

**Supervised Autonomy.** The task mode for hard, reasoning-heavy work: you supply correctness conditions, tools that determinize the recurring steps, and monitoring to shape the process, rather than taking a single unsupervised pass.

**Loop engineering.** Designing the agent's generate-check-correct loop rather than treating generation as a single pass.

## The Governed Engineering Environment

The environment that holds the fleet to a standard, and the mechanisms it is built from.

**Governed Engineering Environment.** An engineering environment in which policy is encoded into models and mechanisms rather than relying on human memory or repeated inspection.

**Support ratio.** Support-apparatus lines of code divided by production lines of code — a measure of how much governed environment a fleet has built around the product it governs.

MAGE organizes governance mechanisms into four archetypes. Constraints reduce the space of actions that can be taken. Sensors observe the engineering environment and report violations. Validators evaluate whether a candidate artifact satisfies an engineering obligation. Gates control whether work may advance. These categories describe the role a mechanism plays in the engineering environment, not the outcome it ultimately contributes to. A single implementation may participate in more than one role: a linter acts as a sensor, while a gate consumes its result to block a commit.

**Governance Mechanism.** A repeatable structure in the governed engineering environment that encodes an engineering policy. Every mechanism primarily serves one of four archetypal roles: constraint, sensor, validator, or gate.

**Constraint.** Restricts the permissible action space.

**Sensor.** Detects violations of engineering policy.

**Validator.** Evaluates an artifact against an engineering obligation.

**Gate.** Controls whether work may proceed across a workflow boundary.

These archetypes are not mutually exclusive implementations. A single tool may participate in multiple roles. For example, a linter senses a violation, while a commit hook or CI pipeline acts as the gate that prevents the change from advancing.

**Lint.** An automated check that scans code for a banned pattern and fails the commit when it finds one, so a rule holds without a human remembering it.

**Hook.** A hard mechanism the harness fires deterministically at an injection point — before or after the agent acts. The enforcement primitive that lints and gates are built on.

**Invariant.** A predicate over a model that must always hold — the testable claim a gate or a model-checker enforces.

**Model drift.** A model and the code it describes stop agreeing — the divergence a drift gate exists to catch.

**Drift Gate.** A build-time check that fails when a model and the code it describes disagree, keeping the model from decaying into stale documentation.

**Structured (model).** Said of a model written in an explicit, declared shape a machine can read and validate — a schema, not prose — so a build can check the system against it for drift.

**Executable source-of-truth.** An architecture that binds a model and the code that must agree with it tightly enough that a drift gate can block the build the moment they diverge.

**Traceability.** The round-trip join between a model and the code it governs: every model node maps to the code it constrains, and back.

**Pattern.** A reusable solution to a recurring governance problem, documented so engineers can apply it consistently.

**The Model Zoo.** Part 2's tour of the 4+1 architectural views — logical, process, development, physical, scenarios — as executable, drift-gated models, each walked on the real DocAble codebase.

## DocAble specifics

Two mechanisms from the book's running example, DocAble.

**Fidelity Validator.** The mechanism that asserts a remediated document's meaning survived the remediation, catching the case where a file became more accessible and less true to the original.

**Provenance Layer.** The mechanism that stamps every artifact the system inserts, so a document's remediation history can be reconstructed and any single change explained or reversed. (Distinct from model provenance, which tracks what a derived model was generated from.)
