Part 2 — Modeling  ::  Chapter 11

2.7 Scenarios and the Joined Model

2.7.1 The Scenarios View: what the system does for someone

Scenario / joined view · Behavioral

  • Engineering question — Does the whole system still accomplish the user's goal through valid states once the separate models are composed?
  • Model — one goal walked end to end across the other views — the join an engineer performs, not a seventh mega-model the system stores.
  • Property — the goal completes only through a sequence of valid states, with every cross-cut — ownership, authorization, a measured bound, provenance — satisfied at each hop.
  • Quality attribute — end-to-end correctness, the composite of what the other models each guarantee.

Does a real goal actually work, end to end, across everything the other four views project separately? The Scenarios view is the projection over the connected system model that walks a goal across the other four rather than holding the system still. The Logical view says what the system is, the Process view what it does at once, the Development view how it is packaged, the Physical view where it runs — four static portraits, each a slice of the same connected model. The +1 view sets them in motion. A scenario — a use case, a journey — walks a real goal end to end, and in walking it exercises the other four and validates that they hold up. Kruchten made scenarios the +1 for exactly this reason: a view is validated by walking it, and the scenario is the walk.

The scenario is where the models are held honest. The five views are not parallel documentation; they are a reasoning system projected from one connected representation — the Scenarios view removes the burden of validating four independent models separately by exercising all of them through a single engineering goal, and turns the Alignment Thesis back on the views themselves.

One general type anchors the view. A user journey names the interfaces a user moves through and the actions they take to accomplish something of value. Each of this chapter's models embodies that type or serves it, and they are introduced where they enter. The chapter builds to a flagship demonstration — four models joined on a single fact so a product goal reaches all the way to how the deploy rations its tests.

The four models that feed the flagship join each set up their part of the composition, with the full construct-and-invariant treatment of each in the appendix.

2.7.2 The user-journey model

The user-journey model makes the product's journeys first-class typed entities — each an actor pursuing a goal through ordered steps, every boundary-crossing step joined to the endpoint it calls. It assesses dependency correctness: does every step a journey declares have a real call site, and is every real call declared? A call-site drift lint checks both directions. The idea that makes it the join's entry point is that the journey copies nothing — a step's endpoint references the service-flow model, its call-site anchor references the real code, and those two references are the keys the coverage and placement models reach through. Name the journey once and the other models join to it.

Learn more about this governance mechanism: user-journey model.

2.7.3 The agent-orchestration model

The agent-orchestration model is the developer-journey counterpart — the scenarios view pointed at the fleet rather than the user. It models the agent lifecycle (Dispatched→Working→Landed→Tombstoned, with Abandoned and recovery) as a typed state machine, and the orchestrator's own refill-and-bank loop as a journey. It assesses lifecycle soundness: a tombstone before a commit, or a landed agent that never tombstones, is an illegal transition a checker catches. The distinctive move is method parity — the substrate that produces the software is governed by the same tier-derivation and drift machinery pointed at the product, so "is the fleet as checkable as what it ships" is a checked property. It sits in the Scenarios view rather than the Process view because its organizing spine is a goal-directed developer journey — the orchestrator pursuing "land the ratified work, refill the pool" — and method parity is a Scenarios move; the lifecycle state machine is the construct that journey runs on, and its one liveness invariant (a landed agent eventually tombstones) routes to the Process view's temporal checker rather than making the model a Process entity. Its full construct-and-invariant treatment is in the appendix.

Learn more about this governance mechanism: agent-orchestration model.

2.7.4 Journey-criticality → test-placement

This model — the Selector in the join below — derives which environment tier a journey's tests run in from the journey's criticality: a MAJOR part runs the fast local tier and the full staging matrix, a MINOR part runs staging only. The asymmetry is deliberate: local is the scarce, serialized host a developer hits first, so a major path earns a fast-tier local test to catch a regression before it ever reaches staging, while a minor path runs only on the elastic staging fleet where boxes are cheap. It assesses placement soundness. The tier is derived, never stored: a stored tier literal is banned, so you cannot quietly push a major path off the slow local gate to speed a run up. To move it you must demote it to MINOR — a visible edit that says out loud "this path is no longer major." A coverage-floor lint then holds the promise "every major part has a fast-tier test," which makes a green local run mean something. Its full construct-and-invariant treatment is in the appendix.

Learn more about this governance mechanism: journey-criticality test-placement.

2.7.5 Coverage → model-node mapping

Coverage-to-node mapping projects the test suite's coverage onto the model's nodes — states, seams, invariants, journey endpoints — instead of its lines (node coverage over line coverage, as Metrics laid out). It assesses node-coverage adequacy: is every meaning I care about exercised by some test? An untested invariant cannot hide inside a 95% line number here, because the invariant is a node, and a node is either covered or a visible gap. An uncovered node is a backlog item; an uncovered node in the critical subset is a build-blocking gate. In the join below it answers the plain question the criticality floor rests on — are the journey's endpoints tested at all? Its full construct-and-invariant treatment is in the appendix.

Learn more about this governance mechanism: coverage-to-node mapping.

2.7.6 Journey task-closure — asserting the goal completed

The three models above ask whether a journey's test exists, runs, and runs in which tier. None asks what the test asserts at the end. Split the pair the model turns on: a flow assertion says the journey ran — a page returned 200, a card appeared — while a task assertion says the user got the thing they came for. A test built on flow alone can green while the task is broken, the artifact never painted, the file never downloaded. The gap is one hop past the last flow assertion, and it is where a real production break hid — a navigation to the editor route succeeded while the accessibility view it should have shown failed to load. Journey task-closure closes that hop. It promotes the journey's terminal "what works means" out of a review-checklist paragraph into a typed closure post-condition: a small boolean expression over reusable observable predicates, joined by AND, OR, and NOT, "the artifact rendered AND a control is inspectable AND no error-fallback is shown." The leaves come from a shared library a journey subclasses rather than hand-rolling, and each prefers an accessibility observable — a role, an accessible name — because that is how the user perceives that the task is done.

From the expression a pure function derives a closure-strength (TASK_CLOSED, FLOW_ONLY, or DISABLED), stored nowhere by hand. Two leaves are flow-only: navigated to a URL, a route returned 2xx. An expression may reference them, but a closure built only from them derives FLOW_ONLY, and on a major journey that is a build finding — the mechanical form of "a journey test should have caught it." That asymmetry is the model's teeth; Figure 2.7-1 draws the expression tree and the grade it derives. This model assesses closure meaning, the axis its three siblings leave to human review: presence and tier versus the meaning of the terminal assertion. And because the closure is typed rather than prose, the same definition resolves two ways: a browser assertion in the fast local tier, and a headless probe against the pre-promotion canary. That restores "staging catches anything local catches" for the task dimension, a containment the fast post-deploy battery had been blind to because it checks page integrity, never task closure. Its full construct-and-invariant treatment is in the appendix.

Learn more about this governance mechanism: journey task-closure.

2.7.7 Worked join — the journey↔coverage↔deploy-policy composition

The compositional question: watch one fact — a journey is major — travel through four models with nothing said twice, until a product goal reaches all the way to how the deploy rations its tests. The other model pages each show a single model; this one shows them joining, not repeating. Four models compose on one shared key — the journey and its endpoints:

  • the user-journey model (M13) names the journey and its endpoints;
  • the coverage-to-node map (M5) asks whether those endpoints are tested at all;
  • the criticality-to-placement Selector (M6) derives which host tier each test runs on from the journey's criticality;
  • the execution-policy Scheduler (M7) decides how each host runs the tests it was handed — fan out, or serialize.

No model owns another's facts; each joins on the journey and its endpoints.

The three questions the join answers

Three questions the raw deploy scripts and test config cannot answer on their own.

  • Goal-to-gate coverage: does a green local run mean every major journey actually ran? The criticality floor makes "local-green implies every major path was exercised locally" a checked property, not a hope — and journey task-closure sharpens what ran means, proving the terminal assertion closes the user's task rather than merely reaching the last flow step.
  • Placement soundness: is any major journey mis-filed as staging-only? Because the host tier is derived from criticality and stored nowhere by hand, you cannot quietly shove a major path off the local gate; you must demote it to minor, a visible edit.
  • Rationing correctness under cost and resource pressure: does the deploy fan tests out when it safely can, and serialize them only when it must? The Scheduler honors a cost gate everywhere but rations concurrency only where a scarce box demands it, so a single-worker host serializes while an elastic host fans out, from one profile table.

The composite picture

Everything so far has examined models individually. This figure is the first time they cooperate. The join has no single appendix diagram, so this composite is built from the four real panels, adding only the join edges between them; read it left to right, in Figure 2.7-2.

The invariants the join spans

The join's invariants span all four models, collected in Table 2.7-1. All are safety properties; the liveness that concurrency hands the fleet is stated and routed in the Process view, whose form-match rule sends a liveness invariant to a temporal checker.

2.7.8 The Joined Model

2.7.9 The views pay off when they join

The five views earn their keep separately. The Logical view answers a structural question, the Process view a concurrency one, the Development view an ownership one, the Physical view a placement one, and the Scenarios view a goal. Each is a projection: it keeps the entities and relations its question needs and drops the rest. But a real engineering task rarely stays inside one view. It starts in one and reaches across the others. The larger value shows up there — not in any single projection, but in what the projections do when they meet.

2.7.10 A request walks the connected slice

Trace a single request. A user asks for a feature. The Scenarios view names the journey that delivers it. That journey names endpoints, and the endpoints resolve in the Logical view to components and the dependencies among them. Those components run as services and concurrent workers in the Process view, ship inside packages someone owns in the Development view, and land on deployment targets in the Physical view. Tests, invariants, ownership, and policy attach along the walk. The agent never carries the whole codebase. It carries the connected slice the question actually touches, and the walk is what assembles that slice.

2.7.11 The graph is what lets the views meet

The walk works only because every view names the same entities. A service in the Logical view is the same service the Process view schedules and the Physical view places. They agree because they cite one identity, not because someone kept five diagrams consistent by hand. That is the work the system knowledge graph does. The graph is not a sixth picture standing beside the five views. It is what lets the views meet on stable identity. Each projection discards what its own question ignores; the joins recover exactly the neighboring facts the next question needs. Five independent diagrams drift independently. Five projections over shared entities join, reuse facts, and expose a contradiction the moment one appears.

2.7.12 Where Modeling meets Alignment

This is also where the Modeling Thesis meets the Alignment Thesis. While a relation lives only in someone's head — service A consumes queue B, journey J reaches endpoint E, worker W may run beside worker X — nothing can check it. Write the relation down explicitly, and the environment gains something to check against: only a worker of this class may consume that queue; every endpoint this journey names must exist; these two workers must never hold the same lock. Making the relation explicit is the Modeling move. Attaching the predicate is the Alignment move. The richer the representation, the more of engineering judgment shifts from probabilistic reasoning toward a check the build can run on its own.

So a model earns its place twice. It compresses the system into a slice a bounded reasoner can hold, and it creates a surface on which an obligation can become executable. The first payoff is why this Part built the models. The second is why the next Part can act on them.

This Part supplied the world the fleet reasons through; the next Part gives that world authority. It takes the relations this Part made explicit and teaches the environment to insist on them.

2.7.13 The mental toolbox

The Part opened with one question and promised a table at its close. Here it is. You came into Part II able to say why models matter; you leave it able to choose one. We did not pick these models because a methodology prescribed five boxes to fill — we began with what an engineer needed to know, and each need selected a representation. Work back through the models this Part built on DocAble — structure and ownership, behavior and execution, measurement and documentation — and a small, reusable toolbox falls out, collected in Table 2.7-2. For each engineering concern it gives the model that answers it, the property the model then lets you state, and the quality attribute that property serves. The columns run in the order the opener named: name what you need to reason about, reach for the model, read off the property, and land on a quality an engineer already knows how to want.

The test of the Part is not whether you can recite these rows for DocAble. It is whether you can fill the same table for a system of your own.

The flagship earlier in this chapter walked the join move on the fleet's own models. The same move composes the six product models above into a single end-to-end scenario: a document arrives, is planned and split, remediated under a single owner with every change stamped, validated and merged, its evidence derived, and delivered — one goal walked across all six, each hop governed by a different model. The system keeps the six models separate, each pinned to its code by a drift check; the scenario is the join you perform across them, not a seventh mega-model it stores.

2.7.14 What each model hands forward

The join showed the models meeting; the hinge above showed why an explicit relation can carry a predicate. The handoff makes it concrete, per model. Part II owns the chain through the property and stops there on purpose — stating "only declared edges are legal" is a different act from refusing the undeclared one, and refusing it is the next Part's work. So each model hands forward a typed seam, collected in Table 2.7-3: the property it owns, the quality that property serves, and the authority surface the next Part will build to enforce it — named in role and shape so the next Part is free to design the mechanism. Those surfaces are the four Alignment archetypes: a constraint that makes the violation unexpressible, a sensor that reads reality back out of the code, a validator that compares reality to the model, and a gate that blocks the divergence before it ships.

Table 2.7-3. The Modeling→Alignment handoff — the property each model hands to the next Part and the authority surface (constraint · sensor · validator · gate) that will enforce it. Two cells name a declared gap rather than a gate.

The next Part confronts this; this Part does not fabricate a central gate.

Two cells name a gap, not a gate, and the gap is the honest part. The measurement model is fully built and instrumented, yet its cost ceiling is report-only in production — sensed, logged, never enforced. And the end-to-end scenario has no single gate: its correctness is the conjunction of the six per-model surfaces, asserted together only by a whole-pipeline smoke, with no typed state-graph walked to prove every path reaches completion through legal states. Both are modeled but not yet governed. Naming them is the point. A property an engineer can state, and a build cannot yet enforce, is not a hole in the book; it is the book pointing at where the next Part, and the real work, begins.

2.7.15 The Scope of Modeling

2.7.16 This book's boundary

MAGE does not replace established modeling disciplines. The models in this Part are deliberately lightweight — enough structure to answer recurring engineering questions, support agent reasoning, and permit mechanical checks. When the engineering question requires stronger analysis, use the established formalism built for it. This book teaches one discipline — keep the map equal to the territory, so the model stays the interface the fleet reasons through — and points to where each concern goes when a sketch stops being enough. Modeling software systems is a deep field with decades of literature behind it; the rest of this chapter is a map to it.

2.7.17 When a sketch graduates

There is a moment when a working sketch stops carrying its weight, and it is worth learning to see it coming. A sketch should become an analytic model when the quality goal hardens into a measurable constraint. The sketch is fine while the goal is a soft preference; the analytic tool earns its cost the moment the goal becomes a constraint you can measurably fail.

The signal is the goal itself hardening. "Fast is good" is a preference, and a napkin sketch of the call graph carries it fine. Sharpen it to "every frame must finish inside 16 milliseconds" and you have a real-time system — you now need schedulability analysis, not a vibe about which parts look slow. "Less memory is nice" is a preference too. Sharpen it to "this must fit on a board with 64 kilobytes of RAM" and you need an honest memory model, budgeted byte by byte. The concern did not change; the preference became a constraint, and the day a constraint can fail is the day the sketch has to graduate. Learn to feel that hardening, and the rest of this chapter is a map of where to go once you feel it. Graduating a sketch is the same motion the Part's ladder describes from the other side: you climb a rung when a recurring engineering question makes the next capability worth its cost.

Inset — Protocols and TLA+

When a property is not about one component but a protocol — many actors interleaving over time, each taking steps in an order you do not control — a single state assertion is not enough, and even a bounded walk of one component misses the cross-actor races. You specify the protocol in a temporal-logic language (TLA+ is the best-known), stating the actors, their steps, and the safety and liveness properties the interleaving must satisfy. A model checker then explores every interleaving the actors can produce under the stated model and bounds and either establishes the properties for that model or hands you a counterexample trace. This is the heaviest tool the Part points to, reserved for the invariant whose failure lives in a schedule no example test will ever pick — a distributed reservation, a lease-and-preempt loop, a two-phase hand-off between services.

2.7.19 Models tier; reasoning descends

One scaling move underlies every model here. The models tier — system, subsystem, component, module, implementation, each a coarser or finer grain of the same territory. A finite reasoner does not hold them all at once; it enters at the level its task needs and descends only as far as the work forces, reading the system model to place a change, dropping to a component's invariants when it touches that component, reaching raw code last.

Every tool this chapter points to — UML, TLA+, queueing theory — is another way to keep some model honest against some territory, and to reason at the coarsest grain the task allows before dropping to a finer one. Model at the coarsest level that answers the engineering question; descend toward implementation only when the question requires it.

2.7.20 Can alignment exist without models?

One question sits under everything this Part has built, and it is worth answering before the next Part takes these models up as authority: can alignment exist without models at all?

Yes. Natural-language prompts, briefs, examples, and supervision guide agents successfully, sometimes spectacularly. MAGE does not claim otherwise. A prompt is a representation too, only a weak one: implicit, local, untyped, mostly opaque to tools, and hard to compose, validate, or keep true as the system moves. It can steer a build. It cannot, on its own, state, compose, validate, and enforce the obligations engineering assurance rests on.

So the claim is narrow, and worth stating exactly. Implicit or weakly structured representations support correspondingly weak forms of authority. Explicit models are not a prerequisite for useful software; they are the substrate on which progressively stronger guarantees become possible. Without explicit models, alignment cannot become authoritative.

Read the whole argument as one line.

Natural-language intent can guide autonomous work. Explicit models transform that intent into an engineering substrate. Alignment transforms that substrate into authority.

That honest reading closes the argument. This Part walked each kind of model on real code and showed the drift gate that holds each one to the code, so the map cannot quietly rot away from the territory. What it has not shown is how you reach that state from a codebase that carries none of it. The models are built; the next Part gives them authority.
