# Behavioral Models: What May Happen?

A structural model describes relationships among parts of a system. A behavioral model describes how the system acts or changes over time. Depending on the question, we might model messages exchanged in a protocol, steps in a workflow, or a quantity that changes continuously. Here we focus on a common choice for software systems: discrete states and the events that move a system between them. With such a model, we can ask whether a job can finish before it starts, or whether a job that starts will ever finish.

## States, Transitions, and Behavioral Analysis {#states-transitions-and-behavioral-analysis}

As with structural models, we begin with a small example, then examine the properties and analyses it supports before turning to DocAble.

### Constructing a Behavioral Model {#constructing-a-behavioral-model}

A service processes jobs that may be waiting, running, completed, or failed. If a job reports completion before its work finishes, the service may deliver an incomplete result to the user as though it were finished.

**Question.** Can a job report completion before anyone has started it? To find out, we need to know where a job begins, which event starts it, and from which states the service permits completion. We can set aside the database schema, scheduling algorithm, and retry machinery for now. If a job can finish too early, we ought to be able to see how in a model small enough to trace by hand.

<!-- point: the-reduction-is-what-makes-behavior-checkable | Reducing a service to states and transitions turns "can it reach a state it should never occupy?" from a reconstruction over scattered handlers into a question a person or tool can answer. -->

Four states and three events suffice. Let \(S=\{\mathrm{IDLE},\mathrm{RUNNING},\mathrm{DONE},\mathrm{FAILED}\}\) be the states, with each job starting in \(\mathrm{IDLE}\). The events are \(E=\{\mathrm{start},\mathrm{finish},\mathrm{fail}\}\). We still need to say which events are permitted in each state and where they take the job.

<!-- point: transition-semantics-can-construct-intended-behavior | A partial transition function defines the effects of start, finish, and fail in a four-state job lifecycle. Undefined pairs admit no transition, and the same function can guide implementation, interpretation, or test generation. | terms: semantic-commitment, modeling-principle -->

What an event does depends on the state in which it occurs. The following partial function \(\delta:S\times E\rightharpoonup S\) gives the next state for each permitted pair:

<!-- eq: \begin{aligned} \delta(\mathrm{IDLE},\mathrm{start}) &= \mathrm{RUNNING},\\ \delta(\mathrm{RUNNING},\mathrm{finish}) &= \mathrm{DONE},\\ \delta(\mathrm{RUNNING},\mathrm{fail}) &= \mathrm{FAILED}. \end{aligned} -->

**Semantics.** Each entry specifies the next state for a permitted state–event pair. An undefined pair admits no transition. Both \(\mathrm{DONE}\) and \(\mathrm{FAILED}\) are terminal.

**Analysis.** Try \(\mathrm{finish}\) from \(\mathrm{IDLE}\). There is no entry for that pair, so the model forbids the transition. Now try \(\mathrm{start}\) followed by \(\mathrm{finish}\). The first entry takes the job to \(\mathrm{RUNNING}\), from which the second takes it to \(\mathrm{DONE}\).

The model settles when a job may finish while leaving the engineer free to choose how to implement it. An agent might store the state in a database, manage jobs through a queue, or use an in-memory scheduler. A state-machine interpreter can consult the entries directly. A test generator can use those same entries to produce a sequence of events and predict the state the implementation should report afterward.

A failed attempt need not mean a failed job. [ref:canonical-behavioral] extends the four-state example with retries, using Pending for IDLE and Succeeded for DONE. In this richer model, a repairable failure moves a running job into Retrying while the retry budget remains. Let \(r\) count retries already started, initially zero. Starting another attempt increments \(r\) and returns the job to Running. A nonrepairable failure, or a failure after all \(N\) retries have been used, takes the job to Failed. A job can therefore succeed after an earlier attempt failed, while the retry budget bounds the additional attempts.

### Properties and Analyses {#behavioral-properties-and-analyses}

Behavioral models let us investigate which states a system can reach, which sequences of events are permitted, and whether required outcomes eventually occur. These questions distinguish properties of individual states from properties of complete executions.

<!-- point: semantics-are-states-and-permitted-transitions-and-the-omissions-are-the-obligations | A behavioral model represents states and transitions; it can specify allowed behavior or describe behavior to be checked against a requirement. Safety and liveness properties ask different questions over the admitted executions. -->

Starting at Pending and following permitted arrows gives us one possible execution of the model. Trace Pending, Running, Retrying, Running, Succeeded. That path shows that success after a retry is *reachable*. Here the arrows specify behavior the service permits. In a model derived from an implementation, the same path would describe behavior to evaluate against a requirement.

One path can establish reachability, and one bad path can disprove a **safety** requirement. Suppose the requirement is that a job must enter Running before it reaches Succeeded. Finding one execution that does so leaves all the other executions to consider. Instead, search for a path from Pending to Succeeded that avoids Running. Any such path would show exactly how premature completion could occur; in the figure, there is none.

A job can obey every ordering rule and still never finish. The requirement that every started job eventually succeeds or fails is a **liveness** property. A limit of three retries bounds the number of attempts, but says nothing about how long a worker may remain in Running. Observing one slow attempt cannot settle whether it will ever finish.

<!-- point: behavior-has-a-long-repertoire-of-state-transition-representations | State-transition models make lifecycle and recovery questions explicit; state machines, labeled transition systems, and statecharts represent behavior, while temporal specifications state properties over executions. -->

To investigate progress, we must say what can keep a job waiting and what allows it to resume. If the service relies on a timeout, represent what happens when it fires and state the assumption that it will be delivered. We can then ask whether any execution under those assumptions can avoid both terminal states indefinitely. Temporal model checking evaluates such requirements over executions [cite: baier-katoen2008].

Linear Temporal Logic (LTL) provides notation for properties over executions [cite: baier-katoen2008]. For one job, let \(\mathrm{Started}\) mark the state immediately after execution begins, and let \(\mathrm{Succeeded}\) and \(\mathrm{Failed}\) denote its terminal states. The requirement that every start eventually leads to termination can be written as

<!-- eq: \mathrm{G}\bigl(\mathrm{Started}\rightarrow\mathrm{F}(\mathrm{Succeeded}\lor\mathrm{Failed})\bigr). -->

Here \(\mathrm{G}\) means “always” and \(\mathrm{F}\) means “eventually”: whenever the start marker holds, the same job must eventually succeed or fail. For this interpretation, a finite execution that cannot continue remains in its final state. Whether the formula holds depends on the transitions and environmental assumptions represented in the model. For a more complex lifecycle, statecharts can organize related states hierarchically and represent concurrent activity [cite: harel1987].

We now turn to two behavioral models from DocAble: one specifies the order in which a recovered artifact may be published, and the other distinguishes a worker's current claim from one that has expired.

## DocAble: Job Lifecycles and Recovery {#docable-job-lifecycles-and-recovery}

DocAble distributes document accessibility work across workers that may fail or lose their assignments. Recovery raises two behavioral questions beyond the simple job lifecycle in [the preceding subsection](2.4-behavioral.html#states-transitions-and-behavioral-analysis). Can a worker publish a recovered result in an unsafe order? Can a former owner return and interfere with a newer assignment? The first requires a model of publication states; the second requires a model of ownership across competing workers.

### Publishing a recovered result {#publishing-a-recovered-result}

A worker recovering a document job may have a corrected artifact available locally before uploading it to persistent storage. If the worker updates the database record first and then crashes, the record can point to an artifact that other workers cannot retrieve. What ordering of publication and database updates prevents this failure?

**Recovery-ordering model · Behavioral**

- **Engineering question** — In what order may recovery publish an artifact and update the record that refers to it?

<!-- -->

- **Model** — a transition system over the recovery lifecycle; the decisive fact is a transition that does *not* exist.

<!-- -->

- **Property** — the database record may refer to the fallback artifact only after that artifact has been uploaded to persistent storage.

<!-- -->

- **Quality attribute** — data integrity; crash-safety.

<!-- point: the-decisive-fact-is-an-absent-edge-between-staged-and-durable | The recovery obligation lives in the gap between local staging and durable publication: there is no direct FALLBACK_STAGED to DB_UPDATED edge, so the model excludes executions in which the record points at a not-yet-durable artifact. -->

[ref:recovery-ordering-model] represents the recovery operation using three states. In `FALLBACK_STAGED`, the corrected artifact exists locally; in `FALLBACK_UPLOADED`, it has been published to durable storage; and in `DB_UPDATED`, the database refers to it. The permitted path passes through all three states. The prohibited transition from `FALLBACK_STAGED` directly to `DB_UPDATED` represents the unsafe ordering: the database would refer to an artifact that had not yet been published.

<!-- label: recovery-ordering-model -->
<!-- figure: assets/recovery-ordering-model.svg | *Recovery-ordering model.* The artifact must be persisted before the database may refer to it. The crossed path illustrates the prohibited shortcut from `FALLBACK_STAGED` to `DB_UPDATED`. -->

To check the ordering property, search for an execution that reaches `DB_UPDATED` without first visiting `FALLBACK_UPLOADED`. The three-state model has no such execution. In a larger lifecycle, checking only for the direct forbidden transition would be insufficient: another sequence of transitions might reach `DB_UPDATED` while bypassing publication. This is a safety property, not a liveness guarantee. A worker could wait or retry indefinitely without violating the ordering requirement.

<!-- point: the-recovery-ordering-is-a-slice-of-a-larger-lifecycle | The recovery model keeps the states needed to check publication order; a fuller job lifecycle can support broader workflow questions when it includes the relevant transitions. -->

The three-state recovery model is a reduction for checking publication order. DocAble’s fuller job lifecycle includes queued, leased, remediating, and completed or failed states. That model can address broader workflow questions when it includes the relevant transitions; the smaller recovery model keeps only what the ordering question needs.

### Distinguishing a current owner from a returning one {#distinguishing-a-current-owner-from-a-returning-one}

<!-- point: ownership-has-a-long-vocabulary-of-claims-and-leases | Concurrent workers can acquire, lose, and regain rights to a job; locks, leases, capabilities, and claims express different aspects of access and ownership, which the model selects according to the question. -->

DocAble leases each in-flight job to one worker. Suppose worker A stalls and its lease expires. Worker B acquires the job, but A later returns and attempts to release its old assignment. How can the system distinguish A’s obsolete claim from B’s current one? [ref:ownership-constructs] distinguishes several constructs for representing access and ownership. DocAble combines two: a claim records the assignment, and a lease limits its lifetime.

<!-- label: ownership-constructs -->
<!-- table: *Constructs for access and ownership.* Locks, leases, capabilities, and claims express different aspects of a worker's right to act. [short: Constructs for access and ownership] -->
| Construct | What it expresses |
|---|---|
| Lock | Coordinates access to a resource. An exclusive lock admits one holder at a time. |
| Lease | Grants a right for a limited period; expiry can make that right available for reassignment [cite: graycheriton1989]. |
| Capability | Carries authority to perform specified operations on a resource; that authority need not be exclusive. |
| Claim | Records a worker’s assignment to a job and the conditions under which that assignment is valid. |

<!-- point: leased-iff-owner-is-the-models-definition | A job is leased exactly when it has an owner; the two are the same fact from two sides, so the model represents ownership as the presence of a current claim — this is what "leased" means, and it sets up the invariant that follows. -->

The model represents ownership through a current claim relating a worker to a job. A job is leased exactly when it has such a claim; ownership and lease status are not separate facts that can disagree within this model. Each claim also records a generation and a lifetime. Expiry makes the job available for reassignment, and a new assignment advances the generation. The generation distinguishes successive claims even when they concern the same job.

**In-flight lease · Ownership**

- **Engineering question** — Who currently owns this in-flight work, and can a returning stale owner disturb the current claim?

<!-- -->

- **Model** — a claim relating a worker to a job, stamped with a generation and a lifetime; reclaim advances the generation.

<!-- -->

- **Property** — a stale claim cannot clear or supersede the current one.

<!-- -->

- **Quality attribute** — correctness under concurrency; crash-safety.

<!-- point: the-epoch-generation-makes-a-stale-release-inapplicable | Suppose A holds generation 7, stalls, and is reclaimed; the job is re-leased to B at generation 8; a late release from A carrying generation 7 must not clear B's generation-8 claim, and the generation makes that decidable. | terms: soft-vs-hard-governance -->

[ref:in-flight-ownership-states] follows one possible execution. Worker A acquires generation 7, then stalls until its lease expires. Worker B reclaims the job at generation 8. When A returns and attempts to release generation 7, the operation must not clear B’s current claim. The job remains owned by B at generation 8. The generation number makes the stale operation distinguishable from a release by the current owner. Without that distinction, A’s delayed release could clear B’s valid assignment.

<!-- label: in-flight-ownership-states -->
<!-- figure: assets/in-flight-ownership-states.svg | *Ownership under contention.* Worker A’s generation-7 claim expires and worker B acquires generation 8. A later release from A cannot clear B’s current claim. Recording the generation makes stale operations distinguishable from operations authorized by the current owner. -->

<!-- point: a-claim-carries-the-facts-that-make-contention-decidable | A claim binds a holder to a resource and carries which holder, which generation of claim, and when it expires — the generation being what tells a current claim from a superseded one — and because the hard failures live in interleavings, the characteristic analysis is state-space exploration with invariant checking. -->

The illustrated execution is only one possible ordering of events. To investigate the invariant, explore the interleavings of lease expiry, reassignment, and delayed release. At each reachable configuration, check whether a release from an earlier generation can clear or supersede the current claim. A counterexample would identify an event sequence that violates ownership; checking the reachable configurations establishes the property within the model’s declared scope.

The publication model separates a local artifact from a durably stored one. The ownership model separates a current claim from a superseded one. In each case, the useful addition is a distinction that changes whether a state change is acceptable. The models make those distinctions available for analysis; the later Alignment chapter examines the mechanisms that enforce them.

<!-- point: the-lease-model-omits-the-processing-topology | The model omits the processing topology: ownership, generation, lifetime, and reclamation are the consequential properties, and the implementation later changed how the job's work is partitioned without invalidating the model — the pointers to the code changed, not the model. -->

Notice what this model omits: the processing topology. Ownership, generation, lifetime, and reclamation matter to the question of who controls a job; how the job's work is partitioned does not. DocAble's implementation changed over time to improve performance while preserving those ownership semantics. We changed the pointers to the code, but not the model. The ownership properties could therefore remain invariants across those changes. The inset shows how a relationship built into the model can become an invariant when an implementation stores its parts separately.

> #### Inset — What is an invariant? {#inset-invariant}
>
> An **invariant** is a property required to hold over a declared domain of states, structures, or observations. In a behavioral state machine, the invariant may be a predicate that must hold in every reachable state; in a structural model, it may require every observed dependency to belong to a declared set; in a measurement model, it may require a quantity to remain within a hard capacity bound. State both the property *and* the domain the checker claims to establish it over.
>
> Take a behavioral illustration. A job carries two fields at once — a `status` of `free`, `leased`, or `done`, and a `lease_owner` that names the holding worker or is empty. At the model level, leased-iff-owner was a definition; an implementation that represents the two sides as separately written fields turns it into a property that can fail, which is exactly why you write the invariant down. "A job is leased if and only if it has an owner" is a predicate over the pair. A `free` status with a lingering `lease_owner` is a stale lease; a `leased` status with no owner is a lost lease. Separating the two writes can make either inconsistent state reachable, and both break the predicate. For a finite behavioral model, the following pseudocode checks the predicate in every reachable state. The model must specify initial states and transitions for both fields.
>
> *Pseudocode*
>
>     reachable = exploreAll(jobModel)
>
>     for state in reachable:
>         assert (state.status == "leased") ==
>                (state.lease_owner != None)
>
> Here `exploreAll` denotes exhaustive exploration of the model, not a particular programming API. A failed assertion identifies a reachable state that violates the invariant. The check establishes the property over the model’s reachable states, not automatically over the implementation.

<!-- point: the-lease-answers-ownership-behavioral-and-measurement-questions-at-once | Read as ownership the lease says who controls a job; read as behavioral it traces a claimed-held-expired-reclaimed lifecycle; counted, it measures how much work is in flight — one representation, three questions. -->

A lease illustrates how one representation can answer several classes of question. Its owner identifies who currently controls a job. Its generation and lifetime distinguish current claims from stale ones and support reasoning about expiry and reclamation. Counting the current claims across jobs gives a measurement of how much work is in flight. These questions concern ownership, behavior, and capacity, yet they draw on the same represented facts.

<!-- point: overlap-confirms-the-classes-sort-questions-not-data-structures | The overlap follows from the distinction introduced at the chapter's opening: model classes identify engineering questions, not mutually exclusive data structures — the observation the closing section builds on to connect the models. -->

The overlap follows from the distinction introduced at the opening of the chapter: model classes identify engineering questions, not mutually exclusive data structures. One representation can serve several questions when it preserves the facts each requires. {{sec:scenarios-and-the-joined-model}} develops this idea further by connecting models through shared identities.
