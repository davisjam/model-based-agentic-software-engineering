# Making Models Executable

<!-- point: an-executable-model-is-an-active-engineering-artifact | An executable model participates directly in computation and can be mechanically reconciled with the system — an active engineering artifact, not a parallel description. | terms: model-as-map, executable-source-of-truth, drift-gate -->
<!-- index-def: model-as-map -->
A model reduces the amount of system detail an engineer or agent must reconstruct to answer a question.
In this book, an **executable model** earns a stronger claim: its structure participates directly in
computation — querying, derivation, generation, analysis, or checking — and the relationships it claims
to represent can be mechanically reconciled with the system. *Executable* here does not require the model
itself to be a simulator; it means the model is an active engineering artifact rather than a parallel
description.

<!-- point: docable-supplies-the-running-examples-part-v-gives-it-in-full | DocAble supplies the running examples; Part V gives the full system. Here we extract only the machinery that makes the teaching models trustworthy. | terms: model-zoo, drift-gate -->
<!-- index-def: model-zoo -->
DocAble supplies the running examples; this chapter extracts the machinery required to keep the
teaching models connected to the system they represent.

<!-- point: every-model-in-part-2-is-one-executable-schema | Every Part-2 model is one executable schema, worn several ways. | terms: executable-source-of-truth, model-zoo, drift-gate -->
<!-- slogan: one-trunk-five-views -->
> ### The Executable Model Pattern {#executable-model-pattern}
>
> Every executable model in Part II is described through the same six questions:
>
> - **What entities and relations** does it represent — which slice of the system knowledge graph?
> - **What engineering question does it make cheap and reliable to answer?**
> - **What invariant** must hold?
> - **How is it derived** — from the code, or the code from it?
> - **How is its claimed correspondence or property checked, and at what cadence?**
> - **What drift** does the check prevent?
>
> The first question fixes the model as an explicit slice of the knowledge graph the last two
> chapters built; the other five are the executable-model pattern the rest of the book develops.

## Why models are cheaper to keep alive

<!-- section-terms: thesis-modeling, executable-source-of-truth, mbse -->

<!-- point: what-commodity-intelligence-changes-is-maintenance-economics | Models are not newly useful; commodity intelligence changes part of their maintenance economics — the repetitive upkeep a coding fleet performs cheaply and often. | terms: mbse, model-drift, executable-source-of-truth -->
Models are not newly useful. What commodity intelligence changes is part of their maintenance economics.
In code-centric workflows, every additional representation creates a standing obligation: derive it,
reconcile it, regenerate its consumers, repair its references when the implementation moves, and notice
when the representation no longer describes what it claims to describe. Much of that work is repetitive. A
coding fleet can perform it cheaply and often.

<!-- point: the-design-cost-remains-only-the-upkeep-got-cheaper | The design cost remains — someone still decides which question deserves a model; what became cheaper is the repeated upkeep, which makes repository-native models practical. | terms: mbse, executable-source-of-truth, map-and-territory -->
That does not remove the design cost. Someone still decides which question deserves a model, which facts
are authoritative, what abstraction to use, how derivation runs, and which disagreements matter. What
becomes cheaper is the repeated upkeep after those decisions have been made. That change makes
repository-native models practical in places where a manually synchronized secondary artifact would have
been difficult to justify.

> ### Inset — What MAGE takes from MBSE and SysML {#inset-sysml}
>
> Model-based systems engineering is a much larger discipline than this book attempts to teach. MAGE
> shares its central engineering instinct: important properties should live in explicit representations
> that support analysis, traceability, and verification rather than only in implementation or prose.
> SysML, for example, provides typed constructs for system structure, requirements, constraints, and
> verification relationships [cite: friedenthal-sysml]. MAGE borrows that concern while using
> deliberately lightweight, repository-native representations suited to agentic software work. Where
> code and model describe the same fact, derive or reconcile the relationship mechanically rather than
> relying on a manually synchronized second copy.

### Example — Siemens
Siemens runs on executable models as a matter of course. SysML and CAD, simulation models, virtual
ECUs, and a bill-of-materials structure are the artifacts engineers actually work in; code is
generated from them and verification is derived from them. The executable model is the ordinary
medium of the work — a model sitting upstream of the
implementation rather than beside it.

### Example — Spotify
Spotify makes a narrower executable model pay at fleet scale. Its System Model and Backstage catalog
carry dependency and endpoint lineage with stable identities, and the architecture diagrams are
generated from that metadata rather than drawn by hand. When a migration targets an endpoint, the
fleet acts through the model of the estate, not the raw code — an executable representation driving
real change across thousands of repositories.

### Example — DocAble
DocAble is one software implementation of the pattern, and its distinctive slot is the typed
intermediate representation[note: The terminology is deliberate. Compiler pipelines have long introduced intermediate representations that expose the information a particular analysis or transformation needs while suppressing irrelevant source-level detail [cite: appel-compilers]. MAGE reuses the same representational move at the engineering-system level, without claiming that every model is a compiler IR — some are, most are not.]: every remediation is a node in a typed IR the validator walks, so a fix
is an object a gate can check rather than a diff to eyeball. DocAble additionally uses blocking drift
checks to fail the build when selected model/code relations disagree.

## The shared machinery beneath the views

<!-- section-terms: executable-source-of-truth, drift-gate -->

<!-- point: the-trunk-is-the-shared-machinery-that-makes-every-view-executable | Shared machinery makes every view executable and drift-proof. | terms: executable-source-of-truth, drift-gate, trunk -->
<!-- index-def: executable-source-of-truth -->
Most of the catalogue's method models belong to no single view. They are the machinery that makes
*every* model executable and drift-proof, introduced once here and revisited where each view needs it:

- **The executable source-of-truth** — the pattern behind every model, defined at the top of this
  chapter: the model is structured data agents read to navigate, generators consume to emit the
  artifacts that must agree with it, and drift gates block on divergence.
- **The drift and parity gates** — the lints and tests that enforce model-and-reality parity in both
  directions, so no model drifts unilaterally.
- **The agent-first harness** — a thin hand-rolled layer over frozen records: adopt the genre's
  schema, skip its heavyweight runtime.
- **The read and generate surfaces** — one canonical query API over every model, and generators that
  emit real artifacts *from* the models, each provenance-headed so a hand-edit is caught.

The shape is familiar from compilers and model-driven development: maintain a representation with explicit semantics, let transformations consume it, and derive downstream artifacts rather than independently restating the same facts [cite: appel-compilers] [cite: brambilla2017]. MAGE extends the pattern beyond program translation. A source model may generate policy, documentation, configuration, validation inputs, or code. The derived artifact must remain downstream of the authority that produced it.

Three rules organize how any of them stays true.

### Derive and join; do not repeat

<!-- section-terms: derive-and-join, join-key -->

<!-- index-def: derive-and-join -->
<!-- point: a-model-is-derived-and-joined-never-repeated | A model is derived and joined, never repeated. | terms: derive-and-join, join-key -->
A model here is **derived** — from the code, or the code from it — never kept beside the code as a
parallel document. And it **joins** to its neighbours on a shared key rather than restating them.
The service-flow model *is* the list the access policy is generated from and the call graph is
checked against; it holds no second copy of the endpoints. The journey model *joins* to those
endpoints by call-site rather than copying them. Restate a fact in two models and you are back to
keeping two copies in sync by hand. Derivation and join are the cure.

### State the derivation direction

<!-- section-terms: derivation-direction, model-from-code, model-to-code -->

<!-- index-def: derivation-direction -->
<!-- point: name-the-direction-of-derivation-up-front | Name the direction of derivation up front. | terms: derivation-direction, model-from-code, model-to-code -->
A model and the code stay equal by derivation, and derivation runs in one of two directions. The
machinery depends on the direction.

<!-- index-def: model-from-code -->
<!-- index-def: model-to-code -->
- **Model-from-code (induce and reconcile).** The code is authoritative; the model is a projection
  of it, reconciled at build time. The component-zone model reads the real directory tree; a
  journey's dependency list is derived from its real call sites. The drift gate is a *reconciler*:
  it re-induces the model from the code and fails on divergence. The usual case for a large codebase
  an agent must operate.
- **Model-to-code (specify and generate).** The model is authoritative; the code, config, or docs
  are generated from it. The access policy, the service catalog, and the wire-contract types are
  emitted from the service-flow model. The drift gate is a *freshness and provenance check*: the
  generated artifact carries a header, and a hand-edit or stale regeneration is a finding.

<!-- point: most-models-are-model-from-code-because-the-codebase-came-first | Most models are model-from-code; the codebase came first. | terms: model-from-code, model-to-code -->
Most of Part II's models are model-from-code, because the codebase pre-existed them. The service-flow
model is the clearest model-to-code case, and it is bidirectional — some fields generated to code,
others reconciled from it — which is why its gate checks both directions. Each model page names its
direction.

### Separate observed fact from authored intent

<!-- section-terms: model-from-code, drift-gate -->

<!-- point: extraction-says-only-what-is-authored-intent-says-what-ought | Repository-graph tools show the descriptive half; extraction alone says only what IS. Deciding what is permitted, what a component ought to own, or which invariant to preserve requires authored intent. | terms: model-from-code, drift-gate -->
Repository-graph tools demonstrate the descriptive half of the pattern: parse source into a persistent
graph so an agent can traverse dependencies and identities without repeatedly rereading files. Such
graphs can reduce navigation work substantially, but extraction alone says only what *is*. It cannot
decide whether a dependency is permitted, whether a component ought to own a responsibility, or which
invariant the architecture intends to preserve. Those claims require authored intent.

> ### Inset — Repository-graph tools {#inset-code-graph}
>
> A repository-graph tool parses the codebase into a persistent graph an agent queries instead of
> re-reading files: what calls this function, what depends on this module, which path connects this
> endpoint to that table. Recent systems — RepoGraph [cite: ouyang2024repograph], CodexGraph
> [cite: liu2024codexgraph], RANGER [cite: shah2025ranger], and Codebase-Memory
> [cite: vogel2026codebasememory] — derive such graphs for navigation, dependency traversal, and agent
> retrieval, reporting substantial token and tool-call reductions at some cost in answer quality. These
> systems demonstrate the value of derived repository graphs for navigation and retrieval; authored
> intent is the additional ingredient needed to state what the system ought to permit.

<!-- point: a-code-graph-and-an-authored-model-compose-through-a-check | The extracted graph supplies the IS; the authored model supplies the OUGHT; a check reads one against the other. | terms: model-from-code, drift-gate -->
A code graph can find every caller of a raw format library. An authored architecture model can declare
that only one structured seam may call it. A check can compare the observed callers with the permitted
set. The extracted graph supplies the *is*; the authored model supplies the *ought*.

<!-- point: spec-driven-development-authors-the-ought-as-prose | Prose specifications can carry an OUGHT too; their weakness is mechanical — prose is harder to compose, validate, and reconcile against a moving implementation. | terms: model-to-code, drift-gate -->
Prose specifications can carry an *ought* too, and many agent workflows use them successfully. Their
weakness is mechanical: prose is harder to compose, validate, and reconcile against a moving
implementation. Teams that scale spec-driven workflows often end up adding routing, indexing, generated
documentation, and doc/code mismatch checks — the same pressures that motivate progressively stronger
representation here.

### Keep map and territory connected

<!-- section-terms: map-and-territory, traceability, drift-gate -->

<!-- index-def: map-and-territory -->
<!-- index-def: traceability -->
<!-- point: a-model-earns-trust-over-its-surface-only-if-elements-trace-back | A model earns trust over its claimed surface only if its elements relate back to the system; that relationship is traceability, and it should be live where practical. | terms: map-and-territory, traceability, round-trip, drift-gate -->
A model earns trust over a claimed surface only if its elements can be related back to the system they
represent. That relationship is **traceability**. For code-facing models, the useful round trip is often
bidirectional: from a model element to the implementation that realizes it, and from an implementation
element back to the model that owns or describes it.

<!-- point: the-traceability-relation-should-be-live-not-a-frozen-pointer | Resolve the target against current code when the check runs; a deleted target then becomes a finding rather than a stale green edge. | terms: round-trip, snapshot-vs-derived, drift-gate -->
The traceability relation should itself be live where practical. A stored pointer to a line number or
symbol name is another snapshot that can drift. Resolve the target against current code when the check
runs; a deleted target then becomes a finding rather than a stale green edge. This removes the
failure mode a frozen pointer guarantees: silently surviving after its target disappears.

DocAble learned this after a hand-maintained retirement checklist let model references drift during a
dispatch-plane migration; Part V reconstructs the incident.

## How a model stays trustworthy

<!-- section-terms: map-and-territory, drift-gate, model-drift -->

<!-- point: trust-is-bounded-by-the-models-declared-surface | Trust is bounded by the model's declared surface; a model needs a credible relationship to the facts it claims, or every agent that treats it as a reasoning surface inherits the same stale assumption. | terms: map-and-territory, drift-gate -->
Trust is bounded by the model's declared surface. A model need not describe every line of code; it does
need a credible relationship to the facts it claims to represent. Otherwise every agent that treats the
model as a reasoning surface inherits the same stale assumption.

<!-- point: two-layers-cover-the-relationship-mechanical-and-judgment | Two layers cover the relationship: a mechanical layer that re-derives or checks claims, and a judgment layer for semantics not yet captured by a predicate. | terms: drift-gate, snapshot-vs-derived, model-drift -->
<!-- slogan: derived-defends-snapshotted-drifts -->
Two layers can cover that relationship. The **mechanical layer** handles claims that can be re-derived
or checked: an anchor still resolves, a declared edge still exists, an observed edge is still permitted.
The **judgment layer** handles semantics not yet captured by a predicate: prose whose meaning no longer
matches the implementation, an architectural distinction the schema cannot express, an obligation whose
interpretation remains contextual. A human — or another probabilistic reasoner — can inspect that layer,
but the result is not equivalent to deterministic coverage.

<!-- point: two-gaps-remain-the-semantic-miss-and-the-unmodeled-region | Two gaps remain: a semantic miss (the mechanical relation resolves but its meaning changed) and an unmodeled region (no relation to check). Both mark where human judgment is filling a representational gap. | terms: model-drift, drift-gate, map-and-territory -->
Two gaps remain. A **semantic miss** occurs when the mechanical relation still resolves but its meaning
has changed. An **unmodeled region** has no relation to check at all. Both are important because they
identify where human judgment is still filling a representational gap. Repeated gaps are candidates for
governance conversion later: add a model, refine an abstraction, or add a control when the recurring
judgment is worth retiring.

remaining gaps.

## An executable model is its schema plus its checked predicates

<!-- point: an-executable-model-is-its-schema-plus-its-checked-predicates | In the operational sense used here, an executable model is its structured schema plus the predicates and derivations machines can actually consume. -->
Operationally, an executable model is its structured schema plus the predicates and derivations
machines can consume. The schema gives
the entities, fields, edges, and states; the checked predicates state what must remain true over that
structure. Fields (b) and (c) of the reference template below give the **structured schema** — records,
edges, state machines. Field (d) adds the **checked predicates**, each named by a stable id and held
true at its declared cadence by its checker — a drift lint or a model check.

<!-- point: a-schema-without-checked-properties-is-half-the-executable-model-pattern | A structure that names its parts but carries no machine-consumable properties may still be a useful model; it is only half of the executable-model pattern this chapter builds. -->
A structure that names its parts but carries no machine-consumable properties may still be a useful
model; it is only half of the **executable-model pattern** this chapter is building. Draw the schema and
stop, and it can rot the first time the code moves past it; the checker keeps it honest. The predicates
are not arbitrary — they come from the failures the system met. In the DocAble build the gaps the models
caught were violated-but-unstated invariants: a property the system had always needed and never written
down, promoted to a checked predicate the moment it broke. [ref:coherence-triangle] draws the two
structural edges and marks that provenance link as the dashed arc it is.

<!-- index-def: invariant -->
> ### Inset I1 — What is an invariant? {#inset-invariant}
>
> An **invariant** is a property intended to hold over a defined model domain. In a behavioral state
> machine, that often means a predicate that must hold in every reachable state; in a structural model,
> it may mean that every observed dependency belongs to a permitted set; in a measurement model, that a
> quantity remains below a bound. The important discipline is to state both the property and the domain
> over which the checker claims to establish it.
>
> Take a behavioral illustration: a job whose state is two fields at once — a `status` of `free`,
> `leased`, or `done`, and a `lease_owner` that names the holding worker or is empty. Different steps
> write the two fields, so they *can* fall out of agreement, which is why you write the invariant down.
> "A job is leased if and only if it has an owner" is a predicate over the pair:
> `(status == "leased") == (lease_owner is not None)`. A state where `status` is `free` but a
> `lease_owner` lingers is a stale lease; a state where `status` is `leased` but no owner is set is a
> lost lease. Both are reachable the moment the two writes separate, and both break the predicate. The
> move that makes this more than a comment: the predicate is *checked*, exhaustively, by a tool.
>
> ```
> STATES = product({"free", "leased", "done"}, {None, "worker-1", "worker-2"})
> def invariant(s):                                # leased iff owned
>     return (s.status == "leased") == (s.lease_owner is not None)
> assert all(invariant(s) for s in reachable_states())   # check every reachable state
> ```

<!-- index-def: model-drift -->
<!-- index-def: drift-gate -->
Two terms this Part leans on, stated once. **Drift** is the condition where a model and the code it
describes disagree — the map no longer matches the territory. A hand-maintained diagram drifts
silently the first time a developer changes the code and forgets the diagram. A **drift gate** is the
build-time check that set-diffs the model against reality in both directions and fails the build on
any divergence: model ⊆ reality catches a model element with no code behind it; reality ⊆ model
catches code the model never declared. Because the gate runs on every build, the first commit that
diverges on a checked relation fails, not the fiftieth. Drift the gate does not check can still slip
through, so the gate bounds accumulation over what it checks. A model does not only reduce context; it
can turn a global semantic question into a local predicate over structured state.

The appendix documents each model through a uniform five-field reference template: what the model is

<!-- label: model-page-template -->
<!-- table: The five-field model-page template — the field, what it states, and the reader's question it answers. Every appendix model-reference page fills it. [short: The five-field model-page template] -->
| Field | What it states | The reader's question it answers |
| :-- | :-- | :-- |
| **(a) Engineering question / property** | the question the model answers that the raw code cannot make cheap and reliable — "is Q true?", not "it models X" | *What is it for?* |
| **(b) Constructs and relations** | the typed record kinds, the meaning-carrying fields, the edges between them — the model's slice of the system knowledge graph | *What is it made of?* |
| **(c) Visual depiction** | the diagram matched to the model's natural type (state machine → state diagram; topology → deployment diagram), with an accessible description stating content and takeaway | *What does it look like?* |
| **(d) Invariants, and how checked** | the predicates that must hold, each with its checker — a drift lint, a coverage floor, a model check, a parity gate; prose-only invariants are flagged UNTESTED | *How do I trust it?* |
