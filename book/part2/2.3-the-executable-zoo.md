# The Executable Zoo

<!-- point: this-part-walks-each-model-on-real-code | This Part walks each model on real, drift-checked code. | terms: model-zoo, drift-gate, invariant -->
<!-- index-example: model-as-map -->
The purpose of a model is to reduce the amount of system an engineer — or an agent — must
reason about at once. That is why models exist, and it is why a coding fleet changes their
economics: fewer tokens held in-window, more velocity, higher quality, from the same
artifact.

The last two chapters built the ascent that reaches here: raw context becomes connected
knowledge, and connected knowledge structures into a model. This chapter defines the model at
the top of that climb — the **executable** one, the kind the environment can check — and shows
how to keep the code from drifting away from it. A model is the sweet spot between prose too
vague to enforce and code too verbose to reason over; the earlier chapters ended on a promise,
that this book would walk each kind of model on real code, with real invariants. This Part
cashes that promise.

<!-- point: a-real-drift-checked-codebase-sits-under-every-model | One real codebase carries dozens of drift-checked models. | terms: model-zoo, drift-gate -->

Recall the system behind all of this. There is a real codebase under every model that
follows — DocAble, the production accessibility service this book runs on. It carries
{{real_model_count}} real, structured, drift-checked models and uses everything in this book to
stay coherent. The full account is at the back, in
[The Built System](5.3-the-built-system.html) — {{part:5}}.

<!-- point: every-model-in-part-2-is-one-executable-schema | Every Part-2 model is one executable schema, worn five ways. | terms: executable-source-of-truth, model-zoo, drift-gate -->
<!-- slogan: one-trunk-five-views -->
> ### The Executable Model Pattern {#executable-model-pattern}
>
> Everything after this chapter is **one trunk, worn five ways** — one executable core, five projected views. Every executable model answers the same questions, and the first is new: it fixes the model as an explicit slice of the system knowledge graph the last two chapters built.
>
> - **What entities and relations** does it represent — which slice of the system knowledge graph is it?
> - **What engineering question** does it let you settle that the raw code cannot?
> - **What invariant** must hold?
> - **How is it derived**, from the code or the code from it?
> - **How is that checked** on every build?
> - **What drift** does the check prevent?
>
> The first question is new here, because every model is now an explicit slice of the system knowledge graph; the remaining five are the executable-model pattern the rest of the book develops. Read the rest of Part 2 as instances of it.

## Why models are newly central

<!-- section-terms: thesis-modeling, executable-source-of-truth, model-zoo -->

<!-- point: the-economic-argument-for-models-runs-three-ways | Agents need, maintain, and enforce models; one plays four roles. | terms: thesis-modeling, executable-source-of-truth, reasoning-horizon, long-horizon-task -->
<!-- index-example: reasoning-horizon -->
<!-- index-example: long-horizon-task -->
Part 1 derived the Modeling Thesis from the machine; this Part builds the executable-model
architecture that earns it, then tests it across five views. Recall only the
shape of the argument: agents **need** models (a raw codebase overruns the window), can
**maintain** them (regeneration and reconciliation are the cheap repeated cognition the substrate
now supplies), and can **enforce** them (model-aware checks at the action and admission boundaries
make a model a surface the build holds the code to). One artifact then serves four roles at once —
the agent's reasoning interface, the engineer's specification, the generator's source, and the
build's assurance surface. Its primary purpose is not documentation but a semantically dense
object to reason *through*: building a large system is a long-horizon task whose reasoning state
outruns any window, and the model is what pulls that state back within reach.

<!-- point: the-executable-source-of-truth-delivers-the-four-roles | The executable source-of-truth architecture delivers the four roles. | terms: executable-source-of-truth, drift-gate -->
<!-- index-def: executable-source-of-truth -->
The architecture that delivers all four roles is the **executable source-of-truth**.
The model is structured data. Agents read it to navigate and reason; generators consume
it to emit the artifacts that must agree with it; drift gates block the build the
moment code and model diverge. Every view in this Part is that one architecture.

## The upkeep that constrained MBSE, a fleet now pays cheaply

<!-- section-terms: model-zoo, model-drift -->

<!-- point: mbse-failed-on-upkeep-not-ideas | MBSE failed on upkeep, not on its ideas. | terms: mbse, model-drift, upkeep -->

Model-based systems engineering did not fail on its ideas. One major expense that constrained it
in the mainstream was recurring synchronization labor — the standing cost of keeping a hand-drawn
model matched to a moving codebase. A person notices the code changed, finds the diagram it
touched, and edits the diagram to agree. That work is dull, unending, and the first thing a
deadline cuts, so the diagrams drifted, then lied, then got ignored, and a discipline with sound
ideas earned a reputation for ceremony. A generation learned to build without them: students
came back from internships saying nobody used models, and they were right — nobody did.

<!-- point: the-fleet-supplies-cheaply-the-one-expense-that-buried-mbse | A fleet supplies MBSE's one fatal expense cheaply. | terms: mbse, upkeep, map-and-territory -->

The agent changes exactly that term. Re-inducing a model from the code, diffing it against
the last version, regenerating the artifacts it feeds — this is the dull, unending work a
fleet does at sharply lower marginal labor cost. The one expense that constrained MBSE is the one
an agent fleet now supplies at a fraction of the human cost. A practice that never repaid its upkeep suddenly pays: the map stays
equal to the territory because the recurring upkeep has moved off the human payroll. Someone
still authors the model, the reconciliation rule, and the gate — what shrank is the standing
maintenance, not the design. This is what mature engineering already looks like — the model is
the work surface and the code is downstream — and the fleet is only the catalyst that finally
made its upkeep affordable. This chapter earns that claim: every model below is drift-checked
on every build, not by a human who might forget.

<!-- point: the-zoo-is-large-enough-that-one-model-is-never-the-whole-picture | One model is never the whole picture. | terms: model-zoo, four-plus-one-views -->
<!-- index-def: model-zoo -->
The move now is to stop listing kinds of model and start walking them. The companion
catalogue holds {{real_model_count}} implemented, drift-checked system-models — the actual
embodiments of every kind the last chapter named. Counting the general model *types* used to
classify them yields {{model_count}} named entries. The two numbers measure different things and
should never read as a discrepancy: {{real_model_count}} models are built and gated in the running
system; {{model_count}} counts those models plus the general types they instantiate. Treat
that number as evidence rather than ambition; it grounds a single claim: the zoo is large
enough that one model is never the whole picture. The next chapter makes that precise — each
view is a projection over one connected representation, and no single projection answers every
engineering question.

<!-- point: the-formal-definition-is-the-zoos-admission-test | The formal model definition is the zoo's admission test. | terms: model, model-zoo, drift-gate -->
What admits a candidate to the zoo is the formal definition from
[The Agent Stack](3.1-the-agent-stack.html): a deliberately reduced, machine-readable
representation of system intent, structure, behavior, policy, or evidence — one that
supports reasoning, derivation, or checking, and is mechanically maintained against the
system it represents. Registries, graphs, manifests, state machines, typed records: each
earns the word the same way, by naming what it represents and carrying the gate that
holds it true. A structure that fails a clause — a dashboard nothing derives from, a
diagram nothing checks — stays out, however useful it is.

<!-- point: mbse-here-is-derived-software-modeling-of-discrete-systems | MBSE here means derived software models of discrete systems. | terms: mbse, sysml, discrete-software -->

> ### Inset — What is SysML, and what does MAGE take from it? {#inset-sysml}
>
> **SysML** is one major notation for model-based systems engineering [cite: friedenthal-sysml]: blocks, constraint blocks, and verify-and-satisfy traceability, drawn in a modeling tool. A constraint block ties a required property to the element it governs; a verify-and-satisfy edge traces a requirement to the thing that meets it. MAGE borrows that concern — a typed invariant with a pointer to the check that verifies it *is* a constraint block in all but the notation — but implements it in a **repository-native, drift-gated** form. What it refuses is SysML's usual *form*: a model drawn beside the code. A second drawing of what the code already is snapshots the moment the code moves — the failure a derived model exists to kill. Borrow the words where they name something; keep the model bound to the code, derived in either direction and gated either way, not drawn alongside it.
>
> The scope stops at *discrete* software. A system with continuous or real-time dynamics wants a different toolkit — the timed and hybrid automata of Alur and Dill [cite: alur-dill1994]. That is out of scope here, and the place to read next if your system touches the physical world.

<!-- point: the-model-level-buys-fewer-tokens-velocity-and-quality-together | The model level buys fewer tokens, velocity, and quality together. | terms: silver-bullet, thesis-modeling, context-window -->

Working at the model level, with an agent doing the lifting, points at three things a team usually
trades against one another: fewer tokens spent, more velocity, and higher quality. The preface
reported living that combination rather than modeling it. [data: velocity] That is the fewer-tokens leg named on the first page, now paid in: a model binds intent to
implementation *and* shrinks what the agent must hold in-window to act on it — the book's
answer to churn, the failure that limits an agent fleet. Whether the model level genuinely delivers all three together, and at what
cost, is a larger claim than one chapter's evidence can carry; it is taken up later, once the model
pages below have supplied the evidence. Each model page is a small piece of it. A controlled
navigation pilot puts a first number under the fewer-tokens leg; [Keeping the Models in
Sync](2.12-keeping-models-in-sync.html) reports it.

<!-- worked-examples: thesis-modeling -->
### Example — Siemens
Siemens runs on executable models as a matter of course. SysML and CAD, simulation models, virtual
ECUs, and a bill-of-materials structure are the artifacts engineers actually work in; code is
generated from them and verification is derived from them. The executable model is not an aspiration
there but the ordinary medium of the work — the strongest external evidence that a model can sit
upstream of the implementation rather than beside it.

### Example — Spotify
Spotify makes a narrower executable model pay at fleet scale. Its System Model and Backstage catalog
carry dependency and endpoint lineage with stable identities, and the architecture diagrams are
generated from that metadata rather than drawn by hand. When a migration targets an endpoint, the
fleet acts through the model of the estate, not the raw code — an executable representation driving
real change across thousands of repositories.

### Example — DocAble
DocAble is one software implementation of the pattern, and its distinctive slot is the typed
intermediate representation: every remediation is a node in a typed IR the validator walks, so a fix
is an object a gate can check rather than a diff to eyeball. It also reaches the rung even the
model-first company does not — a drift gate that fails the build when a model and the code it governs
disagree, holding the map equal to the territory instead of merely keeping the two in step.

<!-- takeaway -->
The shared move is executable *modeling* made central: the model is the object the fleet reads,
generates from, and checks against. Where the model is bound to the territory by a blocking drift
gate, as in DocAble, the representation stops describing the system and starts holding it true — the
one rung the strongest external cases here do not reach.

## The trunk: machinery that holds any view true

<!-- section-terms: executable-source-of-truth, drift-gate -->

Before the views, one chapter of framing. Most of the catalogue's method models do not

- **The executable source-of-truth.** The pattern behind every view, named and defined at the

- **The read and generate surfaces.** One canonical query API over every model

> Learn more about this governance mechanism: [model query surface](appendix-b-query-surface.html).

These are the framing chapter's home. The view chapters name them again where each view's

Three rules organize the whole Part.

### Derive and join; do not repeat

<!-- section-terms: derive-and-join, join-key -->

<!-- index-def: derive-and-join -->
<!-- point: a-model-is-derived-and-joined-never-repeated | A model is derived and joined, never repeated. | terms: derive-and-join, join-key -->

The last chapter warned against repetition: two models that say the same thing must now be
kept in sync. This Part sharpens that warning into the zoo's organizing rule. A model here
is **derived** — from the code, or the code from it — never kept beside the code as a
parallel document. And it **joins** to its neighbours on a shared key rather than restating
them. Restate a fact in two models and you are back to keeping two copies in sync by hand.

<!-- point: derivation-and-join-are-the-cure-for-repetition | Derivation and join are the cure for repetition. | terms: derive-and-join, join-key -->

The service-flow model *is* the list the access policy is generated from and the call graph
is checked against — it holds no second copy of the endpoints to re-list. The journey model
*joins* to those endpoints by call-site rather than copying them. Repetition is the failure.
Derivation and join are the cure. The flagship demonstration is the third worked example in
the Scenarios chapter, where four models join so a journey's criticality reaches all the way
to which host a test runs on, with no fact stated twice.

### State the derivation direction

<!-- section-terms: derivation-direction, model-from-code, model-to-code -->

<!-- index-def: derivation-direction -->
<!-- point: name-the-direction-of-derivation-up-front | Name the direction of derivation up front. | terms: derivation-direction, model-from-code, model-to-code -->

A model and the code it concerns stay equal by derivation, and derivation runs in one of two
directions. Say which up front, because the machinery differs.

<!-- index-def: model-from-code -->
<!-- index-def: model-to-code -->
- **Model-from-code (induce and reconcile).** The code is authoritative; the model is a
  projection of it, reconciled at build time. The component-zone model reads the real
  directory tree; a journey's dependency list is derived from its real call sites. Here the
  drift gate is a *reconciler*: it re-induces the model from the code and fails on divergence.
  Reach for this when the code is the ground truth and the model is a compact, queryable view
  of it — the usual case for a large codebase an agent must operate.
- **Model-to-code (specify and generate).** The model is authoritative; the code, config, or
  docs are generated from it. The access policy, the service catalog, the wire-contract types
  are emitted from the service-flow model. Here the drift gate is a *freshness and provenance
  check*: the generated artifact carries a header, and a hand-edit or a stale regeneration is
  a finding. Reach for this when the model is the design intent and you want the artifact to
  obey it.

<!-- point: most-of-the-zoo-is-model-from-code-because-the-codebase-came-first | Most of the zoo is model-from-code; the codebase came first. | terms: model-from-code, model-to-code -->

Most models in the zoo are model-from-code, because the codebase pre-existed the models. The
service-flow model is the clearest model-to-code case, and it is bidirectional — some fields
generated to code, others reconciled from it — which is why its gate checks both directions.
Each model page names its direction.

### Extracted Code Graphs and Intent-Bearing Models

<!-- section-terms: model-from-code, drift-gate -->

<!-- point: a-code-graph-recovers-structure-an-authored-model-declares-intent | A code graph recovers structure; an authored model declares intent. | terms: model-from-code, drift-gate -->

The purest model-from-code artifact is not one of the zoo's own views. It is the repository
graph a growing class of tools now hands a coding agent: a parser walks the repository into a
persistent, queryable graph of its entities and relations — functions, classes, imports, calls,
endpoints, schemas, tables — so the agent reasons through the graph instead of re-reading raw
files on every task. By the Modeling Thesis, that is the token argument already made for the zoo,
pointed outward.

Recent repository-graph systems make that map increasingly capable; the inset surveys them. MAGE's
separate concern is how that descriptive structure joins to authored intent and mechanically
enforced policy.

> ### Inset — What do repository-graph tools do? {#inset-code-graph}
>
> A repository-graph tool parses the codebase into a persistent graph an agent queries instead of re-reading files: what calls this function, what depends on this module, which path connects this endpoint to that table. Recent systems — RepoGraph [cite: ouyang2024repograph], CodexGraph [cite: liu2024codexgraph], RANGER [cite: shah2025ranger], and Codebase-Memory [cite: vogel2026codebasememory] — derive such graphs for navigation, dependency traversal, and agent retrieval. Codebase-Memory reports roughly a tenfold reduction in tokens and 2.1 times fewer tool calls against a file-exploration agent, at some cost in answer quality (83 percent against 92). These tools *report* what they measured and *derive* the graph; they do not *establish* MAGE's join claim — that is the next paragraph's work.

Here is where the join bites. An extracted graph describes what exists. It can show that
component A calls component B. Extraction alone cannot say whether A is *permitted* to call B,
whether B owns that responsibility, which user goal the edge serves, or what invariant the call
must preserve. None of those are syntactic facts waiting in the artifact to be recovered. An
engineer decided them.

The derivation-direction rule named one axis: which artifact is authoritative, code or model. Lay a second axis across
it. Not how the representation was made, but what claims it is authorized to make. A descriptive
model recovers the territory. An intent-bearing model states the shape the territory is meant to
have. The first is built to navigate and to estimate impact. The second is where specification,
prediction, and governance live.

The boundary bends both ways. A MAGE model may begin as an induced description of existing code,
and a code graph may fold in documentation, schemas, or inferred clusters. So provenance is not
the question. Authority is. Does the representation report that an edge exists, or declare the
edge permitted? Does it list the running services, or name which service owns a capability? Does
it record observed behavior, or define the transitions the system is allowed to make?

<!-- point: a-code-graph-and-an-authored-model-compose-through-a-gate | Code graph and authored model compose through a gate. | terms: model-from-code, drift-gate -->

Put that way, the two kinds of model compose rather than compete. A code graph finds every caller
of a raw PDF library. An authored architecture model declares that a single structured model owns
mutation of that format. A gate compares the extracted callers against the permitted set and turns
any extra edge into a build finding. The graph supplies the current fact, the authored model
supplies the policy, and the gate reads one against the other. This is the same drift check the
zoo runs everywhere, now with a descriptive map on one side and a normative model on the other.

That composition is a governed engineering environment in miniature, and it settles where these
tools sit. A code knowledge graph is a strong input to MAGE: it can serve the observed-reality
side of any drift or parity gate. What it does not carry by itself is the *ought*. The Modeling
Thesis puts both representations in front of the reasoner, the map of what is and the model of
what should be. The Alignment Thesis keeps the descriptive map, the intended design, and the
running code from drifting apart in silence.

A shorthand, offered as a center of gravity and not a fence: a code knowledge graph compresses
implementation; a MAGE model compresses engineering meaning. Both are models. Both can be
induced. Both help an agent reason. What MAGE requires past the graph is a place for the ought,
and a mechanism that holds the is against it.

<!-- point: spec-driven-development-authors-intent-as-prose-not-a-typed-model | Spec-driven development authors intent as prose, not a structured model. | terms: model-to-code, drift-gate -->

The ought can also be authored a simpler way: by writing it down. Spec-driven development gives
every feature a written specification the agent implements against — a real move toward authored
intent, the same normative commitment MAGE makes, and it holds until the corpus grows. The
difference is representation. A spec states the ought in prose, which does not compress and drifts
unseen; a spec the code has moved past produces *"syntactically correct code that was wrong,"*
because the agent trusts it. A structured model states the same ought in a form the machine reads:
the right slice is small by construction, and a gate holds the model against the code, so it cannot
go stale-but-trusted — the failure the field reports name most sharply. The sidebar walks where one
team's report broke and how its hand-built remedies map onto this chapter's machinery.

> ### Sidebar — Spec-driven development, from the field {#sidebar-spec-driven}
>
> Recent studies of spec-driven agent workflows converge on the same normative point. An industrial one-person-squad case that ran an explicit spec-driven process to deliver work scoped for a four-person team reports that specification quality and institutional knowledge — not raw model capability — decided the outcome [cite: vilasboas2026onedeveloper]. One team's field report is exact about where it broke [cite: sdd-abdurrahman-2026]: a naive preload reached roughly thirty-five thousand tokens at startup, of which about six percent was relevant, and the agent degraded once the window passed half full. Its remedies climb the same hill this chapter climbs. Living specs, one per feature and edited in place, are the derive-don't-snapshot rule under another name. A thin router and index that load only the matching documents reach for [a context-management layer](appendix-d-context-management-stack.html). Generated wikis and [a CI check that flags a doc-against-code mismatch](2.12-keeping-models-in-sync.html) are a drift gate and derived traceability, bolted onto a prose corpus after the fact. The report *frames* where it broke; it does not *establish* the general claim.

So three ways to hand a fleet a system it can reason about fall on one axis. A code knowledge
graph recovers what the code *is*. A spec writes down what it *should be*, in prose the agent must
re-read and can outrun. A structured model states that same ought where a compiler and a gate can
hold it to the code. Only the last keeps intent both compact and true.

### Trace every model element to code

<!-- section-terms: traceability, drift-gate -->

<!-- index-def: traceability -->
<!-- point: every-model-traces-to-the-code-in-both-directions | Every model traces to the code in both directions. | terms: traceability, round-trip, drift-gate -->

A model earns trust only if you can get from a model element back to the lines that realize
it, and forward from a line to the model element that governs it. That round-trip is
**traceability**. It is exactly what the safety-critical standards demanded and exactly what
the drift gate mechanizes: the reconciler *is* a traceability check that runs on every build.
The forward direction is itself measurable — how much of the tested code reaches any model —
and driving that number up is how the case study drained its unmodelled code. [data: mmm-drain]

<!-- point: the-template-folds-a-traceability-note-into-every-page | The template folds a traceability note into every page. | terms: traceability, per-model-template, join-key -->

Traceability is why the per-model template folds a one-line note into each page — the
direction the model derives, and the join key from a model row back to the code. A reader
always knows how to round-trip from the picture to the lines.

<!-- point: a-zoo-of-drifted-views-is-worse-than-none | A zoo of drifted views is worse than none. | terms: model-drift, traceability, round-trip -->

The round-trip is also what the whole zoo rests on. A set of views earns trust only while every
view still tracks the code it depicts; the moment one describes a subsystem the code has retired,
it misleads every agent that reasons through it. A zoo of drifted views is worse than none,
because it lends false confidence. A view stays equal to the code only if something re-checks it
once both have hundreds of authors and a fleet rewriting the territory daily.

<!-- point: the-round-trip-must-be-derived-not-snapshotted | The round-trip must be derived, not snapshotted. | terms: round-trip, governance-graph, snapshot-vs-derived -->
The answer this book defends is that the round-trip must itself be **derived**, not snapshotted.
Picture the graph it walks — model element to lint to code entry point to test to registry row,
each hop an edge. Write those edges down once and trust them, and the graph is a frozen snapshot
that drifts the first time a symbol it names is deleted. Give each edge the mechanism that
re-proves it — resolve the target against the code and see whether it still exists — and a
deletion turns the edge red. A check that re-resolves its target against the code carries no stored
copy of the fact, so it cannot silently lag behind an edit; a stored edge can. Re-resolution is not
infallibility — a live resolver can still be incomplete, or mis-resolve an anchor — but it removes
the one failure a snapshot guarantees: falling quietly out of date.

<!-- point: a-resolving-edge-is-both-drift-detection-and-navigation | A resolving edge is both drift-detection and navigation. | terms: governance-graph, symbol-anchor, context-window -->
The graph pays a second dividend. Because a resolving edge means the map is current, an agent can
*walk* it to pull the slice of a codebase it cannot hold in one window — up from a line to the
invariant that governs it, down to the code that realizes it. The systems model a senior engineer
keeps in their head becomes a navigable index the fleet reasons through. Drift-detection and
navigation are one property wearing two faces: an edge that resolves is both a true claim and a
current map. The next section reads the concrete mechanism off DocAble's real drift; the catalogue
carries it as its own entry.

## Keeping the models honest — the traceability substrate

<!-- section-terms: traceability, governance-graph, snapshot-vs-derived -->

<!-- point: the-substrate-was-built-from-what-broke-not-designed-up-front | The substrate was built from what broke, not designed. | terms: governance-graph, snapshot-vs-derived -->
DocAble did not design this up front. It tried the cheaper approach first, watched it fail on
real work, and built the machinery from what broke. The story is worth walking, because it
shows the exact shape a snapshot rots into and why a derived edge does not.

<!-- point: a-stale-model-makes-agents-plan-against-a-system-that-no-longer-exists | A stale model makes agents plan against a dead system. | terms: model-drift, map-and-territory -->
A model is only as good as its agreement with the code. Say a model still describes a
*poll-based* dispatch plane after a serverless *push* plane replaced it — DocAble's real
mid-project migration — and every agent that trusts the
model plans against a system that no longer exists. The map has to equal the territory, or the
map lies.

<!-- point: the-checklist-approach-fails-because-a-hand-maintained-list-rots | A hand-maintained checklist rots the moment the code moves. | terms: model-drift, snapshot-vs-derived -->
The tempting way to keep them equal is a checklist: when you retire a subsystem, remember to
update the model too. DocAble tried that and it failed the way it always fails. A cutover retired
the poll plane, the retirement doc dutifully reconciled the architecture docs and the agent boot
context, and it forgot the models. The forgotten edge stayed green because nothing re-checked it.
That is the pattern under every silent drift: a hand-maintained list rots the moment the code
moves without it, and no one notices until the stale fact bites.

### Reading the fix off real drift

<!-- section-terms: sensor, model-drift, snapshot-vs-derived -->

<!-- point: the-fix-was-read-off-real-drift-not-guessed | The fix was read off real drift, not guessed. | terms: model-drift, sensor, snapshot-vs-derived -->
The right sensor was read off real drift rather than guessed. The models were left deliberately
ungoverned for weeks and the fleet allowed to drift them, so the fix could come from observed
failure instead of imagination. An audit of the closed work — every job green at its own
done-check — turned up two dozen silent divergences at a signal-to-noise near one. A checker
tightened past the producer it now rejected; a typed function shipped and wired to nothing; a
reconciliation lint gone red the instant its work closed. Sort those cases by what caught them
and one line separates the clean from the drifted. The clean ones had a sensor that re-read the
code at check time. The drifted ones kept a second copy of the fact, maintained by hand, that
fell behind.

<!-- point: the-graph-is-nodes-the-system-already-has-joined-by-re-proved-edges | The graph joins existing nodes by re-proved edges. | terms: governance-graph, symbol-anchor, join-key -->
So DocAble keeps a **traceability graph** in place of a checklist, and every edge in it is
*derived* — re-checked against the code at scan time rather than trusted from the last time
someone looked. The nodes are things the system already has: a model element, the lint that
enforces it, the code entry point that realizes it, the test that verifies it, a registry row, a
doc surface. The edges are the joins between them — *this invariant governs that code root*,
*that test verifies this invariant*. Each edge carries the mechanism that re-proves it: run the
resolver against the target and see whether the symbol still exists.

### Two decisions that make the graph resist rot

<!-- section-terms: governance-graph, drift-gate -->

- **Anchor to symbols, never to line numbers.** An edge points at a function or class *definition*, resolved statically — not at a file-and-line. Line numbers churn under every edit above them; a symbol survives every edit that does not delete it. When five journey anchors drifted stale under a refactor, the cause was line-anchoring. A symbol anchor moves with the code it names.
- **A missing symbol is a finding, not a crash.** When an edge points at a symbol that no longer resolves — deleted, renamed, moved out — the edge goes red, and that red is the drift becoming visible. The sharper case: when the model wants to point at logic for which *no clean symbol exists*, buried in a god-function, the absence signals the code is missing an abstraction the model needs. The anchor doubles as a probe for where the code is under-factored.

<!-- point: the-symbol-walk-fires-at-a-slower-cadence-because-the-cadence-follows-the-cost | The symbol walk fires slowly because cadence follows cost. | terms: symbol-anchor, governance-graph, sensor -->
The sensor that walks the graph runs at a slower cadence than the per-commit gates, on purpose.
Resolving a symbol against the code — a jedi or Roslyn round-trip per anchor — costs far more than
the cheap membership lookups a commit hook can afford, and the costlier the check, the slower the
cadence it earns: the derived-edge check fires at review and done-checking time, not on every
commit. A second, cheaper
guard sits on the anchors themselves, watching for the case a symbol walk cannot catch — a pointer
left naming a dead implementation while a replacement was built beside it. That pointer-drift
guard was earned by the most expensive drift of the build, a retired *deploy-orchestration
script* whose stale pointers still named a dead implementation and fired a prod-blocking deploy.

<!-- point: derived-sensors-defend-snapshotted-ones-drift | Derived sensors defend; snapshotted ones drift. | terms: sensor, snapshot-vs-derived, model-drift -->
This is the same commitment as the one structured model under every format, one level up. There, a fix
applied through the model holds for every format because there is exactly one place to apply it. Here, a model
stays true to the code because the join between them is re-derived, not remembered. A correctly
implemented live resolver does not incur temporal drift from a stored copy: it reads the source of
truth at check time rather than carrying a copy that can age. A hand-maintained copy of the same
fact always can. **Derived sensors defended; snapshotted ones drifted** — the audit's line held for
that reason.

## A model is its schema plus its checked predicates

<!-- point: a-model-page-draws-one-shape-three-times | Every model page draws the coherence triangle: schema, invariants, checker. -->
Every model page in this Part draws the same **coherence triangle**. Fields (b) and (c) give the
**structured model** — records, edges, state machines. Field (d) adds the **checked invariants**,
the predicates that must hold, each named by a stable id; its checker (the drift lint or model
check) holds each predicate true at build time. Model, invariants, checker — the
constraint-and-verify vocabulary the chapter already borrowed from SysML, where a constraint block
wires to the check that satisfies it. Read the triangle as one operational equation: an executable
model is its schema plus its checked predicates.

<!-- point: the-invariants-and-gate-complete-the-models-value | A model's value is both its schema and checked invariants. -->
The model provides two kinds of value. First, the schema — records, edges, state machines —
names the parts and gives the tools something to read. Second, the invariants that get
checked: the predicates that must hold. Value both. The triangle's point is that the
invariants and their checker *complete* the model's value, not that the schema earns nothing. A
structure that names its parts but promises nothing you can test is only half a model; field
(a) drew that line, and field (d) stamps an unchecked invariant UNTESTED. Draw the schema and
stop, and it rots the first time the code moves past it. The checker keeps it honest.

<!-- point: each-invariant-was-earned-from-a-failure | Each invariant was earned from a failure. -->
The invariants are not arbitrary. They come from the failures the system met. In the DocAble
build, the gaps the models caught were violated-but-unstated invariants — a property the
system had always needed and never written down, promoted to a checked predicate the moment it
broke. Part 5 records the act behind each one: deciding, for every failure, whether it was a
one-off to patch or the symptom of a missing mechanism. Promoting the property to a checked
invariant is what makes the model the right abstraction, not merely a plausible one. That
provenance is a true claim about where the invariants came from, not a structural edge of the
triangle. [ref:coherence-triangle] draws the two structural edges and marks the provenance link as
the dashed arc it is.

<!-- index-def: invariant -->
> ### Inset I1 — What is an invariant, and how do you write one? {#inset-invariant}
>
> An **invariant** is a statement that must be true in *every* state your system can reach — a
> property the system promises never to violate. You write one as a predicate over the model's
> state, then you ask the model whether any reachable state breaks it. Take a job whose state is
> two fields at once: a `status` of `free`, `leased`, or `done`, and a `lease_owner` that names the
> holding worker or is empty. The two fields are written by different steps, so they *can* fall out
> of agreement — that is exactly why you write the invariant down. "A job is leased if and only if
> it has an owner" is a predicate over the pair: `(status == "leased") == (lease_owner is not None)`.
> A state where `status` is `free` but a `lease_owner` lingers is a stale lease; a state where
> `status` is `leased` but no owner is set is a lost lease. Both are reachable the moment the two
> writes separate, and both break the predicate. Because the invariant concerns a single state, you
> check it by visiting every reachable state and evaluating the predicate there. The move that makes
> this more than a comment: the predicate is *checked*, exhaustively, by a tool, not eyeballed on a
> diagram. That is the step from "we believe this holds" to "the checker establishes that no
> reachable state violates the predicate."
>
> ```
> STATES = product({"free", "leased", "done"}, {None, "worker-1", "worker-2"})
> def invariant(s):                                # leased iff owned
>     return (s.status == "leased") == (s.lease_owner is not None)
> assert all(invariant(s) for s in reachable_states())   # check every reachable state
> ```

<!-- index-def: model-drift -->
<!-- index-def: drift-gate -->
Two terms this Part leans on, stated once as mainline reference — they are the book's own
machinery, not background a reader might already know. **Drift** is the condition where a model
and the code it describes disagree — the map no longer matches the territory. A human-maintained
diagram drifts silently the first time a developer changes the code and forgets the diagram. A
**drift gate** is the build-time check that set-diffs the model against reality in both directions
and fails the build on any divergence: model ⊆ reality catches a model element with no code behind
it; reality ⊆ model catches code the model never declared. Because the gate runs on every build,
the drift the gate models cannot accumulate — the first commit that diverges on a checked relation
fails, not the fiftieth. Drift the gate does not model, a fact no invariant covers, can still slip
through, so the gate bounds accumulation over what it checks, not over everything. That bounded
guarantee is still what separates an executable model from a diagram: the diagram drifts silently
on *any* change, the gated model cannot drift silently on a change it checks.

Why this matters for autonomy: a model does not only reduce context. It can turn a global
semantic question into a local predicate over structured state.
