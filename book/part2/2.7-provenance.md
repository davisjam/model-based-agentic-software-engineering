# Provenance Models: What Happened, and What Evidence Records It?

When an autonomous system changes a user's artifact, completion is not the only fact worth preserving.
Engineers and users may need to know what changed, what changed it, and why. A provenance
model represents that history as structured evidence rather than prose reconstructed after the fact.

<!-- box-family: model-card -->
> #### Attribution model · Provenance
>
> - **Engineering question** — What happened to this artifact, which operation produced the change, and what evidence
>   records it?
> - **Model** — a run made of operations, each naming its target, its mutation, the pass that made it,
>   and the evidence it left.
> - **Property** — consequential operations have structured attribution linking the action, target,
>   mutation, responsible pass, and retained evidence.
> - **Quality attribute** — auditability, debuggability, and consistency between what changed and what is
>   reported.

<!-- point: a-provenance-model-selects-events-that-matter-to-explanation-not-a-full-trace | The attribution model records the events that matter to engineering explanation and audit, not a trace of every function call. -->
[ref:attribution-model] draws a reduced provenance model: a run contains operations, and each operation
names a target, a mutation, the pass responsible, and the evidence it left. This is not a trace of every
function call. That would reproduce execution rather than model it. The model keeps only the events
needed for explanation and audit.

<!-- label: attribution-model -->
<!-- figure: assets/attribution-model.svg | *Attribution provenance model.* A run contains consequential operations; each operation records its target, mutation, responsible pass, and retained evidence. Audit and explanation can be derived from this shared history. -->

<!-- point: record-once-derive-the-explanations | A human-facing explanation is derived from the structured action record rather than maintained as a second, independently-written account. -->
The system derives its other views from that record. Human-facing explanations are generated from the
structured action history rather than maintained separately. **Record once, derive the explanations.**
This reduces inconsistency between what the system did and what its documentation says.

## Provenance Is Modeled History

<!-- point: provenance-begins-by-choosing-consequential-events | Provenance begins by choosing which events carry explanatory identity. -->
Recording history is not the same as modeling it. An execution offers far more than an engineer wants to
keep — function calls, allocations, retries, intermediate values, model requests, filesystem operations.
Capturing all of it produces an execution trace, not necessarily a useful provenance model. Provenance begins when the engineer chooses which events deserve stable identities for
explanation and audit. For DocAble, that boundary is the consequential mutation. The
edit record states what changed, its target, and the evidence left behind while suppressing most of
the computation that produced it. That reduction makes the history useful for audit and replay rather than
merely exhaustive.

<!-- point: event-grain-is-part-of-the-provenance-model | Event grain is part of the provenance model. -->
The choice of grain is therefore part of the model. Choose too coarse a grain and distinct consequential
changes collapse into an opaque "document modified" event. Choose too fine a grain and the record becomes
another execution trace that must be reconstructed into meaning. The useful grain answers the
engineering questions the model exists for: what changed, why, and can this be reproduced?

## A Record Can Be Executable Without Becoming the Implementation

<!-- point: a-typed-edit-record-replays-deterministically | The typed edit record replays a remediation deterministically. -->
DocAble's edit record has an unusual property for a provenance model: it runs. During a remediation session
the PDF path records document mutations as typed `PdfEdit` values in a per-session log — roughly thirty
variants covering the changes the editor can make. A replay engine applies the same sequence
deterministically, so the record can both explain and reproduce the remediation.

<!-- point: an-executable-record-is-not-the-implementation | A replayable record still omits the reasoning that produced it. -->
Executability does not make the record a complete behavioral model of the remediation system. It still
omits the reasoning, analyses, control decisions, retries, and computations that produced those edits. The
record says which consequential mutations happened, not why the system chose them.

<!-- point: record-and-replay-separate-three-questions | Structure, realized history, and replay are three separate capabilities. -->
Record and replay separate three questions that are easy to conflate. The computation graph asks what
computations may compose. The provenance record says which consequential mutations did occur. Replay asks a
third: can that realized history be reproduced? No one of these representations subsumes the
others.

<!-- point: graph-and-edit-log-are-not-joined-today | Computation graph and edit log answer different questions, unjoined. -->
The two representations are not joined today. A `PdfEdit` identifies a PDF structure element,
not a computation-graph node. For a `TypedPatchProducer`, however, runtime edits are the realized output
of a modeled computation. Shared computation identity could join the execution record to the static graph
if that relation becomes useful.

[ref:two-reductions-static-realized] sets the two representations side by side.

<!-- point: a-provenance-model-does-not-guarantee-every-operation-records-its-attribution | Whether every consequential operation actually records its attribution is an Alignment question, not something the provenance model itself guarantees. -->
One limit matters. A provenance model does not guarantee
that every consequential operation actually records its attribution. That is an Alignment question.
DocAble addresses it separately by requiring typed mutation verbs to emit attribution records and
checking that obligation structurally. Part III examines that mechanism. **Part II models the evidence
the operation should leave; Part III asks what mechanism, if any, gives that obligation authority.**

as a system.
