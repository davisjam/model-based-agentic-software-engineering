# System Knowledge: Connecting the Models

<!-- point: different-questions-drew-different-models-joined-where-needed | Different questions require different models of one system; shared identity and explicit correspondence connect them where a question crosses views. | terms: system-knowledge -->

Different questions require different views of the same system. Following Fairbanks, we understand software architecture as the structures needed to reason about a system, including the software elements, the relations among them, and properties of both [cite: fairbanks2010]. A component view exposes decomposition, a behavioral view shows legal transitions, a deployment view records allocation, and a quantitative view can supply a resource bound. An architectural decision can draw on several of these views. To decide whether two workers can share a host within its memory budget, for example, an engineer needs to know which workers may run together, how much memory each needs, and how much the host provides.

The views need to agree on the identities and relationships that their questions cross. A deployment record and a memory budget can each serve its own purpose if the engineer can identify the workers and host in both. MBSE methods likewise connect requirements, design models, analyses, and verification results so that engineers can follow a decision across representations [cite: estefan2008mbse] [cite: madni2018mbse]. When these views are cheap to derive, maintain, and query, more of that knowledge can remain explicit between tasks.

## Connecting Models to Answer Engineering Questions {#connecting-models-to-answer-engineering-questions}

<!-- section-terms: system-knowledge, join-key -->

Connecting models lets us answer questions that no individual representation can settle. Sometimes the connection brings together facts about the same entity. Other times it lets us evaluate relationships between representations, or investigate the behavior of components that interact. The question determines what information must be shared and what analyses become possible. [ref:model-connection-analyses] distinguishes three common analytical uses; these can overlap, and the first two may both use relational joins.

| Connection | What it enables | Example | Analysis |
|---|---|---|---|
| Combine facts | Bring together attributes of the same entity recorded separately. | Connect a service’s deployment configuration to its latency measurements. | Join, aggregation |
| Relate representations | Evaluate a relationship or derive a fact across models. | Derive invocation grants from permitted service calls and deployment identities. | Join, graph comparison, constraint checking |

Suppose users report that a service is responding slowly. Its owner, deployment configuration, and performance measurements are recorded separately. Without connecting those records, an engineer may struggle to identify who should investigate, which resources the service has, and whether its current configuration explains the observed performance.

**Question.** How can we bring these representations together to investigate the problem?

<!-- point: the-unity-that-matters-is-semantic-not-syntactic | Shared identities let different representations refer to the same service, work item, or operation without requiring a common file format or metamodel. | terms: join-key -->

The service catalog identifies the owner, the deployment model records the resource allocation, and a measurement record supplies recent response times. Shared service identities let the engineer or agent connect these representations and obtain the relevant facts without reconstructing their relationships from source code or directory names. The records need not share a file format. The connection lets the engineer examine observed performance alongside the resources assigned to that deployment; it does not by itself establish the cause of the slowdown.

<!-- point: join-static-and-runtime-only-when-a-question-pays | A static model and a history answer different questions; stable task identity permits a join when observations help answer a structural question. | terms: derive-and-join, join-key -->

The deployment model describes where the service runs and what resources it has been assigned; an execution history records what happened during particular requests. Joining measurements from that history to the service identity can reveal a performance problem without turning the deployment model into a log. Why not combine all these representations into one comprehensive description? Taken to its extreme, that description would read like the implementation itself, with all the detail that modeling was intended to suppress. Separate models preserve the distinctions needed for different questions; their connections let engineers reason across those distinctions without carrying every detail into every analysis.

<!-- point: an-agent-enters-through-the-object-its-task-names-and-traverses-outward | An engineer or agent can begin at the entity named by a task and follow the modeled relationships required by its engineering question. | terms: join-key -->

An engineer or agent can therefore enter through the object named by a task and follow the relations its question requires: from service to owner, from service to deployment, from deployment to measurement. A query interface makes these connections traversable. The agent needs the connected slice that answers the question, rather than every model in the project.

<!-- point: joining-models-makes-cross-representation-properties-available | Joining models makes properties that cross individual representations available for reasoning. | terms: derive-and-join, join-key -->

Other connections derive a fact that neither representation records alone. Suppose the policy allows a report service to invoke a renderer. The policy names the two services, while the deployment model records the runtime identity under which the report service runs. Joining the permitted call to that identity determines which principal needs permission to invoke the renderer. Neither model contains that complete answer by itself: the policy does not name the environment's principal, and the deployment record does not decide which calls should be permitted.

A model can also connect an obligation to its evidence. A latency requirement might identify the workload and response-time bound, while a test catalog identifies the measurement that evaluates them. Linking the requirement to that test makes a missing measurement visible. SysML represents this relationship through verification cases that identify the subject and the requirements to be evaluated [cite: omg2025sysml]. Whether the test supplies adequate evidence, and whether its result should block release, remain further engineering decisions.

Behavioral models can also be connected, but sharing identifiers does not determine their combined behavior. Suppose one model describes a worker completing a job while another describes lease expiry and reassignment. To determine whether a former owner’s completion can be accepted after another worker acquires the job, we must specify how their events interact: which synchronize, which can interleave, and how completion messages are delivered. A composed model exposes interleavings and interactions that neither model represents in isolation. Properties established for each component separately do not necessarily establish a property of their interaction. State exploration can search for an unsafe sequence; temporal model checking can investigate requirements over complete executions.

<!-- point: joins-are-also-where-information-is-lost | A join can preserve entity identity while losing a distinction needed by the decision; shared identity does not establish semantic adequacy. | terms: derive-and-join, model-drift -->

A join only works if it preserves the distinctions the decision needs. A record may use the correct user identifier and still reduce an unlimited entitlement to a finite-credit balance. Shared identity makes the connection explicit; it does not guarantee that the information passed across it is adequate.

Models can be connected across different concerns or across levels of abstraction. A service catalog, deployment model, and measurement record provide different views of the same service; joining them connects information that no individual view contains. A service-level architecture and a module-level dependency graph instead describe related structure at different levels of detail. The latter introduces classes, interfaces, and dependencies omitted from the former, but must preserve any architectural boundaries established by the higher-level model.

The relationship between abstraction levels recalls the classical technique of **stepwise refinement** [cite: wirth1971program]: progressively transforming an abstract description into a more detailed realization while preserving its required properties. In agentic engineering, an agent can perform much of this refinement, choosing algorithms, data structures, and internal organization within the freedom left by the higher-level model. The engineer remains responsible for deciding which properties must survive that translation. Explicit relationships between abstraction levels make those obligations available for analysis and checking rather than relying on the agent to infer them correctly.

These connections depend on more than finding records with matching names. The representations must identify the intended entities, preserve the distinctions needed for the analysis, and remain related as the system changes. The next question is how to maintain that correspondence.

## Maintaining Correspondence {#maintaining-correspondence}

<!-- section-terms: map-and-territory, traceability, drift-gate -->

<!-- point: derive-and-join-do-not-repeat | Prefer shared identity and derivation over independently maintained copies of the same fact; where duplication is unavoidable, make the correspondence explicit and checkable. | terms: derive-and-join, join-key -->

<!-- index-def: derive-and-join -->

A connection remains useful only while the participating representations refer to the intended entities and preserve the relationships the analysis depends on. Shared identifiers help establish those relationships, but do not prevent the representations from drifting apart. Prefer references to a common source over independently maintained copies of the same fact. A deployment record can refer to the service catalog's identifier rather than copying the service's description and owner. A report can join the two records when it needs their combined information. Where a second representation must contain a copy, make its source and correspondence check explicit. Otherwise every copy becomes another fact engineers must remember to update.

<!-- point: a-family-of-models-risks-a-second-system-of-record-that-diverges | Multiple models can diverge from the system or one another; the correspondence mechanism depends on which representation owns each fact. | terms: map-and-territory, drift-gate -->

<!-- index-def: map-and-territory -->

Models and implementations can fall out of correspondence as a system changes. Maintaining their relationships requires deciding which representation is authoritative for each property and how correspondence with other representations should be established and checked. [ref:derive-generate-trace] distinguishes three arrangements:

<!-- point: where-neither-is-fully-derivable-maintain-traceability-and-check-decidable-predicates | Where neither model nor implementation fully determines the other, traceability records a defined relationship between model elements and current implementation targets so engineers and agents can inspect correspondence and assess the impact of changes. | terms: map-and-territory, traceability, drift-gate -->

<!-- index-def: traceability -->

- **Derive from implementation.** A dependency graph extracted from call sites describes the connections found in the code. A drift check can repeat the extraction and compare the result with a maintained view. Agreement covers the relationships the extraction observes.
- **Generate from models.** An authoritative schema can generate the types used by interface clients. A freshness check compares the checked-in types with the current generator output. The schema determines those types while leaving the client’s algorithms open.
- **Trace and check correspondence.** A behavioral model might specify permitted transitions while leaving their implementation to an agent. Traceability links each modeled transition to the functions that implement it. A check can establish that a referenced function still exists; whether it implements the transition correctly requires further evidence.

<!-- figure: assets/derive-generate-trace.svg | *Three correspondence patterns.* Derivation extracts models from implementation; generation produces implementation artifacts from models; traceability connects representations maintained independently. Each relationship covers selected properties or artifacts rather than necessarily determining the entire implementation. -->

<!-- point: the-computation-model-is-the-generate-case-execution-follows-it | A runner can read a task model to determine dependency order and readiness without generating a separate artifact. | terms: map-and-territory, derive-and-join -->

An authoritative model can also be interpreted directly during execution. Consider the build with two independent compilations and one link task. The runner reads the declared dependencies to start each compilation when it is ready and to delay linking until both object files exist. Nothing has to generate a schedule in advance. An engineer can query those same dependencies to find which task a changed object file could affect.

The third arrangement is particularly useful when agents implement systems whose models specify only selected properties. The models preserve engineering decisions while leaving other implementation choices open. The three arrangements can coexist within one system, and their coverage can change as engineers learn which properties need explicit representation. These correspondence patterns apply between models at different abstraction levels as well as between models and implementation; a refinement relationship identifies which higher-level properties a more detailed representation must preserve.

The following DocAble examples show how shared identities, derived dependencies, and checked correspondence connect models used for different engineering purposes.

DocAble uses connections among engineering models to answer questions about its remediation pipeline and deployed services. ### One Dependency for Execution and Analysis

Suppose we change a remediation pass. Which later computations depend on its output, and will they still execute in the required order? In [ref:chapter:2.3-structural], we introduced DocAble's remediation-computation graph for investigating dependencies. Connecting those dependencies to the execution declarations lets us examine their scheduling consequences without reconstructing the pipeline from code. For a DOCX job with table-header repair enabled, one pass marks table headers and another checks the table's structure. The registry declares that the repair pass writes table-header information and that the structure check reads it.

Matching that write to that read gives a dependency: repair must precede the check. The scheduler uses the dependency to order the work, so the check examines the table after the header pass has run.

<!-- point: a-separate-python-view-projects-the-model-for-analysis | The Office analytical graph projects resource edges from the same registry read/write metadata used by scheduling; the PDF projection uses parallel typed declarations held in correspondence by blocking checks. -->

The Office registry also emits its resource dependencies for a separate Python graph view. The edge from table-header repair to the structure check therefore comes from the same read/write metadata used by scheduling. An engineer can inspect which computations depend on table-header information, or join their identities to measurements, without executing the remediation pipeline. The Python graph provides the analytical view; the execution machinery does not schedule from it.

PDF uses a different connection. Its analytical edges are projected from parallel typed declarations of what each pass produces and consumes, including information consulted only to decide whether a pass runs. Blocking checks hold those declared relationships in correspondence with the executable pipeline.

<!-- point: one-source-of-truth-supports-both-directions | One set of Office read/write declarations supplies both scheduling and analysis; PDF analytical relations instead depend on checked correspondence with parallel declarations. -->

The Office example makes the same dependency available for execution and analysis; it does not derive a new relationship by joining independent models. The execution machinery uses the declared relationships to schedule work; the analytical view exposes the structure needed for queries and checks. The important question is which representation owns each fact and how each consumer remains connected to that source. Where separate declarations are necessary, as in the PDF view, checked correspondence carries that connection.

### What One Document Run Changed

<!-- point: event-grain-is-part-of-the-provenance-model | DocAble records consequential document mutations as typed operations; the selected grain supports audit, debugging, and a changelog. -->

A static computation graph does not record the mutations performed during a particular run. DocAble records consequential document changes as typed operations: each operation names its target, the mutation made, the responsible remediation pass, and the retained evidence. That history supports audit, debugging, and a changelog. Recording only “document modified” would lose the very distinctions those uses need.

<!-- point: a-typed-edit-record-replays-deterministically | Typed PDF edit values form a per-session log that a replay engine can apply deterministically while omitting the reasoning that produced them. -->

During a PDF remediation session, typed edit values form a per-session log. A replay engine can apply the same sequence deterministically. This record preserves the mutations while omitting the reasoning, analyses, control decisions, and retries that produced them. The computation graph asks what may compose; the edit record asks what happened to this artifact. [ref:two-reductions-static-realized] contrasts these two reductions.

<!-- point: proposed-edits-and-applied-history-are-different-representations | A typed changeset represents intended PDF mutations before application; per-operation results and attribution distinguish proposed changes from what was actually applied, independently of the producer's reasoning strategy. -->

DocAble’s PDF changeset interface also represents edits before they happen. A changeset is an ordered collection of typed operations, each naming a target and a supported mutation, such as assigning alternative text or changing a structural tag. The proposing computation does not manipulate PDF objects directly. An applier resolves the targets against the current document and returns a result for each operation. The proposal expresses intended mutations; the results and attribution record show what was actually applied.

A specialized remediation pass, a general-purpose agent, or a human editor can propose operations using the same vocabulary. The interface preserves the information needed to apply and inspect the change while leaving its producer’s reasoning unspecified. {{chapter:alignment}} examines the constraints on applying such proposals; {{chapter:software-factories}} returns to the reasoning strategies that can produce them.

<!-- point: record-and-replay-separate-three-questions | Declared computations, recorded mutations, and replay answer what may compose, what happened in a run, and whether its recorded mutations can be reproduced. -->

A shared computation identity can join the recorded edits to the static model when needed, while preserving the distinction between what was declared and what happened. -->

<!-- point: provenance-boundary-model-records-a-lint-guarantees-every-mutator-stamps | Structural checks require attribution records but do not establish the semantic correctness of their content. | terms: soft-vs-hard-governance -->

DocAble joins staged-run latency and cost to stable computation identities, so measurements can be queried alongside the static graph. The per-session edit log remains a separate provenance record; it is not a per-run execution graph over computation nodes. Recording attribution is also distinct from ensuring that every mutation records it. A structural check requires typed mutation operations to emit attribution, but it cannot establish that the semantic explanation inside the record is correct.

### Joining a Call to Its Deployment Permission

<!-- point: the-interservice-edge-is-a-worked-join | One typed interservice-call edge joins to deployment configuration for the callee URL, to runtime identity for the required invocation grant, and to the service catalog for topology agreement; 28 modeled edges produce 10 distinct grants, a deployment plan no single artifact contains. | terms: derive-and-join, join-key -->

A permitted interservice call requires several models to agree. A typed edge records that one service may call another. Deployment configuration identifies the environment variable carrying the callee's URL. The caller's runtime identity determines which invocation grant the cloud's access-control configuration must contain. Joining the edge to these records determines both how to reach the callee and who is permitted to invoke it; a further comparison checks agreement with the service catalog's documented topology. Twenty-eight modeled call edges produce ten distinct invocation grants once shared runtime identities are accounted for. No single source artifact contains that deployment plan.

DocAble introduced the join after service URLs were wired correctly but the matching invocation grant was absent, taking staging down with authorization errors. The repair made URL wiring and authorization two consequences of the same modeled edge, so a later change could derive them together rather than requiring another bespoke grant.

<!-- point: connections-can-create-information | Connections can create information that no individual model contains: the call model lacks the environment-specific runtime identity, the deployment environment does not state the intended topology, and their join determines the permission that should exist. | terms: derive-and-join, join-key -->

Connections can create information that no individual model contains. The call model does not contain the environment-specific runtime identity; the deployment environment does not independently state the intended call topology. Joining them determines the permission that should exist.

Each connection has a specific purpose. Resource declarations supply a dependency, computation identities connect measured cost to a pass, an edit record explains a document change, and a call joined to a deployment identity determines a permission. Keeping these relationships explicit lets engineers inspect the evidence behind each analysis and detect disagreements between representations.
