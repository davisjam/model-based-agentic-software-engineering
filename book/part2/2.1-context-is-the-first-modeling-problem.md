# Context Is the First Modeling Problem

<!-- section-terms: thesis-modeling, reasoning-horizon, context-window -->

<!-- point: a-reasoner-arrives-knowing-nothing-about-your-system | A commodity reasoner arrives knowing almost nothing about your system. | terms: reasoning-horizon, context-window, thesis-modeling -->
A commodity reasoner arrives knowing almost nothing about your system. Its training gave it
languages, frameworks, patterns, and general engineering sense. It did not give it your services,
your ownership boundaries, your deployment topology, the invariant you added last quarter, or
yesterday's migration. Every one of those facts lives in your repository, and the agent starts each
task without them.

<!-- point: rediscovery-is-the-binding-cost-at-system-scale | Rediscovering the system from source is the binding cost at scale. | terms: reasoning-horizon, context-window, long-horizon-task -->
You can make it rediscover them. Point it at the source and let it read its way to an understanding
of what calls what and who owns which service. That works until the system grows past the point
where discovery fits in a window. Rediscovery consumes context, reconstruction consumes reasoning,
and both are paid again the next time another agent arrives with an empty window. At system scale,
the rediscovery tax is the cost that binds.

<!-- point: the-first-purpose-of-a-model-is-better-context | The first purpose of a model is modest: give the intelligence better context. | terms: thesis-modeling, reasoning-horizon, context-window -->
The first purpose of a model is therefore modest. Before it verifies anything, before it governs
anything, a model gives the intelligence better context. Externalize the system knowledge an agent
should not have to rediscover. Name the services, modules, APIs, queues, owners, deployment
targets, requirements, policies, and tests. Name the relations among them. Now the agent does not
carry the whole estate in its window. It retrieves the connected slice the task needs and leaves
the rest on disk.

## The system knowledge graph

<!-- section-terms: system-knowledge-graph, structured-relationships -->

<!-- point: the-simplest-useful-form-is-a-graph | The simplest useful form of that knowledge is a graph. | terms: system-knowledge-graph, structured-relationships -->
<!-- index-def: system-knowledge-graph -->
The simplest useful form for that knowledge is a graph. Call it the *system knowledge graph*. Its
nodes are engineering entities: services, modules, endpoints, queues, databases, deployment
targets, requirements, tests, owners, and policies. Its edges name the relations among them: calls,
depends on, deployed to, owned by, implements, verified by, governed by. Properties hang from both.
A service has a tier; an endpoint has an authentication requirement; a deployment has a region.

<!-- point: graph-is-structure-not-storage | Graph names the structure, not the storage technology. | terms: system-knowledge-graph, structured-relationships -->
The graph need not live in a graph database. Assemble it from YAML, repository metadata,
infrastructure declarations, schemas, and registries joined on stable identifiers, and you have the
same graph. The word *graph* names the structure, not the storage technology. What matters is that
the knowledge has stable entities, explicit relations, and machine-readable joins, so a tool or an
agent can traverse it instead of re-deriving it from raw files each time.

<!-- point: relevance-follows-relationships | Context engineering expressed structurally: relevance follows relationships. | terms: context-engineering, system-knowledge-graph, structured-relationships -->
<!-- index-def: context-engineering -->
This is *context engineering* expressed structurally. Choosing what to put in the prompt stops
being a guess about which documents might help. It becomes a question with a structural answer:
which engineering facts and relations does this task touch? A graph makes that answer tractable,
because relevance can follow relationships. Start at the service the task names, and the neighbors
it needs come with it — its callers, the queue it consumes, the policy that governs the queue, the
tests that carry the policy. The agent reasons over a connected slice instead of a document dump.

## Industry already lives here

<!-- section-terms: knowledge-representation, externalized-knowledge, thesis-modeling -->

<!-- point: knowledge-rep-is-the-first-rung | Externalized knowledge representation is the first rung of the Modeling Thesis. | terms: knowledge-representation, thesis-modeling, externalized-knowledge -->
<!-- index-def: knowledge-representation -->
<!-- index-def: externalized-knowledge -->
Externalizing knowledge this way is the first rung of the Modeling Thesis, and much of current
industrial practice already stands on it. Service catalogs expose components and ownership.
Dependency graphs expose what calls what. Infrastructure-as-code exposes placement. Policy corpora
expose obligations. Developer portals join these surfaces for the engineers who read them and,
increasingly, for the agents that reason over them. This is *knowledge representation*: engineering
knowledge moved out of a person's head, or an agent's transient context, into an artifact the next
one can retrieve rather than reconstruct.

<!-- point: knowledge-rep-universal-graph-common-executable-not | Knowledge representation is universal in the corpus; graph-shaped representation common; invariant-bearing models not. | terms: knowledge-representation, system-knowledge-graph, thesis-modeling -->
State the reach of that claim carefully, because the evidence later in this book is precise about
it. Knowledge representation is universal in the corpus; graph-shaped system representation is
common; invariant-bearing executable models are not. The organizations studied differ in how
strongly they structure the knowledge, yet all of them externalize facts an agent would otherwise
reconstruct. Zenseact makes the motive explicit: its routing machinery selects the task-relevant
expertise and loads only that, rather than pouring the whole corpus into the window. Context
engineering is the purpose; a knowledge graph is one strong way to serve it, and not the only one.

<!-- worked-examples: externalized-knowledge -->
### Example — Spotify
Spotify externalized its service estate before its agents arrived. The Backstage catalog names
every service, its owners, its dependencies, and its endpoints, each with a stable identity a tool
can resolve — the estate written down as a retrievable graph rather than carried in anyone's head.
An agent that lands on a migration reads the slice the task touches out of that catalog instead of
crawling thousands of repositories to reconstruct it.

### Example — Cloudflare
Cloudflare externalized its standards, not its system, and that is the instructive limit. It turned
a sprawl of RFCs into a curated corpus where every requirement carries a stable slug that survives
the edits around it, so an agent retrieves the obligation that governs a change without its author
present. The obligations are represented far more strongly than the system they govern, which stays
mostly unmodeled. Knowledge representation is strong here; system modeling is not — the first rung
climbed while the higher ones are left for later.

### Example — Shopify
Shopify externalizes knowledge more softly. Every public agent session becomes a searchable artifact
the company mines into skills, conventions, and defaults, so one engineer's experience is retrieved
by the next agent rather than lost when the window closes. The representation is informal — prose
skills loaded on demand, not a structured model of the system — which is externalization at the first
rung: real, retrievable, and deliberately soft.

### Example — DocAble
DocAble is one software implementation of the pattern. It assembles a system knowledge graph from
registries, schemas, and YAML joined on stable identifiers, so an agent retrieves the connected slice
a task needs instead of re-reading the repository each time. It reaches deeper rungs later in this
Part, but here it does only what the others do: move the system's facts out of the window and onto
disk where the next agent can find them.

<!-- takeaway -->
The shared move is *externalized knowledge*: put the system's entities and relations in a durable,
retrievable artifact so the next agent inherits them instead of rediscovering them. It is the first
rung of the Modeling Thesis, and the one every organization here already stands on — the strength
varies from a typed catalog to a corpus of prose skills, but the externalization is universal.
<!-- worked-examples-end -->

<!-- point: legibility-is-only-the-first-rung | Legibility is only the first rung; structured knowledge can tell the environment what must be true. | terms: thesis-modeling, thesis-alignment, structured-relationships -->
But legibility is only the first rung. A graph that makes the system legible tells an agent what to
think about. It does not yet tell the environment what must be true. Once the knowledge has
explicit structure, the same representation can carry more than context. It can carry engineering
intent a machine is able to check. That is the next step, and it is where modeling begins to turn
into control.
