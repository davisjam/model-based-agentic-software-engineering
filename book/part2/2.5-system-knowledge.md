# System Knowledge: Connecting the Models

<!-- point: different-questions-drew-different-models-joined-where-needed | Different questions require different models of one system; shared identity and explicit correspondence connect them where a question crosses views. | terms: system-knowledge, modeling-substrate -->

Different questions require different models of the same system. A service catalog names components, a deployment model places them in an environment, a lifecycle model records their states, and an execution record reports what happened. These representations need not become one large model. They need to agree on the identities and relationships that engineering questions cross. MBSE methods connect requirements, design models, analyses, and verification results so that engineers can follow a decision across these representations.[cite: estefan2008mbse][cite: madni2018mbse]

## A Heterogeneous Modeling Substrate

<!-- section-terms: system-knowledge, modeling-substrate -->

<!-- index-def: modeling-substrate -->

A **modeling substrate** is the collection of representations through which engineers and agents can recover and relate consequential system knowledge. Its models can differ in shape: a registry, a state machine, a decision table, and a measurement record each preserve what their questions need. A shared service identifier can connect a catalog entry to a deployment and its measurements without requiring those records to share a file format. SysML provides one formal account of views: a viewpoint identifies stakeholder concerns, and a view selects and presents model content to address them.[cite: omg2025sysml]

<!-- point: the-unity-that-matters-is-semantic-not-syntactic | Shared identities let different representations refer to the same service, work item, or operation without requiring a common file format or metamodel. | terms: modeling-substrate, join-key -->

Suppose an agent is investigating a slow report service. The catalog supplies the service's owner, the deployment model supplies its resource allocation, and the measurement record supplies recent response times. Each record uses the same service identity. The agent can follow those connections to obtain the relevant facts; it does not have to reconstruct from names and directory locations whether the three records describe the same component.

<!-- point: derive-and-join-do-not-repeat | Prefer shared identity and derivation over independently maintained copies of the same fact; where duplication is unavoidable, make the correspondence explicit and checkable. | terms: derive-and-join, join-key -->

<!-- index-def: derive-and-join -->

Prefer shared identity and derivation over independently maintained copies of the same fact. A deployment record can refer to the service catalog's identifier rather than copying the service's description and owner. A report can join the two records when it needs their combined information. Where a second representation must contain a copy, make its source and correspondence check explicit. Otherwise every copy becomes another fact engineers must remember to update.

### Execution History and Provenance

<!-- point: join-static-and-runtime-only-when-a-question-pays | A static model and a history answer different questions; stable task identity permits a join when observations help answer a structural question. | terms: derive-and-join, join-key -->

A static model and a history answer different questions. A workflow model says which tasks depend on which; an execution record says which tasks ran on a particular occasion. Joining duration measurements to task identities can reveal an expensive part of the workflow without turning the dependency graph into a log. The history still needs its own model because the useful events and their grain depend on the question.

<!-- point: observable-history-is-not-automatically-useful-a-provenance-model-selects-it | A provenance model selects the history needed to answer an engineering question rather than recording every observable event. -->

For example, a text editor's provenance record might name an insertion or deletion, its target, the resulting change, and the actor or operation responsible. “Document changed” would be too coarse to explain an edit; a trace of every memory access would bury the edit in irrelevant detail. The provenance model selects the events that support explanation. If those edits have defined replay semantics and the original document is available, replay can apply the recorded sequence again. That does not reconstruct the reasoning that led to the edits.

### Questions that span models

<!-- point: joining-models-makes-cross-representation-properties-available | Joining models makes properties that cross individual representations available for reasoning. | terms: derive-and-join, join-key, modeling-substrate -->

Some answers require a join. Suppose the policy allows a report service to invoke a renderer. The policy names the two services, while the deployment model records the runtime identity under which the report service runs. Joining the permitted call to that identity determines which principal needs permission to invoke the renderer. Neither model contains that complete answer by itself: the policy does not name the environment's principal, and the deployment record does not decide which calls should be permitted.

A model can also connect an obligation to its evidence. A latency requirement might identify the workload and response-time bound, while a test catalog identifies the measurement that evaluates them. Linking the requirement to that test makes a missing measurement visible. SysML represents this relationship through verification cases that identify the subject and the requirements to be evaluated.[cite: omg2025sysml] Whether the test supplies adequate evidence, and whether its result should block release, remain further engineering decisions.

<!-- point: joins-are-also-where-information-is-lost | A join can preserve entity identity while losing a distinction needed by the decision; shared identity does not establish semantic adequacy. | terms: derive-and-join, model-drift -->

A join only works if it preserves the distinctions the decision needs. A record may use the correct user identifier and still reduce an unlimited entitlement to a finite-credit balance. Shared identity makes the connection explicit; it does not guarantee that the information passed across it is adequate.

<!-- point: an-agent-enters-through-the-object-its-task-names-and-traverses-outward | An engineer or agent can begin at the entity named by a task and follow the modeled relationships required by its engineering question. | terms: modeling-substrate, join-key -->

An engineer or agent can therefore enter through the object named by a task and follow the relations its question requires: from service to owner, from service to deployment, from deployment to measurement. A query interface makes these connections traversable. The agent needs the connected slice that answers the question, rather than every model in the project. [ref:substrate-traversal] draws that outward walk.

## Maintain Explicit Correspondence

<!-- section-terms: map-and-territory, traceability, drift-gate -->

<!-- point: a-family-of-models-risks-a-second-system-of-record-that-diverges | Multiple models can diverge from the system or one another; the correspondence mechanism depends on which representation owns each fact. | terms: map-and-territory, drift-gate -->

<!-- index-def: map-and-territory -->

Multiple models create a correspondence problem: represented facts can diverge from the system or from one another. Engineer the relationship between map and territory so divergence is caught rather than assumed away. Which machinery you reach for depends on which side is the source of truth.

<!-- point: name-the-direction-of-derivation-up-front | Maintain correspondence according to the source of truth: derive a view from implementation, generate an artifact from a model or read the model during execution, or maintain traceability where neither side fully determines the other. | terms: derivation-direction, model-from-code, model-to-code -->

<!-- index-def: derivation-direction -->

Make the direction of correspondence explicit. Where the implementation is the source of truth, derive the model. Where the model is the source of truth, a generator can produce the downstream artifact, or a runner can read the model directly during execution. Where neither fully determines the other, maintain traceability and check the mechanically decidable correspondences. Model-transformation languages make such relationships executable: OMG's Query/View/Transformation (QVT) standard can check a declared relation between models or update a target model to satisfy it.[cite: omg2016qvt] [ref:derive-generate-trace] shows derivation, generation, and traceability; direct interpretation is another way to use an authoritative model.

<!-- index-def: model-from-code -->

<!-- index-def: model-to-code -->

### Derive when implementation owns the truth

The model is a projection of the implementation. A component registry can read the directory tree; an observed dependency list can be induced from call sites. A drift check re-derives the selected facts and reports divergence from the maintained view. The correspondence covers what that derivation observes, not every property of the program.

### When the model is the source of truth

**Generation** produces an artifact from a model: code, configuration, or documentation. For example, a schema can generate the types used by interface clients. A freshness check compares the checked-in artifact with current generator output; provenance identifies the model and generation step that produced it. The generator preserves that declared correspondence while leaving open whether the schema expresses the right contract.

<!-- label: derive-generate-trace -->
<!-- figure: assets/derive-generate-trace.svg | *Three correspondence patterns.* Derivation produces a view from implementation; generation produces an artifact from a model; traceability relates representations neither of which fully determines the other. A runtime can also interpret a model directly, as the build example below illustrates. -->

<!-- point: the-computation-model-is-the-generate-case-execution-follows-it | A runner can read a task model to determine dependency order and readiness without generating a separate artifact. | terms: map-and-territory, derive-and-join -->

**Interpretation** uses the model directly during execution, without generating a separate artifact. Return to the build with two independent compilation tasks and one link task. The build declaration names each task and states that linking requires both object files. A runner reads those declarations to decide which tasks are ready: it may start the independent compilations, but it must wait for both results before linking. The compiler and linker still perform the individual operations. Their dependency order comes from the build declaration.

The same declaration can answer a question without running the build. To find what a changed object file could affect, project the declared dependencies into a graph and follow its outgoing edges. In this example, the path reaches the link task. The runner uses the relationships to schedule work; the analytical view exposes them for queries and checks. DocAble's connected-models inset develops these two uses and shows how the correspondence differs across document formats.

> #### Worked example — Connecting the views of a document service {#inset-docable-connected-models}
>
> DocAble improves document accessibility through passes that analyze or change a document. Workers and services execute those passes, and the product retains evidence about the resulting artifact. Its modeling problem therefore crosses several views: the intended computation, the execution arrangement, and what one run actually changed. The worked question is how those views can share facts without becoming independent accounts that drift apart.

> <!-- point: a-heterogeneous-substrate-of-structured-records | DocAble's models differ in shape on purpose: roughly 130 structured model records plus data dialects share identities, derivations, query surfaces, and traceability where useful, are represented as data so map and territory stay separable, and nothing forces them into a single representation. | terms: modeling-substrate, representation-form, map-and-territory -->
>
> DocAble uses different representations for different engineering questions. Registries describe components and their relations; state machines describe transitions; other models encode contracts, decisions, quantitative relationships, or recorded history. Roughly 130 structured model records plus several data dialects represent component identity and metadata, deployment topology, inter-service edges, data flow, required environment, state machines, and the governance graph itself. They share identities, derivations, query surfaces, and traceability where engineers need to connect them, while retaining the form suited to each question. Where a model is intended to provide independent evidence about an artifact, the model must remain distinguishable from that artifact. {{chapter:software-factories}} shows how this modeling substrate is maintained and used in the governed engineering environment.

> The Office registry also emits its resource dependencies for a separate Python graph view. The edge from table-header repair to the structure check therefore comes from the same read/write metadata used by scheduling. An engineer can inspect which computations depend on table-header information, or join their identities to measurements, without executing the remediation pipeline. The Python graph provides the analytical view; the execution machinery does not schedule from it.

Its analytical edges are projected from parallel typed declarations of what each pass produces and consumes, including information consulted only to decide whether a pass runs. The execution machinery uses the declared relationships to schedule work; the analytical view exposes the structure needed for queries and checks. The important question is which representation owns each fact and how each consumer remains connected to that source. Where separate declarations are necessary, as in the PDF view, checked correspondence carries that connection.

>
> A static computation graph does not record the mutations performed during a particular run. DocAble records consequential document changes as typed operations: each operation names its target, the mutation made, the responsible remediation pass, and the retained evidence. This record preserves the mutations while omitting the reasoning, analyses, control decisions, and retries that produced them. The computation graph asks what may compose; the edit record asks what happened to this artifact. [ref:two-reductions-static-realized] contrasts these two reductions.
>

>
> <!-- point: provenance-boundary-model-records-a-lint-guarantees-every-mutator-stamps | Structural checks require attribution records but do not establish the semantic correctness of their content. | terms: soft-vs-hard-governance -->
>
> DocAble joins staged-run latency and cost to stable computation identities, so measurements can be queried alongside the static graph. The per-session edit log remains a separate provenance record; it is not a per-run execution graph over computation nodes. Recording attribution is also distinct from ensuring that every mutation records it. A structural check requires typed mutation operations to emit attribution, but it cannot establish that the semantic explanation inside the record is correct.
>
> **Joining a call to its deployment permission**
>
> <!-- point: the-interservice-edge-is-a-worked-join | One typed interservice-call edge joins to deployment configuration for the callee URL, to runtime identity for the required invocation grant, and to the service catalog for topology agreement; 28 modeled edges produce 10 distinct grants, a deployment plan no single artifact contains. | terms: derive-and-join, join-key -->
>
> A permitted interservice call requires several models to agree. A typed edge records that one service may call another. Deployment configuration identifies the environment variable carrying the callee's URL. The caller's runtime identity determines which invocation grant the cloud's access-control configuration must contain. Joining the edge to these records determines both how to reach the callee and who is permitted to invoke it; a further comparison checks agreement with the service catalog's documented topology. Twenty-eight modeled call edges produce ten distinct invocation grants once shared runtime identities are accounted for. No single source artifact contains that deployment plan.
>
> DocAble introduced the join after service URLs were wired correctly but the matching invocation grant was absent, taking staging down with authorization errors. The repair made URL wiring and authorization two consequences of the same modeled edge, so a later change could derive them together rather than requiring another bespoke grant.
>
> <!-- point: connections-can-create-information | Connections can create information that no individual model contains: the call model lacks the environment-specific runtime identity, the deployment environment does not state the intended topology, and their join determines the permission that should exist. | terms: derive-and-join, join-key -->
>
> Connections can create information that no individual model contains. The call model does not contain the environment-specific runtime identity; the deployment environment does not independently state the intended call topology. Joining them determines the permission that should exist.
>
> **Connecting a property to its checker**
>
> <!-- point: a-declared-property-can-determine-what-evidence-must-exist | For concurrency properties, modeled facts select the required checker kind under a project rule; engineers supply the checker, and a repository check verifies the declared kind and referenced file. | terms: derive-and-join, drift-gate -->
>
> DocAble also links a property to the checker required to examine it. A document job can arrive more than once, so concurrent deliveries must not each dispatch a new set of child jobs. The state-machine model records the participants, the atomic database operation used to claim the job, and the requirement that dispatch occur at most once. The project's verification policy uses those facts to require a checker that explores every reachable state of a bounded model. DocAble calls this requirement a *verification tier*: a category that selects the required kind of check.
>
> Engineers and their agents write and maintain the checker code. For this property, a separately authored Python model represents three deliveries and their claim, dispatch, and acknowledgement steps. A reusable search routine explores their possible orderings and checks that dispatch occurs at most once. Disabling the modeled atomic claim produces duplicate dispatch, confirming that the check can detect the fault it targets. The invariant record cites this checker. A repository check follows the citation and requires an existing file and the declared checker kind specified by the tier. Running the checker and judging whether its bounded model adequately represents the implementation remain separate tasks. {{chapter:alignment}} examines how to assess the evidence and decide whether a failed check should block a commit.
>
> Each connection has a specific purpose. Resource declarations supply a dependency, computation identities connect measured cost to a pass, an edit record explains a document change, and a call joined to a deployment identity determines a permission. Keeping those relations explicit lets engineers inspect the connection that an analysis depends on, instead of treating membership in a model family as evidence that the models agree.

<!-- point: derivation-solves-correspondence-not-architecture-quality | A derived analytical graph still omits implementation detail, and derivation preserves only its declared correspondence rather than establishing architecture quality. | terms: map-and-territory, alignment-principle -->

An analytical graph remains a view even when its edges are derived. It can suppress method bodies, internal algorithms, runtime history, timing, and most application state while keeping the relationships needed for a structural question. Deriving an edge avoids maintaining that edge independently. It does not show that the declared dependency is desirable, or that the graph includes every relationship a different question might need.

<!-- point: where-neither-is-fully-derivable-maintain-traceability-and-check-decidable-predicates | Where neither model nor implementation fully determines the other, traceability records a defined relationship between model elements and current implementation targets so engineers and agents can inspect correspondence and assess the impact of changes. | terms: map-and-territory, traceability, drift-gate -->

<!-- index-def: traceability -->

### Trace and check where neither owns the truth

Where neither side can be fully derived from the other, **traceability** records their relationship explicitly. A behavioral model might link a transition to the functions that implement it while leaving their algorithms unspecified. The relation lets an engineer or agent find the relevant implementation from the model and identify which model elements may need review after a code change. Each link needs a defined meaning and a target that can be identified in the current system. These links make the claimed correspondence available for inspection and checking.

<!-- point: two-layers-cover-the-relationship-mechanical-and-judgment | Mechanical correspondence has a declared surface: some claims are decidable, others remain semantic and require judgment, unmodeled properties have no model-based coverage, and a recurring miss is a candidate for refining the representation or adding a control. | terms: drift-gate, map-and-territory, model-drift -->

### Some correspondence remains semantic

Mechanical checks establish only the correspondences they evaluate. They can determine whether an anchor resolves, an observed dependency belongs to the permitted set, or a generated artifact is current. Those results do not settle every question about the model's meaning: semantic claims may still require judgment, and properties left out of the model receive no model-based coverage. When a failure recurs, engineers can ask whether to refine the representation or add a control ([ref:model-sync-two-layer-net]).

<!-- label: model-sync-two-layer-net -->
<!-- figure: assets/model-sync-two-layer-net.svg | *Coverage of model correspondence.* Mechanical checks cover only claims the representation makes decidable; semantic claims still require judgment, and unmodeled properties have no model-based coverage. -->

<!-- point: an-executable-model-is-its-schema-plus-its-checked-predicates | A structured schema plus checked predicates is one executable-model pattern; generation, simulation, transformation, and analysis are others, and correspondence to a changing system still requires checks or derivations. | terms: drift-gate, modeling-principle -->

For invariant-bearing models, one useful executable pattern is a structured schema plus checked predicates over that schema. The schema defines entities, relations, fields, or states; the predicates state properties that a checker evaluates over the declared domain. Other executable models may instead drive generation, simulation, transformation, or analysis. A schema alone does not establish correspondence to a changing system; checks or derivations are needed where that correspondence matters. [ref:coherence-triangle] draws that relationship.

<!-- label: coherence-triangle -->
<!-- figure: assets/coherence-triangle.svg | *Checked predicates over a structured model.* A structured model supplies the domain; invariants state properties over that domain; a checker evaluates them at a declared cadence. This is one executable-model pattern, not the definition of executability. -->

<!-- point: no-synchronization-mechanism-proves-semantic-correctness | Synchronization does not establish that the model is correct; a model can be perfectly in sync and still express the wrong architecture. | terms: map-and-territory, drift-gate, modeling-principle -->

None of this proves the model *right*. Synchronization does not establish that the model is correct, that the architecture it expresses is good, or that the modeled surface captures every relationship that matters. A pointer can resolve while its meaning has changed; a schema and its generated client can agree while a live producer emits something else. The guarantee the machinery offers is narrower:

> **For the surface the model claims, check the correspondence that can actually be decided.**

<!-- point: the-narrow-guarantee-is-the-boundary-part-iii-begins-at | Correspondence follows the source of truth: derive an implementation view, generate an artifact or interpret an authoritative model, and trace and check where neither representation fully determines the other. | terms: modeling-principle, alignment-principle, map-and-territory -->

Derive views from the implementation when it supplies the facts. When the model supplies them, generate artifacts from it or let execution read it directly. Where neither fully determines the other, maintain traceability and check the declared correspondence.

## Modeling Makes Properties Available to Engineering

<!-- point: a-model-does-not-govern-by-existing-it-makes-a-property-explicit | Models make properties explicit; whether to enforce them is a separate decision. | terms: modeling-principle, alignment-principle -->

A model does not govern the system merely by existing. A structural model can name a forbidden dependency without preventing it; a behavioral model can name an illegal transition without rejecting it; a measurement model can represent a budget without stopping work that exceeds it. Modeling makes these properties explicit. It does not enforce them.

Suppose a worker-pool model records the number of running jobs and the capacity available to execute them. The comparison may help an operator plan a larger pool, help the system tune admission, or supply a hard rule that refuses work above the bound. Those uses require different mechanisms. The quantities and their units make the comparison meaningful; they do not decide what crossing the bound should do.

<!-- point: measurement-boundary-modeling-and-enforcement-are-separate | A measurement model defines quantities and their reference bounds; observation, adaptation, and enforcement require separate decisions and mechanisms. -->

[ref:modeling-perp-enforcement] draws that separation. A measurement can supply evidence without being a hard limit. Engineers must also decide who chooses the reference value, how the quantity is collected, and what action follows from the comparison.

<!-- label: modeling-perp-enforcement -->
<!-- figure: assets/modeling-perp-enforcement.svg | *Modeling and enforcement are separate decisions.* The measurement model defines the quantity and reference bound; Alignment determines whether the result is observed, used to adapt behavior, used to trigger graceful degradation, or enforced by a gate. -->

<!-- point: relational-obligations-need-enough-representation | Local syntactic obligations need little modeling; architectural boundaries, temporal obligations, distributed ownership, provenance, and end-to-end policy need enough representation to expose the relevant relationships, which Modeling makes available to analysis and governance. | terms: modeling-principle, alignment-principle -->

Local syntactic obligations can often be checked with little explicit modeling. Architectural boundaries, temporal obligations, distributed ownership, provenance requirements, and end-to-end policies require enough representation to expose the relevant system relationships. Modeling makes those relationships available to analysis and, where appropriate, to governance.

They are also available to design. A dependency graph may reveal that an execution boundary is artificial; a behavioral model may expose a recovery protocol that should change; a quantitative model may show that an otherwise plausible decomposition cannot meet its resource envelope. In each case, analysis of the model can change the architecture before implementation commits to the choice.

<!-- point: alignment-does-not-require-a-separately-represented-model | Alignment does not require every obligation to have a separately represented model — some properties are observable at an action or artifact boundary and can be constrained directly; models extend the range of properties available for analysis and enforcement. | terms: modeling-principle, alignment-principle -->

Alignment does not require every obligation to have a separately represented model. Some properties are already observable at an action or artifact boundary and can be constrained directly. Models extend the range of properties available for analysis and enforcement.

<!-- point: docable-models-arose-around-expensive-questions | Models are justified by engineering questions whose relevant distinctions would otherwise be expensive or unsafe to reconstruct; shared identities connect views where a decision crosses them. | terms: modeling-principle, model-classes -->

The examples began with engineering questions: where a dependency belongs, which state changes are allowed, who owns a job, what a decision permits, and which facts must be joined. Different questions required different reductions. Shared identity and explicit correspondence connect them where a decision crosses views.

{{chapter:alignment}} asks which obligations the engineered environment should enforce, where they become decidable, and what evidence and mechanisms are sufficient to enforce them.

> #### Deep dive — Beneath commodity intelligence: why structure helps {#inset-beneath-commodity-intelligence}
>
> Research on context engineering and agent architectures treats the organization of work as part of the reasoning system. Across this literature, external memory, selective retrieval, tool interaction, and task decomposition determine what information a reasoning step receives and what it must do with that information.[cite: mei2025contextengineering][cite: wang2024autonomousagents] Access to state remains different from reasoning over it. Keeping a record available does not ensure that the agent will recover the relationships needed for a particular decision. Organizing the information and dividing the work can reduce what each step must search, reconstruct, or infer. Anthropic's agentic coding guidance separates exploration and planning from implementation and recommends explicit tests.[cite: cherny2025agenticcoding]
>
> Engineering models supply a further kind of structure: a representation of the system that gives those reasoning steps shared meaning. A harness may divide a change into tasks. Kiro, for example, organizes the work in requirements, design, and task documents that developers can review.[cite: swaminathan2025kiro] An architecture model can identify the components and permitted calls those tasks must respect. A behavioral model can expose an ordering that spans several tasks. Links between models and implementation let an agent move from a modeled relationship to the affected code and follow connections into other parts of the system. Engineers can therefore shape both how the agent performs the work and the system knowledge through which it reasons.
>
> Explicit models also make delegated implementation easier for engineers to direct. This follows the MBSE practice of making system specifications, design decisions, and their verification explicit and traceable.[cite: madni2018mbse] Engineers can inspect the relationships a proposed change must preserve and decide which failed checks should block acceptance. Agents can use those representations to plan work and choose how to implement it within the declared bounds. Because the decisions are recorded in project artifacts, engineers can carry them forward when they change the foundation model or harness. They can also revise the models and checks when the requirements change. The same structure that reduces reconstruction for agents keeps the decisions governing their work available for human inspection and revision.

<!-- point: part-2-ends-where-part-3-begins-the-models-already-pay-enforcement-is-a-separate-question | Models preserve decisions, expose relationships, and support analysis; the next engineering question is which obligations to enforce and through what evidence and mechanisms. | terms: modeling-principle, alignment-principle -->

In {{chapter:alignment}}, we take up the next engineering decision: which obligations the engineered environment should enforce, where they become decidable, and what evidence and mechanisms are sufficient. {{chapter:one-problem-many-models}} follows these ideas through successive engineering decisions in one system. {{chapter:software-factories}} returns to these models as part of the engineering environment surrounding agentic production, and {{chapter:theory}} examines when carrying explicit representations is worth their cost.
