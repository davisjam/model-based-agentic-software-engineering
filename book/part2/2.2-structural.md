# Structural Models: What Is Connected to What?

Structural models hold a system still. They suppress most behavior and keep the entities, boundaries, containment, dependency, and flow — what parts exist and which rest on which. This is the most familiar reduction in engineering, and the natural place to begin.

## The Canonical Move: Structure and Dependency

<!-- point: structure-has-a-long-repertoire-of-graphs-that-keep-entities-and-relations | Component and dependency graphs, call graphs, data-flow diagrams, and deployment topologies all name the entities a question needs and the declared relations between them, and drop the behavior. -->

A component diagram names which services exist; a dependency graph names which modules rest on which; a call graph names which procedures may invoke which; a data-flow diagram names how information moves through transformations; a deployment topology names what is connected across execution locations. The graphical forms differ, but the reduction is the same: keep the entities and the declared relations, discard the behavior ([ref:canonical-structural]).

<!-- point: a-structural-model-selects-both-entities-and-relations-and-the-edge-label-carries-the-meaning | A structural model selects the entities a question needs and the relations between them; the edge label specifies the relationship being modeled, so a generic "related-to" edge discards the distinction the model exists to preserve. -->

The model selects both the entities and the relations. A graph of service boundaries should not carry every helper function; if the question is about architecture, that detail only makes the model worse. The edge label specifies the relationship being modeled. "A depends on B," "A calls B," and "a record is stored in a database" are different relations; collapsing them into a generic "related-to" edge throws away exactly the distinction the model was built to preserve.

<!-- point: once-structure-is-explicit-the-properties-are-graph-properties-and-the-analyses-graph-operations | Explicit structure turns the claims an engineer wants into graph properties — local, path, or whole-graph — and the analyses into ordinary graph operations: reachability, reverse traversal, cycle detection, impact and conformance. -->

Once structure is explicit, the claims an engineer wants become graph properties. Some are local: component A may not depend directly on component C. Some concern paths: every route from ordinary logic to a format-specific library must cross a sanctioned seam. Some concern the whole graph: the dependency relation must be acyclic. The analyses follow — reachability, reverse traversal to find what depends on a node, cycle detection, impact analysis over a proposed change, and conformance of an observed graph against a declared one. A question that would otherwise mean reading imports, configuration, and deployment manifests becomes an operation over a declared graph.

<!-- point: derived-structure-and-declared-structure-are-different-claims | Static analysis can derive the graph from code and engineers can declare it as intent; one describes what the system appears to do, the other what it is supposed to do, and Chapter 3 treats the difference. -->

Static analysis can sometimes derive the graph from the implementation; in other cases engineers declare the architecture as intent. Those are different claims: one describes what the system appears to do, the other what it is supposed to do. {{chapter:alignment}} treats the distinction carefully.

## Choose the Relation for the Question

Suppose a web application's user interface should reach its database only through an application service. A three-layer model can represent that boundary: user interface, application service, database. The property concerns paths. Every route from the interface to the database must cross the service; a direct interface-to-database edge would violate the intended architecture. The model can omit the service's internal algorithms because those details do not decide whether the boundary is crossed.

A build dependency graph answers a different question. Suppose two independent source files are compiled and their object files are then linked into one executable. Model the compilation tasks and the link task as nodes, with an edge from each compilation to linking. The two edges express what linking needs. A change to one compilation result affects the link task, but the graph gives no reason to rerun the other compilation. This is a dependency question, so the useful entities are tasks and their products rather than architectural layers.

The relation's meaning also matters within one workflow. A task may consume an earlier result as data, or inspect a condition solely to decide whether it should run. Both create dependencies, but they support different questions about how information contributes to the output. A model that records only an undifferentiated arrow cannot answer those questions. DocAble's document-processing pipeline provides a worked example of both architectural boundaries and typed computation dependencies.

> #### Worked example — Two structural views of document repair {#inset-docable-structural}
>
> DocAble is a service that repairs accessibility problems in documents, such as missing alternative text, unmarked table headers, or incorrect reading order. The same operation may need a different implementation for a Word document and a PDF. Its structural models let engineers separate two questions: where format-specific changes belong, and how the repair computations depend on one another.
>
> **Where may a document change?**
>
> DocAble supports several structured document formats through libraries powerful enough to alter their underlying object structures. Those libraries are necessary, but they sit behind a deliberate architectural boundary: most remediation logic works through DocAble's structured-document abstractions rather than reaching into a format-specific implementation directly.
>

> - **Engineering question** — Where is document mutation supposed to occur?

> - **Property** — the intended architecture places format-specific mutation behind one sanctioned seam; ordinary remediation logic is not intended to bypass it.

> - **Quality attribute** — architectural integrity and modifiability.

>
> The necessary model is small. [ref:document-mutation-model] draws it: remediation logic operates *through* a structured-document model, which has a separate *implementation* for each format—DOCX, PPTX, PDF, LaTeX, etc. It says nothing about queues, retries, deployment, user sessions, or the mechanics of individual repairs. Those facts are real but irrelevant to the question; the reduction preserves only the architectural boundary that matters.

>
> The principal property is a path constraint: every ordinary route to format-specific mutation must cross the structured-document seam. The model makes that requirement explicit so that a checker can look for bypasses. Enforcement requires a further step: DocAble's static analyses reject code that reaches a raw format library directly. In {{chapter:alignment}}, we discuss mechanisms for enforcing this architectural relation.

>
> <!-- index-def: model-drift -->
>
> A structural model carries the opposite risk too. The code moves and the drawing does not, so the boundary it shows quietly stops matching the system. That gap between a model and the system it describes is **model drift**. Later sections make the correspondence explicit by deriving, generating, or tracing between model and implementation.
>
> **What computations depend on one another?**
>
> <!-- point: a-second-structural-question-reaches-inside-the-pipeline | A second structural question reaches inside remediation: which computations make up the pipeline, and how do they depend on one another; the first reduction treats each registered pass as a node. -->
>
> The document-mutation model asked where one kind of change belongs. A second structural question reaches further inside the system: what computations make up remediation, and how do they depend on one another? DocAble runs a document through a collection of registered remediation passes. A pass may detect a condition, produce information a later pass uses, decide whether remediation should proceed, apply a bounded change to the intermediate representation, or edit a larger region directly. That structure exists in the implementation whether or not a model names it. The first reduction is the obvious one: treat each registered pass as a node, and suppress the statements, library calls, and loops inside it.
>
> **Remediation-computation model · Structural**
>
> - **Engineering question** — What computations make up remediation, and how does information move among them?
>
> <!-- -->
>
> - **Model** — a static directed graph whose nodes are registered computations and whose typed edges represent declared composition among them.
>
> <!-- -->
>
> - **Property** — declared data dependencies and control dependencies are distinguishable and consistent with pipeline ordering; each modeled computation also states how bounded its mutation is — a typed, comparable patch for all or a declared subset of its edits, or a direct in-place edit — and, on a separate axis, which apply seam a patch producer uses.
>
> <!-- -->
>
> - **Quality attribute** — analyzability, modifiability, and architectural integrity.
>
> <!-- point: the-computation-model-distinguishes-data-flow-from-control-composition | DocAble's computation model represents registered computations as nodes and distinguishes a data-flow edge (information consumed to produce a result) from a control edge (information consulted only to decide whether to run). -->
>
> DocAble's remediation-computation model represents registered computations as nodes and distinguishes two kinds of composition. A data-flow edge means one computation produces information another consumes in producing its result. A control edge means one computation produces information another consults only to decide whether it should run. Treating both as a generic dependency would obscure a consequential distinction: information that contributes to a result is different from information that controls whether the computation occurs. [ref:from-nodes-to-composition] draws a small fragment of the graph. These relationships are visible without reconstructing them from type declarations and function bodies.

>
> The first model preserves one architectural relation. The second preserves a family of typed compositional relations over the same system.
>
> <!-- point: the-model-also-records-how-bounded-each-effect-is | The same model records how bounded each computation's effect is — a typed patch for all or part of its edits, or a direct in-place edit — exposing distinctions the implementation contains but does not represent uniformly. -->
>
> The same model also records how bounded each computation's effect is: some produce typed patches, some produce them for part of their work and edit directly for the rest, and most edit document state directly. These distinctions do not declare one form universally better. They make previously implicit differences available for engineering questions about composition and mutation.
>
> <!-- point: the-static-graph-is-not-one-execution-of-it | The computation model is static per run, but other views attach observations to its stable computation identities — DocAble joins staged-run latency and cost to those identities without turning the structural graph into an execution log. -->
>
> The computation model remains static with respect to any one run: it records no per-job invocation history, retries, or model fingerprint. Other views can nevertheless attach observations to its stable computation identities. DocAble joins staged-run telemetry to those identities, so measured latency and cost can be queried alongside the structural model without turning the structural graph into an execution log. The per-session mutation record remains separate: it records what happened to one artifact, not the execution history of the computation graph.
>
> <!-- point: the-identity-spine-supports-added-views-without-enlarging-the-schema | Additional engineering views attach by computation identity rather than enlarging the structural schema; declared properties state intent, measured properties report observation, so an unmeasured value is unknown, not zero. -->
>
> The same identities can support additional engineering views without enlarging the structural schema each time. Separate providers can record complexity, bounded execution, latency, test coverage, or checker trust against the same computation identity. Declared properties state engineering intent. Measured properties report observations and may have incomplete coverage. An unmeasured latency is therefore unknown, not zero. Joining these views lets engineers ask questions about combinations of properties while keeping each representation focused on its own question.
>
> The two reductions keep different relations because they support different changes. To investigate a bypass of the document abstraction, inspect the architectural paths. To investigate the effect of changing a repair pass, inspect its declared inputs, outputs, and dependents. Neither question requires a complete model of the product.

A structural model earns its detail by the question it helps answer. Architectural paths, data dependencies, and control dependencies preserve different facts even when each is drawn with boxes and arrows.
