# One System, Several Views

<!-- section-terms: projection, four-plus-one-views, scenarios-view -->

One connected representation does not imply one view. The last chapter built a single executable
core — typed entities and relations, held equal to the code. If the whole system is one connected
model, why keep many models at all?

Because no one projection answers every engineering question. A service dependency useful during a
migration tells you little about lock ordering; a deployment relation useful for capacity planning
tells you little about a user's journey. The same system therefore needs several **projections**,
each keeping the entities, relations, and properties one question needs and suppressing the rest.

<!-- point: projections-are-chosen-by-the-question | Each projection answers one engineering question; the model classes name the kinds worth projecting for. | terms: projection, four-plus-one-views -->
<!-- index-def: four-plus-one-views -->
Which projections, then? Each answers one engineering question, and the models ahead sort by the
*kind* of question they answer. That the same architecture needs several complementary views is an old
observation: Kruchten's **4+1 views** named five of them a generation ago [cite: kruchten1995], the
classic statement that no single diagram captures a software architecture. Here that observation is
the starting point, not the organizing frame. The connected core organizes the models; the question
chooses the projection. The inset grounds the 4+1 as precedent; [ref:trunk-and-views] draws the one
core and the views projected from it.

> ### Inset — Kruchten's 4+1, as historical grounding {#inset-kruchten}
>
> The classic statement that one diagram cannot hold a whole architecture is Kruchten's **4+1
> views**: a *logical* view (what the system is), a *process* view (what runs at once), a
> *development* view (how the source is packaged and owned), and a *physical* view (where it runs),
> plus a *scenarios* view that animates the other four and validates them. Name them once and move on.
> The view-names are precedent, not the coordinate system this book carries — the five model classes
> are. What MAGE keeps from 4+1 is the plural itself: an architecture needs several views, and they
> should share one body of facts rather than drift as separate diagrams.

## The trunk beneath the views

<!-- point: separate-diagrams-drift-independently-a-connected-core-does-not | Separate diagrams drift independently; projections over one connected core join on identity and expose contradictions. | terms: projection, drift-gate, model-drift -->
Draw those projections the classic way — several diagrams, each maintained on its own — and they drift
independently, each ageing the first time its author forgets it. The move here is to make them
projections over one connected engineering model instead: views drawn from shared entities join on
identity, reuse facts, and expose contradictions wherever two of them disagree about the same element.

<!-- point: the-connected-core-carries-a-drift-gate-the-view-frameworks-never-had | The connected core carries a drift gate the classical view frameworks never had. | terms: drift-gate, four-plus-one-views, model-drift -->
That connected core is what MAGE adds beneath the projections, and it carries what the classical view
frameworks did not: a drift gate. Kruchten described the views; he had no way to fail a build when a
view and the code disagreed. Here every projection is a structured model a tool reads on every build,
gated the moment the model and the code diverge. A framework tells you *which* views you need; the
gate keeps each one from becoming a diagram that rots.

## The framework is a choice; the core is not

<!-- section-terms: executable-source-of-truth, four-plus-one-views -->

<!-- point: once-the-core-is-executable-a-framework-is-a-projection-not-a-second-model | An executable core makes a framework a projection. | terms: executable-source-of-truth, projection, four-plus-one-views -->
Once the core is a structured model held equal to the code, a *framework* is a **projection over that
core, not a second thing you maintain**. The word *core* needs one clause: it is not a single
universal metamodel but a **joined set of authoritative source models** — each owning its own slice,
linked on shared keys — and a projection may draw from several at once. You keep that one joined core
and render whatever view-set the audience needs from it.

<!-- point: rival-frameworks-are-renderings-of-one-executable-core | Rival frameworks are renderings of one executable core. | terms: projection, executable-source-of-truth, c4 -->
Change the audience and you change the projection; the model stays put. Runtime analysis wants
Kruchten's Process view; a customer asking "what do you send my data through?" wants a
[C4](https://c4model.com) Context-and-Container view; a compliance reviewer wants a data-flow
diagram. Rival methodologies at first blush — yet each is a rendering of the same structure, and a
system whose core is executable can derive any of them.

<!-- point: a-lens-is-a-second-projection-that-hides-content-but-cannot-invent-it | A lens hides content but cannot invent it. | terms: lens, projection, drift-gate -->
The same move works one level finer. Even inside a single framework, a view must choose *what to
show*: a customer's Container view hides the internal helper mesh a maintainer needs; a privacy review
shows only the data stores and where they egress. That choice is a second projection, and it stays
honest by a clean split. The **content** — which containers, edges, and external systems exist — is a
pure function of the source models, authored by no one. The **lens** picks which of that content a
view shows; it may hide a node, but it can never invent one. Name a container the sources no longer
contain and the lens fails the same drift gate the view does, so even "the customer's slice" cannot
drift from the truth.[note: The programming-languages literature calls a view that hides source detail a "lens"; a well-behaved lens is bidirectional, pairing a "get" that projects the view with a "put" that pushes an edit back onto the source, tied by round-trip laws [cite: foster-lenses2007]. The projection here uses only the "get" half — a reader consults the view, nobody edits it to change the code — so this is a view projection, not a full lens. What carries over is the read-side contract the drift gate enforces: a view may hide content the sources contain, never invent content they do not.] [ref:projection-axes] draws both projection axes — framework and lens.

The transferable claim sits one level up: hit the joined executable core, and the framework wars
dissolve into projection choices. Choose the core with care; choose the framework, and the lens, to
fit the reader.

## The graph gives identity; the view gives semantics

<!-- point: identity-is-shared-semantics-differ | Identity is shared across views; each view supplies its own semantics. | terms: projection -->
There is a seductive but wrong reading: that everything is *really* one knowledge graph, and the
views are just paths through it. That flattens the exact distinctions the models exist to teach.

A state machine is not interesting because it can be drawn as nodes and edges. It is interesting
because transition semantics let you answer a behavioral question — can this system reach a bad state?
A concurrency model is interesting because it exposes possible interleavings and the shared-resource
invariants they threaten. A scenario is interesting because it validates several views together
against one goal.

So keep the hierarchy explicit. The connected representation supplies **identity and relations** — the
stable entities the views all join on. Each view supplies the **semantics for one engineering
question** — the behavior, the concurrency, the placement, the journey its projection reasons about.
The graph is what lets the views meet; the view is what makes a projection worth drawing. Lose that
split and modeling degenerates into graph universalism, where every model is "just a graph" and none
answers anything.

## Reading the views

<!-- point: the-models-ahead-sort-into-five-classes | The models ahead sort into five classes by the kind of question each answers — the one coordinate system to carry forward. | terms: projection, scenarios-view -->
The models ahead sort by the kind of question each answers — five **classes**: structural, behavioral,
decision, measurement, and documentation. That is the one coordinate system to carry forward; each
class names a kind of question worth projecting for, and the model chapters are grouped by it. The
Part closes with the move that joins several classes at once — a scenario walked end to end.

<!-- point: the-class-tag-names-the-question-the-chapter-groups-by-arrival | The class tag names the question a model answers; the chapter groups models by the question you arrived with. | terms: projection -->
Because each model is a projection over the one connected representation, the chapters that follow need
not re-teach *what a model is*. Each opens with its **engineering question**, then frames the model as
the projection that answers it — which entities and relations it keeps, and which it drops. A class tag
and a chapter title can differ without contradiction: the tag names the kind of question the model
answers, the chapter groups models by the question you arrived with, so a model tagged *Decision* can
be taught inside a chapter about structure. The reduction is the value: an agent planning a structural
change should not have to carry every pod, lock, and user journey in its window. Model once; project
the view the question requires.
