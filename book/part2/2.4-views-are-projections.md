# Views Are Projections

<!-- section-terms: four-plus-one-views, projection, logical-view, scenarios-view -->

One connected representation does not imply one view. The last chapter built a single
executable trunk — typed entities and relations, held equal to the code. This chapter answers
the question that trunk raises: if the whole system is one connected model, why does the zoo
hold many models at all?

Because no one projection answers every engineering question. A service dependency useful
during a migration tells you little about lock ordering. A deployment relation useful for
capacity planning tells you little about a user's journey. The same system therefore needs
several **projections**, each keeping the entities, relations, and properties one engineering
question needs and suppressing the rest.

<!-- point: 4-plus-1-supplies-the-projection-set | Kruchten's 4+1 supplies the projection set over one connected representation. | terms: four-plus-one-views, projection, logical-view, process-view, development-view, physical-view, scenarios-view -->
<!-- index-def: four-plus-one-views -->
Kruchten's **4+1 views** supply a well-worn set of those projections. Kruchten observed that no
single diagram captures a software architecture, and that four complementary views plus a fifth
that ties them together cover what a working engineer needs to see. The last chapter named
Kruchten as the reason one model is never enough; this chapter states the relationship exactly.
The views do not organize the zoo — the connected representation does. The four-plus-one names
the *questions* worth projecting for. The inset defines the five; [ref:trunk-and-views] draws the
one trunk and the views projected from it, and marks what this book adds.

> ### Inset — What are Kruchten's 4+1 views? {#inset-kruchten}
>
> - **The Logical view** — the functional structure: the objects, the types, and how they relate. What the system *is*, as a designer sees it.
> - **The Process view** — concurrency and synchronization: what runs at once, the locks, the runtime dynamics. What stays consistent under interleaving.
> - **The Development view** — the module and organization structure: how the source is packaged, layered, and owned. How the code is arranged for the people and agents who build it.
> - **The Physical view** — the mapping of software to hardware: where processes run, across which hosts and network boundaries. Where the parts live.
> - **The Scenarios view (the +1)** — the use cases and journeys that animate the other four and validate them. What the system does for someone, walked end to end.

## Kruchten supplies the views; MAGE adds the trunk

Do not read this as *Kruchten was wrong*, or as knowledge graphs superseding architectural
views. The clean statement keeps both:

> Kruchten tells us which questions need different views. The connected representation tells us
> how those views share one body of facts.

In the original formulation the five views are complementary *descriptions* of an architecture,
each drawn and maintained on its own. Here they become machine-readable projections over a
connected engineering model. The distinction is the whole point. Five independent diagrams can
drift independently — each ages the first time its author forgets it. Five views projected from
shared entities join on identity, reuse facts, and expose contradictions where two projections
disagree about the same element.

Kruchten described the views; he did not have a drift gate. The drift gate is what this Part
adds beneath them: every view here is not a diagram a human maintains but a structured model a
tool reads on every build, with a gate that fails the build the moment the model and the code
disagree. The four-plus-one tells you *which views you need*; the drift gate keeps each view
from becoming a diagram that rots. That is what makes a projection something the build can keep
true rather than a picture that quietly falls behind the code.

## The framework is a choice; the core is not

<!-- section-terms: executable-source-of-truth, four-plus-one-views -->

<!-- point: once-the-core-is-executable-a-framework-is-a-projection-not-a-second-model | An executable core makes a framework a projection. | terms: executable-source-of-truth, projection, four-plus-one-views -->

Making the model executable is why this Part is not really *about* 4+1. Kruchten's five views
are how *this book* organizes the walk, because they map cleanly to an engineer's questions. But
once the core is a structured model held equal to the code, the *framework* is a **projection
over that core, not a second thing you maintain**. The word *core* needs one boundary clause: it
is not a single universal metamodel but a **joined set of authoritative source models** — the
{{real_model_count}} of the zoo, each owning its own slice, linked on shared keys — and a
projection may draw from several of them at once. You keep that one joined executable core and
render whatever view-set the audience needs from it.

<!-- point: rival-frameworks-are-renderings-of-one-executable-core | Rival frameworks are renderings of one executable core. | terms: projection, executable-source-of-truth, c4 -->

Change the audience and you change the projection; the model stays put. An engineer doing runtime
analysis wants Kruchten's Process view. A customer asking "what are the moving parts, and what do you
send my data through?" wants a [C4](https://c4model.com) Context-and-Container view. A reader reasoning
about invariants wants SysML's constraint-block vocabulary. A compliance reviewer wants a data-flow
diagram. Rival methodologies, at first blush — yet each is a rendering of the same structure, and a
system whose core is executable can derive any of them: the C4 view is the same projection move as the
Process view, run over the physical/deployment model instead of the state machine.

<!-- point: a-lens-is-a-second-projection-that-hides-content-but-cannot-invent-it | A lens hides content but cannot invent it. | terms: lens, projection, drift-gate -->

The same move works one level finer. Even inside a single framework, a view must choose *what to show*: a
customer's Container view hides the internal helper mesh a maintainer needs; a privacy review shows only
the data stores and where they egress. That choice is a second projection, and it stays honest by a clean
split. The **content** — which containers, edges, and external systems exist — is a pure function of the
source models, authored by no one. The **lens** picks which of that content a view shows; it may hide a
node, but it can never invent one. Name a container the sources no longer contain and the lens fails the
same drift gate the view does, so even "the customer's slice" cannot drift from the truth. This
read-only, hide-but-never-invent projection borrows its name from a formal idea in the
programming-languages literature; the inset marks exactly how much of that idea applies.
[ref:projection-axes] draws both projection axes — framework and lens.

> ### Inset — Is this projection a *lens*? {#inset-lens}
>
> The programming-languages literature calls a view that hides source detail a **lens**, and a *well-behaved* lens is bidirectional: it pairs a `get` that projects the view with a `put` that pushes an edit on the view back onto the source, the two tied by algebraic round-trip laws [cite: foster-lenses2007]. The projection in this chapter uses only the `get` half. A reader consults a Container view or a privacy slice; nobody edits the diagram to change the code. There is no `put`, so there are no round-trip laws to satisfy — this is a **view projection**, not a full lens. What carries over is the read-side intuition: a view may hide content the sources contain, but it can never invent content they do not. The drift gate enforces exactly that one contract. Add an update path later — edit the view, regenerate the source — and you would owe the full lens laws; until then, borrow the picture, not the algebra.

What this Part teaches, then, is *modeling* in the general; 4+1 merely supplies the spine, chosen
because it maps cleanly onto an engineer's questions, and each view gets built and drift-gated on real
code. The transferable claim sits one level up: hit the joined executable core, and the framework wars dissolve
into projection choices. Choose the core with care; choose the framework, and the lens, to fit the
reader.

## The graph gives identity; the view gives semantics

There is a seductive but wrong reading of all this: that everything is *really* one knowledge
graph, and the five views are just paths through it. That reading flattens the exact distinctions
the zoo exists to teach.

A state machine is not interesting because it can be drawn as nodes and edges. It is interesting
because transition semantics let you answer a behavioral question — can this system reach a bad
state? A concurrency model is not interesting because it is a graph. It is interesting because it
exposes possible interleavings and the shared-resource invariants they threaten. A scenario is not
interesting because a journey is a path. It is interesting because it validates several views
together against one goal.

So keep the hierarchy explicit. The connected representation supplies **identity and relations** —
the stable entities the views all join on. Each view supplies the **semantics for one engineering
question** — the behavior, the concurrency, the placement, the journey that its projection is
built to reason about. The graph is what lets the views meet; the view is what makes a projection
worth drawing. Lose that split and the Part degenerates into graph universalism, where every model
is "just a graph" and none of them answers anything.

## Reading the five views

Because each view is a projection over the same connected representation, the chapters that follow
need not re-teach *what a model is* five times. Each opens instead with its **engineering
question**, then frames the view as the projection that answers it — which entities and relations
it keeps, and which it drops. The reduction is the value: an agent planning a structural change
should not have to carry every pod, lock, and user journey in its window.

The five walk in Kruchten's order. The Logical view is first: what the system is made of, and what
may depend on what.
