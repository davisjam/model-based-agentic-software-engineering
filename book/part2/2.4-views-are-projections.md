# One System, Several Views

<!-- section-terms: projection, four-plus-one-views, scenarios-view -->

One connected representation does not imply one view. The previous chapter established a shared
substrate of typed entities, relations, and traceability. But no single projection of that substrate
answers every engineering question. A service dependency useful during a migration tells you little
about lock ordering; a deployment relation useful for capacity planning tells you little about a
user's journey.

The same system therefore needs several purposeful **projections**, each keeping the entities,
relations, and properties one question needs and suppressing the rest. That observation is old:
Kruchten's **4+1 views** made the plurality explicit a generation ago [cite: kruchten1995], the
classic statement that no single diagram captures a software architecture. MAGE adds a different
emphasis. The views should reuse identities and facts from a connected substrate rather than
becoming independent pictures that must be reconciled by hand.

<!-- point: projections-are-chosen-by-the-question | Each projection answers one engineering question; the model classes name the kinds worth projecting for. | terms: projection, four-plus-one-views -->
<!-- index-def: four-plus-one-views -->
Which projections, then? Each answers one engineering question, and the models ahead sort by the
*kind* of question they answer. The connected substrate organizes the models; the question chooses
the projection. The inset grounds the 4+1 as precedent; [ref:trunk-and-views] draws the one
substrate and the views projected from it.

> ### Inset — Kruchten's 4+1, as historical grounding {#inset-kruchten}
>
> The classic statement that one diagram cannot hold a whole architecture is Kruchten's **4+1
> views**: a *logical* view (what the system is), a *process* view (what runs at once), a
> *development* view (how the source is packaged and owned), and a *physical* view (where it runs),
> plus a *scenarios* view that animates the other four and validates them. Name them once and move on.
> The view-names are precedent, not the coordinate system this book carries — the five model classes
> are. What MAGE keeps from 4+1 is the plural itself: an architecture needs several views, and they
> should share one body of facts rather than drift as separate diagrams.

## The trunk beneath the views

<!-- point: separate-diagrams-drift-independently-a-connected-core-does-not | Separate diagrams drift independently; projections over one connected substrate join on identity and expose contradictions. | terms: projection, drift-gate, model-drift -->
Draw those projections the classic way — several diagrams, each maintained on its own — and they drift
independently, each ageing the first time its author forgets it. The move here is to make them
projections over one connected engineering model instead: views drawn from shared entities join on
identity, reuse facts, and expose contradictions wherever two of them disagree about the same element.

<!-- point: the-connected-substrate-keeps-a-view-from-becoming-a-second-copy | Derivation, traceability, and parity checks keep a machine-readable view from becoming an unchecked second copy of the code. | terms: drift-gate, four-plus-one-views, model-drift -->
That connected substrate is what MAGE adds beneath the projections. Its implementation strengthens the
relationship between view and territory by making the projections machine-readable and mechanically
maintaining the facts they claim to represent. A framework tells you *which* view may be useful;
derivation, traceability, and parity checks keep a view from becoming an unchecked second copy of the
code.

## The framework is a choice; the core is not

<!-- section-terms: executable-source-of-truth, four-plus-one-views -->

<!-- point: framework-and-audience-are-separate-projection-choices | Framework and audience are separate projection choices over one set of source models; a view may omit facts but never invent them. | terms: executable-source-of-truth, projection, lens, c4 -->
Framework and audience are separate choices. The same source models can render a Kruchten-style
Process view for a maintainer, a [C4](https://c4model.com) Context-and-Container view for a customer,
or a data-flow view for a privacy review; a further read-side projection can hide the details one
audience does not need. The rule is simple: a view may omit facts from the source models, but it must
not invent facts they do not contain.[note: The programming-languages literature calls a view that hides source detail a "lens"; a well-behaved lens is bidirectional, pairing a "get" that projects the view with a "put" that pushes an edit back onto the source, tied by round-trip laws [cite: foster-lenses2007]. The projection here uses only the "get" half — a reader consults the view, nobody edits it to change the code — so this is a view projection, not a full lens. What carries over is the read-side contract the drift gate enforces: a view may hide content the sources contain, never invent content they do not.]

## The graph gives identity; the view gives semantics

<!-- point: identity-is-shared-semantics-differ | Identity is shared across views; each view supplies its own semantics. | terms: projection -->
There is a seductive but wrong reading: that everything is *really* one knowledge graph, and the
views are just paths through it. That flattens the exact distinctions the models exist to teach.

A state machine is not interesting because it can be drawn as nodes and edges. It is interesting
because transition semantics let you answer a behavioral question — can this system reach a bad state?
A concurrency model is interesting because it exposes possible interleavings and the shared-resource
invariants they threaten. A scenario is interesting because it validates several views together
against one goal.

So keep the hierarchy explicit. The connected representation supplies **identity and relations** — the
stable entities the views all join on. Each view supplies the **semantics for one engineering
question** — the behavior, the concurrency, the placement, the journey its projection reasons about.
The graph is what lets the views meet; the view is what makes a projection worth drawing. Lose that
split and modeling degenerates into graph universalism, where every model is "just a graph" and none
answers anything.

## Reading the views

<!-- point: the-models-ahead-sort-into-five-classes | The models ahead sort into five classes by the kind of question each answers — the one coordinate system to carry forward. | terms: projection, scenarios-view -->
The models ahead sort by the kind of question each answers — five **classes**: structural, behavioral,
decision, measurement, and documentation. That is the one coordinate system to carry forward; each
class names a kind of question worth projecting for, and the model chapters are grouped by it. The
Part closes with the move that joins several classes at once — a scenario walked end to end.

<!-- point: the-class-tag-names-the-question-the-chapter-groups-by-arrival | The class tag names the question a model answers; the chapter groups models by the question you arrived with. | terms: projection -->
Because each model is a projection over the one connected representation, the chapters that follow need
not re-teach *what a model is*. Each opens with its **engineering question**, then frames the model as
the projection that answers it — which entities and relations it keeps, and which it drops. A class tag
and a chapter title can differ without contradiction: the tag names the kind of question the model
answers, the chapter groups models by the question you arrived with, so a model tagged *Decision* can
be taught inside a chapter about structure. The reduction is the value: an agent planning a structural
change should not have to carry every pod, lock, and user journey in its window. Model once; project
the view the question requires.
