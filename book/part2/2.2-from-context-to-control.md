# From Context to Engineering Model

<!-- section-terms: thesis-modeling, thesis-alignment, structured-relationships -->

<!-- point: an-edge-gains-representational-capabilities-one-property-at-a-time | An edge gains representational capabilities one property at a time: type, semantics + obligation, derivation. Authority is related but separate. | terms: structured-relationships, thesis-modeling, thesis-alignment -->
Suppose the graph records that a worker consumes a queue. As context, the edge helps an agent locate
relevant code. Type the worker, queue, and relation, and tools can traverse the edge reliably. Add
semantic properties and an authored obligation — only workers of class X may consume queues of class Y —
and the representation can now answer an engineering question the bare edge could not. Derive the
representation from implementation, or generate implementation from it, and its correspondence to the
system becomes mechanically testable.

<!-- point: representational-capabilities-vs-authority | Those are representational capabilities. Authority is related but separate — Modeling changes what the environment can KNOW explicitly; Alignment decides what it will DO with an obligation. | terms: thesis-modeling, thesis-alignment -->
Those are **representational capabilities**. Authority is related but separate. A validator or gate may
later consume the obligation and act on a violation; a sandbox may impose another obligation without
using this model at all. Modeling changes what the environment can *know explicitly*. Alignment decides
what the environment will *do* with an obligation.

<!-- point: what-makes-a-representation-an-engineering-model | An engineering model is a deliberately reduced, machine-readable representation structured to answer an engineering question; MAGE favors models that can be queried, derived, traced, or checked so a trusted representation is not an unchecked second truth. | terms: thesis-modeling, structured-relationships -->
<!-- index-def: model -->
In this Part, an **engineering
model** is a deliberately reduced, machine-readable representation structured to answer an engineering
question. MAGE favors models that can also be queried, derived, traced, or mechanically checked against
the system they represent, because a representation trusted by many agents must not become an unchecked
second truth. That is a stronger working criterion than the word *model* carries in every engineering
tradition; it is the operational sense used throughout this Part.

<!-- index-def: structured -->
The word doing the work is **structured**: an explicit, declared shape a machine can read and validate —
a schema, not prose. The structure is what admits the machine. Prose can be read; only a structured
representation can be traversed by a tool, checked against the code, and related to the system it
represents.

## The capability ladder

<!-- section-terms: thesis-modeling, thesis-alignment -->

<!-- point: the-ladder-orders-representational-capabilities | The capability ladder orders representational capabilities, not organizations; each step makes additional engineering questions answerable. | terms: thesis-modeling, structured-relationships -->
<!-- index-def: capability-ladder -->
<!-- index-def: structured-relationships -->
Naming these capabilities gives the rest of the Part a useful ordering. The lower rungs reduce
reconstruction: select relevant context, externalize durable knowledge, and structure relationships.
Higher rungs add semantics, explicit properties, analysis, traceability, and eventually a mechanically
maintained correspondence between model and territory. Each step makes additional engineering questions
answerable. [ref:capability-ladder] draws all eight.

<!-- point: capability-ladder-not-maturity-model | Read the ladder as a capability ladder, not a maturity model; authority is a separate axis — Docker shows real authority low on the ladder. | terms: thesis-modeling, thesis-alignment, capability-ladder -->
The ladder orders representational capability rather than organizational maturity. Docker makes the distinction concrete: it relies heavily
on sandboxes and tests over raw artifacts while exposing comparatively little system intent through
invariant-bearing models. That is real authority without climbing this representational ladder very far.
A stronger model becomes worth its cost when a recurring engineering question cannot be retired cheaply
at the current rung.

## Richer models expose richer authority surfaces

<!-- section-terms: thesis-modeling, thesis-alignment, determinization -->

<!-- point: better-representation-pays-first-in-reasoning | Better representation pays first in reasoning — a service edge becomes a typed relation, a status string a transition, an ownership convention an explicit relation. | terms: thesis-modeling, structured-relationships -->
Better representation pays first in reasoning. A service edge that once merely helped an agent navigate
can become a typed architectural relation; a status string can become a transition in a behavioral
model; an ownership convention can become an explicit relation between a component and its code. Each
move takes meaning that had to be reconstructed and gives it a stable form.

<!-- point: modeling-expands-the-surface-authority-can-operate-over | Once an obligation is explicit enough to evaluate, an Alignment mechanism can consume it. Modeling does not create authority by itself, and authority does not require Modeling; Modeling expands the semantic surface over which authority can operate. | terms: thesis-modeling, thesis-alignment -->
That stable form creates a second payoff. Once an obligation is explicit enough for a machine to
evaluate, an Alignment mechanism can consume it. The service relation can be compared against the
observed call graph; the legal transition table can be checked against attempted state changes; the
ownership relation can be tested against the repository tree. **Modeling does not create authority by
itself, and authority does not require Modeling. Modeling expands the semantic surface over which
authority can operate.**

<!-- point: representation-alignment-proposition | Representation–Alignment Proposition: as engineering intent becomes more explicit and structured, more obligations become eligible for deterministic enforcement. | terms: thesis-modeling, thesis-alignment, determinization -->
> **Representation–Alignment Proposition.** As engineering intent becomes more explicit and structured,
> more obligations become eligible for deterministic enforcement.

<!-- point: the-consequence-is-not-model-everything | The practical consequence is not "model everything"; notice where a fact is repeatedly reconstructed or a property repeatedly adjudicated that the environment could settle if the right abstraction existed. | terms: thesis-modeling, capability-ladder -->
The practical consequence is selective modeling: notice where people repeatedly reconstruct
a fact or adjudicate a property the environment could settle if the right abstraction existed. That gap
is where another rung may pay.

## Where to start

<!-- section-terms: thesis-modeling, brownfield-migration -->

<!-- point: start-at-the-lowest-rung-that-solves-a-real-problem | Start at the lowest step that solves a real reasoning problem; strengthen the model when a recurring question justifies it. | terms: thesis-modeling, brownfield-migration, capability-ladder -->
The ladder answers a question every real team asks: where do I start? Start at the lowest step that solves a reasoning problem you actually have,
then strengthen the representation when a recurring engineering question makes the next step worth its
cost. A catalog that ends the daily "who owns this?" rediscovery is a cheap step well spent. An invariant
is worth stating the third time the same class of bug ships. Let recurring judgment determine when to climb.

<!-- worked-examples: thesis-modeling -->
### Example — Siemens
Siemens shows the far side of the ceiling. An engineer states intent in plain words — "validate this part
under 200 lb in the Y-direction" — and an agent reads the CAD geometry, sets up the finite-element model,
calls a deterministic solver, and returns a validated result. The model is the work surface; the code is
one downstream artifact the model generates; a deterministic solver evaluates the stated question against
the model and its assumptions rather than leaving the calculation to reviewer judgment. Here the
executable model is the work surface rather than a secondary description.

### Example — DocAble
DocAble crosses the same boundary in software, one implementation of the move. It makes an ordinary
codebase queryable through structured models an agent reasons over and a gate checks, so a system built
from source gains the property Siemens's models already have: the representation is analyzable, not just
readable.

<!-- takeaway -->
Cross from a representation that merely supplies context to one whose semantics a machine
can analyze. Other engineering disciplines already work routinely at that level; code-centric software
can make more of its own engineering knowledge available there.
<!-- worked-examples-end -->

<!-- point: a-representation-becomes-a-model-when-it-carries-intent | A representation becomes an engineering model when it carries semantics and intent, not merely facts. | terms: thesis-modeling, structured-relationships -->
A representation becomes an engineering model when it carries semantics and intent, not merely facts. The
edge that only recorded *worker consumes queue* now says which workers *may*, and a machine can act on the
difference. From here, each model is a slice of the system knowledge graph, structured until it answers an
engineering question the raw code cannot. The first question every one of them must answer: what entities
and relations does it represent?
