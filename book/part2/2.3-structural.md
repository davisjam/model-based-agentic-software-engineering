# Structural Models: What Is Connected to What?

A structural model shows which parts of a system exist and how they relate to one another. We can ask, for example, which components depend on a service or where a document may be changed. To answer either question, we can set aside most of what happens inside the components.

## Entities, Relationships, and Graph Analysis {#entities-relationships-and-graph-analysis}

### Constructing a Structural Model {#constructing-a-structural-model}

[ref:canonical-structural] shows the intended architecture of a web application with an API, a cache, and a database. Suppose we want to allow the cache to read from the database while requiring the web component to go through the API. How can we tell whether the architecture permits a bypass?

<!-- label: canonical-structural -->
<!-- figure: assets/canonical-structural.svg | *The structural move: entities and defined relations.* This model states an intended architecture, rather than recording an execution. Every solid arrow denotes a direct dependency; the crossed arrow marks a forbidden bypass. Checking paths makes the obligation precise: every path from Web to Database must pass through API. -->

<!-- point: a-structural-model-selects-both-entities-and-relations-and-the-edge-label-carries-the-meaning | The architectural question selects components and their permitted direct dependencies. -->

**Question.** Can Web reach Database without passing through API? To answer, draw the four components and the dependencies between them. We can leave out the cache’s eviction policy and the database schema. Neither changes which components Web can reach in this model.

**Semantics.** In [ref:canonical-structural], each solid arrow denotes a permitted direct dependency between two components. A path is a sequence of components connected by those arrows. The crossed arrow marks a forbidden direct dependency and is excluded when tracing paths. Web therefore has an indirect route to Database through API and Cache.

<!-- point: once-structure-is-explicit-the-properties-are-graph-properties-and-the-analyses-graph-operations | Removing API and searching for a remaining Web-to-Database path tests whether the declared architecture permits a bypass. -->

**Analysis.** Our architectural requirement is stronger than prohibiting a direct Web-to-Database dependency: every path from Web to Database must pass through API. Remove API and the arrows touching it from a copy of the graph. Start at Web and follow the remaining arrows. In this example Web has no outgoing arrow, so Database is unreachable. Now imagine adding a permitted dependency from Web to Cache. Removing API would leave the path Web \(\to\) Cache \(\to\) Database, showing exactly how the revised architecture would permit a bypass.

### Properties and Analyses {#structural-properties-and-analyses}

**Reachability** asks whether a path connects one entity to another. **Separation** can require that no path connect two entities, or that they become disconnected when a designated boundary is removed. In [ref:canonical-structural], Web is allowed to reach Database, but every route must pass through API. These properties help engineers identify who can reach a protected resource and whether a proposed architecture permits a bypass. **Acyclicity** requires a dependency graph to contain no directed cycles. In a finite, acyclic build graph, the tasks can be ordered so that every prerequisite finishes before its dependent begins. If two compilation tasks each require the other’s output, neither can go first. The dependencies must change before such an order is possible. **Containment** describes how entities are grouped, for example which modules belong to a service. **Cardinality** constrains how many relationships an entity may have, as when every service must have exactly one designated owner.

The corresponding analyses are graph operations. Follow dependency arrows forward to establish reachability or backward to identify which components a change might affect. Remove a boundary node and search for a remaining path to test mandatory traversal. A cycle check determines whether a prerequisite order exists, and counting the ownership links of each service identifies any with missing or multiple owners. Each analysis depends on the meaning of the relationships: the dependency graph in [ref:canonical-structural] can answer the bypass question, but checking ownership requires ownership links.

The general procedure is to identify the entities and relationships relevant to a question, define what those relationships mean, and analyze the resulting graph. The same approach applies to a system’s environment, where we might trace communication pathways or dependencies between organizations, and to its internal structure. DocAble uses two such models of the same software: one to locate architectural boundaries and one to trace dependencies between computations.

## DocAble: Architecture and Computation Dependencies {#docable-architecture-and-computation-dependencies}

DocAble is a service that repairs accessibility problems in documents, such as missing alternative text, unmarked table headers, or incorrect reading order. The same operation may need a different implementation for a Word document and a PDF. Its structural models let engineers separate two questions: where format-specific changes belong, and how the repair computations depend on one another.

**Where may a document change?**

DocAble supports several structured document formats through libraries powerful enough to alter their underlying object structures. Those libraries are necessary, but they sit behind a deliberate architectural boundary: most remediation logic works through DocAble's structured-document abstractions rather than reaching into a format-specific implementation directly.

The necessary model is small. [ref:document-mutation-model] draws it: remediation logic operates *through* a structured-document model, which has a separate *implementation* for each format—DOCX, PPTX, XLSX, PDF, and others. It says nothing about queues, retries, deployment, user sessions, or the mechanics of individual repairs. Those facts are real but irrelevant to the question; the reduction preserves only the architectural boundary that matters.

<!-- point: a-model-precedes-the-constraint-that-protects-it | The model states the path requirement that ordinary mutation routes cross the structured-document seam; DocAble’s static analyses enforce it by rejecting direct access to raw format libraries. | terms: soft-vs-hard-governance -->

The principal property is the mandatory-traversal constraint introduced in [ref:canonical-structural]: every route from ordinary remediation logic to format-specific mutation must cross the structured-document seam. To analyze a sufficiently detailed dependency graph, remove that seam and ask whether remediation logic can still reach a raw format library. Any remaining path identifies a bypass. DocAble's static analyses reject code that reaches a raw format library directly. {{chapter:alignment}} discusses the mechanisms that enforce this architectural relation.

<!-- point: a-structural-model-can-drift-from-the-system-it-describes | A structural model carries the opposite risk — the code moves and the drawing does not — so the boundary it shows quietly stops matching the system; that gap is model drift, and later sections keep the correspondence by deriving, generating, or tracing. -->

<!-- index-def: model-drift -->

A structural model carries the opposite risk too. The code moves and the drawing does not, so the boundary it shows quietly stops matching the system. That gap between a model and the system it describes is **model drift**. Later sections make the correspondence explicit by deriving, generating, or tracing between model and implementation.

**What computations depend on one another?**

<!-- point: a-second-structural-question-reaches-inside-the-pipeline | A second structural question reaches inside remediation: which computations make up the pipeline, and how do they depend on one another; the first reduction treats each registered pass as a node. -->

The document-mutation model identifies where changes belong. A second structural question concerns how remediation computations depend on one another. If we change one computation, which others might be affected? DocAble runs documents through registered remediation passes that detect conditions, produce information for later passes, decide whether work should proceed, or modify document state. To investigate their dependencies, represent each registered pass as a node while leaving its internal statements, library calls, and loops out of the graph.

**Remediation-computation model · Structural**

- **Engineering question** — What computations make up remediation, and how does information move among them?

<!-- -->

- **Model** — a static directed graph whose nodes are registered computations and whose typed edges represent declared composition among them.

<!-- -->

- **Property** — declared data dependencies and control dependencies are distinguishable and consistent with pipeline ordering; each modeled computation also states its mutation behavior — read-only, a typed, comparable patch for all or a declared subset of its edits, or a direct in-place edit — and, on a separate axis, which apply seam a patch producer uses.

<!-- -->

- **Quality attribute** — analyzability, modifiability, and architectural integrity.

<!-- point: the-computation-model-distinguishes-data-flow-from-control-composition | DocAble's computation model represents registered computations as nodes and distinguishes a data-flow edge (information consumed to produce a result) from a control edge (information consulted only to decide whether to run). -->

DocAble's remediation-computation model distinguishes two relationships between registered computations. A data-flow edge means one computation produces information another consumes in producing its result. A control edge means one computation produces information another consults only to decide whether it should run. [ref:from-nodes-to-composition] illustrates both. To investigate a proposed change, follow the outgoing dependencies: changing a classifier may affect which repairs execute, while changing a patch producer may affect computations that consume its output. Treating both relationships as generic dependencies would conceal these different consequences.

The first model preserves one architectural relation. The second preserves a family of typed compositional relations over the same system.

<!-- point: the-model-also-records-how-bounded-each-effect-is | The same model records each computation's mutation behavior — read-only, a typed patch for all or part of its edits, or a direct in-place edit — exposing distinctions the implementation contains but does not represent uniformly. -->

The model also records each computation's mutation behavior. Some computations only inspect the document, some produce typed patches, some produce patches for part of their work and edit directly for the rest, and most edit document state directly. These attributes support another structural question: which computations can modify the document directly, and which produce patches that pass through an applier? The distinctions do not make one approach universally preferable; they expose differences that matter when analyzing composition and mutation.

<!-- point: the-static-graph-is-not-one-execution-of-it | The computation model is static per run, but other views attach observations to its stable computation identities — DocAble joins staged-run latency and cost to those identities without turning the structural graph into an execution log. -->

The computation model remains static with respect to any one run: it records no per-job invocation history, retries, or model fingerprint. Other views can nevertheless attach observations to its stable computation identities. DocAble joins staged-run telemetry to those identities, so measured latency and cost can be queried alongside the structural model without turning the structural graph into an execution log. The per-session mutation record remains separate: it records what happened to one artifact, not the execution history of the computation graph.

<!-- point: the-identity-spine-supports-added-views-without-enlarging-the-schema | Additional engineering views attach by computation identity rather than enlarging the structural schema; declared properties state intent, measured properties report observation, so an unmeasured value is unknown, not zero. -->

The same identities can support additional engineering views without enlarging the structural schema each time. Separate providers can record complexity, bounded execution, latency, test coverage, or checker trust against the same computation identity. Declared properties state engineering intent. Measured properties report observations and may have incomplete coverage. An unmeasured latency is therefore unknown, not zero. Joining these views lets engineers ask questions about combinations of properties while keeping each representation focused on its own question.

The two structural models answer different questions about the same software. To investigate a possible bypass of the document abstraction, follow architectural dependencies and check whether every path crosses the sanctioned seam. To investigate a change to a remediation pass, follow its declared data and control dependencies and inspect its mutation behavior. Neither analysis requires a complete model of DocAble.

A structural model earns its detail by the question it helps answer. Architectural paths, data dependencies, and control dependencies preserve different facts even when each is drawn with boxes and arrows.
