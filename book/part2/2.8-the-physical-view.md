# The Physical View: where the parts live

<!-- point: the-physical-view-maps-where-the-parts-run | The Physical view maps where the parts run. | terms: physical-view, placement -->
<!-- index-def: physical-view -->
*Where does each part run, and at what cost?* The Physical view is the projection over the
connected system model that turns placement into a queryable relation over the same named
entities the other views share, rather than a fact scattered across deployment configuration.
Before an agent deploys, it must answer where each part runs — and that placement is a
correctness decision, not a deployment detail. The Physical view exists for exactly that: it
removes the burden of reasoning about runtime placement from scattered configuration, holding
*where things run* as a model the fleet reads before it deploys, not a fact discovered after.
A system that is functionally correct can still be mis-deployed; only a view that names where
things run catches it.

<!-- point: a-performance-cost-model-anchors-the-view-with-one-honest-gap | A performance-cost model anchors the view, one honest gap. | terms: performance-cost-model, invariant-dag-execution-policy, deployment-topology-model, control-substrate-dependency -->
<!-- index-def: performance-cost-model -->
One general type anchors the view, and it is the honest exception in this zoo. A
**performance and cost model** models the computation itself — what it costs to run, what it
costs to move data, whether to compute locally or remotely, whether to cache or recompute. The
next section takes that gap head-on: the framework supports the cost view, and one real model
*embodies* the load-and-cost half of it, but the pure-latency slice has no dedicated instance,
because no failure had justified building one until one arrived. Three real models carry the view: the
invariant-DAG execution policy (the idea this chapter turns on — per-host cost and load
rationing). *Despite the name, it is a deployment/test* **execution** *DAG — its edges carry typed
intents (correctness, cost-gate, load), not a graph of invariants.* Then the deployment and tier
topology model (placement parity, worked in full below), and the substrate-dependency model (a
computed migration blast radius).

> Learn more about this governance mechanism: [deployment and tier topology model](appendix-b-deployment-topology-model.html).

## The performance/cost view: mostly embodied, one honest gap

<!-- section-terms: performance-cost-model, model-only-where-a-failure-lives -->

<!-- point: the-cost-view-is-partly-embodied-and-the-book-says-so | The cost view is partly embodied; the book says so. | terms: performance-cost-model, honest-gap -->
The zoo names a performance and cost model as a general type, and the framework supports it.
But the catalogue holds only a partial instance, and the book would rather state that flat
than invent a model to fill the slot.

<!-- point: a-per-host-profile-rations-load-and-cost | A per-host profile rations load and cost. | terms: invariant-dag-execution-policy, per-host-load-profile, rationing -->
The load-and-cost half of the view *is* embodied — by the invariant-DAG execution policy below.
Its Scheduler reads a per-host profile of a concurrency ceiling and a budget, and rations both.
The more elastic the host, the wider the Scheduler fans work out; the scarcer the box, the
harder the plan serializes — and a cost gate is honored everywhere, a scarce-resource gate only
where a box demands it. That is a real cost model in action: cost-to-run and
resource-contention, driven from a declared per-host profile.

> Learn more about this governance mechanism: [invariant-DAG execution policy](appendix-b-invariant-dag-execution-policy.html).

<!-- point: model-only-where-a-failure-lives-so-the-latency-slice-stays-empty | Model only where a failure lives; latency slice stayed empty. | terms: model-only-where-a-failure-lives, pure-latency, honest-gap -->
<!-- index-def: model-only-where-a-failure-lives -->
What has no dedicated instance is the *pure-latency* slice: a model of request latency, cache-hit
ratios, and data-movement cost. The framework could carry it the way it carries the others — a
typed profile, invariants, a drift gate. The zoo names the gap rather than padding it, on the
discipline the whole harness leads with: **model only where a failure lives.** Read it precisely: a model built with no decision, invariant, or named risk to
exercise it is the one likely to rot before it is ever checked — nothing reads it, so nothing catches it
drifting. A model built *ahead* of an incident is fine when it answers a live question the moment it lands;
that is ex-ante governance, and it is exercised from day one. What the discipline forbids is the speculative
model with no reader. The latency slice is where the line drew blood.

<!-- point: scale-to-zero-shipped-without-a-latency-model-and-production-paid | Scale-to-zero shipped without a latency model; production paid. | terms: pure-latency, honest-gap, cold-start-latency -->
The clearest evidence that placement is correctness: DocAble has paid for this gap once. To cut idle cost, the fleet let its services scale to zero — a
change the cost half of this model welcomed and the latency half could not weigh. The cold-start
incident from [Metrics](3.5-metrics.html) is exactly this gap surfacing: a warm per-request floor that a
fleet-average number hid, run down over days of telemetry to a resident-runtime re-architecture that cut it
4,057 → 109 ms. Read the full diagnosis there. The Physical-view point is narrower and it is the cost of the
open gap: a latency slice here — request latency typed per service, the cold-start penalty of scaling to
zero an invariant over it — would have weighed that trade before a user ever waited on it, exactly where the
cost half alone could not. The gap stays honest; this is what it costs to leave open.

## The deployment & tier topology model {#deployment-topology-model}

<!-- section-terms: deployment-topology-model, executable-source-of-truth -->

<!-- noqa: book-section-cap | The deployment &amp; tier topology model — a model page rendered from the fixed five-field (a)-(e) template; the fields are one indivisible reference unit a reader scans by reflex across every model, so splitting one page breaks the uniform shape -->

<!-- point: the-topology-model-declares-where-each-service-deploys | The topology model declares where each service deploys. | terms: deployment-topology-model, layer -->
<!-- index-def: deployment-topology-model -->
*The typed statement of where things run — each service's name, its layer, and its tier — from
which the deploy scripts and layering lints reason about a declared topology rather than scattered
constants, and against which the real deploy table is reconciled.*

<!-- point: it-assesses-deployment-parity-and-layer-boundary-soundness | It assesses deployment parity; layer boundary lives in Development. | terms: deployment-parity, layer -->
**(a) Quality property it helps assess.** Deployment parity — *does every service the model declares
deploy at the tier the model says, and does every deployed service appear in the model?* A tier that
drifts in the code without a matching model edit fails the build instead of surfacing as a production
surprise. (The same record also carries the layer-boundary graph the Development view checks — *may this
layer import that one?* — so a cross-layer shortcut is a finding there. Rendered in full under Development;
the Physical view uses this model for placement.)

**(b) Constructs and relations.** A frozen record per service, keyed by name.

- **`Service`** — one deployable unit: its name, its owning layer (web, worker, shared), and its
  tier class (critical, batch).
- **The tier relation**: each `Service` declares the tier it must deploy at; the set of declared
  tiers is what the deploy table is checked against.
- **The layer relation**: the layers form the dependency graph a cross-layer-import lint reads, and
  the same topology is the ground truth the migration blast-radius query joins against.

**(c) Visual depiction.** The natural diagram, [ref:deployment-model-structure], is a deployment diagram — the build host that
produces the image, and the runtime cluster it deploys into. Reused from the model's appendix
Structure slot:

<!-- label: deployment-model-structure -->
<!-- figure: assets/deployment-model-structure.svg | The model declares placement — the build host that produces the image, and the runtime cluster it deploys into. Each service is a frozen record keyed by name, carrying its owning layer and its tier class. A bidirectional parity check reconciles those declared tiers against the real deploy table, so a service that ships at the wrong tier fails the build. -->

**(d) Invariants, and how they are checked.** A bidirectional set-diff and a boundary lint, collected in [ref:physical-invariants]:

<!-- label: physical-invariants -->
<!-- table: Invariants of the Physical view — every service deploys at the tier the model declares, held to the real deploy tables. [short: Invariants of the Physical view: deployment placement] -->
| Invariant | How it is checked |
|---|---|
| Every declared service deploys at the tier the model declares | Parity lint, model ⊆ reality: a declared service missing from the deploy table, or at the wrong tier, is a finding. |
| Every deployed service appears in the model | Parity lint, reality ⊆ model: a service in the deploy table the model never declared is a finding. |

The same model's layer graph carries a third invariant — no import across a forbidden boundary — held by a
cross-layer-import lint and rendered under the Development view.

<!-- point: the-parity-check-runs-both-directions-or-misses-drift | The parity check runs both directions or misses drift. | terms: deployment-parity, set-diff, bidirectional-reconciliation -->
The parity check is a set-diff run both directions against the live service-to-tier map. Read the
model's declared tiers, read the real deploy table, and print each mismatch: a declared service
whose tier differs from the deploy table's, and every deployed name absent from the model. Neither
direction is optional — model ⊆ reality alone would miss a service that shipped without a model
row, and reality ⊆ model alone would miss a tier that drifted in the code.

<!-- point: the-topology-model-derives-from-the-deploy-table | The topology model derives from the deploy table. | terms: model-from-code, join-key, deployment-parity -->
**(e) Traceability and derivation direction.** *Model-from-code.* The parity check re-reads the
real deploy table — the declared service-to-tier configuration the build consumes — and reconciles the
model's topology against it. So the ground truth here is the **deploy configuration**, and the property
established is **deployment-configuration parity**: the model agrees with what the build is configured to
deploy. Whether each process then runs at the tier its configuration names — **runtime-deployment
conformance** — is a stronger, runtime check this model does not perform. The join key is the service name,
which indexes both the `Service` record and its row in the deploy table. The model is authoritative for the
layer graph it holds — the import lint reads it directly — and reconciled against the deploy configuration
for the tier placement it checks.

*Also seen in:* Development (a layer boundary is a packaging fact). Rendered in full here.

That model says where the parts run. The next one says where the *checks* run — the same
physical-placement thinking, applied to the gates themselves rather than the services.

## The invariant-DAG execution policy {#invariant-dag-execution-policy}

<!-- section-terms: invariant-dag-execution-policy -->

<!-- noqa: book-section-cap | The invariant-DAG execution policy — a model page rendered from the fixed five-field (a)-(e) template; the fields are one indivisible reference unit a reader scans by reflex across every model, so splitting one page breaks the uniform shape -->

<!-- point: a-host-identical-graph-plus-a-scheduler-rations-per-host | A host-identical graph plus a Scheduler rations per host. | terms: invariant-dag-execution-policy, edge-intent, per-host-load-profile -->
<!-- index-def: invariant-dag-execution-policy -->
<!-- slogan: profile-edit-not-graph-edit -->
The insight is one sentence: **correctness dependencies stay in the graph; host-specific resource limits
live in a scheduler profile.** What must be true on *every* host — B is wrong without A — belongs in the
deploy graph. How *hard a particular box may be pushed* — how many steps run at once, whether a cost gate is
worth honoring — belongs in that host's profile, read by a Scheduler. Move the stress between hosts and you
edit the profile, never the graph: **profile edit, not graph edit.**

<!-- point: it-assesses-graph-portability-and-rationing-correctness | It assesses graph portability and rationing correctness. | terms: graph-portability, rationing, edge-intent -->
**(a) Quality property it helps assess.** Two, both about how a host runs the work it was handed.

- **Graph portability**: *is the deploy graph the same on every host?* Load-specific edges are
  banned from the graph and migrated to the Scheduler, so the graph itself carries only host-
  identical correctness and cost intents, and cannot fork per host.
- **Rationing correctness under cost and resource pressure**: *does the deploy fan work out when
  it safely can, and serialize only when it must?* The Scheduler honors a cost gate everywhere but
  rations concurrency only where a scarce box demands it, all from one profile table.

**(b) Constructs and relations.** An edge-intent axis plus a per-host Scheduler.

- **The edge intent** — each deploy-graph edge carries a typed intent. `CORRECTNESS` means B is wrong
  without A, honored on every host. `COST_GATE` means A is a cheap check gating an expensive B,
  honored by default and relaxable only under an unbounded budget. `LOAD` means B contends with A for
  a scarce box; it is *banned in the graph*, migrated to the Scheduler.
- **`HostLoadProfile`** — a per-host record with two knobs. A **concurrency ceiling** — how many roster
  items may run at once (1 for a single scarce box; large for an elastic one). And a **budget** — a spend
  ceiling, in dollars, on this host's work. A *finite* budget means spend is scarce, so cost gates are
  honored: an expensive step runs only after its cheap gate clears. An *unbounded* budget (infinity) means
  spend is not the constraint here, so the cost gate protects nothing and is relaxed. The elastic staging
  box runs unbounded; a metered box runs finite.
- **The Scheduler** — reads a host's profile and emits an execution plan: how many roster items
  may run at once, and whether to honor the cost gate. Load rationing is a semaphore, not a graph
  edge.

The mapping is a pure function of the profile — `plan = plan_for(host_profile)` — and it is small enough to
read as a table:

<!-- noqa: book-float-ref — inline host-profile → plan mapping strip making the Scheduler function scannable, a reference not a numbered cross-referenced float -->
| Host profile | Ceiling | Budget | Emitted plan |
|---|---|---|---|
| Elastic staging | none (unbounded) | ∞ (unbounded) | fan the whole ready wave out; relax cost gates |
| Metered prod | low finite | finite | small concurrency; honor cost gates |
| Scarce local box | 1 | finite | serialize; honor cost gates |

Moving stress between hosts edits one row of this table — never the deploy graph.

**(c) Visual depiction.** The natural diagram, [ref:dag-policy-structure], is a data-flow — edge intents route, load leaves the
graph for the Scheduler, and a per-host profile drives the plan. Reused from the model's appendix
Structure slot:

<!-- label: dag-policy-structure -->
<!-- figure: assets/dag-policy-structure.svg | *Profile edit, not graph edit.* Correctness and cost-gate edges stay in the deploy graph, host-identical; the load intent is banned from the graph and moves to the Scheduler, which reads a per-host profile and emits the execution plan. Moving stress between hosts edits the profile, never the graph. -->

**(d) Invariants, and how they are checked.** A load-edge ban and a plan derivation, collected in [ref:host-stress-invariants]:

<!-- label: host-stress-invariants -->
<!-- table: Invariants of the host-stress model — load edges migrate to the Scheduler, never the deploy graph. [short: Invariants of the Physical view: host-stress edges] -->
| Invariant | Temporal shape | How it is checked |
|---|---|---|
| No deploy edge carries the `LOAD` intent | *□P* (safety) | Load-edge lint reads the graph and the Scheduler's graph-resident intent set; a `LOAD` edge is a finding. |
| The deploy graph is identical on every host | *□P* (safety) | Graph-parity check: the same graph is emitted for every host; a per-host fork is a finding. |
| The execution plan is a pure function of the host profile | *□P* (safety) | Derive-and-assert: the plan is recomputed from the profile, never hand-stored. |

<!-- point: the-execution-plan-derives-from-the-host-profile | The execution plan derives from the host profile. | terms: model-from-code, per-host-load-profile, join-key -->
**(e) Traceability and derivation direction.** *Model-from-code.* The plan is derived from the
per-host profile by a pure function, and a hand-stored plan or a `LOAD` edge is banned outright.
The join key is the host name, which indexes both the `HostLoadProfile` and the deploy phase that
runs under the emitted plan. This model is walked in full, with its Scheduler code, in the
Scenarios chapter's join example — here it is the Physical-view resident that the join reaches
into.

*Also seen in:* Process (concurrency rationing is a runtime-dynamics concern) and Scenarios (the
join example). Rendered in full in the Scenarios chapter; referenced here for the placement and
cost half.

## The control↔substrate dependency model {#control-substrate-dependency}

<!-- section-terms: control-substrate-dependency -->

<!-- point: declared-substrate-stances-turn-a-migration-grep-into-a-blast-radius | Declared substrate stances make a migration blast radius computable. | terms: control-substrate-dependency, migration-safety, blast-radius -->
<!-- index-def: control-substrate-dependency -->
The substrate-dependency model makes each governance mechanism declare, as typed metadata, the
substrate assumption it bakes in — bound to one substrate, substrate-aware, or
substrate-agnostic. It assesses **migration safety**: before a cross-cutting substrate change,
exactly which mechanisms assume the old substrate? That declaration turns a grep into a
*computed blast radius*. Joining the declared stances against the topology model on
the migration target prints the in-scope mechanisms as a table — a real answer, not a hopeful
search that misses the one whose assumption is implicit. A declaration lint requires the stance,
so a mechanism that reads the substrate silently cannot hide from the join. The appendix carries
its typed schema and the join code in full.

Worked once, on the plane the fleet actually migrated. When DocAble retired the Redis poll plane for a Cloud
Tasks push plane, the question was: *which mechanisms bake in "workers pull from a Redis sorted set"?* The
join answers it before the change lands. In scope are the mechanisms whose declared stance is *bound* to the
poll seam — the ones that read or maintain the sorted-set queues directly:

- the **queue-depth metric**, which reads the sorted-set structures to report backlog;
- the **stale-job sweep**, which reclaims work by scanning the pull queues;
- the **cancellation cleanup**, which must remove a cancelled job from every queue structure;
- the **priority-preservation requeue**, which re-enters preempted work ahead of same-class fresh work on
  the sorted set.

Each declares "bound to the poll plane," so each surfaces in the join's table for a migration whose target
is the push plane — a *computed* answer, not a hopeful grep that would miss the one whose Redis assumption is
implicit. A substrate-agnostic mechanism (say, one that reads only durable Postgres truth) declares its
stance and correctly does *not* appear.
