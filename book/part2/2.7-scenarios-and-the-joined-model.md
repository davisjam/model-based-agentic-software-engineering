# Scenarios and the Joined Model

## The Scenarios View: what the system does for someone

<!-- point: the-scenarios-view-walks-a-goal-and-validates-the-four | The Scenarios view walks a goal and validates the four. | terms: scenarios-view, four-plus-one-views -->
<!-- index-def: scenarios-view -->
*Does a real goal actually work, end to end, across everything the other four views project
separately?* The Scenarios view is the projection over the connected system model that walks a
goal across the other four rather than holding the system still. The Logical view says what the
system is, the Process view what it does at once, the Development view how it is packaged, the
Physical view where it runs — four static portraits, each a slice of the same connected model.
The +1 view sets them in motion. A **scenario** — a use case, a journey — walks
a real goal end to end, and in walking it exercises the other four and validates that they hold
up. Kruchten made scenarios the +1 for exactly this reason: a view is validated by walking it,
and the scenario is the walk.

**The scenario is where the models are held honest.** The five views are not parallel
documentation; they are a reasoning system projected from one connected representation — the
Scenarios view removes the burden of validating four independent models separately by exercising
all of them through a single engineering goal, and turns the Alignment Thesis back on the views
themselves.

<!-- point: a-user-journey-anchors-the-view-with-five-real-models | A user journey anchors the view; models enter where used. | terms: user-journey-model -->
One general type anchors the view. A **user journey** names the interfaces a user moves through
and the actions they take to accomplish something of value. Each of this chapter's models embodies
that type or serves it, and they are introduced where they enter. The chapter builds to the zoo's
flagship demonstration — four models joined on a single fact so a product goal reaches all the way
to how the deploy rations its tests.

The four models that feed the flagship join each set up their part of the composition, with the
full construct-and-invariant treatment of each in the appendix.

## The user-journey model {#user-journey-model}

<!-- section-terms: user-journey-model -->

<!-- point: the-user-journey-model-copies-nothing-and-the-zoo-joins-to-it | The user-journey model copies nothing; the zoo joins to it. | terms: user-journey-model, dependency-correctness, join-key -->
<!-- index-def: user-journey-model -->
The user-journey model makes the product's journeys first-class typed entities — each an actor
pursuing a goal through ordered steps, every boundary-crossing step joined to the endpoint it
calls. It assesses **dependency correctness**: does every step a journey declares have a real
call site, and is every real call declared? A call-site drift lint checks both directions. The
idea that makes it the join's entry point is that the journey *copies nothing* — a step's
endpoint references the service-flow model, its call-site anchor references the real code, and
those two references are the keys the coverage and placement models reach through. Name the
journey once and the rest of the zoo joins to it.

> Learn more about this governance mechanism: [user-journey model](appendix-b-user-journey-model.html).

## The agent-orchestration model {#agent-orchestration-model}

<!-- section-terms: agent-orchestration-model -->

<!-- point: method-parity-governs-the-fleet-like-the-product-it-ships | Method parity governs the fleet like the product it ships. | terms: agent-orchestration-model, method-parity, lifecycle-soundness -->
<!-- index-def: agent-orchestration-model -->
The agent-orchestration model is the developer-journey counterpart — the scenarios view pointed
at the fleet rather than the user. It models the agent lifecycle
(`Dispatched`→`Working`→`Landed`→`Tombstoned`, with `Abandoned` and recovery) as a typed state
machine, and the orchestrator's own refill-and-bank loop as a journey. It assesses **lifecycle
soundness**: a tombstone before a commit, or a landed agent that never tombstones, is an illegal
transition a checker catches. The distinctive move is **method parity** — the substrate that
produces the software is governed by the same tier-derivation and drift machinery pointed at the
product, so "is the fleet as checkable as what it ships" is a checked property. It sits in the
Scenarios view rather than the Process view because its organizing spine is a goal-directed
developer journey — the orchestrator pursuing "land the ratified work, refill the pool" — and
method parity is a Scenarios move; the lifecycle state machine is the construct that journey runs
on, and its one liveness invariant (*a landed agent eventually tombstones*) routes to the Process
view's temporal checker rather than making the model a Process entity. Its full
construct-and-invariant treatment is in the appendix.

> Learn more about this governance mechanism: [agent-orchestration model](appendix-b-agent-orchestration-model.html).

## Journey-criticality → test-placement {#journey-criticality-test-placement}

<!-- section-terms: journey-criticality-test-placement -->

<!-- point: a-journeys-criticality-derives-its-test-tier-never-stored | A journey's criticality derives its test tier, never stored. | terms: journey-criticality-test-placement, placement-soundness, derivation-direction -->
<!-- index-def: journey-criticality-test-placement -->
This model — the **Selector** in the join below — derives which environment tier a journey's
tests run in from the journey's criticality: a `MAJOR` part runs the fast local tier and the
full staging matrix, a `MINOR` part runs staging only. The asymmetry is deliberate: local is the
scarce, serialized host a developer hits first, so a major path earns a fast-tier local test to
catch a regression before it ever reaches staging, while a minor path runs only on the elastic
staging fleet where boxes are cheap. It assesses **placement soundness**. The
tier is *derived, never stored*: a stored tier literal is banned, so you cannot quietly push a
major path off the slow local gate to speed a run up. To move it you
must demote it to `MINOR` — a visible edit that says out loud "this path is no longer major." A
coverage-floor lint then holds the promise "every major part has a fast-tier test," which makes a
green local run mean something. Its full construct-and-invariant treatment is in the appendix.

> Learn more about this governance mechanism: [journey-criticality test-placement](appendix-b-journey-criticality-test-placement.html).

## Coverage → model-node mapping {#coverage-model-mapping}

<!-- section-terms: coverage-model-mapping, node-coverage -->

<!-- point: projecting-coverage-onto-nodes-makes-an-untested-invariant-visible | Projecting coverage onto nodes makes an untested invariant visible. | terms: coverage-model-mapping, node-coverage, invariant -->
<!-- index-def: coverage-model-mapping -->
<!-- index-def: node-coverage -->
Coverage-to-node mapping projects the test suite's coverage onto the model's *nodes* — states,
seams, invariants, journey endpoints — instead of its lines (node coverage over line coverage, as
[Metrics](3.5-metrics.html) laid out). It assesses **node-coverage
adequacy**: is every meaning I care about exercised by some test? An untested invariant cannot
hide inside a 95% line number here, because the invariant is a node, and a node is either covered
or a visible gap. An uncovered node is a backlog item; an uncovered node
in the critical subset is a build-blocking gate. In the join below it answers the plain question
the criticality floor rests on — are the journey's endpoints tested at all? Its full
construct-and-invariant treatment is in the appendix.

> Learn more about this governance mechanism: [coverage-to-node mapping](appendix-b-coverage-model-mapping.html).

## Journey task-closure — asserting the goal completed {#journey-task-closure}

<!-- section-terms: journey-task-closure -->

<!-- point: task-closure-types-what-the-terminal-assertion-must-mean | Task-closure types what the terminal assertion must mean. | terms: journey-task-closure, closure-strength, flow-vs-task -->
<!-- index-def: journey-task-closure -->
The three models above ask whether a journey's test *exists*, *runs*, and runs *in which tier*. None
asks what the test asserts at the end. Split the pair the model turns on: a *flow* assertion says
the journey ran — a page returned 200, a card appeared — while a *task* assertion says the user got
the thing they came for. A test built on flow alone can green while the task is broken, the artifact
never painted, the file never downloaded. The gap is one hop past the last flow assertion, and it is
where a real production break hid — a navigation to the editor route succeeded while the accessibility
view it should have shown failed to load. Journey task-closure closes that hop. It promotes the
journey's terminal "what *works* means" out of a review-checklist paragraph into a typed `closure`
post-condition: a small boolean expression over reusable observable predicates, joined by AND, OR, and
NOT, *"the artifact rendered AND a control is inspectable AND no error-fallback is shown."* The leaves come from a
shared library a journey subclasses rather than hand-rolling, and each prefers an accessibility
observable — a role, an accessible name — because that is how the user perceives that the task is done.

<!-- point: a-flow-only-closure-on-a-major-journey-is-a-finding | A flow-only closure on a major journey is a finding. | terms: closure-strength, flow-vs-task -->
From the expression a pure function derives a **closure-strength** (`TASK_CLOSED`, `FLOW_ONLY`, or
`DISABLED`), stored nowhere by hand. Two leaves are flow-only: *navigated to a URL*, *a route returned
2xx*. An expression may reference them, but a closure built only from them derives `FLOW_ONLY`, and on
a major journey that is a build finding — the mechanical form of "a journey test should have caught it."
That asymmetry is the model's teeth; [ref:task-closure-tree] draws the expression tree and the grade it
derives. This model assesses **closure meaning**, the axis its three
siblings leave to human review: presence and tier versus the meaning of the terminal assertion. And
because the closure is typed rather than prose, the same definition resolves two ways: a browser
assertion in the fast local tier, and a headless probe against the pre-promotion canary. That
restores "staging catches anything local catches" for the task dimension, a containment the fast
post-deploy battery had been blind to because it checks page integrity, never task closure. Its full
construct-and-invariant treatment is in the appendix.

<!-- label: task-closure-tree -->
<!-- figure: assets/task-closure-tree.svg | *Task-closure as an expression tree.* A boolean `closure` is an AND over observable predicates — the artifact rendered, a control is inspectable, no error-fallback shown. Two **flow-only** leaves (navigated to a URL; a route returned 2xx) are the weak ones: they prove a flow ran, not that the task closed. A pure `closure-strength()` reads the leaves and emits exactly one grade — `TASK_CLOSED`, `FLOW_ONLY`, or `DISABLED`. A `FLOW_ONLY` grade on a MAJOR journey is a build finding. -->

## Worked join — the journey↔coverage↔deploy-policy composition {#worked-join}

<!-- section-terms: models-join-not-repeat, join-key -->

<!-- point: four-models-join-on-one-fact-with-nothing-said-twice | Four models join on one fact, nothing said twice. | terms: models-join-not-repeat, join-key, traceability -->
<!-- index-def: models-join-not-repeat -->
**The compositional question:** *watch one fact — a journey is* major — *travel through four models
with nothing said twice, until a product goal reaches all the way to how the deploy rations its
tests.* The other model pages each show a single model; this one shows them **joining, not
repeating.** Four models compose on one shared key — the journey and its endpoints:

- the **user-journey model** (M13) names the journey and its endpoints;
- the **coverage-to-node map** (M5) asks whether those endpoints are tested at all;
- the **criticality-to-placement Selector** (M6) derives which host tier each test runs on from the
  journey's criticality;
- the **execution-policy Scheduler** (M7) decides *how* each host runs the tests it was handed — fan
  out, or serialize.

No model owns another's facts; each joins on the journey and its endpoints.

### The three questions the join answers

Three questions the raw deploy scripts and test config cannot answer on their own.

- **Goal-to-gate coverage**: *does a green local run mean every major journey actually ran?* The
  criticality floor makes "local-green implies every major path was exercised locally" a checked
  property, not a hope — and journey task-closure sharpens what *ran* means, proving the terminal
  assertion closes the user's task rather than merely reaching the last flow step.
- **Placement soundness**: *is any major journey mis-filed as staging-only?* Because the host tier
  is derived from criticality and stored nowhere by hand, you cannot quietly shove a major path off
  the local gate; you must demote it to minor, a visible edit.
- **Rationing correctness under cost and resource pressure**: *does the deploy fan tests out when
  it safely can, and serialize them only when it must?* The Scheduler honors a cost gate everywhere
  but rations concurrency only where a scarce box demands it, so a single-worker host serializes
  while an elastic host fans out, from one profile table.

Everything so far has examined models individually. This figure is the first time they
cooperate. The join has no single appendix diagram, so this composite is built from the four real panels,
adding only the join edges between them; read it left to right, in [ref:join-composite].

### The invariants the join spans

The join's invariants span all four models, collected in [ref:scenarios-invariants]. All are safety properties; the liveness that concurrency hands the fleet is stated and routed in the Process view, whose form-match rule sends a liveness invariant to a temporal checker.

<!-- label: scenarios-invariants -->
<!-- table: Invariants of the Scenarios view — the properties the journey-to-test join spans and how each is checked. [short: Invariants of the Scenarios view] -->
| Invariant | How it is checked |
|---|---|
| Every major journey-part has a test in the fast local tier | Coverage-floor lint (M6) walks the model; a major part with no local test is a finding. |
| A journey's declared deps match its real call sites, both ways | Call-site drift lint (M13): every declared dep has a real call site, every call site is declared. |
| Every declared journey endpoint is exercised by some test | Undertested-journey audit (M5): join coverage to the endpoint nodes; an uncovered endpoint is a gap. |
| The host tier is a pure function of criticality | Derive-and-assert (M6): a stored tier literal is banned; the lint recomputes the derivation. |
| No deploy edge carries the `LOAD` intent | Load-edge lint (M7) reads the graph and the Scheduler's graph-resident intents; a `LOAD` edge is a finding. |
| Staging's test set is a superset of local's and of prod's | Containment property test plus a live-model lint (M6): recompute containment by calling the selector, not auditing a matrix. |

### The Selector and Scheduler in code

Two pieces of real policy code make the join concrete — the **Selector** derives a host's test
roster from the journey model, and the **Scheduler** rations that roster per host. The full listing
is in the [invariant-DAG execution policy](appendix-b-invariant-dag-execution-policy.html) and
[journey-criticality](appendix-b-journey-criticality-test-placement.html) appendix entries; the join
needs only the Scheduler's call and its result:

```python
plan = plan_for(host_profile)   # (permits, honor_cost_gate), from the profile alone
```

The three named hosts show the whole behavior in one table:

<!-- noqa: book-float-ref — inline host→plan mapping strip making the Scheduler behavior scannable, a reference not a numbered cross-referenced float -->
| Host | Ceiling | Budget | Derived plan | Behavior |
|---|---|---|---|---|
| `local` | 1 | 100.0 | 1 permit, honor cost gate | **serialize** — scarce VM, cost gate + load gate both apply |
| `staging` | `None` (elastic) | ∞ | all permits, cost gate relaxed | **fan out** — no box scarce, no budget |
| `prod` | 4 | 50.0 | 4 permits, honor cost gate | low finite smoke ceiling |

Moving the stress burst between hosts is a one-cell edit to the profile table, not to the deploy
graph — which is why `LOAD` stays out of the DAG.

Five views, walked on real code, each with its invariants and the checker that holds them true. The
zoo has {{model_count}} named models, and the number makes Kruchten's point for him: no single
view is ever the whole picture. What the safety-critical world did because lives were at stake — keep
the models honest, trace every requirement to the code that realizes it — the rest of us now do too.
We do it because an agent will pay the upkeep, and because here, keeping the models executable proved
cheaper than reconstructing and re-inspecting the system by hand each time we needed to trust a
release.

## The Joined Model

## The views pay off when they join

<!-- point: the-views-are-worth-more-joined-than-apart | The five views are useful apart; their real value appears when they join. | terms: four-plus-one-views, model-zoo -->
The five views earn their keep separately. The Logical view answers a structural
question, the Process view a concurrency one, the Development view an ownership one,
the Physical view a placement one, and the Scenarios view a goal. Each is a projection:
it keeps the entities and relations its question needs and drops the rest. But a real
engineering task rarely stays inside one view. It starts in one and reaches across the
others. The larger value of the zoo shows up there — not in any single projection, but
in what the projections do when they meet.

## A request walks the connected slice

<!-- section-terms: scenarios-view, logical-view, process-view, development-view, physical-view -->

<!-- point: a-request-traverses-every-view-along-one-connected-slice | One engineering question traverses every view along a single connected slice. | terms: scenarios-view, logical-view, process-view, development-view, physical-view -->
Trace a single request. A user asks for a feature. The Scenarios view names the journey
that delivers it. That journey names endpoints, and the endpoints resolve in the Logical
view to components and the dependencies among them. Those components run as services and
concurrent workers in the Process view, ship inside packages someone owns in the
Development view, and land on deployment targets in the Physical view. Tests, invariants,
ownership, and policy attach along the walk. The agent never carries the whole codebase.
It carries the connected slice the question actually touches, and the walk is what
assembles that slice.

## The graph is what lets the views meet

<!-- point: the-graph-lets-the-views-meet-on-stable-identity | The system knowledge graph joins the views on stable identity, not on hand-kept consistency. | terms: system-knowledge-graph, four-plus-one-views -->
The walk works only because every view names the same entities. A service in the Logical
view is the same service the Process view schedules and the Physical view places. They
agree because they cite one identity, not because someone kept five diagrams consistent
by hand. That is the work the system knowledge graph does. The graph is not a sixth
picture standing beside the five views. It is what lets the views meet on stable
identity. Each projection discards what its own question ignores; the joins recover
exactly the neighboring facts the next question needs. Five independent diagrams drift
independently. Five projections over shared entities join, reuse facts, and expose a
contradiction the moment one appears.

## Where Modeling meets Alignment

<!-- point: an-explicit-relation-can-carry-a-predicate | Once a relation is written down explicitly, the environment can attach a predicate to it. | terms: thesis-modeling, thesis-alignment, map-and-territory -->
This is also where the Modeling Thesis meets the Alignment Thesis. While a relation lives
only in someone's head — service A consumes queue B, journey J reaches endpoint E, worker
W may run beside worker X — nothing can check it. Write the relation down explicitly, and
the environment gains something to check against: only a worker of this class may consume
that queue; every endpoint this journey names must exist; these two workers must never
hold the same lock. Making the relation explicit is the Modeling move. Attaching the
predicate is the Alignment move. The richer the representation, the more of engineering
judgment shifts from probabilistic reasoning toward a check the build can run on its own.

<!-- point: a-model-earns-its-place-twice | A model earns its place twice — it compresses the system for reasoning, and it creates a surface for obligations. | terms: thesis-modeling, thesis-alignment -->
So a model earns its place twice. It compresses the system into a slice a bounded reasoner
can hold, and it creates a surface on which an obligation can become executable. The first
payoff is why this Part built the zoo. The second is why the next Part can act on it.

<!-- point: this-part-supplied-the-world-the-next-part-gives-it-authority | This Part supplied the structured world; the next Part gives that world authority. | -->
This Part supplied the world the fleet reasons through; the next Part gives that world
authority. It takes the relations this Part made explicit and teaches the environment to
insist on them.

## This book's boundary

<!-- index-def: scope-of-modeling -->
<!-- point: this-book-is-an-introduction-the-doorway-outward | This chapter is the doorway outward. | terms: scope-of-modeling, model-zoo -->
This Part climbed one ascent: from selecting the right context, to connected knowledge, to
executable models, to a governed model the environment holds equal to the code. This
chapter stands at the top of that climb and opens the door past it. This book is an
introduction. It gives you enough kinds of model to start, and one
discipline — keep the map equal to the territory, so the model stays the interface the
fleet reasons through — that makes them pay. It does not teach any single formalism in
depth, and the zoo is not the whole field. Modeling software systems is a deep discipline
with decades of literature behind it. This chapter is the doorway out: it teaches you to
recognize the moment a sketch stops being enough, and points to where each concern goes next.

## When a sketch graduates

<!-- section-terms: scope-of-modeling -->

<!-- point: graduate-when-the-goal-sharpens-past-the-sketch | Graduate tools when the quality goal sharpens past the sketch. | terms: scope-of-modeling -->
There is a moment when a working sketch stops carrying its weight, and it is worth learning to
see it coming. **A sketch should become an analytic model when the quality goal hardens into a
measurable constraint.** The sketch is fine while the goal is a soft preference; the analytic tool
earns its cost the moment the goal becomes a constraint you can measurably fail.

<!-- point: the-recognition-signal-is-a-preference-hardening-into-a-constraint | The signal: a soft preference hardening into a hard constraint. | terms: scope-of-modeling -->
The signal is the goal itself hardening. "Fast is good" is a preference, and a napkin sketch of
the call graph carries it fine. Sharpen it to "every frame must finish inside 16 milliseconds" and
you have a real-time system — you now need schedulability analysis, not a vibe about which parts
look slow. "Less memory is nice" is a preference too. Sharpen it to "this must fit on a board with
64 kilobytes of RAM" and you need an honest memory model, budgeted byte by byte. The concern did
not change; the preference became a constraint, and the day a constraint can fail is the day the
sketch has to graduate. Learn to feel that hardening, and the rest of this chapter is a map of
where to go once you feel it. Graduating a sketch is the same motion the Part's ladder describes
from the other side: you climb a rung when a recurring engineering question makes the next
capability worth its cost.

<!-- index-def: protocols-and-tla -->
> ### Inset — Protocols and TLA+ {#inset-tla}
>
> When a property is not about one component but a *protocol* — many actors interleaving over time, each taking steps in an order you do not control — a single state assertion is not enough, and even a bounded walk of one component misses the cross-actor races. You specify the protocol in a **temporal-logic language** (TLA+ is the best-known), stating the actors, their steps, and the safety and liveness properties the interleaving must satisfy. A model checker then explores every interleaving the actors can produce *under the stated model and bounds* and either establishes the properties for that model or hands you a counterexample trace. This is the heaviest tool the Part points to, reserved for the invariant whose failure lives in a schedule no example test will ever pick — a distributed reservation, a lease-and-preempt loop, a two-phase hand-off between services.

<!-- index-def: digital-twin -->
<!-- point: digital-twins-shadow-a-physical-thing-out-of-scope | The digital twin shadows a physical thing, not code. | terms: digital-twin, cyber-physical-systems, map-and-territory -->
> ### Sidebar — What is a digital twin? {#sidebar-digital-twin}
>
> One branch of modeling this book leaves untouched is the *digital twin*: a live model of a physical thing, kept in step with its real counterpart by a stream of sensor data, and used to predict and control it. Digital twins are the modeling practice of embedded and cyber-physical systems — aircraft engines, factory lines, power grids, anything where the model shadows a running machine. Ours shadow a codebase; a twin shadows a turbine. The spine is the same — a model kept equal to its territory and reasoned over in the thing's place — but the territory is physical and the toolkit differs. The concept is commonly credited to Michael Grieves; for the engineering discipline under it, Lee and Seshia's *Introduction to Embedded Systems: A Cyber-Physical Systems Approach* is the standard on-ramp.

## Models tier; reasoning descends

<!-- noqa: book-visual — a one-paragraph reflective note on why the zoo tiers, not a structure or behavior to draw; the tiering it names is already carried by the Development view's own diagrams -->

<!-- section-terms: scope-of-modeling, reasoning-horizon, four-plus-one-views -->

<!-- point: tiered-models-are-how-a-finite-reasoner-scales-to-an-unbounded-system | Tiered models are how a finite reasoner scales. | terms: scope-of-modeling, reasoning-horizon, four-plus-one-views -->
<!-- index-example: reasoning-horizon -->
One scaling move underlies the whole zoo. The models tier:
system, subsystem, component, module, implementation, each a coarser or finer grain of the
same territory. A finite reasoner does not hold all of them at once. It enters at the level
its task needs and descends only as far as the work forces — reading the system model to
place a change, dropping to a component's invariants when it touches that component,
reaching raw code last. That descent is how tiered models scale the reasoning horizon:
each level covers more of the system per unit of working memory, so a bounded reasoner
spends its capacity only where the task actually bites.

<!-- point: every-tool-keeps-a-model-honest-against-some-territory | Every tool keeps a model honest against some territory. | terms: scope-of-modeling, map-and-territory, thesis-modeling -->
That descent is the move to carry out of the zoo. Every tool this chapter points to — UML, TLA+,
queueing theory, a digital twin — is another way to keep some model honest against some territory,
and to reason at the coarsest grain the task allows before dropping to a finer one. This book taught
one instance of that move, on software, with an agent paying the upkeep that once buried the
practice. The rest of the field is the same move on other territories. The day your quality goal
hardens past the sketch — the day you feel that graduation — one of these tools is where the
reasoning descends next.

## Can alignment exist without models?

<!-- point: alignment-without-models-yields-weak-authority | Implicit representations support only weak authority; explicit models are the substrate for stronger guarantees. | terms: thesis-modeling, thesis-alignment -->
One question sits under everything this Part has built, and it is worth answering before the
next Part takes these models up as authority: can alignment exist without models at all?

Yes. Natural-language prompts, briefs, examples, and supervision guide agents successfully,
sometimes spectacularly. MAGE does not claim otherwise. A prompt is a representation too, only
a weak one: implicit, local, untyped, mostly opaque to tools, and hard to compose, validate,
or keep true as the system moves. It can steer a build. It cannot, on its own, state,
compose, validate, and enforce the obligations engineering assurance rests on.

So the claim is narrow, and worth stating exactly. Implicit or weakly structured
representations support correspondingly weak forms of authority. Explicit models are not a
prerequisite for useful software; they are the substrate on which progressively stronger
guarantees become possible. **Without explicit models, alignment cannot become
authoritative.**

Read the whole argument as one line.

> Natural-language intent can guide autonomous work.
> Explicit models transform that intent into an engineering substrate.
> Alignment transforms that substrate into authority.

<!-- point: part-2-closed-the-zoo-part-3-gives-authority | The models are built; the next Part gives them authority. | -->
That honest reading closes the zoo. This Part walked each kind of model on real code and
showed the drift gate that holds each one to the code, so the map cannot quietly rot away
from the territory. What it has not shown is how you reach that state from a codebase that
carries none of it. The models are built; the next Part gives them authority.
