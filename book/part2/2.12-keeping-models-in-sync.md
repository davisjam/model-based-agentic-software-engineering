# Keeping the Models in Sync with the Code: A Measurement

This chapter keeps two different things true, and it is worth not conflating them. The provenance model
in the opening section keeps the *explanation* in sync with the change the code made. The drift
measurement that follows keeps the *model* in sync with the code it represents. Two syncs, two pairs. So
the documentation-hygiene aside near the end — stale status headers, a stale number left in prose — is
drift *of documentation*, caught by a reading pass; it is not the Documentation model, whose provenance
a derivation holds true by construction.

## Keeping the explanation true to the change: a provenance model

A system that changes a customer's artifact owes an explanation of what it changed and why. A
remediation inserts a description, retags a heading, repairs a reading order — then hands back an account
of the work. Those are two claims, and they can disagree. When the explanation is written by hand,
separately from the code that does the work, the two drift: the account omits half of what happened, or
names a change the code never made. And when something goes wrong, "which step made this change?" becomes
a multi-hop hunt across files — each hop cheap, the whole chain expensive. The question this model
answers: *does the human-facing explanation of what changed stay in sync with what the code actually did?*

> #### Provenance-and-changelog model · Documentation
>
> - **Engineering question** — Does the human-facing explanation of what changed stay in sync with what the code actually did?
> - **Model** — a provenance model: every mutation stamped, every inserted artifact recorded, and the customer-facing changelog *derived* from those stamps rather than written by hand.
> - **Property** — every change is stamped, every inserted artifact is recorded and survives to the output, and the changelog is a loss-free projection of the stamps — so what the customer is told changed equals what the code did.
> - **Quality attribute** — understandability, maintainability, auditability.

The architecture reverses the usual relationship: rather than describe the work afterward, the code
records it as it works, and the explanation is a *view* of that record. DocAble builds this as a mark
that rides inside the document itself. Three moves, in order:

- **Mutate, then stamp.** Every verb that changes the document writes an entry — which verb, in which
  pass, visible or invisible — into a provenance registry embedded in the file. A change that ships
  without its stamp is the failure this move exists to prevent.
- **Insert, then record.** Every artifact the tool adds is recorded with its locator and its placement,
  and it carries a reserved name-prefix so a later reader — and the validator — can tell an inserted
  artifact from one the author wrote.
- **Derive, don't author.** The changelog the customer reads is projected from the registry, one row per
  stamped entry, loss-free. Nobody writes it by hand. An empty registry yields an empty changelog — by
  construction, the document tells the truth about itself.

What the model buys is a single equality: what the customer is told changed equals what the code did. It
earns that because the registry the code writes as it works is the *only* source the changelog reads.
There is no second, hand-kept account to drift, so diagnosis turns from a cross-file hunt into a lookup.
The shape of the derivation is a mutation writing a stamp, the registry fanning out to a validation and a
customer-facing changelog.

The production model carries more than this view keeps: a separate stamp mechanism per document format,
an inserted-content registry with its own placement invariants, and a typed ownership contract naming
which code may write each stamp. This view keeps the loop — every change stamped, every insert recorded,
the changelog derived from the stamps — because the engineering question here is only whether the
explanation stays true to the change. What the tidy version hides is precisely what makes the loop
possible: before you can enforce a correspondence between code and explanation, you need a representation
in which that correspondence can be *stated*.

**Generalize.** The class is **Documentation**, and it is a model like the others in this Part, not a
category apart: the explanation is a *model of the action*, and like any model it can drift from what it
represents. The property it exposes is provenance-consistency — the account and the act stay equal, and
every statement in the account points back to what produced it. The move is useful wherever a system acts
on a user's artifact and must later explain or reverse what it did. The defense is always the same shape:
derive the explanation from a record the actor writes *as it acts*, force the emission with a check, and
generate the human-facing artifact from the record — rather than write the explanation separately and hope
the two agree.

**Industry variation.** Audit logs, data-pipeline provenance, change-data-capture, and regulatory audit
trails are all this model — a record the actor writes as it acts, and an explanation derived from it. What
separates the real ones from the theater is enforcement: whether emitting the record is optional or
mandatory.

<!-- worked-examples: externalize-knowledge -->
### Example — Cloudflare
Cloudflare keeps provenance by pinning identity, not location. A requirement in its policy corpus carries a
stable slug that survives edits to the surrounding document, and statements retain pointers back to the
originating sections that produced them. Move the text, rewrite the section, and the reference still
resolves — because the reference names an identity, not a line. This is the provenance function realized as
stable-identity referencing over a curated corpus, without a stamp emitted at the moment of change.

### Example — Siemens
Siemens threads provenance across an entire product lifecycle. Requirements, models, software, and tests are
traced to one another through a lifecycle system — the digital thread — so a change at one end can be
followed to what it touches at the other. The realization is heavyweight and cross-domain: traceability
maintained as first-class links across tools that were never one tool. Same function — keep a pointer from
each statement back to what produced it — carried by an estate rather than by a per-change stamp.

<!-- takeaway -->
The function is provenance: keep the explanation consistent with the system, and keep a pointer from each
statement back to what produced it. The realization is a company's own. Cloudflare pins identity to a
stable slug; Siemens threads traceability across a lifecycle estate; DocAble stamps each change at the
moment it makes it and derives the changelog from the stamps. Three realizations, one engineering move.
<!-- worked-examples-end -->

The full stamp-registry schema, the inserted-content placement invariants, and the changelog projection
belong to the provenance-and-stamp mechanism the model rests on — the per-format stamp writers and the
inserted-content registry — rather than to a separate document a reader must keep in sync.

> **Handoff to Alignment** — does the explanation of what changed stay in sync with what the code did → the provenance-and-changelog model → every change is stamped, every inserted artifact recorded, and the changelog is a loss-free projection of the stamps → understandability, maintainability, auditability → in Alignment the property acquires authority: a wiring check that fails the build on any mutator verb returning without writing a stamp is the constraint that makes an un-stamped change unexpressible; the reserved name-prefix on each inserted artifact is the sensor that tells inserted content from authored; an end-of-remediation validator walks the recorded insertions and confirms each survived to the output with its locator and placement intact; a gate fails loud on any new violation before the output ships.

With the account held true to the change, the chapter turns to the other sync it is named for: keeping the
*model* true to the *code*. That one is a measurement.

## The question: the map must equal the territory, or the bridge lies

Drift enforcement is where a model stops merely helping the fleet reason and the environment begins
refusing to let the model and the code silently disagree. Everything it promises rests on one
requirement.

A context-bounded fleet governs a context-exceeding codebase *through* structured models. The models are
the bridge the agents reason across. So the map must stay equal to the territory — equal over the
relations the model claims to represent, not over every line of code. Stated precisely: the model must
remain consistent with the territory over its declared surface. If a model claims something the code no
longer does, every agent that trusts the model inherits the lie.

<!-- index-def: models-bridge -->
> **The models-bridge.** The governed channel between the code and the authored models: the traceability edges that connect model elements to the code they represent, plus the drift checks that hold the two in agreement — the path by which authored models reach the agent's task context and its checks, and the relationship the agent reasons across.

"Keep the model in sync with the code, automatically" is the thesis question. It has a cheap-sounding
answer and an expensive-sounding one, and the honest result is that neither alone is enough.

## The mechanism: a two-layer net, and freshness by derivation

Sync holds through two layers stacked over the model↔code gap.

- **The soft layer — the reading pass.** A definition-of-done review reads the model's prose surface
  against the code: a frozen status header, a phase index missing a landed phase, a stale count in a
  sentence. A human or an Opus catches these because they live in prose. This layer aims; it cannot
  block, and it is fallible.
- **The hard layer — the derived floor.** A reconciliation lint resolves each model anchor against a
  live symbol in the code. The anchor points at a function or class definition a static resolver can
  find, not at a line number and not at a snapshotted copy. Reading the anchor resolves current code,
  not a stored copy. The relation is recomputed from live code rather than copied from a prior scan,
  which eliminates one class of temporal staleness — the drift a snapshot accrues between the scan that
  recorded it and the run that reads it. (A live resolver still depends on the anchor, the parser, the
  build, and the model's completeness; it removes the *snapshot* failure, not every failure.)

<!-- slogan: derived-defends-snapshotted-drifts -->
The property that does the work is **freshness by derivation, not by process.** A snapshot-plus-sync
process can drift between runs; a resolver over live code cannot. **Derived defends, snapshotted
drifts.** Anchor to a symbol, not a line — and where there is no clean symbol to anchor to, that absence
is itself a signal that the model is missing a point of abstraction (a refactoring target, not a gap to
paper over).

<!-- worked-examples: binds-model-to-territory -->
### Example — DocAble
DocAble closes the gate the rest of the corpus leaves open. Its models are bound to the code by a
derived drift check: each model anchor resolves to a live symbol at build time, and the build fails
the moment a model and the code it claims diverge over a checked relation. Nothing external in the
study reaches this rung — a blocking parity gate over the very territory the agents rewrite — which is
why it is the DocAble-unique move, and one software implementation of it.

### Example — Siemens {other}
Siemens is the instructive near-miss. Its digital thread synchronizes models across domains and
propagates a design change downstream into fresh analysis, which is real and rich. But it
synchronizes and propagates; it does not *block* divergence. The model-first company reaches every
modeling rung except this one — evidence that a blocking drift gate is a distinct capability, not a
free consequence of taking models seriously.

<!-- takeaway -->
The discipline measured here is *binding the model to the territory*: not merely keeping a model and
its code in step, but refusing the build when they disagree. It is the one rung even a decades-deep
model estate need not have, and the one this whole measurement is about.
<!-- worked-examples-end -->

## The model grows with the system

Sync is a living practice, not a one-time alignment. The territory grows; the model is edited to
match; a derived gate fails the build if it is not. Two cases from the study period show the loop. A
new PDF editor endpoint (2026-08-01) had to enter the service-flow catalogue or its parity gate would
fail — a new endpoint is, by construction, either a model edit or a parity failure. And three new
user-journey entities (2026-07-16) had to name their actors, goals, and the endpoints each step
calls, held to the real call sites by a two-way drift lint: a journey that names an endpoint no code
calls, or code that calls an endpoint no journey declares, fails the build.

*Honesty note:* the journey entities landed 2026-07-16 — inside the broader study period, before the
07-22 start of the drift-audit corpus; the service-endpoint example (08-01) is squarely in-window.

## The two failure modes: where drift still escapes

The net has two escape hatches. Neither is a footnote; they bound the claim.

**Failure mode 1 — the judgment miss.** A mis-alignment that is not mechanically decidable needs
subjective judgment. The anchor resolves (the code exists, so the hard floor reads green), yet the
*meaning* drifted. The soft reading layer is the only net for this, and it is fallible by
construction — a subtle semantic drift can pass a green definition-of-done. This is the drift that
slips through a hole in the soft layer.

**Failure mode 2 — the unmodeled.** The unmodeled is the Modeling-Thesis form of the residual the
Alignment part will name: a fact or relation that *should* be modeled but is not, so it has no anchor and no drift-check
can fire over it. You cannot detect drift of a thing you never modeled.
Here the net has no coverage at all — not a hole in a layer, but a region with no layer. When there is
no clean symbol to anchor to, that absence is the signal: it names a missing point of abstraction, a
refactoring target.

Both failure modes lean, by default, on an engineer or an agent *noticing*. The book has two
mechanisms that convert that noticing into machinery — the right in-book targets to cross-link:

- **The missing-model metric** (the orphan-coverage tracer) measures failure mode 2. It walks the *code*
  and asks, for each governance-relevant site, whether any model row or control node reaches it, then
  scores the remainder — the sites nothing models — as a rate and clusters them, so each cluster becomes
  a candidate for a new model. It turns "the estate's blind spot" into a queryable map instead of a thing
  you learn about when it bites. (A sibling metamodel, the **control-coverage census**, rolls *controls*
  up per control-target and flags an under-governed target — a distinct axis, not a measure of the
  unmodeled; do not read one for the other.) [note: A note on metamodels. An object model maps the code — service-flow, journeys, state machines — and its drift-check asks "does this model still match the code?" A metamodel instead checks the completeness of the model set over the territory: "is the right thing modeled at all?" The missing-model metric is the metamodel for failure mode 2 — it converts "an engineer happens to notice something isn't modeled" into a measured coverage gap. The control-coverage census is a different metamodel: it asks whether each control-target is governed, not whether each system fact is modeled. Same genre, different question — keep them apart.]
- **Self-governance — convert failures to controls** (the governance-conversion / "failures become
  machinery" loop; the reflection-facet substrate that extends the governance graph, and chapter 2.6's
  treatment) converts a recurring gap into a new model or control. Where the census *measures* the gap,
  this *closes* it: the unmodeled fact becomes a modeled one, and the net gains a segment it did not
  have.

## The honest reading

The result is narrow, and stating its limits is part of stating it. Four readings bound what this
measurement does and does not show.

- **Preliminary, small N.** Per window, the count of *genuine* model↔code drifts is small — a handful,
  not a headline. The model-sync claim rests on that small set of genuine model drifts the derived floor
  caught, plus zero model-drift reopens under heavy churn — not on any headline catch-rate, which would
  mix doc-legible catches with modeled ones and rest on a denominator too small for the model-sync slice.
  This is a field-report result, not a proof.
- **The catch-rate rose by composition, not by loosening.** The refresh window caught more drift
  (17 of 20 closes vs. the original's 6 of 36) because it moved more territory — product-heavy Epics
  with more doc surface — exactly where the reading layer is the only practical control. The net did
  not get weaker; there was more for it to catch.
- **The claim is narrow and it is about sync, not hygiene.** The three legs: the drift is real and
  used to escape (the ~27 pre-floor findings); the mechanism is derived reconciliation, not
  snapshot-and-sync (freshness by derivation); and it held under load (the churn row, with zero
  model-drift reopens). The doc-hygiene aside is kept separate on purpose.
- **The two failure modes are the boundary of the claim.** Sync is enforced for the modeled and
  mechanically-decidable; it is *aimed* for the semantic; and it is *absent* for the unmodeled until a
  metamodel or a self-governance reflex extends the net. That boundary is the honest shape of the
  result.
