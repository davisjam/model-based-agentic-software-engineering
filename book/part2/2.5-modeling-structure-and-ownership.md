# Modeling Structure and Decisions

Before an agent changes a system it has to answer a handful of questions that raw code answers
slowly and inconsistently: *What is this made of? What depends on what? Who owns this piece? What
may cross this boundary? What third-party material does the build rest on?* An engineer can
reconstruct these answers from implementation and history. A fleet can reconstruct them too, but
repeated reconstruction is precisely the cost this Part is trying to retire.

Structural models settle these questions once and hold the answer true. Each is a projection over
the connected system model that keeps the entities and relations bearing on structure and drops the
rest. This chapter organizes them by what you want to know — what the system is made of, who owns
each piece, what may cross a boundary — and by the two classes those questions fall into:
**Structural** facts about what exists, and **Decision** facts about what is permitted.

## Which services may connect?

<!-- section-terms: service-flow-model, executable-source-of-truth, data-flow-diagram -->

> #### Service-flow model · Decision
>
> - **Engineering question** — Which service may call which, and reach which resource?
> - **Model** — a typed catalog of every service, its endpoints, their authentication, and the wires that join a caller to a callee.
> - **Property** — only declared service-to-service edges are legal, and each carries its declared authentication posture. One node, the public web tier, faces the outside; every other node is internal.
> - **Quality attribute** — security, least-privilege, architectural integrity.

<!-- point: the-service-flow-model-answers-what-the-system-is-made-of | The service-flow model answers what the system is made of and what depends on what. | terms: service-flow-model, wiring -->
Service estates accumulate undocumented edges easily: a quick cross-service call made under deadline
can become permanent architecture without anyone deciding that it should. Deploy configuration and
handler code each hold fragments of the answer to "which service may call which?" The service-flow
model makes that answer explicit as a typed catalog of services, endpoints, authentication, and
permitted wires.

Read the permitted calls as a declared graph — a short list of arrows. The quality service may ask
the generation service. The conformance service may ask the validator. The worker may reach exactly
five downstream services; the merge stage mirrors the worker. Only the web tier is public — it is
the one node that faces the outside, and everything else sits behind an internal, authenticated
door. That allow-list is six or so nodes, one of them public, and every edge that is *not* drawn is
forbidden. [ref:service-allow-list] draws it — the one public node, the permitted arrows, and the
forbidden default around everything else.

<!-- label: service-allow-list -->
<!-- figure: assets/service-allow-list.svg | *Declared Service Connectivity.* Only the drawn service relationships are permitted; the web tier is the sole public node. The model makes the absence of an edge meaningful: undeclared connectivity is forbidden. -->

<!-- point: one-service-graph-generates-policy-and-reconciles-the-call-graph | One service graph generates the access policy and reconciles the real call graph. | terms: wiring, access-policy, model-to-code, model-from-code -->
What the model lets you establish is that declared architecture and running implementation cannot
silently diverge, and it earns that in **both directions**. The network access policy is *generated*
from the wires (model-to-code), so what a service may reach stays equal to what the model says it
may. The real call graph is *read back* and reconciled against the wires (model-from-code), so a
call nobody declared surfaces as a finding. A drawing of a service architecture goes stale the
afternoon someone adds an endpoint; this graph fails the build instead.

One illustrative invariant carries the shape: **every declared wire resolves to a real cross-service
call, and every real cross-service call resolves to a declared wire.** A call-graph parity lint holds
both halves — an undeclared call is an ungoverned one, and it is exactly the thing the check refuses.
The natural drawing is a **data-flow diagram**: the model on the left, the generators and parity
gates it feeds on the right, each edge labeled with what flows across it rather than what decides.

A decision model answers *who may do what.* Represent the
permissions explicitly — as data, not scattered call sites — and two powers follow. You can *check*
actual behavior against the declared policy, and you can encode part of the policy in a type so a
violation never compiles. Separate the *permission* from the *action*, write the permission down, and
let something compare the written policy to the running system. Network policy, firewall rules,
service-mesh authorization, and cloud access management are all this one model; the variation across
shops is only the enforcement rung — a firewall at runtime, a policy check at build, a type at
compile — not the shape of the model.

## Who owns each piece, and what may cross a boundary

<!-- section-terms: component-zone-model, code-zone, boundary-kind -->

> #### Component-and-zone model · Structural
>
> - **Engineering question** — Where am I, what may this file touch, and what senses a boundary violation?
> - **Model** — a typed catalog that gives every component a code zone: its directories, its tags, its boundary kind, the external seams it may cross — with one edge drawn forbidden.
> - **Property** — every in-scope source directory is owned by exactly one component, and only a sanctioned seam crosses a boundary. In particular, no ordinary code touches a powerful format library directly; all of it routes through one structured model per format.
> - **Quality attribute** — modularity and maintainability first; corruption-resistance (correctness) is the sharp secondary; keeping dangerous construction in one audited place serves security besides.

A large system rots along its dependency edges. Any file imports any other. A convenient shortcut in
one corner reaches across three subsystems, and six months later no one can say what depends on what.
DocAble's version of the failure is sharper than generic tangle. A powerful document library — the
kind that can rewrite a document's internal object structure — is a loaded weapon. Call it from the
wrong place and you can silently destroy the very accessibility structure the product exists to
build: the delivered file still opens and renders, but its remediation is gone, and the customer
finds out only with a screen reader.

<!-- point: the-component-zone-model-makes-ownership-a-queried-fact | The component-zone model makes ownership and boundary a queried fact. | terms: component-zone-model, ownership-correctness, boundary-soundness -->
<!-- index-def: component-zone-model -->
The next question is the one an agent asks before it edits a line: *where am I, and what may this
file touch?* The **component and zone model** answers it — a typed catalog that gives every
component a code zone (its focus directories, its tags, its boundary kind, the external seams it may
cross). "Which component owns this file" becomes a lookup, not a per-tool guess that each lint,
dispatcher, and context injector re-derives on its own and drifts on its own.

Draw the system as zones — a web tier, a worker tier, a cluster of small services, the storage and
queues, and the core that holds the rule engine and the per-format repair logic — and let dependency
edges run between them. One edge is drawn in red and forbidden: *ordinary code may not reach the raw
format library.* Every mutation of a format passes through one structured model dedicated to that format.
The model is the only door; the raw library lives behind it — a single sanctioned door with the
forbidden edge drawn around it. [ref:typed-seam] draws that single door and the forbidden reach
around it.

<!-- label: typed-seam -->
<!-- figure: assets/typed-seam.svg | *One Sanctioned Seam.* The model makes the architectural boundary explicit: ordinary remediation code may reach the format library only through the structured format model. A separate control makes the forbidden direct edge unexpressible or detectable. -->

<!-- point: ownership-and-boundary-become-lint-findings-not-slow-erosion | Ownership and boundary reaches become findings, not slow erosion. | terms: reverse-mapping, boundary-soundness -->
What the model lets you establish is that ownership and boundaries hold as the tree moves under
them. A reverse-mapping test reconciles the declared zones against the real directory tree in both
directions; a boundary lint refuses a reach outside a component's sanctioned seams. The illustrative
invariant: **every in-scope source directory is owned by exactly one component.** The test runs
reality-⊆-model over the declared source surface — the repository minus the paths that belong to no
component — so a moved or unowned directory is a finding while a vendored tree is exempt.

Find the resource powerful enough that uncontrolled access is dangerous — a raw database handle,
filesystem, format library, or credential — and route access through a single typed seam. Now the
model states a property worth defending: *the dangerous
thing is reachable from exactly one place.* That serves maintainability first — a preservation fix
made once at the seam holds for every caller — and correctness right behind it, because the
corrupting operation becomes unreachable from ordinary code.

<!-- worked-examples: externalize-knowledge -->
This is the layered-architecture and dependency-rule tradition, sharpened: a structural model earns
its keep when it names an edge that must not exist, at a resolution precise enough to police.

### Example — Spotify
Spotify externalizes its component topology and keeps it current by construction. A service catalog and
a System Model span thousands of repositories; ownership and dependency edges are written down, and the
diagrams stay synced because a tool generates them from the same source the services declare. What the
estate does not carry is a blocking gate. The model describes the topology faithfully, yet nothing fails
a build when a service drifts from it. This is the component-and-zone model's own function — topology made
an explicit, agent-facing fact — realized without the drift gate.

### Example — Cloudflare
Cloudflare leads with policy, not system structure, and still externalizes its topology in a catalog of
the same shape. Even a shop whose signature representation is a curated policy corpus externalizes enough
component topology for agents to resolve the estate. The variation is how much semantics the
representation carries and what authority, if any, is attached to it.

### Example — DocAble
DocAble takes the same topology model one rung further and gates it against the real tree. A reverse-mapping
check reads ownership back from the directory structure and set-diffs it against the declared zones in both
directions, so a moved or unowned directory fails the build instead of drifting in silence. Same fact
everyone externalizes — component ownership — but held equal to the code by a check rather than trusted to
stay current.

<!-- takeaway -->
Externalizing the component topology is common; gating it against the real tree is the variation that turns
a faithful drawing into a fact that cannot silently drift.

## Some facts describe; others declare

<!-- point: descriptive-facts-are-derivable-intent-bearing-facts-are-authored | Descriptive facts are derivable; intent-bearing facts are authored. | terms: descriptive-vs-prescriptive, model-from-code, boundary-kind -->
<!-- index-def: descriptive-vs-prescriptive -->
The component and zone model is the cleanest place to see a distinction that runs through every
model in this book. **Some model facts describe what exists; others declare what is allowed.**

- **Descriptive facts** mirror the system. Whether a declared focus directory exists, and whether
  every in-scope directory is owned once, can be read straight off the tree. A drift gate derives
  them and checks them; if the model disagrees with the code, the model is wrong.
- **Intent-bearing facts** — the strong form is a **prescriptive** or **blueprint** fact — declare
  what *ought* to be. *Which* component owns a directory, what boundary kind it is, which seams it
  may cross: the code cannot derive any of these. Someone authored them. The model records the
  intent and a lint defends it.

The distinction becomes load-bearing in Alignment. A drift gate proves
the model and the code *agree* — but agreement is not correctness. A descriptive model can faithfully
mirror a wrong system. **An independently authored *ought* gives the implementation something to be
wrong against even when it accurately describes itself.** That authored intent is the seam a
structural model hands forward to Alignment: the facts that describe can be checked against reality,
and the facts that declare are the ones a guardrail is there to enforce.

## The facts every consumer joins to

> **Domain registries · Structural** *(compressed here; full card in the appendix)*
>
> Some facts change slowly and are read everywhere — the file types the system handles, the
> governance rules it enforces. A fact read in many places and revised rarely is exactly the one
> that drifts when each reader keeps its own copy. A **domain registry** freezes each such fact in
> one table that every consumer joins to by key, so disagreement becomes a build failure rather than
> a latent inconsistency. One slice turns the lens on the governance itself: a rule-metadata registry
> keeps each rule's description beside the rule, and the published rule index — this book's own
> catalogue among them — is generated by reading those blocks, so the description cannot rot into a
> separate document nobody updates.
> *Property: every consumer joins by the registry key; no reader keeps a private copy.*
> [appendix: appendix-c-structure-and-boundaries]

## What third-party material the build depends on

> **Bill of materials · Structural** *(compressed here; full card in the appendix)*
>
> The last structural question looks outward: what does the build pull in that nobody in this
> repository wrote? A **bill of materials** is the dependency graph of the build — every third-party
> package, direct and transitive, the SBOM lens on the code — held complete by a build-time gate, so
> a fresh checkout never breaks on a resolve the author never saw fail. Its companion discipline
> closes the obvious gap: an out-of-band install an agent runs mid-task must land in the same change
> that relies on it, or it stays invisible to the manifest.
> *Property: every package the code or a quality gate imports appears in the matching manifest.*
> [appendix: appendix-c-structure-and-boundaries]

Structure, boundaries, and the decisions about what may cross them are now queryable engineering
facts rather than knowledge an agent reconstructs from raw code each time. What these models leave
out is *time* — what the parts do when many of them run at once, and where each one runs. That is the
next question.
