# Modeling Structure and Ownership

## The Logical View: what the system is

<!-- noqa: book-section-cap | The Logical View — the intro carries the boxed data-flow-diagram primer the reader needs before the view's models; the inset is a self-contained primer, not prose to break up -->

<!-- point: the-logical-view-answers-what-the-system-is | The Logical view answers what the system is. | terms: logical-view -->
<!-- index-def: logical-view -->
*What is this system made of, and what may depend on what?* That is the engineering question the
Logical view answers — a projection over the connected system model that keeps the entities and
relations bearing on structure and drops the rest. Before an agent can change a system, it must
answer that question first: what system am I actually looking at? The Logical view removes the
burden of reconstructing that structure from the implementation each time. Held as a drift-checked
model rather than a boxes-and-arrows sketch, it is the representation the fleet reasons through to
know what the system is — the functional structure of objects, types, and their relations, and the
Modeling Thesis at the grain of one view. It is the view most engineers already draw without
naming; here it is drawn once, projected from the shared model, and kept true.

<!-- point: the-logical-view-is-embodied-by-service-flow-and-registries | Data-flow and type-hierarchy forms; DocAble uses service-flow and registries. | terms: data-flow-diagram, type-hierarchy, service-flow-model, domain-registries -->
Common Logical-view forms include the **data-flow diagram** — which traces what data exists and who may
touch it — and the **type hierarchy** — which shows the concrete specializations of an abstract concept.
In DocAble the view is embodied chiefly by two models on live code: the **service-flow model**, the
functional structure of a service-oriented architecture, and the **typed domain registries**, the facts
that functional model rests on.

> Learn more about this governance mechanism: [service-flow model](appendix-b-service-flow-model.html).

> Learn more about this governance mechanism: [domain registries](appendix-b-domain-registries.html).

<!-- point: a-data-flow-diagram-traces-data-across-transforms | A data-flow diagram traces data across transforms. | terms: data-flow-diagram -->
<!-- index-def: data-flow-diagram -->
> ### Inset I5 — What is a data-flow diagram? {#inset-dataflow}
>
> A **data-flow diagram** traces *data* moving through transforms — a source, the stages that
> reshape it, and the sink — where each edge names *what flows across it*, not *what decides*.
> It differs from a control flowchart: a flowchart's diamonds branch on decisions; a
> data-flow's edges carry a document, a JSON blob, a rendered page. It is the natural lens for
> **security and privacy**, because the question there is exactly "where does this data go, and
> who may touch it on the way?" Draw it left to right, label each edge with the data on the
> wire, and a reader sees the path a piece of data takes and every component that handles it.
>
> <!-- figure: assets/dataflow-inset.svg | Each edge names the data on the wire — bytes in, a structured model through the transforms, a stamped model out. -->

<!-- point: an-inheritance-hierarchy-shows-what-kinds-the-system-handles | Type hierarchy is the companion form, named and set aside. | terms: type-hierarchy -->
A **type hierarchy** is the companion form: an abstract concept at the root and its concrete
specializations as leaves, read to see which extensions exist and where a new one would attach.
DocAble's document-format hierarchy is one — the abstract format at the root, the slide, word-processor,
spreadsheet, and PDF formats as leaves, each running the same operations against a different file model —
but the Logical view here is carried by the two models below, not by the hierarchy, so the concept is
named and set aside.

The two models below carry the view; data-flow and type hierarchy are the vocabulary they draw on.

## The service-flow / API model {#service-flow-model}

<!-- section-terms: service-flow-model, executable-source-of-truth -->

<!-- point: the-service-flow-model-is-a-service-architectures-typed-source-of-truth | The service-flow model is a service architecture's typed source-of-truth. | terms: service-flow-model, executable-source-of-truth, wiring -->

<!-- noqa: book-section-cap | The service-flow / API model — a model page rendered from the fixed five-field (a)-(e) template; the fields are one indivisible reference unit a reader scans by reflex across every model, so splitting one page breaks the uniform shape -->
*The typed source-of-truth for a service-oriented architecture — its services, their
endpoints, their authentication, and the wiring between them — from which the access policy
and environment wiring are generated and against which the real call graph is checked.*

<!-- point: the-model-answers-three-questions-scattered-config-cannot | The model answers three questions scattered config cannot. | terms: wiring, access-policy, contract-parity -->
**(a) Quality property it helps assess.** Three, each a question the scattered deploy config
and handler code cannot answer without a single model.

- **Wiring correctness**: *does every declared caller-to-callee edge have a real call site,
  and every real cross-service call a declared edge?* An undeclared call is an ungoverned one.
- **Access-policy parity**: *does the generated network access policy match the wiring the
  model declares?* The policy is emitted from the model, then diffed against the committed
  artifact — so what a service may reach stays equal to what the model says it may.
- **Contract parity**: *does each endpoint's declared request and response shape match the
  handler that serves it?* A drifted contract is a runtime failure the model turns into a
  build failure.

**(b) Constructs and relations.** A typed catalog in the dialect of a service-catalog schema,
adopted for its hard-won structure and read by the project's own tools.

- **`Service`**: one deployable unit, with its name, its owning layer, and the endpoints it
  serves.
- **`Endpoint`** — one API surface on a service: its path, its auth requirement, and its
  declared request and response contract.
- **`Wire`**: one declared caller-to-callee edge, joining a calling service to a called
  endpoint. The set of wires is the graph the access policy is generated from and the call
  graph is checked against.

**(c) Visual depiction.** The natural diagram, [ref:service-model-structure], is a data-flow — the model on the left, the
generators and parity gates it feeds on the right. Reused from the model's appendix Structure
slot:

<!-- label: service-model-structure -->
<!-- figure: assets/service-model-structure.svg | The service model feeds generators and parity gates. It is authoritative for what it generates and reconciled against reality for what it checks; either side diverging blocks the build. -->

**(d) Invariants, and how they are checked.** The checkers are the trunk drift-and-parity
machinery, pointed at the service graph, collected in [ref:logical-invariants]:

<!-- label: logical-invariants -->
<!-- table: Invariants of the Logical view — each with the check that holds it. [short: Invariants of the Logical view] -->
| Invariant | How it is checked |
|---|---|
| Every declared wire has a real call site | Call-graph parity lint: each `Wire` edge must resolve to a real cross-service call. |
| Every real cross-service call is a declared wire | Same lint, reverse direction — an undeclared call is a finding. |
| The generated access policy matches the wiring | Freshness lint over the generated policy: regenerate from the model, diff against the committed artifact. |
| Each endpoint's contract matches its handler | Contract parity check joining the `Endpoint` shape to the handler signature. |

<!-- point: the-service-flow-model-derives-bidirectionally | The service-flow model derives in both directions. | terms: derivation-direction, model-to-code, model-from-code, join-key -->
**(e) Traceability and derivation direction.** *Bidirectional.* The access policy and
environment wiring are model-to-code — generated from the declared model. The call-graph
parity runs model-from-code — it re-reads the real call sites and reconciles. The join key
from a model row to the code is the endpoint path, which indexes both a `Wire` edge and the
handler that serves it.

full here; referenced from the Physical chapter.

## The domain registries {#domain-registries}

<!-- section-terms: domain-registries, executable-source-of-truth -->

<!-- point: frozen-registries-are-the-single-source-every-consumer-joins-to | Frozen registries are the single source every consumer joins. | terms: domain-registries, join-key, fact-consistency -->
**Freeze engineering facts that change slowly but are consulted everywhere.** A fact read in
many places and revised rarely is exactly the fact that drifts when each reader keeps its own
copy; make it a registry every consumer joins to by key, and disagreement becomes a build
failure instead of a latent inconsistency.

The domain registries are the frozen tables the service-flow model rests on — the file types the system
handles, and other slowly-changing facts. Each is the single
source of truth for its slice: every place that presents a domain fact joins to the registry by key
rather than keeping its own copy, so they cannot disagree.

This is the view's *second* model, so it takes the compact strip, not the full five-field treatment
again — the parity machinery is the same trunk drift-and-parity check already shown above:

<!-- noqa: book-float-ref — compact key-value metadata strip for the view's second model, an inline reference not a numbered cross-referenced float -->
| | |
|---|---|
| **Quality property** | Fact consistency — every consumer of a domain fact agrees, because each joins to the registry. |
| **Join key** | The registry key (for the file-type registry, the format id / extension). |
| **Derivation** | Authored (the registry is the source of truth); consumers are checked *against* it. |
| **Checker** | A copied registry value in a consumer is a finding — the consumer must read the fact live. |
| **View** | Logical (one slice, the rule-metadata registry, is walked in full in the Development chapter). |

Concretely: the file-type registry lists the formats DocAble remediates. Three consumers read it by key —
the customer-facing comparison doc, the internal coverage table, and the code that switches on file type —
so a format added in one place appears in all three or the build fails. Copying `"pptx"` into a handler
instead of joining to the registry is the exact move the checker rejects. That turns "keep the docs in
sync" from a discipline into a build failure. Its full construct-and-invariant treatment is in the
appendix.

The Logical view names what the system is. Next, the Process view: what happens when many of
the parts run at once.

## The Development View: how the source is organized

<!-- point: the-development-view-maps-how-the-source-is-organized | The Development view maps how the source is organized. | terms: development-view -->
<!-- index-def: development-view -->
*How is the implementation packaged, and who owns each piece?* That is the question the
Development view answers — a projection over the connected system model, distinct from the
Process view's runtime-consistency question. The Process view held the running system
consistent. The Development view steps off the runtime entirely and looks at the source: how
the code is packaged into modules, which layer may depend on which, and who owns each piece. It
is the view the people and agents who *build* the system reason through. Before an agent
changes a line it must answer two questions — where am I in this codebase, and what may this
file touch? — and this view is the map that answers them.

<!-- point: one-general-type-and-two-real-models-carry-the-view | One general type and two real models carry the view. | terms: bill-of-materials, component-zone-model, rule-metadata-registry, domain-registries -->
One general type anchors the view. A **bill of materials** captures a project's dependencies,
direct and transitive — the software supply chain a build rests on. Two real models embody the
view on live code. The first is the component and zone model, the ownership and boundary map. The
second is the rule-metadata registry, the slice of the domain registries that models the governance
rules themselves — the same typed rule index this book's own catalogue is generated from, so the
book itself is partly governed by a model it describes.

> Learn more about this governance mechanism: [component and zone model](appendix-b-component-zone-model.html).

> Learn more about this governance mechanism: [domain registries](appendix-b-domain-registries.html).

<!-- point: a-bill-of-materials-demands-a-complete-dependency-manifest | A bill of materials demands a complete dependency manifest. | terms: bill-of-materials, sbom, dependency-manifest -->
<!-- index-def: bill-of-materials -->
A **bill of materials** — the view's general type — is the dependency graph of a build: every
third-party package it pulls in, direct and transitive, the SBOM lens on the code. It is a
development-view concern because a dependency is a packaging fact, not a runtime one: it decides
what the build fetches and what a fresh checkout must resolve.

DocAble makes that genre concrete as a **build-time completeness gate**. The gate fails the build
when a package the code or a quality gate imports is absent from the matching manifest, so a fresh
checkout can never break on a resolve the author never saw fail. Its companion discipline: an
out-of-band install an agent runs during a task must land in the same change that relies on it, or
it is invisible to the manifest — and invisible is where a supply-chain surprise lives. The bill of
materials is not a document someone maintains; it is the manifest the gate holds complete on every
build.

So much for what the build depends on. The next model answers the question an agent asks
first: where am I, and what is this file allowed to touch?

## The component & zone model {#component-zone-model}

<!-- section-terms: component-zone-model -->

<!-- noqa: book-section-cap | The component &amp; zone model — a model page rendered from the fixed five-field (a)-(e) template; the fields are one indivisible reference unit a reader scans by reflex across every model, so splitting one page breaks the uniform shape -->

<!-- point: the-component-zone-model-makes-ownership-a-queried-fact | The component-zone model makes ownership a queried fact. | terms: component-zone-model, code-zone, boundary-kind -->
<!-- index-def: component-zone-model -->
*A typed catalog of every component's code zone — its focus directories, its tags, its boundary
kind, its external seams, its read surfaces — so "which component owns this file, and what may
touch it" is a queried fact rather than a per-tool guess.*

<!-- point: it-assesses-ownership-correctness-and-boundary-soundness | It assesses ownership correctness and boundary soundness. | terms: ownership-correctness, boundary-soundness, reverse-mapping -->
**(a) Quality property it helps assess.** Two, both drifting silently the moment a directory
moves.

- **Ownership correctness**: *which component owns this file, and does that answer match the
  real directory tree?* A reverse-mapping test reconciles the declared zones against the tree in
  both directions, so a moved directory fails the test instead of quietly staling every tool's
  private inference.
- **Boundary soundness**: *may this component's zone reach that seam?* The declared boundary
  kind and sanctioned seams make an out-of-bounds reach a lint finding, not a slow erosion.

**(b) Constructs and relations.** A typed registry keyed by component.

- **`Component`** — one unit of ownership: its focus directories, its tags, its boundary kind
  (internal, a trust edge, an external seam), and its declared read surfaces.
- **The zone relation**: each `Component` claims a set of directories; their union must partition a
  **declared source surface** — the repository tree minus the paths that belong to no component
  (root config, top-level docs, generated output, vendored trees). The reverse-mapping test asserts
  the match both ways over that surface, so a moved or unowned *in-scope* directory is a finding
  while a vendored tree is not.
- **The seam relation**: each boundary component declares the external seams it may cross, so a
  reach outside the declared set is a finding.

**(c) Visual depiction.** The natural diagram, [ref:component-model-structure], is a component flow — the registry feeding the
tools that read it, with a reverse-mapping test joining registry to real tree. Reused from the
model's appendix Structure slot:

<!-- label: component-model-structure -->
<!-- figure: assets/component-model-structure.svg | The component registry feeds the boundary lints, dispatch, and context injection — every tool reads the same ownership answer — and a reverse-mapping test joins it to the real tree in both directions. -->

**(d) Invariants, and how they are checked.** A reverse-mapping test and boundary lints, collected in [ref:development-invariants]:

<!-- label: development-invariants -->
<!-- table: Invariants of the Development view — each with the check that holds it. [short: Invariants of the Development view] -->
| Invariant | How it is checked |
|---|---|
| Every declared zone matches a real directory | Reverse-mapping test, model ⊆ reality — a declared zone with no directory is a finding. |
| Every in-scope source directory is owned by exactly one component | Reverse-mapping test, reality ⊆ model, over the declared source surface — an unowned or double-owned in-scope directory is a finding; declared out-of-scope paths are exempt. |
| No component reaches a seam its boundary kind forbids | Boundary lint over the declared seam set. |

<!-- point: the-component-zone-model-derives-from-the-directory-tree | The component-zone model derives from the directory tree. | terms: model-from-code, reverse-mapping, join-key -->
**(e) Traceability and derivation direction.** *Split by field.* The reverse-mapping test re-reads
the real directory tree, so the tree is ground truth for a zone's **existence** and the tree's
**coverage** — but not for a component's *intent*. Who owns a directory, what boundary kind a
component is, and which seams it may cross are **authored**: the model records them and the boundary
lint defends them; the code cannot derive them.

<!-- noqa: book-float-ref — inline field-authority strip splitting the (e) derivation direction by field, a reference not a numbered cross-referenced float -->
| Field | Authority | How it is held |
|---|---|---|
| Zone existence — does each declared focus-dir exist? | **from code** | Reverse-mapping test, model ⊆ reality |
| Tree coverage — is every in-scope directory owned once? | **from code** | Reverse-mapping test, reality ⊆ model |
| Ownership assignment — *which* component owns a directory | **authored** | Declared; the test checks consistency, not that the choice is right |
| Boundary kind — internal / trust-edge / external seam | **authored** | Declared per component |
| Sanctioned seams — which seams a boundary may cross | **authored** | Declared set; the boundary lint holds every reach inside it |

The join key is the focus directory: a reader round-trips from a `Component` record to the files it
owns by that path prefix, and dispatch, lints, and context injection all resolve ownership through
the same key.

*Also seen in:* Logical (a component is a functional-structure unit). Rendered in full here.

That model maps the code. What maps the governance itself? The next registry turns the lens on
the rules — and, because this book is generated from that same index, on the book you are
reading.

## The rule-metadata registry {#rule-metadata-registry}

<!-- section-terms: rule-metadata-registry, domain-registries -->

<!-- point: rule-metadata-lives-beside-each-rule-and-generates-the-index | Rule metadata lives beside each rule and generates the index. | terms: rule-metadata-registry, rule-index-consistency, round-trip -->
<!-- index-def: rule-metadata-registry -->
The rule-metadata registry is the self-referential slice of the domain registries: the governance
rules' own metadata, and so a model the governance machinery — and this book — are partly governed
by. It assesses **rule-index consistency**: does the published index match the rules declared in the
code?

The move is to keep the metadata *beside the rule it describes*. Each entry carries a small typed
block at its own site. Here is the one for the component & zone model above:

```
| Form        | typed-ir   |
| Move        | package    |
| Model       | is-a-model |
| Enforcement | Hard       |
```

The index is generated by reading every such block, one row per rule. That same block becomes:

```
| Component & zone model | typed-ir | package | is-a-model | Hard | … |
```

Two gates hold the round-trip. A **completeness lint** fails a rule whose block omits a required
field. A **freshness lint** re-generates the index and fails the build if the committed rows differ
from the regeneration — so the index cannot drift from the blocks it summarizes. Because the
description lives next to the rule, it cannot rot into a separate document nobody updates, and a
reader round-trips from a published index row straight to the declaring site. This book's catalogue
is built exactly this way: the row you would find in its index is generated from the block on the
entry's page, and the same freshness gate holds them equal.

---

This view answered the two questions an agent asks before it edits: where am I, and what may this
file touch. The source is mapped. What the map leaves out is where the packaged parts actually
*run* — on which hosts, under what cost and load ceiling. That is the Physical view.
