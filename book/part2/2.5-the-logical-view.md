# The Logical View: what the system is

<!-- noqa: book-section-cap | The Logical View — the intro carries the boxed data-flow-diagram primer the reader needs before the view's models; the inset is a self-contained primer, not prose to break up -->

<!-- point: the-logical-view-answers-what-the-system-is | The Logical view answers what the system is. | terms: logical-view -->
<!-- index-def: logical-view -->
*What is this system made of, and what may depend on what?* That is the engineering question the
Logical view answers — a projection over the connected system model that keeps the entities and
relations bearing on structure and drops the rest. Before an agent can change a system, it must
answer that question first: what system am I actually looking at? The Logical view removes the
burden of reconstructing that structure from the implementation each time. Held as a drift-checked
model rather than a boxes-and-arrows sketch, it is the representation the fleet reasons through to
know what the system is — the functional structure of objects, types, and their relations, and the
Modeling Thesis at the grain of one view. It is the view most engineers already draw without
naming; here it is drawn once, projected from the shared model, and kept true.

<!-- point: the-logical-view-is-embodied-by-service-flow-and-registries | Data-flow and type-hierarchy forms; DocAble uses service-flow and registries. | terms: data-flow-diagram, type-hierarchy, service-flow-model, domain-registries -->
Common Logical-view forms include the **data-flow diagram** — which traces what data exists and who may
touch it — and the **type hierarchy** — which shows the concrete specializations of an abstract concept.
In DocAble the view is embodied chiefly by two models on live code: the **service-flow model**, the
functional structure of a service-oriented architecture, and the **typed domain registries**, the facts
that functional model rests on.

> Learn more about this governance mechanism: [service-flow model](appendix-b-service-flow-model.html).

> Learn more about this governance mechanism: [domain registries](appendix-b-domain-registries.html).

<!-- point: a-data-flow-diagram-traces-data-across-transforms | A data-flow diagram traces data across transforms. | terms: data-flow-diagram -->
<!-- index-def: data-flow-diagram -->
> ### Inset I5 — What is a data-flow diagram? {#inset-dataflow}
>
> A **data-flow diagram** traces *data* moving through transforms — a source, the stages that
> reshape it, and the sink — where each edge names *what flows across it*, not *what decides*.
> It differs from a control flowchart: a flowchart's diamonds branch on decisions; a
> data-flow's edges carry a document, a JSON blob, a rendered page. It is the natural lens for
> **security and privacy**, because the question there is exactly "where does this data go, and
> who may touch it on the way?" Draw it left to right, label each edge with the data on the
> wire, and a reader sees the path a piece of data takes and every component that handles it.
>
> <!-- figure: assets/dataflow-inset.svg | Each edge names the data on the wire — bytes in, a structured model through the transforms, a stamped model out. -->

<!-- point: an-inheritance-hierarchy-shows-what-kinds-the-system-handles | Type hierarchy is the companion form, named and set aside. | terms: type-hierarchy -->
A **type hierarchy** is the companion form: an abstract concept at the root and its concrete
specializations as leaves, read to see which extensions exist and where a new one would attach.
DocAble's document-format hierarchy is one — the abstract format at the root, the slide, word-processor,
spreadsheet, and PDF formats as leaves, each running the same operations against a different file model —
but the Logical view here is carried by the two models below, not by the hierarchy, so the concept is
named and set aside.

The two models below carry the view; data-flow and type hierarchy are the vocabulary they draw on.

## The service-flow / API model {#service-flow-model}

<!-- section-terms: service-flow-model, executable-source-of-truth -->

<!-- point: the-service-flow-model-is-a-service-architectures-typed-source-of-truth | The service-flow model is a service architecture's typed source-of-truth. | terms: service-flow-model, executable-source-of-truth, wiring -->

<!-- noqa: book-section-cap | The service-flow / API model — a model page rendered from the fixed five-field (a)-(e) template; the fields are one indivisible reference unit a reader scans by reflex across every model, so splitting one page breaks the uniform shape -->
*The typed source-of-truth for a service-oriented architecture — its services, their
endpoints, their authentication, and the wiring between them — from which the access policy
and environment wiring are generated and against which the real call graph is checked.*

<!-- point: the-model-answers-three-questions-scattered-config-cannot | The model answers three questions scattered config cannot. | terms: wiring, access-policy, contract-parity -->
**(a) Quality property it helps assess.** Three, each a question the scattered deploy config
and handler code cannot answer without a single model.

- **Wiring correctness**: *does every declared caller-to-callee edge have a real call site,
  and every real cross-service call a declared edge?* An undeclared call is an ungoverned one.
- **Access-policy parity**: *does the generated network access policy match the wiring the
  model declares?* The policy is emitted from the model, then diffed against the committed
  artifact — so what a service may reach stays equal to what the model says it may.
- **Contract parity**: *does each endpoint's declared request and response shape match the
  handler that serves it?* A drifted contract is a runtime failure the model turns into a
  build failure.

**(b) Constructs and relations.** A typed catalog in the dialect of a service-catalog schema,
adopted for its hard-won structure and read by the project's own tools.

- **`Service`**: one deployable unit, with its name, its owning layer, and the endpoints it
  serves.
- **`Endpoint`** — one API surface on a service: its path, its auth requirement, and its
  declared request and response contract.
- **`Wire`**: one declared caller-to-callee edge, joining a calling service to a called
  endpoint. The set of wires is the graph the access policy is generated from and the call
  graph is checked against.

**(c) Visual depiction.** The natural diagram, [ref:service-model-structure], is a data-flow — the model on the left, the
generators and parity gates it feeds on the right. Reused from the model's appendix Structure
slot:

<!-- label: service-model-structure -->
<!-- figure: assets/service-model-structure.svg | The service model feeds generators and parity gates. It is authoritative for what it generates and reconciled against reality for what it checks; either side diverging blocks the build. -->

**(d) Invariants, and how they are checked.** The checkers are the trunk drift-and-parity
machinery, pointed at the service graph, collected in [ref:logical-invariants]:

<!-- label: logical-invariants -->
<!-- table: Invariants of the Logical view — each with the check that holds it. [short: Invariants of the Logical view] -->
| Invariant | How it is checked |
|---|---|
| Every declared wire has a real call site | Call-graph parity lint: each `Wire` edge must resolve to a real cross-service call. |
| Every real cross-service call is a declared wire | Same lint, reverse direction — an undeclared call is a finding. |
| The generated access policy matches the wiring | Freshness lint over the generated policy: regenerate from the model, diff against the committed artifact. |
| Each endpoint's contract matches its handler | Contract parity check joining the `Endpoint` shape to the handler signature. |

<!-- point: the-service-flow-model-derives-bidirectionally | The service-flow model derives in both directions. | terms: derivation-direction, model-to-code, model-from-code, join-key -->
**(e) Traceability and derivation direction.** *Bidirectional.* The access policy and
environment wiring are model-to-code — generated from the declared model. The call-graph
parity runs model-from-code — it re-reads the real call sites and reconciles. The join key
from a model row to the code is the endpoint path, which indexes both a `Wire` edge and the
handler that serves it.

## The domain registries {#domain-registries}

<!-- section-terms: domain-registries, executable-source-of-truth -->

<!-- point: frozen-registries-are-the-single-source-every-consumer-joins-to | Frozen registries are the single source every consumer joins. | terms: domain-registries, join-key, fact-consistency -->
**Freeze engineering facts that change slowly but are consulted everywhere.** A fact read in
many places and revised rarely is exactly the fact that drifts when each reader keeps its own
copy; make it a registry every consumer joins to by key, and disagreement becomes a build
failure instead of a latent inconsistency.

The domain registries are the frozen tables the service-flow model rests on — the file types the system
handles, and other slowly-changing facts. Each is the single
source of truth for its slice: every place that presents a domain fact joins to the registry by key
rather than keeping its own copy, so they cannot disagree.

This is the view's *second* model, so it takes the compact strip, not the full five-field treatment
again — the parity machinery is the same trunk drift-and-parity check already shown above:

<!-- noqa: book-float-ref — compact key-value metadata strip for the view's second model, an inline reference not a numbered cross-referenced float -->
| | |
|---|---|
| **Quality property** | Fact consistency — every consumer of a domain fact agrees, because each joins to the registry. |
| **Join key** | The registry key (for the file-type registry, the format id / extension). |
| **Derivation** | Authored (the registry is the source of truth); consumers are checked *against* it. |
| **Checker** | A copied registry value in a consumer is a finding — the consumer must read the fact live. |
| **View** | Logical (one slice, the rule-metadata registry, is walked in full in the Development chapter). |

Concretely: the file-type registry lists the formats DocAble remediates. Three consumers read it by key —
the customer-facing comparison doc, the internal coverage table, and the code that switches on file type —
so a format added in one place appears in all three or the build fails. Copying `"pptx"` into a handler
instead of joining to the registry is the exact move the checker rejects. That turns "keep the docs in
sync" from a discipline into a build failure. Its full construct-and-invariant treatment is in the
appendix.
