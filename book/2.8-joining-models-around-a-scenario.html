Part 2 — Modeling  ::  Chapter 12

2.8 Joining Models Around a Scenario

A real engineering goal rarely stays inside one model. A scenario — a use case or journey — walks a goal end to end and forces several projections to meet: structural dependencies, behavior, ownership, placement, measurement, and provenance may all matter before the goal closes. The scenario does not replace validation of those models individually. Its value is compositional: it exposes whether the facts and properties that were sensible in isolation still join coherently around one piece of work.

The scenario itself is therefore not a seventh mega-model. It is a traversal across models joined on stable identities.

Scenario / joined view · Behavioral

  • Engineering question — Does the whole system still accomplish the user's goal through valid states once the separate models are composed?
  • Model — one goal walked end to end across the other models — the join an engineer performs, not a seventh mega-model the system stores.
  • Property — the goal completes only through a sequence of valid states, with every cross-cut — ownership, authorization, a measured bound, provenance — satisfied at each hop.
  • Quality attribute — end-to-end correctness, the composite of what the other models each guarantee.

One type anchors the walk. A user journey names the interfaces a user moves through and the actions they take to accomplish something of value. Each model in this chapter serves that walk, and each is introduced where it enters. The chapter builds to a flagship demonstration — four models joined on a single fact, so a product goal reaches all the way to how the deploy rations its tests.

2.8.1 The user-journey model

The user-journey model makes the product's journeys first-class typed entities — each an actor pursuing a goal through ordered steps, every boundary-crossing step joined to the endpoint it calls. It assesses dependency correctness: does every step a journey declares have a real call site, and is every real call declared? A call-site drift lint checks both directions. The idea that makes it the join's entry point is that the journey copies nothing — a step's endpoint references the service-flow model, its call-site anchor references the real code, and those two references are the keys the coverage and placement models reach through. Name the journey once and the other models join to it.

The same walk turns on the fleet as well as the product: pointed at the agents that build the software rather than the users it serves, the scenario becomes method parity — the substrate that produces the software is governed by the same machinery pointed at the product. Part IV takes that up where it operates the fleet; the appendix carries its full model.

2.8.2 The feeder models

Three small models feed the flagship, each answering one question about a journey's tests. They are named here with the single property each contributes; their full construct-and-invariant treatments are in the appendix, and the join below shows each doing its part.

  • Journey-criticality → test-placement — the Selector in the join. It derives which host tier a journey's tests run in from the journey's criticality: a major part earns the fast local tier and the full staging matrix, a minor part runs staging only. It assesses placement soundness, and its property is that the tier is derived, never stored — a stored tier literal is banned, so you cannot quietly push a major path off the slow local gate; to move it you must demote it to minor, a visible edit. Learn more.
  • Coverage → model-node mapping — projects the test suite's coverage onto the model's nodes — states, seams, invariants, journey endpoints — instead of its lines. It assesses node-coverage adequacy, and its property is that an untested invariant cannot hide inside a 95% line number, because the invariant is a node, and a node is either covered or a visible gap. Learn more.
  • Journey task-closure — the three models above ask whether a journey's test exists, runs, and runs in which tier; none asks what the test asserts at the end. Task closure asks whether a journey test proves that the user achieved the goal rather than merely that the flow ran. Split the pair it turns on: a flow assertion says the journey ran; a task assertion says the user got the thing they came for. A test built on flow alone can green while the task is broken — the artifact never painted, the file never downloaded. The model expresses closure through typed observable predicates and derives a closure-strength grade (TASK_CLOSED, FLOW_ONLY, or DISABLED), each predicate preferring an accessibility observable because that is how the user perceives the task is done. A major journey whose test proves only navigation is a visible gap — a FLOW_ONLY grade on a major journey is a build finding, the mechanical form of "a journey test should have caught it." The appendix gives the expression language and the full model. Learn more.

2.8.3 Worked join — the journey↔coverage↔deploy-policy composition

The compositional question: watch one fact — a journey is major — travel through four models with nothing said twice, until a product goal reaches all the way to how the deploy rations its tests. The other model pages each show a single model; this one shows them joining, not repeating. Four models compose on one shared key — the journey and its endpoints:

  • the user-journey model (M13) names the journey and its endpoints;
  • the coverage-to-node map (M5) asks whether those endpoints are tested at all;
  • the criticality-to-placement Selector (M6) derives which host tier each test runs on from the journey's criticality;
  • the execution-policy Scheduler (M7) decides how each host runs the tests it was handed — fan out, or serialize.

No model owns another's facts; each joins on the journey and its endpoints.

The three questions the join answers

Three questions the raw deploy scripts and test config cannot answer on their own.

  • Goal-to-gate coverage: does a green local run mean every major journey actually ran? The criticality floor makes "local-green implies every major path was exercised locally" a checked property, not a hope — and journey task-closure sharpens what ran means, proving the terminal assertion closes the user's task rather than merely reaching the last flow step.
  • Placement soundness: is any major journey mis-filed as staging-only? Because the host tier is derived from criticality and stored nowhere by hand, you cannot quietly shove a major path off the local gate; you must demote it to minor, a visible edit.
  • Rationing correctness under cost and resource pressure: does the deploy fan tests out when it safely can, and serialize them only when it must? The Scheduler honors a cost gate everywhere but rations concurrency only where a scarce box demands it, so a single-worker host serializes while an elastic host fans out, from one profile table.

The composite picture

Everything so far has examined models individually. This figure is the first time they cooperate. The join has no single appendix diagram, so this composite is built from the four real panels, adding only the join edges between them; read it left to right, in Figure 2.8-1.

The invariants the join spans

The join's invariants span all four models, collected in Table 2.8-1. All are safety properties; the liveness that concurrency hands the fleet is stated and routed with the behavioral model, whose form-match rule sends a liveness invariant to a temporal checker.

Two pieces of real policy code make the join concrete — the Selector derives a host's test roster from the journey model, and the Scheduler rations that roster per host. Tracing one fact through four models

The join keys chain, and a reader can walk them against the figure: the endpoint ties M13 to M5, the criticality ties M13 to M6, the derived tier ties M6 to M7's roster, and the host profile ties the roster to the plan. Follow those four keys and "this journey is major" round-trips all the way to "these tests serialize on the local box" — nothing hand-stored along the way, a stored tier or a LOAD edge banned outright, and a drift lint mechanizing each hop. The joined view is a traversal across models, not a seventh mega-model.

2.8.4 The Payoff Is in the Join

The models pay off when they join

Each model earns its keep separately. The structural model answers a dependency question, the behavioral model a concurrency one, the ownership model a responsibility one, the deployment model a placement one, and the scenario a goal. Each is a projection: it keeps the entities and relations its question needs and drops the rest. But a real engineering task rarely stays inside one model. It starts in one and reaches across the others. The larger value shows up there — not in any single projection, but in what the projections do when they meet.

A request walks the connected slice

Trace a single request. A user asks for a feature. The scenario names the journey that delivers it. That journey names endpoints, and the endpoints resolve to components and the dependencies among them. Those components run as services and concurrent workers, ship inside packages someone owns, and land on deployment targets. Tests, invariants, ownership, and policy attach along the walk. The agent never carries the whole codebase. It carries the connected slice the question actually touches, and the walk is what assembles that slice.

The graph is what lets the projections meet

The walk works only because every model names the same entities. A service named in the structural model is the same service the behavioral model schedules and the deployment model places. They agree because they cite one identity, not because someone kept five diagrams consistent by hand. That is the work the system knowledge graph does. The graph is not a sixth picture standing beside the models. It is what lets the projections meet on stable identity. Each projection discards what its own question ignores; the joins recover exactly the neighboring facts the next question needs. Five independent diagrams drift independently. Five projections over shared entities join, reuse facts, and expose a contradiction the moment one appears.

2.8.5 Where Modeling Meets Alignment

A relation that lives only in human memory can still influence engineering work — a reviewer can remember it, an agent can infer it, a test may indirectly expose its violation. What the environment lacks is a stable semantic object it can reuse without reconstructing the relation each time. Modeling supplies that object. "Service A consumes queue B," "journey J reaches endpoint E," and "worker W may run beside worker X" become explicit relations with stable identities and meanings.

Once they are explicit, more obligations become mechanically expressible: only workers of this class may consume that queue; every endpoint named by this journey must exist; these two workers must never hold the same lock. Making the relevant semantics explicit is the Modeling move. Deciding what authority should act on the obligation is the Alignment move.

This is why MAGE teaches Modeling first. Not because Alignment is impossible without it — Docker's sandboxes and raw-artifact tests already disproved that — but because explicit abstractions move the boundary. Questions that otherwise require probabilistic reconstruction or human judgment can become properties the environment can analyze and, where appropriate, enforce.

The selection rule is the same one this Part has used throughout: choose the coarsest representation at which the engineering question becomes answerable. Too coarse and the property has no purchase; too fine and the reasoner pays for detail the question does not need.

2.8.6 The mental toolbox

The Part opened with one question and promised a table at its close. Here it is. You came into Part II able to say why models matter; you leave it able to choose one. We did not pick these models because a methodology prescribed five boxes to fill — we began with what an engineer needed to know, and each need selected a representation. Work back through the models this Part built on DocAble — structure and ownership, behavior and execution, measurement and documentation — and a small, reusable toolbox falls out, collected in Table 2.8-2. For each engineering concern it gives the model that answers it, the property the model then lets you state, and the quality attribute that property serves. The columns run in the order the opener named: name what you need to reason about, reach for the model, read off the property, and land on a quality an engineer already knows how to want.

Concurrency and ownership are not a sixth kind of model; they are a specialization — an owner and a lease laid over the behavioral machine, and the queue structures the owner claims from added to the structural one. The test of the Part is not whether you can recite these rows for DocAble. It is whether you can fill the same table for a system of your own.

The flagship earlier in this chapter walked the join move on the fleet's own models. The same move composes the six product models above into a single end-to-end scenario: a document arrives, is planned and split, remediated under a single owner with every change stamped, validated and merged, its evidence derived, and delivered — one goal walked across all six, each hop governed by a different model. The system keeps the six models separate, each pinned to its code by a drift check; the scenario is the join you perform across them, not a seventh mega-model it stores.

2.8.7 Variation between the models is the next Part's subject

Some of these properties already have concrete mechanisms in DocAble; others do not. That variation is useful rather than embarrassing. A model can make a property explicit and measurable before the organization decides that violation should block work. The production cost envelope is one example: modeled and sensed, but report-only on the live path.

Part III takes that variation as its subject. It asks which obligations should be constraints, which require sensors, which evidence a validator should judge, where a gate should block progress, and where human judgment remains appropriate because the necessary semantics are not yet represented or the decision should not be mechanized.

2.8.8 When Lightweight Models Stop Being Enough

MAGE does not replace established modeling disciplines. The models in this Part are deliberately lightweight — enough structure to answer recurring engineering questions, support agent reasoning, and permit mechanical checks. When the engineering question requires stronger analysis, use the established formalism built for it.

There is a moment when a working sketch stops carrying its weight. A sketch should become an analytic model when the quality goal hardens from a soft preference into a constraint you can measurably fail. "Fast is good" is a preference a napkin sketch carries fine; sharpen it to "every frame must finish inside 16 milliseconds" and you have a real-time system that needs schedulability analysis, not a vibe about which parts look slow. The concern did not change; the preference became a constraint, and the day a constraint can fail is the day the sketch has to graduate. That is the same motion the Part's ladder describes from the other side: you climb a rung when a recurring engineering question makes the next capability worth its cost.

Each model here is deliberately lightweight relative to the analytic tradition behind it. When a goal hardens past what the light version can express, an established tool is already waiting. One scaling move underlies all of this. The models tier — system, subsystem, component, module, implementation — and a finite reasoner enters at the level its task needs, descending only as far as the work forces. Every tool this chapter points to keeps some model honest against some territory at the coarsest grain the task allows. Model at the coarsest level that answers the engineering question; descend toward implementation only when the question requires it.

2.8.9 The Handoff to Alignment

Can Alignment exist without explicit models? Yes. A sandbox can forbid network access. A compiler can reject an illegal construct. A test can block a regression against observed behavior. A reviewer can adjudicate a system-level obligation no tool can currently express. These are real forms of authority, and useful systems can be built around them.

Their limit is what the environment can state and observe without reconstructing additional semantics. Local controls work well on local facts; richer engineering questions — architecture, ownership, lifecycle, end-to-end policy — often require a representation at the level where the property exists. Without it, an agent or a human fills the semantic gap each time.

That is the claim this Part has earned. Models change the scale of the questions we can reason about and the properties we can make explicit. As representation becomes richer, more engineering judgment becomes eligible for analysis and deterministic enforcement; what remains outside the representation remains probabilistic, human, or both.

Part II therefore ends where Part III begins. The models are not waiting to become "real" through enforcement; they already pay in reasoning, prediction, composition, and traceability. Part III asks the separate question of authority: which obligations should the environment hold, by which mechanisms, and with what evidence.
