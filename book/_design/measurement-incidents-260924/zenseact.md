# Zenseact — measurement & incidents lens

Source: `book/_design/evidence-factory-cases-260923/zenseact/README.md`. One substantive source; agents do knowledge work, not software realization [C5]. This sheet is short because the record is.

## 1. What Zenseact reports measuring

- **One number in the entire record**: context savings of 67–98% (financial queries) and 43–97% (engineering queries) from two-level skill disclosure [E18]. It measures the **router**, not the platform's effect on anyone's work; method, sample, and baseline unstated [GAPS 7]. Category: factory/process (context effectiveness).
- A per-turn "quality score" exists in the execution flow [E19] — mechanism named; scorer, scale, use, and consequence all unstated [GAPS 8]. Mechanism ≠ metric.
- **Skill disclosure misses** are logged, dashboarded, and fed to an "automated skill improvement pipeline," with a typed three-row failure taxonomy each carrying a prescribed remedy [E25][E26]. This is a real measurement-driven loop — but it repairs retrieval *fit*, not answer correctness, and nothing verifies the loop has improved anything [GAPS 15].
- Production/productivity: **not reported** — no agent count, adoption, users, sessions, time saved, or cost [E31].
- Product/quality: **not reported** — no evaluation suite, benchmark, or golden answers; nothing tests whether an answer is right [GAPS 9]. For a platform feeding executive scorecards, the evidence file calls this the largest single hole.
- Human/organizational: **not reported.**

## 2. Incidents

- **None reported.** No incident, wrong-answer account, correction path, or rollback appears anywhere [GAPS 10].
- The nearest failure-to-structure items: (a) the **founding failure** — the prior open-source-framework approach "did not scale" and "measurable outcomes were lacking," which motivated the platform rebuild [E3] — an organizational lesson converted into architecture, stated by the authors; (b) the disclosure-miss taxonomy above, which converts routing failures into typed, resolved findings [E26].

## 3. Model-critique note

Zenseact's distinctive measured-and-managed concern is **federated ownership** — who builds and owns agents, with the platform team off every domain's critical path [E28][C16] — an organizational-structure axis the factory model's authority/process vocabulary touches only obliquely. Single case; and note the case is not a software factory at all, so its vote on the software-factory model is limited.

The safety-critical machinery (SPARK proofs in CI, ASIL-D requirement-to-contract checks [E32][E33]) is documented only in an undated vendor case study with **no stated connection to agents** [E36]; no measurement crosses between the two halves of the record.
