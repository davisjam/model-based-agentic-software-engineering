5.3 The Road to MAGE

This chapter illustrates

✓ The Modeling Thesis · ✓ The Alignment Thesis · ✓ The Governed Engineering Environment · ✓ Governance Conversion

The last chapter told what the build cost. This one tells what it produced, and then how the method was forced out of it. Two halves. First, the system that ultimately shipped — enough of it that the destination is clear. Then the staircase: the order in which the pieces of MAGE appeared, each one demanded by a load the piece before it could no longer carry.

5.3.1 What ultimately got built

A user uploads a file. The system figures out what kind of document it is, breaks it into work, remediates each piece, checks the result against a real accessibility standard, stamps what it changed, and returns the corrected file with evidence that the job was done. Six responsibilities carry that load, and Figure 5.3-1 draws the whole path.

  • A front door takes the upload, authenticates the user, meters usage against a quota, and puts the job on a queue.
  • A dispatcher splits the document into chunks — slides, pages, sheets — so a hundred-slide deck finishes in about a minute instead of an hour.
  • A remediation core does the repair. A typed command-line engine walks the document through a structured model of its format and, for each thing that needs fixing, applies a deterministic rule or asks a model.
  • A check engine maps each remaining finding to a specific clause of the accessibility standard, so the system carries its own conformance vocabulary instead of outsourcing every verdict.
  • A fidelity validator catches the file that came out more accessible and less true.
  • A provenance layer stamps every insertion, giving the document the auditable trust a university requires.

Those six responsibilities are the product. What surrounds them is larger. The support apparatus — tests, lints, models, load-bearing documentation — runs about 3.0 times the size of the production code. Call that inversion gold-plating if you like, but the more code the fleet produces, the smaller the fraction any human reads, and at this volume no one reads the diffs at all. The apparatus performs the repeatable checks that direct review cannot scale to provide. Its growth is drawn in the Build chapter; here it is enough to say the environment around the product outweighs the product.

5.3.2 The LLM as a function call

A foundation model is a probabilistic component. Ask it the same question twice and you may get two answers. Ask it something slightly outside its training and it answers anyway, confidently, wrong. And yet it is the only component in the system that can look at an arbitrary figure and describe it. You have to build a reliable system out of an unreliable part.

The pattern that makes this work treats the model as a typed function call. Deterministic code owns the workflow and decides when a step needs judgment rather than a rule. Only then does it reach for the model. It packs a bounded task into a typed input — this figure, this context, this question — and the model must answer in a typed output shape. A deterministic validator sits at the trust boundary: the model's answer is a candidate, not a result, and code checks it against the standard and the input's meaning before it is allowed in. The workflow is deterministic. The model is a subroutine inside it. The subroutine is never trusted on its word. The shape is old — proof engineering separates the untrusted work of writing a proof from the trusted kernel that checks it; the kernel, not the author's confidence, decides what is admitted 11. Talia Ringer et al., “QED at Large: A Survey of Engineering of Formally Verified Software,” Foundations and Trends in Programming Languages 5, nos. 2–3 (2019): 102–281, https://arxiv.org/abs/2003.06458.. MAGE's move is to compose that one boundary across a whole production line. Figure 5.3-2 draws the caller, the typed contract, and the validator.

Now zoom out one level. The coding agents that built DocAble are the same kind of component: powerful, probabilistic, capable of a confident wrong turn. The methods in the earlier chapters are this same pattern applied to them — bound the task, type the interface, validate before you trust. You have seen the move in the small, on a vision model writing alt text; the rest of the book is the move in the large.

5.3.3 Three places the same idea surfaced

The system carries that discipline in more than one place. Three are worth a half-page each, not as new principles but as the same one materializing.

The reactive seam. The back end is small services wired to react to events: an upload is split into chunks, a queue hands each chunk to a stateless worker, the worker publishes a completion, a fan-in step assembles the file. The split of duties is declared — transient coordination in one store, authoritative truth in another. For most of the system's life those workers polled size-stratified queues under a custom autoscaler on a cluster that billed around the clock, the wrong cost shape for a bursty product. A serverless push plane replaced it, and the business logic did not change: a reactive, input-triggered handler already is the serverless execution model, and no durable state lived in a worker for the recycle to lose. Prior structural discipline made the migration a change of deployment target rather than a rewrite. Figure 5.3-3 draws both carriers.

The closed edit language. The editor never edits the document. A user gesture — change this alt text, reorder these elements — becomes one typed edit operation drawn from a small, closed vocabulary, and the document model is the only thing that touches the document. A typed operation can be validated before it applies, stamped as it applies, and refused when it breaks a constraint; a closed vocabulary can be kept closed by a lint. That is what turns an edit surface into a governance boundary — and it is why the same seam carries the pipeline's output. When automated remediation decides a figure needs alt text, it emits the very set-alt-text a human would. One document model, one edit language, two producers. A language built so a human could edit safely turned out to be a language a pipeline could target for free. Figure 5.3-4 draws both producers into it.

The function call, once more. The mapping from a remediation task to an edit operation is itself a function: task in, operation out, with a bounded model call inside and a validator at the exit. The edit language is the typed output contract. The frontier models could skip all of this and remediate a slide deck directly. But direct remediation buys neither thing a university needs. You cannot audit what a direct edit changed, and you cannot trust that the standard was met and the meaning survived. Routing every change through one validated, stamped operation buys both.

These are not three more MAGE principles. They are three places where the same principle materialized: represent the important boundary explicitly, then put the authority on it. A local decision made for its own reason keeps banking that option — the reactive seam banked serverless, the edit language banked a second producer — but the recurring shape, not the dividends, is the point.

5.3.4 The staircase

MAGE was never designed on a whiteboard. It accreted. Every model, every control arrived the same way: the codebase grew, the quality bar rose, the current system proved inadequate, and the next thing was demanded. Read what follows as a staircase, and watch the job title climb — co-coder, QA, review lead, tech lead, architect. Each rung names the center of gravity of my work, not a title I held. Each is a job the rung below could no longer do. And each was safe to climb only because the step under it first minted a control that caught what the delegation would otherwise have dropped.

Why the job title climbs

The ladder rests on one hinge: governance. Every rung is a successive delegation. I hand the fleet a piece of the tactics — write this code, audit that diff, run this zone — and keep the strategy. That handoff is safe only because a control catches what the delegation drops: a lint reddens on the boundary I stopped watching, a gate refuses the commit I stopped reading, a model means I no longer hold the map in my head. Delegation climbs exactly as far as the controls will carry it, and no farther. Get the governance wrong and the ladder runs in reverse: the misses surface days later in some downstream gate, and I am pulled back down into the tactics to firefight, reading diffs again with no one minding the strategy.

Co-coder — I reviewed every line. One format, a few hundred lines, and me. When the agent proposed a change I read the diff, judged it, merged it. The whole quality mechanism was one human reviewer, and it worked because the volume was small enough that one person could hold it in his head. That gate does not scale. Agents write code far faster than a human can read it, and the more they wrote the further behind I fell. The bottleneck was me.

QA — I dispatched an agent to audit the work. The first offload was to hand the review itself to a second agent that read the first one's diff and reported what it found. The checking left my hands. But an audit is the weakest kind of control: it runs when I remember to run it, over code that has already drifted, and it makes enforcement durable only after the fact. That planted the question that drove everything downstream: which of these findings could become a lint — cheap, deterministic, run at commit time — so I never have to look for that class again?

Review lead — one audit became a crew. A single generalist reviewer over a large codebase is a firehose with no aim: it never comes back empty, it cannot rank a cosmetic nit against an architectural break, and it applies a PDF rule to the web layer. So I split the one reviewer into specialists, each with a narrow charter — a duplication audit, an architecture audit, a naming audit, a security audit — and ran each per architectural region. A finding now carried two coordinates: which kind of concern and which part of the system. Then the cheaper move: much of what an audit checks is deterministic. "Does any file outside the PDF region import the PDF library?" needs a lint, not a language model. So every decidable finding moved down to a lint, and the crew retreated to the judgment a lint cannot make. This is the first plain governance-conversion move — today's audit finding is tomorrow's lint.

Tech lead — named zones, so an agent can reason locally. A crew is still a crew of agents, and here the agent's nature bites. A cold-start agent with a finite context window cannot reach the tacit knowledge a human team keeps in its head: which file is canonical, which of two look-alikes is live. Think of it as a contractor with no memory of yesterday; it has to be told, in the code, every time. So I partitioned the system into named zones — a queryable statement of what the parts are and where their boundaries lie. Hand an agent one zone and it reasons inside it, fenced by a boundary lint that refuses an edit reaching across a zone it has no business touching. Each zone declares the powerful library it alone may reach, and a lint reads that declaration and reddens on any file outside the zone that imports the library directly — the "one structured model per format" rule enforced by a machine walking a declaration rather than by my vigilance. This was the first model I wrote for the fleet to read rather than a piece of the product.

Architect — the codebase modeled. {#refactor-cost} By this rung I looked at code almost never. What changed is that I stopped holding the system in my head and committed it to explicit models the fleet reasons through. The zone descriptions became a typed registry the tools query at runtime — not documentation about the architecture but the architecture in a form a tool can read. Adding a single typed field to it, naming which zones may cross an external boundary, replaced four hand-maintained allowlists that were quietly drifting and unlocked three lints all reading that one field; on its first run the new boundary lint surfaced a backlog of latent violations no one had had a way to ask about. The refactoring got cheaper because the models told me where to look and where to stop: a cross-format migration that touched fifty-eight files and rewrote five thousand lines took about five hours of agent time over a dinner break. When the mechanical cost of restructuring collapses, the economics invert — postponing the right shape becomes the expensive choice. The hard part was never touching fifty-eight files; it was knowing that fifty-eight files should be touched.

Field note — the map that pointed at a ghost. A stack of models has its own failure mode: drift. One model named a code symbol; the symbol was later renamed and moved; nothing noticed. The model still looked authoritative while pointing at a ghost, the fleet read the ghost as truth, and the blow-up landed days later in a deploy step instead of at the change that caused it. That incident is what forced the models to grow a nervous system — a traceability substrate whose every edge re-resolves against a live symbol, so a broken reference reddens at the change that broke it. Part II carries the mechanism in full; here it is enough that the drift was real and the substrate was its answer.

The models were not bookkeeping. Turning the system's unmodeled regions into explicit models surfaced real, shipping bugs the green tests had missed — the payoff that proves the modeling was not decorative.

What modeling found that green tests missed. Three live defects, each forced into view by the act of modeling a seam:

  • A cross-runtime exit code one runtime emitted and the other had never enumerated, so a genuine failure was silently misfiled as a generic error.
  • Incomplete cleanup on redelivery — a failure path purged a job's database rows and blobs but skipped the queue structures its sibling path always cleaned, leaking chunks on a rare edge.
  • A last-write-wins editor race in which two concurrent saves silently discarded one's work.

None was a hypothetical the model raised. Each was a live defect the modeling exposed.

Those defects came out of a discipline that turns the brownfield problem inward: instead of modeling only what I happened to notice, an instrument walks the tests that reach no model and names the regions still unmodeled. That instrument — how it measures modeling completeness and drives a loop that closes the gaps it finds — belongs to the Brownfield chapter; what matters here is that the method eventually turned its own instruments back on the parts of itself it had not yet named. Figure 5.3-5 draws the five-rung climb.

5.3.5 Delegation climbed as far as the controls carried it

The method that began with a human reading every line arrived at a system that models its own structure and dispatches work to close the gaps it finds. Nothing on the climb was planned. Each rung was demanded by a load the rung below could no longer carry, and each was safe to climb only because a control first caught what the delegation dropped. Delegation climbed exactly as far as the controls could carry it. The governed engineering environment is the accumulated structure that made successive delegation safe — the models, the controls, and the query surface grown until the apparatus outweighed the product it guards.

This book opened on one diagram — The MAGE Method at a Glance — that named every part before the argument had earned it. Each box is now a real thing in a system that ships: the fleet that prints code faster than anyone reads it, the explicit models it reasons through, every probabilistic part sealed in a bounded and validated call, and the controls minted one failure at a time. The case study was the evidence; whether the method transfers is the question Part 6 takes up.
