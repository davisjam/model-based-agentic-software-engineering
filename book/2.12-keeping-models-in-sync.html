Part 2 — Modeling  ::  Chapter 18

2.12 Keeping the Models in Sync — A Measurement

2.12.1 The question: the map must equal the territory, or the bridge lies

This chapter reaches the top of the Part's ascent. Drift enforcement — rung eight — is where a model stops merely helping the fleet reason and the environment begins refusing to let the model and the code silently disagree. Everything the rung promises rests on one requirement.

A context-bounded fleet governs a context-exceeding codebase through structured models. The models are the bridge the agents reason across. So the map must stay equal to the territory — equal over the relations the model claims to represent, not over every line of code. Stated precisely: the model must remain consistent with the territory over its declared surface. If a model claims something the code no longer does, every agent that trusts the model inherits the lie.

The models-bridge. The governed channel between the code and the authored models: the traceability edges that connect model elements to the code they represent, plus the drift checks that hold the two in agreement — the path by which authored models reach the agent's task context and its checks, and the relationship the agent reasons across.

"Keep the model in sync with the code, automatically" is the thesis question. It has a cheap-sounding answer and an expensive-sounding one, and the honest result is that neither alone is enough.

2.12.2 The mechanism: a two-layer net, and freshness by derivation

Sync holds through two layers stacked over the model↔code gap.

  • The soft layer — the reading pass. A definition-of-done review reads the model's prose surface against the code: a frozen status header, a phase index missing a landed phase, a stale count in a sentence. A human or an Opus catches these because they live in prose. This layer aims; it cannot block, and it is fallible.
  • The hard layer — the derived floor. A reconciliation lint resolves each model anchor against a live symbol in the code. The anchor points at a function or class definition a static resolver can find, not at a line number and not at a snapshotted copy. Reading the anchor resolves current code, not a stored copy. The relation is recomputed from live code rather than copied from a prior scan, which eliminates one class of temporal staleness — the drift a snapshot accrues between the scan that recorded it and the run that reads it. (A live resolver still depends on the anchor, the parser, the build, and the model's completeness; it removes the snapshot failure, not every failure.)

The property that does the work is freshness by derivation, not by process. A snapshot-plus-sync process can drift between runs; a resolver over live code cannot. Derived defends, snapshotted drifts. Anchor to a symbol, not a line — and where there is no clean symbol to anchor to, that absence is itself a signal that the model is missing a point of abstraction (a refactoring target, not a gap to paper over).

Worked Examples

DocAble. DocAble closes the gate the rest of the corpus leaves open. Its models are bound to the code by a derived drift check: each model anchor resolves to a live symbol at build time, and the build fails the moment a model and the code it claims diverge over a checked relation. Nothing external in the study reaches this rung — a blocking parity gate over the very territory the agents rewrite — which is why it is the DocAble-unique move, and one software implementation of it.

Siemens. Siemens is the instructive near-miss. Its digital thread synchronizes models across domains and propagates a design change downstream into fresh analysis, which is real and rich. But it synchronizes and propagates; it does not block divergence. The model-first company reaches every modeling rung except this one — evidence that a blocking drift gate is a distinct capability, not a free consequence of taking models seriously.

Takeaway. The discipline measured here is binding the model to the territory: not merely keeping a model and its code in step, but refusing the build when they disagree. It is the one rung even a decades-deep model estate need not have, and the one this whole measurement is about.

2.12.3 The model grows with the system: two worked examples

Sync is a living practice, not a one-time alignment. The territory grows; the model is edited to match; a derived gate fails the build if it is not. Two real cases from the study period show the loop.

Adding a service endpoint (2026-08-01). The "pictures-not-pages" PDF pilot added a new editor endpoint, GET /api/pdf-page-image/{job_id}/{page} — the PDF analogue of the existing slide-image and docx-page-image endpoints. The service-flow model (the Backstage-dialect Component/API catalogue under system-models/services/) had to gain that endpoint or the generated catalogue would no longer match the source. The commit that landed it (6fd0b6d51a) says so in its own words: the endpoint "was added to the editor cluster YAML but the generated Backstage entity was not regenerated," which "Restores gen-web-api-entities --check to green." The added model fragment names the new endpoint and its responses — /api/pdf-page-image/{job_id}/{page}: get: { summary: "…the PDF analogue of /api/slide-image", 200: PNG, 400 / 404 / 502 }.

A new service or endpoint is, by construction, either a model edit or a parity failure. The service-flow parity gate (gen-web-api-entities --check, backed by the service-flow-model and service-call-graph drift lints) would have failed the build had the model not been edited to match.

Adding user journeys (2026-07-16; the model kept growing through the drift window). The user-journey model gained three Journey entities — batch-remediate, editor-edit, editor-edit-remediate — authored in commit 01699c8c47, which in the same change extended the service-flow lint to admit the Journey kind. A Journey names an actor, a goal, and ordered steps, and each step names the service endpoints it calls. The batch-remediate Journey names an actor (uploader), a goal (end-to-end remediation), and ordered steps whose calls: lists the endpoints each step hits — step 1 the chunk-decision capacity/convert calls, step 2 the per-chunk C# GenAI/OCR/font calls, step 3 the render + conformance + quality validation calls.

The two-way call-site drift lint (lint-journey-endpoint-coverage.py / lint-journey-service-drift.py) holds each journey's declared endpoints to the real internal_service_client(...) call sites, in both directions — a journey that names an endpoint no code calls, or code that calls an endpoint no journey declares, fails. The model kept growing in the drift window too: the same journey model gained a typed MAJOR/MINOR criticality tier and a JourneyClosure join-key substrate (late July), each with its own derived check.

Honesty note: the three Journey entities were authored 2026-07-16 — inside the broader study period, before the 07-22 start of the drift-audit corpus. No brand-new Journey entity landed in the 07-28→08-04 refresh window; the journey model's growth there was the criticality-tier and closure-key expansion. The service-endpoint example (08-01) is squarely in-window.

2.12.5 The two failure modes: where drift still escapes

The net has two escape hatches. Neither is a footnote; they bound the claim.

Failure mode 1 — the judgment miss. A mis-alignment that is not mechanically decidable needs subjective judgment. The anchor resolves (the code exists, so the hard floor reads green), yet the meaning drifted. The soft reading layer is the only net for this, and it is fallible by construction — a subtle semantic drift can pass a green definition-of-done. This is the drift that slips through a hole in the soft layer.

Failure mode 2 — the unmodeled. The unmodeled is the Modeling-Thesis form of the residual the Alignment part will name: a fact or relation that should be modeled but is not, so it has no anchor and no drift-check can fire over it. You cannot detect drift of a thing you never modeled. Here the net has no coverage at all — not a hole in a layer, but a region with no layer. When there is no clean symbol to anchor to, that absence is the signal: it names a missing point of abstraction, a refactoring target.

Both failure modes lean, by default, on an engineer or an agent noticing. The book has two mechanisms that convert that noticing into machinery — the right in-book targets to cross-link:

  • The missing-model metric (the orphan-coverage tracer) measures failure mode 2. It walks the code and asks, for each governance-relevant site, whether any model row or control node reaches it, then scores the remainder — the sites nothing models — as a rate and clusters them, so each cluster becomes a candidate for a new model. It turns "the estate's blind spot" into a queryable map instead of a thing you learn about when it bites. (A sibling metamodel, the control-coverage census, rolls controls up per control-target and flags an under-governed target — a distinct axis, not a measure of the unmodeled; do not read one for the other.) ** A note on metamodels. An object model maps the code — service-flow, journeys, state machines — and its drift-check asks "does this model still match the code?" A metamodel instead checks the completeness of the model set over the territory: "is the right thing modeled at all?" The missing-model metric is the metamodel for failure mode 2 — it converts "an engineer happens to notice something isn't modeled" into a measured coverage gap. The control-coverage census is a different metamodel: it asks whether each control-target is governed, not whether each system fact is modeled. Same genre, different question — keep them apart.
  • Self-governance — convert failures to controls (the governance-conversion / "failures become machinery" loop; the reflection-facet substrate that extends the governance graph, and chapter 2.6's treatment) converts a recurring gap into a new model or control. Where the census measures the gap, this closes it: the unmodeled fact becomes a modeled one, and the net gains a segment it did not have.

2.12.6 The honest reading

The result is narrow, and stating its limits is part of stating it. Four readings bound what this measurement does and does not show.

  • Preliminary, small N. Per window, the count of genuine model↔code drifts is small — a handful, not a headline. The model-sync claim rests on that small set of genuine model drifts the derived floor caught, plus zero model-drift reopens under heavy churn — not on any headline catch-rate, which would mix doc-legible catches with modeled ones and rest on a denominator too small for the model-sync slice. This is a field-report result, not a proof.
  • The catch-rate rose by composition, not by loosening. The refresh window caught more drift (17 of 20 closes vs. the original's 6 of 36) because it moved more territory — product-heavy Epics with more doc surface — exactly where the reading layer is the only practical control. The net did not get weaker; there was more for it to catch.
  • The claim is narrow and it is about sync, not hygiene. The three legs: the drift is real and used to escape (the ~27 pre-floor findings); the mechanism is derived reconciliation, not snapshot-and-sync (freshness by derivation); and it held under load (the churn row, with zero model-drift reopens). The doc-hygiene aside is kept separate on purpose.
  • The two failure modes are the boundary of the claim. Sync is enforced for the modeled and mechanically-decidable; it is aimed for the semantic; and it is absent for the unmodeled until a metamodel or a self-governance reflex extends the net. That boundary is the honest shape of the result.

Step back from sync to the whole Part. Every model walked here sits on one capability ladder, and the ladder is the Part's real claim: richer representation does not merely make the same intent more legible — higher up, it lets the environment enforce more of what the model says. Figure 2.2-1 climbs it from selecting the right context, through structured knowledge and executable models, to the drift enforcement this chapter builds.

2.12.7 Can alignment exist without models?

One question sits under everything this Part has built, and it is worth answering before the next Part takes these models up as authority: can alignment exist without models at all?

Yes. Natural-language prompts, briefs, examples, and supervision guide agents successfully, sometimes spectacularly. MAGE does not claim otherwise. A prompt is a representation too, only a weak one: implicit, local, untyped, mostly opaque to tools, and hard to compose, validate, or keep true as the system moves. It can steer a build. It cannot, on its own, state, compose, validate, and enforce the obligations engineering assurance rests on.

So the claim is narrow, and worth stating exactly. Implicit or weakly structured representations support correspondingly weak forms of authority. Explicit models are not a prerequisite for useful software; they are the substrate on which progressively stronger guarantees become possible. Without explicit models, alignment cannot become authoritative.

Read the whole argument as one line.

Natural-language intent can guide autonomous work. Explicit models transform that intent into an engineering substrate. Alignment transforms that substrate into authority.

That honest reading closes the zoo. This Part walked each kind of model on real code and showed the drift gate that holds each one to the code, so the map cannot quietly rot away from the territory. What it has not shown is how you reach that state from a codebase that carries none of it. The models are built; the next Part gives them authority.
