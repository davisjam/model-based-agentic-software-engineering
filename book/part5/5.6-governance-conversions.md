# Failures

The system's dead-ends and silent losses are evidence too. The method's third beat — convert
recurring failures into engineering capital — is a claim, and this chapter is where you watch it
run at the source. DocAble is where the loop was first turned, so its failures are where a
recurring failure first became a wall.

Each one below is retold once, in full: the failure, then the mechanism it forced into being,
then the capital that mechanism banked. Read them as the raw material of governance conversion —
the place the aphorisms in the lessons chapter were paid for.

## The instruction satisfied to the letter

<!-- point: an-instruction-satisfied-to-the-letter-and-voided-in-spirit | An under-specified instruction is satisfied to the letter and voided in spirit. | terms: stringly-typed, explicitness-is-essential -->
By April the system was 300,000 lines that worked but were janky — a Rube Goldberg machine,
because it had started as an MVP built only to prove the thing was possible at all. I had imposed
real architecture on the parts I knew were sensitive; the rest — the web layer, the front end — I
hoped the agent would get right, and they turned crufty. So I told it to use typed Python. It did,
in a sense: it used the type `string` for everything. Stringly-typed — the word "type" satisfied
to the letter and voided in spirit, no safety the compiler could give. Told to retrofit real
types, it turned on the checker and made everything strings and ints, without building the
abstractions I actually wanted. The same thing happened porting JavaScript to TypeScript that
week: each ported the cheapest way, because the agent had no model and did not know the names of
things.

The failure is not laziness. It is the shape of an under-specified instruction met by a system
that optimizes for the next green checkmark. "Use types" names a checkbox, not the abstractions,
and the agent found the reading that turned the check green with the least work.

<!-- point: the-fix-was-a-typed-model-per-dense-region-and-lints-to-blocking | The fix: a structured model per dense region, every commodity lint driven to blocking. | terms: audits-into-lints, make-lint-blocking, dense-primitive-region -->
The fix was the recipe the method chapters describe, run on my own codebase. I turned on every
lint from Ruff, Pylint, and ESLint — hundreds of commodity smell checks — and burned weeks
squashing them, making each blocking as it hit zero so it could never come back. Then I worked
region by region: find the dense primitive regions — the stretches doing many low-level operations
by hand, raw calls and untyped strings and ints passed around with no abstraction that owns them —
and induce a structured model that owns each one, rewriting the region to route through it. Each
lint driven to zero was one primitive smell given a name and a home; the coarse
model-view-controller decomposition was the same move at the coarse grain.

<!-- point: structure-is-compression-and-the-models-now-shape-every-task | Structure is compression; the models now shape every later task. | terms: governance-conversion, brownfield-migration -->
A month later I had 200,000 lines that were not janky. The system got smaller as it got better —
structure is compression, and the primitive sprawl had been the bloat. The project's measured
churn corroborates the shape: the add-and-delete peaked exactly during this work, then the
deletions collapsed and later windows went net-additive — the signature of a one-time replacement,
not steady thrashing. [data: churn] In MAGE terms, that month was governance conversion at
brownfield scale. The recurring failures and the same rediscoveries, over and over, became the
models, links, lints, and gates that now shape every later task. The capital was not the 200,000
lines. It was the enforcement that holds the models, the architecture, and the code together every
time the code changes.

## The architecture was the constraint

<!-- point: optimizing-within-an-architecture-that-was-itself-the-constraint | I optimized within an architecture that was itself the constraint. | terms: velocity-exposes-the-danger -->
The service was costing thirty to forty dollars a day to run idle on a Kubernetes cluster. So I
set the agents on a scale-to-zero push: keep the cluster, keep the custom autoscaler, and squeeze
the idle pods down to nothing. For weeks they made it better and better — and it never paid off,
because scaling a cold pod back up took sixty to three hundred seconds, and a five-minute cold
start is a worse problem than the bill. I was optimizing *within* the architecture when the
architecture itself was the constraint. The real move was to change it: go serverless, and let the
platform own the scaling I had been hand-building against its own ceiling.

<!-- point: a-recurring-wall-is-the-signal-to-price-a-paradigm-change | A fix that keeps hitting the same wall is the signal to price a paradigm change. | terms: velocity-exposes-the-danger -->
Coding agents accelerate within the frame you give them, even when the frame is wrong, so a wrong
frame gets very good very fast. This one had a tell, visible only in hindsight: the optimization
kept colliding with the *same* wall. When an in-paradigm fix keeps hitting the paradigm's own
limit, that recurring wall is the mechanism the failure hands you — not a lint, but a decision
rule. Price out the paradigm change instead of buying another round of in-frame optimization.

<!-- point: some-conversions-produce-judgment-not-machinery | Some conversions bank judgment, not machinery. | terms: governance-conversion -->
The capital here is not a wall the environment enforces; some conversions produce judgment, not
machinery. What those weeks bought was a cheap detector for a wrong frame: a fix that recurs
against the same ceiling is evidence about the ceiling, not the fix. It is the same signal, one
level up, as the second occurrence of a failure earning its lint — the recurrence is the
information.

## The decision left open

<!-- point: an-unmade-decision-is-where-the-agent-guesses-worst | The unmade decision is where the agent guesses worst. | terms: optionality-is-poison -->
My merge-train cron kept stalling when two agents edited the same file, and it proposed a one-flag
fix: tell the merge to just take one side and drop the other on any conflict. I signed off without
asking what "drop the other side" meant. For four days it silently deleted real work from the main
branch every time two changes overlapped — the same commit heading landing again and again, each
time a little smaller — while I chased the symptoms one missing function at a time.

The failure was not the flag. It was the decision I left open. The agent filled it with the
cheapest thing that made the error go away, because an open choice at the point of execution
becomes a choice someone has to make now, and the agent makes it to unblock itself, with the
consequences nowhere in its objective.

<!-- point: decide-conflict-handling-up-front-name-the-resolver | Decide conflict handling up front; name the resolver. | terms: optionality-is-poison, explicitness-is-essential -->
The right answer was a merge resolver that understood the files it was merging, and I could have
decided that up front. The mechanism the failure earned is the discipline of naming the
consequential dimensions before execution — the architecture, the types, and, precisely here, what
happens on a conflict — and delegating only the rest. The narrower the agent's search, the more of
its speed lands on the target instead of scattering.

<!-- point: the-capital-was-a-conflict-policy-the-environment-now-carries | The capital was a conflict policy the environment now carries. | terms: governance-conversion, judgment-into-infrastructure -->
What the four days bought was a standing rule: no destructive default on a conflict, and a
resolver that reads the files instead of picking a side. The decision, made once and encoded, is
one no later agent has to re-guess at midnight. That is the move the whole method turns on —
convert the judgment into infrastructure so the call is made once and held.

## "Done" was a claim

<!-- point: two-green-reports-that-were-not-true | Two green reports, neither of them true. | terms: done-is-a-claim -->
Two incidents, close together, made "done is a claim" non-negotiable. Once, a lint gate hit a
stray error, caught it in a catch-all that returned success, and let a run of commits land
completely unlinted while the log said fine. Another time a chain of pin tests passed green — but a
botched merge had landed them onto a tree that was missing the very field they were supposed to
check, so they confirmed a field that existed and never touched the one that mattered. Both
reported done. Neither was.

These are agent-shaped failures: a report of "done" describes the agent's intent, not the state of
the repository, and the gap between the two is exactly where a confident green hides.

<!-- point: the-mechanism-was-a-gate-the-agent-cannot-talk-past | The mechanism: a gate the agent cannot talk its way past. | terms: done-is-a-claim, audits-into-lints -->
The mechanism both failures earned is verification the agent cannot author: re-run the tests
yourself, re-run the lints the work was supposed to satisfy, compare the counts against the claim.
The catch-all taught a sharper rule — a gate that swallows its own error is worse than no gate,
because it reports success it did not earn, so a control must fail loud and never silent-catch. The
pin tests taught that a check is only as trustworthy as the tree it ran against.

<!-- point: the-capital-was-a-control-system-around-the-work | The capital was a control system around the work, not more code. | terms: governance-conversion, judgment-into-infrastructure -->
Out of these, my job changed shape. It shifted from writing implementation to running the control
system around it — decomposing work, cross-checking invariants, hardening tests, re-running the
gates against the real tree, and deciding whether the architecture was genuinely cleaner or merely
different. The capital is that control system: the standing habit and machinery that treat every
"done" as the start of verification, not the end.

## A content-free detector, measured on the wrong world {#fieldnote-content-free-detector}

<!-- point: a-detector-that-measured-the-right-quantity-on-the-wrong-world | A detector measured the right quantity on the wrong world. | terms: tests-for-agent-failure-modes -->
Late in the same stretch, an agent wrote me a content-free detector: if an image's pixels barely
vary, skip the vision model and mark it decorative. Clean, typed, careful. Its own comment
promised a false positive was "not possible" — real photos and charts vary twenty times more than
the cutoff, so nothing real could slip under. The margin was true. It was also measured on the
wrong world. Hand it a Rothko, or Malevich's black square, and the pixels barely vary; the detector
marks the painting decorative and drops it, and a blind student reading an art book gets silence
where the subject should be. No threshold saves you, because a blank spacer and a Malevich are
identical in the one quantity the code looked at. "Content-free" was never a fact about pixels. It
is a fact about an image in a context of use, and the use here is teaching, and teaching includes
the one tradition built to prove that a picture need not vary. The confident "not possible" was the
tell: it marks the spot where the model's picture of its own inputs was too small.

<!-- point: when-the-cheap-proxy-is-unsure-describe-anyway | When the cheap proxy is unsure, describe anyway. | terms: tests-for-agent-failure-modes -->
The mechanism is a rule about proxies: when the cheap proxy is unsure, describe the image anyway. A
content-free detector that has never seen a Rothko will tell you a Rothko is nothing, so the
detector does not get the last word — it defers to the fuller model at the margin. And the test
that guards it is built for the agent's failure mode, not a human's: pin the class — the picture
that varies little but carries everything — rather than the example, so the next confident,
coherent, subtly-wrong subsystem meets a sensor instead of a checkbox.
