# The Road to MAGE

> ### This chapter illustrates {#illustrates}
>
> ✓ The Modeling Thesis · ✓ The Alignment Thesis · ✓ The Governed Engineering Environment · ✓ Governance Conversion

<!-- point: built-system-joins-two-halves | The engineering joins probabilistic models to deterministic code. | terms: vision-language-model -->
The timeline told what happened; this chapter tells what got built. DocAble is one
real system, live in beta, and the governance the book has already laid out lands harder
against a system that realizes it. Frontier models do the parts that require understanding
a slide; ordinary deterministic code does everything else. The interesting engineering
lives in how those two halves are joined.

## What the system does, end to end

<!-- section-terms: governance-target-product, thesis-modeling -->

<!-- point: system-remediates-end-to-end | One upload flows through six parts to a stamped result. | terms: governance-target-product -->
A user uploads a file. The system figures out what kind of document it is, breaks it into
work, remediates each piece, checks the result against a real accessibility standard,
stamps what it changed, and returns the corrected file with evidence that the job was done.
Six responsibilities carry that load.

- **A front door.** A website and an API take the upload, authenticate the user, meter the usage against a quota, and put the job on a queue. A professor drops in a slide deck; the system takes it from there.
- **A dispatcher.** The document is split into chunks — slides, pages, sheets — and each chunk becomes a unit of work handed to a worker. Splitting is what lets a hundred-slide deck finish in about a minute instead of an hour.
- **A remediation core.** A command-line engine, written in a typed language, does the actual repair. It walks the document through a structured model of its format, and for each thing that needs fixing it either applies a deterministic rule or asks a model. This is where alt text gets written, reading order gets set, titles get added, contrast gets fixed.
- **A check engine.** After every pass, a standards-grounded checker maps each remaining finding to a specific clause of the accessibility standard, so the system carries an internal, standards-grounded conformance vocabulary rather than outsourcing every verdict to an outside checker.

> Learn more about this governance mechanism: [standards-grounded check engine](appendix-c-standards-rule-engine.html).

<!-- index-def: fidelity-validator -->
- **A fidelity validator.** The [fidelity validator](1.2-mage-by-example.html) introduced earlier sits here, catching the file that came out more accessible and less true.

> Learn more about this governance mechanism: [fidelity validator](appendix-c-content-validator.html).

<!-- index-def: provenance-layer -->
- **A provenance layer.** The [provenance layer](1.2-mage-by-example.html) from the pipeline stamps every insertion, giving a document the auditable trust a university requires.

> Learn more about this governance mechanism: [per-mutator provenance stamps](appendix-c-mutator-stamps.html).

<!-- point: apparatus-outweighs-and-is-the-review | The support apparatus dwarfs the product and carries repeatable review. | terms: support-ratio -->
Those six responsibilities are the product. What surrounds them is larger. In the talk this book
grew from, I put the code-to-test ratio provocatively: the industry is happy with one line
of tests per line of code, and I had one-to-four. The real recorded figure across the whole
tree is close to that in spirit — the support apparatus, tests and lints and models and
load-bearing documentation together, runs about **{{support_ratio}} times** the size of the
production code. Call that inversion gold-plating if you like — but the more code the fleet
produces, the smaller the fraction of it any human reads, and at this volume no one reads
the diffs at all. The apparatus performs the repeatable checks that direct diff review cannot
scale to provide.

<!-- point: two-commitments-typed-model-and-fail-loud | One structured model per format; the pipeline fails loud. | terms: thesis-modeling -->
Two design commitments run underneath all six. Every format is touched through **one structured
model**, never the raw library, so a fix applied once holds everywhere. And the system
**fails loud**: when the model is unreachable, the pipeline stops rather than quietly
shipping a degraded file.

> Learn more about this governance mechanism: [one structured model per format](appendix-c-pdf-model.html).

## The document is the hard part

<!-- section-terms: vision-language-model, semantic-gap -->

<!-- point: document-is-a-semantic-artifact | A slide is a visual, semantic artifact machines must recover. | terms: semantic-artifact, vision-language-model -->
<!-- point: raw-capability-is-not-a-system | Raw model capability is not a trustworthy system. | terms: semantic-gap, demoable-vs-productizable -->
A slide is not text in a box; it is a visual, semantic artifact — figures, tables, equations,
an order the eye follows. Vision-language models can now recover that meaning from a rendered
slide: read the equation, describe the figure, name what the slide teaches. That capability is
real, and it is not a system. The model understands the slide and nothing about the file format,
the standard, or the cost of being wrong — so paste a deck into a chat model and you get useful
output, never a corrected file you can trust. Turning that flash of capability into something a
university can trust is the engineering the next section gives.

## Designing with a probabilistic component: the LLM as a function call {#llm-as-function-call}

<!-- section-terms: probabilistic-component, llm-as-function-call -->

<!-- point: model-is-a-probabilistic-component | A model is probabilistic; build reliability from an unreliable part. | terms: probabilistic-component -->
A **foundation model** is a probabilistic component. Ask it the same question twice and you
may get two answers. Ask it a question slightly outside what it saw in training and it will
answer anyway, confidently, wrong. Deterministic components admit repeatable, local checks; a
model call requires statistical and contract-based assurance, because identical inputs need
not yield identical outputs. And yet the model call is the only component in this system
capable of general semantic description of an arbitrary figure. You have to build a
reliable system out of an unreliable part.

<!-- point: treat-the-model-as-a-typed-call | Treat the model as a typed function call. | terms: llm-as-function-call, deterministic-vs-judgment-split -->
The pattern that makes this work is to treat the model as a **typed function call**.
Deterministic algorithms control the workflow and define the objective of each step. When
a step needs semantic understanding, the system delegates a *bounded* task to a tool-equipped
model — then a deterministic module validates the returned artifact before it is allowed in.
The workflow is deterministic. The model is a subroutine inside it. The subroutine is never
trusted on its word.

<!-- point: pattern-generalizes-across-domains | The same typed-call pattern holds in software verification. | terms: llm-as-function-call -->

The architecture follows the same untrusted-generator / trusted-checker split used in proof engineering: the checker, not the generator's confidence, decides what is admitted.

> **Where does this trust boundary come from?** The shape is old and rigorous. Proof engineering separates the untrusted work of writing a proof from the trusted kernel that checks it: the kernel, not the author's confidence, decides what is admitted. Ringer and colleagues survey what it takes to make formally verified software scale: proof organization, automation, and maintenance [cite: ringer2019qed]. Recent systems put a language model inside that loop, letting it search for proof structure while a prover returns counterexamples and admits only a closed proof [cite: tu2025agenticverification]. Our own AutoSOUP is one: it verifies component-level memory safety by representing scope, loop bounds, and environment assumptions as explicit unit-proof artifacts, delegating bounded inference through an LLM-as-function-call architecture, and validating each choice against the verification objective [cite: arxiv-2605-10712].
>
> MAGE carries the same trust boundary out of the proof assistant and into ordinary production. The external authority need not be a theorem prover. It can be a type system, a semantic lint, a preservation check, an architecture gate, a conformance engine, or a deploy rule. What must not blur is the guarantee each one carries: a lint proves less than a verifier, a preservation check proves only the property it encodes, and no green local check certifies the whole system. The untrusted generator paired with a trusted checker is not MAGE's invention; MAGE's move is to compose that one shape across the whole line.

Read the pattern in three moves, drawn in [ref:llm-function-call].

- **The caller is deterministic, and it owns the workflow.** Ordinary code decides what happens and in what order. It decides *when* a step needs the model at all — most steps do not. When a step is a matter of judgment rather than a matter of rule, and only then, the caller reaches for the model.
- **The call has a typed contract on both sides.** The task handed to the model is packed into a typed input — this figure, this context, this question — and the answer must come back in a typed output shape the caller can act on. The return value is a structured, checkable artifact, never an unstructured response whose role is ambiguous; natural-language content, such as a line of alt text, appears only inside a typed field with a declared purpose.
- **A deterministic validator sits at the trust boundary.** The model's answer is a *candidate*, not a result. Before it is incorporated, deterministic code checks it: does it satisfy the standard, does it preserve the input's meaning, does it fit the contract. On a pass, the caller incorporates the candidate and moves on; on a fail, it retries or falls back.

<!-- label: llm-function-call -->
<!-- figure: assets/llm-as-function-call.svg | *LLM as a Function Call.* A deterministic caller packs a task into a typed input; the foundation model returns output under a typed contract; a validator passes it before use. Determinism on both ends makes the call safer and governable: a malformed or mechanically invalid generation costs a retry rather than entering the document unchecked; semantic error remains bounded by the quality checks the validator actually implements. -->

<!-- point: spine-ascent-alignment-mechanisms | A validator at the trust boundary gives intent authority. | terms: trust-boundary, llm-as-function-call, thesis-alignment -->
<!-- point: defensible-claim-on-an-unreliable-model | The function-call shape defends a claim on an unreliable model. | terms: infinite-midwit, trust-boundary -->
This is why DocAble can make a defensible claim on top of an infinite midwit. The model
supplies the one thing deterministic code cannot: it looks at the figure and understands
something. Everything around that understanding — when to ask, what to ask, whether to
believe the answer — stays in code you can reason about and test. The probabilistic part is
bounded on both sides — a typed call in, a validated check out — which is what makes it safer
to call and possible to govern, not what makes it certain.

<!-- point: discipline-earned-the-hard-way | Skip the wrapper and the model finds the unguarded exception. | terms: llm-as-function-call, demoable-vs-productizable -->
This discipline was earned the hard way. Skip the wrapper and the model will find the
exception you did not guard — I assure you. Agents are the fastest road to a working demo
and the fastest road to a subtle, confident, wrong result. The function-call shape keeps
the first from becoming the second.

## Three views of the same system

<!-- section-terms: four-plus-one-views -->

<!-- point: three-views-from-real-models | Three architectural views, each from a real system model. | terms: four-plus-one-views -->
A model shows a view. The sections below draw three architectural views of DocAble from its
real system models, each answering a different question: how the services are shaped, and why
that shape let the whole system change its deployment target without a rewrite; how the front
end decomposes around a small edit language; and how that edit language becomes the target of
the automated pipeline — the function-call pattern above, seen once more.

The second and third views turn on one structure:
**one document model, one edit language, two producers, one validation-and-provenance boundary.**
A single structured model owns every change to a document. A small closed edit language is the only
way to ask for a change. Two producers — a human in the editor and the automated pipeline —
speak that one language. And every operation crosses one boundary that validates it and stamps
it before it touches the model. Hold those four facts and the rest of the chapter is detail
hung on them.

## View 1 — a reactive service seam, and how it made serverless natural

<!-- section-terms: service-flow-model, deployment-topology-model -->

<!-- point: reactive-stateless-service-seam | Small services react to events over a communication-truth split. | terms: service-flow-model, reactive-seam -->
The back end is a set of small services wired to react to events. A user's upload lands at a
web front door, which splits the document into chunks and enqueues each chunk as a unit of
work. A queue hands each chunk to a stateless worker. The worker remediates its chunk and
publishes a completion. A fan-in step collects the completions and assembles the finished
file. At the logical level each transition is an event handed forward; how a given hop is
*carried* is a deployment choice. Two commitments hold the seam together: services stay
reactive and stateless, and the split of duties is declared — Redis carries transient
coordination, the database carries authoritative truth. [ref:reactive-seam] draws the seam and the two ways it deploys.

> Learn more about this governance mechanism: [service-flow model](appendix-b-service-flow-model.html).

<!-- label: reactive-seam -->
<!-- figure: assets/services-reactive-view.svg | *The Reactive Seam.* Top: the logical flow — the web front door enqueues chunks, a queue hands each to a stateless worker that remediates it and publishes a completion, and a fan-in step assembles the finished file, each transition an event handed forward. Bottom: the same logical flow carried two ways — the retired Kubernetes plane, where workers *polled* Redis for chunks under a custom autoscaler, and the serverless push plane that replaced it, where the platform pushes each chunk to a worker that scales from zero. Because a reactive, stateless handler already is the serverless execution model, the re-platforming deleted complexity rather than adding it: the custom scaler and the per-prefix cluster rule fell away, replaced by native scale-to-zero. -->

<!-- point: reactive-shape-made-serverless-migration-easy | The reactive shape turned a hard serverless migration easy. | terms: serverless, poll-vs-push -->
<!-- point: the-seam-is-the-serverless-model | A reactive, stateless, modeled seam is already the serverless model. | terms: serverless, reactive-seam -->
That shape is what made a hard migration easy: **when the logical architecture is reactive and
stateless, the deployment target becomes an interchangeable concern rather than an architectural
rewrite.** For most of the system's life the workers *polled* size-stratified Redis queues under a
custom autoscaler on a Kubernetes cluster that billed around the clock — the wrong cost shape for a
bursty product. A serverless **push** plane replaced it, and changing the execution model required
no change to the business logic: a reactive, input-triggered handler already *is* the serverless
execution model, and no durable state lived in a worker for the recycle to lose. The inversion
*deleted* complexity rather than adding it — the custom autoscaler and the per-prefix cluster rule
fell away. The figure draws both deployment carriers; the service-flow model appendix pointer above
holds the seam's wiring in full.

<!-- point: convergence-not-aim-is-the-lesson | Built reactive and stateless for other reasons, it ran serverless. | terms: reactive-seam -->
None of the three hardening pushes that produced this shape — the reactive conversion, the
move to statelessness, the modeling of the cross-service invariants — was aimed at serverless.
Each was motivated on its own terms. Their convergence is the lesson: a system built reactive,
stateless, and modeled turns out, without having been designed specifically for serverless, to
be a system that runs cleanly serverless. The reactive seam was not a feature of the migration.
It was its precondition.

<!-- point: architectural-optionality-names-the-recurring-pattern | A local decision quietly banks a future option. | terms: reactive-seam -->
This is a pattern the case study hits more than once, so it earns a name: a decision made for a
local reason quietly buys a future option nobody paid for. Call it **architectural optionality** —
good architecture is optionality banked now and spent later. The reactive seam banked serverless.
Further on, one shared edit language will bank a second producer, and a cheap-to-refactor codebase
will bank near-free restructuring. Each option was a dividend on a decision taken for another
reason entirely.

<!-- point: the-operating-loop-in-one-migration | The agent phases a design, surfaces judgment calls, then executes. | terms: supervised-autonomy, phased-design -->
Here is how fast the seam let the migration go — the operating loop the rest of the book
describes. [The timeline](5.2-the-build.html) already tells the migration
itself: a Monday teardown of an idle Kubernetes cluster, the production deployment serverless by
that night, the migration and its hardening settling over the next day — about {{serverless_commits}}
commits structured into {{serverless_phase_count}} phased designs. What matters here is the loop those
phases ran: the agent proposes a phased design, it surfaces the decisions that need a human — one to eight
judgment calls a phase — I make those calls, and it executes. A re-platforming of the kind that usually
means a coordinator rewrite instead settled over a day or two, because the seam had already
been built right.

## View 2 — the front end as model-view-controller over a shared edit language

<!-- section-terms: edit-language, thesis-modeling -->

<!-- point: the-editor-is-an-mvc-loop | The editor is an MVC loop over one document. | terms: mvc, edit-language -->
The front end is a small single-page application plus a set of supporting surfaces — an
account view, a job history, an operator dashboard, and the editor. The piece worth drawing is
the editor, because it shows the cleanest decomposition. The editor runs as a **model-view-controller**
loop over one document — an approximate architectural view, not a textbook framework
implementation: a gesture becomes one typed command, and the document model applies it as a
unidirectional state update. It is drawn in [ref:editor-mvc].

- **The view** — two panes: the page with overlay boxes on each structural element, and a list of per-element cards with editable fields for alt text, role, decorative-or-not, and reading order.
- **The controller** takes a user gesture — edit this alt text, change this role, drag these children into a new order — and does one disciplined thing: rather than reaching into the document and mutating it, it translates the gesture into a single typed **edit operation**.
- **The model** — the document's intermediate representation. Its only input is an edit operation; it applies the operation and returns the state the view re-renders from.

<!-- label: editor-mvc -->
<!-- figure: assets/frontend-mvc-editor-dsl.svg | The editor as one MVC loop over the document. A gesture flows View to Controller; the controller emits one typed edit op from a closed vocabulary; the model applies it and returns state to re-render the View. The same edit language is what the automated pipeline produces. -->

<!-- point: a-closed-edit-vocabulary | A closed edit vocabulary is the one way to change. | terms: closed-vocabulary, edit-language -->
The operation the controller emits is drawn from a small, closed vocabulary: set the alt text,
set the role, mark an element decorative, reorder the reading order, set the document title,
set the language, override the displayed text. That vocabulary is a little language for
changing a document — an edit language. Every gesture routes through it for the reason that runs
under the whole system: a document has exactly one way to be changed. The
editor never edits the document. The UI never mutates format objects directly; it emits commands
to the document model, and the model is the only thing that touches the document.

> Learn more about this governance mechanism: [closed edit-operation vocabulary](appendix-c-remediation-verbs.html).

Here is what MAGE adds to the textbook picture. In classical model-view-controller the command
exists to decouple the view from the model — a convenience of construction. Here the command is
load-bearing for *governance*. Because every gesture becomes one typed edit operation drawn from a
closed vocabulary, the edit surface stops being a scatter of ad-hoc mutations and becomes a single
named boundary a machine can hold. A typed operation can be validated before it applies, stamped
as it applies, and refused when it violates a constraint; a closed vocabulary can be *kept* closed
by a lint. Fowler and Gamma would recognize the loop; what they did not need is the closure — the
guarantee that there is no other way to change the document. That guarantee is what turns an edit
language into a governance surface, and it is why the same seam can carry both a human's gesture
and, in the next view, the pipeline's output.

<!-- point: one-language-many-formats-is-modeling-thesis | One edit language across formats is the Modeling Thesis miniature. | terms: thesis-modeling, edit-language -->
The read-only diff views for slides and word processor files share this shape, differing only
in the adapter that fetches their structure. One surface, one edit vocabulary, many formats.
A fix or a constraint applied to the edit language holds for
every format and every producer that speaks it, and the more producers speak it, the more
each fix is worth. This is the Modeling Thesis in
miniature — a structured model binding what a change *means* to how the document is *touched*, so
intent and mutation semantics share one enforceable seam.

## View 3 — the edit language as the target of automated remediation

<!-- section-terms: edit-language, transformation -->

<!-- point: the-two-halves-join-here | The two halves join here through the function-call pattern. | terms: llm-as-function-call -->
Here the two halves of the system join, and the join is the function-call pattern from earlier
in the chapter, seen once more.

<!-- point: two-producers-of-one-language | Human and automated paths produce one edit language. | terms: edit-language, two-producers -->
The edit language the editor speaks is not only the editor's. It is the **same target the
automated pipeline produces**. When the pipeline decides a figure needs alt text, the result
it emits is an edit operation — the very `set-alt-text` the editor would emit if a human did
it by hand. The human path and the automated path are two producers of one language, and they
flow into one document model that applies each operation and stamps it — architectural optionality
again: a language built so a human could edit safely turned out to be a language a pipeline could
target for free.

<!-- point: task-to-operation-is-a-function-call | The task-to-edit mapping is an LLM-as-function-call instance. | terms: transformation, llm-as-function-call -->
<!-- index-example: transformation -->
The mapping from a remediation *task* to an edit *operation* is a function: task in, operation
out. And that function is a concrete instance of the [LLM as a function
call](#llm-as-function-call). Inside it, a bounded task — this figure, this context, this
question — is packed into a typed input and handed to the model as a call; the model returns a
candidate; and a deterministic validator checks the candidate before it is allowed to become
an edit. The edit language is the typed output contract. An honest caveat: this task-to-edit
function is mostly hardcoded today and will be fleshed out. What matters now is the shape and
the trajectory, not a finished implementation — the concept is that automated remediation and
hand editing are the same operation reached two ways. [ref:two-producers] draws both paths into one edit language.

<!-- label: two-producers -->
<!-- figure: assets/dsl-remediation-function.svg | *Two Producers, One Language (target architecture; partially implemented).* The human path emits ops by hand; the automated path turns a remediation task into an op through a task-to-edit function — an instance of LLM-as-function-call. Both emit the same closed edit vocabulary into one document model that applies and stamps each edit. The task-to-edit function is today mostly hardcoded; the figure records the intended shape, not a finished implementation. -->

<!-- section-terms: traceability, trust-boundary -->

<!-- point: route-through-the-language-buys-audit-and-trust | Routing through one validated language buys audit and trust. | terms: traceability, trust-boundary -->
The frontier models can already skip all of this. Opus and the project's own agent can take a
slide deck and remediate it directly — at least for slides — with no pipeline, no edit
language, no validator. So why build the machinery at all? Direct remediation buys neither of
the two things a university needs. You cannot **audit** what a direct edit changed: the model
hands back a file, not a list of typed changes you can inspect, explain, and reverse. And you
cannot **trust** it: there is no deterministic check that the standard was met and the meaning
survived. Routing every change through one edit language and one validated boundary buys both.
Traceability falls out systematically once every change already passes through a typed, stamped
operation — each edit carries a history you can reconstruct. Confidence comes from the validator that sits at the trust
boundary and refuses a candidate that fails.

<!-- point: scoping-the-call-scopes-the-reasoning | Scoping each call to one task scopes reasoning and cost. | terms: transformation, sizing-the-leap -->
There is a third dividend, and it connects this view to a habit the book returns to later.
Scoping each model call to one bounded task also **scopes the reasoning**: the tighter the
task, the less the model must reason over, and the smaller and more checkable each answer is. A model
asked to describe *this* figure under *this* context does less work than a model asked to
remediate a whole document in one shot. That scoping is the same move as
building the remediation as a **series of small, bounded transformations** rather than one
giant leap — the same idea seen from the reasoning angle instead of the pipeline angle. In DocAble,
scoping each call this way cut the irrelevant context the model had to carry and made a failure cheap
to localize to one task; whether many small calls cost less *total* inference than one large call
depends on how much context each repeats and the per-call overhead. (See: *transformation* — everything a model does well is a sized
transformation, and sizing the leap is the skill.)

That is the whole architecture in one line: one document model, one edit language, two producers,
one validated and stamped boundary — the human editor and the automated pipeline reaching the same
typed operation two ways.

<!-- point: views-rendered-from-models-kept-honest | The views render from real models kept honest by traceability. | terms: model-zoo, snapshot-vs-derived -->
These three views were not drawn by hand. They were rendered from DocAble's real system
models — typed records the fleet reasons through — and those models stay true to the code only
because a traceability substrate re-checks them against it, the deep-dive we return to in
[the Model Zoo](2.3-the-executable-zoo.html).

## Same song, second verse

<!-- section-terms: llm-as-function-call, thesis-alignment -->

<!-- point: wrap-the-unreliable-part | Wrap the unreliable part: bound, type, validate. | terms: llm-as-function-call, vision-language-model -->
Notice the shape of the argument, because the book made it again at a larger scale. A model
can do the one thing deterministic code cannot — look at a figure and understand it — and it
is unreliable. You do not make it reliable by trusting it more. You make a reliable system by
wrapping it: bound what you ask, type what comes back, validate before you believe. Inside
DocAble, the wrapped component is a vision-language model writing alt text.

<!-- point: agents-are-the-same-component | The agents are the same component, wrapped the same way. | terms: thesis-alignment, probabilistic-component -->
Zoom out one level and the coding *agents* that built DocAble are the same kind of component:
powerful, probabilistic, capable of a confident wrong turn. The methods in the earlier
chapters are the same pattern applied to *them* — bound the task, type the interface, validate
before you trust. You have now seen, in the small, the pattern the rest of the book applied in
the large. Same song, second verse.

<!-- point: mage-accreted-under-rising-bar | Each model began small, expanding as the rising bar demanded. | terms: governance-conversion -->
The MAGE methodology emerged from months of work with coding agents.
I initially expected to prompt the agents and have them make what I wanted, and for a little
while that sufficed. But the more my ambition grew, the less mere prompting could carry, and
I accumulated more and more of the method.
Every model, every constraint, every sensor in the built system arrived the same way:
  a growing codebase and a rising quality bar demanded it, and I usually began with the smallest mechanism that closed the observed class, then expanded it when the rising bar exposed a wider need.
Then the system grew again, the bar rose again, the current system proved inadequate, and the next thing was demanded.
MAGE is the name for what was left standing after enough of those rounds.

<!-- point: staircase-of-delegated-jobs | Each step mints the model or control the next needs. | terms: mbse -->
What follows walks the order in which the pieces appeared, and I suggest you read it as a
staircase. Each step answers a load the step before it could no
longer carry. Watch the job title climb as you go — co-coder, QA, review lead, tech lead, architect —
each rung a job the one before it could no longer do, and each one handed off only
because the step below had made it safe to let go.
The titles name the center of gravity of my work, not an organizational hierarchy or a claim
that one person literally replaced each profession. And climbing did not eliminate the
lower-level work; it made it exceptional rather than continuous — I still drop down a rung when a
control misses, as the box below describes.
The models did accrete along the way, but the road this chapter walks is the climb of the seat,
and the governance that made each rung safe to let go.

<!-- point: governance-makes-delegation-safe | Governance makes each rung's delegation safe to let go. | terms: constraints-and-sensors -->

> ### Why the job title climbs
>
> The whole ladder rests on one hinge, and it is **governance**. Every rung is a successive delegation. I hand
> the agents a piece of the *tactics* — write this code, audit that diff, run this zone — and keep
> the *strategy* for myself. That handoff is only safe because a control caught what the delegation
> would otherwise have dropped. A lint reddens on the boundary I stopped watching; a gate
> refuses the commit I stopped reading; a model the fleet reasons through means I no longer have to
> hold the map in my head. Governance is what makes it safe to let go. Delegation climbs exactly
> as far as the controls will carry it, and no farther.
>
> Get the governance wrong and the ladder runs in reverse. The controls that were supposed to catch
> the dropped thing miss it, the misses surface days later in some downstream gate, and I am pulled
> back down into the tactics to firefight. I am reading diffs again, chasing a drift the
> map no longer shows, with no one left minding the strategy. That is the *Claude is the fastest road to
> hell* principle at fleet scale: the same speed, now pointed through a governance gap instead of riding atop,
> carrying the whole crew downhill as fast as it once carried them up.

## [role: Co-coder] Step one — I reviewed everything myself

<!-- section-terms: human-as-quality-gate -->

<!-- point: human-is-the-quality-gate | At small volume one human reviews every line. | terms: human-as-quality-gate -->
At the start there was one document format, a few hundred lines, and me. When the agent
proposed a change I read the diff, decided it was right or wrong, and merged it. The
entire quality mechanism in the first week was one human reviewer. It works, and it works
precisely because the volume is small enough that one person can hold the whole thing in
his head and say yes or no to every line.

<!-- point: human-gate-does-not-scale | The human gate cannot scale; agents outrun review. | terms: human-as-quality-gate -->
The obvious trouble with that gate is that it does not scale.
A real system takes more code than one person can read, and agents write code far faster than a human can review it — the more they wrote, the further behind I fell.
The first crack was thus a queue: work finished faster than I could bless it, and I became the bottleneck.

## [role: QA] Step two — I dispatched an agent to audit the work

<!-- section-terms: audits-into-lints, constraints-and-sensors -->

<!-- point: dispatch-an-agent-to-review | An agent audits the work; checking leaves my hands. | terms: governance-target-agent -->
The first offload was to hand the review itself to an agent. Instead of reading every diff,
I dispatched a second agent to audit the first one's work and report what it found. Now the
*checking* of the work had left my hands and entered the fleet. The human stopped being the
reviewer of record and started being the reviewer of the reviewer.

<!-- point: audit-is-the-weakest-control | An audit is the weakest control; make it a lint. | terms: audits-into-lints, static-analysis -->
That move taught a lesson. A test or an audit is not
a chore bolted onto the work — it is a **control**, a discrete artifact that fires on a
violation. But an *audit* is the weakest kind of control: it externalizes the question without yet
making enforcement durable. Its findings become durable only when the audit is scheduled, or when
the decidable part is promoted into a lint — which is why an audit is expensive, deferrable, and
after-the-fact. It runs when I remember to
run it, over a codebase that has already drifted. The audit worked, but it planted a
question that drove everything downstream: which of these audit findings could become a
*lint* — deterministic and cheap static analysis — so I never had to look for that class of failure again?
Today's audit finding is tomorrow's lint.

## [role: Review Lead] Step three — one audit became a crew

<!-- section-terms: specialist-crew, component-zone-model, audits-into-lints -->

<!-- point: one-generalist-reviewer-is-unaimed | One generalist reviewer cannot rank or localize findings. | terms: specialist-crew -->
The single reviewing agent worked, but it had a flaw I could not brief away.
Pointed at a hundred thousand lines, one audit agent always found *something* to complain about — it never came back empty.
And it could not do two things I needed.
It did not rank heterogeneous findings reliably enough to be actionable, so a cosmetic nit and a real architectural break arrived side by side with equal weight.
And it could not tell one part of the codebase from another, so a rule that mattered in the PDF model got applied, out of place, to the web layer.
A single generalist reviewer over a large codebase is a firehose with no aim.

<!-- point: split-into-a-specialist-crew | A specialist crew replaces the generalist, each narrow charter. | terms: specialist-crew -->
The fix was to stop dispatching one reviewer and start dispatching a **crew** — a set of specialists, each with a narrow charter.
I split the one audit into distinct briefs by *type* of concern: a **DRY** audit that hunts duplicated logic, an **architecture** audit that checks the code against its own stated rules, a **naming** audit, a **security** audit.
Each brief knows one thing well and ignores everything else, so its findings are all of one kind and can be ranked against each other instead of against apples.

<!-- point: zones-aim-the-crew | Architectural zones aim each audit; findings gain two coordinates. | terms: code-zone -->
Aiming the crew took a second idea, and it is the one that matters for the rest of this chapter: **architectural zones**.
I partitioned the codebase into named regions and let each audit run per zone.
Now a finding carries both coordinates — *which kind of concern* and *which part of the system* — and the firehose becomes a grid of aimed jets.
The zone idea is the seed of the first real model, and step four is where it grows up; here it is just the thing that made the crew usable.

<!-- point: spine-ascent-externalized-knowledge | The written architecture rules externalize knowledge past memory. | terms: audits-into-lints, governance-target-agent -->
A crew brief is a standing artifact the orchestrator re-dispatches per zone.
Here is the head of the real **architecture** audit — the one that checks code against the architecture rules the project has written down for itself:

<!-- inset: A standing brief — the architecture audit -->
```markdown
# Architecture Compliance Audit Agent

**Purpose:** Verify that code follows the architectural rules and
invariants documented in CLAUDE.md, DESIGN.md, and ORCHESTRATION.md.
Catches violations before they become production bugs.

## What to check

For each rule below, verify the code matches what the docs say. If
the docs have been updated but the code hasn't, that is a finding.

- **Library discipline:** Verify PDF production code uses the one
  sanctioned PDF library only, that the tag-tree-stripping library is
  absent from tag-tree operations, and that GenAI calls go through the
  single client factory.
- **State machine discipline:** Verify the async job lifecycle uses the
  explicit state machine with a terminal-state guarantee in `finally`,
  and that metric hooks are wired as state-entry callbacks, not
  scattered calls.
- **Redis vs DB responsibility:** Flag durable state kept in Redis, or
  dispatch queues kept in the database.

## Output

Each finding: file:line, rule violated, 1-2 sentence description.
Cap at 15 findings. Prioritize by production-incident risk.
```

Read the brief and the two ideas are both visible.
The `## What to check` list is the *type* charter — this agent reasons about architectural rules and nothing else.
The `Cap at 15 findings. Prioritize by production-incident risk.` line is the fix for the firehose: a narrow charter can rank, because everything it returns is the same kind of thing.
And this brief runs once per zone, so the same rules get checked against the PDF model, the web layer, and the dispatch plane as separate passes — the *target* coordinate.

<!-- point: audit-to-lint-at-fleet-scale | Deterministic checks moved down to cheap lints. | terms: audits-into-lints, static-analysis, ban-lint -->
The crew taught the lesson that drove everything after it.
Once I was paying agent tokens to run these audits on a cadence, the waste was obvious: an audit is a probabilistic agent re-reading the code every time, and much of what it checks is *deterministic*.
"Does any file outside the PDF zone import the PDF library?" does not need a language model — it needs a lint.
So I leaned hard into two cheaper controls that match the crew's briefs one-for-one.
First, **commodity lints** — the off-the-shelf static-analysis rules that catch the generic smells at low marginal implementation cost.
Second, **custom lints** written to mirror each audit brief: the architecture audit's "one sanctioned PDF library" check became a boundary lint that reads the zone declaration and reddens on a cross-zone import, deterministically, at commit time.
The audit crew did not disappear; it retreated to the findings a lint genuinely cannot make — the ones that need judgment.
Everything a machine could decide moved down to the machine.
This is the audit-to-lint move — today's audit finding is tomorrow's lint — run at fleet scale, and it is what freed the crew to be worth its tokens.

## [role: Tech Lead] Step four — zones, so an agent can reason locally

<!-- section-terms: component-zone-model, context-window, governance-target-agent -->

<!-- point: cold-start-agent-lacks-tacit-knowledge | A finite-context agent cannot hold a team's tacit knowledge. | terms: context-window -->
A crew that coordinates is still a crew of agents each of whom has to understand the code
it touches. And here the agent's nature bites. A cold-start agent with a finite context
window cannot reach the tacit knowledge a human team keeps in its collective head — which
file is canonical, what this module *means*, which of two look-alikes is the live one. A
human learns that by working in the codebase for months. Think of the agent instead as a
contractor with no memory of yesterday: it arrives knowing nothing
and has to be *told*, in the code, every time.

<!-- point: spine-ascent-context-selection | A zone selects which knowledge enters the agent's reasoning. | terms: component-zone-model, context-window -->
<!-- point: named-zones-enable-local-reasoning | Named zones let an agent reason inside one, fenced. | terms: component-zone-model -->
The answer was to partition the system into named **zones** — a model that says, out loud
and in a queryable form, what the parts are and where their boundaries lie. Once the system
is carved into zones, an agent can be handed one zone, reason inside it locally, and be
fenced from the rest. A boundary lint can then refuse an edit that reaches across a zone it
has no business touching. The zone model turns "hold the whole 280-thousand-line codebase within
one reasoning horizon" — which no finite-context agent can do — into "reason inside this zone,"
which it can.

A zone is a small typed record. Here are two real ones — the PDF and PowerPoint object
models, side by side:

<!-- inset: Two zones, side by side -->
```python
Component(
    name="pdf-model",
    focus_dirs=(RepoRelPath("backend/src/AdaTool.PdfModel"),),
    boundary_kind="internal",
    external_seams=("pdf-lib",),          # ONLY this zone may call the PDF library; banned in every other zone
    description="PDF object model + typed mutators",
),
Component(
    name="slides-model",
    focus_dirs=(RepoRelPath("backend/src/AdaTool.SlidesModel"),),
    boundary_kind="internal",
    external_seams=("openxml",),          # ONLY this zone may call the Office library; banned in every other zone
    description="PPTX Office-XML model + typed mutators",
),
```

<!-- point: spine-ascent-the-turn | The seams field gains a boundary lint: the turn. | terms: ban-lint, code-zone, thesis-alignment -->
<!-- point: a-boundary-lint-enforces-the-seam | A boundary lint reads the zone field and reddens. | terms: ban-lint, code-zone -->
Read `external_seams` and the whole discipline is legible. The `pdf-model` zone is the *only*
one allowed to reach the canonical PDF library; `slides-model` is the only one allowed to reach
the Office library. A boundary lint reads that field at check-time and reddens on any file
outside the `pdf-model` zone that imports the PDF library directly — the "one structured model per
format" rule from the built-system chapter, enforced not by vigilance but by a zone declaration
a machine walks. The agent working the PDF zone is handed `focus_dirs` as its lane and
`external_seams` as its permission slip: the dispatcher scopes its lane, and the boundary lint
rejects one important class of wandering.

<!-- point: zone-model-is-first-mage-model | The zone model is MAGE's first explicit model, for agents. | terms: component-zone-model, governance-target-agent -->
The zone model was the first explicit system model at the center of what became MAGE, because it is the first time I wrote down
a *model of the system's own structure* for the fleet to read, rather than a piece of the
product. Its audience is the fleet; a user never sees it.

## [role: Architect] Step five — the codebase modeled, from components.py to MAGE {#refactor-cost}

<!-- section-terms: executable-source-of-truth, component-zone-model, refactoring-is-free -->

<!-- point: commit-the-system-to-explicit-models | I stopped holding the system and committed it to models. | terms: mbse -->
By this step I never looked at code at all. What changed is that I stopped *holding the system
in my head* and started committing it into explicit models — the system the fleet reasons *through*. It has one shape with three movements: a first model the fleet reads at
runtime, a set of sibling models that grew up around it, and a substrate that keeps all of
them honest. Together they are MAGE.

<!-- point: zone-model-becomes-executable | The zone model becomes a file the fleet executes. | terms: executable-source-of-truth -->
The first movement was to make the zone model a file the fleet reads at runtime. That is where
the method crosses from *documenting* the structure to *executing* on it.

<!-- point: registry-is-the-architecture | The typed registry is the architecture, queryable by tools. | terms: executable-source-of-truth, component-zone-model -->
A typed registry of the system's own components — its zones, their focus directories, the
seams each one is allowed to cross — is not documentation *about* the architecture. It *is*
the architecture, in a form a tool can query. Operationally, it is the authoritative architecture
model for the concerns its fields represent; the running code remains the implementation. The zone
I showed above is one row of it; the row's *shape* is a frozen dataclass:

<!-- inset: The registry the fleet reads -->
```python
@dataclass(frozen=True)
class Component:
    """One system component."""
    name: str
    focus_dirs: tuple[RepoRelPath, ...]
    tags: frozenset[str] = field(default_factory=frozenset)
    kind: str = "leaf"                                      # leaf | group | meta
    external_seams: tuple[ExternalSeam, ...] = ()           # the powerful libs it may reach
    import_allowed_components: tuple[ComponentName, ...] = ()  # who it may import
```

<!-- point: spine-ascent-structured-relationships | Typed fields make dependencies and seams queryable edges. | terms: component-zone-model, executable-source-of-truth -->
<!-- point: each-field-answers-an-agents-question | Each typed field answers a question an agent would guess. | terms: component-zone-model -->
Every field is a machine-readable answer to a question an agent would otherwise have to guess.
`focus_dirs` answers "what files are in my lane?" `external_seams` answers "which powerful
library am I permitted to touch?" `import_allowed_components` answers "who am I allowed to
depend on?" When a lint needs to know "which components may cross which external boundary," it
does not hardcode a list that rots — it reads `external_seams` at lint-time. When the
dispatcher needs to know which files a brief may touch, it reads `focus_dirs`. When context has
to be injected into an agent's prompt, the question stops being "which files do I paste?" and
becomes "what durable artifact should exist so the right context is *selectable
deterministically*?"

<!-- point: one-field-unlocked-many-lints | One typed field replaced allowlists and unlocked three lints. | terms: reflective-codebase, static-analysis -->
The payoff was concrete and it compounded. Adding a single typed field to that registry —
one field naming which components cross an external boundary — replaced four hand-maintained
allowlists that were quietly drifting and unlocked three new lints all reading the same field.
On its first run the new boundary lint surfaced a large backlog of latent violations no one had
had a way to ask about before. The type named a previously-anonymous shape, and the named shape
became a question you could pose to the whole codebase at once. The reflective codebase *is* the
agent substrate. The more the system knows about itself, the less the agent has to guess.

<!-- point: cheap-refactoring-inverts-economics | Cheap refactoring inverts architecture's economics; postponing becomes expensive. | terms: refactoring-is-free, judgment-is-the-scarce-resource -->
The refactoring got cheaper because the models told me exactly where to look and where to stop
looking. They took the guesswork out of migration planning: instead of a plausible repository-wide
estimate, I got a traceable scope calculation derived from the model. A cross-format
migration that touched fifty-eight files and rewrote five thousand lines — the kind of change
I might once have deferred — took about five hours of agent time over a dinner
break. When the mechanical cost of restructuring collapses, the economics of architecture
invert: postponing the right shape becomes the expensive choice, and building the right model
becomes something you can do the moment you see you need it. The hard part was never touching
fifty-eight files; it was knowing that fifty-eight files should be touched. The marginal
mechanical edit cost collapsed; deciding *which* model to build, and validating the migration,
remained expensive.

### A view per property I had to guarantee

<!-- section-terms: four-plus-one-views, model-only-where-a-failure-lives, model-drift -->

<!-- point: spine-ascent-system-models | Each view adds semantics guarding one system property. | terms: four-plus-one-views, model-only-where-a-failure-lives -->
<!-- point: a-view-per-guaranteed-property | Each model is a view guarding one rising property. | terms: four-plus-one-views, model-only-where-a-failure-lives -->
Once that first model paid off, the others followed — but the right way to see the set is not
"more models." Each model is a **view** of the system, and each view exists to answer for one
**property or quality attribute** I had to guarantee: a property like *deployability*, a quality
attribute like *security*. The set was never planned. What grew was the *demand*. The faster the
fleet moved, the higher the bar on each property rose, and a rising bar on a property I could
no longer hold in my head is exactly what forced a view to carry it. The models accreted on
demand — one view for each quality question that needed a distinct reasoning surface.

- **A service-flow model** — the view that guards *event-wiring correctness*. It appeared when the back end became enough services that no one could hold the wiring in their head. That view is what later made a hard re-platforming close to a change of deployment target — the same architectural optionality the built-system chapter named, seen from the model side.
- **Synchronization contracts** — the view that guards *concurrency safety*. They appeared when concurrent agents and concurrent workers started tripping over shared state, and the invariants that had lived only in prose had to be encoded where a checker could walk them.
- **A deployment-topology model** — the view that guards *deployability*. It appeared when the system ran in more than one place and the boot-time environment each service needs stopped fitting in anyone's memory.
- **Domain registries** — the view that guards *vocabulary closure*. The closed edit vocabulary, the remediation verbs, the mutator stamps: each appeared when a set of strings needed to become a typed, enumerable thing a lint could hold closed.

<!-- point: a-stack-of-views-drifts | A stack of views drifts into stale ghosts. | terms: model-drift, symbol-anchor -->
None of these was drawn from a master diagram. Each was the smallest view that answered for one
rising property. But a stack of views has a failure mode of its own, and it is the one that
turns a map into a lie: **drift**. A view that names a code symbol goes stale the moment that
symbol is renamed, deleted, or moved, and nothing notices — the view still *looks* authoritative
while pointing at a ghost. The fleet reads the ghost as truth, and the blow-up lands days later
in a downstream gate instead of at the change that caused it.

### The substrate that keeps the models honest

<!-- section-terms: governance-graph, snapshot-vs-derived, traceability -->

<!-- point: traceability-graph-of-derived-edges | A traceability graph links models by derived edges. | terms: governance-graph, snapshot-vs-derived, symbol-anchor -->
So the models grew a nervous system. A traceability substrate links every model to its lint,
its code entry-point, its proof, and its sibling models as a typed graph whose every edge is
a *derived* obligation a lint re-checks against a resolvable symbol: authoritative edges resolve
live symbols rather than depending on stored line numbers. Derived edges defend; snapshotted ones drift.

<!-- point: two-kinds-of-drift-two-catches | Deterministic drift is a lint; semantic drift a gate. | terms: model-drift -->
Drift comes in two kinds, and the substrate catches each a different way, because the two are
not the same problem.
The first kind is **deterministic**. The code moved: a symbol was renamed, deleted, or hoisted
into a different module, and a view's edge now points at nothing. That is mechanically decidable,
so a machine decides it. A lint walks every edge in the graph and re-resolves its anchor against
the live code; an edge that no longer resolves reddens on the spot. There is no judgment in it —
the symbol is either there or it is not — so this is a lint, run deterministically, and a broken
edge fails at the change that broke it rather than days downstream.
The second kind is **judgment**. The code still resolves — every anchor points at a real symbol —
but the *change altered what the view claims*. A function still exists, but it no longer does
what the invariant says it does; a checker was quietly made stricter than the producer it now
rejects. No lint can see this, because nothing on disk is broken; the map matches the territory
symbol-for-symbol and lies anyway. So this drift is caught by a review gate, not a lint: the
definition-of-done audit at the close of every unit of work asks, in as many words, *did this
change alter a model?* — and routes a "yes" to a judgment-bearing review owned by the responsible
engineer, possibly performed initially by an agent. Deterministic drift is a
wall; semantic drift is a question you have to keep asking.

<!-- point: the-graph-equals-map-to-territory | The graph keeps the map equal to the territory. | terms: governance-graph, symbol-anchor -->
That pairing — a lint that walks the anchors for the drift a machine can decide, and a review
gate that asks the human-or-agent question for the drift it cannot — is the whole mechanism. The catalogue carries it as
[symbol-anchored traceability graph](appendix-b-symbol-anchored-traceability-graph.html).
The graph is what keeps the map equal to the territory — over the symbols and relations the model
claims to represent — which is the only condition under which a
context-bounded agent can safely operate a context-exceeding codebase *through* the models. The
structured models, the substrate that keeps them honest, and the query surface the fleet reasons
through — together these are MAGE. [ref:mage-staircase] draws the five-rung climb.

<!-- label: mage-staircase -->
<!-- figure: assets/mage-staircase.svg | *The MAGE Staircase.* Five rungs, each a job the one below could no longer do, and each safe to climb only because the step under it first minted the control the next would need. Co-coder: one human reviews every line, until volume outruns him. QA: an agent audits the work, until one generalist reviewer cannot rank or localize. Review lead: a crew of specialists runs per zone. Tech lead: named zones let an agent reason locally, fenced by a boundary lint. Architect: the system is committed to explicit models the fleet reasons through, held honest by a traceability substrate — that is MAGE. The ladder runs in reverse the moment governance misses what a delegation dropped. -->

<!-- section-terms: missing-model-metric, brownfield-migration -->

<!-- point: turn-brownfield-inward | Turn the brownfield problem inward: what is still unmodeled? | terms: brownfield-migration -->
The Architect rung is where the ladder ends, but the work on it does not.
Every model so far was built the same way: I noticed a load and modeled it.
That is a *supply-side* method — it models what I happen to see.
Once there are a dozen models and a traceability graph, the obvious question is the one I could
not answer by looking harder: **what is still unmodeled?**
That is the [Brownfield](4.2-brownfield.html) problem, turned inward on my own system.
A greenfield method invents the models it wants up front; a brownfield method inherits a large,
already-built system and has to *discover* the models the system already implies but nobody has
drawn yet. That is the situation I was actually in, and it needed a different instrument.

<!-- point: missing-model-metric-walks-code-to-model | The Missing Model Metric finds tests reaching no model. | terms: missing-model-metric, orphan-test, granularity-gap -->
The instrument is the **Missing Model Metric**, the dual of test coverage. Ordinary coverage walks
model-to-code — for each model, is it tested? This one walks **code-to-model**: start from a test,
follow the production code it exercises, and ask whether any of that code carries a model anchor. A
test that reaches *no* anchor is an **orphan**; clustered by the unmodeled code they run through, the
orphans are a candidate list of *missing models*. (The mechanics are laid out in full in
[the Brownfield chapter](4.2-brownfield.html); here what matters is what the metric revealed.)
On its first run over the dispatch subsystem — the *most* heavily modeled corner of the codebase,
where orphans should have been rare — more than half the tests came back orphaned (the pilot rate, {{missing_model_pilot_percent}}).
A sharpening pass turned that scolding into a map: every orphan reached code the model already
knew at the coarse structural level, but that carried no fine behavioral model. The structural
map was complete; the behavioral map covered the concurrency-critical spine and stopped. The
metric had found a *granularity gap*, and it named exactly where to close it — three genuine
candidate models: the durable-state persistence layer, the cost-and-subprocess pipeline, and the
chunking-merge-and-validation path.

<!-- point: a-loop-drives-orphans-down | A loop lowers the orphan rate by adding models. | terms: missing-model-metric, orphan-test -->
That map drove a loop, and the loop has run.
Measure the orphan rate; rank the biggest clusters; for the largest, found a modeling Epic and
drive it to a strong structured model under a real design review; re-measure; take the next cluster.
The key property is the one that makes it a *modeling* instrument rather than a testing one: you
do not move the number by adding a test — you move it by adding a *model*.
Wave by wave, the loop worked as designed. The three seed models drove the dispatch subsystem's
orphan rate down from its {{missing_model_pilot_percent}} pilot to {{orphan_after_first_epic}}, and the
next cluster — the sidecar persistence seams — carried it lower still along the drain series
([data: mmm-drain]). Each closed model converted exactly
the tests that reach its new anchors from orphan to modeled — the expected directional response,
which supports that the metric is tracking its declared relation.

**What modeling found that green tests missed**

<!-- point: modeling-found-real-shipping-bugs | Modeling found real shipping bugs the green tests missed. | terms: orphan-test -->
The loop was not bookkeeping. Building those models found real, shipping bugs the green tests had
missed — the payoff that justifies the whole method. Modeling the cross-language pipeline seam
caught a subprocess exit code that one runtime emitted and the other had never enumerated, so a
"the service should have worked" failure was being silently misfiled as a generic error. Anchoring
the chunking model to its one canonical cleanup seam exposed a failure path that purged a job's
database rows and blobs but skipped the queue structures its sibling path always cleaned — a chunk
leak on a rare redelivery edge. And modeling the interactive editor's save round-trip surfaced an
unfenced last-write-wins race in which two concurrent edits silently discarded one's work. None of
these was a hypothetical the model raised; each was a live defect the act of modeling forced into
view.

<!-- point: mage-was-demanded-not-designed | MAGE was demanded step by step, never designed. | terms: governance-conversion -->
So the method that began with a human reviewing every line arrived at a system that measures its
own modeling completeness and dispatches work to close the gap it finds — a codebase modeling
*itself*, brownfield, in a loop. The metric and the orchestration loop identify candidate modeling
work; the engineer still decides what model should exist.
MAGE was never designed. It was demanded, step by step, by a system that kept growing and a bar
that kept rising — and the last thing it demanded was that the method turn its own instruments
back on the parts of itself it had not yet named.
