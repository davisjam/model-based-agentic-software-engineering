4.6 The Field Guide

THE PORTABLE MOVES

The method is a small set of transferable moves. Take the pattern, avoid the anti-pattern, size the mechanism by cost times frequency, and run the checklist.

You can apply every move in this chapter to a codebase this book has never seen.

The chapters before this one taught the method through one deep case and a handful of outside teams. This one strips the case away. What is left is the part that ports: a set of moves you can carry to your own repository without adopting anyone's platform, tooling, or story.

Everything here descends from one shape. Modeling makes intent explicit, Alignment gives that intent authority, and the failures the work reveals feed back into both — so each pass begins from a stronger position than the last. The patterns are how you make a move, the anti-patterns are how a move goes wrong, the heuristics are how you size it, and the checklists are how you start on Monday. Each entry names the chapter it comes from, so you can read the full treatment when a move is the one you need.

4.6.1 The patterns

A pattern is a move the method makes again and again, in a form you can reuse.

  • - Bootstrap from the environment you already own. Do not wait for a clean start. A drifted wiki is an immature model; a legacy test suite is a floor to refactor over; a decades-old schema is a representation an agent can already reason through. Begin at the lowest rung that pays and strengthen the representation only when a recurring engineering question earns the next one. (Brownfield.)
  • - Prefer a constraint; add a sensor for the drift you cannot scope away. A constraint prevents the mistake inside the iteration, so the wrong move is never available to pick and no failed loop is spent catching it. A sensor lets the mistake happen and catches it after, at the cost of an iteration. Build the constraint where you can; reach for the sensor only for the drift a constraint cannot foreclose. (The Governed Environment.)
  • - Determinize what you can specify up front; convert every recurring surprise into a mechanism. Write down the rules you know before the first line of code and give each a cheap deterministic check. Then watch the work run, and turn each failure you did not foresee into a durable control. Most real mechanisms come from the second half, not the first. (The Governed Environment, Governance Conversion.)
  • - Wear a control in with audit, drain, promote. Land a new check advisory: every finding reported, no commit blocked, so it never breaks an agent in flight. Drain the findings to zero with ordinary work. Only then flip it to blocking, so the class can never return. The order is the safety — flipping a check to blocking while findings remain breaks every agent's commit at once. (Brownfield.)
  • - Route the agent's judgment through a model, not the code. Where you own a structured representation — a schema, a state model, a solver — ask it whether the answer is right, instead of asking a language model whether the code looks correct. Choose the coarsest abstraction that can express the property you need; a finer model costs more to write and run without always buying a stronger guarantee. (Brownfield.)
  • - Generate evidence built to falsify a claim, and admit only the claim that survives. Do not accept an agent's work on its own word. State the property the output must obey across the whole input space and hand a generator the job of hunting a counterexample; where an untrusted-bytes boundary has no law worth stating, fuzz it and fix each finding to the stable point in the specification, not the failing seed. (Validation with Agents.)
  • - Never add metadata without adding a consumer. A tag, a backlink, an ownership field, a machine-readable mirror — each earns its place only when an audit, a brief, a retrieval step, an analysis, or a gate reads it. Metadata with no reader is one more surface free to drift. (Brownfield.)
  • - Encode the procedure, and a class of work becomes delegable. When you find yourself re-teaching the same discipline to every fresh agent, package it: the knowledge it needs plus the decision procedure for applying it, triggered by the work in front of it. A method that lives in memory is the first thing velocity drops. (The Skills.)
  • - Treat the pile of controls as a system in its own right. Every control can be correct and the system of controls still be wrong. Keep three views over one control set: a catalogue of what exists, a collision graph of which two make incompatible demands on a shared resource, and a coverage census of which target has nothing watching it at all. (When Guardrails Collide.)

4.6.2 The anti-patterns

An anti-pattern is a move that looks reasonable and fails predictably. Learn its shape so you catch yourself making it.

  • - The teetering tower. Governance whose maintenance costs more attention than the failures it prevents. Three symptoms: agents spend more time servicing controls than doing product work; false positives dominate, the checks crying wolf more than they catch; the controls guard failures that are both low-cost and low-frequency. When you see one, price the upkeep and size it down. (The Skills.)
  • - All sensors, no constraints. The purely organizational answer to an unreliable worker wraps it in process: a review, an approval, an evidence trail, a sign-off. Every one of those is a sensor that inspects the output after the fact. It can raise the odds and shrink the blast radius, yet it never removes a failure class, because it watches the action space instead of scoping it. (The Governed Environment.)
  • - Trusting words to hold. Tell an agent "always follow this template" and it will agree and then not reliably do it, because an instruction is a probability flip: a prompt raises the odds, it does not settle them. Guidance aims a reasoner; it cannot block one, and it rots. Determinize the instruction into a condition the environment enforces. (The Governed Environment.)
  • - Promoting a control before the tree is clean. Flip a check to blocking while findings remain and you break every in-flight agent's commit at once. The promotion is safe only in one order: advisory first, drained to zero, then blocking. (Brownfield.)
  • - Trusting "done" as a fact. An agent reporting a task complete is describing its intent, not the state of your repository, and the two drift apart constantly — a sibling change broke a test, a marker rotted, the thing it "verified" quietly routed through a fallback. Re-run the gates yourself, at HEAD, and let a fact answer where a claim was offered. (The Skills.)
  • - Expecting a derived model to catch an unspecified absence. A missing authorization check has no failing test by definition — if a test caught it, the check was specified. A model read off the code records the missing check as correctly absent, and the drift gate agrees with the bug. A mirror cannot see what was never specified; some goals stay a human job, and naming that residual honestly is what makes the mechanized core credible. (The Governed Environment.)
  • - Fixing the failing input instead of the class. When a generator surfaces a crash, patching the exact bytes leaves every neighbouring input that would break the same way. Trace the failure back to the point in the specification the input violated and fix that, so the fix covers every input the format allows, not the single seed that tripped it. (Validation with Agents.)
  • - Steering by a surface number. A whole-project cloud bill tells you to pay the invoice and nothing about what to change; "the suite covers 87% of lines" reports and does not name which untested code matters. A metric earns its place only when it drives a decision, and the surface number usually cannot. (Metrics.)
  • - Growing controls only where it last hurt. Convert failures reactively and the control estate grows toward the targets that already failed, while a target that has never bitten draws nothing. The reactive discipline, left to itself, leaves whole targets structurally un-watched — a blind spot no single control's code reveals. Audit the balance proactively across every target. (When Guardrails Collide.)

4.6.3 The heuristics

A heuristic is a judgment rule for the calls no pattern makes for you.

  • - Size by cost times frequency. How hard a mechanism a failure earns turns on two factors multiplied: how much the failure costs, times how often it happens. Cheap-and-rare you leave to judgment. Cheap-and-frequent earns a lint or script. In the costly column, prefer architectural prevention — make the mistake impossible — with a gate as the immediate floor. The costly-and-frequent corner earns both. Escalate one tier when the failure is hard to detect, hard to reverse, or legally intolerable. (Brownfield.)
  • - Climb for a question, not the view. Take the next rung of representation when a question you keep re-answering by hand would stop recurring once the model could answer it for you. Do not build a complete executable model for its own sake; strengthen the representation only where a real reasoning problem pays for the rung. (Brownfield.)
  • - Know whether you are minting a soft mechanism or a hard one. A soft mechanism — a brief, a house rule, a structured model that aims the agent's reasoning — raises the odds but cannot block, and it rots. A hard one — a lint, a gate, a typed seam — holds the line regardless of whether the agent cooperates. Never claim a mechanism is enforced when you have only recommended it. (The Skills.)
  • - Convert, don't just repair. When a failure smells class-level, do not only patch the instance — build the durable mechanism that kills the class. Today's audit finding, a thing you noticed by reading, is tomorrow's lint, a thing the machine notices for you. A bug in more than one file means "fix the sites and add the check," not "fix the sites and hope." (The Skills, Governance Conversion.)
  • - Let recurrence be the trigger. A failure seen twice — sometimes once, if it was bad enough — is the clue that you are either failing to detect the problem, so you need a sensor, or failing to prevent it, so you need a constraint. Recurrence is the signal that a mechanism is owed. (Governance Conversion.)
  • - Measure one level deeper. Ask what decision the measurement must drive, and measure the level just below the surface number so the data can act rather than merely report. Split the cloud bill by service and the dominant one names your first target; measure coverage against the model's named invariants and it names the gap instead of hiding it in a percentage. (Metrics.)
  • - Define correctness first; it fixes the abstraction level. Correctness is not one thing — it means one thing for security, another for semantics, another for privacy — and the definition tells you the grain you need. Write down what correct even means, then pick the coarsest model that can express it and the cheapest analysis that enforces it. (Brownfield.)
  • - Harvest real producers before hand-rolling a generator. A grammar you write yourself covers only the dialects you thought to encode. The format's independent producers have already generated the legal-but-unusual space for you, a breadth no single authored grammar reaches. Reach for a from-scratch generator only where no real producer exists. (Validation with Agents.)
  • - Know the healthy baseline before you chase a failure. State what "normal" looks like for each lifecycle first. Most sessions are steady-state, and you cannot recognize a break until you can name the shape it broke from. (The Skills.)

4.6.4 The checklists

A checklist turns a pattern into something you run on Monday.

Starting a brownfield migration

The three migration approaches — top-down from intent, bottom-up from code, and lint-cover-then-induce — run as one repeating loop, short enough to keep on a card (Brownfield):

  1. Find the stable abstractions — the spine your quality case actually rests on, not every function.
  2. Model only those — top-down from intent, bottom-up from code, meeting at the grain the property lives at.
  3. Drift-gate the model — a check that fails when code and model disagree, worn in audit-only, then drained, then blocking.
  4. Measure the orphans — walk each test to the code it exercises and ask whether that code traces to any model node; each orphan cluster is the next model you owe.
  5. Repeat — the metric hands you the next stable abstraction, and the loop turns again.

Minting a new mechanism

When a failure recurs and a mechanism is owed, run the reflexes before you build (The Skills, The Governed Environment):

  • Name the failure class, not the instance — if you cannot name the recurring failure, it is not a mechanism yet.
  • Ask prevent or catch — a constraint that scopes the action away, or a sensor that catches the drift.
  • Ask soft or hard — a mechanism that aims the agent, or one that holds regardless.
  • Size it by cost times frequency; reach for architecture before a control, and price the mechanism's own upkeep before you build it.
  • Check with the engineer on any wall — every wall you raise also constrains the agent, so place it with care.

Cross how much a failure costs against how often it happens; each cell names the smallest change that still closes the class (Brownfield). Table 4.6-1

Choosing a validation strategy

Read the signal in the code under test and reach for the technique whose oracle fits (Validation with Agents):

  • A stated law over structured inputs — a round-trip, a content-preservation guarantee, an ordering — reaches for a property test; the law is the oracle you can already write down.
  • An untrusted-bytes boundary with a never-crash contract and no per-input law worth stating reaches for a coverage-guided fuzzer; fix its findings to the stable specification point, not the seed.
  • A structured model with a declared legal-outcome set or invariant reaches for fuzz plus the model — point wild inputs at the model's surface and judge against its declared classes; where a real third-party producer exists, let its dialect be the corpus.
  • A concurrency invariant reaches for a state-model search — a property test for a local state predicate, a systematic or bounded interleaving search for a temporal one.

Auditing your governance estate

Turn the method on the governance system itself, keeping three views over the same set of controls (When Guardrails Collide):

  • The catalogue — what controls exist, one row each.
  • The collision graph — which two controls make incompatible demands on a shared resource; route the mechanically decidable edges to a sensor and the semantic ones to a human.
  • The coverage census — bin every control by the target it guards, and surface the target with nothing watching it, or with only soft aims and no hard hold.

These are the moves, without the case that produced them. The method ran end to end across this Part — the brownfield recipe, the skills that carry it, the generative checks that hold the result, and the conversion loop that turns each failure into the next mechanism. None of it came from a whiteboard; every move was forced by one real system under a real deadline. The next Part tells that system's story from the beginning.
