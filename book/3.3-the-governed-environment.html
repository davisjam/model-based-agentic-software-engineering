Part 3 — The Governed Engineering Environment  ::  Chapter 16

3.3 The Governed Environment: Ex-Ante and Ex-Post

One rule runs this whole chapter: an ex-post failure becomes an ex-ante control when judgment classifies the recurrence and encodes it in the environment. That is the move that turns a mistake you caught once into a check the environment enforces on every agent after. You cannot write a trustworthy environment down in advance; the question is how trust grows from the failures no specification predicted.

It has two halves, because governance does. Some things you know in advance and write into a specification up front. But real engineering rarely works that way — you discover what you are building by building part of it. So a governed environment carries what you can decide before you start and what you can only learn along the way, and the promotion rule is the hinge between them.

That an agentic team needs governance of its own is beginning to draw formal treatment. Recent academic work proposes a domain-specific language for governance policies across mixed human-agent projects 11. Adem Ait et al., “Towards Automated Governance: A DSL for Human-Agent Collaboration in Software Projects,” in “Proceedings of the 40th IEEE/ACM International Conference on Automated Software Engineering (ASE), New Ideas and Emerging Results Track,” special issue, Proceedings of the 40th IEEE/ACM International Conference on Automated Software Engineering (ASE), New Ideas and Emerging Results Track, 2025, https://arxiv.org/abs/2510.14465.. MAGE converges with that direction at a different grain: not a single policy language, but a repertoire of governance mechanisms drawn from a production case.

3.3.1 Ex-ante: everything you can decide up front

Some things you genuinely know from the beginning, and you should write every one of them down. This is specification-driven development, and where you can do it, you should. A coding style guide is the everyday example — Google has one, Airbnb has one — full of rules like "every function carries a comment" or "we never call exec outside this one approved place." Give the agent those rules, then write deterministic checks for them, or better, have the agent write the checker. If a program's output has a required format, the checker that confirms it is cheap and the agent implements it. Deciding the right policy and maintaining its fit are not cheap — a cost this Part later proves.

3.3.2 Ex-post: everything you learn by building

But you will not know everything, and pretending otherwise is the mistake. You will discover that performance is a problem and you have no performance model, that a model version has a tic — every LLM's fondness for the em-dash is the running joke — and that the tics move when you upgrade. So you build governance ex-post: after the fact, iteratively, strapping on new mechanisms as failures reveal themselves and the software's real properties emerge. You define what you can up front, and stay willing to discover the rest.

The honest version of the loop is less tidy than the ex-ante story makes it sound. You set up the governance you can imagine in advance, launch the work, and then watch it burn and try to fix it. The failures you did not foresee teach you which mechanism to build next. Ex-post governance is not a fallback for a weak plan; it is where most of the real mechanisms come from, because most of the real failures are the ones no specification predicted.

The engine of the whole discipline is what you do to hold a quality goal: you set up a mechanism that keeps it. You place some mechanisms up front, from what you know about the domain, and add more in response to a recurring or consequential failure — a mistake caught in yesterday's manual audit becomes today's automatic check, enforced on every agent thereafter instead of re-caught by inspection. That conversion runs the printer loop's own shape (introduced in Loops and Models), escalated: when the loop keeps hitting one wall, judgment turns the failure class into a durable mechanism (Figure 3.3-1). The payoff is an environment left more capable of absorbing the next change. Conversions accrue — the positive dual of churn, a dynamic Part 6 names and bounds.

None of this is new as an instinct. Manufacturing stops the line at a defect and reshapes the work so it cannot recur; resilience engineering treats an incident as a signal about the system, not a verdict on the operator 22. E. Hollnagel et al., Resilience Engineering: Concepts and Precepts (Ashgate, 2006).; site reliability practice turns each outage into a blameless postmortem whose action items become durable work 33. B. Beyer et al., Site Reliability Engineering: How Google Runs Production Systems (O'Reilly Media, 2016).; Shingo built mistake-proofing into the fixture itself 44. Shigeo Shingo, Zero Quality Control: Source Inspection and the Poka-Yoke System, trans. Andrew P. Dillon (Productivity Press, 1986).. MAGE inherits that family. The changed ingredient is velocity: the fleet surfaces structural gaps fast enough that the environment accumulates reliability one class at a time.

3.3.3 The controls accumulate

Run the promotion rule for a season and the environment fills with controls — nearly all discovered ex-post, the obligations no up-front specification would have named. The case project shows the shape: Figure 3.3-2 counts its two hardest control surfaces — project-specific lint files and gate scripts — at the same four windows the build passed through.

The curve is the accumulation, not its cause. Those lint files carry 993 registered lint specs at the final window, each a policy the environment now enforces on every agent. What the count cannot separate is which controls a failure drove and which the domain suggested up front — the two modes interleave by design, and no commit trail cleanly splits them. But the discipline that converts a failure is documented and named: a paired fix-and-lint tag marks the commits that ship a code fix beside the check that forbids its recurrence, appearing in 208 commits, and 27 lints name a specific dated incident in their own text, spot-checked as genuine conversions. Read the curve as a documented, growing discipline, then — not a measured causal rate. For the data, see The Governed Environment: Ex-Ante and Ex-Post →

Conventional wisdom offers a rough rule for how large the environment should grow — about one line of tests per line of production — and The timeline and the work measures the ratio MAGE reaches against it. Either way, a mechanism takes one of two forms, and the difference between them is the difference between a firewall and a smoke detector.

3.3.4 Constraints and sensors

A mechanism is one of two moves — prevent the mistake, or catch it — and Figure 3.3-3 draws the split.

First, the argument for reaching for a mechanism at all. Words alone do not hold. Tell the agent "make sure the briefs always follow this template" and it will say, "Sure, boss" — and then not reliably do it, because it is a probability flip. A prompt raises the odds; it does not settle them. But you can determinize that: before the agent launches, confirm every required part of the template is present, and refuse the launch when it is not. The soft instruction becomes a hard gate. That move — from a probability you nudge to a condition you enforce — splits into the two forms below.

A sensor detects drift. It lets the mistake happen and catches it after the fact, and because it fires after, it fails the loop iteration: the agent runs again to fix what the sensor caught. Your test suite in CI is a sensor, and so are your lints. It would be better if the model never wrote the bug; but if it does, the sensor catches it before the code ships. The cost of a sensor is iterations — detect, fail, re-iterate — and that cost is the reason you do not reach for one first.

A sensor is only as good as the signal it can read. Observability is the property that a running system exposes enough signal to explain what it did and catch what went wrong. It is the wiring under every sensor: the event a gate fires on, the log a checker reads, the trace that turns "the build failed" into "the build failed here, for this reason." Build the observability first and the sensor has something to watch; skip it and it stares at a blank wall.

A constraint prevents drift. Where a sensor detects an instance of the mistake after the fact, a constraint makes the whole class impossible: it scopes the agent's action space within the iteration, so the wrong move is never available to pick. The cleanest example is types. Suppose the agent represents a state with bare strings. Being a language model underneath, it will cheerfully reach for a synonym next time, and the synonym silently fails to match — you learn that an iteration later, when the test suite crashes. Tell it to use an enumeration instead, and the failure mode evaporates: it can no longer invent an unlisted value, and if it tries, the compiler rejects it on the spot. The enum forbids the bug rather than watching for it, and no iteration is spent catching it — which is why the catalogue leans so hard on structured models and closed enumerations over free-form strings.

Learn more about this governance mechanism: closed enumerations over free-form strings.

A footnote on control engineering. Constraint and sensor are the working terms of control engineering. A governed plant — a reactor, an autopilot — carries constraints on the inputs and states it may reach and sensors on the outputs it produces, so the controller reads the error and corrects the next cycle. A fleet of probabilistic machines is a plant you cannot run open-loop; the governed environment is the loop you close around it. Engineers have run unruly physical processes this way for a century.

Learn more: Nancy Leveson's Engineering a Safer World 55. Nancy G. Leveson, Engineering a Safer World: Systems Thinking Applied to Safety (MIT Press, 2011). applies the same systems view to safety engineering.

A footnote on closing the loop in the wild. Ericsson's EIAP closed loop pairs intent-based operation over curated, real-time network state with a controlled actuation surface, and decouples the model lifecycle from the application lifecycle: closed-loop autonomy needs both a state representation and a bounded actuation surface, or it is not operational autonomy 66. Ericsson, “Intelligent Core Automation with EIAP and Capps,” Ericsson, 2026, https://www.ericsson.com/en/blog/2026/6/intelligent-core-automation-with-eiap-and-capps..

Two axes cross here, and it pays to hold them apart. A mechanism has a form — soft, it aims the agent, or hard, it holds regardless — and a move — a constraint, it prevents, or a sensor, it detects. The two are independent: a constraint can be soft (a structured model that aims the agent's reasoning) or hard (an enum the compiler enforces), and a sensor can be soft (a convention that reminds) or hard (a lint that blocks). Constraint-versus-sensor is what the mechanism does; soft-versus-hard is how firmly. Figure 3.3-4 lays the two axes out as a grid.

Most real mechanisms are a package across both axes. A structured model is a soft constraint on the agent's reasoning — it aims the agent at the right shape without forcing it — shipped with hard sensors, the lints and drift-parity gates that catch what it only aims at. The definition-of-done review is the same shape: a runbook that constrains the steps, wrapped in sensors that flag a drifted one. So name the package and tag its primary move: prefer a constraint where you can build one, add a sensor for the drift you cannot scope away. ("Architecture" is the design activity that builds constraints — not a third kind of thing.)

Seen from the outside, this is what a purely organizational answer leaves on the table. Faced with an unreliable worker, the instinct is to wrap it in process: a review, an approval, an evidence trail, a sign-off. Every one of those is a sensor — each lets the mistake happen and inspects the output afterward. A discipline built only of sensors can raise the odds and shrink the blast radius, yet it never removes a failure class, because it watches the action space instead of scoping it. The constraint is the move that answer does not have: it works ex-ante, inside the iteration, so the wrong move is never available to pick — reliability by construction, not inspection after the fact.

A footnote on the factory floor. The Engineer's Seat introduced Toyota's names for these two moves: the constraint is poka-yoke, and the sensor's fail-the-iteration reflex is jidoka. The lesson Toyota drew is the one this section just argued — inspection at the end of the line cannot build quality in. A fleet of agents is a production line for code, and it relearns the same economics.

Two axes, one bounded term

One boundary before moving on, because without it the word swells. Prompts, documents, lints, tests, metrics, hooks, models — everything in the environment starts to look like "a governance mechanism," and a term that covers everything governs nothing. Bound it:

Governance mechanism. A repeatable environmental structure that encodes an engineering policy and either constrains an action, detects a violation, requires evidence, or controls admission.

The clause list is not one flat set of four peers. It is two questions crossing. Constraint and sensor classify _how_ a mechanism treats a failure — prevent it, or catch it — the catalogue's Move axis, three-valued: constraint, sensor, or _package_ for a bundle carrying both. Evidence and admission classify _where_ a mechanism acts — at the loop's closing door, not at the action. An evidence mechanism demands the change carry its proof: a provenance stamp, a re-derived test result, a completion re-checked rather than self-reported. An admission mechanism decides whether the result may advance at all — the admission rule of the engineered loop (1.3), holding the last door. Both are still built out of constraints and sensors; they earn their names from their position in the loop. So the earlier split is the whole Move axis, and evidence and admission are a second, positional cut across it.

The two compose into how a loop earns the right to advance: cheap checks run early and bind their result to an exact tree, so a later, more expensive stage checks that binding rather than trusts a report, and the definition of done recomputes the full evidence at close instead of reading a marker. Cheap evidence early, full re-derivation late, never a trusted self-report.

The definition also settles a boundary this book leans on. A model file is policy. It becomes a mechanism only when some agent, tool, or gate consumes it — injected into an agent's context, it is the soft constraint met earlier; read by a lint, a gate, or a generator, it is a hard sensor. So a structured model can be a soft constraint and still be inert on disk, because "soft constraint" already names the consuming step the model alone does not perform. The model supplies the policy; the consumption supplies the holding.

Before the synthesis, watch the conversion run outside one project — the failure that motivates it is mine, the pattern that answers it is not.

Field note — the pipeline that ran open-loop. One of our document-remediation pipelines had every mark of a clean design: a single driver, one phase taxonomy, a typed contract on every pass, a startup sort that checked the order. It had drifted anyway. The declared order and the actual order had come apart at seven places, and the seven were not scattered — they sat exactly where the accessibility-AI loop churned hardest, each new trick wired straight into the run path, skipping the registry. The registry was a constraint that held for the passes routed through it; the inline additions routed around it, and my one guard only ever looked at registered passes. The repair was the missing sensor: a parity check that compares the passes that actually run against the declared graph and fails when an unregistered one appears. That is the conversion in miniature — a failure I could not afford to catch by hand became a check the environment now runs on every build.

Worked Examples

Docker. Docker's exploratory agents filed an issue for every anomaly they found, and the humans reading those issues stopped listening. Rather than re-tune the prompt, the team routed every discovering skill through a project-manager that deduplicates and confirms before a report is filed, so the noisy sensor became a governed one. A parallel miss — self-evaluation kept passing its own work — became a rule that a separate reviewer grades every change, because generation is not evaluation.

Shopify. Shopify treats each recurring failure as a reason to change the environment, not to re-instruct the agent. Private sessions taught no one twice, so the coding agent was made public-channel-only and every session became a searchable artifact mined into skills and defaults; free-roaming generation over millions of lines proved unreliable and was replaced by declarative, reproducible workflows. The converted artifact is often soft — a skill, a default — yet the loop holds: a failure seen twice becomes a fixture the next agent inherits.

Zenseact. Zenseact's agents do knowledge work over the company's own systems, and their sharpest failure is a routing miss: the skill a task needs exists, but the retrieval layer fails to surface it. The miss is detected and recorded as telemetry, an automated pipeline analyzes it, and the disclosure mechanism is updated so later agents get the right context. The failure is diagnosed as an environmental one — the environment failed to present the right representation — and the repair targets the environment, not the model.

DocAble. DocAble runs the conversion as a standing discipline. A defect caught once in a manual audit is encoded the same day as an automatic check the environment enforces on every later agent, and the two commits — the fix and the lint that forbids its recurrence — ship together under one paired tag. That tag marks two hundred-odd commits, and the control substrate it grew is the curve shown earlier: from zero to hundreds of registered checks, each one a failure that will not return.

Takeaway. The shared move is governance conversion: a failure caught once is promoted into a standing mechanism the environment enforces on every later agent, so the correction outlives the incident that taught it.

What it adds up to

Step back and this is what you are really doing: describing policies for how the engineering work should proceed, and letting those policies produce the rules of the road the agents operate within. That combination — determinize what you can, then convert every recurring surprise into a constraint or a sensor — is the governed engineering environment.

One frame ties this chapter to the last Part. A model extends the reasoning horizon by externalizing knowledge: the fleet reasons through a compact picture instead of rebuilding the whole system in working state. A governed environment extends the same horizon by externalizing judgment: the engineer decides once that some invariant must hold, encodes it as a constraint or a sensor, and the environment carries that obligation afterward. Neither agent nor engineer keeps "don't break invariant X" in working memory, because the ground they stand on keeps it. Modeling externalizes knowledge and alignment externalizes judgment; both buy back the same scarce thing — how much of a system a bounded reasoner can hold coherent at once.

3.3.5 The residual: goals no mechanism reaches

The synthesis reads as if it settles everything. It does not: some goals split into neither. No cheap sensor can see the failure and no constraint can scope it away, because the failure is an absence nobody specified, and you cannot watch for the violation of a rule no one wrote or forbid an action the design never mentioned.

Security remediation is the clean case. A missing authorization check has no failing test — by definition. If a test caught it, the check was specified; if it was specified, it would not be missing. The gap is invisible because nothing ever named it. So the goal stays a human job: someone has to look at the system and know the check should be there. Call this the residual — the third outcome beside prevent and detect. Which of your goals land in it sets your real throughput ceiling: the mechanized goals run at fleet speed, and these run at yours.

This is not the soft end of the soft-versus-hard axis you just met. A soft mechanism — a structured model that aims the agent, a convention that reminds — is still a mechanism: a named artifact that raises the odds and that you can point to. The residual has none. There is nothing to name, nothing to tag as a constraint or a sensor, nothing to add to the census. It is the complement of the two moves, not a third value on the axis.

Naming the residual costs the method nothing; a method that claims to mechanize everything is the one to distrust. The residual is the honest edge that makes the mechanized core credible — it says plainly what the catalogue does not cover, and that admission is what lets you trust the coverage it does claim.

Nor is the residual a fixed wall. You can sometimes pull a goal out of it by authoring the missing spec. The same absence that defeats a sensor defeats a derived model: a model read off the code records the missing check as correctly absent, and the drift gate agrees with the bug — a mirror cannot see what was never specified (the same absence, restated for models, 2.2). A journey test that asserts only "the flow ran" greens while the user's task is broken, until a human authors the terminal task-closure assertion that says what done means (3.6). Everything in this chapter governed the code the fleet writes. But the fleet does not only write code — it operates a system, and the operating judgment an agent lacks is its own residual; the next chapter captures as much of it as a runbook can hold.
