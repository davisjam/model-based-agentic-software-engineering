# The MAGE Workflow

<!-- point: mage-is-one-recurring-cycle-not-a-catalogue-of-techniques | MAGE is one recurring cycle, not a catalogue of isolated techniques. | terms: thesis-modeling, thesis-alignment -->
The previous Parts introduced the ideas one at a time. This Part joins them into an
engineering method — and a method is something you run, not something you read. MAGE is not a
catalogue of isolated techniques; it is one recurring cycle that every task turns through.
Modeling makes intent explicit, Alignment gives that intent authority, and the failures the
work reveals feed back into both — so each pass begins from a stronger position than the last.

<!-- thesisbox -->
> ### THE MAGE CYCLE
>
> Model the intent. Give that intent authority. Convert recurring failures into engineering capital.
>
> **Repeat.**

<!-- point: the-workflow-is-a-loop-you-run-not-a-checklist-you-finish | The workflow is a loop you run, not a checklist you finish. | terms: thesis-modeling, thesis-alignment -->
Suppose you are beginning a new engineering effort. Not a legacy estate — a clean start, a
prototype, a company that shipped its first commit last week. What does MAGE actually have you
*do* on Monday morning? This chapter answers that, walking the cycle one turn at a time before
the rest of the Part puts each move to work in earnest. The loop is the same whether you are
migrating a hundred-thousand-line tangle or building on a blank page; only the starting rung
differs. A brownfield estate starts you low on the capability ladder and asks you to climb from
where you stand. Greenfield lets you start higher and stay ahead of the mess. Either way you
run the same loop, and every turn of it leaves the environment more capable than before.

## The loop, one turn at a time

<!-- point: a-turn-begins-with-a-need-named-plainly | A turn begins with a need, named plainly. | terms: thesis-modeling -->
**Need.** A turn begins with something you want to be true — a feature to ship, a property to
guarantee, a class of bug to end. Name it plainly, because the name is what everything
downstream binds to. The need is not "write this function"; it is the smaller, sharper claim
underneath — *this input yields that output*, *this invariant holds across every path*, *this
mistake can never ship again*. Most of the method is disciplined about answering one question:
what is the cheapest representation that makes this need checkable?

<!-- point: model-the-need-into-something-an-agent-can-reason-through | Model the need into a representation an agent can reason through. | terms: thesis-modeling, governed-environment -->
**Model.** Turn the need into an explicit model — a representation of the system's intent and
structure that an agent can reason through, rather than intent left implicit in a few people's
heads. This is the Modeling Thesis, the first move of every turn: make the thing you care about
legible to a machine before you ask a machine to change it. You do not start by building a
complete executable model. You start at the lowest rung that pays and strengthen the
representation only when a recurring question earns the next one. On a brownfield estate the
model you already own is the drifted wiki nobody quite trusts;
[Brownfield](4.2-brownfield.html) is the whole chapter on climbing from there. On a clean start
the model is whatever you sketch first — a data-flow diagram, a typed contract, a property — and
you refine it against the code as the code appears.

<!-- point: the-fleet-does-the-implementation-against-the-model | The fleet writes the implementation against the model. | terms: thesis-modeling, governed-environment -->
**Agent work.** Now the fleet writes the code. The model is what makes that delegable: an agent
briefed with the represented intent produces work aimed at the need instead of vibe-coding
toward a plausible shape. The discipline of *how* you package the method so a fresh agent
applies it on reflex — the reasoning it walks, the checks it runs, the context it pulls — is
itself an engineered artifact. [The Skills](4.3-the-skills.html) shows the three the companion
repository ships, and the portable architecture behind them: a body of knowledge plus a
decision procedure an agent triggers and follows.

<!-- point: validation-re-checks-the-work-against-the-model-automatically | Validation re-checks the work against the model, automatically and forever. | terms: thesis-alignment, generative-validation -->
**Validation.** The environment now checks the work against the model — and keeps checking it,
on every later change, without anyone remembering to. This is the Alignment Thesis: represented
intent becomes authority the environment enforces, not a one-time review you trust and forget.
The strongest form of the check does not merely reproduce a known-good dot; it generates
evidence built to *falsify* the model's claim and lets through only what survives the search.
[Validation with Agents](4.4-generative-validation.html) draws that family — property tests,
fuzzing, and the synthesis of fuzzing with a structured model — as the two theses standing in
one place.

<!-- point: failures-are-the-agenda-not-an-interruption | Failure is the agenda, not an interruption. | terms: governance-conversion -->
**Failure.** The checks will catch things, and some things will slip past them and come back.
This is not the loop breaking; it is the loop working. A contradiction between the model and the
code means exactly one of three things — the model is wrong, the model is at the wrong grain, or
the code has a bug — and every one of them is a real finding. The failures the environment caught
while you slept are tomorrow's agenda, not an interruption to it.

<!-- point: a-recurring-failure-earns-a-durable-mechanism | The second time a failure recurs, it earns a durable mechanism. | terms: governance-conversion, make-lint-blocking -->
**Governance conversion.** Here the cycle closes and compounds. When a failure recurs, you do
not just fix the instance — you convert the *class* into a mechanism the environment applies for
you, so a later agent meets the check instead of rediscovering the failure. A recurring
rediscovery becomes a lint; a costly-and-frequent mistake becomes a structured model that makes
it impossible; a convention that must hold becomes a blocking gate. The size of the mechanism is
set by how much the failure costs times how often it happens.
[Governance Conversion](4.5-governance-conversion.html) is the method for that move — how a
recurrence is recognized, sized, and mechanized, and when a soft convention that aims earns
promotion to a hard control that holds.

<!-- point: each-turn-leaves-the-environment-more-capable-than-before | Each turn leaves the environment more capable than the last. | terms: thesis-modeling, thesis-alignment, governance-conversion -->
**Repeat.** Then the loop turns again, from firmer ground. Models grow richer, mechanisms grow
stronger, and the environment accumulates engineering capital instead of paying the same
reasoning costs over and over. Each day's judgment becomes the next day's infrastructure. That
compounding is the point of running the loop rather than reaching for the moves ad hoc: a fix
made once holds for every agent that follows, and the cost of the next change falls because the
last one left a mechanism behind.

## The daily practice

<!-- point: the-loop-seen-from-the-desk-is-a-daily-rhythm | Seen from the desk, the loop is a daily rhythm. | terms: governance-conversion, thesis-modeling -->
Put end to end, the cycle has a daily shape. You start the day by reading what broke — the
failures the environment caught while you slept are the agenda. You spend the middle of it
modeling: turning the spine of whatever you are building into something an agent can reason
through. You end it by converting — the failure that recurred today earns its mechanism before
tomorrow, so it never recurs again. Do that on a loop and the environment compounds: each day's
judgment becomes the next day's infrastructure. The operator's version of this rhythm — the
morning questions and the between-sessions reflex that fires them automatically — is the
[Daily Review](appendix-d-daily-review.html) card.

<!-- point: the-loop-is-not-tied-to-one-product | The loop is not tied to one product. | terms: governed-environment -->
The method is not tied to one product, and it did not come from a whiteboard. Every move in the
cycle was forced by real systems under real deadlines — the one deep case this book induces from,
and the industry teams that reached the same moves independently under other names. Once you can
see the loop, you can ask which real environment already runs a version of it.
[The Field Guide](4.6-the-field-guide.html) tours six of them — Siemens, Spotify, Shopify,
Docker, Cloudflare, Zenseact — so you can find the one that looks like the system you already
own and take the practice that fits.
