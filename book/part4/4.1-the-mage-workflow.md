# The MAGE Workflow

<!-- point: mage-is-one-recurring-cycle-not-a-catalogue-of-techniques | MAGE is one recurring cycle, not a catalogue of isolated techniques. | terms: thesis-modeling, thesis-alignment -->
The previous Parts introduced the ideas one at a time. This Part joins them into an
engineering method — and a method is something you run, not something you read. MAGE is not a
catalogue of isolated techniques; it is one recurring cycle that every task turns through.
Modeling makes intent explicit, Alignment gives that intent authority, and the failures the
work reveals feed back into both — so each pass begins from a stronger position than the last.

<!-- point: parts-ii-iii-taught-nouns-this-table-says-why-they-cohere | Parts II and III taught the nouns; this table says why they belong together. | terms: thesis-modeling, thesis-alignment -->
Parts II and III each took one property of the substrate and built a response to it — a
model here, a mechanism there. Read end to end, that can look like a list of techniques. It
is not. Every response in the last two Parts traces back to a handful of substrate
properties, and each of those properties routes to exactly one step of the method this
chapter runs. [ref:substrate-landscape] says why the pieces belong together, before this
chapter turns them into verbs.

Three verbs carry most of the table's weight — Model, Align, Convert — and they are exactly

*Bootstrap* is the harder case, when nothing has been modeled yet and the loop has to start

environment has run long enough to have a lifecycle worth watching —
[Lifecycles and Runbooks](4.5-lifecycles-and-runbooks.html) is that machinery. None of the
seven rows is new; each restates a property Part II or Part III already earned the hard way.
What is new is the column that says which verb of the method each one becomes.

<!-- thesisbox -->
> ### THE MAGE CYCLE
>
> Model the intent. Give that intent authority. Convert recurring failures into engineering capital.
>
> **Repeat.**

<!-- point: the-workflow-is-a-loop-you-run-not-a-checklist-you-finish | The workflow is a loop you run, not a checklist you finish. | terms: thesis-modeling, thesis-alignment -->
Suppose you are beginning a new engineering effort. Not a legacy estate — a clean start, a
prototype, a company that shipped its first commit last week. What does MAGE actually have you
*do* on Monday morning? This chapter answers that, walking the cycle one turn at a time before
the rest of the Part puts each move to work in earnest. The loop is the same whether you are
migrating a hundred-thousand-line tangle or building on a blank page; only the starting rung
differs. A brownfield estate starts you low on the capability ladder and asks you to climb from
where you stand. Greenfield lets you start higher and stay ahead of the mess. Either way you
run the same loop, and every turn of it leaves the environment more capable than before.

## The loop, one turn at a time

<!-- point: a-turn-begins-with-a-need-named-plainly | A turn begins with a need, named plainly. | terms: thesis-modeling -->
**Need.** A turn begins with something you want to be true — a feature to ship, a property to
guarantee, a class of bug to end. Name it plainly, because the name is what everything
downstream binds to. The need is not "write this function"; it is the smaller, sharper claim
underneath — *this input yields that output*, *this invariant holds across every path*, *this
mistake can never ship again*. Most of the method is disciplined about answering one question:
what is the cheapest representation that makes this need checkable?

<!-- point: model-the-need-into-something-an-agent-can-reason-through | Model the need into a representation an agent can reason through. | terms: thesis-modeling, governed-environment -->
**Model.** Turn the need into an explicit model — a representation of the system's intent and
structure that an agent can reason through, rather than intent left implicit in a few people's
heads. This is the Modeling Thesis, the first move of every turn: make the thing you care about
legible to a machine before you ask a machine to change it. You do not start by building a
complete executable model. You start at the lowest rung that pays and strengthen the
representation only when a recurring question earns the next one. On a brownfield estate the
model you already own is the drifted wiki nobody quite trusts;
[Brownfield](4.2-brownfield.html) is the whole chapter on climbing from there. On a clean start
the model is whatever you sketch first — a data-flow diagram, a typed contract, a property — and
you refine it against the code as the code appears.

<!-- point: the-fleet-does-the-implementation-against-the-model | The fleet writes the implementation against the model. | terms: thesis-modeling, governed-environment -->
**Agent work.** Now the fleet writes the code. The model is what makes that delegable: an agent
briefed with the represented intent produces work aimed at the need instead of vibe-coding
toward a plausible shape. The discipline of *how* you package the method so a fresh agent
applies it on reflex — the reasoning it walks, the checks it runs, the context it pulls — is
itself an engineered artifact. [The Skills](4.4-the-skills.html) shows the three the companion
repository ships, and the portable architecture behind them: a body of knowledge plus a
decision procedure an agent triggers and follows.

<!-- point: validation-re-checks-the-work-against-the-model-automatically | Validation re-checks the work against the model, automatically and forever. | terms: thesis-alignment, generative-validation -->
**Validation.** The environment now checks the work against the model — and keeps checking it,
on every later change, without anyone remembering to. This is the Alignment Thesis: represented
intent becomes authority the environment enforces, not a one-time review you trust and forget.
The strongest form of the check does not merely reproduce a known-good dot; it generates
evidence built to *falsify* the model's claim and lets through only what survives the search.
[Validating Change](4.3-validating-change.html) draws that family — property tests,
fuzzing, and the synthesis of fuzzing with a structured model — as the two theses standing in
one place.

<!-- point: failures-are-the-agenda-not-an-interruption | Failure is the agenda, not an interruption. | terms: governance-conversion -->
**Failure.** The checks will catch things, and some things will slip past them and come back.
This is not the loop breaking; it is the loop working. A contradiction between the model and the
code means exactly one of three things — the model is wrong, the model is at the wrong grain, or
the code has a bug — and every one of them is a real finding. The failures the environment caught
while you slept are tomorrow's agenda, not an interruption to it.

<!-- point: a-recurring-failure-earns-a-durable-mechanism | The second time a failure recurs, it earns a durable mechanism. | terms: governance-conversion, make-lint-blocking -->
**Governance conversion.** Here the cycle closes and compounds. When a failure recurs, you do
not just fix the instance — you convert the *class* into a mechanism the environment applies for
you, so a later agent meets the check instead of rediscovering the failure. A recurring
rediscovery becomes a lint; a costly-and-frequent mistake becomes a structured model that makes
it impossible; a convention that must hold becomes a blocking gate. The size of the mechanism is
set by how much the failure costs times how often it happens.
[Closing the loop](#the-conversion-loop), later in this chapter, is the method for that move — how a
recurrence is recognized, sized, and mechanized, and when a soft convention that aims earns
promotion to a hard control that holds.

<!-- point: each-turn-leaves-the-environment-more-capable-than-before | Each turn leaves the environment more capable than the last. | terms: thesis-modeling, thesis-alignment, governance-conversion -->
**Repeat.** Then the loop turns again, from firmer ground. Models grow richer, mechanisms grow
stronger, and the environment accumulates engineering capital instead of paying the same
reasoning costs over and over. Each day's judgment becomes the next day's infrastructure. That
compounding is the point of running the loop rather than reaching for the moves ad hoc: a fix
made once holds for every agent that follows, and the cost of the next change falls because the
last one left a mechanism behind.

## Closing the loop: governance conversion {#the-conversion-loop}

<!-- section-terms: governance-conversion -->

<!-- point: a-conversion-runs-six-steps | A conversion runs the same six steps. | terms: governance-conversion -->
<!-- index-example: governance-conversion -->
When a check goes red, the reflex the method trains is not to patch the instance but to close the
class it belongs to. The reason is plain: you cannot read every diff a fleet produces, so you
govern the *failures*, not the steps. A conversion is that reflex run on purpose — it turns an
*ex-post* failure into an *ex-ante* mechanism, in the same six steps every time, and naming them
makes the move repeatable rather than lucky.

- **Failure.** A real breach — a check that lied, a silent data loss, a subsystem that looks
  right and is wrong across every file. The raw material is always a concrete thing that went
  wrong, not a hypothetical.
- **Diagnosis.** Trace the breach to the point it actually violated. Not the seed input, not the
  one file — the rule underneath it. A crash traces to the point in the format specification the
  input broke; a bad merge traces to the decision no one made. Diagnose one level below the
  symptom.
- **Generalization.** Ask what *class* this failure belongs to. One stringly-typed module is an
  instance; "the agent reads an under-specified instruction for the cheapest green checkmark" is
  the class. The mechanism you owe defends the class, so you have to name it.
- **Mechanism.** Build the thing that makes the whole class impossible or caught — a type that
  removes the ambiguity, a lint that fires on every recurrence, a gate the agent cannot talk its
  way past, a decision rule you apply by reflex. Prefer the smallest mechanism that closes the
  class.
- **Retirement of the failure class.** The mechanism now runs on every future agent,
  automatically, so the class stops recurring. The failure is not fixed once; it is *retired* —
  removed from the space of things anyone has to rediscover, until the mechanism is revised or
  itself retired.
- **Engineering capital.** What you banked is not the patch. It is a standing constraint or
  sensor that holds the class closed for free, every time the code changes. Each conversion
  compounds: the environment gets a little more governed, and the next failure lands against a
  denser net.

<!-- point: the-recurrence-is-the-information | The recurrence itself is the information. | terms: governance-conversion, velocity-exposes-the-danger -->
The loop reads the same at two scales. At the small grain, a recurring lint smell earns a
blocking lint. At the large grain, an *in-paradigm fix that keeps hitting the same wall* is the
signal to price a paradigm change — the recurrence is evidence about the ceiling, not about the
fix. Both are the same move: a failure that comes back a second time has told you where a
mechanism is owed, and the information was in the *repetition*, not the instance.

<!-- point: some-conversions-bank-judgment-not-machinery | Some conversions bank judgment, not machinery. | terms: governance-conversion -->
Not every conversion ends in a wall the environment enforces. Some bank a decision rule you now
apply by hand — "no destructive default on a conflict," "when the cheap proxy is unsure, describe
anyway." The output of the loop varies with the failure: a type, a lint, a gate, a standing
policy, or a detector for a wrong frame. What does not vary is the discipline of spending the
judgment *once* and encoding it, so neither you nor any later agent re-makes the call at midnight.

## From soft to hard {#from-soft-to-hard}

<!-- section-terms: soft-vs-hard-governance, audits-into-lints -->

<!-- point: soft-aims-hard-holds | Soft governance aims the agent; hard governance holds. | terms: soft-vs-hard-governance -->
<!-- index-def: soft-vs-hard-governance -->
The mechanisms a conversion produces sort along one axis: soft governance *aims* the agent, hard
governance *holds* regardless of cooperation. A brief, a convention, a note in a doc — these aim;
the agent can still miss or ignore them. A lint, a type, a gate — these hold; the agent cannot
proceed through them uncooperatively. Both belong in a mature environment, and the skill the loop
demands is reading which a given failure has earned.

<!-- point: never-happen-specifies-a-hard-mechanism | "This must never happen" specifies a hard mechanism. | terms: soft-vs-hard-governance -->
The operational question is not what soft and hard *mean*; it is when a failure earns promotion
from guidance to machinery. Not everything earns a wall — a low-cost, rarely-recurring failure
can stay a note. But the moment you catch yourself saying "this must *never* happen," you have
already specified a hard mechanism, and you should build it. A convention that says *never* is a
convention that eventually gets violated at velocity. The cost of the failure, not its
tidiness, decides how far right on the axis it belongs.

<!-- point: the-second-occurrence-earns-a-lint | The second occurrence of a failure earns a lint. | terms: audits-into-lints, governance-conversion -->
<!-- index-def: audits-into-lints -->
The move that makes governance conversion compound is turning audits into lints. The first time a
failure class appears, you inspect for it by hand — an audit, expensive and easy to forget. The
signal that you owe a mechanism is the *second* time. A failure that recurs has earned its
mechanism, and once you build it the same failure is caught on every future agent, automatically,
until the mechanism is revised or retired. Today's audit finding is tomorrow's lint; a bug found
in more than one place is not "fix N files" but "fix N files *and* add the check that keeps file
N+1 from ever having it." That promotion — hand-inspection to standing sensor — is how a governed
environment stops paying attention per instance and starts paying it once per class.

<!-- point: convert-judgment-into-infrastructure-encode-once | Convert judgment into infrastructure; encode each call once. | terms: judgment-into-infrastructure, governance-conversion -->
Run the loop long enough and the pattern behind it shows through: the discipline that pays is the
one that converts judgment into infrastructure. Every decision you make well, you encode once — as
a type, a lint, a gate, a rule — so you never make it again and neither does any agent after you.
That is the whole method compressed to a sentence.

## The daily practice

<!-- point: the-loop-seen-from-the-desk-is-a-daily-rhythm | Seen from the desk, the loop is a daily rhythm. | terms: governance-conversion, thesis-modeling -->
Put end to end, the cycle has a daily shape. You start the day by reading what broke — the
failures the environment caught while you slept are the agenda. You spend the middle of it
modeling: turning the spine of whatever you are building into something an agent can reason
through. You end it by converting — the failure that recurred today earns its mechanism before
tomorrow, so it never recurs again. Do that on a loop and the environment compounds: each day's
judgment becomes the next day's infrastructure. The operator's version of this rhythm — the
morning questions and the between-sessions reflex that fires them automatically — is the
[Daily Operator Review](appendix-d-daily-review.html) card.

<!-- point: kaizen-is-the-manufacturing-name-for-this-daily-loop | Manufacturing named this daily loop first; MAGE runs it on software. | terms: governance-conversion -->
<!-- gloss-only: Jidoka | The Toyota Production System's stop-the-line move: halt the instant a defect appears, so nothing downstream builds on it; the manufacturing lineage of the sensor's fail-the-iteration reflex. -->
<!-- gloss-only: Kaizen | Continuous improvement as the Toyota Production System practices it: every recurring problem becomes a permanent countermeasure; the manufacturing lineage of MAGE's convert-a-failure-into-a-mechanism loop, run daily on the lifecycle. -->
<!-- gloss-only: Poka-yoke | Mistake-proofing, from the Toyota Production System: shape the work so the defect cannot occur (the fixture that refuses a part mounted backwards); the manufacturing lineage of the constraint. -->
<!-- gloss-only: Toyota Production System | The manufacturing quality tradition, also called lean production, that named poka-yoke, jidoka, and kaizen; MAGE's governance mirrors its moves in software. -->
Improving the process itself is engineering too — you optimize the product, and you optimize the
process that makes it. Manufacturing folded that work into the line, and Toyota's production system
named the moves: *poka-yoke*, mistake-proofing that shapes the work so a defect cannot happen;
*jidoka*, stopping the line the instant a defect appears; and *kaizen*, the habit behind both —
every recurring problem engineered out for good. Those name the manufacturing lineage of the moves
this book already runs: the constraint, the sensor, and the conversion loop. Kaizen is the closest
name for MAGE's own method — the improvement loop, run daily on the lifecycle itself, the same
convert-when-it-recurs reflex this chapter turns on.

<!-- point: the-loop-is-not-tied-to-one-product | The loop is not tied to one product. | terms: governed-environment -->
The method is not tied to one product, and it did not come from a whiteboard. Every move in the
cycle was forced by real systems under real deadlines — the one deep case this book induces from,
and the industry teams that reached the same moves independently under other names. Once you can
see the loop, you can ask which real environment already runs a version of it.
Part VI's [MAGE in the Wild](6.6-where-mage-fits.html) sets six of them side by side — Siemens,
Spotify, Shopify, Docker, Cloudflare, Zenseact — reconstructions that show the same moves recurring
under other names. One of them makes the first move of the loop concrete.

<!-- worked-examples: thesis-modeling -->
### Example — Siemens
Siemens is a model-first engineering organization: for decades its engineers have stated intent
against explicit, owned system models — a digital thread that carries a design across mechanical,
electrical, and software domains — instead of leaving it implicit in code and documents. The
consequential decision routes through the model, and a deterministic solver, not a person's
recollection, returns the verdict. The move a software team can copy is that routing — put the
thing you care about into a model you own, then let a deterministic check answer against it.

<!-- takeaway -->
Models-as-working-language is neither exotic nor new; a model-first discipline has run it at
industrial scale for decades. What MAGE adds is carrying that discipline into software a fleet
writes, where the model an agent reasons through is what makes the work checkable at all.
<!-- worked-examples-end -->

## Task sizing {#task-sizing}

<!-- section-terms: sizing-the-leap, transformation -->

<!-- point: size-each-task-to-a-leap-the-fleet-can-check | Size each task to a leap the fleet can check. | terms: sizing-the-leap, transformation -->
<!-- index-def: transformation -->
<!-- index-def: sizing-the-leap -->
<!-- index-def: compounding-failure-probability -->
The unit of work you hand an agent should be large enough to exploit the model's capabilities and
small enough that its result can be meaningfully evaluated. Frame each task as a **transformation** —
an explicit input, an explicit output, and a checkable step between them — and size that step to the
model and to the guarantee you need. Speak at too low a level and you have written the code yourself;
ask for too large a leap and you get back something plausible you cannot check. A stronger model
supports a bigger leap, but task fit and representation often matter more than raw strength: even a
strong model stalls when the task sits far from anything it has seen.

<!-- point: keep-leaps-short-so-per-step-risk-cannot-compound | Keep leaps short so per-step risk cannot compound. | terms: compounding-failure-probability, sizing-the-leap -->
Keep the leaps short, because independent per-step risk compounds. A long, unaudited chain of edits
accumulates error faster than intuition expects, and a failure buried in the middle of one is the
hardest kind to localize. So put a checkable boundary at every seam. Size each transformation small
enough that its result can be inspected as it lands, not gathered up and hoped over at the very end —
a short transformation is not merely less likely to fail; it is a place you can *check*, and the
check is what caps the risk.

<!-- point: docable-sizes-the-leap-down-to-checkable-typed-edits | DocAble sizes the leap down to checkable typed edits. | terms: sizing-the-leap, transformation -->
DocAble sizes this deliberately. The remediation core could ask a strong model for the whole leap —
here is a document, hand back an accessible one. A capable model can sometimes do exactly that. But
the call reasons over the entire document every time, which is slow and expensive, and the result is
unauditable: you cannot see which change it made, or why. So the system sizes the leap down. It
scopes the work to a closed vocabulary of small typed edits — set the alt text on this image, set the
role of this block, reorder these children — the same edit language the interactive editor speaks in
Part V. The agent is asked for one bounded edit at a time. Each call reasons over one scoped task
instead of the whole document, and each edit comes back typed, stamped, and reversible. Same fleet,
same model; a different task size turns an opaque rewrite into a stream of edits you can check.

> Learn more about this governance mechanism: [remediation verbs](appendix-c-remediation-verbs.html).

<!-- point: a-well-sized-transformation-of-the-wrong-shape-still-fails | A well-sized transformation of the wrong shape still fails. | terms: transformation -->
Sizing is only half of it. The transformation also has to be the right *shape* for the task and the
model, and I learned that the expensive way. For two weeks I sized a transformation beautifully and
pointed it at the wrong problem: I pulled a PDF's reading order out of the geometry of its bounding
boxes and handed that geometry to cheap vision models, which are bad at geometry. The model
cheerfully made a doomed shape better and better. A well-sized transformation of the wrong shape is
still the wrong transformation. So the skill has two halves — size the leap, and find the one leap
that fits both your task and your model, then abandon the one that does not.
