# The Field Guide: Which Environment Looks Like Yours?

The method lands differently in every environment. This chapter tours six governed
environments — six teams who reached for the same engineering moves under different
constraints — so you can find the one that looks like your own and take the practice
that fits.

Throughout this Part we step outside DocAble repeatedly to watch the same moves appear
elsewhere: at Siemens, Spotify, Shopify, Docker, Cloudflare, and Zenseact. These are not
endorsements, and they are not benchmarks. They are contrasting implementations, each
lighting up a different region of the design space. None of them is where MAGE came from.
The method was induced from one deep case, DocAble, whose full story waits in Part V; the
six teams here show that its moves port to environments built for other reasons, under
other names.

Read the cards as practitioner reports, not proof. Each is drawn from a public account of
how one organization works, so a silence in a card reflects what the account describes,
not a capability the organization lacks. What earns the tour is the agreement across such
different systems: six starting points, one recurring grammar.

Start with the identities. Each organization in this book teaches one move better than the
rest. Meet them by that move first; the cards below and every later chapter hold to it.

<!-- case-onepager: siemens -->
<!-- label: op-siemens -->
| **Siemens** · embedded / CPS / model-based engineering · *teaches modeling-first engineering* |
|---|
| **Starting point.** Siemens inverts the brownfield. Its agents do not arrive at a codebase to be tamed. They arrive into an engineering culture that spent decades encoding intent, geometry, physics, requirements, and verification into executable models, with source code as one downstream artifact those models generate rather than the source of truth. On the sharpest prototype an engineer states intent in plain words — "validate this part under 200 lb in the Y-direction" — and the agent reads the CAD geometry, sets up the finite-element model, calls the solver, and returns a validated report. |
| **Primary investment.** The model estate itself: SysML and UML, CAD, simulation, bills of materials, digital twins, and a traceable digital thread that links requirements to implementation. Deterministic physics does the mechanized work. Solvers, software-in-the-loop, virtual ECUs, and coverage stand where a lint would stand in a software shop. |
| **MAGE interpretation.** This is the sample's strongest external Modeling case. The model sits upstream of the implementation, code is generated from UML rather than annotated after the fact, and the division of labor is clean: probabilistic semantic reasoning upstream, deterministic physics and verification downstream. Bootstrap is unusually rich, since decades of standards, models, and tooling predate the agent as inherited engineering capital the agent operates the moment it can. |
| **Practice to steal Monday morning.** Ask the deterministic question against a model, not against the code. Where you already own a structured representation — a schema, a state model, a solver — route the agent's judgment through it and let the model decide whether the answer is right, instead of asking an LLM whether the code looks correct. This is what mature engineering already looks like: the agent operates the existing machinery at the abstraction level where engineers make decisions. |
| **Failure if copied blindly.** The sources show engineering-loop feedback in abundance and no failure-to-new-governance loop. The model tells you when a design is wrong, but nothing here converts a recurring agent mistake into a durable new control — governance conversion, MAGE's most distinctive move, is exactly the soft spot. Copy the model-first substrate and you inherit that gap. Most software teams also have no decades-deep model estate to inherit; you build those rungs, you do not find them. |

<!-- case-onepager: spotify-honk -->
<!-- label: op-spotify -->
| **Spotify** · software / large-scale platform · *teaches fleet operations and verification* |
|---|
| **Starting point.** Spotify is the case where the environment came first. For years before autonomous coding agents existed, it standardized its software estate for human engineers and deterministic bots: a catalog that named every service and its owners, fleet-wide tooling that could push one change across thousands of repositories, and an automatic gate that admitted work on evidence. When the agent arrived, Spotify swapped a probabilistic reasoner in for the transformation step and left the surrounding machinery standing. |
| **Primary investment.** A mature platform built ahead of need — the Backstage catalog with dependency and endpoint lineage, standardized stacks, a body of structured standards, verifiers and static linters, and an automerger that admits work on strong evidence. The estate is represented three ways: an architecture model, a body of policy, and the tests that stand in for proof. |
| **MAGE interpretation.** The sample's strongest Alignment instance: verifiers, linters, the pre-merge gate, and the automerger all act on later work with the author gone. Modeling is strong too, since the catalog and its synced diagrams give the agent a real picture of the estate to reason over. Determinization lands the decidable checks on deterministic gates and leaves only the residual semantic judgment to a probabilistic reviewer. |
| **Practice to steal Monday morning.** Build the governed substrate for the workforce you have now, then hand it to the agent almost unchanged. Standardize the estate, model its components and owners, and put targeting, verification, and admission on deterministic rails before any agent shows up — so the agent inherits a ground that admits work on evidence rather than on trust. The environment is prior to the agent, and you can build it first. |
| **Failure if copied blindly.** Spotify runs no generalized drift gate holding a model to the territory, and its second governance-conversion loop is stated as strategy rather than measured as effect; the productivity numbers are self-reported, not a causal test. The head start is the whole point. Copy the outcome without the years of platform investment and there is nothing for the agent to drop into — this story will not rescue a 50,000-line startup with no platform team. |

<!-- case-onepager: shopify -->
<!-- label: op-shopify -->
| **Shopify** · software / commerce platform · *teaches agent-ready environments and organizational learning* |
|---|
| **Starting point.** Meet Shopify through River, an agent you summon from a public Slack channel to read code, run tests, query the data warehouse, and open a pull request. River is public on purpose. A lesson learned in a private session helps no one else, so every session becomes a searchable artifact the company mines into skills and defaults. |
| **Primary investment.** A single shared work surface stood up before the agent as an explicit substrate: a company monorepo, reproducible Nix execution, CI, and merge queues. Above it sits an organizational habit — keep the work visible — so one engineer's experience becomes everyone's. Each new agent is a profile over the shared substrate rather than a platform of its own. |
| **MAGE interpretation.** The corpus's strongest instance of engineering capital. Private learning is made public, free-roaming work is tightened into deterministic workflow steps, and misuse is answered with a rate limit — a repeated failure-to-structure loop, though the artifact it converts to is often soft. Alignment is strong, carried by sandbox policy in profiles and reproducible execution. Modeling stays partial: a broad representation surface with no invariant-bearing system model. |
| **Practice to steal Monday morning.** Make the work visible before you make it automatic. Run agent sessions somewhere searchable, and treat each transcript as raw material — mine the recurring ones into a skill or a default the next agent inherits. Experience compounds only once it is observable; a private session teaches no one, and a shared one becomes capital. |
| **Failure if copied blindly.** No invariant-bearing system model is described and no drift gate holds a model to the territory; the evidence horizon is short and the outcome numbers are self-reported. The capital is soft — skills, conventions, defaults. Copy the publicness without the reproducible substrate underneath and you get searchable chatter, not compounding capability. |

<!-- case-onepager: cloudflare-codex -->
<!-- label: op-cloudflare -->
| **Cloudflare** · software / infrastructure · *teaches policy and governance* |
|---|
| **Starting point.** Cloudflare had a governance problem before it had an agent problem. Nearly a quarter of a million standards violations flagged, some sixteen thousand serious enough to withhold approval, six hundred specifications reviewed across thousands of invocations: those are the numbers of an organization whose accumulated rules outgrew any one engineer's memory. Its answer turned the standards themselves into machine-readable policy that review-time agents retrieve and enforce. |
| **Primary investment.** Codex, a curated corpus of the organization's own RFCs, turned from prose into structured, machine-readable policy. Each requirement carries a stable identity that survives edits to its originating RFC, and an agent pulls only the statements that bear on the change in front of it, the representation compacting from Markdown to filtered JSON. |
| **MAGE interpretation.** A governed environment whose center of gravity is the Alignment Thesis — a decision made once keeps acting on later work with the author no longer present. Mechanically-checkable requirements compile down to custom linters, the deterministic residue; ambiguous ones go to an LLM reviewer at the point of a merge. Authority is allocated, not asserted: agents may withhold approval or block a merge, but humans propose, approve, and promote policy through an approved→enforced lifecycle. |
| **Practice to steal Monday morning.** Give each rule a stable identity and a graduated path to power. Externalize your standards into a retrievable corpus, and let a new obligation land advisory first and earn its blocking authority — approved before enforced — so a policy scales the reach of a decision without any agent acquiring the right to make it. |
| **Failure if copied blindly.** The policy is structured; the governed system is largely not modeled. The reviewer still asks an LLM whether the code appears to satisfy the requirement, rather than checking a predicate against a model of the system. And the governance-conversion loop is described but not measured — incidents become RFCs become rules, but the recurrence-retired half is never shown. Structured policy over an unmodeled system is a ceiling, not a destination. |

<!-- case-onepager: docker -->
<!-- label: op-docker -->
| **Docker** · software / developer infrastructure · *teaches runtime authority and evaluation* |
|---|
| **Starting point.** Docker began from a question about trust: how much freedom can you give an agent whose behavior you cannot fully predict? Its answer moved the boundary off the prompt and into the runtime. Each agent runs in a disposable microVM where the forbidden thing is simply absent — the home SSH directory is not in the agent's world, rather than a rule telling it not to look — so inside the box it installs, runs, and modifies freely. |
| **Primary investment.** The sandbox substrate and a library of role-scoped skills, plus a worker/reviewer loop and a human standing between every pull request and the main branch. A small team of role-specialized agents runs on CI, each free to investigate the unexpected, with an independent reviewer grading work the author never grades. |
| **MAGE interpretation.** The sample's sharpest Alignment instance: the microVM sandbox, network allow-and-deny lists, role-scoped tools, CI, tests, and a human admission gate all place authority outside the reasoner. Governance conversion is strong at small scale. Determinization fits awkwardly, and the book reads it as a tension rather than a refutation — Docker determinizes its tests eagerly but keeps admission deliberately probabilistic. Modeling is the sample's weakest: rich soft knowledge, no invariant-bearing model. |
| **Practice to steal Monday morning.** Put the limit in the state space, not the prompt. Give the agent a sandbox where the dangerous capability is absent rather than forbidden, and inside that box let it install, run, and modify without asking. Hard boundaries enable more autonomy, not less: bound the world, and the agent can range freely within it. |
| **Failure if copied blindly.** No invariant-bearing system model is described and no drift gate exists; admission stays probabilistic with a human on every merge, over the shortest evidence horizon in the set. The boundary keeps the agent safe without ever making its work checkable against a model — so autonomy scales inside the box, but review does not amortize, and the human stays on every merge. |

<!-- case-onepager: zenseact -->
<!-- label: op-zenseact -->
| **Zenseact** · engineering knowledge work / automotive · *teaches knowledge routing and delegated expertise* |
|---|
| **Starting point.** Zenseact carries the method past source code. Its agents do not write software; they do knowledge work across the company's own systems, reasoning over issue trackers, code review, CI, search, and even ERP to decide which tool and which piece of expertise a task needs. The origin is telling: an earlier, open approach "did not scale," so the team rebuilt the environment around the same commodity models. |
| **Primary investment.** ZAP, a federated platform. A central team owns the runtime, permissions, and context machinery, while each domain team ships an agent as little more than a directory holding a config file and a skill. A deterministic TF-IDF router selects context, and a per-tool, per-role permission table bounds authority. |
| **MAGE interpretation.** Alignment is strong, second only to Docker: an auto/confirm/deny table per tool and role, allow-listed and depth-limited delegation, and deterministic tools behind structured seams place authority outside the reasoner. Determinization hardens three judgments others leave probabilistic — execution, authority, and context selection. The reasoning horizon shows the set's strongest measured context reduction, disclosed progressively through the router. Modeling stays partial: rich skills, no model of what the system is or must remain. |
| **Practice to steal Monday morning.** Govern capability discovery itself. Do not let the agent decide which tool or which expertise a task needs — make the environment route it, deterministically, disclosing only the skill that scores relevant so the context window stays small. Centralize the machinery and decentralize the domain knowledge: the platform team owns the runtime, the domain team owns the agent. |
| **Failure if copied blindly.** No invariant-bearing system model is described and no model-to-territory join exists; the outcome vocabulary strains on non-artifact-production work, and no effectiveness numbers are reported. The measured win is context reduction, not reasoning quality — the router proves it moves less context, not that the agent reasons better for it. |
