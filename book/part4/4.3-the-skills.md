# The Skills

<!-- point: the-book-ships-three-skills-of-a-portable-kind | The book ships three skills of a portable kind. | terms: self-operate, self-governance, self-communicate -->
A method only helps while someone remembers to apply it. Left as prose in a book, it has to
be re-taught to every fresh agent and every new project by hand, and a discipline that lives
in memory rather than in the environment is the first thing velocity drops. So a book of
method ought to ship with batteries, and this one does. The companion repository ships three
such skills — **self-operate**, **self-governance**, and **self-communicate** — and the
mastery-skill architecture behind them is portable to any harness that supports conditional
context and tools. Each packages the methodology of the preceding chapters as something an
agent triggers and follows. This chapter walks the architecture, with the three as its worked
examples.

<!-- point: a-mastery-skill-packages-knowledge-and-a-decision-procedure | A mastery-skill packages a knowledge-base and a decision procedure. | terms: skill-soft-control, mastery-skill -->
These are an unusual kind of skill. You have probably seen
plenty of *tool-skills* — a skill that teaches the model an interface: to do XYZ with this MCP
server or CLI, here is the shape of the call. What follows is a different animal: a
*mastery-skill*, which packages a body of knowledge and a disciplined decision procedure for
applying it — not an interface to one tool, but a way of doing the work well. ("Mastery-skill"
is the teaching handle; the machinery is a knowledge-base plus a procedure the agent runs, not
judgment poured into the model.) That is why the three below take a
chapter to walk, where a tool-skill would take a paragraph.

Teams are converging on the same reading of a skill: encode the procedure, and a class of
work becomes delegable. Atlassian's Jira team delegates KTLO work — flaky tests, feature-flag
cleanup, vulnerabilities, accessibility — by turning each into an explicit work item carrying
context plus workflow instructions, so a maintenance class becomes delegable once the tacit
repair procedure is encoded, not because the agent got clever [cite:atlassian2026maintenance].
Twilio's is sharper: an unguided agent asked to "verify users" hand-rolls a six-digit OTP,
while its skill redirects to a dedicated Verify product and inherits rate limiting, fraud
controls, and routing the operator never thought to request [cite:twilio2026skills].

> **Two kinds of skill.** A *tool-skill* teaches an interface — the calls, flags, and shapes for
> operating one tool (an MCP server, a CLI, an API). A *mastery-skill* packages a knowledge-base
> and a decision procedure for doing a task well, independent of any single tool. This book's three
> skills are mastery-skills; [appendix: appendix-skill-recipe] is the full recipe for
> building one.

<!-- point: the-three-skills-harden-run-and-explain-one-substrate | The three harden, run, and explain one substrate. | terms: self-operate, self-governance, self-communicate -->
The three are complements: one hardens the fleet, one runs it, one
explains it — the same system seen from three angles, drawn in [ref:three-skills]. Read them by the job,
not the name: you reach for whichever one matches the work in front of you — harden, run, or explain — and
the skill is that job made installable.

<!-- label: three-skills -->
<!-- figure: assets/three-skills.svg | *The Three Skills.* One substrate seen from three angles, each shipped as an installable skill. Self-governance hardens the fleet — it triggers on a recurring failure and converts the class into a durable mechanism. ## Self-operate: the lifecycles, made runnable

<!-- section-terms: self-operate, lifecycle -->

<!-- point: self-operate-holds-the-lifecycles-of-running-a-repo | Self-operate holds the lifecycles of running a repo. | terms: self-operate, lifecycle, conditioning-the-search -->
<!-- index-def: self-operate -->
Self-operate is the starting point, because it holds the lifecycles of running a repo —
the recurring repository lifecycles this project needed to operate. Pull a ticket and build a feature. Pull a
ticket and fix a bug. Optimize the codebase. Handle resource exhaustion. Each of those is
written down as a model — I did say models everywhere, and I meant it — because that is how
you constrain the agent's search and bias it toward doing the work the way you want.

> Learn more about this governance mechanism: [self-operate (operator runbook skill)](appendix-a-operator-runbook-skill.html).

<!-- point: playbooks-let-an-orchestrator-loop-react-to-events | Playbooks let an orchestrator loop react to events. | terms: runbook, agent-orchestration-model -->
On top of the models sit the playbooks — one per lifecycle, each with briefs for its judgment
steps. This is what lets an orchestrator agent, itself running as a reactive loop, know how to
respond when an event arrives. The loop turns on inputs from the environment: it is the
*dispatch → work → land → tombstone* lifecycle from
[Loops and Models](1.3-loops-and-models.html), now written down for the operator to run.

> ### When an agent lands, what next?
>
> - **Agent landed** → open the Epic file, which lists the launches the feature needs.
> - **Feature done?** Not done → launch the next item. Done → run the definition-of-done audit over the
>   whole Epic (does the model still match the code?).
> - **DoD passes** → mark it done, move it to the closed pile.
> - **Still active** → record the status and the commit that made progress, then launch the next item.

That definition-of-done audit exists because of one hard-won rule.

> "Done" is a claim, not a fact.

<!-- point: dont-trust-a-done-claim-re-run-the-gates-yourself | Don't trust a done claim; re-run gates. | terms: done-is-a-claim, drift-gate -->
An agent reporting a task complete is describing its *intent*, not the state of your repository,
and the two drift apart constantly — a sibling change broke a test, a marker rotted, the thing
it "verified" quietly routed through a fallback. So you do not trust the claim. You re-run the
gates yourself, at HEAD, and let a fact answer where a claim was offered.

That rule is one of several the skill teaches. Three worth quoting, because they show the shape
of the whole:

> ### Self-operate — three principles
>
> - **Determinize the runnable, brief the judgment.** A runbook step is one of three kinds. If a
>   machine can do it, make it a runnable line. If it needs judgment a brief can carry, write the
>   brief — and when that judgment is a measurement, the brief is a rubric: you cannot machine-check
>   whether an essay is good, but you can grade its topic sentences, its technique, its obvious
>   errors. If it needs judgment no brief can carry, escalate. A runbook that blurs the three sends a
>   human to do a machine's work, or a machine to make a human's call.
> - **The lifecycle is a state machine, not a habit.** Dispatch, work, land, tombstone — an agent's
>   life is a sequence of states with legal transitions, and you write it down as one. A habit lives
>   in the operator's head and rots; a state machine names every state and the move out of it, so the
>   loop turns on events from the environment instead of on memory.
> - **Orient positive before you hunt a break.** Know the healthy baseline first — what "normal"
>   looks like for each lifecycle. Most sessions are steady-state; you cannot recognize a break
>   until you can state the shape it broke from.

## Self-governance: the catalogue and the posture

<!-- section-terms: self-governance, governance-catalogue -->

<!-- point: recurrence-signals-a-missing-sensor-or-constraint | Recurrence signals a missing sensor or constraint. | terms: self-governance, sensor, constraint -->
<!-- index-def: self-governance -->
The second skill, self-governance, triggers on a simple signal: a bad thing happened more
than once — sometimes just once, if it was bad enough. Recurrence is the clue that you are
either failing to *detect* the problem (you need a sensor) or failing to *prevent*
it (you need a constraint, a wall). You have not put the wall in the right spot, or you have
not put a badge reader on the door.

<!-- point: the-skill-ships-a-catalogue-plus-a-minting-posture | The skill ships a catalogue plus a minting posture. | terms: governance-catalogue, ex-ante-governance, governance-conversion -->
<!-- index-def: governance-catalogue -->
At its center is a catalogue of governance mechanisms and worked examples — roughly {{mechanism_count}}
in this edition, and still growing as new failures surface new mechanisms. I did not know these
were the mechanisms I would need until I started building and kept hitting failures; the higher
the velocity rose, the more failures appeared, and new *kinds* of failure with them, and each
mechanism I invented to kill one went into the catalogue. The hope is that this becomes ex-ante
governance for *you*: the mistakes I made and solved become a tested starting catalogue rather
than an empty page — install it and say
"audit my codebase and help me find room for governance." You will, of course, find your own
failures too, because you run a different model, different constraints, different customers,
different operators, and all of it shapes your agent's behavior. So the skill ships not just the
catalogue but a **posture** — the heuristics for minting new mechanisms well.

<!-- point: minted-rules-live-in-the-boot-context-mission-method-rules | Minted rules live in the boot context: mission, method, rules. | terms: governed-environment, ex-ante-governance -->
Where do the minted rules live? In the harness's always-loaded project context — the one
document every agent boots with, so it is where governance either binds or does not. Every
harness has one such surface — Claude Code loads `CLAUDE.md`, other agent harnesses load their
own always-present equivalent — and whatever the harness, give that surface three parts, coarse to fine.

> ### The boot-context document: Mission, Method, Rules
>
> - **Mission** — what the project optimizes for, the values that break a tie. *Mission orients.*
> - **Method** — the engineering principles that hold across any project of this kind, independent of the
>   domain. *The method teaches judgment.*
> - **Rules** — the specific, stably-numbered guardrails this codebase enforces, each a one-line
>   boot-context statement pointing at the deeper doc that carries it in full. *The rules bind.*
>
> A self-governance skill grows the third part as failures earn new rules.

If you want a scaffold to start your own, the
[CLAUDE.md rule index](appendix-a-claude-md-rule-index.html) appendix ships a **CLAUDE-starter**
download built from a real, mature one.

## The posture: minting new mechanisms well

<!-- section-terms: teetering-tower, right-level-of-enforcement -->

<!-- point: avoid-a-teetering-tower-of-governance | Avoid a teetering tower of governance. | terms: teetering-tower, right-level-of-enforcement, constraint -->
<!-- index-def: teetering-tower -->
The first heuristic is to **avoid a teetering tower of governance.** Do too much of this and
tending the tower becomes the work itself: the agent side-quests into polishing the linter
while the product waits. Three symptoms tell you the tower is teetering.

- Agents spend more time servicing controls than doing product work.
- False positives dominate — the checks cry wolf more than they catch.
- The controls guard failures that are both low-cost and low-frequency.

Each is a governance whose upkeep outweighs its benefit. When you see one, size the control the
way [Brownfield](4.2-brownfield.html) sizes any governance — against the cost and the frequency of the failure it
prevents — and when you say "this must *never* happen," remember you are choosing a wall, and
every wall constrains the agent. A well-placed wall is pure gain; a wall across the only fire
exit is a disaster the day there is a fire. Because of this the skill will not silently enforce
a mechanism without checking with you — you are the engineer who knows the context.

<!-- point: a-passive-skill-needs-a-hook-to-fire-it | A passive skill needs a hook to fire it. | terms: skill-soft-control, hook-hard-control, reflection-hook -->
The move generalizes. A skill on its own is *passive*: it sits and waits to be invoked, and an
agent heads-down in the work will not stop to invoke it. A hook brings it to life — kaizen on a
timer, the improvement loop from [The Engineer's Seat](1.6-the-engineers-seat.html) run without
waiting for a human to notice the recurrence. The right cadence is proportional to how fast
recurrence becomes visible: reflect often enough that a repeated failure shows up while its cause
is still fresh. The timer fires, the prompt lands, and the skill reaches into its catalogue of
every way you might handle this class of failure. From that catalogue it **resolves the
mechanically classifiable cases and surfaces the design forks** — "we keep hitting this; here are
two ideas, which should I try?" — then waits. That hand-off is deliberate: the hook makes the
reflection happen, the catalogue supplies the options, and the judgment call stays yours.

> ### From DocAble: the thirty-minute reflection
>
> In DocAble the reflection hook fired about every thirty minutes in the orchestrator loop, asking whether
> the last window hit a recurring failure or solved one problem several different ways. At agentic velocity
> you cover enormous ground in thirty minutes, so a repeat inside that window was a reliable signal that a
> mechanism was owed. Solving it several ways is a don't-repeat-yourself smell in the code; hitting the same
> *process* wall repeatedly — "I failed to create a VM," again — is a process smell.

> Learn more about this governance mechanism: [reflection-facet substrate](appendix-a-reflection-facet-substrate.html).

Underneath the posture sit a few reflexes the skill applies on every touch. Three of them:

> ### Self-governance — three principles
>
> - **Convert, don't just repair — audit becomes lint.** When a failure smells class-level, do not
>   only patch the instance. Build the durable mechanism that kills the class. Today's audit finding —
>   a thing you noticed by reading — is tomorrow's lint, a thing the machine notices for you. A bug
>   in more than one file means "fix the sites *and* add the check," not "fix the sites and hope."
> - **Guidance aims; machinery holds.** A mechanism is soft or hard. A soft one — a brief, a house-rule
>   — can *aim* a probabilistic agent but cannot block it, and it rots. A hard one — a lint, a gate,
>   a typed seam — *holds the line* regardless of whether the agent cooperates. Know which you are
>   minting, and never claim a mechanism is enforced when you have only recommended it.
> - **Architecture before sensors.** Prefer making the error impossible over catching it after. A
>   structured model with one sanctioned seam beats a validator that scolds you for using the wrong one.
>   Where a failure is costly, do both — belt-and-suspenders is a feature. But reach for the wall
>   first, and remember that every wall you raise also constrains the agent, so place it with care.

Even a soft mechanism can be admitted like a hard one. NVIDIA treats a skill as a deployable
capability, not a static prompt, and runs it through an eight-stage supply chain — source,
review, scan, evaluate, skill card, sign, catalog, sync — where scanning looks for
agent-specific threats (hidden instructions, trigger abuse, excessive agency, tool poisoning,
purpose/access mismatch), not only conventional software risk [cite:nvidia2026verifiedskills].

## Self-communicate: how the agent writes and draws

<!-- section-terms: self-communicate, lexicon -->

<!-- point: self-communicate-governs-the-agents-prose-and-diagrams | Self-communicate governs the agent's prose and diagrams. | terms: self-communicate, documentation-hierarchy -->
<!-- index-def: self-communicate -->
The third skill, self-communicate, governs how the agent explains itself — to you and to other
people. Docs are a soft mechanism for an agent, but they are a genuine tool for humans, so the
skill carries guidance on the kinds of technical documentation, crediting the Diátaxis project
for enumerating them and the Apache Foundation for the exemplars it learns style and voice from.
It targets prose that avoids imprecise claims and the grating verbal tics, and that is as terse
as it can be without losing the reader. When the agent writes, it turns here. When it needs a
drawing, the skill says "use me," and teaches drawing in Mermaid — dropping to HTML or SVG only
when Mermaid cannot express the shape. That keeps the agent from trying to hand-generate raw
PNGs, a thing it will attempt and be bad at. The book's house style specializes this portable
default: narrative figures in the book use hand-authored SVG, while the reusable skill remains
Mermaid-first.

## The lexicon: one concept, one word

<!-- section-terms: lexicon -->

<!-- point: a-lexicon-gives-one-concept-one-consistent-word | A lexicon gives one concept one consistent word. | terms: lexicon -->
<!-- index-def: lexicon -->
Self-communicate also owns a **lexicon**: the house vocabulary for your repo, so one concept gets
one word, used consistently. You can bootstrap it — point the skill at existing material and have
it walk the repository, surface the terms you use with specific meaning, and write down the
working definitions. That walk tends to catch two failures at once: different words for the same
concept, and the same word for different concepts. Both confuse any reader, human or agent, and
finding them may show you mistakes in your own thinking. "There are actually two concepts here —
help me name them." Now they have names, and you can retrofit structure onto the writing — which
is, exactly, the code problem from [Brownfield](4.2-brownfield.html), wearing different clothes.

The lexicon is one specialization of a stance the skill carries into both legs. Three of its
principles govern the whole:

> ### Self-communicate — three principles
>
> - **Less is more — the representation must not distract from the idea.** In prose that means
>   Hemingway: cut the fluffy adjective, the qualifier, the sentence that restates the last one. In
>   drawing it means Tufte and Picasso's *Bull* — strip the chartjunk until only the marks that carry
>   the idea remain. Operationally: before you ship a passage or a figure, delete every element and
>   check whether the idea still lands; keep only what its absence would break.
> - **Name the concept, then use the name.** A name is a handle: it carries a concept's meaning and
>   its constraints in one token. In prose, reach for the established term — say "circuit breaker,"
>   not a fresh paragraph re-deriving one. In drawing, reach for the format's native construct — an
>   SVG `<marker>` with `orient="auto"` *is* an arrowhead; it rotates to its line and pins to the
>   endpoint, so it cannot land crooked the way a hand-stitched triangle can. Use the marker.
> - **Decide the mode before the sentences.** A section is a tutorial, a how-to, a reference, or an
>   explanation — the four Diátaxis shapes. Decide the mode of each section before writing it; when a
>   document serves two modes, separate them visibly rather than braiding them into one paragraph. A how-to
>   written as an explanation confuses the reader who wanted steps. Fix the shape first; the prose follows.

Those are the three skills that ship with the book. I hope they are of use.

## The construction recipe is a pattern of its own

<!-- point: every-skill-is-base-model-orthogonal-models-and-a-skill-md | Every skill: base model, orthogonal models, SKILL.md. | terms: per-model-template, model-zoo, orthogonal-models -->
The three feel of a piece because they were all built the same way. Three layers, every
time. A **base model of the domain** at the bottom. **Orthogonal models** layered on top — cuts
through the base along independent axes, each adding a dimension without disturbing the others. And a
top-level **`SKILL.md` of principles** that ties the models together and tells the agent when to reach
for which. Set the three skills side by side along those layers, as [ref:skill-construction-matrix] lays out, and the shared skeleton — drawn in [ref:skill-recipe] — shows through.

## Worked examples

<!-- section-terms: self-governance, governance-catalogue -->

Shipping the method as skills is one project's answer to a pattern the industry is finding in
parallel: encoded knowledge is an asset that compounds, and each site accumulates it. Read the
three below as moves on a path a normal team can start walking, not as platforms to envy — Part VI's
[MAGE in the Wild](6.6-where-mage-fits.html) sets six such systems side by side as evidence the moves travel.

<!-- worked-examples: institutional-knowledge-capital -->
### Example — Docker
Docker, the runtime-authority case, makes the move by encoding testing and repair know-how as a
library of foundational skills every agent inherits, so each CI role stands on accumulated
procedure instead of re-deriving it — the skill library is the representation; the compounding is
what it becomes.

### Example — Shopify
Shopify runs the same move at organizational scale: every agent session runs in public and
becomes a searchable artifact the company mines into skills and defaults, so a lesson one
engineer learns becomes the whole company's the next day. The move a team can copy is making the
work visible and mining it; the org-wide memory is where the path leads.

### Example — Zenseact
Zenseact, the knowledge-routing case, federates the move: a central team owns the runtime while
each domain team contributes an agent as little more than a directory holding a config and a
skill, domain expertise accreting as reusable skills a router surfaces on demand.

<!-- takeaway -->
The shared move is *institutional-knowledge-capital*: hard-won engineering knowledge becomes an
encoded, reusable asset that compounds, so the next agent inherits it instead of re-deriving it.
DocAble ships that capital as installable batteries — three mastery-skills plus a catalogue of
governance mechanisms grown from real failures; Part V tells that story in full.

> **Left for later: the team dimension.** This book is written as "you and your agents," but
> production software is built by teams, and the team dimension is its own chapter. A model that
> governs one person's work has to become a shared artifact — reviewed, owned, and defended by
> more than its author. Review changes shape when an agent wrote the diff: who reads it, and
> against what. And when a model drifts, someone has to own the reconciliation. Those are real
> questions with real answers. Part 6 returns to this as a boundary and research question, not a
> solved practice. This is a field report and a method,
> not a survey of team practice, so I mark the boundary here rather than gesture past it.
