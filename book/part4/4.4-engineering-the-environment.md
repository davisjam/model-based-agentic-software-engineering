# Engineering the Environment

So far, we have applied Modeling and Alignment to the system we are building. We can apply them to the machinery we use to build it as well. Agents are dispatched, work is integrated, checks are executed, and failures require recovery. These activities have structures, behaviors, resource requirements, and obligations of their own.

As DocAble grew, I encountered problems in this engineering machinery much as I encountered problems in the product. Some required new models, others required changes to the implementation, and others exposed shortcomings in the controls I had already established.

## Modeling Engineering Work {#lifecycle-models-and-recovery}

A method has to survive terrible, horrible, no good, very bad days, too. Full disks, conflicted branches, vanished agents, stalled queues, flaking tests—the quotidian catastrophes of software engineering.

In one DocAble incident, my orchestrating agent attempted to recover from a partly completed cherry-pick sequence. It aborted the sequence, discarding earlier successful picks along with the unsuccessful one. I needed the agent to distinguish abandoning the current operation from undoing work that had already succeeded.

The resulting rule specified `git cherry-pick --quit` for leaving the sequence without undoing the earlier picks. Unlike `--abort`, this operation cleared the sequencer state while preserving the commits already applied. It did not resolve the conflict; that work remained. The automated cherry-pick procedure used `--quit` when it encountered a conflict, preserving the successful work for subsequent recovery.

The same modeling technique we used for remediation jobs in {{chapter:modeling}} applies to engineering work. We can represent the states in which an assignment or integration operation may find itself, the transitions available from each state, and the properties that recovery must preserve. In this case, the important distinction was between work already completed successfully and the operation that had encountered a failure.

<!-- index-def: deterministic-firing -->

Not every recovery decision needs to be made mechanically. I could establish a procedure for investigating a particular failure, specify when that procedure should be invoked, and leave the agent to exercise judgment within it. A mechanically observable event could trigger the procedure without determining its every step. For example, reaching a context threshold can cause a hook to request a handoff that the agent must still compose. Automate the arrival of the decision procedure, not every decision.

The incident had revealed an inadequacy in my engineering environment rather than in DocAble’s remediation software. I responded in much the same way: identify the distinction the existing implementation failed to preserve, represent it explicitly, and establish a mechanism that subsequent work could use.

## Improving the Execution of Engineering Work {#when-validation-becomes-the-bottleneck}

As I increased the number of agents developing DocAble, the engineering environment encountered resource problems of its own. Agents could produce changes faster than some of the machinery could evaluate them. One particularly instructive example concerned the scheduling of validation.

Before a November 2026 redesign, completed changes arrived in batches roughly every ten minutes, while the full test suite took about thirty minutes. The validation queue grew even though implementation was progressing well. I therefore asked which checks had to pass before each merge and which could examine several changes together.

An initial asynchronous arrangement launched expensive checks in the background after each merge. Making validation asynchronous reduced the time an agent spent waiting for it. It did not reduce the amount of validation work the host performed. As more agents completed changes, more validation runs competed for the same resources and overloaded the host. I had changed when the work occurred without addressing how much work occurred.

I therefore separated the scheduling of the expensive validation sweep from the arrival of individual merges. Several changes could be examined by one sweep, and a lock prevented overlapping sweeps. Inexpensive checks remained synchronous at the merge boundary, while broader validation ran separately, as [ref:docable-validation-scheduling] shows.

Broad repository checks were scheduled every thirty minutes against new commits on the main branch, in an isolated worktree. A blocking failure raised an alert and stopped new agent dispatch until the orchestrator acknowledged or handled it; acknowledgment permitted work to resume while repair was tracked separately. Before deployment, the full validation suite ran against the candidate being shipped.

This arrangement reduced contention, but it also changed when I could discover certain defects. A change could be integrated before the next broad validation sweep, and several intervening changes could make a subsequent failure harder to localize. I therefore had to decide which obligations required evidence before integration and which could be evaluated later. The per-merge, scheduled, and predeployment checks supplied evidence at different boundaries; a scheduled failure could still interrupt subsequent work.

I had encountered a related engineering problem while redesigning document processing in {{sec:interlude-one-problem-many-models}}. In both cases, the event that initiated work did not necessarily define the best way to execute that work. Separating the arrival of work from its execution schedule gave me additional design choices.

## Evaluating and Revising the Controls {#engineering-capital-depreciates}

An audit of my engineering models appeared to show that ten providers had the required uniqueness checks. Every check passed. Unfortunately, all ten were checking the wrong thing.

Each check examined identifiers in a shared graph, where uniqueness was already guaranteed, rather than the source records belonging to its provider. Two source records could claim the same identifier and silently overwrite one another as the provider’s catalog was constructed. Checking the shared graph could not establish uniqueness in those original records. The checks established a true property of the wrong collection.

The repair changed both the checks and the evidence for trusting them. Each check examined its provider’s source records, and a test deliberately introduced a duplicate that the check had to reject. This gave us evidence that the revised check would detect the violation it was intended to find. Where an obligation is enforced at an admission boundary, we can also test whether the detected violation prevents admission.

This is closely related to mutation testing and fault injection. We deliberately introduce a defect to evaluate the machinery responsible for detecting or handling it. The subject of evaluation is now the engineering control rather than the product it ordinarily evaluates. In {{sec:constraints-sensors-validators-gates}}, the consumer mistook an incomplete validation for a clean result; here, the uniqueness checks examined the wrong records.

As the system changes, the representations and mechanisms used to evaluate it can become inadequate. A check may continue to execute successfully while no longer examining the property it was intended to establish. Maintaining the engineering environment therefore requires evaluating the correspondence between its controls and the obligations they enforce, just as maintaining the product requires evaluating its correspondence with engineering intent.

These episodes illustrate that Modeling and Alignment apply to the engineering environment as well as to the product. The environment has its own architecture, behavior, resource requirements, and obligations. We can model these properties, evaluate the environment’s operation, and revise its implementation as we discover deficiencies. Improvements to this environment can then benefit many subsequent changes to the product.
