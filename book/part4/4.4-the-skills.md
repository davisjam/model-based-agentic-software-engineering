# The Skills

<!-- point: the-book-ships-three-skills-of-a-portable-kind | The book ships three skills of a portable kind. | terms: self-operate, self-governance, self-communicate -->
A method only helps while someone remembers to apply it. Left as prose in a book, it has to
be re-taught to every fresh agent and every new project by hand, and a discipline that lives
in memory rather than in the environment is the first thing velocity drops. So a book of
method ought to ship with batteries, and this one does. The companion repository ships three
such skills — **self-operate**, **self-governance**, and **self-communicate** — and the
mastery-skill architecture behind them is portable to any harness that supports conditional
context and tools. Each packages the methodology of the preceding chapters as something an
agent triggers and follows. This chapter walks the architecture, with the three as its worked
examples.

<!-- point: a-mastery-skill-packages-knowledge-and-a-decision-procedure | A mastery-skill packages a knowledge-base and a decision procedure. | terms: skill-soft-control, mastery-skill -->
These are an unusual kind of skill. You have probably seen
plenty of *tool-skills* — a skill that teaches the model an interface: to do XYZ with this MCP
server or CLI, here is the shape of the call. What follows is a different animal: a
*mastery-skill*, which packages a body of knowledge and a disciplined decision procedure for
applying it — not an interface to one tool, but a way of doing the work well. ("Mastery-skill"
is the teaching handle; the machinery is a knowledge-base plus a procedure the agent runs, not
judgment poured into the model.) That is why the three below take a
chapter to walk, where a tool-skill would take a paragraph.

Teams are converging on the same reading of a skill: encode the procedure, and a class of
work becomes delegable. Atlassian's Jira team delegates KTLO work — flaky tests, feature-flag
cleanup, vulnerabilities, accessibility — by turning each into an explicit work item carrying
context plus workflow instructions, so a maintenance class becomes delegable once the tacit
repair procedure is encoded, not because the agent got clever [cite:atlassian2026maintenance].
Twilio's is sharper: an unguided agent asked to "verify users" hand-rolls a six-digit OTP,
while its skill redirects to a dedicated Verify product and inherits rate limiting, fraud
controls, and routing the operator never thought to request [cite:twilio2026skills].

> **Two kinds of skill.** A *tool-skill* teaches an interface — the calls, flags, and shapes for
> operating one tool (an MCP server, a CLI, an API). A *mastery-skill* packages a knowledge-base
> and a decision procedure for doing a task well, independent of any single tool. This book's three
> skills are mastery-skills; [appendix: appendix-skill-recipe] is the full recipe for
> building one.

<!-- point: the-three-skills-harden-run-and-explain-one-substrate | The three harden, run, and explain one substrate. | terms: self-operate, self-governance, self-communicate -->
The three are complements: one hardens the fleet, one runs it, one
explains it — the same system seen from three angles, drawn in [ref:three-skills]. Read them by the job,
not the name: you reach for whichever one matches the work in front of you — harden, run, or explain — and
the skill is that job made installable.

<!-- label: three-skills -->
<!-- figure: assets/three-skills.svg | *The Three Skills.* One substrate seen from three angles, each shipped as an installable skill. Self-governance hardens the fleet — it triggers on a recurring failure and converts the class into a durable mechanism. ## Self-operate: the lifecycles, made runnable

<!-- section-terms: self-operate, lifecycle -->

<!-- point: self-operate-holds-the-lifecycles-of-running-a-repo | Self-operate holds the lifecycles of running a repo. | terms: self-operate, lifecycle, conditioning-the-search -->
<!-- index-def: self-operate -->
Self-operate is the starting point, because it holds the lifecycles of running a repo —
the recurring repository lifecycles this project needed to operate. Pull a ticket and build a feature. Pull a
ticket and fix a bug. Optimize the codebase. Handle resource exhaustion. Each of those is
written down as a model — I did say models everywhere, and I meant it — because that is how
you constrain the agent's search and bias it toward doing the work the way you want.

> Learn more about this governance mechanism: [self-operate (operator runbook skill)](appendix-a-operator-runbook-skill.html).

<!-- point: playbooks-let-an-orchestrator-loop-react-to-events | Playbooks let an orchestrator loop react to events. | terms: runbook, agent-orchestration-model -->
On top of the models sit the playbooks — one per lifecycle, each with briefs for its judgment
steps. This is what lets an orchestrator agent, itself running as a reactive loop, know how to
respond when an event arrives. The loop turns on inputs from the environment: it is the
*dispatch → work → land → tombstone* lifecycle from
[Loops and Models](1.3-loops-and-models.html), now written down for the operator to run.

> ### When an agent lands, what next?
>
> - **Agent landed** → open the Epic file, which lists the launches the feature needs.
> - **Feature done?** Not done → launch the next item. Done → run the definition-of-done audit over the
>   whole Epic (does the model still match the code?).
> - **DoD passes** → mark it done, move it to the closed pile.
> - **Still active** → record the status and the commit that made progress, then launch the next item.

That definition-of-done audit exists because of one hard-won rule.

> "Done" is a claim, not a fact.

<!-- point: dont-trust-a-done-claim-re-run-the-gates-yourself | Don't trust a done claim; re-run gates. | terms: done-is-a-claim, drift-gate -->
An agent reporting a task complete is describing its *intent*, not the state of your repository,
and the two drift apart constantly — a sibling change broke a test, a marker rotted, the thing
it "verified" quietly routed through a fallback. So you do not trust the claim. You re-run the
gates yourself, at HEAD, and let a fact answer where a claim was offered.

That rule is one of several the skill teaches. Three worth quoting, because they show the shape
of the whole:

> ### Self-operate — three principles
>
> - **Determinize the runnable, brief the judgment.** A runbook step is one of three kinds. If a
>   machine can do it, make it a runnable line. If it needs judgment a brief can carry, write the
>   brief — and when that judgment is a measurement, the brief is a rubric: you cannot machine-check
>   whether an essay is good, but you can grade its topic sentences, its technique, its obvious
>   errors. If it needs judgment no brief can carry, escalate. A runbook that blurs the three sends a
>   human to do a machine's work, or a machine to make a human's call.
> - **The lifecycle is a state machine, not a habit.** Dispatch, work, land, tombstone — an agent's
>   life is a sequence of states with legal transitions, and you write it down as one. A habit lives
>   in the operator's head and rots; a state machine names every state and the move out of it, so the
>   loop turns on events from the environment instead of on memory.
> - **Orient positive before you hunt a break.** Know the healthy baseline first — what "normal"
>   looks like for each lifecycle. Most sessions are steady-state; you cannot recognize a break
>   until you can state the shape it broke from.

## Self-governance: the catalogue and the posture

<!-- section-terms: self-governance, governance-catalogue -->

<!-- point: recurrence-signals-a-missing-sensor-or-constraint | Recurrence signals a missing sensor or constraint. | terms: self-governance, sensor, constraint -->
<!-- index-def: self-governance -->
The second skill, self-governance, triggers on a simple signal: a bad thing happened more
than once — sometimes just once, if it was bad enough. Recurrence is the clue that you are
either failing to *detect* the problem (you need a sensor) or failing to *prevent*
it (you need a constraint, a wall). You have not put the wall in the right spot, or you have
not put a badge reader on the door.

<!-- point: the-skill-ships-a-catalogue-plus-a-minting-posture | The skill ships a catalogue plus a minting posture. | terms: governance-catalogue, ex-ante-governance, governance-conversion -->
<!-- index-def: governance-catalogue -->
At its center is a catalogue of governance mechanisms and worked examples — roughly {{mechanism_count}}
in this edition, and still growing as new failures surface new mechanisms. I did not know these
were the mechanisms I would need until I started building and kept hitting failures; the higher
the velocity rose, the more failures appeared, and new *kinds* of failure with them, and each
mechanism I invented to kill one went into the catalogue. The hope is that this becomes ex-ante
governance for *you*: the mistakes I made and solved become a tested starting catalogue rather
than an empty page — install it and say
"audit my codebase and help me find room for governance." You will, of course, find your own
failures too, because you run a different model, different constraints, different customers,
different operators, and all of it shapes your agent's behavior. So the skill ships not just the
catalogue but a **posture** — the heuristics for minting new mechanisms well.

<!-- point: minted-rules-live-in-the-boot-context-mission-method-rules | Minted rules live in the boot context: mission, method, rules. | terms: governed-environment, ex-ante-governance -->
Where do the minted rules live? In the harness's always-loaded project context — the one
document every agent boots with, so it is where governance either binds or does not. Every
harness has one such surface — Claude Code loads `CLAUDE.md`, other agent harnesses load their
own always-present equivalent — and whatever the harness, give that surface three parts, coarse to fine.

> ### The boot-context document: Mission, Method, Rules
>
> - **Mission** — what the project optimizes for, the values that break a tie. *Mission orients.*
> - **Method** — the engineering principles that hold across any project of this kind, independent of the
>   domain. *The method teaches judgment.*
> - **Rules** — the specific, stably-numbered guardrails this codebase enforces, each a one-line
>   boot-context statement pointing at the deeper doc that carries it in full. *The rules bind.*
>
> A self-governance skill grows the third part as failures earn new rules.

If you want a scaffold to start your own, the
[CLAUDE.md rule index](appendix-a-claude-md-rule-index.html) appendix ships a **CLAUDE-starter**
download built from a real, mature one.

## The posture: minting new mechanisms well

<!-- section-terms: teetering-tower, right-level-of-enforcement -->

<!-- point: avoid-a-teetering-tower-of-governance | Avoid a teetering tower of governance. | terms: teetering-tower, right-level-of-enforcement, constraint -->
<!-- index-def: teetering-tower -->
The first heuristic is to **avoid a teetering tower of governance.** Do too much of this and
tending the tower becomes the work itself: the agent side-quests into polishing the linter
while the product waits. Three symptoms tell you the tower is teetering.

- Agents spend more time servicing controls than doing product work.
- False positives dominate — the checks cry wolf more than they catch.
- The controls guard failures that are both low-cost and low-frequency.

Each is a governance whose upkeep outweighs its benefit. When you see one, size the control the
way [Brownfield](4.2-brownfield.html) sizes any governance — against the cost and the frequency of the failure it
prevents — and when you say "this must *never* happen," remember you are choosing a wall, and
every wall constrains the agent. A well-placed wall is pure gain; a wall across the only fire
exit is a disaster the day there is a fire. Because of this the skill will not silently enforce
a mechanism without checking with you — you are the engineer who knows the context.

<!-- point: a-passive-skill-needs-a-hook-to-fire-it | A passive skill needs a hook to fire it. | terms: skill-soft-control, hook-hard-control, reflection-hook -->
The move generalizes. A skill on its own is *passive*: it sits and waits to be invoked, and an
agent heads-down in the work will not stop to invoke it. A hook brings it to life — kaizen on a
timer, the improvement loop from [The Engineer's Seat](1.6-the-engineers-seat.html) run without
waiting for a human to notice the recurrence. The right cadence is proportional to how fast
recurrence becomes visible: reflect often enough that a repeated failure shows up while its cause
is still fresh. The timer fires, the prompt lands, and the skill reaches into its catalogue of
every way you might handle this class of failure. From that catalogue it **resolves the
mechanically classifiable cases and surfaces the design forks** — "we keep hitting this; here are
two ideas, which should I try?" — then waits. That hand-off is deliberate: the hook makes the
reflection happen, the catalogue supplies the options, and the judgment call stays yours.

> ### From DocAble: the thirty-minute reflection
>
> In DocAble the reflection hook fired about every thirty minutes in the orchestrator loop, asking whether
> the last window hit a recurring failure or solved one problem several different ways. At agentic velocity
> you cover enormous ground in thirty minutes, so a repeat inside that window was a reliable signal that a
> mechanism was owed. Solving it several ways is a don't-repeat-yourself smell in the code; hitting the same
> *process* wall repeatedly — "I failed to create a VM," again — is a process smell.

> Learn more about this governance mechanism: [reflection-facet substrate](appendix-a-reflection-facet-substrate.html).

Underneath the posture sit a few reflexes the skill applies on every touch. Three of them:

> ### Self-governance — three principles
>
> - **Convert, don't just repair — audit becomes lint.** When a failure smells class-level, do not
>   only patch the instance. Build the durable mechanism that kills the class. Today's audit finding —
>   a thing you noticed by reading — is tomorrow's lint, a thing the machine notices for you. A bug
>   in more than one file means "fix the sites *and* add the check," not "fix the sites and hope."
> - **Guidance aims; machinery holds.** A mechanism is soft or hard. A soft one — a brief, a house-rule
>   — can *aim* a probabilistic agent but cannot block it, and it rots. A hard one — a lint, a gate,
>   a typed seam — *holds the line* regardless of whether the agent cooperates. Know which you are
>   minting, and never claim a mechanism is enforced when you have only recommended it.
> - **Architecture before sensors.** Prefer making the error impossible over catching it after. A
>   structured model with one sanctioned seam beats a validator that scolds you for using the wrong one.
>   Where a failure is costly, do both — belt-and-suspenders is a feature. But reach for the wall
>   first, and remember that every wall you raise also constrains the agent, so place it with care.

Even a soft mechanism can be admitted like a hard one. NVIDIA treats a skill as a deployable
capability, not a static prompt, and runs it through an eight-stage supply chain — source,
review, scan, evaluate, skill card, sign, catalog, sync — where scanning looks for
agent-specific threats (hidden instructions, trigger abuse, excessive agency, tool poisoning,
purpose/access mismatch), not only conventional software risk [cite:nvidia2026verifiedskills].

## Self-communicate: how the agent writes and draws

<!-- section-terms: self-communicate, lexicon -->

<!-- point: self-communicate-governs-the-agents-prose-and-diagrams | Self-communicate governs the agent's prose and diagrams. | terms: self-communicate, documentation-hierarchy -->
<!-- index-def: self-communicate -->
The third skill, self-communicate, governs how the agent explains itself — to you and to other
people. Docs are a soft mechanism for an agent, but they are a genuine tool for humans, so the
skill carries guidance on the kinds of technical documentation, crediting the Diátaxis project
for enumerating them and the Apache Foundation for the exemplars it learns style and voice from.
It targets prose that avoids imprecise claims and the grating verbal tics, and that is as terse
as it can be without losing the reader. When the agent writes, it turns here. When it needs a
drawing, the skill says "use me," and teaches drawing in Mermaid — dropping to HTML or SVG only
when Mermaid cannot express the shape. That keeps the agent from trying to hand-generate raw
PNGs, a thing it will attempt and be bad at. The book's house style specializes this portable
default: narrative figures in the book use hand-authored SVG, while the reusable skill remains
Mermaid-first.

## The lexicon: one concept, one word

<!-- section-terms: lexicon -->

<!-- point: a-lexicon-gives-one-concept-one-consistent-word | A lexicon gives one concept one consistent word. | terms: lexicon -->
<!-- index-def: lexicon -->
Self-communicate also owns a **lexicon**: the house vocabulary for your repo, so one concept gets
one word, used consistently. You can bootstrap it — point the skill at existing material and have
it walk the repository, surface the terms you use with specific meaning, and write down the
working definitions. That walk tends to catch two failures at once: different words for the same
concept, and the same word for different concepts. Both confuse any reader, human or agent, and
finding them may show you mistakes in your own thinking. "There are actually two concepts here —
help me name them." Now they have names, and you can retrofit structure onto the writing — which
is, exactly, the code problem from [Brownfield](4.2-brownfield.html), wearing different clothes.

The lexicon is one specialization of a stance the skill carries into both legs. Three of its
principles govern the whole:

> ### Self-communicate — three principles
>
> - **Less is more — the representation must not distract from the idea.** In prose that means
>   Hemingway: cut the fluffy adjective, the qualifier, the sentence that restates the last one. In
>   drawing it means Tufte and Picasso's *Bull* — strip the chartjunk until only the marks that carry
>   the idea remain. Operationally: before you ship a passage or a figure, delete every element and
>   check whether the idea still lands; keep only what its absence would break.
> - **Name the concept, then use the name.** A name is a handle: it carries a concept's meaning and
>   its constraints in one token. In prose, reach for the established term — say "circuit breaker,"
>   not a fresh paragraph re-deriving one. In drawing, reach for the format's native construct — an
>   SVG `<marker>` with `orient="auto"` *is* an arrowhead; it rotates to its line and pins to the
>   endpoint, so it cannot land crooked the way a hand-stitched triangle can. Use the marker.
> - **Decide the mode before the sentences.** A section is a tutorial, a how-to, a reference, or an
>   explanation — the four Diátaxis shapes. Decide the mode of each section before writing it; when a
>   document serves two modes, separate them visibly rather than braiding them into one paragraph. A how-to
>   written as an explanation confuses the reader who wanted steps. Fix the shape first; the prose follows.

Those are the three skills that ship with the book. I hope they are of use.

## Worked examples

<!-- section-terms: self-governance, governance-catalogue -->

Shipping the method as skills is one project's answer to a pattern the industry is finding in
parallel: encoded knowledge is an asset that compounds, and each site accumulates it. Read the
three below as moves on a path a normal team can start walking, not as platforms to envy — Part VI's
[MAGE in the Wild](6.6-where-mage-fits.html) sets six such systems side by side as evidence the moves travel.

<!-- worked-examples: institutional-knowledge-capital -->
### Example — Shopify
Shopify runs the same move at organizational scale: every agent session runs in public and
becomes a searchable artifact the company mines into skills and defaults, so a lesson one
engineer learns becomes the whole company's the next day. The move a team can copy is making the
work visible and mining it; the org-wide memory is where the path leads.

### Example — Zenseact
Zenseact, the knowledge-routing case, federates the move: a central team owns the runtime while
each domain team contributes an agent as little more than a directory holding a config and a
skill, domain expertise accreting as reusable skills a router surfaces on demand.

<!-- takeaway -->
The shared move is *institutional-knowledge-capital*: hard-won engineering knowledge becomes an
encoded, reusable asset that compounds, so the next agent inherits it instead of re-deriving it.
DocAble ships that capital as installable batteries — three mastery-skills plus a catalogue of
governance mechanisms grown from real failures; Part V tells that story in full.

## The patterns

<!-- section-terms: governed-environment, governance-conversion -->

A pattern is a move the method makes again and again, in a form you can reuse.

<!-- point: bootstrap-from-the-environment-you-already-own | Bootstrap from the environment you already own. | terms: brownfield-migration, governed-environment -->
**Bootstrap from the environment you already own.** Do not wait for a clean start. A drifted wiki is an immature model; a legacy test suite is a floor to refactor over; a decades-old schema is a representation an agent can already reason through. Begin at the lowest rung that pays and strengthen the representation only when a recurring engineering question earns the next one. ([Brownfield](4.2-brownfield.html).)

<!-- point: reach-for-a-constraint-first-add-a-sensor-for-the-rest | Reach for a constraint first; add a sensor for the rest. | terms: constraint, sensor -->
**Prefer a constraint; add a sensor for the drift you cannot scope away.** A constraint prevents the mistake inside the iteration, so the wrong move is never available to pick and no failed loop is spent catching it. A sensor lets the mistake happen and catches it after, at the cost of an iteration. Build the constraint where you can; reach for the sensor only for the drift a constraint cannot foreclose. ([The Governed Environment](3.3-the-governed-environment.html).)

<!-- point: determinize-what-you-know-convert-what-you-learn | Determinize what you know; convert what you learn. | terms: governed-environment, ex-ante-governance, ex-post-governance -->
**Determinize what you can specify up front; convert every recurring surprise into a mechanism.** Write down the rules you know before the first line of code and give each a cheap deterministic check. Then watch the work run, and turn each failure you did not foresee into a durable control. Most real mechanisms come from the second half, not the first. ([The Governed Environment](3.3-the-governed-environment.html), [Governance Conversion](4.1-the-mage-workflow.html).)

<!-- point: audit-drain-promote-to-wear-a-lint-into-a-legacy-tree | Audit, drain, promote to wear a lint into a legacy tree. | terms: make-lint-blocking, thesis-alignment -->
**Wear a control in with audit, drain, promote.** Land a new check advisory: every finding reported, no commit blocked, so it never breaks an agent in flight. Drain the findings to zero with ordinary work. Only then flip it to blocking, so the class can never return. The order is the safety — flipping a check to blocking while findings remain breaks every agent's commit at once. ([Brownfield](4.2-brownfield.html).)

<!-- point: ask-the-deterministic-question-against-a-model | Ask the deterministic question against a model, not the code. | terms: model-as-map, generative-validation -->
**Route the agent's judgment through a model, not the code.** Where you own a structured representation — a schema, a state model, a solver — ask it whether the answer is right, instead of asking a language model whether the code looks correct. Choose the coarsest abstraction that can express the property you need; a finer model costs more to write and run without always buying a stronger guarantee. ([Brownfield](4.2-brownfield.html).)

<!-- point: generate-to-falsify-admit-only-what-survives | Generate to falsify; admit only what survives. | terms: generative-validation, thesis-alignment -->
**Generate evidence built to falsify a claim, and admit only the claim that survives.** Do not accept an agent's work on its own word. State the property the output must obey across the whole input space and hand a generator the job of hunting a counterexample; where an untrusted-bytes boundary has no law worth stating, fuzz it and fix each finding to the stable point in the specification, not the failing seed. ([Validation with Agents](4.3-validating-change.html).)

<!-- point: never-add-metadata-without-a-consumer | Never add metadata without a consumer. | terms: governance-package, governed-environment -->
**Never add metadata without adding a consumer.** A tag, a backlink, an ownership field, a machine-readable mirror — each earns its place only when an audit, a brief, a retrieval step, an analysis, or a gate reads it. Metadata with no reader is one more surface free to drift. ([Brownfield](4.2-brownfield.html).)

<!-- point: package-the-procedure-so-the-work-becomes-delegable | Package the procedure so a class of work becomes delegable. | terms: mastery-skill, governance-conversion -->
**Encode the procedure, and a class of work becomes delegable.** When you find yourself re-teaching the same discipline to every fresh agent, package it: the knowledge it needs plus the decision procedure for applying it, triggered by the work in front of it. A method that lives in memory is the first thing velocity drops. ([The Skills](4.4-the-skills.html).)

<!-- point: govern-the-accumulated-governance | Govern the accumulated governance. | terms: governance-graph, soft-vs-hard-governance -->
**Treat the pile of controls as a system in its own right.** Every control can be correct and the system of controls still be wrong. Keep three views over one control set: a catalogue of what exists, a collision graph of which two make incompatible demands on a shared resource, and a coverage census of which target has nothing watching it at all. ([When Guardrails Collide](3.6-when-guardrails-collide.html).)

## The anti-patterns

<!-- section-terms: teetering-tower, constraints-and-sensors -->

An anti-pattern is a move that looks reasonable and fails predictably. Learn its shape so you catch yourself making it.

<!-- point: the-teetering-tower-of-governance | The teetering tower — upkeep outweighs benefit. | terms: teetering-tower, right-level-of-enforcement -->
**The teetering tower.** Governance whose maintenance costs more attention than the failures it prevents. Three symptoms: agents spend more time servicing controls than doing product work; false positives dominate, the checks crying wolf more than they catch; the controls guard failures that are both low-cost and low-frequency. When you see one, price the upkeep and size it down. ([The Skills](4.4-the-skills.html).)

<!-- point: all-sensors-and-no-constraints | All sensors, no constraints — removes no failure class. | terms: sensor, constraint -->
**All sensors, no constraints.** The purely organizational answer to an unreliable worker wraps it in process: a review, an approval, an evidence trail, a sign-off. Every one of those is a sensor that inspects the output after the fact. It can raise the odds and shrink the blast radius, yet it never removes a failure class, because it watches the action space instead of scoping it. ([The Governed Environment](3.3-the-governed-environment.html).)

<!-- point: words-alone-are-a-probability-flip | Words alone are a probability flip. | terms: soft-vs-hard-governance, constraint -->
**Trusting words to hold.** Tell an agent "always follow this template" and it will agree and then not reliably do it, because an instruction is a probability flip: a prompt raises the odds, it does not settle them. Guidance aims a reasoner; it cannot block one, and it rots. Determinize the instruction into a condition the environment enforces. ([The Governed Environment](3.3-the-governed-environment.html).)

<!-- point: flipping-a-check-to-blocking-with-findings-open | Flipping a check to blocking with findings still open. | terms: make-lint-blocking -->
**Promoting a control before the tree is clean.** Flip a check to blocking while findings remain and you break every in-flight agent's commit at once. The promotion is safe only in one order: advisory first, drained to zero, then blocking. ([Brownfield](4.2-brownfield.html).)

<!-- point: trusting-a-done-claim | Trusting a done claim. | terms: done-is-a-claim, drift-gate -->
**Trusting "done" as a fact.** An agent reporting a task complete is describing its intent, not the state of your repository, and the two drift apart constantly — a sibling change broke a test, a marker rotted, the thing it "verified" quietly routed through a fallback. Re-run the gates yourself, at HEAD, and let a fact answer where a claim was offered. ([The Skills](4.4-the-skills.html).)

<!-- point: the-mirror-that-agrees-with-the-bug | The mirror that agrees with the bug. | terms: residual, mirror-vs-spec -->
**Expecting a derived model to catch an unspecified absence.** A missing authorization check has no failing test by definition — if a test caught it, the check was specified. A model read off the code records the missing check as correctly absent, and the drift gate agrees with the bug. A mirror cannot see what was never specified; some goals stay a human job, and naming that residual honestly is what makes the mechanized core credible. ([The Governed Environment](3.3-the-governed-environment.html).)

<!-- point: patching-the-seed-not-the-spec-point | Patching the seed, not the spec point. | terms: stable-spec-point, fuzzing -->
**Fixing the failing input instead of the class.** When a generator surfaces a crash, patching the exact bytes leaves every neighbouring input that would break the same way. Trace the failure back to the point in the specification the input violated and fix that, so the fix covers every input the format allows, not the single seed that tripped it. ([Validation with Agents](4.3-validating-change.html).)

<!-- point: the-invoice-level-metric | The invoice-level metric reports but cannot act. | terms: measure-one-level-deeper -->
**Steering by a surface number.** A whole-project cloud bill tells you to pay the invoice and nothing about what to change; "the suite covers 87% of lines" reports and does not name which untested code matters. A metric earns its place only when it drives a decision, and the surface number usually cannot. ([Metrics](3.5-metrics.html).)

<!-- point: reactive-growth-leaves-a-target-un-watched | Reactive growth leaves a target un-watched. | terms: governance-graph, governance-conversion -->
**Growing controls only where it last hurt.** Convert failures reactively and the control estate grows toward the targets that already failed, while a target that has never bitten draws nothing. The reactive discipline, left to itself, leaves whole targets structurally un-watched — a blind spot no single control's code reveals. Audit the balance proactively across every target. ([When Guardrails Collide](3.6-when-guardrails-collide.html).)

## The heuristics

<!-- section-terms: right-level-of-enforcement, measure-one-level-deeper -->

A heuristic is a judgment rule for the calls no pattern makes for you.

<!-- point: size-by-cost-times-frequency-architecture-first | Size by cost times frequency; architecture before controls. | terms: right-level-of-enforcement -->
**Size by cost times frequency.** How hard a mechanism a failure earns turns on two factors multiplied: how much the failure costs, times how often it happens. Cheap-and-rare you leave to judgment. Cheap-and-frequent earns a lint or script. In the costly column, prefer architectural prevention — make the mistake impossible — with a gate as the immediate floor. The costly-and-frequent corner earns both. Escalate one tier when the failure is hard to detect, hard to reverse, or legally intolerable. ([Brownfield](4.2-brownfield.html).)

<!-- point: take-the-next-rung-when-a-recurring-question-earns-it | Take the next rung when a recurring question earns it. | terms: brownfield-migration, governed-environment -->
**Climb for a question, not the view.** Take the next rung of representation when a question you keep re-answering by hand would stop recurring once the model could answer it for you. Do not build a complete executable model for its own sake; strengthen the representation only where a real reasoning problem pays for the rung. ([Brownfield](4.2-brownfield.html).)

<!-- point: guidance-aims-machinery-holds | Guidance aims; machinery holds. | terms: soft-vs-hard-governance -->
**Know whether you are minting a soft mechanism or a hard one.** A soft mechanism — a brief, a house rule, a structured model that aims the agent's reasoning — raises the odds but cannot block, and it rots. A hard one — a lint, a gate, a typed seam — holds the line regardless of whether the agent cooperates. Never claim a mechanism is enforced when you have only recommended it. ([The Skills](4.4-the-skills.html).)

<!-- point: convert-dont-just-repair | Convert, don't just repair — audit becomes lint. | terms: governance-conversion -->
**Convert, don't just repair.** When a failure smells class-level, do not only patch the instance — build the durable mechanism that kills the class. Today's audit finding, a thing you noticed by reading, is tomorrow's lint, a thing the machine notices for you. A bug in more than one file means "fix the sites and add the check," not "fix the sites and hope." ([The Skills](4.4-the-skills.html), [Governance Conversion](4.1-the-mage-workflow.html).)

<!-- point: the-second-time-a-failure-shows-up-it-earns-its-mechanism | The second time a failure shows up, it has earned its mechanism. | terms: governance-conversion -->
**Let recurrence be the trigger.** A failure seen twice — sometimes once, if it was bad enough — is the clue that you are either failing to detect the problem, so you need a sensor, or failing to prevent it, so you need a constraint. Recurrence is the signal that a mechanism is owed. ([Governance Conversion](4.1-the-mage-workflow.html).)

<!-- point: measure-one-level-deeper | Measure one level deeper. | terms: measure-one-level-deeper -->
**Measure one level deeper.** Ask what decision the measurement must drive, and measure the level just below the surface number so the data can act rather than merely report. Split the cloud bill by service and the dominant one names your first target; measure coverage against the model's named invariants and it names the gap instead of hiding it in a percentage. ([Metrics](3.5-metrics.html).)

<!-- point: choose-the-fitness-function-then-the-cheapest-abstraction | Choose the fitness function, then the cheapest abstraction that enforces it. | terms: fitness-function -->
**Define correctness first; it fixes the abstraction level.** Correctness is not one thing — it means one thing for security, another for semantics, another for privacy — and the definition tells you the grain you need. Write down what correct even means, then pick the coarsest model that can express it and the cheapest analysis that enforces it. ([Brownfield](4.2-brownfield.html).)

<!-- point: harvest-real-producers-before-hand-rolling-a-grammar | Harvest real producers before hand-rolling a grammar. | terms: producer-dialect-corpus -->
**Harvest real producers before hand-rolling a generator.** A grammar you write yourself covers only the dialects you thought to encode. The format's independent producers have already generated the legal-but-unusual space for you, a breadth no single authored grammar reaches. Reach for a from-scratch generator only where no real producer exists. ([Validation with Agents](4.3-validating-change.html).)

<!-- point: orient-positive-before-you-hunt-a-break | Orient positive before you hunt a break. | terms: lifecycle -->
**Know the healthy baseline before you chase a failure.** State what "normal" looks like for each lifecycle first. Most sessions are steady-state, and you cannot recognize a break until you can name the shape it broke from. ([The Skills](4.4-the-skills.html).)

## The checklists

<!-- section-terms: governance-conversion, right-level-of-enforcement -->

A checklist turns a pattern into something you run on Monday.

### Starting a brownfield migration

<!-- point: the-brownfield-loop-in-five-moves | The brownfield loop, in five moves. | terms: brownfield-migration, missing-model-metric -->
The three migration approaches — top-down from intent, bottom-up from code, and lint-cover-then-induce — run as one repeating loop, short enough to keep on a card ([Brownfield](4.2-brownfield.html)):

1. **Find the stable abstractions** — the spine your quality case actually rests on, not every function.
2. **Model only those** — top-down from intent, bottom-up from code, meeting at the grain the property lives at.
3. **Drift-gate the model** — a check that fails when code and model disagree, worn in audit-only, then drained, then blocking.
4. **Measure the orphans** — walk each test to the code it exercises and ask whether that code traces to any model node; each orphan cluster is the next model you owe.
5. **Repeat** — the metric hands you the next stable abstraction, and the loop turns again.

### Minting a new mechanism

<!-- point: the-minting-reflexes | The minting reflexes. | terms: right-level-of-enforcement, constraint, sensor -->
When a failure recurs and a mechanism is owed, run the reflexes before you build ([The Skills](4.4-the-skills.html), [The Governed Environment](3.3-the-governed-environment.html)):

- **Name the failure class**, not the instance — if you cannot name the recurring failure, it is not a mechanism yet.
- **Ask prevent or catch** — a constraint that scopes the action away, or a sensor that catches the drift.
- **Ask soft or hard** — a mechanism that aims the agent, or one that holds regardless.
- **Size it** by cost times frequency; reach for architecture before a control, and price the mechanism's own upkeep before you build it.
- **Check with the engineer** on any wall — every wall you raise also constrains the agent, so place it with care.

### Sizing a mechanism

<!-- point: the-sizing-matrix-as-a-decision-aid | The sizing matrix as a decision aid. | terms: right-level-of-enforcement, teetering-tower -->
Cross how much a failure costs against how often it happens; each cell names the smallest change that still closes the class ([Brownfield](4.2-brownfield.html)). [ref:sizing-matrix-fieldguide]

<!-- label: sizing-matrix-fieldguide -->

| Cost times frequency | Rare failure | Frequent failure |
|---|---|---|
| **Cheap** | Leave it to judgment. A mechanism here is the first brick in the teetering tower. | A cheap lint or script — the tokens agents burn working around it are real cost. |
| **Costly** | A runbook with a named escape; a blocking gate once the failure's shape is decidable. | Prevention first where feasible: a structured model that makes the mistake impossible, with a gate as the immediate floor. This corner earns both. |
| **Any cell** | Escalate one tier when the failure is hard to detect, hard to reverse, or legally intolerable. | Escalate one tier. |

### Choosing a validation strategy

<!-- point: the-generative-validation-decision-aid | The generative-validation decision aid. | terms: generative-validation, oracle -->
Read the signal in the code under test and reach for the technique whose oracle fits ([Validation with Agents](4.3-validating-change.html)):

- **A stated law over structured inputs** — a round-trip, a content-preservation guarantee, an ordering — reaches for a **property test**; the law is the oracle you can already write down.
- **An untrusted-bytes boundary** with a never-crash contract and no per-input law worth stating reaches for a **coverage-guided fuzzer**; fix its findings to the stable specification point, not the seed.
- **A structured model** with a declared legal-outcome set or invariant reaches for **fuzz plus the model** — point wild inputs at the model's surface and judge against its declared classes; where a real third-party producer exists, let its dialect be the corpus.
- **A concurrency invariant** reaches for a **state-model search** — a property test for a local state predicate, a systematic or bounded interleaving search for a temporal one.

### Auditing your governance estate

<!-- point: the-three-views-over-one-control-set | Three views over one control set. | terms: governance-graph, soft-vs-hard-governance -->
Turn the method on the governance system itself, keeping three views over the same set of controls ([When Guardrails Collide](3.6-when-guardrails-collide.html)):

- **The catalogue** — what controls exist, one row each.
- **The collision graph** — which two controls make incompatible demands on a shared resource; route the mechanically decidable edges to a sensor and the semantic ones to a human.
- **The coverage census** — bin every control by the target it guards, and surface the target with nothing watching it, or with only soft aims and no hard hold.

## The Engineer's Day

<!-- point: the-day-runs-the-loop-through-instruments | The engineer's day runs the loop through instruments. | terms: governance-conversion, lifecycle -->
The workflow chapter walked the loop one turn at a time. Here it is again, not as a diagram but as a desk. Through the day the engineer does not think in named phases; they read instruments, and the instruments carry the loop for them. Each panel below distils a fuller card in the operator's reference. The panel is the working summary. The card is the full face.

### Morning: read what the night left

<!-- point: morning-routes-attention-before-it-spends-any | The morning routes attention before it spends any. | terms: governance-conversion, missing-model-metric -->
The day opens the way the loop's daily rhythm already promised: you read what broke while you slept. Five questions route that read. Are the models healthy? Did any failure recur? Did anything move the wrong way since yesterday? Any regressions? Anything that should become infrastructure? Each question resolves to one instrument, so the morning review is a routing pass, not a sixth gauge. Its automated twin fires the same five between sessions, and the reflex does not wait on you to remember. ([Daily Review](appendix-d-daily-review.html).)

<!-- point: two-health-reads-answer-most-of-the-morning | Two health reads answer most of the morning. | terms: model-as-map, drift-gate -->
Two of those questions are health reads, and they share one face each. **Are the models still equal to the code?** Drift gates green, the Missing-Model surface draining toward its chosen floor, the traceability graph resolving every claim with no dangling anchors, each model regenerated inside its sync window. Green across the four rows and you can reason through the model instead of the code. **Is the environment running right?** Read the churn curve first, because it names which build phase you are in and healthy churn peaks at mechanization then collapses; then confirm the sync gates hold and the validators still exercise the corpus. ([Model Health](appendix-d-model-health.html), [System Health](appendix-d-system-health.html).)

### The instruments on the desk

<!-- point: the-dashboard-splits-steering-from-certifying | The dashboard splits what you steer by from what you certify with. | terms: measure-one-level-deeper, right-level-of-enforcement -->
Behind the morning read sits one panel that holds every metric the build acts on, split into two bands. You steer by the formative band while the work is in flight. You certify with the summative band once it matures.

> ### The operator's dashboard
>
> - **Steer by it (formative)** — the Missing-Model drain that points you at the next orphan cluster, velocity and churn reading which build phase you are in, and the coverage oracles that say whether the generator exercised the whole input space. These pick your next move.
> - **Certify with it (summative)** — the model's token-savings against its context budget, the support-ratio and control-growth curves, and the Epic-closure rate that separates durable throughput from raw output. These grade the program.

Choose the band you need and scan it. The metrics reference one level down steers a single iteration; this panel steers the whole program. ([The Operator's Dashboard](appendix-d-operators-dashboard.html).)

### Midday: where judgment goes

<!-- point: watch-where-attention-lands-and-convert-the-repeats | Watch where attention lands; convert what you keep deciding by hand. | terms: governance-conversion, right-level-of-enforcement -->
Through the middle of the day one reflex runs under everything: watch where your attention actually lands. Attention on architecture and validation is the system working as designed, the scarce and intended work. Attention rising on reading code is a model gap asking to be closed. Attention going to emergencies is a failure class asking to be converted. And any decision you make by hand more than once is a candidate to become infrastructure. That last move is the engine of the whole loop, a repeated judgment turned once into a mechanism and then spent for free on every later change. ([Human Judgment](appendix-d-human-judgment.html).)

### Before you ship: the preflight

<!-- point: certify-a-release-from-gates-not-from-feel | Certify a release from gates, not from feel. | terms: generative-validation, done-is-a-claim -->
A release is not cleared from feel. A pilot does not certify a plane by how it looks, and a MAGE operator does not certify a release by how the week went. Run the preflight instead, where every box reads a gate already built rather than a fresh judgment.

> ### Release preflight
>
> - **Models current** — regenerated at HEAD, the Missing-Model surface within its floor.
> - **Model–code parity** — the drift and parity gates report the two equal.
> - **Validators pass** — correctness, conformance, and the coverage oracles exercised and green.
> - **Fidelity acceptable** — the content still means what it meant before the transformation.
> - **Gates passing** — the staged-deploy staircase green end to end.
> - **Overrides reviewed** — every escape hatch since the last release read and understood, not silently inherited.
>
> Six green, cleared to ship. Any red, the release waits.

([Release Readiness](appendix-d-release-readiness.html).)

### What the day makes of you

<!-- point: the-day-names-three-competencies-part-six-develops | The day points at three competencies Part VI develops. | terms: thesis-modeling, thesis-alignment, governance-conversion -->
Run enough of these days and the shape of the work stands out. The reading is not overhead around the job; it is the job the engineer's seat became. Three competencies come to dominate it: **model design**, **governance design**, and **evidence engineering** — authoring the language the fleet reasons through, turning a failure class into a mechanism that holds, and building an environment whose output can be consumed as assurance. Part VI takes up what that does to the profession itself. Here it is enough to have watched the day that produces it.
