# Operating MAGE

<!-- point: agent-knows-git-not-your-environments-lifecycles-so-write-them-down | The agent lacks your operating context; write it down. | terms: lifecycle, runbook -->
The workflow runs a change, migration gets a system onto the method, and validation tells you a change is good. One practical question is left: how do you keep the whole thing running? You know what to do when the disk fills up, when two branches conflict, when an incident pages you at 2 a.m. You know it so well you barely notice you know it. The agent knows none of it. Out of the box it knows how to commit to Git; what it does not know is the life cycle of *your* engineered environment. The disk fills, and here is what to do when the disk fills — that instruction will never be in the agent's context unless you put it there. It has no operating context, no sense of "how we do things around here," and the more of that judgment your operation runs on unwritten, the more helpless the agent is the moment the healthy path ends. So a governed environment for real work writes the knowledge down — as lifecycles, as the runbooks that ride on top of them, and as the honest readings that let both steer.

<!-- point: written-down-operating-judgment-becomes-authority | Written down, operating judgment becomes authority over the fleet. | terms: lifecycle, thesis-alignment -->
Written down, that judgment is operational intent made explicit — and this chapter's move is to give it authority. A lifecycle names the healthy path and the way out of each failure; a runbook encodes each prohibition as a mechanism at the right level where it can. That is the alignment ladder applied to operations: intent stated as an invariant, then held by the environment rather than left to whoever is awake at 2 a.m. Operating MAGE is those two things and one more — lifecycles, runbooks, and the metrics that let a loop read its own state — run as one recurring rhythm.

## The lifecycle as a model

<!-- section-terms: lifecycle, failure-mode-effects-analysis -->

<!-- point: a-lifecycle-is-the-healthy-path-then-a-failure-map-off-each-node | A lifecycle: write the healthy path, then map failures. | terms: lifecycle -->
<!-- index-def: lifecycle -->
Start with the lifecycles, because everything else hangs off them. A lifecycle is the correct operation of one recurring activity: how a bug report moves from filed to fixed, how a feature moves from design to shipped. Write the healthy path first. Then, from each node on that path, map the failure states — the ways this step can go wrong — and for each failure, the action to take. Think of it as a grid: every node crossed with every symptom, and in each cell, what to do.

<!-- point: fmea-names-the-way-out-and-the-prohibition-because-the-agent-knows-neither | FMEA-inspired: name each failure's way out and prohibition. | terms: failure-mode-effects-analysis -->
<!-- index-def: failure-mode-effects-analysis -->
This grid is **FMEA-inspired**, after *failure mode and effects analysis* — the reliability practice that enumerates how a thing can fail and what each failure costs. Full FMEA weighs more than the book borrows: each failure's causes, its severity, how often it occurs, how readily it is detected, and the priority ranking that falls out. The book takes the enumeration and adds the part people skip — how to get *out* of each failure again. You know how to get out. If two branches conflict, you read both sides, work out what each was trying to accomplish, and reconcile them. If the disk fills, you find the fat part of the system — the cache, usually — and wipe it. The agent knows none of this. So you coach it: where the hot points are, and, in every failure path, what is *not allowed*. Encode the prohibition as a mechanism at the right level where you can — a Git hook, an agent hook — and where you cannot, tell the agent plainly.

> *A footnote on the disk-fills failure.* Left to itself, an agent that needs to free a full
> disk may reach for the biggest lever it can name — `rm -rf /` will certainly free the space.
> That is not a hypothetical; agents really do it. It is exactly why you coach the hot points
> *and* the prohibitions, rather than trusting it to guess which fat is safe to trim.

<!-- point: name-the-sin-and-the-way-out-not-the-prohibition-alone | Pair each prohibition with its sanctioned way out. | terms: pink-elephant -->

> **Principle — Pair every prohibition with a sanctioned recovery path.** Naming a forbidden act
> raises an honest worry: does saying "don't" plant the very idea, the way telling someone not to
> picture a pink elephant paints one? In practice the naming helped — but only when the escape was
> named alongside the ban. My orchestrator kept reaching for a destructive Git command to bail out of
> a stuck merge, the one that resets the branch and silently discards the changes already applied, and
> twice lost committed work that way. A bare "never abort the merge" leaves the agent stuck with
> nowhere to go. What worked was pairing the forbidden command with the sanctioned one that clears the
> stuck state *without* dropping the applied work, so the rule reads "not that lever, this one." Name
> the sin alone and you may plant the temptation; name the sin *and the way out*, and you replace it.

<!-- point: the-fleet-itself-runs-on-a-lifecycle-you-can-check | The fleet itself runs on a lifecycle you can check. | terms: agent-orchestration-model, method-parity, lifecycle-soundness -->
<!-- index-def: agent-orchestration-model -->
The sharpest lifecycle is the one the fleet itself runs on. Point the same discipline at the substrate that *produces* the software and you get the **agent-orchestration model** — the agent's own life written as a typed state machine (`Dispatched → Working → Landed → Tombstoned`, with `Abandoned` and recovery), and the orchestrator's refill-and-bank loop written as the journey that drives it. It assesses **lifecycle soundness**: a tombstone before a commit, or a landed agent that never tombstones, is an illegal transition a checker catches. The move worth naming is **method parity** — the substrate that produces the software is governed by the same tier-derivation and drift machinery pointed at the product, so "is the fleet as checkable as what it ships?" becomes a checked property rather than a hope. The lifecycle state machine is the construct the journey runs on, and its one liveness invariant — *a landed agent eventually tombstones* — routes to a temporal checker.

> Learn more about this governance mechanism: [agent-orchestration model](appendix-b-agent-orchestration-model.html).

<!-- point: dont-trust-a-done-claim-re-run-the-gates-yourself | Don't trust a done claim; re-run gates. | terms: done-is-a-claim, drift-gate -->
That state machine is also why an operator never takes a report at face value. **"Done" is a claim, not a fact.** An agent reporting a task complete is describing its *intent*, not the state of your repository, and the two drift apart constantly — a sibling change broke a test, a marker rotted, the thing it "verified" quietly routed through a fallback. So you do not trust the claim. You re-run the gates yourself, at HEAD, and let a fact answer where a claim was offered. The lifecycle names `Landed` as a state with an entry condition; re-running the gates is how you check the transition actually fired.

## Runbooks: determinize the runnable, brief the judgment

<!-- section-terms: runbook, deterministic-vs-judgment-split -->

<!-- point: a-runbook-splits-into-deterministic-and-judgment-steps-governed-differently | A runbook splits into deterministic and judgment steps. | terms: runbook, deterministic-vs-judgment-split -->
<!-- index-def: runbook -->
Once the healthy path and the failure map are written, the thing you hand the agent is a **runbook** (or playbook): the steps to take, whether recovering from a failure or working a fresh ticket. The one discipline that makes a runbook work is to split it into two kinds of step — the deterministic and the judgment-laden — because the two are governed completely differently. [ref:runbook-split] fences the one judgment step between two deterministic ends.

> Learn more about this governance mechanism: [runbook](appendix-a-operational-playbooks.html).

Fencing the one judgment step between deterministic ends bounds the messy part and leaves a logged trace a checker can grade. -->

### The deterministic parts get tools

<!-- point: deterministic-parts-get-tools-not-improvisation | Deterministic steps get executable tools, not improvisation. | terms: deterministic-vs-judgment-split -->
<!-- index-def: deterministic-vs-judgment-split -->
Anything that has a single correct outcome should be an executable script the agent runs, not a procedure it improvises. Leave it to improvisation and it will get it right most of the time — and you will wish you had automated it the one time it does not.

<!-- point: determinizing-a-step-buys-a-trace-with-two-consumers | Determinizing buys a trace with two consumers. | terms: reasoning-trace, deterministic-vs-judgment-split -->
Determinizing a step buys you more than a reliable outcome — it buys an **inspectable execution trace**. An improvised step leaves nothing behind: its run is smoke, gone the moment it finishes. Pin the step to an executable procedure and the run becomes a record — the inputs it read, the branch it took, the value it produced — in a fixed shape you can replay and compare. Be precise about what that trace is: it is evidence of *what ran*, not the *reasoning* for why a branch was right. That rationale is a separate record, logged around the judgment step when it makes the call.

The trace earns its keep through two consumers. The first is **the next turn of the loop**: last run's trace is this run's input, so the agent starts from what was already established instead of re-deriving it, and the loop converges instead of wandering. The second is **a checker that reads the trace itself** — a reviewer, human or agent, that never watched the step run but can audit the path it took and flag a run that went where it should not. A bare judgment step gives you a verdict; a determinized step gives you a trace to hold that verdict to account.

### The judgment parts: the roughest algorithm that still fits

<!-- section-terms: deterministic-vs-judgment-split, rubric -->

<!-- point: judgment-parts-get-the-roughest-algorithm-that-still-fits | Judgment steps get the roughest algorithm that fits. | terms: conditioning-the-search -->
**The judgment parts get the roughest algorithm that still fits.** For a well-constrained decision, write the algorithm down and let the agent do the glue. For an open-ended one — a cyber threat hunt, where the premise is that the attacker did something you never anticipated — do not over-constrain: give heuristics and strategies to explore, and stop there. Remember that you are biasing the search: steer it down the wrong path and it will never reach the place you wanted. So if you do not know how to do the thing, do not write as though you did — give hints. If you truly do not know, say "solve this open-endedly," and accept the trade: the looser the guidance, the more tokens the agent spends, and the less likely it is to land.

<!-- point: a-judgment-that-is-a-measurement-gets-a-rubric | A judgment that is a measurement gets a rubric. | terms: rubric -->
<!-- index-def: rubric -->
When a judgment step is really a *measurement*, give it a **rubric**. You cannot write a checker for "is this painting good" or "is this student essay good," but you can break the question into parts a reader can assess: how are the topic sentences, how is the technique, are there grammatical errors, are there blotches from bad storage? Against a rubric the agent makes real judgments — grading each dimension and returning feedback good enough to act on. What stays with a person is the *final verdict on taste*, the whole-work call the rubric deliberately declines to reduce to a threshold.

<!-- point: the-pre-canned-brief-is-the-strongest-form-templating-delegation-itself | The pre-canned brief templates delegation itself. | terms: pre-canned-brief -->
<!-- index-def: pre-canned-brief -->
The strongest form of this is the **pre-canned brief**. When an orchestrator agent hands work to a sub-agent, you do not want it inventing, each time, how to explain the task. You want a template it adapts — the work already articulated in writing. The companion repository leans on exactly this: every dispatch is composed from a template that pre-places the required instructions, and a brief-linter checks the template is intact before the agent launches. The delegation itself becomes a governed step, not a fresh improvisation each time.

> Learn more about this governance mechanism: [brief-linting](appendix-a-brief-linting.html).

<!-- point: typing-each-runbook-step-makes-the-deterministic-judgment-split-mechanical | Typing each step makes the deterministic-judgment split mechanical. | terms: deterministic-vs-judgment-split, runbook -->
The split has a mechanical form once you write runbooks at scale. Type every step as one of three kinds, and let the type decide how the step is governed. A deterministic step is *runnable*: it carries the exact tool line to run. The judgment steps divide by whether an agent can take them. A *judgment-automatable* step carries a pre-canned brief the orchestrator dispatches to a strong model, the missing middle between "run this" and "you decide." A *judgment-irreducible* step carries the words to surface to the person, because the call must stay theirs. [ref:runbook-step-kinds] gives the three kinds and what each must carry. Typing the step makes the shape checkable: a tool line on a judgment step, or a dispatched brief on a runnable one, is a contradiction a linter catches before the runbook ships. The failure map from the last section joins the same way, each symptom routed to its runbook by its class rather than its exact error text, so a fresh failure that rhymes with a known one still finds the way out.

<!-- label: runbook-step-kinds -->
<!-- table: *The Three Step Kinds.* What each kind must carry and how each is governed: a deterministic step runs a tool, while the judgment steps split by whether an agent or a person decides. Typing the step makes the split mechanical — a mismatch is a lint finding. [short: Typing a runbook's steps] -->
| Step kind | What it is | What it must carry | How it is governed |
|---|---|---|---|
| Runnable | A deterministic step with one correct outcome | The exact tool line to run | The tool runs it; its logged trace is what a second checker reads |
| Judgment-automatable | Reasoning no script can do, but a strong-model dispatch can — the missing middle | A pre-canned brief the orchestrator dispatches | A brief-linter checks the brief is intact before launch |
| Judgment-irreducible | Reasoning that must stay with the person | The words to surface, and why | Surfaced to the operator, never dispatched |

The split is no DocAble idiosyncrasy. Systems that share no code and answer to different regulators reach for the same fence between the step a machine can decide and the step that needs a mind.

<!-- worked-examples: determinization -->
### Example — Siemens
Siemens draws the same fence as a clean division of labor across a safety-critical toolchain: probabilistic semantic reasoning upstream, deterministic physics and verification downstream. The decidable obligation — does the design satisfy its specified constraints — lands on a deterministic mechanism, while the open-ended reading of intent stays with the model. The division is the design, not an afterthought bolted on once the model proved unreliable.

### Example — Zenseact
Zenseact hardened three judgments that other sites leave probabilistic. Execution runs through deterministic tools, authority is settled by an explicit permission table rather than the agent's discretion, and context selection is decided by a TF-IDF router instead of a guess. Each was a step that could have been improvised and was instead pinned to a repeatable mechanism, so the same input takes the same path every run.

### Example — Docker {counter-example}
Docker is where the pattern fits awkwardly, and the awkwardness teaches the boundary. Its agents determinize what carries hard evidence — the tests run as deterministic gates — but the admission decision is kept deliberately probabilistic, an independent reviewer plus a human, because collapsing that call to a threshold would forfeit the very judgment it exists to weigh. Docker does not disconfirm the rule; it determinizes the tests and *declines* to determinize admission, marking by choice the line the discipline itself draws between the two kinds of step.

### Example — DocAble
DocAble's accessibility pipeline is built on the split. The structural work — reading a document's tag tree, checking reading order, rewriting the parts that have one correct shape — runs as deterministic tools that leave a replayable trace. The judgment-laden work — describing an image, naming what a figure is *for* — routes to a model against a rubric, because no script can write the alt text. Each step is governed by its kind, not run as one undifferentiated remediation pass.

<!-- takeaway -->
The shared move is *determinization*: separate the steps with a single correct outcome — which earn an executable tool and a replayable trace — from the steps that need judgment, which earn the roughest algorithm that still fits, and govern each by its kind.
<!-- worked-examples-end -->

<!-- point: operating-judgment-becomes-something-the-environment-holds | Written down, operating judgment becomes something the environment holds. | terms: lifecycle, runbook, deterministic-vs-judgment-split -->
Step back and this half of the chapter is one instruction wearing three shapes: a lifecycle writes down the healthy path and the way out of each failure, a runbook rides on top and splits every step by its kind, and the pre-canned brief hands that split to the next agent intact. What used to live only in your head — how the work is done here, and what must never be done — becomes something the environment holds and can enforce.

One thing the runbook still needs, the lifecycle cannot supply: something to steer by. Every loop it drives is blind without an honest reading of its own state — a metric.

## The sensing half: observe, diagnose, convert

<!-- section-terms: measure-one-level-deeper -->

<!-- point: a-metric-is-the-sensing-half-of-the-loop | A metric is the sensing half of the loop. | terms: loop-engineering, sensor -->
A loop takes an input, reasons, acts, and folds the result back around. The workflow chapter spent its words on the acting half; operating the loop needs the sensing half, because a loop with no honest sense of its own state cannot steer at all. A signal senses; a metric is a signal rendered as a measurement; a playbook acts on it and a mechanism enforces against it. The metric comes first, because the other two are blind without it. A playbook that fires on a number measuring the wrong thing does the wrong work; a mechanism grading on a number too coarse to name the fault blocks the wrong commit. So the question that governs every metric is not "can I measure this?" — almost anything can be counted — but "does this number drive a decision?"

### Measure one level deeper

<!-- point: measure-one-level-deeper-because-the-surface-number-cannot-act | Measure one level deeper; the surface number cannot act. | terms: measure-one-level-deeper -->
<!-- index-def: measure-one-level-deeper -->
John Ousterhout names the rule [cite: ousterhout2018]: **always measure one level deeper** — one level, not as deep as you can go. A metric earns its place only when it drives a decision, and the surface number usually cannot: the surface metric gives you the facts; one level deeper gives you the optimization targets.

<!-- point: a-cloud-bill-reports-but-splitting-it-by-service-acts | A cloud bill reports; splitting it by service acts. | terms: measure-one-level-deeper -->
Think of the cloud bill. It tells you what the whole project spent last month. That number is real, and useless: it tells you to pay the invoice, and nothing about what to change — which service to slim, which call to batch, which cascade to cut. Split the same bill by service and it starts to act. One service usually dominates, the rest trail off in a thin tail, and the dominant one names your first target. You measured one level deeper, and the deeper number carries a decision the shallow one buried.

<!-- point: line-coverage-is-the-invoice-level-number | Line coverage is the invoice-level number; go deeper. | terms: measure-one-level-deeper, line-coverage -->
The same trap hides in test coverage. "The suite covers 87% of lines" is the invoice-level number — a headline that reports and does not act. It cannot tell you *which* untested code matters, because a line in a throwaway string helper counts the same as a line in the job state machine. The metrics below run a spectrum from the hard, deterministic end to the soft, judgment-laden one, and the flagship in the middle is coverage measured one level deeper — coverage that names the gap instead of hiding it in a percentage. [ref:one-level-deeper-table] collects the move, and the wrong turn each surface number invites.

<!-- label: one-level-deeper-table -->
<!-- table: *Measure One Level Deeper.* For each surface number: the wrong move it invites, the decision it must drive, and the deeper cut that acts. [short: Measure one level deeper] -->
| Surface number | The wrong move it invites | Decision it must drive | Measured one level deeper |
|---|---|---|---|
| Whole-project cloud bill | Pay the invoice; nothing to change | Which service to slim, which call to batch | Cost split by service — one dominates and names the first target |
| "87% of lines covered" | Chase the percentage upward | Which untested code actually matters | Model-claim coverage — the named invariant no test exercises |

AI adoption is a contemporary version of the same measurement error. Counting AI-assisted pull requests, generated lines, token spend, or gross merge rate tells you activity changed; it does not tell you whether engineering improved. LinearB's 2026 benchmark moves one level deeper, pairing throughput with PR yield and rework [cite: linearb2026]; industry reporting, meanwhile, finds only 31% of teams measure AI's impact at all, and many who claim gains cannot show the gains survived downstream [cite: riggins2026]. The metric that acts reaches the engineering decision: what durable work arrived, at what quality, and at what cost in human attention and rework?

<!-- point: metrics-run-a-hard-to-soft-spectrum | Metrics run hard to soft; don't confuse the two. | terms: soft-vs-hard-governance -->
A **hard** metric is deterministic: a machine reads it, and the same input yields the same number every time. A **soft** metric is judgment-laden: it points a human or an agent at a place worth looking, but it cannot be reduced to a threshold that decides on its own. Both are worth having. The mistake is to treat one as the other — to block a build on a soft signal, or to leave a hard fact to a reviewer's memory. [ref:metric-spectrum] lays the metrics out from the hard end to the soft.

### The hard end: a number that feeds the model

<!-- section-terms: deployment-topology-model, measure-one-level-deeper -->
<!-- point: cold-start-latency-and-the-deeper-cause | The deeper cold-start number named runtime init. | terms: cold-start-latency, measure-one-level-deeper -->
Start at the deterministic end. A serverless fleet scales to zero; when a request wakes a cold instance, the user waits while the container boots and the runtime loads. The obvious way to read that wait is as the penalty of scaling from zero — measure it, and if it hurts, pay to keep a warm instance running. The obvious reading was wrong. The conformance service — a document validator wrapping a Java tool — carried a 4,057 ms *warm* floor, a wait no warm instance could remove. Measuring one level deeper named the cause: the Java tool ran as a subprocess launched once per request, so every call paid a fresh runtime startup. The fix was a re-architecture — keep the runtime resident instead of relaunching it — and the warm floor fell from 4,057 ms to 109 ms. The tempting surface explanation, that the images were simply too big, was also wrong: a 433 MB service cold-started fine. The barrier was runtime initialization, not image size, and only the deeper measurement said so.

<!-- point: a-model-sums-the-longest-cold-start-path | A model sums the worst-case cold-start path. | terms: deployment-topology-model, longest-path-sum -->
I found that tax by hand, spot-checking the one service whose latency looked wrong — and spot-checking does not scale. It catches the service that draws your eye, misses the ones that do not, and says nothing about how the services interact. The sharpest question is the *chain*: a request that lands when every downstream service is cold triggers a cascade of cold-starts along the critical path. So the worst case is a **longest-path sum** — each step contributes the slowest cold-start it waits on, and the path total is the sum of those per-step maxima. That sum, not the per-service number and not the fleet average, predicts the worst latency a real user can hit.

<!-- point: the-hard-ends-defining-move-is-the-number-feeds-the-model | The hard end's defining move: the number feeds the model. | terms: deployment-topology-model, executable-source-of-truth -->
Here the hard end shows its defining move: **the number feeds the model.** The cold-start measurements do not live in a dashboard a human reads and forgets. They land as typed fields on the deployment-topology model the fleet reasons through — a `cold_start_ms` and a `warm_ms` on each service's plane record. A recompute tool reads those fields and derives the longest-path worst case over the journey graph. When a later measurement writes a fresher number, the tool reads it live and the worst-case total refines on its own, no edit required. The measurement pipeline commits the refreshed values itself, under a bypass-prefixed housekeeping commit — because a runbook reminder to *commit the new numbers* rots, and the model drifts from the fleet it describes. Build the map's upkeep into the machine that changes the territory rather than asking a person to remember it.

> Learn more about this governance mechanism: [deployment-topology model](appendix-b-deployment-topology-model.html).

<!-- point: as-built-the-seam-is-in-and-the-data-catches-up | As-built: the seam is in, the data catches up. | terms: deployment-topology-model -->
As-built, the live-annotation path exists but is not yet populated — the tool runs off a snapshot table of measured values, each row citing the commit that measured it, because the fleet is mid-migration and no service carries the live annotation yet. The machinery to read the model live exists; the model is not fully fed. That is the ordinary shape of real work: the machinery lands first, and the data catches up.

### The flagship: coverage measured one level deeper

<!-- section-terms: coverage-model-mapping, traceability -->
<!-- point: line-coverage-answers-a-syntactic-question-not-the-semantic-one | Line coverage answers a syntactic question, not the semantic one. | terms: line-coverage, invariant -->
Line coverage answers a **syntactic** question: did this line run under some test? That is a fact about source text, and it is genuinely useful. But it cannot answer the question an engineer actually has, which is **semantic**: is the *claim this code makes* exercised by a test? A file can sit at 95% line coverage while the one function that implements a critical invariant is never called by any test at all — its lines swept up incidentally by an unrelated test that imports the module. The 95% is true and irrelevant to the claim you care about, and the mismatch is invisible, because a percentage has nowhere to put the gap.

<!-- point: the-fix-joins-a-traceability-graph-to-the-coverage-oracle | The fix joins a traceability graph to the coverage oracle. | terms: traceability, symbol-anchor -->
The fix joins two things the system already has. The first is a **traceability graph** that links each model claim — an invariant, a state-machine transition, a service-flow edge — to the code that implements it. The link points at an **anchor**: the `(path, symbol)` of the function that carries the claim. The second is the ordinary coverage oracle, which knows exactly which source lines ran. Compose them:

> anchor → its symbol → that symbol's line range → intersect with the covered-line set → *is this model claim's code exercised?*

<!-- point: the-composition-counts-model-claims-and-reports-a-named-verdict | The composition counts model claims and reports a named verdict. | terms: coverage-model-mapping, symbol-anchor -->
That composition changes the unit of measurement. Line coverage counts lines; this counts **model claims**. The anchors supply the numerator's units; coverage supplies the ground truth of what ran. The metric then reports a named verdict rather than a bare percentage: *this invariant's implementing code is not exercised by any test.* An anonymous 87% becomes an actionable list of the exact model claims your suite walks past.

<!-- point: the-genre-check-names-this-requirements-based-coverage | The genre check names this requirements-based coverage. | terms: coverage-model-mapping, requirements-based-coverage -->
This is not a new invention, and it should not be. Run the genre check and the family has a name: **requirements-based coverage** — the discipline avionics standards mandate, and the shape open-source requirement-tracing tools encode with git-native items linked to their tests. The system's traceability graph already adopted that schema, so there is no bespoke "model coverage" number to dream up. The one synthesis the off-the-shelf tools lack: they check that a requirement *has* a linked test; they do not check that the linked test *executes* the requirement's code. Joining the trace edge to the live coverage oracle closes that last gap.

> Learn more about this governance mechanism: [requirements-based coverage](appendix-b-coverage-model-mapping.html).

<!-- point: the-honesty-layer-reports-a-breakdown | The honesty layer reports a breakdown, not a percentage. | terms: coverage-model-mapping -->
The honesty layer matters as much as the aggregation. A single percentage lies when its denominator is fuzzy, so every figure reports a breakdown: exercised, not-exercised, unmeasurable (the anchor could not be resolved to code), and out-of-surface (a database-tier claim that is legitimately not code you can cover). "80%" then reads as what it is — *80% of the fifty measurable claims are exercised; twelve more are unmeasurable and owe a burn-down; eight are out of surface by design.* That is a number that affords the engineering, because you can see which part of it you can act on. And it cost a join, not a rebuild: the anchors already carry their `(path, symbol)`, and the covered-line set is a plain read of the coverage database the test runner already writes.

### The dual: draining unmodelled code {#mmm-drain}

<!-- section-terms: coverage-model-mapping, traceability -->
<!-- point: turn-the-arrow-around-and-orphans-appear | Turn the arrow around and orphan tests appear. | terms: coverage-model-mapping, missing-model-metric -->
The flagship measures model → code, so code with no model at all stays invisible to it. Turn the arrow around and a second metric appears. Walk from each *test* to the code it runs, and ask whether that code reaches any model-anchored symbol at all. A test whose exercised code reaches no model is an **orphan** — it guards behavior no model describes. The orphan rate, clustered by the unmodelled code the orphans touch, is a ranked list of the models still missing. This is the metric that steers the modeling loop: [ref:mmm-drain-curve] shows what happened when the fleet worked that list down; [ref:mmm-drain-table] gives each re-run.

<!-- label: mmm-drain-curve -->

The metric is a model-discovery instrument, not a gate. Each re-run names the biggest remaining orphan cluster; an Epic then builds the missing structured model and its invariants for that subsystem; the tracer runs again and the orphan rate falls, because that subsystem's code now traces up to a model. Repeated cluster by cluster, the drain took the orphan rate from 56% at the pilot to **7.89% at the latest committed point** — code-to-model coverage rising from 44% to about **92%**. Once the residual dozen orphans are set aside as glue code — web-route and seam wiring with no model to miss — the **genuine-orphan rate is 0%**. The metric drove the modeling, and the falling curve is the record of the modeling landing.

Two honesty notes bound the claim. The population is comparable across runs but not fixed: the denominator drifts from 144 to 152 tests as the suite evolves, and the first 56% point was scoped to the dispatch subsystem before the instrument widened. So read the curve as the same instrument re-run on a near-identical, evolving population, not a fixed-N replay. A clean fixed-N series would re-run the tracer at each tagged commit over one frozen population; that measurement is pending and would sharpen the curve without changing its direction.

> **Sidebar — Field note: reading the trace graph backward.**
> The link graph the drain walks has a second use, and it comes for free. Read forward — model claim to
> code — it measures coverage. Read *backward*, it surfaces duplication the code hid: two symbols
> carrying the same action off different model nodes (a consolidation waiting to happen); a vocabulary
> mirrored across a service boundary (one model both sides should read from); and incomplete
> composition, where some paths reach the canonical seam and a sibling quietly reaches a partial one —
> that last read caught a real resource leak on a cleanup path, not just a tidiness note.
>
> This is an observation, not a tool. The loop fired it by hand, on some modeling efforts and not
> others, and left it a field note — the yield has not yet earned the machinery, and building it before
> it does would be the over-engineering the method warns against.

### The soft end: doc-derived tests

<!-- section-terms: soft-vs-hard-governance -->
<!-- point: a-doc-derived-test-pins-a-doc-claim-and-its-metric-is-genuinely-soft | A doc-derived test pins a doc-claim; its metric is soft. | terms: doc-derived-test -->
Slide to the far end, where the metric stops being a number a threshold can act on and becomes a judgment a human has to make. A **doc-derived test** pins a behavior stated in a cited document or spec; the test carries a trailer naming its source, and when that source is edited the test is regenerated so pin and prose stay in step. The metric it invites — *is this doc-claim pinned by a test?* — is genuinely soft. It has no clean denominator. "How many claims does this document make?" is a matter of reading: one reader finds six, another nine, and neither is wrong. You cannot reduce it to a percentage the way you can reduce line coverage, because the set of claims is not enumerable by machine.

> Learn more about this governance mechanism: [doc-derived test](appendix-c-ddt-pin-trailers.html).

<!-- point: gating-this-soft-signal-manufactures-hollow-tests | Gating this soft signal manufactures hollow tests. | terms: doc-derived-test, seam -->
The softness runs deeper than a fuzzy denominator. A doc-derived test is only as good as the seam it tests against. If the code welds its decision logic to live I/O, there is no pure surface to assert a value against, and the test falls back to pinning the *shape* of the source — that a function exists, that a docstring reads a certain way. That test stays green even when you gut the function's body: it measures nothing about behavior. So the signal is inseparable from a judgment about readiness — are the types sound, is there a seam to test through, is the contract even documented? Only a person can answer that. Treat it as hard — wire it to a gate that blocks on a coverage-of-doc-claims threshold — and you manufacture the very hollow tests it was meant to prevent.

> **Measurement honesty: a null result with no headroom.**
>
> The most useful honesty in measurement is the one that catches you before you publish a comfortable
> non-result. An ablation was run to see whether giving the fleet a structured model helped it on a
> fixed set of tasks: run each task with the model and without it, and compare the scores. The
> comparison came back a null — no difference. The tempting reading is "the model did not help." The
> correct reading is that the instrument could not have shown help if help existed, because both arms
> scored at the ceiling. When the with-model arm and the without-model arm both nearly max the rubric,
> there is no room between them for an effect to appear.
>
> There is a structural reason the per-task cut was blind, and it generalizes. A task small enough to
> freeze into a benchmark cell is usually small enough to solve without the map. The value a structured
> model buys is a system-level one — the fix that lands once and holds everywhere, the drift a gate
> catches over months, a context-bounded fleet operating a codebase no context can hold at once — and
> none of that shows up inside a single self-contained gate-pass. So the lesson is not "the model did
> not help." It is "measure the effect at the level where the effect lives," and be willing to say, in
> print, that a chosen instrument could not see it. The study that produced this null also retracted an
> earlier claim that had read the same null as a measured absence — correcting the record when the data
> will not support the sentence is the discipline that makes the rest of the numbers trustworthy.

## The model runs the machinery

<!-- section-terms: executable-source-of-truth -->
<!-- point: the-model-runs-the-machinery-rather-than-picturing-it | The model runs the machinery, rather than picturing it. | terms: executable-source-of-truth -->
The hard end and the flagship follow one pattern. The models do more than stay in sync with the code as documentation: they are **consumed at runtime to produce the metrics.** The cold-start numbers land as typed fields on the deployment-topology model, and a tool reads the model to derive the longest-path worst case. The coverage flagship walks the traceability graph, follows each model claim to its anchor, and measures *that*, rather than scanning source text for functions that look important. In both, the model is not a picture of the machinery. The model runs the machinery — it tells the metric tool what to measure and how to read it.

<!-- point: a-component-distance-grade-drives-a-gate-three-ways | A component-distance grade drives a gate three ways. | terms: component-zone-model -->
The sharpest instance ties a metric straight back to a mechanism. A pre-commit gate has to decide whether a lint finding should block a commit. The naive gate blocks on any finding anywhere, which drowns an agent in pre-existing debt it did not cause. The better gate grades each finding by its **distance from the change** in the typed component graph, and the grade decides the gate's behavior:

> Learn more about this governance mechanism: [model-graded finding severity](appendix-b-model-graded-finding-severity.html).

- **HARD** — the finding sits on a file this commit touched. Block; it is the commit's own debt.
- **SOFT** — the finding sits in the *same component* as a touched file, but not on it. Report, name it, ask the agent whether the change plausibly caused it — but do not block, or concurrent agents race to fix the same pre-existing problem and collide.
- **SILENT** — the finding sits in a different component entirely. Suppress it at commit time; the whole-tree deploy gate remains the backstop.

<!-- point: the-grade-is-a-model-read-metric-driving-a-sensor | The grade is a model-read metric driving a sensor. | terms: component-zone-model, sensor -->
The grade is a metric — a distance, read from the model at check time — and it drives a sensor's decision directly. Same finding, three gate behaviors, chosen by consulting the component graph about how far the finding is from the change. Here the model earns its keep at the moment a commit is made: queried live to grade a gate — the machinery, run by the model.

The full instrument panel — every metric with what it counts, its place on the hard–soft axis, its healthy direction, and the formative/summative split a mature environment steers and certifies by — is collected in [appendix: appendix-operators-reference]. What belongs in the method is the principle the panel is built from: read the number one level below the surface, where it names a target instead of a total, and a loop can steer by it.

## The operating rhythm

<!-- section-terms: governance-conversion, lifecycle -->

<!-- point: operating-is-one-recurring-rhythm | Operating MAGE is one recurring rhythm. | terms: lifecycle, runbook, measure-one-level-deeper -->
Put the three together and operating MAGE is one recurring rhythm. A lifecycle names the healthy path and the way out of each failure. A runbook rides on top and types each step so the machine runs what it can and a brief carries what it cannot. A metric reads the loop's own state one level deep, so the rhythm steers by a fact instead of a feeling. Observe the state, diagnose the break, convert the recurrence into a mechanism — then the next turn starts from firmer ground. Nothing here is a fourth activity beside Model, Align, and Convert; it is those three run day after day, with the instruments that keep them honest.

<!-- point: the-day-names-three-competencies-part-six-develops | Operating the method names three competencies Part VI develops. | terms: thesis-modeling, thesis-alignment, governance-conversion -->
Run enough of these days and the shape of the work stands out. The reading is not overhead around the job; it is the job the engineer's seat became. Three competencies come to dominate it: **model design**, **governance design**, and **evidence engineering** — authoring the language the fleet reasons through, turning a failure class into a mechanism that holds, and building an environment whose output can be consumed as assurance. Part VI takes up what that does to the profession itself. Here it is enough to have watched the work that produces it.
