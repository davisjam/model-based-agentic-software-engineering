# One Problem, Many Models

Let us see how these ideas work together. While building DocAble, I encountered a problem processing large PowerPoint presentations. I had a working system, but I had neglected to model one of its resource requirements. Satisfying that requirement led me to reconsider the architecture and, in turn, to ask further engineering questions.

I began by modeling what DocAble retained in memory. I then developed models of execution, latency, and cost to investigate alternative designs. Notice how the questions change as the episode proceeds. Each model helped answer a question, but the answer could give me reason to ask another. I also had to decide which of the properties I discovered should constrain subsequent changes to the system.

## Modeling Memory Residency {#modeling-memory-residency}

### One Document, One Worker {#one-document-one-worker}

Originally, one DocAble worker processed an entire document. The worker ran in Kubernetes: it opened the document, retained the information needed for remediation in memory, modified the document, and produced the result. [ref:interlude-execution-unit] traces the architectural changes that followed.

When a GenAI operation needed an image, the worker retrieved it from the document already in memory.

<!-- label: interlude-execution-unit -->
<!-- figure: assets/interlude-execution-unit.svg | *Three approaches to document residency.* (a) One worker retains the document structure and its media. (b) Dividing the document into chunks reduces the content assigned to each worker. (c) Separating document structure from media allows workers to retrieve media as needed rather than retain the entire payload. -->

The resulting architecture worked on ordinary inputs, but larger documents exposed its limitations. Teaching presentations contained more slides, images, and other media than a single worker could comfortably hold in memory. I needed to reduce the amount of document content each worker processed at once. I had specified how DocAble should process documents, but I had forgotten to tell Claude what memory consumption was acceptable.

### Dividing the Document among Workers {#pages-as-the-unit-of-scale}

My first response was to introduce ChunkWorker, which divided a document into page ranges ([ref:interlude-execution-unit], panel b). Each worker retained the structure and media needed to remediate its pages, and the resulting patches were recombined into the complete document. Multiple chunks could run concurrently, and each worker required less memory. Smaller workers could also reduce infrastructure costs and improve cold-start behavior.

Chunking worked across a much broader workload, including hundreds of teaching documents from multiple universities. I had other features to develop and other problems to solve.

*Lesson: A satisfactory design need not be replaced merely because a better one exists. Engineering time is limited, and other problems may deserve it more.*

Eventually, however, a media-heavy presentation of roughly 250 MB exceeded the limits of this design. I could have reduced the chunk size further, but smaller chunks would also reduce the context available for semantic judgments and increase coordination costs. I now had reason to reconsider the design rather than continue adjusting its parameters.

### Separating Document Structure from Media {#a-new-class-of-input}

Dividing documents into page ranges reduced the amount of content each worker processed, but did not remove the underlying dependence on document size. I therefore examined what a worker actually needed to retain in memory. A presentation contains both the structure needed to reason about its contents and the media associated with that structure. Did the worker need to retain all that media throughout remediation?

Modern Office documents use Office Open XML (OOXML). A `.pptx`, `.docx`, or `.xlsx` file is a package containing many parts. Much of its semantic structure is XML: text, slides, relationships, identifiers, and references among objects. Large binary assets such as images and other media live alongside those XML parts inside the package.

The structural portion is comparatively small. It is largely text, and even an unusually large Office document may require only low megabytes to represent its semantic skeleton. The media payload can be hundreds of megabytes. Most remediation operations need only the structural portion; they may reach into the media, but not every media byte need be resident at once.

Until this point, I had largely accepted the working representation supplied by the document library. Opening an OOXML package brought its structure and media into the worker’s object graph. That was convenient while the documents fit in memory. The larger presentation gave me a reason to separate the two.

### Skeletonizing the Document {#remove-media-from-the-working-set}

I introduced a representation that retained the document’s structure but kept its media elsewhere. For OOXML documents, the pipeline streams through the package, moves media into external storage, and leaves references to that media in a much smaller structural skeleton. I call this transformation skeletonization.

Remediation then operates on the skeleton ([ref:interlude-execution-unit], panel c). If a GenAI operation needs an image, the worker follows the reference and streams that media through the network to the GenAI service without first materializing the document's complete media payload in worker memory. Recombination follows the same discipline in reverse. The worker no longer needs memory proportional to total media size.

*Lesson: Changing the representation of a system can change the resource requirements of the computations that operate on it.*

Chunking had enabled me to process the documents encountered so far. But how much memory should I allocate to each worker? In the cloud, I pay for the memory I allocate. If I allocate too much, I waste money. If I allocate too little, the hosting service kills the worker before it finishes processing the document. Processing one large presentation successfully would not tell me how much memory to allocate for the next. I needed a model that would let me predict memory consumption from the contents of a document.

To bound the whole worker, I must include its runtime and other baseline memory as well as the memory needed to process the document. The residency requirement is:

<!-- eq: \begin{aligned} \operatorname{RSS}_{\mathrm{peak}} &\le C,\\ C &= M_{\mathrm{base}} + M_{\mathrm{stream}} + M_{\mathrm{skeleton}} + M_{\mathrm{handles}} + M_{\mathrm{work}}. \end{aligned} -->

Here \(M_{\mathrm{base}}\) bounds the worker's runtime and other baseline resident memory, including the headroom needed for memory management. The remaining terms bound the rolling stream buffer, structural skeleton, handles, and remediation working set. Within the declared operating envelope, \(C\) is independent of aggregate media payload size.

The bound depends on bounded streaming buffers, a structural skeleton whose size remains inside the declared envelope, and bounded active state at each media consumer. The write path must stream too; buffering the complete payload before writing would merely move the memory spike. Pathological structure, oversized individual objects, excessive concurrency, or an unmodeled resource can still exhaust memory.

*Lesson: Successfully processing one input does not tell us how the system will behave on the next. A resource model can help us provision the system for inputs we have not yet encountered.*

<!-- index-def: measure-one-level-deeper -->

### Measuring and Explaining Memory Consumption {#why-one-level-deeper-matters}

I intended to use the residency model to make decisions about worker memory allocations. Before relying on it, I needed evidence that it explained the memory consumption I observed. Ousterhout describes this practice of investigating the mechanism behind a measured quantity as measuring one level deeper [cite: ousterhout2018].

I needed to test both the reading and writing paths. A PDF recombination experiment shows approximately flat peak-RSS scaling across a count-scaled media sweep when each object is flushed. That result supports the tested recombination path; the corresponding OOXML media-size sweep remains a designed validation step.

*Lesson: Measuring a quantity tells us how much of it we observed, not necessarily why. A model can explain the measurement and support predictions; further measurements can test that explanation.*

### Memory as an Obligation for Subsequent Changes {#memory-did-not-stop-mattering}

I had prioritized memory because running out of it prevented DocAble from processing a document at all, whereas inefficient execution made processing slower or more expensive. With memory consumption better understood, I could turn my attention to latency and cost. But a faster implementation that exhausted worker memory would not be an improvement. Other engineering problems may require us to protect safety, timing, or numerical accuracy first.

I had changed the architecture to satisfy a memory obligation. This was active alignment. I could now use the residency model to guide further designs and establish checks for passive alignment, protecting the memory bound during subsequent changes. The obligation became part of the alignment kernel introduced in [ref:4.1-the-dynamics-of-mage:heading:establish-a-kernel-before-expanding] for the execution changes that followed.

For example, I could not simply increase the number of concurrent GenAI calls without considering their combined memory requirements. I used a semaphore to limit active calls and modeled their memory consumption as the concurrency limit multiplied by the memory required per call. Later, when considering a cache for rendered presentations, I required its memory use to be bounded and larger cached artifacts to be stored externally before shipment.

*Lesson: Improvements to one property must respect the obligations established for others. The alignment kernel helps us preserve earlier engineering accomplishments while pursuing new ones.*

The memory model also changed which execution choices were worth reconsidering. We turn next to the dependencies that determine how remediation work can be scheduled.

## Modeling Execution and Latency {#modeling-execution-and-latency}

### Why Are We Still Chunking? {#why-are-we-still-chunking}

Skeletonization also gave me a reason to reconsider the execution architecture. I had introduced ChunkWorker to limit memory consumption by dividing documents into page ranges. I was still paying the coordination costs of a design whose original purpose was to reduce memory consumption. With that problem addressed differently, was partitioning work by page still the best way to organize remediation?

A page tells us where content occurs, not which computations depend on which others. The computation model introduced in [ref:2.3-structural:heading:what-computations-depend-on-one-another] and connected to scheduling in [ref:2.6-system-knowledge:heading:docable-connecting-engineering-models] identifies registered computations and the information dependencies among them. The question here was whether those dependencies could support a better execution policy.

Consider alt-text generation. Each page can first be analyzed independently. Those analyses supply information used to construct shared document context. Once that context exists, the GenAI queries for individual images can proceed independently. The dependency graph identifies which computations require earlier results; for a particular job, the computations whose prerequisites are satisfied form the ready frontier. An executor can schedule that frontier subject to resource and mutation restrictions.

The same graph admits different execution policies. [ref:interlude-graph-two-partitions] shows the distinction.

<!-- label: interlude-graph-two-partitions -->
<!-- figure: assets/interlude-graph-two-partitions.svg | *Two execution policies over the same remediation graph.* (a) Page-oriented execution groups computations by where their artifacts occur. (b) Frontier execution groups computations by when their prerequisites are satisfied. The computations and their dependencies are unchanged; only their scheduling differs. -->

Page identity could remain useful for locality, debugging, rate limiting, or failure isolation without determining how all remediation work was scheduled.

I therefore separated the remediation graph from its executor. The graph described the work and its dependencies; the executor determined how to schedule that work. I could schedule by frontier and later exploit page locality if measurements justified it, without redesigning remediation.

A frontier executor can repeatedly schedule computations whose prerequisites have been satisfied, record their outputs, and identify the next set of ready computations. The dependency ordering is an ordinary topological traversal of a directed acyclic graph; the executor must also respect the applicable resource and mutation constraints.[^topo-dag]

I also did not need to implement every scheduling policy I could imagine. The dependency model let me investigate alternative policies before committing to their implementation. I could retain the execution model while constructing other representations of the same computations for analysis.

*Lesson: A design decision that was appropriate under one set of constraints may become inappropriate when those constraints change. Understanding why a design was chosen helps us decide when to reconsider it.*

### Using the Graph to Find and Remove Bottlenecks {#analyze-before-you-build}

More workers cost money. Before increasing concurrency, I wanted to know whether the additional workers would actually reduce latency. Which computations could run concurrently, and which would have to wait for others? Critical-path analysis helps distinguish these possibilities. [ref:interlude-analysis-before-build] illustrates two ways to shorten a critical path: decomposing expensive work or changing the dependencies among operations.

<!-- label: interlude-analysis-before-build -->
<!-- figure: assets/interlude-analysis-before-build.svg | *Analyzing dependency graphs to redesign execution.* (a) Critical-path analysis identifies the longest weighted dependency chain, which sets a latency floor of 12 seconds in this illustrative graph. Two possible responses are shown. (b) Decomposing the dominant operation into independent suboperations reduces the modeled critical path to 7 seconds, excluding coordination overhead. (c) Changing the information dependencies can remove a serial constraint altogether. In DocAble’s image-description pipeline, replacing propagation of previously generated descriptions with shared rendered context allowed the image-description operations to proceed independently. -->

Panel (a) shows a weighted dependency graph. Its critical path, \(A \to B \to D \to F\), takes 12 seconds, compared with 6 seconds for the alternative path. Adding workers cannot shorten the critical path without changing the work or its dependencies. One possibility is to decompose the dominant operation. In panel (b), splitting B into three independent operations reduces the modeled critical path from 12 to 7 seconds.

Notice that the decomposition reduces latency while increasing the total processing time of the suboperations from eight to nine seconds. Whether this is worthwhile depends on the importance of response time relative to processing and coordination costs.

Another possibility is to reconsider the dependencies themselves. In DocAble’s contextual image-description pipeline, each generated description was passed to the next image-description operation. The resulting chain had depth proportional to the number of images. For \(N\) images, with each GenAI call taking roughly \(t\), the serial latency floor approached \(N \cdot t\). Adding workers could not remove that dependency.

The model exposed a distinction between the existing implementation and the information the operations actually needed. Each image required adequate surrounding context, but not necessarily the preceding image’s generated description. Rendering the surrounding pages once supplied a shared visual representation that each image-description operation could consume independently. Panel (c) shows how changing the information dependencies removed the serial chain.

*Lesson: We can improve execution by changing how work is scheduled, how it is divided, or what work is required. A dependency model helps us distinguish these opportunities and reason about their consequences.*

### Modeling the Cost of Repeated Document Processing {#the-second-resource-model}

Improving the GenAI operations was an obvious way to try to reduce latency. But how much of the processing time was actually spent on GenAI? Dividing remediation among workers could require several workers to perform the same document-processing operations. I wanted to know whether eliminating that repeated work offered a better opportunity to reduce latency than accelerating the GenAI calls.

Let \(R\) be the number of remediation rounds, \(F\) the elapsed time required for one whole-document processing invocation, and \(G\) the contribution of the remaining GenAI operations and their distribution to elapsed time. In a simplified execution model, whole-document processing occurs once per remediation round and once more when applying the accumulated changes. If invocation costs are similar and these costs do not overlap, the total elapsed time is

<!-- eq: T = (R+1)\,F + G -->

For example, suppose a document requires four remediation rounds, each whole-document processing invocation takes 10 seconds, and the remaining GenAI operations contribute 20 seconds to elapsed time. The model predicts \(T = (4+1)(10) + 20 = 70\) seconds. Fifty of those seconds come from processing the document five times: once for each remediation round and once more to apply the accumulated changes. Cutting the GenAI contribution in half would save 10 seconds; eliminating two production rounds would save 20.

I could also test this model against measurements. Suppose a single-invocation design takes \(T_1=F+G\), while a repeated-round design takes \(T_R=(R+1)F+G\). If the two designs share these component costs, their measured execution times let me estimate \(F\) and \(G\). A negative estimate would contradict the assumptions of the model rather than provide a useful calibration.

*Lesson: A model need not be elaborate to be useful. Even a simple quantitative model can reveal that we are trying to optimize the wrong part of a system.*

### Predicting Latency {#predicting-latency}

Running more computations concurrently in the cloud would introduce overhead for starting workers, transferring information, and coordinating their work. Would the additional concurrency save more time than this overhead consumed? I could use the dependency graph and estimates of operation times to investigate the question before changing the execution architecture.

Removing the dependencies among individual image descriptions did not remove every serial dependency. Each description still needed information produced by earlier computations. For the representative workload used during this analysis, the relevant GenAI chain had three dependent levels whose per-call times add to an irreducible floor ([ref:interlude-latency-floor]).

<!-- label: interlude-latency-floor -->
<!-- figure: assets/interlude-latency-floor.svg | *The GenAI critical path in a fragment of DocAble’s remediation graph.* Arrows indicate execution dependencies. Other remediation computations can proceed concurrently, but the three GenAI calls must execute in sequence. Their estimated and measured durations imply a latency floor of approximately 7.7 seconds for this modeled workload. -->

With local concurrency limited to six, the representative 37-image workload required \(\lceil \frac{37}{6}\rceil=7\) waves of image-description calls. Adding their estimated durations to the two preceding summary operations and a small CPU allowance yielded a predicted latency of about 33 seconds. With cloud concurrency of 64, those calls could execute in one wave. Even after accounting for estimated cold-start and round-trip costs, the predicted latency fell to about 11.5 seconds, a roughly 2.9× improvement. The prediction depended on those overhead estimates and required staging measurements before cutover. The local cap also reflected memory: concurrent ChunkWorkers each held format-native document state. Skeletonization reduced that per-worker residency, making wider execution feasible without multiplying the same large media working set.

### Evaluating a Design Before Implementing It {#predicting-the-cost-of-a-design-change}

Implementing an architectural alternative merely to discover that it would be too slow is an expensive way to evaluate a design. I could instead investigate some of its performance consequences using the models I had already developed.

Before implementing a proposed intermediate representation, I could add its production and consumption to the dependency graph. I could then recompute the critical path, the number of execution rounds, and the amount of work available for concurrent execution. A new computation might add no latency if it fits within the available slack on a noncritical path and sufficient execution resources are available. One that extended the critical path would increase the predicted latency and might require another distributed execution round.

*Lesson: Even when implementation is inexpensive, analyzing a design before building it can be worthwhile. A model can help us reject poor alternatives and identify promising ones.*

### Learning from Prediction Errors {#use-prediction-error-as-evidence}

I was using these predictions to decide which designs were worth implementing. If the predictions were substantially wrong, I might be making poor engineering decisions even when the resulting software worked. I therefore had reason to investigate discrepancies between predicted and measured performance. The error may lie in our estimates, our understanding of the system, or the implementation itself. [ref:interlude-prediction-residual] illustrates several possibilities and the process of revising and testing the model.

<!-- label: interlude-prediction-residual -->
<!-- figure: assets/interlude-prediction-residual.svg | *Learning through prediction and measurement.* (a) A model supports predictions that can be compared with measurements of the implementation. Disagreement motivates investigation and revision. For example, queue overhead may have been underestimated. Two apparently independent computations may share a serialized resource, or media loading may introduce a cost the latency model omitted.

*Lesson: A discrepancy between prediction and measurement is useful evidence. Even when the implementation appears to work, the discrepancy may reveal an error in our understanding of the system.*

## Preserving and Revising Models {#preserving-and-revising-models}

### Revising Models without Abandoning Obligations {#models-get-falsified-the-obligation-survives}

The memory model also made predictions that I could test independently of the implementation’s apparent success. Some of those predictions turned out to be wrong. I had attributed roughly 2.4 GiB of memory to a PDF library’s retained document graph. A probe that walked an image-heavy PDF and forced garbage collection found about 1 MiB of live managed graph. That was not the process’s total resident memory: the library used memory mapping, and resident mapped pages and other allocations required separate accounting. The result showed that I had attributed the large memory requirement to the wrong holder.

Another design projected a worker footprint of 90 to 120 MiB after rendering changes. The investigation instead found that rendering already ran elsewhere and that moving the remaining worker-side rendering machinery would recover only about 6 MiB. A later adversarial sweep exposed a different omission: peak memory grew with decoded image area, not just stored media size. I extended the model and added an admission gate for inputs outside the declared envelope.

I also recorded how each measurement was obtained. A measured quantity might describe a particular document, workload, configuration, or revision of the software. Comparing measurements obtained under different conditions could otherwise lead me to revise a model that was correct for its original assumptions. A figure taken on a development host was marked as such and did not become the value used in the model until the deployment environment reproduced it. A process-level measurement may omit memory included in the container’s total.

Nor was the memory work finished before the execution-time work began. I was still investigating memory consumption while developing the time models. I wanted subsequent changes to preserve acceptable memory consumption, not necessarily the first model I had constructed to explain it. Later work could challenge the model, recalibrate it, or replace it with a better one.

*Lesson: A model is not the obligation it represents. We can revise or replace a model without abandoning the engineering obligation that motivated it.*

### Preserving Performance Obligations {#what-carries-forward}

As I developed these models, I had to decide which of their properties should constrain subsequent engineering. Some models helped me understand the system or compare designs. Others expressed obligations that later implementations needed to preserve. A useful prediction did not necessarily warrant a new enforcement mechanism.

Having invested time in improving performance, I did not want subsequent agents to undo those improvements. But requiring every implementation to reproduce a particular benchmark time would make acceptance depend on hosts, services, cold starts, and other environmental effects. What could I require subsequent implementations to preserve instead?

The performance ratchet holds structural quantities instead — the quantities the model says contribute to execution cost: production rounds, GenAI calls, capture invocations, and render invocations. Tests count each quantity deterministically on two fixed fixtures and fail when a count exceeds its frozen baseline. The review discipline permits lowering a baseline freely but requires a named justification in its history before raising it.

*Lesson: When a measured property is expensive or unreliable to evaluate repeatedly, we may be able to enforce properties that contribute to it. Protecting those properties can complement direct evaluation of the original obligation.*

### Combining Models to Answer Engineering Questions {#the-resulting-model-family}

I could no longer make decisions about concurrency by considering latency alone. Increasing concurrency could reduce processing time while increasing memory consumption and coordination costs. I needed to use several of the models together. [ref:interlude-model-family] collects the seven models and the engineering questions each addresses.

<!-- label: interlude-model-family -->
<!-- table: Models for large-file remediation. [short: Models for large-file remediation] -->
| Model | Question |
|---|---|
| Media residency | What must reside in worker memory? How should memory scale with media size? |
| Batch execution | How do batch size and concurrency affect latency, cost, and truncation risk? |
| Critical path | What sets the latency floor? Which nodes are optimization targets? |
| Distribution | Where should ready work execute? What coordination costs does that introduce? |
| Remediation graph | What work exists, and what depends on what? |
| Fact / IR catalogue | Which derived facts feed later computations? How deep is the information-dependency chain? |
| Image fidelity | What representation of media is required, and what does rendering it cost? |

These models take different forms because they answer different questions. The remediation graph and fact catalogue describe the computations and their information dependencies. The batch model supplies estimates of operation costs, which the critical-path model uses to predict latency. The distribution model describes where computations execute and the costs of coordinating them. The media-residency model constrains how much work can execute concurrently.

Some answers follow from structure; others depend on calibrated measurements. The critical path identifies ordering that more workers cannot remove, while a latency prediction depends on operation times and coordination costs. Keeping those sources of knowledge distinct makes disagreement informative: a measurement can require a new parameter, a revised relation, or another model. [ref:chapter:appendix-a-resource-models-and-execution-design] brings the resulting resource, execution, and measurement relationships together as a construction blueprint.

*Lesson: Different models answer different engineering questions. By establishing relationships among them, we can answer questions that no individual model answers adequately.*

### Using the Models to Evaluate Subsequent Changes {#model-aware-change-impact}

The models developed during this episode also helped me reason about changes I had not yet undertaken. Suppose I wanted to increase the number of workers processing a document concurrently. Which properties would I need to evaluate before accepting that change?

The execution model would help me identify the work that could proceed concurrently. The residency model would help me estimate the memory required by that work. The latency and cost models would help me assess whether the additional concurrency was worthwhile. Other models could identify ownership and ordering obligations affected by the proposed change.

[ref:3.2-governance-mechanisms:heading:semantic-commitment-and-mechanization] examined how models can support the construction of checks. Here, relationships among models can help us select checks for a proposed change. [ref:model-aware-change-impact] illustrates how these relationships can help determine which evaluations a proposed change requires. Rather than asking an agent to reconstruct the relevant engineering obligations from the implementation, we can follow the relationships among the models, the affected components, and the available checks.

<!-- label: model-aware-change-impact -->
<!-- figure: assets/two-evidence-boundaries.svg | *Model-aware change impact.* Suppose an agent proposes increasing concurrency. Which obligations might the change affect? The execution model identifies the affected work, the memory model exposes possible resource violations, and the latency model identifies performance consequences. These relationships guide the selection of correctness tests, memory measurements, and performance checks for admission. Incomplete or stale relationships may require broader validation. -->

This use of model relationships builds on change-impact analysis, requirements traceability, model-based impact analysis, and regression test selection [cite: bohner1996impact;gotel1994traceability;briand2006impact;rothermel1997selection]. Such an analysis is only as complete as the relationships it represents. It can identify evaluations warranted by known dependencies, but it cannot establish that we have represented every property the change might affect. [ref:chapter:appendix-a-model-based-test-selection] develops the corresponding engineering machinery.

*Lesson: Models can help us determine what to evaluate as well as how to evaluate it. Explicit relationships among models, implementation components, and obligations can reduce the work of selecting evidence for a proposed change.*

This episode began with a document DocAble could not process. Investigating the failure led me to construct a model, change the implementation, and discover further engineering questions. I pursued some of those questions because they offered opportunities to improve the system; others could wait. Measurements revealed shortcomings in some of my models, while other models identified properties I wanted subsequent implementations to preserve. I could not have specified all seven models at the beginning, because I did not yet know which questions I would need to answer.
