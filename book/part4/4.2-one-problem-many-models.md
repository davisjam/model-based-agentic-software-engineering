# One Problem, Many Models

Let us see how these ideas work together in an engineering problem I encountered while building DocAble. I began with a working system, discovered a property I had neglected to model, and changed the implementation to satisfy a new obligation. That change opened up further opportunities to improve the system, each of which raised new engineering questions.

The initial problem was memory exhaustion when processing large PowerPoint presentations. Solving it required reconsidering what DocAble retained in memory and how it divided remediation work among workers. I then developed models of execution, latency, and cost to investigate alternative designs. As I implemented and measured those designs, I discovered shortcomings in the models themselves. By the end of the episode, I had both a different architecture and a collection of related models and controls that would guide subsequent engineering.

## Modeling Memory Residency {#modeling-memory-residency}

### One Document, One Worker {#one-document-one-worker}

DocAble originally treated an entire document as one unit of execution. A long-running Kubernetes worker opened the document, held the state needed for remediation in memory, modified it, and produced the result. [ref:interlude-execution-unit] traces the architectural progression from whole-document execution through page chunking to skeletonized residency.

<!-- label: interlude-execution-unit -->
<!-- figure: assets/interlude-execution-unit.svg | *Three approaches to document residency.* (a) One worker retains the document structure and its media. (b) Dividing the document into chunks reduces the content assigned to each worker. (c) Separating document structure from media allows workers to retrieve media as needed rather than retain the entire payload. -->

The document therefore served as both the user's artifact and the worker's in-memory unit of computation. Media needed by GenAI operations was read from that resident representation and sent to the foundation model as needed.

The resulting architecture worked on ordinary inputs, but larger documents exposed its limitations. Teaching presentations contained more slides, images, and other media than a single worker could comfortably hold in memory. I needed to reduce the amount of document content each worker processed at once. I had specified how DocAble should process documents, but I had forgotten to tell Claude what memory consumption was acceptable.

### Dividing the Document among Workers {#pages-as-the-unit-of-scale}

My first response was to introduce ChunkWorker, which divided a document into page ranges ([ref:interlude-execution-unit], panel b). Each worker processed a portion of the document, retaining the structure and media needed to remediate those pages. The resulting patches were then recombined into the complete document.

Each worker now handled only part of the document, and multiple chunks could run concurrently. More importantly, chunking reduced the memory required by an individual worker. Memory affects both infrastructure cost and cold-start behavior, so a smaller worker was useful even for documents that did not strictly require chunking to fit.

Chunking worked across a much broader workload: ordinary teaching presentations and hundreds of documents from multiple universities. Page ranges gave each ChunkWorker a practical bound on its working state, and experience provided no reason to replace that design merely because another architecture was possible.

This architecture accommodated the inputs encountered so far. The page boundary gradually became part of how DocAble was understood: a document was divided into chunks because chunks were how large documents were processed. A roughly 250 MB media-heavy presentation eventually exceeded that operating regime.

Smaller chunks could reduce memory consumption further, but they would also reduce the context available for semantic judgments and increase coordination costs. Chunking therefore presented a tradeoff between memory use and the information available to each operation.

### Separating Document Structure from Media {#a-new-class-of-input}

Dividing documents into page ranges reduced the amount of content each worker processed, but did not remove the underlying dependence on document size. I therefore examined what a worker actually needed to retain in memory. A presentation contains both the structure needed to reason about its contents and the media associated with that structure. Did the worker need to retain all that media throughout remediation?

Modern Office documents use Office Open XML (OOXML). A `.pptx`, `.docx`, or `.xlsx` file is a package containing many parts. Much of its semantic structure is XML: text, slides, relationships, identifiers, and references among objects. Large binary assets such as images and other media live alongside those XML parts inside the package.

The structural portion is comparatively small. It is largely text, and even an unusually large Office document may require only low megabytes to represent its semantic skeleton. The media payload can be hundreds of megabytes. Most remediation operations need only the structural portion; they may reach into the media, but not every media byte need be resident at once.

Until this point, DocAble had largely accepted the storage representation supplied by the document format as its working representation. For Office documents, that meant opening the OOXML package through the document library and letting its structure and media participate in the in-memory object graph; other formats followed analogous format-native representations. That was reasonable while the input sizes fit the worker. Handling a roughly 250 MB media-heavy file without allocating correspondingly large workers required reconsidering the arrangement itself.

Chunking reduced the amount of media resident in each worker, but memory consumption still depended on the media contained in that chunk. The residency model exposed a different possibility: retain the document’s structure while keeping its media outside the worker’s persistent working set ([ref:interlude-execution-unit], panel c).

### Remove Media from the Working Set {#remove-media-from-the-working-set}

The memory problem came from coupling document structure to media residency: total media size increased the worker's persistent working set even though most remediation operations needed only the document's structural skeleton. Skeletonization removes that coupling. For OOXML documents, the pipeline streams through the package, moves media into external storage, and leaves stable references in a much smaller structural skeleton.

Remediation then operates on the skeleton ([ref:interlude-execution-unit], panel c). If a GenAI operation needs an image, the worker follows the reference and streams that media through the network to the GenAI service without first materializing the document's complete media payload in worker memory. Recombination follows the same discipline in reverse. The worker no longer needs memory proportional to total media size.

The corresponding memory invariant states the property directly:

<!-- eq: \begin{aligned} \operatorname{RSS}_{\mathrm{peak}} &\le C,\\ C &= M_{\mathrm{stream}} + M_{\mathrm{skeleton}} + M_{\mathrm{handles}} + M_{\mathrm{work}}. \end{aligned} -->

The four terms bound memory for the rolling stream buffer, structural skeleton, handles, and remediation working set. Within the declared operating envelope, \(C\) is independent of aggregate media payload size.

Chunking had shown that the observed documents worked. Skeletonization supports a structural claim over a declared class of inputs: peak worker memory is bounded independently of total media size, provided the modeled path never retains the complete payload.

That claim depends on bounded streaming buffers, a structural skeleton whose size remains inside the declared envelope, and bounded active state at each media consumer. The write path must stream too; buffering the complete payload before writing would merely move the memory spike. Pathological structure, oversized individual objects, excessive concurrency, or an unmodeled resource can still exhaust memory.

The implementation enforces the assumptions behind the bound as invariants; measurement checks that the realized system behaves as the model predicts. The PDF path already shows approximately flat peak-RSS scaling across a count-scaled media sweep when each object is flushed; the corresponding OOXML media-size sweep remains a designed validation step.

My original requirement concerned the operations DocAble had to perform on a document. It did not distinguish the information those operations required from the memory costs of the implementation. The residency model made that distinction explicit. A worker could retain the document’s structural representation while retrieving media as needed, rather than retaining the entire media payload throughout processing.

The resulting design removed aggregate media payload size from the principal memory-residency term. The worker still required memory for document structure, active computations, and streaming buffers. The model therefore predicted a particular improvement in scaling behavior, rather than constant memory consumption under every possible change in document size.

Changing the architecture to satisfy the residency model is active alignment. Once correspondence is established, the model and invariant checks provide passive alignment: later changes must preserve the memory property or justify revising the model and its checks. The memory obligation became part of the alignment kernel for the execution changes that followed.

### Model the Cause, Not Just the Symptom {#why-one-level-deeper-matters}

Measuring peak memory tells us how much memory the worker consumed. It does not tell us why. The residency model explains how document structure and media contribute to memory consumption, and predicts how memory should change as we vary the input.

We need both the model and the measurements. The model helps us predict the behavior of documents we have not yet processed; measurements help us discover whether the model is correct. Ousterhout describes this practice as measuring one level deeper [cite: ousterhout2018]. The additional measurement is worthwhile when it helps us understand the mechanism responsible for the observed behavior.

### Memory as an Obligation for Subsequent Changes {#memory-did-not-stop-mattering}

I could now investigate ways to reduce latency and cost, but the new designs still had to satisfy the memory obligation. A faster implementation that exhausted worker memory would not be an improvement.

I had prioritized memory because running out of it prevented DocAble from processing a document at all, whereas inefficient execution made processing slower or more expensive. The service-sizing model later captured this asymmetry: allocating too much memory costs money; allocating too little can kill the process. Other engineering problems may require us to protect safety, timing, or numerical accuracy first.

That coupling became explicit in the engineering machinery. The frontier-worker design bounded active calls with a semaphore and modeled its footprint as the concurrency limit multiplied by the per-call working set. Wider work therefore required more batches rather than an unbounded resident set. In a later latency campaign, production shipment of a deck-to-PDF cache was conditional on bounding its memory use and spilling cached artifacts to external storage. The earlier resource model had become part of the environment within which the later one operated.

The memory model also changed which execution choices were worth reconsidering. We turn next to the dependencies that determine how remediation work can be scheduled.

## Modeling Execution and Latency {#modeling-execution-and-latency}

### Why Are We Still Chunking? {#why-are-we-still-chunking}

Skeletonization also gave me a reason to reconsider the execution architecture. I had introduced ChunkWorker to limit memory consumption by dividing documents into page ranges. With that problem addressed differently, was partitioning work by page still the best way to organize remediation?

A page tells us where content occurs, not which computations depend on which others. The computation model introduced in [ref:2.3-structural:heading:what-computations-depend-on-one-another] and connected to scheduling in [ref:2.6-system-knowledge:heading:docable-connecting-engineering-models] identifies registered computations and the information dependencies among them. The question here was whether those dependencies could support a better execution policy.

Consider alt-text generation. Each page can first be analyzed independently. Those analyses supply information used to construct shared document context. Once that context exists, the GenAI queries for individual images can proceed independently. The dependency graph identifies which computations require earlier results; for a particular job, the computations whose prerequisites are satisfied form the ready frontier. An executor can schedule that frontier subject to resource and mutation restrictions.

The same graph admits different execution policies. [ref:interlude-graph-two-partitions] shows the distinction.

<!-- label: interlude-graph-two-partitions -->
<!-- figure: assets/interlude-graph-two-partitions.svg | *Two execution policies over the same remediation graph.* The graph contains actions—page analysis, construction of document context, and GenAI queries—and information dependencies among them. (a) A page partition groups actions by the page their artifacts occur on, so it can span several dependency levels. (b) A frontier groups actions by readiness: page analyses execute first, their results enable construction of document context, and that context enables independent GenAI queries for alt text. The work and its dependencies are unchanged; only the execution boundary changes — so the choice between (a) and (b) is a scheduling decision, not a remediation redesign. -->

The graph explains the ordering. Independent work can run together; a consumer waits only for information it needs from upstream. Pages do not create those dependencies. Information does. The executor repeatedly schedules the ready frontier, records its outputs, and advances to the next frontier as dependencies are satisfied.[^topo-dag]

I could now reconsider the design of ChunkWorker. Page-oriented and frontier-oriented execution are not different remediation graphs. They are different ways of partitioning the same graph. Page execution groups work by where it occurs; frontier execution groups work by when it is ready.

Skeletonization removed the memory pressure that had made page ranges the natural execution boundary, so page identity no longer needs to determine execution. It can survive as metadata on graph nodes—useful for locality, debugging, rate limiting, or failure isolation—without remaining the fundamental unit of executable remediation.

For the present problem, the architecture therefore needs only a clean seam between the remediation graph and its executor: the graph supplies ready work and its dependencies; the executor consumes them. The executor can schedule by frontier now and exploit page locality later if measurements justify it. I did not need to implement both scheduling policies merely because I could imagine them. The dependency model let me investigate their likely consequences before committing to either implementation. Separating the graph from its executor lets us change the scheduling policy later without redesigning remediation. In the realized architecture, that execution-driving representation remains distinct from richer analytical projections built over the same computation identities. The distinction matters later: a model may govern realization while another view of the same structure serves analysis.

### Redesigning the Critical Path {#analyze-before-you-build}

Representing remediation as a dependency graph does more than provide an execution plan. The graph can be analyzed before an executor—or a proposed architectural change—is implemented. [ref:interlude-analysis-before-build] illustrates how critical-path analysis can identify a bottleneck and suggest two kinds of redesign: decomposing expensive work or changing the dependencies among operations.

<!-- label: interlude-analysis-before-build -->
<!-- figure: assets/interlude-analysis-before-build.svg | *Analyzing dependency graphs to redesign execution.* (a) Critical-path analysis identifies the longest weighted dependency chain, which sets a latency floor of 12 seconds in this illustrative graph. Two possible responses are shown. (b) Decomposing the dominant operation into independent suboperations reduces the modeled critical path to 7 seconds, excluding coordination overhead. (c) Changing the information dependencies can remove a serial constraint altogether. In DocAble’s image-description pipeline, replacing propagation of previously generated descriptions with shared rendered context allowed the image-description operations to proceed independently. -->

Panel (a) shows a weighted dependency graph. Its critical path, \(A \to B \to D \to F\), takes 12 seconds, compared with 6 seconds for the alternative path. Adding workers cannot shorten the critical path without changing the work or its dependencies. One possibility is to decompose the dominant operation. In panel (b), splitting B into three independent operations reduces the modeled critical path from 12 to 7 seconds.

Another possibility is to reconsider the dependencies themselves. In DocAble’s contextual image-description pipeline, each generated description was passed to the next image-description operation. The resulting chain had depth proportional to the number of images. For \(N\) images, with each GenAI call taking roughly \(t\), the serial latency floor approached \(N \cdot t\). Adding workers could not remove that dependency.

The model exposed a distinction between the existing implementation and the information the operations actually needed. Each image required adequate surrounding context, but not necessarily the preceding image’s generated description. Rendering the surrounding pages once supplied a shared visual representation that each image-description operation could consume independently. Panel (c) shows how changing the information dependencies removed the serial chain.

### Modeling the Cost of Repeated Document Processing {#the-second-resource-model}

The execution model told me which computations could proceed independently. To compare execution designs, I also needed to understand their costs. In particular, dividing remediation among workers could require several workers to perform the same document-processing operations.

Let *R* be the number of remediation rounds, *F* the cost of producing the whole document once, and *G* the remaining GenAI work. The model represented execution without page chunks as

<!-- eq: T = (R+1)\,F + G -->

For example, suppose a document requires four remediation rounds, whole-document production takes 10 seconds, and the remaining GenAI work takes 20 seconds. The model predicts *T* = (4+1)(10) + 20 = 70 seconds. Fifty of those seconds come from producing the document five times: once for each remediation round and once more to apply the accumulated changes. Cutting the GenAI work in half would save 10 seconds; eliminating two production rounds would save 20. In this example, we spend too much time rebuilding the document. The model therefore identifies repeated whole-document production as a quantity worth attacking.

I could also test whether this model was correct. Its calibration procedure inverted observed execution times to recover its components, and it rejected any fit whose inferred costs came out negative. Measurement could therefore disagree with the engineering account rather than merely supplying another number to optimize against.

### Predicting Latency {#predicting-latency}

Critical-path analysis also supports quantitative latency predictions when operation costs are available. For the representative workload used during this analysis, the relevant GenAI chain had three dependent levels whose per-call times add to an irreducible floor ([ref:interlude-latency-floor]).

<!-- label: interlude-latency-floor -->
<!-- figure: assets/interlude-latency-floor.svg | *The GenAI critical path in a fragment of DocAble’s remediation graph.* Arrows indicate execution dependencies. Other remediation computations can proceed concurrently, but the three GenAI calls must execute in sequence. Their estimated and measured durations imply a latency floor of approximately 7.7 seconds for this modeled workload. -->

For the representative 37-image workload, local concurrency of six required seven waves, yielding a predicted latency of about 33 seconds. Modeled cloud concurrency of 64 could execute that frontier in one wave; including estimated cold-start and round-trip costs gave about 11.5 seconds, a roughly 2.9× improvement. The prediction depended on those overhead estimates and required staging measurements before cutover. The local cap also reflected memory: concurrent ChunkWorkers each held format-native document state. Skeletonization reduced that per-worker residency, making wider execution feasible without multiplying the same large media working set.

### Predicting the Cost of a Design Change {#predicting-the-cost-of-a-design-change}

Before implementing a proposed intermediate representation, I could add its production and consumption to the dependency graph. I could then recompute the critical path, the number of execution rounds, and the amount of work available for concurrent execution. A computation outside the critical path might add no latency, provided that sufficient resources were available. One that extended the critical path would increase the predicted latency and might require another distributed execution round. These predictions helped me decide which designs were worth implementing and measuring.

### Learning from Prediction Errors {#use-prediction-error-as-evidence}

A useful feature of a quantitative model is that we can test its predictions. When measured latency differs substantially from a prediction, we have another engineering problem to investigate. Have we estimated a parameter incorrectly? Have we misunderstood a dependency? Have we omitted a computation or a source of overhead? Alternatively, the implementation might not follow the modeled design.

Each explanation calls for a different response. We can revise a parameter, change the structure of the model, investigate an omitted mechanism, or correct the implementation. We can then repeat the analysis and compare its prediction with further measurements. [ref:interlude-prediction-residual] illustrates this process and the possible sources of a prediction error.

<!-- label: interlude-prediction-residual -->

Disagreement motivates investigation and revision. For example, queue overhead may have been underestimated. Two apparently independent computations may share a serialized resource, or media loading may introduce a cost the latency model omitted.

## Preserving and Revising Models {#preserving-and-revising-models}

### Preserving Performance Obligations {#what-carries-forward}

As I developed these models, I had to decide which of their properties should constrain subsequent engineering. Some models helped me understand the system or compare designs. Others expressed obligations that later implementations needed to preserve. A useful prediction did not necessarily warrant a new enforcement mechanism.

I chose not to use observed wall-clock time as the basis for the performance ratchet. Wall time varies with hosts, services, cold starts, and other environmental effects, so a benchmark score from one machine makes a poor obligation. The performance ratchet holds structural quantities instead — the quantities the model says contribute to execution cost: production rounds, GenAI calls, capture invocations, and render invocations. Tests count each quantity deterministically on two fixed fixtures and fail when a count exceeds its frozen baseline. The review discipline permits lowering a baseline freely but requires a named justification in its history before raising it. The environment therefore preserves part of the *explanation* for performance rather than a number that only reproduces on the machine that produced it.

### Models Get Falsified; the Obligation Survives {#models-get-falsified-the-obligation-survives}

The memory model also made predictions that I could test independently of the implementation’s apparent success. Some of those predictions turned out to be wrong. One held that a PDF library's whole-file object model kept roughly 2.4 GiB resident; measurement found about 1 MiB live, because the file was memory-mapped and the image bytes never entered the managed heap. Another projected that moving rendering off the worker would recover 90 to 120 MiB; the landed measurement recovered about 6, because rendering was already running off the worker. A later adversarial sweep found a scaling dimension the bound had not covered at all: peak memory rose with decoded image area rather than with stored media size. The response was to extend the model and add an admission gate that refuses inputs outside the declared envelope. A capacity model elsewhere in the same environment was eventually caught about twofold too low against dozens of measured sweeps, and its parameter was recalibrated rather than the measurement discounted.

I also recorded how each measurement was obtained. A measured quantity might describe a particular document, workload, configuration, or revision of the software. Comparing measurements obtained under different conditions could otherwise lead me to revise a model that was correct for its original assumptions. A figure taken on a development host was marked as such and did not become the value of record until the deployment environment reproduced it. A process-level measurement may omit memory included in the container’s total.

Nor was the memory work finished before the execution-time work began. I was still investigating memory consumption while developing the time models. What became durable was not a particular bound but the requirement to reason explicitly about the resource. Later work could challenge the model, recalibrate it, or replace it with a better one. It could not silently return memory behavior to an unexamined implementation detail. The retained controls preserve the resource obligation even when the model used to evaluate it changes.

The episode therefore left more than a revised implementation. It left several models whose relationships could support later decisions, even as their parameters and assumptions continued to change.

### The Resulting Model Family {#the-resulting-model-family}

[ref:interlude-model-family] collects the models and the engineering questions each addresses.

<!-- label: interlude-model-family -->
<!-- table: Models for large-file remediation. [short: Models for large-file remediation] -->
| Model | Question |
|---|---|
| Media residency | What must reside in worker memory? How should memory scale with media size? |
| Batch execution | How do batch size and concurrency affect latency, cost, and truncation risk? |
| Critical path | What sets the latency floor? Which nodes are optimization targets? |
| Distribution | Where should ready work execute? What coordination costs does that introduce? |
| Remediation graph | What work exists, and what depends on what? |
| Fact / IR catalogue | Which derived facts feed later computations? How deep is the information-dependency chain? |
| Image fidelity | What representation of media is required, and what does rendering it cost? |

These models take different forms because they answer different questions. Some are typed graphs, some quantitative functions, some declarations of entities and invariants. They stay separate and compose through shared identities and explicit relationships. The remediation graph and fact catalogue supply the static dependency structure, and the batch model supplies per-call cost; the critical-path model combines the two into latency. The distribution model describes where work runs and which coordination costs that arrangement introduces. The media-residency model supplies the independent memory bound that makes the execution design affordable.

Some answers follow from structure; others depend on calibrated measurements. The critical path identifies ordering that more workers cannot remove, while a latency prediction depends on operation times and coordination costs. Keeping those sources of knowledge distinct makes disagreement informative: a measurement can require a new parameter, a revised relation, or another model. [ref:chapter:appendix-a-resource-models-and-execution-design] brings the resulting resource, execution, and measurement relationships together as a construction blueprint.

### Using the Models to Evaluate Subsequent Changes {#model-aware-change-impact}

The models developed during this episode also helped me reason about changes I had not yet undertaken. Suppose I wanted to increase the number of workers processing a document concurrently. Which properties would I need to evaluate before accepting that change?

The execution model would help me identify the work that could proceed concurrently. The residency model would help me estimate the memory required by that work. The latency and cost models would help me assess whether the additional concurrency was worthwhile. Other models could identify ownership and ordering obligations affected by the proposed change.

[ref:model-aware-change-impact] illustrates how these relationships can help determine which evaluations a proposed change requires. Rather than asking an agent to reconstruct the relevant engineering obligations from the implementation, we can follow the relationships among the models, the affected components, and the available checks.

This use of model relationships builds on change-impact analysis, requirements traceability, model-based impact analysis, and regression test selection [cite: bohner1996impact;gotel1994traceability;briand2006impact;rothermel1997selection]. Such an analysis is only as complete as the relationships it represents. It can identify evaluations warranted by known dependencies, but it cannot establish that we have represented every property the change might affect. This episode began with Evaluation: DocAble could not process a document. It led to Modeling and then to changes in the implementation, which exposed further engineering questions. Measurements revealed shortcomings in some of my models, while other models identified properties that I wanted subsequent implementations to preserve. I could not have specified all seven models at the beginning of the episode, because I did not yet know which questions I would need to answer.
