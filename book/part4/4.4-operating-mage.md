# Operating MAGE

<!-- point: a-method-must-survive-ordinary-days | A method has to survive ordinary days, not only successful changes. | terms: lifecycle, runbook -->
A method has to survive ordinary days, not only successful changes. Repositories fill disks, branches
conflict, agents disappear, queues stall, tests flake, deployments degrade, and assumptions age.
Engineers already know how to recover from much of this — but often only as tacit operating
knowledge. Autonomous work exposes the cost of leaving that knowledge in someone's head: the disk
fills, and the instruction for what to do about it will never be in the agent's context unless you
put it there.

<!-- point: operating-mage-has-four-connected-forms | Operating MAGE makes recurring work explicit in four connected forms: lifecycles, events, runbooks, and metrics. | terms: lifecycle, runbook, measure-one-level-deeper -->
Operating MAGE makes recurring work explicit in four connected forms. **Lifecycles** model healthy
progress and the important failure states. **Events** bind intervention to the moments when it
matters. **Runbooks** externalize the sanctioned response and separate execution from judgment.
**Metrics** expose the actual state the loop needs to decide whether it is healthy. Events are the
missing bridge between modeling the lifecycle and having the environment actually react.

<!-- point: not-all-operating-structure-is-authoritative | Not all operating structure is authoritative; a lifecycle is a model, an event fires deterministically though its payload may carry judgment, a metric is evidence, and authority appears only where a constraint, validator, or gate acts. | terms: lifecycle, soft-vs-hard-governance -->
Not all of that structure is authoritative. A lifecycle is a model. An event fires deterministically,
though its payload may still carry judgment. A runbook may contain both deterministic tools and
judgment guidance. A metric produces evidence. Authority appears only where constraints, validators,
or gates act on those structures. Keeping those roles separate is what lets the operating environment
remain understandable as it grows.

## Model the lifecycle

<!-- section-terms: lifecycle, failure-mode-effects-analysis -->

<!-- point: a-lifecycle-is-the-healthy-path-then-a-failure-map | A lifecycle: write the healthy path, then name the failure states that matter and the sanctioned recovery from each. | terms: lifecycle -->
<!-- index-def: lifecycle -->
Start with the healthy path of a recurring activity: how a bug moves from reported to fixed, how a
feature moves from designed to shipped, how an agent moves from dispatched to landed. Then name the
failure states that matter and the sanctioned recovery from each. The result is a lifecycle model:
not every thing that can happen, but the states and transitions an operator needs in order to
recognize healthy progress and recover from important breaks.

<!-- point: fmea-supplies-the-enumerate-failures-instinct | FMEA supplies a neighboring instinct — enumerate failure modes rather than inventing recovery under pressure. | terms: failure-mode-effects-analysis -->
<!-- index-def: failure-mode-effects-analysis -->
**FMEA** — *failure mode and effects analysis* — supplies a useful neighboring instinct: enumerate
failure modes rather than waiting to invent recovery under pressure. Full FMEA weighs more than the
book borrows — each failure's causes, its severity, how often it occurs, how readily it is detected.
MAGE takes the enumeration and adds an operational emphasis: what state are we in, what transition is
legal next, and which recovery action is forbidden or sanctioned?

<!-- point: pair-every-prohibition-with-a-recovery-path | Pair each prohibition with its sanctioned way out; a bare "don't" leaves a stuck agent with no exit. | terms: pink-elephant -->
Pair prohibitions with recovery paths. "Never use this destructive merge command" leaves a stuck
agent with a prohibition and no exit. "When this state occurs, do not use X; use Y because it
preserves the already-applied work" supplies the missing path. Where the prohibition can be made
structural, encode it as authority. Where it cannot, preserve the guidance explicitly.

> **Principle — Pair every prohibition with a sanctioned recovery path.** Naming a forbidden act
> raises an honest worry: does saying "don't" plant the very idea, the way telling someone not to
> picture a pink elephant paints one? In practice the naming helped — but only when the escape was
> named alongside the ban. My orchestrator kept reaching for a destructive Git command to bail out of
> a stuck merge, the one that resets the branch and silently discards the changes already applied, and
> twice lost committed work that way. A bare "never abort the merge" leaves the agent stuck with
> nowhere to go. What worked was pairing the forbidden command with the sanctioned one that clears the
> stuck state *without* dropping the applied work, so the rule reads "not that lever, this one." Name
> the sin alone and you may plant the temptation; name the sin *and the way out*, and you replace it.

<!-- point: the-fleet-itself-runs-on-a-lifecycle | The fleet's own lifecycle deserves the same treatment as the product: make its legal transitions explicit and validate the ones the environment can decide. | terms: agent-orchestration-model, lifecycle-soundness -->
<!-- index-def: agent-orchestration-model -->
The fleet's own lifecycle deserves the same treatment as the product. Point the discipline at the
substrate that *produces* the software and you get the **agent-orchestration model** — the agent's
life written as a typed state machine (`Dispatched → Working → Landed → Tombstoned`, with `Abandoned`
and recovery), and the orchestrator's refill-and-bank loop as the journey that drives it. It assesses
**lifecycle soundness**: a tombstone before a commit, or a landed agent that never tombstones, is an
illegal transition a checker catches. If Dispatched, Working, Landed, and Tombstoned are meaningful
states, make their legal transitions explicit and validate the ones the environment can decide. The
one liveness invariant — *a landed agent eventually tombstones* — routes to a temporal checker.

> Learn more about this governance mechanism: [agent-orchestration model](appendix-b-agent-orchestration-model.html).

<!-- point: dont-trust-a-done-claim-re-run-the-gates | A report of "done" does not establish that the repository entered the required state; re-evaluate the entry condition at the work-unit boundary. | terms: done-is-a-claim, drift-gate -->
That state machine is also why an operator never takes a report at face value. **"Done" is a claim,
not a fact.** An agent reporting a task complete is describing its *intent*, not the state of your
repository, and the two drift apart constantly — a sibling change broke a test, a marker rotted, the
thing it "verified" quietly routed through a fallback. So you do not trust the claim. You re-run the
gates yourself, at HEAD, and let a fact answer where a claim was offered. The lifecycle names
`Landed` as a state with an entry condition; re-running the gates is how you check the transition
actually fired.

## Bind reactions to lifecycle events

<!-- section-terms: lifecycle, lifecycle-event-binding, deterministic-firing -->

<!-- point: a-lifecycle-says-what-states-matter-events-make-the-right-step-arrive | A lifecycle names the states that matter; binding a reaction to a transition makes the right procedure arrive at the right time. | terms: lifecycle, lifecycle-event-binding -->
<!-- index-def: lifecycle-event-binding -->
A lifecycle model says which states matter. Operation improves when an important transition can also
make the right procedure available at the right moment. Do not rely on an actor to remember to
inspect the lifecycle, notice that a transition happened, retrieve the right procedure, and invoke
it. Where the event is mechanically observable, bind the response to the event.

<!-- point: the-firing-can-be-deterministic-while-the-payload-holds-judgment | Binding does not require a mechanical response: the firing can be deterministic while the payload still contains judgment. | terms: deterministic-firing, deterministic-vs-judgment-split -->
<!-- index-def: deterministic-firing -->
Binding the reaction does not require the reaction itself to be mechanical. **The firing can be
deterministic while the payload still contains judgment.** An agent reaches a context threshold: a
hook deterministically requests a handoff, but the agent must still summarize what matters. A
deployment fails a health check: the event deterministically opens the recovery path, but an engineer
may still decide whether rollback is warranted. A repeated failure is observed: the reflection
procedure runs on its own, but whether that failure deserves a new mechanism stays an engineering
decision.

<!-- point: wire-known-failures-to-sanctioned-reactions-automate-the-arrival-not-the-decision | Wire known failure events to sanctioned reactions rather than waiting for an operator to notice; the aim is to automate the arrival of the decision procedure, not every decision. | terms: lifecycle-event-binding -->
Wiring known failure events to their sanctioned reactions is the full expression of this idea: the
reaction fires rather than waiting for an operator to notice the failure. A structured signal surface
carries the events; something reacts to each one, so silent degradation cannot accrete for hours
behind a health signal nobody queries. The point is not to automate every decision. **It is to
automate the arrival of the decision procedure.** [ref:event-reaction-fire] draws the full path from
a lifecycle transition to the next state.

<!-- label: event-reaction-fire -->
<!-- figure: assets/event-reaction-fire.svg | *Binding a Reaction to a Lifecycle Event.* A lifecycle transition emits an observable event that fires the reaction deterministically, though its payload still splits three ways — execute a known action, delegate a bounded judgment, or escalate to a human. The firing is mechanical; the procedure it delivers may still hold judgment. [short: Lifecycle event → deterministic fire → execute / delegate / escalate → next state] -->

## Externalize operational judgment

<!-- section-terms: runbook, operational-playbook, deterministic-vs-judgment-split -->

<!-- point: a-good-runbook-preserves-how-an-engineer-reasons-not-only-the-commands | A good runbook preserves how an experienced engineer reasons through a recurring situation, without pretending every step has one mechanical answer. | terms: runbook, operational-playbook -->
<!-- index-def: runbook -->
A good runbook does more than list commands. Its deeper job is to preserve how an experienced
engineer reasons through a recurring situation, without pretending that every step has one mechanical
answer.

> ### Inset — What is a runbook?
>
> A runbook is a prepared operating procedure for a recurring task or failure condition. In site
> reliability engineering, runbooks preserve the diagnostic and recovery knowledge an operator should not
> have to reconstruct while a service is failing.
>
> The idea predates agentic software engineering. Google's SRE practice prepares incident procedures in
> advance rather than improvising under pressure, and reports substantially lower recovery time when
> responders have an established playbook — while stressing that no playbook replaces an engineer who can
> reason through an unfamiliar failure [cite: beyer2016sre]. Its incident-management guidance treats
> predefined roles, procedures, live state, handoffs, and rehearsal as infrastructure for reliable
> response, not paperwork written after the outage [cite: beyer2016sre].
>
> Industry practice has pushed the same idea toward runbook automation. PagerDuty describes runbooks as
> standardized operational procedures that capture expert methods, so known diagnostic and remediation work
> can be delegated; executable runbooks turn scripts, API calls, commands, and manual steps into repeatable
> workflows [cite: pagerduty2021runbook]. The caution matters too: a runbook is necessarily incomplete, and
> a stale procedure can be more dangerous than no procedure, because responders may trust it during a crisis
> [cite: pagerduty2021runbook].
>
> Empirical study of real incident response shows why pre-externalized judgment is worth the effort.
> Sillito and Kutomi analyze thirty software incidents from engineer interviews and public reports, tracing
> how engineers detect, investigate, and mitigate production failures — and document how difficult and
> variable that work is [cite: sillito2020incident]. That variability is the problem space a runbook
> exists to tame.
>
> MAGE keeps the conventional purpose — externalize operational knowledge before it is needed — but changes
> the internal shape. A traditional runbook can read like a flat sequence: detect the problem, check a
> dashboard, run a command, inspect the result, decide what to do, recover the service. That sequence hides
> an important distinction: some steps have one mechanically correct outcome; others require judgment.
>
> A MAGE runbook types its steps. A **runnable** step has one outcome the environment can compute, so it
> carries the exact executable operation. A **delegable-judgment** step requires reasoning but can be handed
> to an agent with bounded context, explicit criteria, and a required output. A **human-judgment** step names
> the decision that remains with the operator, rather than hiding it inside prose an autonomous actor may
> read as permission.
>
> The change is subtle and important: **the SRE runbook externalizes procedure; the MAGE runbook also
> externalizes the division of judgment inside that procedure.** That lets the environment do more than
> display instructions. It can lint the runbook's shape, execute the deterministic steps, dispatch bounded
> judgment with prepared context, surface irreducible decisions, record the resulting trace, and bind the
> procedure to lifecycle events.
>
> The runbook stays a model, not a guarantee. Its steps can drift; its assumptions can expire; and prose
> does not acquire authority merely because an agent reads it. The surrounding tools, validators,
> constraints, and gates determine which parts of the procedure actually bind.
>
> *Further reading:* Google's *Site Reliability Engineering*, especially "Emergency Response" and "Managing
> Incidents" [cite: beyer2016sre]; PagerDuty's incident-response and runbook-automation guidance
> [cite: pagerduty2021runbook]; Sillito and Kutomi's empirical study of software-system incident response
> [cite: sillito2020incident].

<!-- point: type-each-step-by-who-or-what-can-honestly-decide-it | Conventional SRE runbooks externalize procedure; MAGE adds one distinction — type each step by who or what can honestly decide it. | terms: deterministic-vs-judgment-split, runbook -->
Conventional SRE runbooks externalize the response procedure; the inset gives the established form.
MAGE adds one distinction needed for agentic operation: type each step by who or what can honestly
decide it. Classify each step by the kind of work it holds. [ref:externalize-judgment] shows the
three kinds and the form each one takes.

<!-- label: externalize-judgment -->
<!-- figure: assets/externalizing-judgment.svg | *Externalizing operational judgment.* Recurring procedure should not be flattened into prose or into automation. A deterministic step becomes an executable tool; a bounded-judgment step receives prepared context and a decision procedure; an irreducible judgment is surfaced explicitly to a human. [short: Externalizing judgment — recurring procedure → three kinds (deterministic/bounded/irreducible) → three forms (tool/prepared brief/human)] -->

<!-- point: a-deterministic-step-should-usually-become-executable | A deterministic step should usually become executable: preserve the sanctioned operation itself, not a paragraph telling an agent how to reconstruct it. | terms: deterministic-vs-judgment-split -->
A deterministic step should usually become executable. If there is one sanctioned way to clear a
cache, rotate a worker, reconcile a registry, or check a health condition, preserve the operation
itself rather than a paragraph that tells an agent how to reconstruct it.

<!-- point: a-bounded-judgment-step-carries-a-prepared-brief-not-an-instruction-to-investigate | A bounded-judgment step carries the material the judgment needs — relevant state, allowed choices, distinguishing criteria, required output — a prepared brief, not an instruction to "investigate." | terms: deterministic-vs-judgment-split, runbook -->
A bounded-judgment step carries the material needed to make the judgment: the relevant state, the
allowed choices, the criteria that distinguish them, and the required output. That is a prepared
brief, not merely an instruction to "investigate."

<!-- point: an-irreducible-judgment-should-be-surfaced-honestly | An irreducible judgment should be surfaced honestly; the environment can collect evidence and narrow the question without pretending the final decision is mechanical. | terms: deterministic-vs-judgment-split -->
An irreducible judgment should be surfaced honestly. The environment can collect evidence, narrow the
question, and make the alternatives legible without pretending that the final decision is mechanical.

<!-- point: playbooks-externalize-which-kind-of-reasoning-each-step-requires | Operational playbooks are models of engineering practice: they externalize not only what to do, but which kind of reasoning each step requires. | terms: operational-playbook, mastery-skill -->
<!-- index-def: operational-playbook -->
This is why operational playbooks are models of engineering practice. They externalize not only what
to do, but which kind of reasoning each step requires. It connects directly to the next chapter: a
mastery skill is one way to package exactly this kind of recurring judgment. [ref:runbook-split]
fences the one judgment step between two deterministic ends.

> Learn more about this governance mechanism: [runbook](appendix-a-operational-playbooks.html).

<!-- label: runbook-split -->
<!-- figure: assets/config-optimization-runbook.svg | *The Fenced Judgment Step.* A run-measure-assess loop wraps a three-step spine: determinize the data space, apply judgment, then determinize the experiment space. Fencing the one judgment step between deterministic ends bounds the messy part and leaves a logged trace a checker can grade. -->

<!-- point: determinizing-buys-a-trace-not-an-explanation | Determinizing a step buys a structured execution trace — evidence of what ran, not an explanation of why the decision was correct. | terms: reasoning-trace, deterministic-vs-judgment-split -->
<!-- index-def: deterministic-vs-judgment-split -->
Determinization buys more than repeatability. A tool can leave a structured execution trace: what
input it read, what branch it took, what state it changed. That trace is evidence of *what ran* — not
an explanation of *why* the surrounding engineering decision was correct. Preserve rationale
separately where judgment supplied the choice. The trace then earns its keep twice: last run's trace
is this run's input, so the loop converges instead of wandering; and a checker that never watched the
step run can audit the path it took and flag a run that went where it should not.

<!-- point: type-each-step-to-make-the-split-mechanical | Type every step as runnable, delegable judgment, or human judgment, and let the type decide how the step is governed. | terms: deterministic-vs-judgment-split, runbook -->
Written at scale, the split takes a mechanical form. The same three kinds carry operating names —
**runnable**, **delegable-judgment**, and **human-judgment** — and the type decides how each step is
governed. Typing the step also makes its shape checkable: a tool line on a judgment step, or a
dispatched brief on a runnable one, is a contradiction a linter catches before the runbook ships.
[ref:runbook-step-kinds] gives the three kinds and what each must carry.

<!-- label: runbook-step-kinds -->
<!-- table: *The Three Step Kinds.* What each kind must carry and how each is governed: a runnable step runs a tool, while the judgment steps split by whether an agent or a person decides. Typing the step makes the split mechanical — a mismatch is a lint finding. [short: Typing a runbook's steps] -->
| Step kind | What it is | What it must carry | How it is governed |
|---|---|---|---|
| Runnable | A deterministic step with one correct outcome | The exact tool line to run | The tool runs it; its logged trace is what a second checker reads |
| Delegable judgment | Reasoning no script can do, but a strong-model dispatch can — the missing middle | A pre-canned brief the orchestrator dispatches | A brief-linter checks the brief is intact before launch |
| Human judgment | Reasoning that must stay with the person | The words to surface, and why | Surfaced to the operator, never dispatched |

<!-- point: the-fence-is-no-docable-idiosyncrasy | Systems that share no code reach for the same fence between the step a machine can decide and the step that needs a mind. | terms: deterministic-vs-judgment-split -->
The split is no DocAble idiosyncrasy. Systems that share no code and answer to different regulators
reach for the same fence between the step a machine can decide and the step that needs a mind.

<!-- worked-examples: determinization -->
**Siemens** draws the fence as a clean division of labor across a safety-critical toolchain:
probabilistic semantic reasoning upstream, deterministic physics and verification downstream. The
decidable obligation lands on a deterministic mechanism; the open-ended reading of intent stays with
the model. **Zenseact** hardened three judgments other sites leave probabilistic — execution through
deterministic tools, authority settled by an explicit permission table, context selection decided by
a router rather than a guess. **Docker** determinizes what carries hard evidence — the tests run as
deterministic gates — but keeps admission deliberately probabilistic, an independent reviewer plus a
human, because collapsing that call to a threshold would forfeit the judgment it exists to weigh.
**DocAble** routes structural work (reading a tag tree, checking reading order) to deterministic tools
that leave a replayable trace, and judgment-laden work (describing an image) to a model against a
rubric, because no script can write the alt text.

<!-- takeaway -->
The shared move is *determinization*: separate the steps with a single correct outcome — which earn
an executable tool and a replayable trace — from the steps that need judgment, which earn the
roughest algorithm that still fits, and govern each by its kind.
<!-- worked-examples-end -->

## Measure the state that matters

<!-- section-terms: measure-one-level-deeper, sensor, resource-mediation -->

<!-- point: operational-control-fails-when-it-acts-on-a-proxy | Operational control fails easily when it acts on a proxy that only sometimes tracks the property of interest. | terms: sensor, measure-one-level-deeper -->
Operational control fails easily when it acts on a proxy that only sometimes tracks the property that
matters. A worker count is not resource pressure. Separate processes are not independent when they
contend for the same machine-wide resource. A marker left on disk is not proof that an actor is
alive.

<!-- point: govern-the-state-that-constrains-the-system-not-the-one-convenient-to-count | Observe and govern the state that actually constrains the system, not merely the state that is convenient to count. | terms: sensor, measure-one-level-deeper -->
<!-- index-def: resource-mediation -->
The general rule: observe and govern the state that actually constrains the system, not merely the
state that is convenient to count. Sometimes the answer is a better sensor. Sometimes it is an
explicit registry. Sometimes it is mediation — when many actors share a resource whose capacity
matters, route access through a control that knows the capacity, rather than asking each actor to
infer whether proceeding is safe.

<!-- point: use-the-simplest-direct-signal-available | Use the simplest direct signal available: govern memory pressure rather than job count, mediate a shared test resource rather than trust process isolation, record lifecycle state rather than reconstruct liveness from side effects. | terms: sensor, resource-mediation, agent-orchestration-model -->
Use the simplest direct signal available.

- **Govern the pressure, not the proxy.** Read memory pressure rather than assuming job count predicts it.
- **Mediate the shared resource.** Route a contended test resource through a mediator rather than assuming
  process isolation provides resource isolation.
- **Record the state, don't reconstruct it.** Write lifecycle state to a registry rather than inferring
  liveness from incidental side effects.

<!-- point: this-is-not-a-demand-for-perfect-observability | This is not a demand for perfect observability; the point is to notice when a proxy drives a consequential decision and the approximation has stopped being good enough. | terms: measure-one-level-deeper -->
This is not a demand for perfect observability. The point is to notice when the proxy drives a
consequential decision and the approximation is no longer good enough. From here, return to the
chapter's existing measurement discipline: measure one level deeper.

<!-- point: an-operating-loop-needs-evidence-about-its-own-state | An operating loop needs evidence about its own state; the useful metric is the one that changes the next engineering decision. | terms: loop-engineering, measure-one-level-deeper -->
An operating loop needs evidence about its own state. The useful metric is not the number easiest to
collect but the one that changes the next engineering decision. A whole-project cloud bill tells you
what you spent; cost by service may tell you what to change. Aggregate line coverage tells you how
much source ran; claim-level coverage may tell you which invariant your suite never exercised.
Counting AI-assisted pull requests or generated lines tells you activity changed; pairing throughput
with yield and rework [cite: linearb2026] tells you whether engineering improved.

<!-- point: ousterhouts-rule-measure-one-level-deeper | Ousterhout's rule: measure one level deeper — one level, not arbitrarily deep — where the deeper cut exposes the decision the surface number hides. | terms: measure-one-level-deeper -->
<!-- index-def: measure-one-level-deeper -->
Ousterhout's rule is apt [cite: ousterhout2018]: **measure one level deeper.** One level, not
arbitrarily deep. A metric earns its maintenance cost when the deeper cut exposes an optimization
target, failure class, or decision the surface number hides. "The suite covers 87% of lines" is the
invoice-level number — it reports and does not act, because a line in a throwaway string helper counts
the same as a line in the job state machine.

<!-- point: keep-measurement-separate-from-authority | A metric is evidence; a validator may interpret it against a bound and a gate may then act, but the number itself carries no authority. | terms: soft-vs-hard-governance, sensor -->
Keep measurement separate from authority. A metric is evidence. A validator may interpret it against
a bound; a gate may then act on that verdict. Some evidence is mechanically decidable and appropriate
for automated admission. Other evidence is intentionally judgment-laden and should point a reader
toward a decision rather than masquerade as a threshold. [ref:metric-spectrum] lays measurements out
by how far a machine can decide them.

<!-- label: metric-spectrum -->
<!-- figure: assets/metric-spectrum.svg | *Evidence and Judgment.* Some measurements support repeatable machine evaluation; others identify where a human or agent must still interpret meaning. Authority belongs to the validator or gate that consumes the evidence, not to the number itself. -->

### One hard example: coverage measured one level deeper

<!-- section-terms: coverage-model-mapping, traceability -->

<!-- point: line-coverage-answers-a-syntactic-question | Line coverage answers a syntactic question — did this line run — not the semantic one an engineer has: is the claim this code makes exercised? | terms: line-coverage, invariant -->
Line coverage answers a **syntactic** question: did this line run under some test? A file can sit at
95% line coverage while the one function that implements a critical invariant is never called by any
test — its lines swept up incidentally by an unrelated test that imports the module. The 95% is true
and irrelevant to the claim you care about, and the mismatch is invisible, because a percentage has
nowhere to put the gap. The question an engineer actually has is **semantic**: is the *claim this
code makes* exercised by a test?

<!-- point: the-fix-joins-a-traceability-graph-to-the-coverage-oracle | The fix joins a traceability graph to the ordinary coverage oracle: follow each model claim to its anchor and intersect its line range with the covered set. | terms: traceability, symbol-anchor, coverage-model-mapping -->
The fix joins two things the system already has. A **traceability graph** links each model claim — an
invariant, a state-machine transition, a service-flow edge — to the code that implements it, pointing
at an **anchor**: the `(path, symbol)` of the function that carries the claim. The ordinary coverage
oracle knows which source lines ran. Compose them:

> anchor → its symbol → that symbol's line range → intersect with the covered-line set → *is this model claim's code exercised?*

<!-- point: the-composition-counts-model-claims-not-lines | The composition counts model claims and reports a named verdict — this invariant's code is exercised by no test — instead of an anonymous percentage. | terms: coverage-model-mapping, symbol-anchor, requirements-based-coverage -->
That composition changes the unit of measurement. Line coverage counts lines; this counts **model
claims**. The metric then reports a named verdict rather than a bare percentage: *this invariant's
implementing code is not exercised by any test.* Run the genre check and the family has a name —
**requirements-based coverage**, the discipline avionics standards mandate — so there is no bespoke
"model coverage" number to invent; the one synthesis off-the-shelf tools lack is joining the trace
edge to the *live* coverage oracle, checking not that a requirement has a linked test but that the
linked test executes the requirement's code. And it cost a join, not a rebuild.

> Learn more about this governance mechanism: [requirements-based coverage](appendix-b-coverage-model-mapping.html).

### One judgment-laden example: doc-derived tests

<!-- section-terms: soft-vs-hard-governance -->

<!-- point: a-doc-derived-tests-metric-is-genuinely-soft | A doc-derived test pins a doc-claim; its metric — is this doc-claim pinned? — is genuinely soft, with no machine-enumerable denominator. | terms: doc-derived-test -->
Slide to the far end, where the metric stops being a number a threshold can act on. A **doc-derived
test** pins a behavior stated in a cited document; the test carries a trailer naming its source, and
when that source is edited the test is regenerated so pin and prose stay in step. The metric it
invites — *is this doc-claim pinned by a test?* — is genuinely soft. "How many claims does this
document make?" is a matter of reading: one reader finds six, another nine, and neither is wrong. The
set of claims is not enumerable by machine.

<!-- point: gating-a-soft-signal-manufactures-hollow-tests | Wire a soft signal to a blocking gate and you manufacture the hollow tests it was meant to prevent. | terms: doc-derived-test, seam -->
The softness runs deeper than a fuzzy denominator. A doc-derived test is only as good as the seam it
tests against; weld the decision logic to live I/O and the test falls back to pinning the *shape* of
the source, staying green even when you gut the function's body. So the signal is inseparable from a
judgment about readiness only a person can make. Treat it as hard — wire it to a gate that blocks on a
coverage-of-doc-claims threshold — and you manufacture the very hollow tests it was meant to prevent.
This is the evidence–authority line drawn sharply: the number aims a reader; it does not admit a
change.

> Learn more about this governance mechanism: [doc-derived test](appendix-c-ddt-pin-trailers.html).

<!-- point: the-detailed-metric-receipts-live-in-part-v | The detailed metric receipts — cold-start latency, the missing-model drain, the null-result ablation — are Part V evidence, not method. | terms: measure-one-level-deeper -->
The receipts behind these principles are Part V evidence, not method. A deterministic cold-start
number, fed into a deployment-topology model, drove a re-architecture that cut a warm floor from
seconds to a fraction of one; a reverse traceability metric drove a brownfield modeling loop that
drained unmodelled code from a majority of the suite toward single digits; and a null-result
ablation, which found no effect only because both arms scored at the ceiling, taught the discipline
of measuring an effect at the level where it lives. [Part V](5.1-the-problem-and-the-bar.html) carries
each with its data and its limitations. The method-level point is smaller and constant: **measure at
the level that drives the next engineering decision.**

### Let useful models drive machinery

<!-- section-terms: executable-source-of-truth -->

<!-- point: an-executable-model-becomes-a-query-surface-for-consumers | An executable model earns more than documentation value when tools consume it directly — it becomes a reusable query surface for many consumers. | terms: executable-source-of-truth -->
An executable model earns more than documentation value when tools consume it directly. A
deployment-topology model can tell a latency analysis which services and paths matter. A traceability
graph can tell a coverage tool which code realizes a particular claim. A component graph can help a
validator decide whether a finding is local to the current change or belongs to an unrelated part of
the estate. This is one of Modeling's practical payoffs: the representation becomes a reusable query
surface. It does not itself supply authority — the consuming validator or gate determines what
consequence follows from the model-derived result.

<!-- point: a-component-distance-grade-supplies-evidence-to-a-validator | A component-distance grade read from the model supplies evidence to a validator, whose verdict determines the gate's behavior at this boundary. | terms: component-zone-model, sensor, thesis-alignment -->
The sharpest instance ties a metric straight back to a mechanism. A pre-commit gate has to decide
whether a lint finding should block a commit. Blocking on any finding anywhere drowns an agent in
pre-existing debt it did not cause. The better gate grades each finding by its **distance from the
change** in the typed component graph, and the grade supplies evidence to a validator, whose result
determines the gate's behavior at this boundary:

> Learn more about this governance mechanism: [model-graded finding severity](appendix-b-model-graded-finding-severity.html).

- **BLOCK at this boundary** — the finding sits on a file this commit touched. It is the commit's own debt.
- **REPORT at this boundary** — the finding sits in the *same component* as a touched file, but not on it. Name it, ask the agent whether the change plausibly caused it, but do not block, or concurrent agents race to fix the same pre-existing problem and collide.
- **SUPPRESS at this boundary** — the finding sits in a different component entirely. The whole-tree deploy gate remains the backstop.

<!-- point: the-grade-is-a-model-read-metric-not-an-authority | Same finding, three gate behaviors, chosen by consulting the model — the grade is evidence read from the model, and the gate carries the authority. | terms: component-zone-model, sensor -->
Same finding, three gate behaviors, chosen by consulting the component graph about how far the
finding is from the change. The grade is evidence — a distance, read from the model at check time —
and the gate is what carries the authority to admit or refuse. The pattern also creates a maintenance
obligation: once machinery depends on the model, stale representation has operational cost. Keep the
model tied to the system strongly enough for the consumer's assurance needs, and retire a consumer
whose value no longer pays for that upkeep. The full instrument panel is collected in
[appendix: appendix-operators-reference]; what belongs in the method is the principle it is built
from — read the number one level below the surface, where it names a target instead of a total.

## The operating rhythm

<!-- section-terms: governance-conversion, lifecycle -->

<!-- point: operating-is-one-recurring-rhythm-across-four-forms | Operating MAGE is one recurring rhythm: the lifecycle names healthy progress and failure, events bind the reaction to the transition, the runbook gives each state a sanctioned next move, and metrics tell whether the loop is improving or merely busy. | terms: lifecycle, runbook, measure-one-level-deeper -->
Put the pieces together and operation becomes a recurring rhythm. The lifecycle tells you what healthy
progress and important failure look like. Events bind the reaction to the transition, so the right
procedure arrives when it matters. The runbook gives each state a sanctioned next move and separates
deterministic execution from judgment. Metrics expose enough state to tell whether the loop is
improving or merely busy. When a break recurs, governance conversion asks what later work should
inherit from the lesson.

> ### Inset — When work stalls, diagnose before adding machinery {#inset-when-work-stalls}
>
> Repeated failure does not always call for another control. Before you build one, ask which part of
> the loop is limiting the work.
>
> | What may be limiting | The question | If that is the gap |
> |---|---|---|
> | **Searcher** | Can the available intelligence find a good candidate? | Change the model, tools, decomposition, or search strategy. |
> | **Model** | Is consequential structure missing from the representation? | Make it explicit. |
> | **Oracle** | Can the environment tell good candidates from bad? | Strengthen the evidence, validation, or simulation. |
> | **Target** | Do we know what "good" even means? | Stop building and learn. |
>
> A stronger reasoner does not settle an unknown requirement; another validator does not supply a
> missing abstraction; more modeling cannot answer a product question whose answer must come from users
> or deployment. Diagnose what is limiting the work before adding machinery — the same distinction
> governance conversion already draws between failures of knowledge, obligation, evidence, evaluation,
> and consequence.

<!-- point: the-rhythm-is-still-model-align-convert | The rhythm is still Model, Align, Convert, run day after day; maintain the resulting structure while it pays and retire it when it does not. | terms: lifecycle, governance-conversion -->
This is still Model, Align, Convert. Model the recurring work and its failure states. Give stable
operational obligations appropriate authority. Convert repeated recovery and repeated judgment into
reusable structure. Maintain that structure while it pays; reconcile or retire it when it does not.
This improvement loop has familiar ancestors — mistake-proofing, continuous improvement, resilience
engineering, and the postmortem discipline of converting incidents into durable changes. MAGE does
not claim those ideas as new; the changed condition is implementation abundance, which can expose
gaps faster than human attention can repeatedly absorb them.

<!-- point: the-rhythm-names-three-competencies-part-six-develops | Run the rhythm long enough and the engineer's work becomes model design, governance design, and evidence engineering. | terms: thesis-modeling, thesis-alignment, governance-conversion -->
Run the rhythm long enough and the engineer's work becomes visible in a different form: **model
design**, **governance design**, and **evidence engineering** — authoring the language the fleet
reasons through, turning a failure class into a mechanism that holds, and building an environment
whose output can be consumed as assurance. Part VI takes up what that means for the profession. Here
it is enough to see those activities emerge from practice.
