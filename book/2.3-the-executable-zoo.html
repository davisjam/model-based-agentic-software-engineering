Part 2 — Modeling  ::  Chapter 8

2.3 Making Models Executable

A model exists to reduce how much system an engineer — or an agent — must reason about at once. An executable model earns a stronger claim: it is structured enough to reason over and bound tightly enough to the code that a build can catch the two disagreeing. That is the model this chapter defines, and the machinery that keeps code from drifting away from it.

One real codebase sits under every model that follows: DocAble, the production accessibility service this book runs on. It carries nineteen structured, drift-checked models and uses everything in this book to stay coherent; the full account is The Built System — Part 5 (The Evidence).

The Executable Model Pattern

Every model in Part 2 is one executable core, several projected views, and every one answers the same six questions:

  • What entities and relations does it represent — which slice of the system knowledge graph?
  • What engineering question does it settle that the raw code cannot?
  • What invariant must hold?
  • How is it derived — from the code, or the code from it?
  • How is that checked on every build?
  • What drift does the check prevent?

The first question fixes the model as an explicit slice of the knowledge graph the last two chapters built; the other five are the executable-model pattern the rest of the book develops.

2.3.1 Why models are newly central

Part 1 derived the Modeling Thesis from three facts about a coding fleet. Agents need models — a raw codebase overruns the window. They can maintain them — regeneration and reconciliation are the cheap repeated cognition the substrate now supplies. And they can enforce them — model-aware checks at the action and admission boundaries make a model a surface the build holds the code to. One artifact then plays four roles at once: the agent's reasoning interface, the engineer's specification, the generator's source, and the build's assurance surface. Building a large system is a long-horizon task whose reasoning state outruns any window, and the model is what pulls that state back within reach.

The architecture that delivers all four is the executable source-of-truth: the model is structured data; agents read it to navigate, generators consume it to emit the artifacts that must agree with it, and drift gates block the build the moment code and model diverge.

2.3.2 The upkeep that constrained MBSE, a fleet now pays cheaply

Model-based systems engineering did not fail on its ideas. It failed on upkeep — the standing cost of keeping a hand-drawn model matched to a moving codebase. Someone notices the code changed, finds the diagram it touched, edits the diagram to agree. That work is dull, unending, and the first thing a deadline cuts, so the diagrams drifted, then lied, then got ignored, and a discipline with sound ideas earned a reputation for ceremony.

A fleet changes exactly that term. Re-inducing a model from the code, diffing it against the last version, regenerating the artifacts it feeds — this is the repeated work a fleet does at a fraction of the human cost. The one expense that constrained MBSE is the one it now supplies cheaply, so the map stays equal to the territory. Someone still authors the model, the reconciliation rule, and the gate; what shrank is the standing maintenance, not the design. Every model below is drift-checked on every build, not by a human who might forget.

What admits a candidate is the formal definition from The Agent Stack: a deliberately reduced, machine-readable representation of system intent, structure, behavior, policy, or evidence — one that supports reasoning, derivation, or checking, and is mechanically maintained against the system it represents. Registries, graphs, manifests, state machines, typed records each earn the word the same way: by naming what they represent and carrying the gate that holds them true. A structure that fails a clause — a dashboard nothing derives from, a diagram nothing checks — stays out, however useful it is.

Inset — What is SysML, and what does MAGE take from it?

SysML is one major notation for model-based systems engineering 11. Sanford Friedenthal et al., A Practical Guide to Sysml: The Systems Modeling Language, 3rd ed. (Morgan Kaufmann, 2014).: blocks, constraint blocks, and verify-and-satisfy traceability, drawn in a modeling tool. A constraint block ties a required property to the element it governs; a verify-and-satisfy edge traces a requirement to the thing that meets it. MAGE borrows that concern — a typed invariant with a pointer to the check that verifies it is a constraint block in all but the notation — but implements it in a repository-native, drift-gated form. What it refuses is SysML's usual form: a model drawn beside the code. A second drawing of what the code already is snapshots the moment the code moves. Keep the model bound to the code, derived in either direction and gated either way, not drawn alongside it.

The scope stops at discrete software. A system with continuous or real-time dynamics wants a different toolkit — the timed and hybrid automata of Alur and Dill 22. Rajeev Alur and David L. Dill, “A Theory of Timed Automata,” Theoretical Computer Science 126, no. 2 (1994): 183–235. — out of scope here, and the place to read next if your system touches the physical world.

Working at the model level, with an agent doing the lifting, points at three things a team usually trades against one another: fewer tokens spent, more velocity, higher quality. For the data, see The Build → The fewer-tokens leg is the one named on the first page — a model binds intent to implementation and shrinks what the agent must hold in-window to act on it. Whether the model level delivers all three together, and at what cost, is a larger claim than one chapter can carry; a controlled navigation pilot puts a first number under the fewer-tokens leg.

2.3.3 The fewer-tokens leg — a navigation pilot

The fewer-tokens leg is directly measurable. In a controlled A/B pilot, an agent answered four navigation questions about the modeled codebase — locate a component, trace an invariant, resolve a tier, find an anchor — once with the MBSE navigation guidance loaded (ON) and once without it (OFF), counting the tokens each arm spent to reach the answer. That gap states the rule: the more derivation the naive path must redo, the more the guidance is worth.

Worked Examples

Siemens. Siemens runs on executable models as a matter of course. SysML and CAD, simulation models, virtual ECUs, and a bill-of-materials structure are the artifacts engineers actually work in; code is generated from them and verification is derived from them. The executable model is the ordinary medium of the work — the strongest external evidence that a model can sit upstream of the implementation rather than beside it.

Spotify. Spotify makes a narrower executable model pay at fleet scale. Its System Model and Backstage catalog carry dependency and endpoint lineage with stable identities, and the architecture diagrams are generated from that metadata rather than drawn by hand. When a migration targets an endpoint, the fleet acts through the model of the estate, not the raw code — an executable representation driving real change across thousands of repositories.

DocAble. DocAble is one software implementation of the pattern, and its distinctive slot is the typed intermediate representation: every remediation is a node in a typed IR the validator walks, so a fix is an object a gate can check rather than a diff to eyeball. It also reaches the rung even the model-first company does not — a drift gate that fails the build when a model and the code it governs disagree, holding the map equal to the territory instead of merely keeping the two in step.

Takeaway. The shared move is executable modeling made central: the model is the object the fleet reads, generates from, and checks against. Where a blocking drift gate binds the model to the territory, as in DocAble, the representation stops describing the system and starts holding it true.

2.3.4 The shared machinery that holds any view true

Most of the catalogue's method models belong to no single view. They are the machinery that makes every model executable and drift-proof, introduced once here and revisited where each view needs it:

  • The executable source-of-truth — the pattern behind every model, defined at the top of this chapter. > Learn more about this governance mechanism: executable source-of-truth.
  • The drift and parity gates — the lints and tests that enforce model-and-reality parity in both directions, so no model drifts unilaterally. > Learn more about this governance mechanism: drift and parity gates.
  • The agent-first harness — a thin hand-rolled layer over frozen records: adopt the genre's schema, skip its heavyweight runtime. > Learn more about this governance mechanism: agent-first MBSE harness.
  • The read and generate surfaces — one canonical query API over every model, and generators that emit real artifacts from the models, each provenance-headed so a hand-edit is caught. > Learn more about this governance mechanism: model query surface.

Three rules organize how any of them stays true.

Derive and join; do not repeat

A model here is derived — from the code, or the code from it — never kept beside the code as a parallel document. And it joins to its neighbours on a shared key rather than restating them. The service-flow model is the list the access policy is generated from and the call graph is checked against; it holds no second copy of the endpoints. The journey model joins to those endpoints by call-site rather than copying them. Restate a fact in two models and you are back to keeping two copies in sync by hand. Derivation and join are the cure.

State the derivation direction

A model and the code stay equal by derivation, and derivation runs in one of two directions. Say which up front, because the machinery differs.

  • Model-from-code (induce and reconcile). The code is authoritative; the model is a projection of it, reconciled at build time. The component-zone model reads the real directory tree; a journey's dependency list is derived from its real call sites. The drift gate is a reconciler: it re-induces the model from the code and fails on divergence. The usual case for a large codebase an agent must operate.
  • Model-to-code (specify and generate). The model is authoritative; the code, config, or docs are generated from it. The access policy, the service catalog, and the wire-contract types are emitted from the service-flow model. The drift gate is a freshness and provenance check: the generated artifact carries a header, and a hand-edit or stale regeneration is a finding.

Most of Part 2's models are model-from-code, because the codebase pre-existed them. The service-flow model is the clearest model-to-code case, and it is bidirectional — some fields generated to code, others reconciled from it — which is why its gate checks both directions. Each model page names its direction.

Descriptive maps and intent-bearing models

The purest model-from-code artifact is the repository graph a growing class of tools now hands a coding agent: a parser walks the repository into a persistent, queryable graph of its entities and relations — functions, classes, imports, calls, endpoints, schemas, tables — so the agent reasons through the graph instead of re-reading raw files. By the Modeling Thesis, that is the token argument pointed outward.

Inset — What do repository-graph tools do?

A repository-graph tool parses the codebase into a persistent graph an agent queries instead of re-reading files: what calls this function, what depends on this module, which path connects this endpoint to that table. Recent systems — RepoGraph 33. Siru Ouyang et al., “Repograph: Enhancing AI Software Engineering with Repository-Level Code Graph,” 2024, https://arxiv.org/abs/2410.14684., CodexGraph 44. Xiangyan Liu et al., “Codexgraph: Bridging Large Language Models and Code Repositories via Code Graph Databases,” 2024, https://arxiv.org/abs/2408.03910., RANGER 55. Pratik Shah et al., “RANGER: Repository-Level Agent for Graph-Enhanced Retrieval,” 2025, https://arxiv.org/abs/2509.25257., and Codebase-Memory 66. Martin Vogel et al., “Codebase-Memory: Tree-Sitter-Based Knowledge Graphs for LLM Code Exploration via Mcp,” 2026, https://arxiv.org/abs/2603.27277. — derive such graphs for navigation, dependency traversal, and agent retrieval. Codebase-Memory reports roughly a tenfold reduction in tokens and 2.1 times fewer tool calls against a file-exploration agent, at some cost in answer quality (83 percent against 92). These tools report what they measured and derive the graph; they do not establish MAGE's join claim.

An extracted graph describes what exists — that component A calls component B. It cannot say whether A is permitted to call B, whether B owns that responsibility, or what invariant the call must preserve. An engineer decided those. So a second axis lies across the derivation-direction one: not how the representation was made, but what it is authorized to claim. A descriptive model recovers the territory; an intent-bearing model states the shape the territory is meant to have. (2.5 develops that distinction where it teaches structural ownership.)

Put that way, the two compose rather than compete. A code graph finds every caller of a raw PDF library; an authored architecture model declares that a single structured model owns mutation of that format; a gate compares the extracted callers against the permitted set and turns any extra edge into a build finding. The graph supplies the current fact, the authored model the policy, the gate reads one against the other. A code knowledge graph can serve the observed-reality side of any drift or parity gate; what it does not carry by itself is the ought.

The ought can also be authored in prose: spec-driven development gives every feature a written specification the agent implements against. It makes the same normative commitment MAGE does, and it holds until the corpus grows. The difference is representation. A spec states the ought in prose, which does not compress and drifts unseen; a spec the code has moved past produces "syntactically correct code that was wrong," because the agent trusts it. A structured model states the same ought where a compiler and a gate hold it against the code, so it cannot go stale-but-trusted.

Sidebar — Spec-driven development, from the field

Recent studies of spec-driven agent workflows converge on the same point. An industrial one-person-squad case that ran an explicit spec-driven process to deliver work scoped for a four-person team reports that specification quality and institutional knowledge — not raw model capability — decided the outcome 77. Marcelo Vilas Boas et al., “One Developer Is All You Need: A Case Study of an AI-Augmented One-Person Squad in a Brownfield Enterprise,” 2026.. One team's field report is exact about where it broke 88. Abdurrahman, “We Adopted Spec-Driven Development, Then the Specs Started Eating Our Context Window,” Medium, July 2026, https://abdurrahman5.medium.com/we-adopted-spec-driven-development-then-the-specs-started-eating-our-context-window-6cb9476dfedc.: a naive preload reached roughly thirty-five thousand tokens at startup, of which about six percent was relevant, and the agent degraded once the window passed half full. Its remedies climb the same hill. Living specs, one per feature and edited in place, are the derive-don't-snapshot rule under another name; a thin router and index that load only the matching documents reach for a context-management layer; generated wikis and a CI check that flags a doc-against-code mismatch are a drift gate and derived traceability bolted onto a prose corpus after the fact.

Keep map and territory equal — traceability

The model is the map; the code is the territory. A model earns trust only if you can get from a model element back to the lines that realize it, and forward from a line to the model element that governs it. That round-trip is traceability — what the safety-critical standards demanded and what the drift gate mechanizes, since the reconciler is a traceability check that runs on every build. The forward direction is itself measurable — how much tested code reaches any model — and driving that number up is how the case study drained its unmodelled code. For the data, see Metrics →

The round-trip must itself be derived, not snapshotted. Picture the graph it walks — model element to lint to code entry point to test to registry row, each hop an edge. Write those edges down once and trust them, and the graph is a frozen snapshot that drifts the first time a symbol it names is deleted. Give each edge the mechanism that re-proves it — resolve the target against the code and see whether it still exists — and a deletion turns the edge red. Re-resolution is not infallibility; a live resolver can still mis-resolve. But it removes the one failure a snapshot guarantees: falling quietly out of date. The edge pays a second dividend — because a resolving edge means the map is current, an agent can walk it to pull the slice of a codebase it cannot hold in one window.

Learn more about this governance mechanism: symbol-anchored traceability graph.

Field note — reading the fix off real drift

DocAble did not design this up front. It kept a hand-maintained checklist first — when you retire a subsystem, remember to update the model too — and watched it rot. A cutover retired a poll-based dispatch plane for a serverless push plane; the retirement doc reconciled the architecture docs and the agent boot context and forgot the models, and the forgotten edge stayed green because nothing re-checked it. Left deliberately ungoverned for weeks, the models accumulated two dozen silent divergences. Sorting them by what caught them drew one line: the clean cases had a sensor that re-read the code at check time; the drifted ones kept a hand-maintained second copy that fell behind. So DocAble replaced the checklist with a traceability graph whose every edge is derived — re-checked against the code at scan time. Two decisions make it resist rot. Anchor to symbols, never line numbers: an edge points at a function or class definition, resolved statically, so it survives every edit that does not delete it. A missing symbol is a finding, not a crash: when an anchor no longer resolves, the edge goes red, and that red is the drift becoming visible. The symbol walk runs at a slower cadence than the per-commit gates, because resolving a symbol costs more than a membership lookup, and cadence follows cost.

2.3.5 A model is its schema plus its checked predicates

Read that as one operational equation: an executable model is its schema plus its checked predicates. Fields (b) and (c) of the reference template below give the structured model — records, edges, state machines. Field (d) adds the checked invariants, the predicates that must hold, each named by a stable id and each held true at build time by its checker — a drift lint or a model check. Model, invariants, checker: the constraint-and-verify vocabulary the chapter borrowed from SysML, where a constraint block wires to the check that satisfies it.

A structure that names its parts but promises nothing you can test is only half a model. Draw the schema and stop, and it rots the first time the code moves past it; the checker keeps it honest. The invariants are not arbitrary — they come from the failures the system met. In the DocAble build the gaps the models caught were violated-but-unstated invariants: a property the system had always needed and never written down, promoted to a checked predicate the moment it broke. Figure 2.3-1 draws the two structural edges and marks that provenance link as the dashed arc it is.

---

What is an invariant, and how do you write one?

An invariant is a statement that must be true in every state your system can reach. You write one as a predicate over the model's state, then ask the model whether any reachable state breaks it. Take a job whose state is two fields at once: a status of free, leased, or done, and a lease_owner that names the holding worker or is empty. Different steps write the two fields, so they can fall out of agreement — which is why you write the invariant down. "A job is leased if and only if it has an owner" is a predicate over the pair: (status == "leased") == (lease_owner is not None). A state where status is free but a lease_owner lingers is a stale lease; a state where status is leased but no owner is set is a lost lease. Both are reachable the moment the two writes separate, and both break the predicate. The move that makes this more than a comment: the predicate is checked, exhaustively, by a tool.

STATES = product({"free", "leased", "done"}, {None, "worker-1", "worker-2"})
def invariant(s):                                # leased iff owned
    return (s.status == "leased") == (s.lease_owner is not None)
assert all(invariant(s) for s in reachable_states())   # check every reachable state

Two terms this Part leans on, stated once. Drift is the condition where a model and the code it describes disagree — the map no longer matches the territory. A hand-maintained diagram drifts silently the first time a developer changes the code and forgets the diagram. A drift gate is the build-time check that set-diffs the model against reality in both directions and fails the build on any divergence: model ⊆ reality catches a model element with no code behind it; reality ⊆ model catches code the model never declared. Because the gate runs on every build, the first commit that diverges on a checked relation fails, not the fiftieth. Drift the gate does not check can still slip through, so the gate bounds accumulation over what it checks — still the line that separates an executable model from a diagram, which drifts silently on any change. A model does not only reduce context; it can turn a global semantic question into a local predicate over structured state.

The remaining insets appear where they are first needed: assertions over sequences and the temporal-logic step-up, bounded model checking, automata, data-flow diagrams, safety versus liveness, protocols and TLA+, and coverage over model nodes.

2.3.6 How to read a model page

Part II teaches modeling by leading each section with an engineering question; the appendix documents each model with a uniform five-field reference template, so a reader who has read one reference page can read any of them on reflex. Table 2.3-2 gives the fields and the reader's question each answers. Above the template sits the first question of the pattern — which slice of the system knowledge graph is this? — and the five fields state what it is for, what it is made of, what it looks like, how you trust it, and how it stays tied to the code.

Table 2.3-2. The five-field model-page template — the field, what it states, and the reader's question it answers. Every appendix model-reference page fills it.
FieldWhat it statesThe reader's question it answers
(a) Quality propertythe question the model answers that the raw code cannot — "is Q true?", not "it models X"What is it for?
(b) Constructs and relationsthe typed record kinds, the meaning-carrying fields, the edges between them — the model's slice of the system knowledge graphWhat is it made of?
(c) Visual depictionthe diagram matched to the model's natural type (state machine → state diagram; topology → deployment diagram), with an accessible description stating content and takeawayWhat does it look like?

The MDSE text (Brambilla, Cabot, and Wimmer, ch. 2) draws the tower in full.

That is the whole of it: an executable model is a structured representation plus checked claims about what must remain true. What remains is to walk real models on real code. The next chapter names what a view is — not a second model to maintain but a projection over the one connected representation, so several views can join on identity where several diagrams would drift.
