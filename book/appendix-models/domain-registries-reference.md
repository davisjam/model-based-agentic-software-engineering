The **Domain Registries** reference page. The chapter *Modeling Structure and Ownership* teaches these
as the single facts every consumer joins to; the full five-field treatment lands here. The
rule-metadata registry is the self-referential slice and gets its own entry below the shared fields.

**(a) Quality property.** **Fact consistency** — every consumer of a slowly-changing domain fact agrees,
because each joins to the registry by key rather than keeping its own copy. A fact read in many places
and revised rarely is exactly the fact that drifts when each reader copies it; the registry makes
disagreement a build failure instead of a latent inconsistency.

**(b) Structure.** One frozen table per domain fact, each the single source of truth for its slice.

- **`Registry`** — a named table keyed by a stable id (for the file-type registry, the format id /
  extension), holding the authored fact and the fields consumers read.
- **The join relation** — every consumer references a registry row by key; no consumer stores a
  private copy of the value.

**(c) Representative figure.** A hub-and-spoke: the registry at the center, each consumer joining to it
by key.


**(d) Invariants.**

<!-- table: Invariants of the domain registries — each with the check that holds it. [short: Domain-registries invariants] -->
| Invariant | How it is checked |
|---|---|
| No consumer keeps a private copy of a registry value | A copied registry value in a consumer is a finding — the consumer must read the fact live by key. |
| Every consumer's join key resolves to a real registry row | Join-integrity check: a reference to an absent key is a finding. |
| A fact added to the registry reaches every consumer | Because consumers join by key, an addition surfaces everywhere or the build fails. |

**(e) Derivation direction.** *Authored.* The registry is the source of truth; consumers are checked
*against* it, never the reverse. The join key is the registry key.

**The rule-metadata registry — the self-referential slice.**

**(a) Quality property.** **Rule-index consistency** — does the published index match the rules
declared in the code? The metadata that describes a governance rule lives beside the rule it describes,
so the description cannot rot into a separate document nobody updates.

**(b) Structure.** Each rule carries a small typed block at its own site — for example:

```
| Form        | typed-ir   |
| Move        | package    |
| Model       | is-a-model |
| Enforcement | Hard       |
```

The index is generated by reading every such block, one row per rule; the same block becomes the
published row:

```
| Component & zone model | typed-ir | package | is-a-model | Hard | … |
```

**(c) Representative figure.** A round-trip: per-rule blocks on the left, the generated index on the
right, a freshness gate joining them.


**(d) Invariants.**

<!-- table: Invariants of the rule-metadata registry — each with the check that holds it. [short: Rule-metadata invariants] -->
| Invariant | How it is checked |
|---|---|
| Every rule block carries all required fields | Completeness lint: a block omitting a required field fails the rule. |
| The committed index matches the blocks | Freshness lint: regenerate the index, fail the build if committed rows differ. |

**(e) Derivation direction.** *Model-to-code.* The index is generated from the authored blocks; a
reader round-trips from a published index row straight to the declaring site. This book's own catalogue
is built the same way — the row in its index is generated from the block on the entry's page, held equal
by the same freshness gate.
