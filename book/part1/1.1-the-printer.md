# The Printer

<!-- point: agents-made-implementation-cheap-not-reliable | Coding agents make implementation cheap enough to change the engineering problem; a sound spec, a useful representation, and evidence do not arrive with that capacity — implementation speed amplifies the engineering around it. | terms: code-fabricator -->
Coding agents make implementation cheap enough to change the engineering problem. Describe a change and a
capable agent can often build it quickly, at a scale that once required substantial human effort. What does
not arrive automatically with that capacity is a sound specification, a useful representation of the system,
or evidence that the result is acceptable. Implementation speed amplifies the engineering around it.

<!-- point: the-agent-is-a-printer-responsibility-in-the-right-place | Treat the agent first as a printer — productive machinery that realizes an engineering description; the metaphor is imperfect but fixes responsibility with the engineer, who owns what the work must mean, satisfy, and prove. | terms: printer-metaphor -->
<!-- index-def: printer-metaphor -->
Think of the agent first as a printer: productive machinery that realizes an engineering description. The
metaphor is imperfect—a capable agent can interpret underspecified directions, reason about alternatives,
and sometimes repair a poor specification—but it fixes responsibility in the right place. The engineer
remains responsible for what the resulting work must mean, satisfy, and prove.

<!-- point: leverage-moves-into-the-environment | As implementation becomes abundant, engineering leverage moves toward the instructions, representations, constraints, evidence, and infrastructure that shape autonomous work. | terms: printer-metaphor, commodity-intelligence -->
When agents perform the implementation, engineering leverage moves into the engineered environment. [ref:engineering-leverage]
shows the shift.

## The Engineering Object

<!-- point: the-agent-is-not-the-engineering-object | Foundation models and agent products keep changing; the durable engineering problem begins when an agent works autonomously where "it usually works" is not an acceptable standard. | terms: commodity-intelligence -->
If you opened a book about agentic software engineering expecting a tour of agents, what comes next may seem
indirect. That is deliberate. Foundation models and agent products will continue to change.[note: A terminological nuisance runs through this field. Engineering was using model long before machine learning adopted the word, so the engineering usage gets precedence in this book: unqualified model means a purposeful representation of an engineered system or some property of it. Machine learning calls its learned artifacts models for the same broad reason—each represents or approximates relationships in some domain, often as a learned function. I therefore use foundation model for the trained machine-learning system and agent for the acting system built around one through a harness, tools, and working state. Where the distinction matters, I will not ask the reader to infer which "model" I mean.] The durable engineering problem begins when an
agent works autonomously on a system large enough, important enough, or long-lived enough that "it usually
works" is not an acceptable standard.

<!-- point: the-object-of-engineering-expands-beyond-implementation | The object of engineering expands beyond the implementation to the environment through which autonomous work proceeds: what the agent can know, what it may do, what evidence it must produce, and which obligations the environment will enforce. | terms: commodity-intelligence -->
The object of engineering therefore expands beyond the implementation. Engineers also design the environment
through which autonomous work proceeds: what the agent can know, what it may do, what evidence it must
produce, and which obligations the environment will enforce.

<!-- point: mage-is-about-that-environment | MAGE is principally about that environment; the method lies in the representations work reasons through, the obligations the environment can make authoritative, and the judgment that decides what should become durable engineering structure. | terms: commodity-intelligence -->
MAGE is principally about that environment. We will get to foundation models, harnesses, tools, hooks,
skills, and workflows because their properties determine what can be engineered around them. But the method
lies in the representations through which work reasons, the obligations the environment can make
authoritative, and the judgment that decides what should become durable engineering structure.

<!-- point: mage-accepts-the-lesson-changes-the-level | External representation, memory, and tools have long improved machine reasoning; MAGE takes the step outward to the engineered environment through which autonomous work proceeds over time. -->
That emphasis has important antecedents. AI research has repeatedly improved machine reasoning by changing
the representations, memory, tools, and external machinery available to the reasoner; recent agentic
software-engineering systems similarly improve performance through retrieval, program structure, and
purpose-built interfaces.[note: On the AI side: LLM+P translates natural-language problems into a classical
planner [cite: liu2023llmp]; MemGPT externalizes state into managed memory tiers [cite: packer2023memgpt];
and Graph of Thoughts makes graph structure part of the reasoning process [cite: besta2024got]. In agentic
software engineering: RepoCoder retrieves repository-level context [cite: zhang2023repocoder]; SWE-agent
engineers the agent-computer interface [cite: yang2024sweagent]; and AutoCodeRover reasons over program
structure rather than treating a project as merely files [cite: zhang2024autocoderover]. The ambition
predates foundation models: Rich and Waters's Programmer's Apprentice envisioned an AI system as a new
agent in the software process, sharing explicit programming knowledge with the engineer across
implementation, design, and requirements [cite: rich-waters]. Part VI returns to what that earlier program
anticipated — and what commodity intelligence changes.] MAGE takes the
next step outward: its subject is not principally the environment needed to solve one task, but the
engineered environment through which autonomous software work proceeds over time.

## Suspect the Setup First {#whose-fault-is-it}

<!-- section-terms: whose-fault, build-instructions -->

<!-- point: suspect-the-engineered-setup-before-a-machine-limit | The Printer suggests a diagnostic rule: suspect the engineered setup before inferring a machine limit. | terms: whose-fault -->
The Printer suggests a useful diagnostic rule: suspect the engineered setup before inferring a machine
limit.

<!-- point: a-photo-does-not-specify-the-object | A 3D printer makes the distinction obvious: appearance does not specify internal structure, materials, tolerances, or loads; the printer needs a representation adequate to the properties the finished object must have. | terms: whose-fault -->
A 3D printer makes the distinction obvious. A photograph may show what an object should look like, but
appearance does not specify its internal structure, materials, tolerances, or loads. The printer needs a
representation adequate to the properties the finished object must have.

<!-- point: plausible-completion-is-not-a-specification | Software agents weaken the analogy but strengthen the engineering problem: a capable agent can infer a great deal from little, but plausible completion is not an explicit statement of which properties must hold, which tradeoffs are acceptable, or what evidence establishes correctness. | terms: whose-fault, build-instructions -->
Software agents weaken the analogy but strengthen the engineering problem. A capable agent can infer a
great deal from a screenshot, a prose request, or an incomplete specification. It may produce an impressive
result from surprisingly little. But plausible completion is not the same as an explicit statement of which
properties must hold, which tradeoffs are acceptable, or what evidence establishes correctness.

<!-- point: inspect-what-the-engineer-controlled-first | When an agent produces the wrong result, inspect first what the engineer controlled — instructions, representation, task boundary, tools, evidence; failed output alone does not establish that the foundation model lacks the capability. | terms: whose-fault, build-instructions -->
When an agent produces the wrong result, inspect first what the engineer controlled: the instructions, the
representation of the problem, the task boundary, the available tools, and the evidence the work was required
to satisfy. Sometimes the foundation model simply lacks the necessary capability. Failed output alone does
not establish that diagnosis.

<!-- point: velocity-amplifies-sound-and-bad-engineering-alike | Abundant implementation raises the stakes: capable agents execute a bad direction at extraordinary speed, and velocity amplifies sound engineering and bad engineering alike. | terms: build-instructions -->
<!-- slogan: danger-in-instructions -->
Abundant implementation raises the stakes. Capable agents can execute a bad direction with extraordinary
speed. Velocity amplifies sound engineering and bad engineering alike.[note: My field notes on this point were less measured: "Claude is the fastest road to hell."]
