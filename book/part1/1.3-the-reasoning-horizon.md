# The Reasoning Horizon

<!-- section-terms: long-horizon-task, reasoning-horizon, churn, context-window -->

<!-- point: supervised-work-is-long-horizon-and-outruns-working-memory | Supervised work is long-horizon; its reasoning state outruns the finite working memory that must hold it. | terms: long-horizon-task, context-window -->
<!-- index-def: long-horizon-task -->
A supervised engineering task runs long. Not a single prompt and a single answer — a
campaign: read the system, form a plan, make a change, check what broke, reconcile, and
carry every earlier decision forward into the next step. Over that campaign the reasoning
state the work depends on keeps growing. The reasoner that holds it does not. It works
through a finite fast working memory, and a **long-horizon task** is one whose reasoning
state outruns the memory available to hold it.

<!-- point: outrun-memory-forces-lossy-compression-that-degrades-into-churn | When state outruns memory it must be compressed and reconstructed; each lossy round trip degrades the reasoning and surfaces as churn. | terms: reasoning-horizon, churn -->
<!-- index-def: reasoning-horizon -->
So the state has to be compressed and reconstructed, over and over. Each round trip is
lossy, and every lossy reconstruction degrades the reasoning it stands in for. The
reasoner rediscovers what it already knew, contradicts a decision it made an hour ago,
re-solves a solved problem. That degradation is **churn** — effort spent rebuilding a
picture the reasoner keeps losing, instead of advancing the system.

<!-- point: the-chain-stated-end-to-end | The chain runs from long-horizon reasoning to churn. | terms: reasoning-horizon, churn -->
Read the chain end to end [ref:reasoning-horizon-fig]. Long-horizon reasoning creates working-memory pressure;
pressure forces compression and reconstruction; lossy reconstruction degrades the
reasoning; degradation surfaces as churn.

<!-- point: capability-moves-the-wall-not-abolishes-it | Greater model capability moves the wall; it does not abolish the finite-state and locality problem. | terms: reasoning-horizon, context-window -->
Greater model capability can move the wall by improving how effectively available state is used; it
does not abolish the finite-state and locality problem. We already see both effects. Models can be
given the same long context and differ dramatically in how much of it they can actually use; RULER
found that effective context length often fell well short of advertised context length and varied
substantially across models [cite:hsieh2024ruler]. And simply putting a fact inside the window does
not make it equally available: Lost in the Middle showed that retrieval and question-answering
accuracy can depend strongly on where relevant information appears in a long context
[cite:liu2024lostmiddle]. A better model may search the warehouse better. It still has a warehouse.

Independent practice reports the same wall. Sourcegraph's study of 1,281 scored agent runs
across 40-plus of the largest open-source repositories found that above roughly 400,000
lines of code, agents navigating by following raw references build an exploration tree that
branches faster than they can prune it — failure arising from the *shape* of the reasoning
substrate, not a shortfall in model capability [cite:sourcegraph2026largecodebase].

## The horizon is a locality problem

<!-- section-terms: reasoning-horizon, context-window, engineering-substrate -->

<!-- point: context-windows-are-an-instantiation-of-the-limit-not-the-limit | Context windows are today's most visible instantiation of the limit, not the limit itself; the durable constraint is locality. | terms: context-window, reasoning-horizon -->
It is tempting to read this as a fact about today's context window, and so as a fact that
the next model will erase. It is not. Context windows are today's most visible
instantiation of the limit, not the limit itself. Future architectures may enlarge working
state, improve recurrence, add persistent memory, or reorganize retrieval. Hardware still
imposes a memory hierarchy: the state available at the bandwidth and latency required for
active reasoning stays finite. Long-horizon engineering therefore keeps facing a locality
problem. The question is not whether the machine has the memory somewhere; it is whether
the *right* state can stay available, coherent, and cheap enough to reason over when
needed.

<!-- point: this-is-an-old-engineering-constraint-in-a-new-form | Software has always been arranged around the memory, compute, and communication hierarchy of its machine; agentic systems inherit the same obligation. | terms: engineering-substrate, reasoning-horizon -->
This is an old engineering constraint in a new form. Software has always been shaped by the
memory, computation, and communication hierarchy of the machine beneath it. We reach for
tmpfs when persistence is unnecessary, because RAM is faster than storage; we keep a
database in memory when latency matters enough to pay for it; we build caches precisely
because refetching the same state from a slower tier is wasteful. A real-time bound is
parameterized to the processor that will run the code, because a worst-case execution time
means nothing independent of the hardware that realizes it. Distributed systems make the
same trade: compute on-device rather than cross a network, prefer a local hop to a remote
one, replicate data near the computation that consumes it. None of these techniques
abolishes the hierarchy. They arrange software so the state and computation needed most
urgently sit near the resources that can serve them cheaply. Agentic systems inherit that
obligation. A larger context window, external memory, a retrieval system, a new neural
architecture — each changes the hierarchy and its constants; none removes the engineering
problem of keeping the right reasoning state close enough to the reasoner when it is needed.
Today's context window is one instantiation of the hierarchy. Architectures and hardware
change the constants; they do not eliminate locality.

<!-- point: the-reasoning-horizon-is-the-latest-instance-of-a-recurring-se-problem | The reasoning horizon is the latest instance of a recurring software-engineering problem: the abstraction is organized around the physical limits of the machine. | terms: reasoning-horizon, engineering-substrate -->
Seen this way, the reasoning horizon is not an exotic property of language models. It is
the latest instance of a recurring software-engineering problem: the abstraction must be
organized around the physical limits of the machine that executes it. Virtual memory,
caches, locality-aware algorithms, real-time scheduling, NUMA awareness, accelerator
programming — software has repeatedly reorganized itself around what the hardware makes
expensive. Reasoning state is now one more resource whose locality has to be engineered.

<!-- point: the-account-earns-the-moves-the-wall-claim | A longer window or new architecture moves the wall without removing it; the hardware account earns that claim rather than asserting it. | terms: reasoning-horizon, engineering-substrate -->
That is what makes the account durable rather than a 2026 quirk. A longer window, a new
memory architecture, a post-transformer system — each moves the wall; none removes it,
because a finite reasoner still has a finite reasoning horizon. The claim is a claim about
the shape of the problem, offered for the reader to test against their own systems, not a
law this one case can prove. It inoculates against the easy dismissal — "GPT-9 will have a
ten-million-token window, so the theory disappears." No: the constants change, the
hierarchy moves, the engineering principle survives.

## What the reasoner should work through

<!-- section-terms: reasoning-horizon, map-and-territory, churn -->

<!-- point: loss-is-a-function-of-the-domain-you-compress-over | The loss in a reconstruction is not a fixed tax; it depends on what you compress over. | terms: reasoning-horizon, map-and-territory -->
Return to the lossy round trip, because it hides the hinge. The loss in a reconstruction is
not a fixed tax on long-horizon work. It depends on *what* the reasoner compresses over.
Compress over raw implementation and the round trip throws away the reasoning along with
the detail. A codebase is large and semantically noisy, most of its bulk irrelevant to any
one decision, and a lossy compaction cannot tell the essential line from the incidental
one. A representation that had already dropped the irrelevant detail would lose far less on
every reconstruction, because what survived would be the information that carried the
reasoning in the first place. The reasoning horizon a human–agent system can hold is not
fixed by the model; it is set by the domain the system reasons through.

<!-- point: the-unanswered-question-pulls-to-part-ii | Close on the open question: if raw implementation is a poor working state for a finite reasoner, what should it work through instead? | terms: reasoning-horizon, map-and-territory -->
Which leaves the chapter on a question it does not answer. If raw implementation is too
large and too semantically noisy to serve as the working state of a finite reasoner, what
*should* the reasoner work through instead? Part I can pose the question; it cannot settle
it. The next Part takes it up.
