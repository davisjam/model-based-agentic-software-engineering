# The Agentic Substrate

<!-- section-terms: engineering-substrate, foundation-model, agentic-harness -->

<!-- point: engineering-methods-follow-from-the-material | Engineering methods fit the substrate they act on; agentic engineering begins by asking what productive substrate entered the process, because its combination and economics change what the engineering environment can do. | terms: engineering-substrate -->
Engineering methods have to fit the substrate they act on. Reinforced concrete works because
concrete takes compression and steel takes tension; where the bars run follows from those
properties. Agentic software engineering likewise begins by asking what kind of productive
substrate has entered the process—not because every property is unprecedented, but because their
combination and economics change what the engineering environment can do.

## The substrate is a pairing

<!-- section-terms: engineering-substrate, foundation-model, agentic-harness -->

<!-- point: model-plus-harness-form-a-new-engineering-substrate | A foundation model and an agentic harness together form the engineering substrate; the useful unit is the pair operating inside an engineering environment. | terms: engineering-substrate, foundation-model, agentic-harness -->
<!-- index-def: engineering-substrate -->
The substrate is two parts, not one. A foundation model supplies broad, inexpensive semantic
reasoning. An agentic harness—the runtime around it—turns reasoning into action by supplying
tools, lifecycle, state, and points where work can be observed or stopped. Neither half alone is
the engineering substrate that matters here; the useful unit is the pair operating inside an
engineering environment.

<!-- point: four-foundation-model-properties | The foundation model brings four properties. | terms: foundation-model -->
The foundation model brings four:

- **Broad semantic reasoning.** It interprets, synthesizes, and searches across
  open-ended domains. Hand it an abstraction — a schema, a state table, a policy —
  and it works over the abstraction, not just a fixed script.
- **Probabilistic output.** Repeated runs can differ, and the model's confidence in
  its own result is not independent evidence that the result is correct. The
  producing run cannot become engineering authority merely by affirming its own
  output.
- **Bounded, reconstructed working state.** Active reasoning state is finite. Durable
  knowledge about the system therefore has to be retained outside the producing run
  and supplied, retrieved, or reconstructed when later work needs it. A harness can
  make that reconstruction much better; it cannot make active reasoning state
  unbounded.
- **Cheap repeated cognition.** Search, generation, repair, reconciliation —
  cognitive work that once cost an engineer's week now runs at a scale that was
  formerly out of reach.

<!-- point: four-harness-properties | The harness adds four properties of its own. | terms: agentic-harness, injection-point -->
The harness adds four of its own. A raw model only recommends; the harness turns
recommendation into action, and every part of that turn is a property the engineer
can use:

- **Tool-mediated action.** The agent touches the world only through identifiable
  interfaces — a file edit, a command, an API call. There are no bare hands.
- **Interposition.** Because every action crosses an interface, a hook or wrapper
  can inspect it, constrain it, redirect it, or deny it at the moment it happens.
- **Lifecycle visibility.** Dispatch, tool calls, compaction, completion, merge,
  deploy — the work's transitions are machine-observable events, not private states
  in a worker's head.
- **Parallel execution.** Many independent reasoning loops run at once, on one
  codebase, around the clock.

<!-- point: the-substrate-framing-is-an-emerging-consensus | None of these properties is alien to human engineering; what changes is their combination and economics, and the harness-engineering literature reaches the same unit of analysis — the model-harness-environment system. | terms: engineering-substrate, agentic-harness -->
None of these properties is wholly alien to human software engineering. Humans also
reason with bounded state, make uncertain judgments, use tools, and rely on evidence
outside themselves. What changes is the combination: broad semantic work is now cheap
and repeatable; implementation can proceed in many parallel reasoning loops; and the
harness exposes machine-observable boundaries around that work. The emerging literature
on harness engineering reaches the same practical unit of analysis: autonomous
capability belongs to the model–harness–environment system rather than to the
foundation model alone [cite: zhong-zhu2026] [cite: young-anthropic2025]
[cite: tan-thinharness2026]. The argument here is not that this substrate abolishes old
engineering problems, but that it changes their economics and exposes new places to act
on them.

## The reasoning horizon {#the-reasoning-horizon}

<!-- section-terms: long-horizon-task, reasoning-horizon, churn, context-window -->

<!-- point: supervised-work-is-long-horizon-and-outruns-working-memory | Scale creates the reasoning problem before an agent enters; a long task is a campaign whose reasoning state grows while the active state available to the reasoner stays finite. | terms: long-horizon-task, context-window -->
<!-- index-def: long-horizon-task -->
Scale creates a reasoning problem before an agent ever enters the picture. A sufficiently large
software system exceeds what one engineer can keep actively in mind; agentic work inherits the
same condition. A long engineering task is not a prompt and an answer but a campaign: read the
system, form a plan, make a change, inspect the result, reconcile what changed, and carry
consequential earlier decisions into the next step. The reasoning state required by that campaign
grows. The active state available to the reasoner remains finite.

<!-- point: outrun-memory-forces-lossy-compression-that-degrades-into-churn | Once the task outruns active state, some state must live elsewhere and be reconstructed; poor reconstruction re-solves solved questions and contradicts earlier constraints — one source of churn. | terms: reasoning-horizon, churn -->
<!-- index-def: reasoning-horizon -->
Once the task outruns active working state, some of that state has to live elsewhere and be
reconstructed when needed. The reconstruction may be excellent or poor. If the reasoner repeatedly
rebuilds its picture from raw implementation, loose notes, or lossy compaction, relevant decisions
disappear into irrelevant detail: solved questions are re-solved, earlier constraints are
contradicted, and context has to be rediscovered. That recurring reconstruction cost is one source
of **churn** [ref:reasoning-horizon-fig].

<!-- point: capability-moves-the-wall-not-abolishes-it | Better models move the boundary by using available state more effectively; they do not abolish the locality problem — a better model searches the warehouse better but still has a warehouse. | terms: reasoning-horizon, context-window -->
Better models can move the boundary by using available state more effectively; they do not abolish
the underlying locality problem. We already see both effects. RULER found that effective context
length can fall well short of advertised context length and vary substantially across models
[cite: hsieh2024ruler]. *Lost in the Middle* showed that a fact's presence inside a long context
does not make it equally available to the reasoner [cite: liu2024lostmiddle]. A better model may
search the warehouse better. It still has a warehouse.

<!-- point: the-chain-stated-end-to-end | Practice at codebase scale reports the same effect; the point is not a line-count threshold but that raw implementation is an expensive reasoning substrate when the question depends on a much smaller set of relationships. | terms: reasoning-horizon, churn -->
Independent practice reports a related effect at codebase scale. Sourcegraph's study of 1,281
scored agent runs across more than 40 large open-source repositories found that agents navigating
by following raw references increasingly built exploration trees they could not prune effectively
as repositories grew [cite: sourcegraph2026largecodebase]. The relevant point is not a magic
line-count threshold. Raw implementation is an expensive reasoning substrate when the engineering
question depends on a much smaller set of relationships.

## The horizon is a locality problem

<!-- section-terms: reasoning-horizon, context-window, engineering-substrate -->

<!-- point: context-windows-are-an-instantiation-of-the-limit-not-the-limit | Context windows are today's most visible instantiation of the limit, not the limit itself; the durable constraint is locality. | terms: context-window, reasoning-horizon -->
It is tempting to read this as a fact about today's context window, and so as a fact that
the next model will erase. It is not. Context windows are today's most visible
instantiation of the limit, not the limit itself. Future architectures may enlarge working
state, improve recurrence, add persistent memory, or reorganize retrieval. Hardware still
imposes a memory hierarchy: the state available at the bandwidth and latency required for
active reasoning stays finite. Long-horizon engineering therefore keeps facing a locality
problem. The question is not whether the machine has the memory somewhere; it is whether
the *right* state can stay available, coherent, and cheap enough to reason over when
needed.

<!-- point: this-is-an-old-engineering-constraint-in-a-new-form | Software has always been arranged around the memory, compute, and communication hierarchy of its machine; agentic reasoning inherits the same obligation. | terms: engineering-substrate, reasoning-horizon -->
This is an old engineering constraint in a new form. Software has always been shaped by the
memory, computation, and communication hierarchy of the machine beneath it. We reach for
tmpfs when persistence is unnecessary, because RAM is faster than storage; we keep a
database in memory when latency matters enough to pay for it; we build caches precisely
because refetching the same state from a slower tier is wasteful. A real-time bound is
parameterized to the processor that will run the code, because a worst-case execution time
means nothing independent of the hardware that realizes it. Distributed systems make the
same trade: compute on-device rather than cross a network, prefer a local hop to a remote
one, replicate data near the computation that consumes it. None of these techniques
abolishes the hierarchy. They arrange software so the state and computation needed most
urgently sit near the resources that can serve them cheaply. Agentic reasoning inherits that
obligation. A larger context window, external memory, a retrieval system, a new neural
architecture — each changes the hierarchy and its constants; none removes the engineering
problem of keeping the right reasoning state close enough to the reasoner when it is needed.
Today's context window is one instantiation of the hierarchy. Architectures and hardware
change the constants; they do not eliminate locality.

<!-- point: the-reasoning-horizon-is-the-latest-instance-of-a-recurring-se-problem | The reasoning horizon is the latest instance of a recurring software-engineering problem: the abstraction is organized around the physical limits of the machine. | terms: reasoning-horizon, engineering-substrate -->
Seen this way, the reasoning horizon is not an exotic property of language models. It is
the latest instance of a recurring software-engineering problem: the abstraction must be
organized around the physical limits of the machine that executes it. Virtual memory,
caches, locality-aware algorithms, real-time scheduling, NUMA awareness, accelerator
programming — software has repeatedly reorganized itself around what the hardware makes
expensive. Reasoning state is now one more resource whose locality has to be engineered.

<!-- point: the-account-earns-the-moves-the-wall-claim | A longer window or new architecture moves the wall without removing it; the hardware account earns that claim rather than asserting it. | terms: reasoning-horizon, engineering-substrate -->
That is what makes the account durable rather than a 2026 quirk. A longer window, a new
memory architecture, a post-transformer system — each moves the wall; none removes it. For
sufficiently large tasks, efficient reasoning still requires a way to keep question-relevant
state close to the reasoner and irrelevant detail out of the active working set, because
active reasoning state stays finite and expensive relative to stored state. The claim is a
claim about the shape of the problem, offered for the reader to test against their own
systems, not a law this one case can prove. It inoculates against the easy dismissal — "GPT-9
will have a ten-million-token window, so the theory disappears." No: the constants change, the
hierarchy moves, the engineering principle survives.

## Probabilistic work needs external authority

<!-- section-terms: foundation-model, engineering-substrate -->

<!-- point: authorship-is-separate-from-assurance | Software engineering has always separated authorship from assurance — we compile instead of trusting a prediction, test instead of accepting an explanation — because the producer's confidence is not enough. | terms: engineering-substrate, foundation-model -->
The second problem is not that agents make mistakes while human programmers do not. Software
engineering has always separated authorship from assurance. We compile code instead of
trusting the programmer's prediction that it compiles; we run tests instead of accepting an
explanation that the program should work; consequential systems add review, static analysis,
formal methods, operational evidence, or independent approval because the producer's
confidence is not enough.

<!-- point: authority-must-reside-outside-the-agent | Commodity intelligence makes that separation more important because implementation is cheap and repeatable; another judgment from the same substrate does not create authority — something outside the producing run must decide what evidence counts. | terms: engineering-substrate, foundation-model -->
Commodity intelligence makes that separation more important because implementation becomes
cheap, fast, and repeatable. A model can propose a change, inspect it, explain it, and often
repair it, but another probabilistic judgment from the same productive substrate does not
automatically create engineering authority. If an obligation matters, something outside the
producing run has to decide what evidence counts and what follows when the obligation is not
met.

<!-- point: alignment-has-semantic-reach-and-modeling-moves-the-boundary-outward | Some obligations need little modeling — a sandbox, compiler, test, or permission system holds them; those are real Alignment, limited by semantic reach. Modeling moves that boundary outward, making larger properties available to the reasoner and to deterministic machinery. | terms: engineering-substrate, foundation-model, thesis-modeling, thesis-alignment -->
Some obligations require little explicit modeling. A sandbox can forbid network access; a
compiler can reject an illegal construct; a test can block a regression against observed
behavior; a permission system can deny an action. Those are real forms of Alignment. Their
limit is semantic reach. When the obligation concerns architecture, ownership, permitted
service relationships, end-to-end lifecycle behavior, or another property not explicit in
the local artifact, the environment needs an abstraction that states the property—or a human
has to reconstruct the missing semantics and judge the case. **Modeling moves that boundary
outward.** It makes larger engineering properties available both to the reasoner and to
deterministic machinery.

## The loop is observable

<!-- section-terms: agentic-harness, injection-point, engineering-substrate -->

<!-- point: agentic-work-occurs-in-an-observable-loop | Agentic work occurs in an observable loop; the engineer need not control hidden reasoning to govern what enters the system — authority can act at the seams the work has to cross. | terms: agentic-harness, injection-point -->
One property of the harness makes external authority practical. Agentic work occurs in an
observable loop rather than one indivisible act. The model may reason internally, but its
inputs, tool calls, edits, outputs, and lifecycle transitions meet an external engineering
environment. The engineer therefore need not control hidden reasoning in order to govern what
enters the system. Authority can act at the seams the work has to cross.

<!-- point: representation-determines-what-the-control-points-can-know | Seams already support local controls without a system model; the deeper opportunity comes when the environment holds explicit abstractions of what matters — the harness supplies the control points, representation determines how much they can know. | terms: agentic-harness, injection-point, engineering-substrate -->
Those seams already support useful local controls without a system model. The deeper
opportunity appears when the environment also possesses explicit abstractions of the
properties that matter: the same observable loop can then be judged against architecture,
policy, behavior, ownership, measurements, and other obligations whose meaning is not visible
in a single action. The harness supplies the control points; representation determines how
much those control points can know.

We can now state the engineering problem completely.
