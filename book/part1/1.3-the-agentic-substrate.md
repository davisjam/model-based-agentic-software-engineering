# The Agentic Substrate

<!-- section-terms: engineering-substrate, foundation-model, agentic-harness -->

<!-- point: engineering-methods-follow-from-the-material | Engineering methods fit the substrate they act on; reinforced concrete works because concrete takes compression and steel takes tension, and agentic engineering likewise begins by asking what productive machinery entered the process and which of its properties matter. | terms: engineering-substrate -->
Engineering methods have to fit the substrate they act on. Reinforced concrete works because concrete takes
compression and steel takes tension; where the reinforcement goes follows from those properties. Agentic
software engineering likewise begins by asking what productive machinery has entered the engineering process
and which of its properties matter.

<!-- point: the-substrate-is-model-plus-harness-in-an-environment | The relevant substrate is not a foundation model alone but a foundation model operating through an agentic harness inside an engineered environment; the combination determines both what autonomous work can do and where engineering can act on it. | terms: engineering-substrate, foundation-model, agentic-harness -->
For MAGE, the relevant substrate is not a foundation model alone. It is a foundation model operating through
an agentic harness inside an engineered environment. The combination determines both what autonomous work
can do and where engineering can act on it.

## Foundation Model and Agentic Harness

<!-- section-terms: engineering-substrate, foundation-model, agentic-harness -->

<!-- point: model-plus-harness-form-a-new-engineering-substrate | A foundation model and an agentic harness together form the engineering substrate; the useful unit is the pair operating inside an engineered environment. | terms: engineering-substrate, foundation-model, agentic-harness -->
<!-- index-def: engineering-substrate -->
The substrate pairs a foundation model with an agentic harness. A foundation model supplies broad,
inexpensive semantic reasoning. An agentic harness—the runtime around it—turns reasoning into action by
supplying tools, lifecycle, state, and points where work can be observed or stopped. Neither half alone is
the engineering substrate that matters here; the useful unit is the pair operating inside an engineering
environment.

<!-- point: four-foundation-model-properties | Four properties of the foundation model matter to the engineering argument. | terms: foundation-model -->
Four properties of the foundation model matter to the engineering argument:

- **Broad semantic reasoning.** A foundation model can interpret, synthesize, and search across open-ended
  domains. Give it an abstraction—a schema, state table, or policy—and it can reason over that abstraction
  rather than merely execute a fixed script.
- **Probabilistic output.** Repeated runs can differ, and the foundation model's confidence in its own
  result is not independent evidence that the result is correct. The producing run cannot create engineering
  authority merely by affirming its own output.
- **Bounded working state.** Active reasoning state is finite. Durable system knowledge must therefore
  persist outside the producing run and be supplied, retrieved, or reconstructed when later work needs it. A
  harness can improve that process; it cannot make active reasoning state unbounded.
- **Cheap repeated cognition.** Search, generation, repair, and reconciliation—cognitive work that once
  consumed substantial engineering labor—can now be repeated at previously impractical scale.

<!-- point: four-harness-properties | The harness contributes four complementary properties; a foundation model produces outputs, and the harness turns those outputs into action and exposes the boundaries through which that action passes. | terms: agentic-harness, injection-point -->
The harness contributes four complementary properties. A foundation model produces outputs; the harness
turns those outputs into action and exposes the boundaries through which that action passes.

- **Tool-mediated action.** The agent touches the world only through identifiable interfaces — a file edit,
  a command, an API call. There are no bare hands.
- **Interposition.** Because every action crosses an interface, a hook or wrapper can inspect it, constrain
  it, redirect it, or deny it at the moment it happens.
- **Lifecycle visibility.** Dispatch, tool calls, compaction, completion, merge, deploy — the work's
  transitions are machine-observable events, not private states in a worker's head.
- **Parallel execution.** Many independent reasoning loops run at once, on one codebase, around the clock.

<!-- point: the-substrate-framing-is-an-emerging-consensus | None of these properties is alien to human engineering; what changes is their combination and economics, and the harness-engineering literature reaches the same unit of analysis — the model–harness–environment system. | terms: engineering-substrate, agentic-harness -->
None of these properties is wholly alien to human software engineering. Humans also
reason with bounded state, make uncertain judgments, use tools, and rely on evidence
outside themselves. What changes is the combination: broad semantic work is now cheap
and repeatable; implementation can proceed in many parallel reasoning loops; and the
harness exposes machine-observable boundaries around that work. The emerging literature
on harness engineering reaches the same practical unit of analysis: autonomous
capability belongs to the model–harness–environment system rather than to the
foundation model alone [cite: zhong-zhu2026] [cite: young-anthropic2025]
[cite: tan-thinharness2026]. [ref:agentic-substrate] shows that combination. This substrate changes the
economics of old engineering problems and exposes new places to act on them.

## The reasoning horizon {#the-reasoning-horizon}

<!-- section-terms: long-horizon-task, reasoning-horizon, churn, context-window -->

<!-- point: supervised-work-is-long-horizon-and-outruns-working-memory | Scale creates the reasoning problem before an agent enters; a long task is a campaign whose reasoning state grows while the active state available to the reasoner stays finite. | terms: long-horizon-task, context-window -->
<!-- index-def: long-horizon-task -->
Scale creates a reasoning problem before an agent ever enters the picture. A sufficiently large
software system exceeds what one engineer can keep actively in mind; agentic work inherits the
same condition. A long engineering task is not a prompt and an answer but a campaign: read the
system, form a plan, make a change, inspect the result, reconcile what changed, and carry
consequential earlier decisions into the next step. The reasoning state required by that campaign
grows. The active state available to the reasoner remains finite.

<!-- point: outrun-memory-forces-lossy-compression-that-degrades-into-churn | Once the task outruns active state, some state must live elsewhere and be reconstructed; poor reconstruction re-solves solved questions and contradicts earlier constraints — one source of churn. | terms: reasoning-horizon, churn -->
<!-- index-def: reasoning-horizon -->
Once the task outruns active working state, some of that state has to live elsewhere and be
reconstructed when needed. The reconstruction may be excellent or poor. If the reasoner repeatedly
rebuilds its picture from raw implementation, loose notes, or lossy compaction, relevant decisions
disappear into irrelevant detail: solved questions are re-solved, earlier constraints are
contradicted, and context has to be rediscovered. That recurring reconstruction cost is one source
of **churn** [ref:reasoning-horizon-fig].

<!-- point: capability-moves-the-wall-not-abolishes-it | Better representations move the boundary by using available working state more effectively; they do not abolish the locality problem — a stronger reasoner searches the warehouse better but still has a warehouse. | terms: reasoning-horizon, context-window -->
Better representations can move the boundary by using available working state more effectively; they do not
abolish the underlying locality problem. We already see both effects. RULER found that effective context
length can fall well short of advertised context length and vary substantially across foundation models
[cite: hsieh2024ruler]. *Lost in the Middle* showed that a fact's presence inside a long context
does not make it equally available to the reasoner [cite: liu2024lostmiddle]. A stronger reasoner may
search the warehouse better. It still has a warehouse.

<!-- point: the-chain-stated-end-to-end | Practice at codebase scale reports the same effect; the point is not a line-count threshold but that raw implementation is an expensive reasoning substrate when the question depends on a much smaller set of relationships. | terms: reasoning-horizon, churn -->
Independent practice reports a related effect at codebase scale. Sourcegraph's study of 1,281
scored agent runs across more than 40 large open-source repositories found that agents navigating
by following raw references increasingly built exploration trees they could not prune effectively
as repositories grew [cite: sourcegraph2026largecodebase]. The relevant point is not a magic
line-count threshold. Raw implementation is an expensive reasoning substrate when the engineering
question depends on a much smaller set of relationships.

## The horizon is a locality problem

<!-- section-terms: reasoning-horizon, context-window, engineering-substrate -->

<!-- point: the-reasoning-horizon-is-a-familiar-systems-problem | The reasoning horizon is not exotic; it is a familiar systems problem — useful state must be kept close enough to the computation that consumes it, and agentic reasoning adds reasoning state to the list caches, virtual memory, NUMA-aware software, and replication already occupy. | terms: reasoning-horizon, engineering-substrate -->
Seen this way, the reasoning horizon is not an exotic property of language models. It is another instance of
a familiar systems problem: useful state must be kept close enough to the computation that consumes it.
Caches, virtual memory, NUMA-aware software, locality-aware algorithms, and distributed replication all
reorganize computation around finite and unequal access to state. Agentic reasoning adds reasoning state to
that list.

<!-- point: new-architectures-move-constants-not-the-principle | Larger windows, persistent memory, retrieval, or new architectures move the boundaries and change the constants; they do not remove the engineering principle that question-relevant state must stay available and cheap to reason over while irrelevant detail stays outside the active working set. | terms: reasoning-horizon, engineering-substrate, context-window -->
Larger context windows, persistent memory, retrieval systems, or new neural architectures will move the
boundaries and change the constants. They do not remove the engineering principle. For sufficiently large
tasks, question-relevant state must remain available and cheap enough to reason over while irrelevant detail
stays outside the active working set.

## Probabilistic work needs external authority

<!-- section-terms: foundation-model, engineering-substrate -->

<!-- point: authorship-is-separate-from-assurance | Software engineering has always separated authorship from assurance — we compile instead of trusting a prediction, test instead of accepting an explanation — because the producer's confidence is not enough. | terms: engineering-substrate, foundation-model -->
The second problem is not that agents make mistakes while human programmers do not. Software
engineering has always separated authorship from assurance. We compile code instead of
trusting the programmer's prediction that it compiles; we run tests instead of accepting an
explanation that the program should work; consequential systems add review, static analysis,
formal methods, operational evidence, or independent approval because the producer's
confidence is not enough.

<!-- point: authority-must-reside-outside-the-agent | Commodity intelligence makes that separation more important because implementation is cheap and repeatable; an agent can propose, inspect, explain, and repair, but another judgment from the same substrate does not create authority — something outside the producing run must decide what evidence counts. | terms: engineering-substrate, foundation-model -->
Commodity intelligence makes that separation more important because implementation becomes
cheap, fast, and repeatable. An agent can propose a change, inspect it, explain it, and often
repair it, but another probabilistic judgment from the same productive substrate does not
automatically create engineering authority. If an obligation matters, something outside the
producing run has to decide what evidence counts and what follows when the obligation is not
met.

<!-- point: alignment-has-semantic-reach-and-modeling-moves-the-boundary-outward | Some obligations need little modeling — a sandbox, compiler, test, or permission system holds them; those are real Alignment, limited by semantic reach. Modeling moves that boundary outward, making larger properties available to the reasoner and to deterministic machinery. | terms: engineering-substrate, foundation-model, thesis-modeling, thesis-alignment -->
Some obligations require little explicit modeling. A sandbox can forbid network access; a
compiler can reject an illegal construct; a test can block a regression against observed
behavior; a permission system can deny an action. Those are real forms of Alignment. Their
limit is semantic reach. When the obligation concerns architecture, ownership, permitted
service relationships, end-to-end lifecycle behavior, or another property not explicit in
the local artifact, the environment needs an abstraction that states the property—or a human
has to reconstruct the missing semantics and judge the case. **Modeling moves that boundary
outward.** It makes larger engineering properties available both to the reasoner and to
deterministic machinery.

## Agentic Work Has Observable Seams

<!-- section-terms: agentic-harness, injection-point, engineering-substrate -->

<!-- point: agentic-work-occurs-through-observable-interfaces | Agentic work occurs through observable interfaces; whatever internal computation produces a proposed action, consequential work reaches the engineering system through inputs, tool calls, edits, outputs, and lifecycle transitions — boundaries the environment can observe, constrain, validate, or stop. | terms: agentic-harness, injection-point -->
Agentic work occurs through observable interfaces. Whatever internal computation produces a proposed action,
consequential work reaches the engineering system through inputs, tool calls, edits, outputs, and lifecycle
transitions. Those boundaries give the engineered environment places to observe, constrain, validate, or
stop the work.

<!-- point: representation-determines-what-the-control-points-can-know | Local controls already operate at these seams without a system model; explicit engineering models extend the semantic reach of the same control points, so an action can be judged not only by what it does but by what it means for architecture, policy, behavior, ownership, measurements, or other represented obligations. | terms: agentic-harness, injection-point, engineering-substrate -->
Useful local controls already operate at these seams without a system model: a sandbox can deny network
access, a hook can reject a command, and a test can block a regression. Explicit engineering models extend
the semantic reach of the same control points. An action can then be judged not only by what it immediately
does, but by what it means for architecture, policy, behavior, ownership, measurements, or other represented
obligations.

The harness supplies the control points; representation determines what those control points can know.
