# Two Problems the Method Must Solve

## The Two Problems in Software

<!-- point: substrate-leaves-two-problems | The engineered environment can improve the agent’s implementation success and support engineers in choosing requirements and establishing whether the result meets them; these aims lead to the Representation Problem and the Enforcement Problem. | terms: engineering-substrate, foundation-model, agentic-harness -->

The probability model in {{sec:reasoning-horizon}} gives us one aim: increase the agent’s chance of implementing all the required features correctly.[^1] The engineered environment—the structures and practices we arrange around the agent’s work—can also support engineers in deciding what those requirements should be and establishing whether the result meets them. These aims lead to two related but distinct engineering problems:

<!-- index-def: enforcement-problem -->

1.  **The Representation Problem.** Large systems contain far more detail than any one engineering question needs, while the active state available to a reasoner is finite. How should a large, evolving system be represented so that the properties relevant to an engineering question can be reasoned about without continually reconstructing them from implementation? {{chapter:modeling}} develops the corresponding part of the MAGE methodology: Modeling.

2.  **The Enforcement Problem.** Autonomous work can be constrained and checked at the interfaces through which it acts, so that the agent is not its own arbiter of validity. How should engineering intent be enforced over autonomous work, so that satisfying important obligations does not depend on the agent remembering, agreeing, or self-certifying each time? {{chapter:alignment}} develops the corresponding part of the MAGE methodology: Alignment.

<!-- point: modeling-and-alignment-complement-one-another | Modeling represents selected system properties; Alignment constrains work and evaluates results. In DocAble, the content representation supports comparison and the validator fails a job that loses original extracted content. | terms: modeling-principle, alignment-principle -->

The two activities complement one another. Modeling makes selected system properties explicit enough to reason about; Alignment uses represented obligations to constrain work and evaluate its results. In the DocAble example, the content representation lets a validator compare the original and revised documents. The validator fails the job if the revised document is missing any of the original extracted content. Together, these structures carry an engineering decision forward into later work. ## The Problem Is Larger than Software

<!-- point: the-problem-is-larger-than-software | Software makes the governing problem visible; it does not create it. -->

Software makes the problem unusually visible, but does not create it.

Suppose an agent is asked to perform consequential work in some other domain. It may analyze a contract, develop an engineering design, reconcile a set of accounts, or synthesize evidence for a scientific question. The artifacts differ, but two problems remain. First, the knowledge needed to do the work may exceed what the agent can reliably reconstruct and reason over in one episode. Second, some judgments matter enough that whether the work takes effect should not depend only on the producing agent having made those judgments correctly.

Those are the same two problems this chapter named the Representation Problem and the Enforcement Problem. Modeling addresses the first by making consequential knowledge available in representations suited to the questions being asked. Alignment addresses the second by giving selected obligations evidence and enforcement outside the producing reasoner. Neither move fundamentally requires source code.

What changes across domains is the engineering material. Software has requirements, architectures, dependency graphs, types, tests, admission gates, permissions, telemetry, and executable artifacts. Mechanical engineering has geometry, tolerances, load models, simulations, and physical tests. Accounting has ledgers, classifications, reconciliations, controls, and audit evidence. Legal work has authorities, claims, elements, facts, procedural rules, and approval structures. The useful representations differ, as do the obligations that can responsibly be enforced.

MAGE is an approach to governing agentic engineering work by engineering what the agent and its environment can know, decide, check, and enforce. This book develops that approach through software engineering because software is where we have exercised it deeply enough to study the mechanisms. The broader claim is theoretical and predictive. If the account is right, similar leverage should appear elsewhere when consequential knowledge can be represented, important obligations can be evaluated with adequate evidence, and the resulting structure is economical to maintain.

The balance between inference, explicit representation, and enforcement will change as agents improve. MAGE does not prescribe that balance in advance; it asks engineers to establish it for the systems and obligations they face.

The following chapters develop the software-engineering mechanisms in detail. {{chapter:theory}} abstracts those mechanisms into a theory. {{chapter:profession}} then asks what remains when the software-specific assumptions are relaxed.

[^1]: Or at least, correctly enough that we can finish the job economically. Human code review and cleanup, or a final pass with a more capable but more expensive model, may supply what the initial agent leaves undone. The relevant cost is that of the whole process, including finding and fixing mistakes; the result must still meet its requirements.
