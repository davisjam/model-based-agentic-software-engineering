# Two Problems the Method Must Solve

## The Two Problems in Software

<!-- point: substrate-leaves-two-problems | The engineered environment can improve the agent’s implementation success and support engineers in choosing requirements and establishing whether the result meets them; these aims lead to the Representation Problem and the Enforcement Problem. | terms: engineering-substrate, foundation-model, agentic-harness -->

The probability model in {{sec:reasoning-horizon}} gives us one aim: increase the agent’s chance of implementing all the required features correctly.[^1] The engineered environment—the structures and practices we arrange around the agent’s work—can also support engineers in deciding what those requirements should be and establishing whether the result meets them.

Better context can help an agent make a consequential judgment correctly. A useful model can sometimes change the task itself: it makes the relevant property explicit enough to analyze or check without reconstructing the implementation. The first improves the agent’s chances of getting the answer right; the second can reduce how often the question must be answered through inference.

These two aims—the agent’s implementation success, and support for engineers choosing requirements and establishing whether the result meets them—lead to two related but distinct engineering problems:

1.  **The Representation Problem.** Large systems contain far more detail than any one engineering question needs, while the active state available to a reasoner is finite. How should a large, evolving system be represented so that the properties relevant to an engineering question can be reasoned about without continually reconstructing them from implementation? {{chapter:modeling}} develops the corresponding part of the MAGE methodology: Modeling.

2.  **The Enforcement Problem.** Autonomous work can be constrained and checked at the interfaces through which it acts, so that the agent is not its own arbiter of validity. How should engineering intent be enforced over autonomous work, so that satisfying important obligations does not depend on the agent remembering, agreeing, or self-certifying each time? {{chapter:alignment}} develops the corresponding part of the MAGE methodology: Alignment.

<!-- point: modeling-and-alignment-complement-one-another | Modeling represents selected system properties; Alignment constrains work and evaluates results. In DocAble, the content representation supports comparison and the validator fails a job that loses original extracted content. | terms: modeling-principle, alignment-principle -->

The two activities complement one another. Modeling makes selected system properties explicit enough to reason about; Alignment uses represented obligations to constrain work and evaluate its results. In the DocAble example, the content representation lets a validator compare the original and revised documents. The validator fails the job if the revised document is missing any of the original extracted content. Together, these structures carry an engineering decision forward into later work. ## The Methodology Extends Beyond Software

<!-- point: the-problem-is-larger-than-software | Delegating work to agents raises the same engineering questions across domains, but the useful representations and credible evidence differ. -->

The same questions will arise wherever humans delegate work to agents. However, the useful representations and credible evidence will differ by domain. Software engineering has architectures, dependency graphs, and tests. Mechanical engineering has geometry, tolerances, simulations, and physical tests. Accounting has ledgers, reconciliations, and audit evidence.

The balance between delegation, explicit representation, and enforcement will change as agents improve. MAGE does not prescribe that balance in advance. It asks engineers to decide which requirements to represent and enforce, and which choices to leave open as degrees of freedom for the agent.

This book develops MAGE through software engineering, drawing on the DocAble case study. {{chapter:modeling}} asks how to represent the knowledge needed for engineering decisions. {{chapter:alignment}} asks how selected obligations can govern the work. {{chapter:theory}} develops the theory and examines its scope and limits. {{chapter:profession}} considers its implications beyond software.

[^1]: Or at least, correctly enough that we can finish the job economically. Human code review and cleanup, or a final pass with a more capable but more expensive model, may supply what the initial agent leaves undone. The relevant cost is that of the whole process, including finding and fixing mistakes; the result must still meet its requirements.
