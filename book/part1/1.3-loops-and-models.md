# Loops and Models

<!-- point: two-ideas-loop-and-model | Two ideas carry the book: the loop and the model. | terms: loop-engineering, model-as-map -->
Two ideas carry the rest of this book, and everything else is a consequence of them.
The first is that all agent work is a *loop*. The second is that an agent steers that
loop well only when you hand it a *model* of the world it is working in. Model-Based
Agentic Software Engineering means engineering that
loop and handing the agent that model, deliberately, every time. Get these two
right and the agent finds your answer fast. Get them wrong, it wanders.

## Everything is a loop

<!-- section-terms: loop-engineering, success-metric -->

<!-- point: agent-work-is-a-fixed-shape-loop | Agent work is a loop of fixed shape. | terms: loop-engineering -->
<!-- index-def: loop-engineering -->
An agent runs in a loop, and the loop has a fixed
shape. It takes an input: the current problem, plus some notion of what success looks
like. It reasons, and it acts in its operating environment. It produces a result. And
that result folds back into the input for the next turn. Input, reasoning, output,
fed around again — each step an input carried to an output by a checkable transformation, a lens Part 4 returns to. Shaping that loop is **commonly called loop engineering**, and
nearly everything in this book is an instance of it. The close of this chapter draws
the loop with the engineer's control points marked ([ref:the-loop]).

Real engineering runs that loop many times over before the work is done. Stripe built a
benchmark around *complete* integrations rather than function-level tasks because real
engineering is long-horizon and stateful — planning, persistent state, and recovery from
failure — with the best-performing runs averaging about 63 turns [cite:stripe2026integrations].

> *A footnote on the loop in the wild.* Elastic's Control Plane team wired a Claude agent
> into monorepo CI so a failing dependency-update PR feeds its build/test logs back to the
> agent, which iterates over failed Gradle steps until green — "self-correcting" PRs. In a
> one-month pilot over 45% of dependencies; human review stayed mandatory and auto-merge was
> disabled when the agent contributed [cite:elastic2026ci].

The loop that *produces* has its own shape, drawn in [ref:printer-loop].

<!-- point: loop-starts-with-a-measurable-metric | Engineering a loop starts with a measurable metric. | terms: success-metric, rubric -->
<!-- index-def: success-metric -->
Engineering a loop well starts with the metric, because the metric is what the agent
steers by. The agent does not magically know your goals or your environment. You have
to make its progress *measurable* — deterministically, through a quantitative check,
or through a rubric that scores a qualitative result. Skip this, and you have told the
agent nothing about what "done" means, so it searches, and searches, and searches, and
never knows when to stop.

<!-- point: orchestrator-is-a-worked-loop-written-as-a-model | The orchestrator is a worked loop written as a model. | terms: loop-engineering, agent-orchestration-model, lifecycle -->
<!-- index-example: loop-engineering -->
The orchestration layer of this book's companion repository is itself a worked example
of a loop engineered this way. The catalogue models the orchestrator — the process
that dispatches agents, waits for them to land work, and cleans up after them — as an
explicit reactive loop with a typed lifecycle: *dispatch → work → land → tombstone*,
then refill and go again. The loop is written down as a model the agent can read —
which is the second idea.

> Learn more about this governance mechanism: [orchestrator model](appendix-b-agent-orchestration-model.html).

## Give it a model of the world

<!-- section-terms: model-as-map, probabilistic-reasoning-machine -->

<!-- point: vibe-coding-io-device-vs-engineering-system | Vibe coding sees an I/O device; engineering, a system. | terms: vibe-coding-vs-engineering -->
> Vibe coding treats the program as an I/O device; engineering treats it as a system.

<!-- point: io-vs-system-is-what-counts-as-proof | The split is what counts as proof a change works. | terms: vibe-coding-vs-engineering, invariant -->
The difference is not aesthetic. It is what counts as proof that a change is good. Treat the
program as an I/O device and the only question is whether the right thing came out this time.
Treat it as a system and you ask what must stay true across every input, and you build the
structure that holds the answer. Agents make both modes cheap, which is why you have to choose
deliberately. The fast, seductive default is the I/O device, and the I/O device is what turns
a hundred thousand lines into a mess nobody can reason over.

<!-- point: model-of-the-world-is-the-input-agent-reasons-over | The world-model is the input the agent reasons over. | terms: model-as-map, engineering-environment -->
The second piece is the input the agent reasons *over*. You have to give it a sense of
the environment: when it pulls this lever, what happens, and what is it even allowed to
do? That sense of the world is itself an input, and the more of it you articulate, the
better the agent knows what kind of reasoning the situation calls for.

<!-- point: model-is-a-probabilistic-reasoning-machine | A foundation model is a probabilistic reasoning machine. | terms: probabilistic-reasoning-machine, foundation-model -->
<!-- index-def: probabilistic-reasoning-machine -->
Why does this work at all? It is easy to feel you are
writing documentation into a void. But a foundation model is, loosely, a probabilistic
reasoning machine. *Probabilistic* means it does not always do exactly what you want.
*Reasoning machine* means it performs useful multi-step operations over abstractions — the
interpretability work probing these
networks keeps turning up real internal structure, and even lets us steer it. [The Agent
Stack](3.1-the-agent-stack.html) makes that case in full. So write the model down:
the agent reads it, and it reasons over it.

<!-- point: agent-behavior-is-a-search-over-a-vast-space | Agent behavior is a search over a vast space. | terms: search-space -->
<!-- index-def: search-space -->
Think of the agent's behavior as a search. It is searching an enormous
space: every place the answer might live, every configuration it might try, every
function that might implement what you asked. That is a big set, right? Far too large to
sweep. So where do you even look?

<!-- point: structuring-loop-and-model-conditions-the-distribution | Loop and model condition the agent's probability distribution. | terms: conditioning-the-search, search-space -->
So when you structure the loop and hand over a model, what you are really doing is
**conditioning the probability distribution of the agent's behavior** — biasing it to
search where the answer actually is. Done well, this takes the agent from failing your
task to completing it. And when it was already completing the task, it now does so in
fewer tokens and less time — materially fewer, in my experience — so you get back to
the interesting parts of your job.

<!-- point: a-model-aims-the-search-and-shrinks-what-is-held | A model aims the search and shrinks what is held. | terms: search-space, context-window -->
A model earns its keep twice over here. It aims the search, and it shrinks what the
agent has to hold — which is what keeps the work from spilling the window and churning.
The case study measures that churn directly: it peaks as the environment is built, then
falls as the built environment holds. [data: churn]

<!-- point: the-printers-seam-is-determinism-vs-probability | The printer metaphor breaks at determinism versus probability. | terms: printer-metaphor, conditioning-the-search -->
> **The metaphor's seam.** Lakoff and Johnson, in *Metaphors We Live By* (1980), show that
> a structural metaphor illuminates where its source and target align and misleads where they
> break, so naming the break is part of honest use. Here is ours: a real 3D printer is
> deterministic — the same G-code yields the same part, every run. This printer is
> probabilistic — the same prompt can yield different output. That is exactly the gap the
> chapter turns on. Because the agent is a probabilistic search and not a deterministic
> extruder, we condition its distribution rather than instruct it. The metaphor claims
> "you get only what you describe"; it does not claim "you get the identical thing twice."

## The four levers of an engineered loop

<!-- noqa: book-section-cap | The four levers of an engineered loop — the word count includes the inlined loop figure's accessible description and lever labels; the prose itself is four short paragraphs and a definition inset around one figure -->

<!-- section-terms: engineered-agent-loop, loop-engineering, success-metric -->

<!-- point: loop-and-model-meet-in-four-engineered-levers | Loop and model meet in four engineered levers. | terms: engineered-agent-loop, loop-engineering -->
Now put the two ideas back together, because they are one machine. A loop alone is
generic; a thermostat runs one. What makes agent work engineerable is that the
environment owns the loop's control points, and you set every one of them.

<!-- index-def: engineered-agent-loop -->
> **Engineered agent loop.** A feedback process in which the environment supplies a
> modeled state, constrains available actions, measures progress against an explicit
> criterion, and determines whether the result may advance.

<!-- point: four-levers-state-actions-criterion-admission | Four levers: state, action surface, criterion, admission. | terms: engineered-agent-loop, success-metric, model-as-map -->
Read the definition as a list of levers, because that is what it is. [ref:the-loop]
draws them at their stations.

- **The state exposed.** What the agent sees is not the world; it is the state you
  supply — and this chapter just argued it should be a *model*.
- **The action surface.** The tools and sanctioned seams the environment offers, so the
  wrong move is simply unavailable.
- **The success criterion.** The metric or rubric you made measurable above.
- **The admission rule.** Whether the result advances is not the agent's call; it is the
  gate its output must pass before the work feeds the next turn.

<!-- label: the-loop -->
<!-- figure: assets/loop-engineering.svg | *The Four Levers.* The engineered agent loop, its control points numbered where the engineer sets them. Read the geometry: three levers govern the path the output travels — the action surface, the success criterion, the admission rule — while one governs what the agent sees going in, the state exposed. That asymmetry is the two theses in miniature. -->

<!-- point: levers-divide-between-the-two-theses | The levers divide between the book's two theses. | terms: engineered-agent-loop, thesis-modeling, thesis-alignment -->
The four levers are the book's two theses in miniature. The first — a modeled state — is
the Modeling Thesis: bind intent and structure into an explicit model, and the agent
reasons through it while the engineer specifies, analyzes, and predicts on it. The other
three — constrained actions, an explicit criterion, an admission rule — are the Alignment
Thesis: mechanisms the environment enforces, holding the output to intent. Part 3 builds
the second set; Part 2 builds the first.

<!-- point: levers-treat-churns-three-not-knowings | The levers treat churn's three not-knowing causes. | terms: engineered-agent-loop, churn -->
The preface named churn as the wall a fleet hits and traced it to three not-knowings.
The levers are where those causes get treated. Not knowing *what to build* and not
knowing *how to realize it* are failures of the exposed state; the modeled state answers
both. Not knowing *how to change the system safely* is a failure of the other three
levers — an unconstrained action, an unmeasured criterion, an ungated admission. Modeling
treats the first two not-knowings,
alignment the third. Both are asserted here, not yet
earned. The next chapter earns them — from the machine itself.
