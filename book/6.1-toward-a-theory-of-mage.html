6.1 Toward a Theory of MAGE

The book has argued from one case, seen in depth. A theory is what lets that case speak past itself: it names the constructs, draws the mechanisms between them, and states what evidence would make the account fail.

The theory offered here is middle-range. It does not claim that every software project will behave like the one this book studied, and it assigns no universal coefficients to the relations it draws — a single system cannot support them. What it offers is a dynamic model of a specific phenomenon: how a fleet of coding agents turns abundant implementation capacity into durable engineering progress, or into churn. Read the whole chapter with that scope in mind; I will not restate it under each claim.

The central claim is not that agentic velocity is inherently productive. Velocity amplifies the fit between the fleet and the engineering environment it runs in. When that environment is incomplete, incoherent, or too weak to hold the work, velocity produces churn, escaped defects, repeated intervention, and governance friction. Those signals create pressure to adapt the environment. Engineers and engineering organizations respond by modeling missing structure, converting recurring failures into durable mechanisms, and reconciling or retiring governance that has grown excessive. When the adaptation works, later agents inherit a more legible action space, and a greater share of raw velocity becomes durable progress.

Theory of MAGE (informal)

Agentic velocity does not create engineering progress. It amplifies whatever governed engineering environment surrounds it.

6.1.1 The dynamic model

Figure 6.1-1 draws the whole theory on one diagram: a single set of constructs rather than four separate pictures, because the four dynamics act on the same system. The figure is a dynamic causal model: one set of constructs joined by the causal paths the four dynamics run over, read as a system rather than as four separate pictures. It borrows the loop-reading convention of system dynamics 11. Donella H. Meadows, Thinking in Systems: A Primer (Chelsea Green Publishing, 2008). without claiming full causal-loop notation — the links carry verbs, not signed polarities. A compact two-loop sketch of the same theory comes later in this chapter (Figure 6.1-6); here it is the full causal model, every construct and path drawn.

The spine runs left to right. Agentic capacity — model capability, concurrency, raw implementation rate — exercises a governed environment whose effective quality the model calls E. That environment shapes agentic work into realized performance — a vector of three measures that move in different desirable directions: durable throughput (higher is better), defect escape (lower is better), and the human attention each unit of durable output costs (lower is better). Because the three move in different directions, the arrow from E into performance has no single sign; it improves the vector, dimension by dimension. The gap between the performance the fleet looks capable of and the durable performance it delivers registers as governance pressure. Pressure meets structural diagnosis — the judgment that reads a signal as a local defect or as evidence of missing structure. Diagnosis drives governance adaptation, which changes E. The changed environment reopens the loop.

Four numbered dynamics run over that spine, and each has a color and a number so the figure survives in grayscale:

  • Blue — the bootstrap path. Prior engineering knowledge seeds the initial environment before any agent runs.
  • Red — the churn/discovery path. Work outruns the environment; churn and failure make the missing governance visible.
  • Green — the governance-adaptation path. A structural diagnosis reshapes the environment for the next agent.
  • Purple — the capability-amplification loop. A stronger environment raises deployed agentic capacity — feasible task size, concurrency, ambition — which pushes the work onto an ungoverned frontier. It does not raise the foundation model's intrinsic capability.

Follow the red path first. It carries the experienced driver of the whole system — the pressure an engineer actually feels — and the other three are best read as answers to it: blue lowers the pressure before it starts, green relieves it once it appears, and purple explains why it never stays relieved.

The four dynamics are not all the same kind, and naming their types sharpens why the system does not settle. Three are feedback loops; bootstrap is the input that sets the initial condition. The red and green paths compose into a balancing loop — churn drives diagnosis, diagnosis drives adaptation, and adaptation reduces churn: a goal-seeking cycle that drives the environment toward fit. Loop [4] is a reinforcing loop — a better environment raises ambition, and greater ambition reopens the frontier: a self-amplifying cycle that keeps moving the target. The balancing loop settles the environment toward fit; the reinforcing loop moves the target the moment it is reached. That pairing — balance toward fit, then reinforce to reopen the frontier — is why MAGE does not converge while capability grows or ambition expands.

6.1.2 The four dynamics

Each dynamic gets its own section below, and each opens with a simplified diagram of just its local causal path. The master figure above already established that the four are one system, so each section shows only the fragment it explains.

The blue path: bootstrap governance

Not all governance is discovered through failure; the blue path, in Figure 6.1-2, seeds the environment before any agent runs.

A project begins with knowledge it inherited and knowledge it can anticipate. A brownfield system already carries architecture, tests, deployment controls, operational history, and institutional obligations. A greenfield project starts with less local evidence, but a skilled engineer can still seed it from prior experience, external standards, known security and reliability practices, and lessons transferred from earlier systems.

Bootstrap governance encodes that ex-ante knowledge into the initial governed environment: a known obligation or a prior lesson becomes a model, a mechanism, or a constrained architecture, and the sum of them sets the environment's starting quality. This is why disciplined organizations and experienced engineers need not rediscover every failure from scratch. A governance conversion in one project — the specific failure-class-to-mechanism move — leaves a durable artifact that becomes bootstrap knowledge in the next; bootstrap reuses that artifact, but bootstrapping is not itself a conversion.

Bootstrap governance is never complete. The environment a product needs depends on the product, its trajectory, and the agents acting on it, and none of that is fully knowable in advance. The blue path lowers the initial failure rate. It does not close the red loop.

The red path: churn makes missing governance visible

The red path, in Figure 6.1-3, is where work outruns a weak environment and the gap surfaces as pressure.

Agentic velocity is not the immediate motive for governance investment. The motive is the experienced gap between what the fleet appears capable of producing and what becomes durable progress. When the environment is weak, raw implementation capacity produces repeated rediscovery, regressions and reversals, escaped defects, recurring human intervention, control friction, and confidently wrong changes that consume tokens without advancing the system. Governance pressure has several forms — churn, escaped defects, repeated intervention, control friction; in the DocAble case, churn dominated, and the book uses churn as the running name for the class.

Velocity earns its place in the model as an amplifier. It clusters latent weakness in time: failure classes that might have arrived months apart under human-paced work land in a single afternoon, and their proximity makes the structure they share visible. Governance pressure is what the operator feels when that happens.

Pressure is not yet knowledge. The next act is judgment. Structural diagnosis distinguishes a local defect from a structural failure class. A local defect gets repaired and the matter ends. In practice the fork is not always binary: a local repair often ships immediately while the structural question stays open, a failure class can remain uncertain, one incident can implicate several structures, and the cost of a mechanism can outweigh the recurrence risk it would retire. The clean fork is the teaching model; the judgment it names is the scarce work of the whole method either way. A structural failure reveals a weak or absent model, abstraction, boundary, invariant, oracle, mechanism, or governance seam — something whose absence will keep producing failures until it is supplied. The red path is where that diagnosis is demanded.

The green path: governance adaptation

The MAGE adaptation cycle

Velocity surfaces churn; churn is diagnosed as missing structure; the structure is converted into a durable mechanism; the improved environment turns more velocity into durable progress — which raises ambition until it finds the next gap, and the cycle runs again.

A structural diagnosis triggers governance adaptation, the green path of Figure 6.1-4.

The core move here is governance conversion: turn a recurring failure class into a durable mechanism the environment enforces on every later agent. Mature adaptation keeps that move and adds four more around it:

  • Represent — make missing intent or structure legible, so agents reason over the right representation.
  • Convert — turn a recurring failure into a durable mechanism.
  • Strengthen — replace weak probabilistic guidance with harder enforcement where the obligation justifies it.
  • Reconcile — resolve controls that duplicate, conflict, or fire in the wrong order.
  • Retire — remove governance that has gone stale or become net-harmful.

The output is not merely more controls. It is a change in the shape of future work. Later agents inherit a more compact representation, clearer constraints, fewer invalid moves, earlier evidence, narrower sanctioned seams, and more reliable admission conditions. That inheritance is the immediate mechanism by which the environment's quality changes — and it is why adaptation can be subtractive as well as additive: reconciling a control collision or retiring a stale gate raises quality without adding a thing.

The quality that adaptation moves needs a definition sharp enough to keep apparatus quantity from standing in for it.

Effective governed-environment quality, E. The degree to which the environment gives agents a current, task-relevant representation of the system, together with coherent, proportionate, machine-actionable coverage of its important obligations.

That quality has four parts, set out in Table 6.1-1; each asks a question the raw apparatus count cannot answer.

Table 6.1-1. The four dimensions of E. Effective governed-environment quality has four parts; each asks a question the raw apparatus count cannot answer.
DimensionThe question it asks
Representation qualityAre the relevant properties legible in the environment's current models?
Enforcement coverageAre important obligations covered by controls proportionate to their decidability and risk — hard mechanisms where they fit, judgment-based review where they do not?
CoherenceDo the mechanisms compose without harmful collision or duplication?
EconomyIs the governance burden proportionate to the risk and value it controls?

Coverage is not the same as hardness. Some obligations are deliberately judgment-based; a high-quality environment assigns hard mechanisms where the obligation is decidable and review where it is not, rather than over-hardening every clause.

Defined this way, E is a conceptual state vector, not a measured scalar. Write it E = (R, C, H, Q) over its four dimensions — representation quality, enforcement coverage, coherence, and economy — which need not collapse into one ordered index the case could report. A large support apparatus raises a dimension of E only if it is coherent, economical, and actually covers the obligations that matter; the same apparatus can instead be duplicated machinery, stale enforcement, or a tower of governance that lowers E while the control count climbs. "Higher effective quality" stays a useful informal shorthand; the equation below does not imply the case supplied a one-dimensional metric.

The purple loop: capability amplification

Successful governance does not end the process; the purple loop of Figure 6.1-5 reopens it.

It expands what the engineer attempts. A stronger environment makes larger delegated tasks feasible, supports greater concurrency, invites more ambitious product requirements, cheapens refactoring, and lets the operator run agentic capacity denser. Every one of those pushes the work into surface the environment has not yet governed, and the expanded frontier exposes new weaknesses. The loop feeds back into deployed agentic capacity — the frontier the operator dares attempt — not the model's inherent ability; a richer environment lets the same model be pointed at larger, denser, more ambitious work.

This is capability amplification, and it is why MAGE does not terminate. The environment can reach a stable operating equilibrium — product ambition settles, the system enters maintenance, agent capacity stops changing, risks are well understood; MAGE fails to converge only while one of those keeps moving. The environment never converges on a final set of controls, because the product, the fleet, and the task frontier keep changing underneath it — and each gain in governance raises the ambition that finds the next gap. The loop also answers a natural objection: that better agents will eventually remove the need for governance. They do the opposite. A more capable fleet raises attainable velocity and ambition, which raises the consequences of a weak model or a missing control. The frontier moves out with the capability, and governance follows it.

6.1.3 Constructs and path-specific moderators

The two conditions the book leaned on — diagnostic capability-fit and authority — are not global switches over the whole model. Each acts on one specific transition, and stating where sharpens what each one predicts. Table 6.1-2 places every construct and moderator on the transition it governs.

Table 6.1-2. Constructs and moderators. Each construct's role in the dynamic model and the transition it operates on — diagnostic capability-fit and authority attach to specific steps, not the whole model.
Construct or moderatorRole in the modelOperates on
Agentic capacityModel capability, concurrency, raw implementation rateInput to agentic work

Diagnostic capability-fit sits on the pressure-to-diagnosis step. The deciding capability here is the human or organizational capacity to read a signal as structural, not the fleet's implementation capability — do not read it as the model/task fit of Part 4. A capable fleet given to someone who cannot tell a local defect from a structural one produces motion without direction; the pressure arrives, but no diagnosis converts it. Authority sits one step later, on diagnosis-to-adaptation. The person who reads the recurring failure has to be able to change the environment — the architecture, the mechanisms, the gates — or the diagnosis dies as a local patch and the class never dies with it.

Stated generally, H7 names the engineering preconditions for learning: a discipline improves only where diagnostic capability-fit and the authority to change the environment can reach each other.

Authority need not live in a single architect. In an organization it is a functioning path from an observed failure to shared infrastructure. Split ownership across teams, owners, and review boards is not fatal on its own. The failure comes when the path terminates in a local patch: the same signal that could have become a shared mechanism produces a private fix instead, and the class survives to recur under the next owner.

One moderator deserves more than a table row, because it sets the theory's reach. Domain governability is the degree to which a domain's important properties can be represented and mechanically checked at all. Some properties are precisely specifiable and checkable — a schema conforms, an invariant holds, an output validates. Others are aesthetic, political, ambiguous, or socially negotiated, and no mechanism settles them. Where governability is low, E has less to grip, and more of the work stays in human judgment. The authorship boundary the closing Part draws is one instance of this moderator, not a separate law.

The levels are worth keeping distinct: raw apparatus quantity and structure, then control-estate coherence acting on it, then the effective quality E that results, then the outcomes E drives. Coherence names a dimension of the resulting E; control-estate coherence names the apparatus property that produces it.

6.1.4 A capability model, not a maturity model

MAGE is a capability model, not a maturity ladder, and the distinction matters because the field has been here before. For two decades the dominant frame for engineering quality was the staged maturity model — the CMM and its CMMI successor — which ranked an organization on a five-rung ladder and told it to climb. The narrower and defensible objection: MAGE is not a universal staged ladder — the bottleneck in front of a project selects its next investment, not a rung above it 22. Terry B. Bollinger and Clement L. McGowan, “A Critical Look at Software Capability Evaluations,” IEEE Software 8, no. 4 (1991): 25–41, https://doi.org/10.1109/52.300034.. (A single pre-CMMI citation cannot carry a full historical verdict on maturity models, and none is attempted here.)

"Capability model" here means a non-staged repertoire of abilities selected by need — not a capability map in the enterprise-architecture sense (an inventory of what an organization can do). The contrast is with staged progression, not with capability-mapping.

The dynamic model gives the alternative directly. A project's current bottleneck selects the next modeling or governance capability it needs; the bottleneck in front of you picks the next control, and no rung waits above it. When escapes climb, you reach for the artifact-side controls. When agents churn against a surface they cannot hold, you invest in the models. When recovery keeps pulling a human back in, you harden the fleet's substrate. Dependencies may impose a local adoption order — some controls presume others — but that order is a dependency, not a rank, and no universal sequence ranks every organization. The reason there are no levels is the reason there are no fitted coefficients: a single case cannot validate a progression that means the same thing everywhere. Different projects enter with different bootstrap environments and feel different pressures, so what replaces "what level am I" is a plainer question — which capabilities do you have, and what does each one buy against the bottleneck you actually face.

6.1.5 Outcomes and observables

The model earns its keep only if its outcomes can be watched. Three of them carry the theory, and they are the three dimensions the productivity literature already names — velocity, quality, and sustainability — read for a fleet rather than a team. Table 6.1-3 states each and the observables that would track it.

Table 6.1-3. The Outcomes. The three primary outcomes the theory predicts, the way to state each so it reads as durable progress rather than raw activity, and the observables that would track it.
OutcomeWhat it measuresExample observables
Durable throughputRaw implementation converted into lasting system progresslanded changes net of rework; churn share; the slope of sustained throughput
Defect escapeRelevant failures reaching later lifecycle stages or productionescaped-defect rate; reopen rate; silent-corruption escape
Human-attention burdenHuman judgment required per unit of durable outputinterventions per landed change; review time; conversion effort

The distinction between activity and outcome is already visible in industry data. LinearB's 2026 benchmark — 83,000 developers across 253 organizations 33. LinearB, “The Engineering Productivity Gap: How Elite AI Teams Are Pulling Away from the Rest,” LinearB, 2026, https://linearb.io/resources/ai-engineering-productivity-gap. — reports large gains in merge rate among heavy AI users, then shows why merge rate alone misleads: among the developers with the highest AI use, yield fell even as merge rates roughly doubled. LinearB ties AI cost to delivered work through PR yield and rework, rather than counting generated code or opened pull requests as value in themselves. Practitioners report the same gap from inside their own organizations. DX deputy CTO Justin Reock told The New Stack that rising AI spend has not produced proportionate shipping velocity, and, more sharply, that the trouble has moved from comprehension to confidence: "We can understand the code … and make changes to it more easily. But we trust less what we're releasing." 44. Jennifer Riggins, “AI Coding Got Faster. Why Didn't Engineering?,” The New Stack, August 9, 2026, https://thenewstack.io/ai-productivity-measurement-gap/. The measurement problem is not whether AI increases activity. It is whether that activity survives review, rework, integration, and operation as durable engineering progress.

MAGE names its outcomes to catch exactly this. Gross implementation velocity is an input, not a result. Durable throughput is the output. Defect escape records what apparent velocity concealed, and human-attention burden records the scarce judgment the surrounding system still consumes. The environment is improving only when these downstream outcomes move, not when the fleet merely produces more artifacts.

State human-attention burden as a rate, not a ceiling. The theory predicts amortization: as recurring failure classes convert into durable governance, the attention required per landed change falls, even if total governance work continues to grow. Per-change attention declines; the aggregate need not.

These observables are directional targets, not turnkey metrics. Each needs instrumentation the theory does not supply: what counts as rework, over what time window, how to separate corrective churn from productive refactoring, how to risk-weight escaped defects, and how to value a unit of human attention. The theory names what to watch and which way it should move; operationalizing each is itself research.

A second discipline governs how the environment itself is read. The quantities easiest to count — the support ratio, the model-coverage fraction, the control count, the gate count, the model-sync rate, the control-interaction findings, the stale-control rate — measure investment or accumulation. They do not measure whether the environment is any good.

A large support apparatus can be effective governance. It can also be duplicated machinery, accidental complexity, stale enforcement, a tower of governance, or an internally conflicting control estate. The number cannot tell you which. A high support ratio gains meaning only when it is joined to an outcome — when the apparatus that leads production is shown to sustain throughput or drive escape down. Treat every apparatus measure as an input or an indicator. Effective governed-environment quality is what the outcomes reveal, and the apparatus is only its raw material.

6.1.6 Principal predictions

Here is where the model sticks its neck out. The dynamic model yields eight principal hypotheses. Each names a mechanism and the single observation that would sink it. Core causal propositions appear here; derivative consequences and domain-specific instances follow as corollaries and specializations.

None of the eight receives an independent, population-level test from this case — one repository cannot test a claim about a population. But the case is not disconnected from them: it supplies the observations from which several were induced, and offers within-case consistency evidence. Every row is stated so a larger study can confirm or falsify it, as a directional, conditional claim — the shape it should take, and the conditions under which it should hold — not a measured law. These are not rhetorical hypotheses. They are the empirical program the theory implies — if the field wishes to falsify MAGE, these are the experiments to run. Table 6.1-4 lists the eight with the observation that would falsify each.

Two of them carry conditions worth stating in the open. H3 does not claim hard controls never fail; it claims that a correctly encoded, adequately scoped mechanism is less sensitive to throughput than finite review, so the gap between them opens as the fleet speeds up. H3 treats determinism as one strong class of repeatable mechanism, not the whole category — anomaly detection, metamorphic and differential testing, and model-based semantic review are statistical yet repeatable, and count toward κ when adequately scoped. H6 does not promise the total oversight bill stops growing; it claims the per-change share falls as classes convert. Strip those conditions and both claims overreach; stated with them, each says only what the evidence can bear.

Corollaries and specializations

Several claims read more precisely as consequences or domain instances of the eight than as coequal predictions — a statement of where each sits in the causal structure, not a demotion of its truth. Speed and stability not trading is a corollary of H2 and H3 together (the claim Accelerate made famous now falls out of the pair rather than standing alone). Faster conversion as tooling matures is a learning-curve specialization of H7; a self-healing substrate follows from H3 and H6. Two claims are one product's surface read through the theory: grammar coverage better predicting format-space escapes is a domain instance of H4, and a fidelity gate killing silent corruption a product-specific instance of H3.

The reasoning-horizon proposition

H4 is the falsifiable form of a wider claim the book has built toward since Part 1. Stated plainly:

The Reasoning-Horizon Proposition. Software engineering is a long-horizon reasoning task. Productivity degrades once the working reasoning state a task requires exceeds the effective reasoning horizon of the human-agent system. Executable models extend that horizon by replacing implementation-level state with semantically richer abstractions that preserve a larger fraction of task-relevant information under repeated compaction.

The horizon extends only when the model is task-relevant, adequately complete, synchronized, usable by the agent, and cheaper to interpret than reconstructing the same facts from code. A model that fails those conditions shortens the effective horizon — it confidently routes reasoning toward a stale or wrong picture, and the agent pays to detect and undo the misdirection.

The proposition and H4 divide the labor. The proposition names the mechanism: a finite reasoning horizon, and a model that extends it by serving as a better compression domain, a higher-semantic-level object whose compaction discards the implementation detail that never mattered. H4 states the test — the efficiency gain, and its widening as the required reasoning state grows. One is the claim about how reasoning scales; the other is the observation that would sink it.

Read the reach carefully. A context window is one instance of a finite reasoning horizon, not the horizon itself. The mechanism does not depend on today's token buffer, so the claim should hold under longer windows and new memory architectures. That last step is an analytic generalization from a single case, not a measured law about future systems. Hold it at the register of the eight hypotheses: offered for replication, not proven.

The proposition draws its own boundary:

MAGE moves the scalability wall; it does not remove it. Models raise the level at which reasoning occurs and delay the point at which working memory becomes the bottleneck. Beyond that point, further decomposition and modularity become unavoidable.

The bound composes with two claims already on the table. It is the mechanism under H4's representation leverage. It also sharpens H5: an unmodelled surface is one the fleet must hold in raw implementation state, at a shorter effective horizon, where churn returns. The capability-amplification loop then keeps the wall in motion, because a stronger environment raises ambition, and ambition finds the next surface the horizon cannot yet reach.

The compounding-governance proposition

A second wide claim runs parallel to the first, and H6 is its falsifiable form. Stated plainly:

The Compounding-Governance Proposition. Governed engineering environments compound: as recurring engineering judgment converts into durable mechanisms, an increasing fraction of future effort over the failure classes those mechanisms cover can extend capability rather than re-solve settled problems, so the environment grows more capable of supporting safe change — for as long as the accumulated engineering capital stays fit. These are returns to accumulated engineering capital over covered classes, not global returns to total governance expenditure.

This is the positive dual of the churn the book opened with. Churn is the regime in which effort dissipates; compounding is the regime in which effort accrues as engineering capital — the stock a conversion banks. The proposition and H6 divide the labor the same way the reasoning-horizon proposition and H4 do. The proposition names the mechanism: judgment spent once, encoded into a mechanism, lowers the recurring reasoning every later change demands. H6 supplies one testable signature — human attention per unit of durable output falls as classes convert. The dynamic is the composition of two loops the model already draws: the green governance-adaptation loop turns failure into a more capable environment, and the purple capability-amplification loop turns that capability into more ambitious work. Compounding does not mean the fleet does less; it means higher-leverage work at a falling per-change cost. This is the economic justification for governance: as classes convert, human attention per unit of durable output falls, so the apparatus pays for itself in reclaimed judgment rather than merely catching defects.

The proposition draws its boundary, and states it plainly:

The returns are increasing, not unbounded, and they attach to engineering capital — coherent, quality-bearing governance — not to apparatus quantity. Accumulation stops compounding two ways: apparatus pushed past the point of fit, and capital that has outlived its fit. Both rejoin the churn curve's rising right band.

A third failure hides inside the first two: accumulated capital that has drifted from the system it models does not merely stop paying — it confidently misdirects, steering later work against a picture no longer true, which is worse than no capital at all.

That boundary is why the churn curve is non-monotonic rather than a story of ever-more-governance, and why mature adaptation retires and reconciles as well as adds — the subject of the next section.

Learning propagation

H8 completes a chain the first seven leave open. H1 says velocity exposes a lesson faster. H7 says authority decides whether the lesson can change the environment. H8 asks what happens next: once a lesson is encoded into a shared, machine-actionable environment, how fast and how reliably does it reach the work that comes after. Read the three together and they name the organizational-learning pipeline end to end: discover faster, convert effectively, propagate automatically.

The lesson need not come from a failure. A better architecture, a newly proven invariant, an improved workflow, a regulatory reading, a new model, a technique one team worked out — each is engineering knowledge, and each propagates the same way once it becomes a model, a constraint, a validator, a skill, a gate, or a governance rule. Future agents inherit it without every engineer first having to learn it.

This proposition connects MAGE to the literature on organizational learning and the learning organization. Senge argues that durable organizational capability depends on systems thinking, shared representations, and mechanisms by which local learning becomes collective learning. MAGE proposes an agentic-engineering specialization of that idea: when engineering knowledge is externalized into machine-actionable models and governance mechanisms, organizational learning can propagate not only through people but through the environment inherited by subsequent work.

The claim is not that MAGE replaces human organizational learning. Judgment still originates with people. The governed engineering environment provides an additional transmission medium through which selected judgments become durable and automatically reusable.

Argyris and Schön 55. Chris Argyris and Donald A. Schön, Organizational Learning: A Theory of Action Perspective (Addison-Wesley, 1978). draw the distinction that maps most closely. Single-loop learning fixes the immediate defect while preserving the governing assumptions; double-loop learning revises the rules and structures that produced it. MAGE's governance conversion is recognizably double-loop: a recurring failure is read structurally, and the environment is changed so later work operates under different rules. MAGE adds one twist their account does not need. The revised governing structure can be executable, so autonomous agents inherit it automatically rather than by being taught. That is the sharpened form engineering capital takes here — not merely accumulated tooling, but institutionalized engineering learning whose effects outlast the individual who learned the lesson.

The book's own making illustrates the mechanism; it does not test it. As the manuscript's governed environment grew richer, improvements to the argument propagated through models, figures, glossary, and tooling faster than memory alone would carry them, and the Colophon returns to this. A single artifact cannot test a claim about a population. H8 is offered, like the others, for external multi-case and longitudinal study. Shopify is its strongest present external instance: public agent sessions became harvestable corporate artifacts mined into skills, prompts, and defaults, and each next agent grew cheaper to stand up — add a bundle, not a platform. Experience became observable, and once observable it propagated to the work that came after.

6.1.7 Two directional relations

Two of the hypotheses have a form clean enough to write down. Neither is a fitted law. Each is a shape — a statement of which way a quantity moves and why, with the parameters named but not measured. Read them as the arithmetic behind the arrows, not as equations with coefficients this case supplied.

The churn relation

Durable throughput is raw velocity net of what churn eats:

V_durable = V_raw · (1 − c)

where V_raw is the raw agentic implementation rate and c is the share of that effort consumed by churn. The substantive claim is about what moves c.

That first relation is definitional, not theoretical — the substantive theory is entirely in what moves c. It carries content only when V_raw and c share one unit: if V_raw is an implementation rate and c is an effort share, state the common unit (commits, engineering effort, tokens, or value) explicitly, because dimensional consistency is not automatic.

As effective quality rises, more of the relevant surface fits the fleet's window before it churns, so along any one dimension-bundle of E

∂c / ∂E < 0 (read as a directional sign over one dimension of the E-vector, not a fitted slope)

churn share falls as effective quality climbs — and it keeps falling even in an overgrown estate, because overgrowth is precisely what lowers E. That is the arithmetic behind H2 and its subsystem sharpening in H5. The non-monotonic curve in the next figure is drawn against a different x-axis — governance apparatus quantity, not E — and the two must not be conflated: churn falls monotonically in E, but non-monotonically in apparatus quantity, because quantity does not monotonically raise E.

But the relation is not monotone across all governance accumulation, and the honesty of the theory turns on saying so. Push apparatus past the point of fit and churn starts to rise again — from collisions, false positives, latency, context burden, and constraints that block legitimate work. The qualitative shape has three bands, drawn in Figure 6.1-7: churn high in the under-governed region, lowest at fit, rising once more where the estate overgrows into a tower of governance.

under-governed → churn high · well-fit → churn lowest · overgrown → churn rises from friction

No exact curve is claimed. The point is the non-monotonicity: apparatus quantity is not the same thing as effective environment quality, and a theory that assumed more governance is always better would miss the entire right-hand band.

Attention-based versus mechanized control

The second relation contrasts two ways to hold a failure class. Let p be the risk-weighted rate of defect opportunity, r(V) the fraction a finite human review still catches at velocity V, and κ the risk-weighted fraction of relevant opportunities covered by effective mechanisms. Then the two escape rates are:

ε_review ≈ p · (1 − r(V)) and ε_control ≈ p · (1 − κ)

Human attention is finite, so r(V) falls as velocity rises — review catches a smaller share of a larger stream, and ε_review climbs toward the raw defect rate p. A correctly wired mechanism is invoked on every change without consuming human attention in proportion to throughput — provided invocation is guaranteed, its capacity scales, it does not time out, bypasses are closed, and the relevant class is covered. Under those conditions κ does not fall with velocity the way finite review does. The claim is not that hard controls never fail. It is conditional and comparative: for adequately scoped mechanisms, κ is less sensitive to throughput than review coverage r(V), so the daylight between "looked obeyed" and "was enforced" widens as the fleet speeds up. That is H3 in one line.

Read both as a toy comparison, not a model. They ignore defects the controls themselves introduce, mechanism false negatives, control degradation over time, correlated opportunities, review triage, and the combined use of review and control together. The notation earns only the directional claim — that κ is less throughput-sensitive than r(V) — and none of the authority a fitted equation would carry.

6.1.8 Does governance eventually become a burden?

The churn curve just showed that accumulation is non-monotonic: past the point of fit, more apparatus makes things worse. So name the positive dynamic the curve's left arm rides — and the line that separates it from the tower on the right.

Churn has a dual. Where churn is the regime in which effort dissipates, compounding is the regime in which effort accrues: each governance conversion banks engineering capital that lowers the future cost of change, so later work extends capability instead of re-solving what judgment already settled. Figure 6.1-8 sets the two side by side — the same environment, opposite signs.

The right arm of the curve forces a distinction between two kinds of accumulation, and the book has been naming its terms all along. Table 6.1-5 pairs each negative dynamic with the positive counterpart a well-fit environment produces.

That last pairing is conditional: repeated manual enforcement of a stable, decidable obligation becomes a reusable governance mechanism, but some judgment is deliberately left manual, and not every manual process should be mechanized.

The right column is not automatic. Accumulation earns it only when it stays capital, and the theory already carries the machinery that decides. Recall that E is a quality, not a quantity: the economy and coherence dimensions ask whether apparatus is proportionate and non-duplicative, and the apparatus-count caveat warns that control count is an indicator, not a substitute. Read through that lens, the right band of the churn curve is accumulation that failed to become capital.

Name the two sides. Bureaucracy is accumulation that raises the cost of change without reducing future reasoning: an extra checklist, an approval gate, a duplicated doc, a process re-applied by hand each time. It adds friction and buys nothing back. Engineering capital is accumulation that lowers the recurring judgment a change demands: a validator, a structured model, an architectural constraint, a reusable mechanism, a generated artifact. Capital compounds; bureaucracy does not. The heuristic falls out of the pair.

A heuristic for any governance decision. Does this increase churn, or increase engineering capital?

Stated for action rather than as a slogan: does the recurring reduction in future reasoning and risk justify the friction, maintenance, and context this mechanism adds? A mechanism can do both at once — add immediate friction and retire future risk, help one subsystem and burden another — so the decision is a weighing, not a sort into two bins.

There is a second way accumulation stops compounding, and it is easy to miss because the apparatus once earned its place. Capital depreciates. A validator written for a subsystem that has since been retired was capital and becomes friction as the product moves on; a constraint tuned to an architecture the fleet has outgrown now blocks legitimate work. So "does not compound" names two failures, not one: apparatus that never reduced future reasoning, and capital that has outlived its fit. This is exactly why mature adaptation is subtractive — the reconcile and retire moves are capital-depreciation management, not merely cleanup of bad apparatus. Compounding is real, and it is bounded; keeping accumulation on the capital side is the work the churn curve's right band exists to warn about.

6.1.9 Evolution of this theory

The theory did not arrive whole — its empirical core came first, induced from a bounded case; the rest is later reflection. What follows keeps the two apart: the induced kernel, the four extensions, and why they carry different epistemic weight.

The first version appeared in the case-study paper Cheap Code, Costly Judgment 66. James C. Davis et al., “Cheap Code, Costly Judgment: A Case Study on Governable Agentic Software Engineering,” 2026, https://arxiv.org/abs/2607.01087.. That paper analyzed the first twelve weeks of the DocAble build and induced a five-step governance-conversion loop:

  1. velocity exposes failure;
  2. the engineer classifies the failure as local or structural;
  3. structural failures are converted into governance;
  4. later agents inherit a narrower, more explicit action space;
  5. repeated conversions raise the environment's capacity to absorb future work.

That loop remains the empirical kernel. It contributes distinctions this chapter preserves: failure must be interpreted, not merely observed; governance works by reshaping subsequent action; conversion is recursive and does not terminate; capability-fit and authority condition whether a structural signal becomes shared infrastructure.

Continued development and roughly two further months of reflection extended the kernel in four ways.

  • Ex-ante governance became a first-class path. The paper emphasized the delta of ex-post governance — controls discovered from failures no one could fully anticipate. Later work sharpened the complement: a disciplined organization or skilled engineer bootstraps a project with inherited architecture, standards, tests, prior incidents, and lessons carried from earlier systems. Conversion in one project becomes ex-ante knowledge in the next. Bootstrap and conversion are two loops, not one.
  • Modeling became a coequal route to governability. The paper treated structured models as one governance mechanism among others. The Modeling Thesis gave them a distinct role. Models do not only constrain output; they compress intent and system structure into a representation the fleet reasons through, surface properties at the right semantic level, and support the drift gate that holds the map equal to the territory.
  • Governance accumulation proved non-monotonic. The paper saw a large, layered substrate and described repeated conversion as compounding governability, already noting the tendency was not strictly monotone. Continued work supplied the missing negative side: mechanisms collide, duplicate, consume context, and block legitimate change. Mature adaptation therefore includes reconciliation and retirement, not only accumulation.
  • The process became visibly multi-loop. The early theory centered one loop — failure, judgment, governance. The book revealed interacting loops: bootstrap establishes the initial environment, churn reveals what is missing, adaptation reshapes future work, and success expands ambition and concurrency onto a new frontier.

The result is still a governance-conversion theory at its core. It now describes MAGE as an adaptive system for governing the engineering environment itself.

Epistemic note. The induced kernel and its later extensions are epistemically different, and the chapter should not blur them. The five-step loop was induced from the bounded case and its incident corpus. The four extensions are grounded in continued development, further observation, and integration across the book. Read the kernel as the case's direct yield and the extensions as refinements proposed for later testing — not as independently confirmed, population-level laws.

6.1.10 Modeling feeds Alignment

The book has carried the two theses side by side, as if Modeling and Alignment were parallel pillars holding up one roof. They are not parallel. One feeds the other, and the comparative cases are what make the direction visible. Modeling makes intent explicit; Alignment makes it binding. In other words: first write down what matters in a form both people and machines can understand, then teach the engineering environment to insist on it. The order is not incidental — a model has to exist before anything can be enforced against it. Without a model, some obligations stay semantic: a reviewer, human or agent, judges them probabilistically over raw code. With the right model, the same obligation becomes a predicate a machine settles on every change. So the through-line of the whole method is a causal edge, not a symmetry — Modeling feeds Alignment — and the working form of that feed is the one the chapter has already stated: modeling expands what Alignment can determinize.

That reframes the Modeling Thesis. Its first job is the one Part 2 argued: a model compresses the system, so an agent reasons farther within a finite window. Its second job is the one the industry comparison forces into the open: a model exposes structure, so some reasoning can leave the agent entirely and move into a deterministic check. A model extends autonomous scale two ways at once — it compresses the system so an agent can work within a finite horizon, and it exposes structure so some reasoning can be removed from the agent and replaced by a mechanism. The first job serves comprehension. The second serves scale directly, and it is the one a book about comprehensibility alone would miss.

Make the second job concrete with one obligation. Say the architecture requires that no request reach the remediation service without passing quota authorization. Verify that against raw code and you are reasoning over hundreds of call sites, handlers, middleware, and injection paths; the honest answer is an LLM's probabilistic judgment. Now give the system an explicit process-and-dependency model in which every allowed route is a represented edge. The obligation collapses to a query — for every path from a request to the remediation service, the quota gate lies on the path — and a machine checks it cheaply on every change. The property did not get easier. The object the question is asked over changed, from an implementation to a model, and the change is what made the question decidable.

Read the two paths side by side and the autonomy consequence is plain. Without the model, an agent changes the system, a human or an LLM must reason globally about whether the obligation still holds, that review is expensive, and human attention becomes the bottleneck that caps the fleet. With the model, the agent changes the system, the environment evaluates the invariant, the result is pass or fail, and no per-change human reasoning stands between the change and the merge. The model turns a long-horizon reasoning problem into a short deterministic query, and that substitution is what raises the ceiling on how much autonomy is safe to grant.

Another engineering discipline shows the endpoint. Siemens does not reason about a physical structure by arguing over the object; it builds a finite-element model — a deliberately restricted representation — and runs a deterministic solver over it. The restriction is the point: constraining the model to a form a solver can operate on is exactly what makes the computation possible. Software can do the same thing. An executable model of a system's state is our finite-element model, and a predicate over it is our solver run. The comparison is not decoration; it shows the far end of the frontier already reached in a field that crossed it decades ago.

The printer metaphor gains a layer here. Through most of the book the model is the blueprint the printer reads — the description the machine builds from. This refinement adds the rest of the shop floor. The model is also the fixture that holds the work in place, the jig that guides the cut, the template the part is checked against, and the gauge that says pass or fail. A blueprint tells the machine what to make. A fixture, a jig, a template, and a gauge are what make automated production safe enough to run without a person watching each part. That is the plainest way to say what the second job of modeling buys: not a better drawing, but the tooling that lets the line run fast without losing trust in what comes off it.

One consequence follows, and it ties this section back to the churn the chapter opened with. A structured model left un-enforced is only advice: the fleet may reason through it and still drift away from it, and a drifted model is worse than none, because it confidently misdirects. Structured models without Alignment dissipate — the effort that built them drains back into churn. Bind them, and each obligation the model makes checkable banks as engineering capital that compounds. That is the churn-and-capital duality read along the feed: Modeling supplies the representation, Alignment attaches the authority that keeps the representation from decaying, and the pair is what turns a model from a drawing the fleet consults into a stock of engineering capital the environment accrues. The feed is why the two theses are one progression and not two achievements — a model becomes capital only once something refuses to let the system contradict it.

6.1.11 What kind of theory this is

Say plainly what kind of theory this is. MAGE is an empirically grounded middle-range theory, developed through design science and reflective practice, then analytically generalized against a heterogeneous set of contemporary industrial field reports. I built a real system over many months, watched where it failed, reshaped the engineering environment around the fleet, and named the constructs that kept recurring. That is a builder reflecting on building. It is a close cousin of action research, but lighter: there were no intervention-and-reflection cycles run with a client organization, so I claim the design-science reading, not the fuller method's apparatus. "Grounded" is lowercase. The theory is grounded in evidence from practice; it is not the product of the formal coding protocol the term Grounded Theory names.

One deep case cannot fix universal coefficients, and the book has never pretended it could: none of the eight relations in the model receives an independent, population-level test. What a single case can do is generate constructs and mechanisms. To learn whether those travel, I set the theory against contemporary industrial field reports — organizations that built their own governed environments with no shared theory to guide them. Those reports do not validate MAGE; practitioner accounts cannot establish causation. They corroborate it, supplying convergent external evidence for its central mechanisms while exposing different operationalizations, additional mechanisms, and boundary conditions the originating case could not have seen.

The research design behind that outward turn works by reconstruction, not inductive coding. Rather than code the industrial reports into a taxonomy of current practice, I reconstructed each system in the MAGE vocabulary and put three questions to it:

  • Which mechanisms the organization describes does the theory naturally explain?
  • Where does the organization expose phenomena the originating case could not observe, so the theory must be refined or extended to hold?
  • Where does the theory predict mechanisms or relationships not yet explicit in the industrial account?

The two evidence sources are asymmetric, and the asymmetry is why they compose. DocAble supplied mechanism depth — full process visibility, but weak external diversity, one system in one setting. The industrial cases supplied variation — heterogeneous contexts, but weak internal process tracing, since a finished retrospective rarely shows the months of failure behind the machinery. Together they support analytic rather than statistical generalization: the aim is not to estimate how often organizations adopt a practice, but to explain why organizations that differ in nearly everything still converge on similar engineering structures. Part 5 introduces the case the theory was formed from. And where those cases pressed, they refined the theory: strengthening it in places, narrowing it in others, extending it where the evidence demanded. A theory that only ever gets confirmed would be the suspicious result. This one changed while its causal skeleton held.

6.1.12 The three levels of evidence

The two sources supply different kinds of evidence, and the terminology should say so. Three levels sit behind the argument.

  • L1 — the originating case. DocAble, watched from inside the machine. Why each mechanism was introduced, what failure forced it, what alternatives were rejected, the months-long build history that produced it. This is genuine process tracing: the engineering happened where I could see it, and I recorded it as it ran. "Case study" names this level, and only this level.
  • L2 — the reconstructions. Cloudflare, Docker, Siemens, Shopify, Spotify, and Zenseact, read from outside the machine. Public engineering reports show what mechanisms each system runs, how they fit, what MAGE calls them, and, as tellingly, what is conspicuously absent. They do not show the engineering history, so no month-by-month narration is possible or attempted. These are reconstructions, not case studies. Calling them case studies would promise DocAble-depth evidence no public account can supply.
  • L3 — validation across the reconstructions. Read the six side by side and the same engineering grammar keeps recurring: six starting points, one governing move, judgment converted into an explicit representation an environment enforces. Agreement across systems that differ in almost everything is the evidence a single case cannot give.

State the asymmetry as a feature. For DocAble we observe the process directly; for Docker we reconstruct the engineering system from public reports. One richly observed inducing case plus a comparative interpretation of independent industrial systems is the clean empirical story of this book: the case carries mechanism depth, the reconstructions carry the variation that shows the mechanisms travel. Read a reconstruction as an engineering report, not a proof, and read a silence in one as what its account left out, not a capability the organization lacks.

6.1.14 Closing

The claim of MAGE is not that more governance produces better software. It is that abundant implementation capacity makes the fit of the engineering environment decisive. Known obligations can be encoded before the work begins. Unknown ones become visible only through churn, failure, and friction. Judgment separates the local defect from the missing structure; authority lets that diagnosis alter the shared environment; models and mechanisms reshape what the next agent can know and do. When the loop works, velocity buys durable progress. When it does not, velocity only reaches the churn wall sooner. That is the theory this book leaves for the next case to test.
