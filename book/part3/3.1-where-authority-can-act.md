# Where Authority Can Act

<!-- section-terms: intervention-boundary, guidance-vs-authority, governed-environment -->

<!-- point: the-environment-intervenes-between-a-proposed-action-and-its-consequence | The environment intervenes between a proposed action and its consequence. | terms: governed-environment, agentic-harness -->
A foundation model produces probabilistic judgments. A harness turns selected judgments into actions.
Once those actions can alter a repository, invoke an API, change infrastructure, or ship an artifact, the
engineering question is no longer only how to steer the reasoner. It is where the surrounding environment
can intervene between a proposed action and its consequence. Part 1
[characterized](1.4-the-new-engineering-problem.html) why the substrate demands that interposition; this
Part builds it.

<!-- point: guidance-influences-behavior-authority-constrains-consequences | Guidance influences behavior; authority constrains consequences. | terms: guidance-vs-authority, thesis-alignment -->
Start with a distinction this Part keeps sharp. **Guidance influences behavior; authority constrains
consequences.** A prompt, brief, example, or playbook can make one action more likely than another, and
that influence can be strong. It does not by itself decide what the environment permits or accepts. A
permission boundary, a type, a validator, or a gate can. MAGE uses both, and reserves *authority* for the
second move.

<!-- point: feedback-is-the-third-piece-it-closes-the-loop-without-creating-authority | Feedback is the third piece: it closes the loop without creating authority. | terms: guidance-vs-authority, governed-environment -->
Feedback is the third piece. A mechanism can make the result of work legible to the next reasoning step: a
failing test, an observed call, a measured latency, a validator's explanation. Feedback creates no
authority either; it closes the engineering loop, so an agent can respond to evidence produced outside its
own judgment.

<!-- point: agents-are-steerable-their-outputs-are-not-guaranteed | Agents are steerable; their outputs are not guaranteed by the instruction that steers them. | terms: agent, thesis-alignment -->
<!-- index-def: agent -->
This is why authority does not live in the instruction you write. An **agent** here is a foundation model
inside a harness, reasoning over the context you supply and acting through the interfaces it is given.
Agents are steerable; their outputs are not guaranteed by the instruction that steers them. A prompt
conditions a probability. It cannot bind an outcome. So the decision that matters — which recommendation
becomes an action, which action becomes the system — has to rest with something the agent cannot talk its
way past. That something is the environment, acting at one of the boundaries this chapter walks.

<!-- point: security-practice-draws-the-same-boundary | Security practice draws the same boundary: secure the process that produces the artifact. | terms: guidance-vs-authority -->
Security practice draws the same boundary. Once agents act before commit time, the repository is too late
to be the security boundary — the tools, permissions, and execution environment that produce a change join
the trusted base, so agentic security must secure the process that creates the artifact, not only the
artifact [cite:snyk2026agenticlifecycle].

<!-- point: authority-can-act-at-several-boundaries-choose-where-the-obligation-is-visible | Authority can act at several boundaries; choose where the obligation is visible and a mechanism can affect the consequence. | terms: intervention-boundary -->
Authority can act at several boundaries in the work. The useful question is not which one is "hardest," but
**where the relevant obligation is visible and where a mechanism can affect the consequence.** Four
representative boundaries recur throughout the book — reasoning input, agent action, the work unit, and the
accepted artifact or runtime state. [ref:intervention-boundaries] puts them on one line.

<!-- label: intervention-boundaries -->
<!-- figure: assets/intervention-boundaries.svg | *Intervention Boundaries.* Engineering intent can influence reasoning, or act with authority at the action, work-unit, and artifact/runtime boundaries. The four are increasing *semantic grains* — one attempted side effect, then a whole unit of work, then the resulting system — not increasing *strengths* of authority. Reasoning input is ordinarily guidance; the other three are places a mechanism can affect the consequence. ## Four intervention boundaries

<!-- section-terms: intervention-boundary, reasoning-input, action-boundary, work-unit-boundary, artifact-runtime-boundary -->

<!-- point: the-first-boundary-is-reasoning-input | The first boundary is reasoning input: ordinarily guidance, not authority. | terms: reasoning-input, intervention-boundary -->
<!-- index-def: reasoning-input -->
The first boundary is **reasoning input** — the context, representations, examples, and instructions put in
front of the reasoner. This is where Modeling and context engineering do most of their work: a finite
reasoner does better when the relevant system knowledge is already externalized and selected for the task.
But placement in context is ordinarily guidance, not authority. The model can misread, forget, or disregard
what it was shown.

<!-- point: the-second-boundary-is-the-action-one-attempted-side-effect | The second boundary is the action: one attempted side effect the harness can inspect or refuse. | terms: action-boundary, intervention-boundary -->
<!-- index-def: action-boundary -->
The second is the **action boundary** the harness and its tools expose — one attempted side effect in view:
a tool call, an API request, a shell command, a file mutation. Permissions can remove an action from the
agent's repertoire; a hook can inspect or reject a proposed action; a tool can expose a deterministic
operation instead of asking the model to improvise it. An alert-triage agent permitted to shift a
maintenance window but forbidden to create infrastructure has a bounded blast radius because the API denies
the forbidden action, not because the prompt politely asks it not to try — the API just returns a clean
403 [cite:cockroachlabs2026agents].

<!-- point: the-third-boundary-is-the-work-unit-a-meaningful-unit-of-many-actions | The third boundary is the work unit: a meaningful unit of many actions, where whole-work obligations become legible. | terms: work-unit-boundary, intervention-boundary -->
<!-- index-def: work-unit-boundary -->
The third is the **work-unit boundary** — a meaningful unit composed of many actions now in view: a
completed task, a pull request, a build, a migration step, a deployment candidate. Obligations that no
single action can express become legible here: that the model and the implementation agree at task
completion, that a change carries all its required evidence, that "done" actually holds. A pre-commit check
can reject a local defect; a task-completion audit can weigh the whole body of work; a deployment gate can
refuse a candidate whose accumulated evidence is inadequate. These boundaries matter because different
obligations become legible at different grains of work.

<!-- point: the-fourth-boundary-is-the-artifact-or-runtime-forbidden-state-made-unexpressible | The fourth boundary is the artifact or runtime: forbidden state made impossible to express or accept. | terms: artifact-runtime-boundary, intervention-boundary, ban-lint -->
<!-- index-def: artifact-runtime-boundary -->
The fourth is the **artifact or runtime boundary** — the resulting system or running state. Types, narrow
APIs, architectural seams, schemas, runtime permissions, and admission policies can make a forbidden state
impossible to express or impossible to accept. The catalogue's running example is a format seam: ordinary
remediation code reaches the raw format library only through one structured interface, while a ban-lint
detects any forbidden direct access. The model states the architecture; the interface and the check give
the boundary its authority.

## Placement and strength are different decisions

<!-- section-terms: intervention-boundary, guidance-vs-authority -->

<!-- point: the-four-boundaries-do-not-form-a-monotonic-scale | The four boundaries do not form a monotonic weak-to-strong scale. | terms: intervention-boundary, guidance-vs-authority -->
The four boundaries do not form a monotonic scale from weak to strong. A narrowly scoped API permission may
bind more absolutely than a late CI check; a type may rule out one state completely while saying nothing
about a system-level obligation a task-completion gate can weigh. **Where a mechanism acts and how much
authority it carries are different design decisions.**

<!-- point: guidance-belongs-on-the-map-but-not-on-the-same-axis-docker-matters | Guidance belongs on the map but not on the same axis; this is why substantial Alignment can exist with little modeling. | terms: guidance-vs-authority, thesis-modeling -->
Guidance belongs on the same map but not on the same axis. Context can strongly influence behavior while
carrying no authority over what is accepted. An environmental control, in turn, can bind an action the model
never reasoned about at all. This is why a bounded execution sandbox matters to the theory: substantial
Alignment can exist with little explicit system modeling. Richer models do something different — they
enlarge the set of properties the environment can state and reason over. They raise the ceiling on what
authority can address; they are not a precondition for authority to act.

## Every boundary is a place to close the loop

<!-- section-terms: intervention-boundary, feedback -->

<!-- point: every-boundary-determines-where-feedback-can-return | Every boundary also determines where feedback can return; earlier evidence means less to reconstruct. | terms: intervention-boundary, feedback -->
<!-- index-def: intervention-boundary -->
<!-- index-def: engineered-agent-loop -->
The boundaries also decide where feedback can return. A harness can preserve durable state before a lossy
compaction; an action hook can explain why a call was refused; CI can hand back a failing invariant while
the change is still fresh in the window; a deployment validator can report which evidence failed admission.
The earlier useful evidence returns, the less work an agent must reconstruct before repairing the miss.

<!-- point: these-mechanisms-do-not-act-independently-deferred-to-3-5 | These mechanisms do not act independently; the interplay is its own problem, deferred to §3.5. | terms: intervention-boundary -->
These mechanisms do not act independently. Two controls may touch the same resource, fire on the same
event, or impose incompatible requirements. That problem is deliberately deferred to [a later
chapter](3.5-when-guardrails-collide.html). For now the point is simpler: the environment offers several
places to guide, observe, constrain, evaluate, and refuse autonomous work. The next question is *which
boundary fits a particular obligation.*

<!-- point: the-alignment-thesis-stated-whole | The Alignment Thesis, stated whole: give engineering intent authority by encoding obligations into authoritative mechanisms — constrain, sense, evaluate, admit — which can act directly, models enlarging their reach. | terms: thesis-alignment, intervention-boundary -->
<!-- index-def: thesis-alignment -->
This is the Part's governing claim, stated whole. **The Alignment Thesis:** give engineering intent
authority over autonomous work by encoding obligations into authoritative mechanisms that constrain actions,
produce evidence, evaluate that evidence, and control admission. Alignment can act directly on actions and
artifacts; richer representations enlarge the set of properties those mechanisms can state and check, but a
model is not required for authority to act. *In other words:* once you have decided what the environment
must hold, stop asking every future agent to remember it — give the obligation to a mechanism the agent
cannot talk its way past.

The method later gives this split a name: **self-governance supplies the judgment; the governed
engineering environment supplies the authority** — the reasoner proposes the move, the environment binds
the consequence (Part IV builds self-governance as the mastery-skill that carries that judgment).

<!-- point: alignment-installed-at-a-boundary-is-easiest-to-see-in-systems-already-running-it | Authority installed at a boundary is easiest to see in systems already running it. | terms: thesis-alignment, intervention-boundary -->
Authority installed at a boundary — rather than asked for in a prompt — is easiest to see in systems already
running it.

<!-- worked-examples: thesis-alignment -->
### Example — Docker
Docker places an agent's authority in the environment, not its instructions: the agent acts only through a
constrained tool seam, and the platform — not the prompt — decides what that seam permits. A move outside
the boundary is refused, not merely discouraged. That is authority at the action boundary, hardened into a
permission the agent cannot talk its way past.

### Example — Zenseact
Zenseact hands each domain team an agent that is little more than a config file and a skill, while a central
team owns the runtime, the permissions, and the context routing. Authority lives in a per-tool, per-role
permission table the environment enforces, so an agent's reach is a property of where it sits in the
platform rather than of how it was asked.

### Example — Spotify
Spotify's migration agents touch the code only through a restricted API and a narrow Git interface, and
every change must clear a merge gate fed by static linters and a semantic reviewer before it lands. The
gate, not the agent's confidence, admits the work — substantial authority placed at the work-unit boundary,
where the change becomes a candidate for the system.

### Example — DocAble
DocAble distributes its controls across the boundaries: a skill in the harness, an action hook, a
pre-commit check, and — its sharpest — a ban-lint that routes every mutation of a document format through
one structured model, at the artifact boundary, so no agent can reach the raw library and silently corrupt a
file. One rule at one gateway holds for every agent that ever touches that code.

<!-- takeaway -->
**Authority does not have one home.** Docker uses a constrained action surface; Zenseact centralizes
permissions in its platform; Spotify places substantial authority at the work unit; DocAble spreads controls
across actions, hooks, checks, and application seams. The common move is not a particular boundary but
environmental authority that does not depend on the producing agent's agreement.
