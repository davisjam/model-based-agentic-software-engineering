# Where Obligations Can Be Enforced

<!-- section-terms: intervention-boundary, guidance-vs-enforcement, governed-environment -->

<!-- point: the-environment-intervenes-between-a-proposed-action-and-its-consequence | The environment intervenes between a proposed action and its consequence. | terms: governed-environment, agentic-harness -->

A foundation model produces probabilistic outputs; a harness turns selected outputs into actions. Once those actions can alter a repository, invoke an API, change infrastructure, or ship an artifact, the engineering question is no longer only how to steer the reasoner. It is where the surrounding environment can intervene between a proposed action and its consequence.

<!-- point: guidance-influences-behavior-enforcement-constrains-consequences | Guidance influences behavior; enforcement determines what the environment permits or accepts, and feedback returns evidence between them. | terms: guidance-vs-enforcement, alignment-principle -->

<!-- index-def: agent -->

Start with the distinction between guidance and enforcement. **Guidance influences behavior; enforcement determines what the environment will permit or accept.** A prompt, brief, example, or playbook can make one action more likely than another, and that influence can be strong. A permission boundary can forbid an action; a validator and gate can refuse a result. Feedback can then return the evidence or explanation to the reasoner—a failing test, an observed call, a measured latency, or a validator's explanation—so that subsequent work can respond. MAGE uses all of these mechanisms, but counts an obligation as enforced only when the engineered environment constrains the relevant action or determines whether the resulting work is accepted rather than merely advising the reasoner.

<!-- point: security-practice-draws-the-same-boundary | Recent agentic-security guidance draws a similar boundary: secure the process that produces the artifact. | terms: guidance-vs-enforcement -->

Recent agentic-security guidance draws a similar boundary. Once agents act before commit time, the repository is too late to be the security boundary: the tools, permissions, and execution environment that produce a change join the trusted base, so agentic security must secure the process that creates the artifact, not only the artifact[cite: snyk2026agenticlifecycle].

<!-- point: enforcement-can-act-at-several-boundaries-choose-where-the-obligation-is-visible | An obligation can be enforced at several boundaries; choose where it is visible and a mechanism can enforce it. | terms: intervention-boundary -->

An obligation can be enforced at several boundaries in the work. **Choose the boundary where the relevant obligation is visible and a mechanism can enforce it.** Four representative boundaries recur throughout the book — reasoning input, agent action, the work unit, and the accepted artifact or runtime state. [ref:intervention-boundaries] puts them on one line.

## Reasoning Input, Action, Work Unit, and Artifact/Runtime

<!-- section-terms: intervention-boundary, reasoning-input, action-boundary, work-unit-boundary, artifact-runtime-boundary -->

<!-- point: the-first-boundary-is-reasoning-input | The first location is reasoning input: ordinarily guidance, not enforcement. | terms: reasoning-input, intervention-boundary -->

<!-- index-def: reasoning-input -->

The first location is **reasoning input**: the context, representations, examples, and instructions put in front of the reasoner. This is where Modeling and context engineering do most of their work: a finite reasoner does better when the relevant system knowledge is already externalized and selected for the task. But placement in context is ordinarily guidance, not enforcement. The model can misread, forget, or disregard what it was shown.

<!-- box-family: inset -->

<!-- inset-domain: Case study -->

> #### Worked inset — DocAble: Supplying Context and Requiring Discovery {#inset-context-engineering}
>
> An agent assigned to change DocAble’s code needs the rules relevant to the files it expects to edit. DocAble is a document-remediation service developed with agents, and its engineering environment selects those rules for each task. Those rules include architectural invariants, ownership declarations, lint requirements, and links to design decisions. The engineering problem is to select that knowledge for a particular task without making every agent reconstruct it from the repository.
>
> DocAble selects context twice. At dispatch, the environment matches the work order’s anticipated files against file-scoped constraint declarations and the models’ file-to-component mappings. It includes the resulting knowledge in the work order. After planning, the agent triggers a second extraction using its refined file set. That pass can surface obligations missed by the initial brief as the proposed change becomes more concrete[cite: davis2026docable]. This is *dynamic context injection*: properties of the work determine which engineering knowledge enters the agent’s context. [ref:docable-context-selection] shows how a task-specific slice supplements the standing instructions.
>
> <!-- label: docable-context-selection -->
> <!-- figure: assets/deliver-context-two-layer.svg | *Selecting context for the work.* Standing instructions and a retrieved task slice supply the agent’s context. DocAble repeats selection after planning, when the anticipated files are clearer. This information path supports reasoning; the separate extraction gate checks that the required discovery event occurred. -->
>
> A Git pre-commit gate rejects the final agent-worktree commit when the dispatch has no recorded second-extraction event. Its condition is deliberately narrower than “the agent followed the rules.” It does not compare the extraction’s file set with the committed files, or establish that the selected constraints were complete, correct, read, or followed. The gate requires a discovery event; correspondence checks and implementation gates must evaluate the obligations that discovery exposes.
>
> Completion requires a different view of the work. DocAble’s definition-of-done audit recomputes evidence over the completed task instead of relying only on an earlier record. Several intermediate commits may legitimately leave a model and its implementation temporarily inconsistent; the completed task is where their required agreement can be assessed. The two mechanisms therefore answer different questions: did the required discovery occur, and does the finished work carry the evidence needed for acceptance? Neither question is answered merely by placing instructions in context. ([appendix: appendix-a-governed-delegation] traces an actual dispatch through model selection, work-order construction, and completion checks.)

Guidance can make an acceptable realization more likely. A sound constraint or admission mechanism can instead rule a represented class of unacceptable realizations out of the surface it governs. Guidance improves the producer's odds; enforcement changes what admission must trust.

<!-- point: the-second-boundary-is-the-action-one-attempted-side-effect | The first enforcement boundary is the action: one attempted side effect the harness can inspect or refuse. | terms: action-boundary, intervention-boundary -->

<!-- index-def: action-boundary -->

The first of the three *enforcement* boundaries is the **action boundary** exposed by the harness and its tools. Here, one attempted side effect is in view: a tool call, an API request, a shell command, or a file mutation.

<!-- box-family: inset -->

<!-- inset-domain: AGENT HARNESS -->

> #### Inset — Hooks and Permissions {#inset-hooks-and-permissions}
>
> Many agent harnesses let engineers intervene in an agent’s work through permissions and lifecycle hooks. For example, a deployment tool can be permitted to inspect production state while its credentials deny permission to modify it. A pre-action hook can invoke a check on a proposed command; if the check is configured to block violations, the harness refuses the command. A post-action hook can check the result or collect evidence, but the operation has already occurred. That evidence can inform a later acceptance decision: a CI or deployment gate can reject a larger unit of work when required checks fail.
>
> We can understand these facilities by separating *where* an intervention occurs from *what* the configured mechanism does. The boundary determines what evidence is available in time to affect the decision. The mechanism determines how that evidence is used: the same failed check at the same hook might produce a warning or stop execution. If the deployment tool must not modify production state, permissions enforced by the production service can refuse a write before it takes effect. A warning after a write cannot satisfy that obligation: the forbidden effect has already occurred. The engineer therefore starts with what must be prevented or established, then chooses a boundary with sufficient evidence and a mechanism whose response enforces that requirement.

<!-- point: the-third-boundary-is-the-work-unit-a-meaningful-unit-of-many-actions | The second enforcement boundary is the work unit, where whole-work obligations become legible. | terms: work-unit-boundary, intervention-boundary -->

<!-- index-def: work-unit-boundary -->

The second enforcement boundary is the **work-unit boundary**, where many actions compose into a meaningful unit: a completed task, pull request, build, migration step, or deployment candidate. Obligations that no single action can express become legible here: that the model and the implementation agree at task completion, that a change carries all its required evidence, that "done" actually holds. A pre-commit check can reject a local defect; a task-completion audit can weigh the whole body of work; a deployment gate can refuse a candidate whose accumulated evidence is inadequate. These boundaries matter because different obligations become legible at different grains of work.

<!-- point: the-fourth-boundary-is-the-artifact-or-runtime-forbidden-state-made-unexpressible | The third enforcement boundary is the artifact or runtime: forbidden state made impossible to express or accept. | terms: artifact-runtime-boundary, intervention-boundary, ban-lint -->

<!-- index-def: artifact-runtime-boundary -->

The third enforcement boundary is the **artifact or runtime boundary**: the resulting system or running state. Types, narrow APIs, architectural seams, schemas, runtime permissions, and admission policies can make a forbidden state impossible to express or impossible to accept. For example, a service account may have permission to read production records but no permission to change them. The permission restricts what the running system can do, regardless of how the agent wrote its code.

## Placement and Strength Are Different Decisions

<!-- section-terms: intervention-boundary, guidance-vs-enforcement -->

<!-- point: the-four-boundaries-do-not-form-a-monotonic-scale | The four boundaries do not form a monotonic weak-to-strong scale. | terms: intervention-boundary, guidance-vs-enforcement -->

The four boundaries do not form a monotonic scale from weak to strong. A narrowly scoped API permission may enforce its obligation more strictly than a late CI check; a type may rule out one state completely while saying nothing about a system-level obligation a task-completion gate can weigh. **Where a mechanism acts and how strongly it enforces an obligation are different design decisions.**

<!-- point: substantial-enforcement-can-exist-without-rich-models | Substantial enforcement can exist without rich models; richer models expand the properties the environment can state and govern. | terms: guidance-vs-enforcement, modeling-principle -->

Richer models can expand the properties the environment is able to state and govern, but substantial enforcement can exist without them. A bounded execution sandbox, for example, can constrain actions without requiring a rich model of the system it contains.

## Return Evidence at the Earliest Useful Boundary

<!-- section-terms: intervention-boundary, feedback -->

<!-- point: every-boundary-determines-where-feedback-can-return | Boundary placement affects what feedback can return and when; timely evidence lets an agent use the reasoning and context already at hand, while delayed feedback may require reconstruction. | terms: intervention-boundary, feedback -->

<!-- index-def: intervention-boundary -->

<!-- index-def: engineered-agent-loop -->

The boundaries also determine what feedback can return and when. An action hook can explain why a call was refused; a CI check can report a violated invariant in the change under review; a deployment validator can identify failed checks or missing required evidence. Placing a check where the obligation can first be evaluated allows useful evidence to return while the relevant work is still in progress. The agent can then revise the change using the reasoning and context already at hand. If feedback arrives after it has moved on, it may have to reconstruct what it changed and why before it can understand the failure and correct the work.

<!-- point: these-mechanisms-do-not-act-independently-deferred-to-3-5 | These mechanisms do not act independently; the interplay is its own problem, deferred to §3.5. | terms: intervention-boundary -->

Controls within the GEE can also interact or conflict; {{sec:when-guardrails-collide}} treats their growing portfolio as a system in its own right.

<!-- point: the-alignment-principle-stated-whole | The Alignment Principle, stated whole: make engineering obligations enforceable by encoding them into mechanisms — constrain, sense, evaluate, admit — that can enforce them; in other words, once an obligation is entrusted to the engineering environment, satisfying it should not depend solely on each future agent remembering it. | terms: alignment-principle, intervention-boundary -->

**The Alignment Principle:** make engineering obligations enforceable through mechanisms that constrain actions or states, produce evidence, or evaluate evidence to control whether work may proceed. *In other words:* once an obligation is entrusted to the engineering environment, satisfying it should not depend solely on each future agent remembering it.

### Examples — Docker and Spotify

Docker Sandboxes routes outbound HTTP and HTTPS requests through a proxy on the host. Under a configured deny-by-default policy, the proxy checks the destination domain against an allowlist and blocks requests to unapproved domains. For example, suppose an agent tries to upload a diagnostic log to a domain absent from the allowlist. The proxy blocks that request before it reaches the destination, even if the agent considers the upload useful. This enforces the domain restriction; it does not establish that content sent to or obtained from an allowed domain is safe[cite: mikhalev2026untrusted].

Spotify requires a proposed change to pass the relevant verifiers before its background coding system opens a pull request. The environment selects independent verifiers from repository contents: finding `pom.xml`, for example, activates a Maven verifier. The agent can invoke verification while editing, and a Claude Code stop hook runs all relevant verifiers before PR creation. If one fails, the system returns an error and does not open the PR. The agent can therefore obtain feedback during its work, while the final invocation makes verification a condition of submitting that work for review[cite: charas2025feedback].

{{chapter:software-factories}} examines how such controls fit into software factories, including Spotify’s migration system.

<!-- takeaway -->

Place the enforcing mechanism at a boundary where the obligation is legible and the environment can evaluate or constrain the relevant work. The appropriate boundary depends on the obligation.
