# Constraints, Sensors, Validators, and Gates

## Constraints and sensors

<!-- section-terms: constraints-and-sensors, constraint, sensor -->

<!-- point: a-mechanism-is-one-of-two-moves-prevent-or-catch | A mechanism is one of two moves: prevent, or catch. | terms: constraint, sensor -->
A mechanism is one of two moves — prevent the mistake, or catch it — and [ref:constraint-vs-sensor] draws the split.

<!-- label: constraint-vs-sensor -->
<!-- figure: assets/constraint-vs-sensor.svg | *Constraint or Sensor.* The two moves and their asymmetric cost. A constraint prevents the mistake inside the iteration, so it costs no failed loop; a sensor catches it after the fact, so it costs at least one. Prefer the constraint where you can build one; add a sensor for the drift you cannot scope away. -->

<!-- point: words-alone-are-a-probability-flip-so-determinize-them-into-a-gate | Words are a probability flip; determinize them into a gate. | terms: soft-vs-hard-governance, constraint -->
<!-- index-def: gate -->
First, the argument for reaching for a mechanism at all. Words alone do not hold. Tell the agent
"make sure the briefs always follow this template" and it will say, *"Sure, boss"* — and then not
reliably do it, because it is a probability flip. A prompt raises the odds; it does not settle them.
But you can *determinize that*: before the agent launches, confirm every required part of the template
is present, and refuse the launch when it is not. The soft instruction becomes a hard gate. That move
— from a probability you nudge to a condition you enforce — splits into the two forms below.

<!-- point: a-sensor-detects-drift-after-the-fact-and-costs-iterations | A sensor detects drift after the fact and costs iterations. | terms: sensor -->
<!-- index-def: sensor -->
<!-- index-example: observability -->
**A sensor detects drift.** It lets the mistake happen and catches it after the fact, and because it
fires after, it fails the loop iteration: the agent runs again to fix what the sensor caught. Your test
suite in CI is a sensor, and so are your lints. It would be better if the model never wrote the bug;
but if it does, the sensor catches it before the code ships. The cost of a sensor is iterations —
detect, fail, re-iterate — and that cost is the reason you do not reach for one first.

<!-- point: a-sensor-is-only-as-good-as-its-observability | A sensor is only as good as its observability. | terms: sensor, observability -->
<!-- index-def: observability -->
A sensor is only as good as the signal it can read. **Observability** is the property that a running
system exposes enough signal to explain what it did and catch what went wrong. It is the wiring under
every sensor: the event a gate fires on, the log a checker reads, the trace that turns "the build
failed" into "the build failed *here, for this reason.*" Build the observability first and the sensor
has something to watch; skip it and it stares at a blank wall.

<!-- point: a-constraint-prevents-drift-within-the-iteration-and-costs-no-iteration | A constraint prevents drift within the iteration, costing none. | terms: constraint, typed-enum -->
<!-- index-def: constraint -->
**A constraint prevents drift.** Where a sensor detects an instance of the mistake after the fact, a
constraint makes the whole class impossible: it scopes the agent's action space *within* the
iteration, so the wrong move is never available to pick. The cleanest example is types. Suppose the
agent represents a state with bare strings. Being a language model underneath, it will cheerfully
reach for a synonym next time, and the synonym silently fails to match — you learn that an iteration
later, when the test suite crashes. Tell it to use an enumeration instead, and the failure mode
evaporates: it can no longer invent an unlisted value, and if it tries, the compiler rejects it on the
spot. The enum forbids the bug rather than watching for it, and no iteration is spent catching it —
which is why the catalogue leans so hard on structured models and closed enumerations over free-form
strings.

> Learn more about this governance mechanism: [closed enumerations over free-form strings](appendix-c-typed-categories.html).

<!-- point: constraint-and-sensor-are-control-engineerings-working-terms | Constraint and sensor come from control engineering. | terms: constraint, sensor, constraints-and-sensors -->

> *A footnote on control engineering.* Constraint and sensor are the working terms of control
> engineering. A governed plant — a reactor, an autopilot — carries constraints on the inputs and
> states it may reach and sensors on the outputs it produces, so the controller reads the error and
> corrects the next cycle. A fleet of probabilistic machines is a plant you cannot run open-loop; the
> governed environment is the loop you close around it. Engineers have run unruly physical processes
> this way for a century.
>
> Learn more: Nancy Leveson's *Engineering a Safer World* [cite: leveson2011] applies the same systems view to safety engineering.

> *A footnote on closing the loop in the wild.* Ericsson's EIAP closed loop pairs intent-based
> operation over curated, real-time network state with a controlled actuation surface, and decouples
> the model lifecycle from the application lifecycle: closed-loop autonomy needs both a state
> representation and a bounded actuation surface, or it is not operational autonomy [cite:ericsson2026closedloop].

<!-- index-def: governance-package -->
<!-- gloss-only: Constraint | A governance mechanism that prevents drift by scoping the agent's action space so the wrong move is unavailable within a loop iteration (a typed enum instead of a string); the prevented mistake costs no failed iteration. -->
<!-- gloss-only: Governance mechanism | A repeatable environmental structure that encodes an engineering policy and either constrains an action, detects a violation, requires evidence, or controls admission — four classes: prevention, detection, evidence, admission. The umbrella for a constraint or a sensor, replacing the ambiguous word "control"; a model joins governance only when something reads or enforces it. -->
<!-- gloss-only: Governance package | A mechanism that bundles several: a soft constraint (a structured model that aims the agent) shipped with hard sensors (the lints and drift-parity gates that catch what the constraint only aims at). -->
<!-- gloss-only: Sensor | A governance mechanism that detects drift after the fact and fails the loop iteration, so the agent must run again to fix what it caught (a lint, a test, a gate); it costs iterations. -->
Two axes cross here, and it pays to hold them apart. A mechanism has a *form* — **soft**, it aims the
agent, or **hard**, it holds regardless — and a *move* — a **constraint**, it prevents, or a
**sensor**, it detects. The two are independent: a constraint can be soft (a structured model that
aims the agent's reasoning) or hard (an enum the compiler enforces), and a sensor can be soft (a
convention that reminds) or hard (a lint that blocks). Constraint-versus-sensor is *what* the
mechanism does; soft-versus-hard is *how firmly*. [ref:form-and-move] lays the two axes out as a grid.

<!-- label: form-and-move -->
<!-- figure: assets/form-move-2x2.svg | *Form × Move.* The two axes are independent: form (soft aims a reasoner, hard holds a line) crosses move (a constraint prevents, a sensor catches). Any move can be built either way — the four cells give one worked example each. -->

<!-- point: most-real-mechanisms-are-a-package-so-tag-the-primary-move | Most mechanisms are a package; tag the primary move. | terms: governance-package, constraints-and-sensors -->
Most real mechanisms are a *package* across both axes. A structured model is a soft constraint on the
agent's reasoning — it aims the agent at the right shape without forcing it — shipped with hard
sensors, the lints and drift-parity gates that catch what it only aims at. The definition-of-done
review is the same shape: a runbook that constrains the steps, wrapped in sensors that flag a drifted
one. So name the package and tag its primary move: prefer a constraint where you can build one, add a
sensor for the drift you cannot scope away. ("Architecture" is the design activity that builds
constraints — not a third kind of thing.)

<!-- point: a-purely-organizational-answer-is-all-sensors-and-never-removes-a-failure-class | A purely organizational answer is all sensors, removing no class. | terms: sensor, constraint -->
Seen from the outside, this is what a purely organizational answer leaves on the table. Faced with an
unreliable worker, the instinct is to wrap it in process: a review, an approval, an evidence trail, a
sign-off. Every one of those is a sensor — each lets the mistake happen and inspects the output
afterward. A discipline built only of sensors can raise the odds and shrink the blast radius, yet it
never removes a failure class, because it watches the action space instead of scoping it. The
constraint is the move that answer does not have: it works ex-ante, inside the iteration, so the wrong
move is never available to pick — reliability by construction, not inspection after the fact.

<!-- point: the-constraint-is-poka-yoke-the-sensors-stop-is-jidoka | The constraint is poka-yoke; the sensor's stop is jidoka. | terms: constraint, sensor -->

> *A footnote on the factory floor.* [The Engineer's Seat](1.5-the-engineers-seat.html) introduced
> Toyota's names for these two moves: the constraint is *poka-yoke*, and the sensor's
> fail-the-iteration reflex is *jidoka*. The lesson Toyota drew is the one this section just argued —
> inspection at the end of the line cannot build quality in. A fleet of agents is a production line
> for code, and it relearns the same economics.

## Two axes, one bounded term {#four-classes-one-bounded-term}

<!-- section-terms: governance-mechanism, constraints-and-sensors -->

<!-- point: governance-mechanism-needs-a-boundary | Without a boundary, the word mechanism swells. | terms: governance-mechanism -->
One boundary before moving on, because without it the word swells. Prompts, documents, lints, tests,
metrics, hooks, models — everything in the environment starts to look like "a governance mechanism,"
and a term that covers everything governs nothing. Bound it:

<!-- index-def: governance-mechanism -->
> **Governance mechanism.** A repeatable environmental structure that encodes an engineering policy
> and either constrains an action, detects a violation, requires evidence, or controls admission.

<!-- point: four-classes-prevention-detection-evidence-admission | Two questions cross: how it treats failure, where it acts. | terms: governance-mechanism, constraints-and-sensors, governance-package -->
<!-- index-def: validator -->
The clause list is not one flat set of four peers. It is two questions crossing. **Constraint and
sensor classify _how_ a mechanism treats a failure — prevent it, or catch it — the catalogue's Move
axis, three-valued: constraint, sensor, or _package_ for a bundle carrying both. Evidence and
admission classify _where_ a mechanism acts — at the loop's closing door, not at the action.** An
evidence mechanism demands the change carry its proof: a provenance stamp, a re-derived test result, a
completion re-checked rather than self-reported. An admission mechanism decides whether the result may
advance at all — the admission rule of the engineered loop (1.3), holding the last door. Both are still
built out of constraints and sensors; they earn their names from their position in the loop. So the
earlier split is the whole Move axis, and evidence and admission are a second, positional cut across it.

The two compose into how a loop earns the right to advance: cheap checks run early and bind their
result to an exact tree, so a later, more expensive stage *checks that binding* rather than *trusts* a
report, and the definition of done recomputes the full evidence at close instead of reading a marker.
Cheap evidence early, full re-derivation late, never a trusted self-report.

<!-- point: a-model-is-not-a-mechanism-until-something-enforces-it | A model joins governance only when something enforces it. | terms: governance-mechanism, model-as-map -->
The definition also settles a boundary this book leans on. **A model file is policy. It becomes a
mechanism only when some agent, tool, or gate consumes it** — injected into an agent's context, it is
the soft constraint met earlier; read by a lint, a gate, or a generator, it is a hard sensor. So a
structured model can be a soft constraint *and* still be inert on disk, because "soft constraint"
already names the consuming step the model alone does not perform. The model supplies the policy; the
consumption supplies the holding.
