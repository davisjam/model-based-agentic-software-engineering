# The Agent Stack

<!-- noqa: book-section-cap | The Agent Stack — the opening's word count includes the stack figure's inlined accessible description and caption; the prose itself is three short paragraphs (the Part-opening derivation frame plus the reach-in question) -->

<!-- section-terms: agent-stack, injection-point, soft-vs-hard-governance -->

<!-- point: the-environment-interposes-between-capability-and-consequence | The governed environment interposes between capability and consequence. | terms: governed-environment, agentic-harness -->
A language model alone gives probabilistic recommendations.
A harness turns some of them into actions.
A governed engineering environment interposes between capability and consequence:
it decides which recommendations become actions, and which actions become the system.
Part 1 [derived](1.4-why-mage-follows-from-the-machine.html) why the substrate demands
that interposition; this Part builds it. An environment can only be trusted where it can
interpose between what the agent proposes and what becomes the system; the first question is
where that interposition can live. That is this chapter's role in the Part's arc: it opens
the on-ramp to Alignment by naming *where* the environment can reach in and attach authority —
the places a represented intent stops being advice and becomes something the build enforces.

<!-- point: governance-material-is-soft-conditioning-hard-authority-feedback | The material: soft conditioning, hard authority, feedback. | terms: soft-vs-hard-governance, governed-environment -->
The building material comes in three kinds. **Soft conditioning** aims the reasoner —
prompts, briefs, models, examples, playbooks. **Hard authority** binds it — tool
interfaces, permissions, schemas, lints, gates, validators. **Feedback** closes the
loop — results made machine-legible, so the agent can repair its own miss. In one
line: soft guidance goes in, deterministic guardrails constrain the actions, and a
deterministic envelope governs what gets admitted out. The three kinds say what a
mechanism does; the four layers, which we turn to next, say where it can live.

<!-- point: alignment-is-the-move-from-guidance-to-obligation | A prompt aligns without creating authority; MAGE is the move from guidance to enforceable obligation. | terms: soft-vs-hard-governance, thesis-alignment -->
That split is the one this Part turns on. A prompt can align behavior without creating
authority. MAGE is concerned with the transition from guidance to enforceable obligation: the
move from soft conditioning, which aims the reasoner, to hard authority, which binds it.

Security practice is drawing the same boundary. Snyk argues that once agents act before
commit time, the repository boundary is too late to be the security boundary: the tools,
skills, permissions and execution environment that produce a change become part of the
trusted computing base — "traditional AppSec secures the artifact; agentic security secures
the process that creates it" [cite:snyk2026agenticlifecycle].

<!-- point: agent-stack-has-four-injection-layers | The agent stack has four layers, each an injection point. | terms: agent-stack, injection-point -->
<!-- index-def: agent-stack -->
If governing an agent means conditioning where it searches, the practical question
follows at once: *where do you reach in to do it?* There are four places, stacked one
atop another, and each gives you a different kind of grip. Once you understand the
stack, every mechanism in this book resolves into the same move: pick a layer, inject
a constraint. [ref:stack-layers] draws the stack; this chapter walks it from the bottom up.

<!-- label: stack-layers -->
<!-- figure: assets/agent-stack-layers.svg | *The MAGE Stack.* Four layers stack from the GenAI foundation model up: the Harness that runs the agent and manages its context window, the Engineering environment of git and its hooks, and at the top the Application — the codebase, its tests, and CI. Each layer is a place to reach in and steer. The governance bar notches into all four, because a mechanism can live at any of them — a skill or hook in the harness, a pre-commit gate in the environment, a ban-lint in the application. Governance is a posture at every level, not one gate bolted on at the end. -->

## First, three definitions

<!-- section-terms: engineering, software-engineering, agent, model, structured -->

<!-- point: definitions-carry-the-books-argument | Three definitions carry the stack; engineering motivates them. | terms: engineering, agent, model -->
Before the walk, three definitions — *agent*, *model*, and the adjective the second
leans on, *structured*. Ordinary words, and every reader arrives with a working sense of
each; this book derives its argument from them, so a working sense will not carry the
weight. Two further terms — *engineering* and *software engineering* — fix *why* an
engineer reaches for a model at all; they matter, but they are not the stack, so the two
boxes below set them off to the side and the walk leans on them by name.

These definitions are shared vocabulary the whole book runs on, and the stack is where they
are first operationally required — you cannot say what a governed environment attaches
authority *to* without saying what an agent and a model are. So they open the Alignment part
not as Modeling foundation misfiled here, but as the terms the on-ramp needs in hand before it
can name where the environment reaches in.

<!-- index-def: engineering -->
> **Engineering.** The discipline of developing operable technological artifacts to solve problems, and of analytically identifying and assessing the competing means to those solutions, each with distinct trade-offs. The engineering move proper: **engineering adds the responsibility to compare alternatives and predict their trade-offs before construction** — an engineer weighs competing architectures against the properties the solution must have, and can predict the outcomes of a decision *prior to building*. The definition of *model* below exists to serve that prediction.

<!-- index-def: software-engineering -->
> **Software engineering.** Development produces a functioning artifact. The engineering move relevant here is *predictive selection*: choosing among workable designs by reasoning about the properties each will produce, and choosing *before* building. Agents sharpen the distinction: when implementation is cheap you can afford to build more than one — in Fred Brooks's words, to build one to throw away — and select among them. Selection needs a basis for prediction, and the basis is a model.

<!-- index-def: agent -->
> **Agent.** A controllable intelligence that reasons over a knowledge base — operationally, a foundation model inside a harness that can reason over supplied context and act through tools.

<!-- point: intelligence-devises-means-within-constraints | Intelligence devises means to goals within constraints. | terms: agent -->
*Intelligence* I will not define in full; a working sense will do. Given constraints and
a goal, an intelligence can devise a *means* to the goal that does not violate the
constraints.

<!-- point: controllable-not-controlled-is-why-governance-exists | Controllable, not controlled, is why governance exists. | terms: agent -->
*Controllable* is the adjective everything else in this book hangs on, and it does
not say *controlled*. A controllable intelligence responds to its handler: change its
environment and the knowledge available to it and it does different things, and it
will generally follow orders. But *controlled* means perfect guarantees of behavior,
where *controllable* means probabilistic ones. The stronger your mechanisms, the
tighter the distribution — never a guarantee. That one adjective is why governance
takes up so much of this book. If agents were controlled, we would not need the
governance at all.

<!-- point: models-are-the-agents-knowledge-base | The models are the agent's knowledge base. | terms: agent, model -->
*Reasoning* is the functional claim: given a query, the agent works over its context to
produce a response, using abstractions and adapting its actions to constraints rather
than reciting stored answers. Whether that counts as reasoning "genuinely" is a debate
this book does not need to win — the practical point is that it operates over the
structure you supply. The *knowledge base* names that structure, and for this book it is
the hinge: the models are the knowledge base.

<!-- point: perceive-act-builds-agents-controllability-governs-them | Perceive-and-act builds agents; controllability governs them. | terms: agent -->

> *A footnote for the reader with a textbook nearby.* This definition departs from
> Russell and Norvig deliberately. For them, an agent is anything that *perceives*
> its environment through sensors and *acts* on it through actuators, and a rational
> agent acts to maximize an expected performance measure. That perceive-and-act
> framing is the right one for *building* an agent. This book is about *governing*
> one, so it foregrounds a different property: controllability, in the cybernetic
> sense of behavior you can steer but not perfectly determine. The gap between
> controllable and controlled is no hedge. It is the reason this book exists.

> **Model, first pass.** A useful approximation of a phenomenon — simplified, but good enough to predict — and, as this book uses the word, a *blueprint*: a prescriptive description of a system to be built, which the built system is bound to realize. The formal definition arrives once its last ingredient, *structured*, is on the table.

<!-- point: model-fidelity-trades-against-cost | Model fidelity trades against reasoning cost. | terms: model -->
The reader likely knows the first sense already: a model as a simplified description,
prized because it *predicts*, not because it is exact. Think *f = ma*, which neglects
friction and is useful anyway; George Box's aphorism — all models are wrong, some are
useful — is the canonical statement. Models in this sense come in kinds:
mathematical, qualitative, relational, data-flow. And their fidelity trades against
cost: the coarser the model, the cheaper it is to reason about, and yet the wider the
error bars on what the reasoning tells you. How much fidelity you need is in the eye
of the application. "It processes information serially" may do to sketch a system,
while reasoning about security or privacy wants a model much closer to the real
thing.

<!-- point: blueprint-models-specify-rather-than-approximate | A blueprint model specifies; the build may not diverge. | terms: model -->
The second sense is the one I embed here. A blueprint does not *approximate* an
existing building; it *specifies* one that does not yet exist, and the builder is
bound to it. A system built to a model may *elaborate* on it, never *diverge* from
it. That is the sense this book leans on.

<!-- point: model-is-constraint-blueprint-and-knowledge-base | A model is constraint, blueprint, and knowledge base. | terms: model, agent -->
The blueprint sense is what lets a model serve as an agent's marching orders. Handed
to an agent, a model is three things at once: a *constraint*, bounding what may be
built; a *blueprint*, saying what to build; and, because the agent reasons over it,
the *knowledge base* for the artifact under construction.

<!-- point: model-does-double-duty-in-this-trade | The word model does double duty; context disambiguates. | terms: model, foundation-model -->
One caution before moving on. In these pages the word does double duty: the
*foundation model* at the bottom of the stack is itself a model in the first sense, a
learned approximation of language and the world, while the models this book teaches
you to write are blueprints in the second. Context will say which is meant.

<!-- point: structured-is-the-broad-sense-a-declared-verifiable-shape | Structured means a declared, verifiable shape, not a variable's type. | terms: model, structured -->
And one adjective before we go, because every blueprint in this book carries it:
*structured*.

<!-- index-def: structured -->
> **Structured.** Said of a model: written in an explicit, declared shape a machine can read and validate — a schema, not prose. The declared structure is what lets a machine hold the system up to the model: read the shape, check it for drift, query it, reason over it, enforce it. Prose can be a model; only a structured model can be checked.

The word is broader than a programming manual's *typed*. A variable has a type; that
is the narrow sense, and type-checking is its sharpest case. The sense this book
strains on is wider: the model has a shape, the shape is written down — fields,
states, relations, all explicit — and a checker can validate any instance against it.
*Structured* is the word I use, over *typed*, because it names that whole span. A type
is one way to declare a shape; a schema, a state table, or a registry will do as well.
Free prose fails the test not because it is vague but because a machine cannot act on
it: it can pattern-match the words, but it cannot hold the code up to them and prove
the two agree.

<!-- point: structured-is-what-admits-the-machine | The structure is what admits the machine. | terms: model, thesis-modeling -->
Watch what the adjective carries. Prose can be a model — simplified, predictive, even
prescriptive; the first half of the model definition asks no more. But every promise
this book makes about models — that they can be read, drift-checked, queried, reasoned
over, enforced, that a gate stays red until the map tells the truth again — is a
promise about *structured* models. The structure is what admits the machine. Drop the
adjective and the drift gate has nothing to read; keep it and the model stops being
documentation and becomes something the build can act on.

<!-- gloss: Drift gate | A build-time check that fails when a model and the code it describes disagree, so the model cannot silently go stale; Part 2 builds it in full. -->

<!-- point: formal-model-definition-assembles-the-pieces | The formal definition assembles approximation, blueprint, and structure. | terms: model, structured -->
Four steps fix the word. **One:** a model is *reduced* — smaller than the system, or it
is just the system again. **Two:** a MAGE model may *describe* what is or *prescribe*
what ought to be — the approximation sense or the blueprint sense. **Three:** it must be
*machine-readable* — structured, per the adjective above. **Four:** its relation to the
system must be *maintained* — a diagram nobody checks fails the day the code moves. The
book calls many things models — registries, graphs, manifests, state machines, typed
records — and each must clear all four. Here is the boundary.

<!-- index-def: model -->
> **Model.** A deliberately reduced, machine-readable representation of a system. It earns the name here only when it supports reasoning, derivation, or checking and is mechanically kept related to the system it represents.

<!-- point: five-load-bearing-terms-do-the-gatekeeping | Five load-bearing clauses gatekeep what counts as a model. | terms: model, drift-gate -->
Every clause earns its place. *Deliberately reduced* excludes the codebase itself; the
territory is not its own map. *Machine-readable* excludes ordinary prose. What a model
represents ranges wide — intent, structure, behavior, policy, evidence — but a data
structure with no referent is none of these and does not qualify. *Supports reasoning,
derivation, or checking* demands the model do work. And *mechanically kept related* is
the sharpest gate: a diagram nobody checks fails it the day the code moves. The next
chapter builds that last clause into a discipline, and Part 2 admits a whole zoo of
representations because each clears all five.

<!-- point: definition-relations-tell-the-book-in-a-nutshell | The definitions' relations summarize the whole book. | terms: engineering, agent, model -->
Now hold them together, because the relations tell the book in a nutshell. An agent is a
controllable reasoner in want of a knowledge base, and a model is a knowledge base that
constrains and specifies. Hand one to the other and you have the method. Engineering
supplies the reason to bother — prediction before construction — and a model is what
makes the prediction cheap. So the book's job is fourfold: describe the kinds of models
useful to agents; show how agents interact with them; keep the models consistent with the
artifact as it is built; and help engineers construct, assess, and predict from them.
Now, the stack.

## The four layers

<!-- section-terms: foundation-model, agentic-harness, engineering-environment -->

<!-- point: foundation-layer-spares-the-model-reasoning-cost | Tell the model where to look; spare its reasoning. | terms: foundation-model, compounding-failure-probability -->
<!-- index-def: foundation-model -->
**At the bottom sits the foundation model.** It comes from a commercial vendor or an
open-weight release, and it is a general language reasoner, able to *induce* an
understanding of your environment — though that induction is expensive, and it happens
fresh every time. The game at this layer, then, is to spare the model that cost: tell
it, up front, where to look. Sometimes you tell it deterministically, with an
executable program; sometimes softly, with written-down pseudocode — the algorithm to
follow, the playbook for a root-cause analysis; often it is a hybrid of the two. The
more reasoning you hand the model up front, the shorter the chain it must construct on
its own. Under the deliberately crude assumption that *n* independent steps each fail
with probability *p*, chain failure rises as

<!-- eq: P(wrong) = 1 − (1 − p)ⁿ -->

The equation is only the intuition — real step errors are neither independent nor equal,
and some are recoverable. The durable point survives the caveats: every unnecessary
re-derivation is one more step in *n*, one more chance to drift.

<!-- point: model-constituents-are-a-control-surface | The model's three parts steer differently. | terms: foundation-model, context-window -->
**What you control in the model.** The foundation model has three parts, and you steer
each one differently.

- **Its reasoning is a grade you buy.** Pick the tier, and size each task to a model
  that can reach the end of its chain — or let the orchestrator route the task to the
  model that fits.
- **Its training data you do not touch.** This book assumes you run the model as it
  ships. Bending the weights to your domain is a real lever, but a resource-intensive
  one, and in the main it is much more cost-effective to optimize the context window
  and revisit at the next generation of foundation models. ([A later
  chapter](5.2-why-this-system-was-a-hard-case.html) treats training data as the novelty axis: how far
  your system sits from what the model has seen decides how hard you must condition it.)
- **Its context window is fixed once a task is running on a chosen model.** You cannot
  enlarge it from inside the task; you can only decide what meaning occupies it. What you
  change is how much each token carries.

<!-- point: models-pack-the-window-denser | You cannot widen the window; pack it denser. | terms: context-window, thesis-modeling -->
So the window bounds the fleet — but not the way it first looks. You cannot widen it;
you can pack it denser. A model is a higher-abstraction representation, more meaning
per token, so the same window holds more of the system. That is the Modeling Thesis
aimed at the window bound: the fleet scales on two capacities, its reasoning grade and
its window.

<!-- point: window-control-is-the-books-bet | Model choice is yours; the book bets on the window. | terms: context-window, thesis-modeling -->
To the extent you control model choice, make it; if you have the resources to tune, it
may help. But this book's position is that controlling the context window is the key,
and modeling is the path we take.

<!-- point: the-model-reasons-over-a-world-representation | The model reasons over a world representation, so equip it. | terms: foundation-model, world-representation, skill-soft-control -->
This layer rests on one claim: the model reasons over an internal picture of its world,
not just the surface of your prompt. Interpretability work such as Othello-GPT shows the
shape of it — a model trained only on Othello move sequences, never shown a board, forms
a recoverable representation of the board state inside the network, and its predictions
track that representation when it is altered [cite: othello-gpt]. That is enough for the
engineering claim here: capable foundation models can operate over structured
representations we supply. The job at this layer is to equip that reasoning — to hand it
your world instead of a guessed one — and the concrete act is packaging the context as a
**skill** the model reaches for. [appendix: appendix-skill-recipe] gives the recipe.

Uber's uReview analyzes over 90% of the ~65,000 diffs opened weekly, but the engineering
story is the machinery around the reviewer — structured context, three-layer confidence
filtering, semantic dedup, a curated benchmark, periodic model selection, and streamed
useful/not-useful feedback — a probabilistic sensor treated as an engineering subsystem
[cite:uber2026ureview]. Uber notes the reviewer is bounded by having only the code — no
past PRs, feature-flag configs, database schemas, or docs — so source code alone bounds
what even a strong semantic reviewer can judge [cite:uber2026ureview].

<!-- point: harness-manages-the-context-window-and-holds-two-mechanism-points | The harness manages the context window and holds two mechanisms. | terms: agentic-harness, context-window, hook-hard-control, skill-soft-control -->
<!-- index-def: agentic-harness -->
<!-- index-def: context-window -->
**On top of the model sits the agentic harness** — Claude Code, OpenCode, and their
kin. The harness takes your prompts, feeds them to the model, and manages the context
window: the fixed budget of tokens the model can hold. Exceed the budget and the harness
must compact — a lossy compression of everything that has happened so far. The
harness is also where two of the most useful mechanism points live, and the line
between them is sharp: a hook is a thing the agent *has* to do; a skill is a thing it
*can choose* to do.

<!-- point: the-harness-layer-has-a-named-taxonomy | The field names a framework, harness, and agent-OS taxonomy. | terms: agentic-harness, agent-stack -->
This book uses **harness** for the runtime that manages context, tools, permissions, and
recovery, and **agent OS** for the same idea widened across agents and resources. The
field's vocabulary here is still unstable; the convention is all we need.

<!-- point: skills-are-soft-hooks-are-hard-tools-are-deterministic | Skills are soft, hooks are hard, tools take deterministic action. | terms: skill-soft-control, hook-hard-control, tool-deterministic-action -->
<!-- index-def: skill-soft-control -->
<!-- index-def: hook-hard-control -->
<!-- index-def: tool-deterministic-action -->
- **Skills are soft mechanisms.** A skill has trigger criteria and a body of guidance:
  "about to touch a PDF? enter this skill." Inside, it holds instructions — pure prose
  ("be careful editing PDFs"), or a mix of prose and code. The code half is a **tool**:
  a library or command-line entry point that lets the model take a *deterministic*
  action — add a page, delete a page, rewrite a run of text — instead of guessing.
- **Hooks are hard mechanisms.** Before or after the harness does something — passing a
  prompt, dispatching a sub-agent, calling a tool — you can run a deterministic program
  that inspects the action and, if it likes, *forbids* it. A hook can look at an
  outbound network call and refuse it; catch an email about to go out with a typo, or
  with sensitive information in it, and block the send. Run after the fact, the same
  hook logs what happened. Either way, you hold authoritative control over the agent's
  behavior at the moment it acts.

CockroachDB's alert-triage agent can adjust maintenance windows across clusters but cannot
create a cluster or modify networking — the API returns a clean 403 — because "the blast
radius of an agent mistake is bounded by its service-account permissions, not by the quality
of its prompt" [cite:cockroachlabs2026agents].

<!-- point: engineering-environment-must-be-written-down-and-offers-git-and-ci-hooks | Write down the engineering environment; it offers git hooks. | terms: engineering-environment, injection-point, hook-hard-control -->
<!-- index-def: engineering-environment -->
**Above the harness sits the engineering environment** — the tools and conventions your
team already uses. Jira holds the tickets. Git holds the code. A named server is where
you deploy; a named node is the head of your compute cluster. Engineers carry all of
this in their heads; an agent arrives with none of it, so for agents it
*must* be written down. This layer also holds your processes: the standard
operating procedures for handling a bug report, running a design review, triaging an
incident. And it, too, offers a concrete injection point. Git has hooks on every command
— before and after commit, pull, push. The classic use is a pre-commit hook that runs a
fast quality check before a change is allowed into the tree, moving feedback as far left
as it will go. Above that, your CI pipeline is another set of stages where mechanisms
attach.

> Learn more about this governance mechanism: [pre-commit hook](appendix-a-pre-commit-hook.html).

<!-- point: application-layer-makes-mistakes-structurally-impossible-via-static-analysis | Static analysis makes a mistake class structurally impossible. | terms: static-analysis, ban-lint -->
**At the top sits your application** — the product code itself, which can carry
governance of its own: models describing how it is supposed to work, and static analyses
that check the code against them. A static analysis at this layer is where a whole class
of mistakes can be made structurally impossible. The companion catalogue's sharpest
examples live here: a **ban-lint that routes all mutation of a document format through a
single structured model**, so that no agent can reach the raw library and silently corrupt the
file. The rule is enforced once, at the one gateway, and it holds for every agent that
ever touches that code.

> Learn more about this governance mechanism: [one structured model per format](appendix-c-pdf-model.html).

## Every layer is a place to steer

<!-- section-terms: injection-point, agent-stack -->

<!-- point: read-each-layer-as-an-injection-opportunity | Read each layer as an injection opportunity. | terms: injection-point, context-window -->
<!-- index-def: injection-point -->
Read the stack as a list of opportunities, because that is what it is. The harness
noticing it is near its context limit and writing out a reliable summary of state and
plan, instead of waiting for a lossy compaction, is an opportunity to help the model
reconstruct less after the window resets. The pre-commit hook is an opportunity to catch
a defect while everything that produced it is still fresh in the model's window, rather
than surfacing it from a failed test three compactions later. The CI pipeline turning a
failure into a message the agent can read is an opportunity to point it back toward the
fix.

<!-- point: every-layer-serves-one-goal-narrow-the-search | Every layer serves one goal: narrow the agent's search. | terms: conditioning-the-search, context-window -->
The goal underneath every layer is the one Part 1 named: narrow the agent's search
toward the choices you want. The window is too small to hold a serious system whole —
the US tax code, a real web application — so structure you fail to supply, the model must
induce on the fly, burning window on the rules of the road instead of the work. Every
mechanism you place on the stack is structure handed for free.

Ramp's Inspect runs each session in a sandboxed Modal VM with everything an engineer has
locally, wired to Sentry, Datadog, LaunchDarkly, Buildkite, GitHub and Slack, on the stated
design goal that it be "never limited by missing context or tools, but only by model
intelligence" — autonomy needs evidence-producing affordances, not merely code-writing
authority [cite:ramp2026inspect].

<!-- point: mechanisms-interact-and-the-interplay-is-its-own-problem | Mechanisms interact; the interplay is its own problem. | terms: injection-point -->
One thing the stack does not show: the mechanisms you install at these layers do not act in
isolation. They run together, and the interactions *between* them have to be governed too — two
that touch the same thing at the same moment pull against each other and confuse the very agent
they were meant to steer. Governing each layer is not enough; the interplay is its own problem,
and [a later chapter](3.6-when-guardrails-collide.html) takes it up.

The interplay grows once the agents themselves multiply. Ericsson's agent fabric treats the
topology *among* agents as governed infrastructure — discovery, routing, observability, a
secure registry all agents authenticate against, lifecycle management, and guardrails that
run inside the execution cycle in real time — on the argument that unmanaged "agent sprawl"
causes resource exhaustion and security holes [cite:ericsson2026agentfabric].

<!-- point: the-stack-grounds-both-theses | The stack grounds both the Modeling and Alignment theses. | terms: thesis-modeling, thesis-alignment -->
Governance is a posture at every layer, not one gate bolted on at the end. The stack is
where the two theses get their footing: a model handed to a layer enacts the Modeling
Thesis, and a hook or lint installed at a layer enacts the Alignment Thesis (both derived
in [Part 1](1.4-why-mage-follows-from-the-machine.html)). The stack gives the slots; it
does not say what to put in them.

<!-- index-def: thesis-alignment -->
This is the Part's governing claim, stated whole. **The Alignment Thesis:** give engineering
intent authority over autonomous work by encoding obligations into deterministic mechanisms
that constrain action, observe violations, evaluate evidence, and control admission. Where the
Modeling Thesis makes intent explicit, the Alignment Thesis makes that intent binding on what
the fleet can do and what the environment will accept. *In other words:* once you have decided
how the system should behave, stop asking every future agent to remember that decision — teach
the environment to enforce it instead. The four verbs — constrain, observe, evaluate, control
admission — are the four mechanism archetypes this Part builds: Constraint, Sensor, Validator,
Gate.

The Alignment Thesis — authority installed at a layer rather than asked for in a prompt —
is easiest to see in systems already running it.

<!-- worked-examples: thesis-alignment -->
### Example — Docker
Docker places an agent's authority in the environment, not its instructions: the agent
acts only through a constrained tool seam, and the platform — not the prompt — decides
what that seam permits. A move outside the boundary is refused, not merely discouraged.
It is the grip the stack names at the harness layer, hardened into a permission the agent
cannot talk its way past.

### Example — Zenseact
Zenseact's platform hands each domain team an agent that is little more than a config file
and a skill, while a central team owns the runtime, the permissions, and the context
routing. Authority lives in a per-tool, per-role permission table the environment
enforces, so an agent's reach is a property of where it sits in the platform rather than
of how it was asked. The control sits at the engineering-environment layer, one rung above
the harness.

### Example — Spotify
Spotify's migration agents touch the code only through a restricted API and a narrow Git
interface, and every change must clear a merge gate fed by static linters and a semantic
reviewer before it lands. The gate, not the agent's confidence, admits the work. That is
the Alignment Thesis installed at the top of the stack, where CI decides what becomes the
system.

### Example — DocAble
DocAble's sharpest alignment control is a ban-lint that routes every mutation of a document
format through one structured model, enforced at the application layer so no agent can
reach the raw library and silently corrupt a file. One rule at one gateway holds for every
agent that ever touches that code. The same posture recurs down the stack — a skill in the
harness, a pre-commit hook in the environment — so the authority is spread across layers,
not concentrated in one.
