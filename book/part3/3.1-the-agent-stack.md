# Where Authority Lives

<!-- noqa: book-section-cap | Where Authority Lives — the opening's word count includes the stack figure's inlined accessible description and caption; the prose itself runs three short beats (the derivation frame, the controllable-not-controlled motivation for external authority, and the reach-in question). -->

<!-- section-terms: agent-stack, injection-point, soft-vs-hard-governance -->

<!-- point: the-environment-interposes-between-capability-and-consequence | The governed environment interposes between capability and consequence. | terms: governed-environment, agentic-harness -->
A language model alone gives probabilistic recommendations.
A harness turns some of them into actions.
A governed engineering environment interposes between capability and consequence:
it decides which recommendations become actions, and which actions become the system.
Part 1 [characterized](1.4-the-new-engineering-problem.html) why the substrate demands that interposition;
this Part builds it. Part 2 carried a structured representation through two roles — **context** an agent
recovers facts from, then an **engineering model** it reasons through. A third remains: when mechanisms in
the environment enforce obligations expressed over that representation, it becomes the **governed
environment**. So the first question is where that interposition can live — the places a represented intent
stops being advice and becomes something the build enforces.

<!-- point: controllable-not-controlled-is-why-authority-leaves-the-prompt | Controllable, not controlled, is why authority must live in the environment. | terms: agent, thesis-alignment -->
<!-- index-def: agent -->
Why must authority live in the environment at all, and not in the instruction you write? Because of what
an agent is. An **agent** here is a *controllable* intelligence acting through tools — a foundation model
inside a harness, reasoning over the context you supply and acting on the world through the interfaces it
is given. The adjective the rest of the book hangs on is *controllable*, and it does not say *controlled*.
A controllable intelligence answers to its handler: change its environment and the knowledge available to
it and it does different things, and it will generally follow orders. *Controlled* would name a guarantee
of behavior. *Controllable* names a probability. The stronger your mechanisms, the tighter the
distribution — never a certainty.

That gap is the whole reason for this Part. A prompt conditions a probability; it cannot bind an outcome.
Were agents controlled, a careful prompt would be governance enough and there would be nothing here to
build. Because they are only controllable, the decision that matters — which recommendation becomes an
action, which action becomes the system — has to rest with something the agent cannot talk its way past.
That something is the environment, reaching in at one of the layers this chapter walks.

> *A footnote for the reader with a textbook nearby.* This departs from Russell and Norvig deliberately.
> For them an agent is anything that *perceives* through sensors and *acts* through actuators, and a
> rational agent acts to maximize an expected performance measure. That framing is the right one for
> *building* an agent. This book is about *governing* one, so it foregrounds a different property:
> controllability — behavior you can steer but not perfectly determine. The gap between controllable and
> controlled is no hedge. It is the reason the book exists.

<!-- point: governance-material-is-soft-conditioning-hard-authority-feedback | The material: soft conditioning, hard authority, feedback. | terms: soft-vs-hard-governance, governed-environment -->
<!-- index-def: engineered-agent-loop -->
<!-- index-def: loop-engineering -->
<!-- index-def: success-metric -->
The building material comes in three kinds. **Soft conditioning** aims the reasoner — prompts, briefs,
models, examples, playbooks. **Hard authority** binds it — tool interfaces, permissions, schemas, lints,
gates, validators. **Feedback** closes the loop — results made machine-legible, so the agent can repair
its own miss. Soft guidance goes in, deterministic guardrails constrain the actions, and a deterministic
envelope governs what gets admitted out. The three kinds say what a mechanism does; the four layers, which
come next, say where it can live.

<!-- point: alignment-is-the-move-from-guidance-to-obligation | A prompt aligns without creating authority; MAGE is the move from guidance to enforceable obligation. | terms: soft-vs-hard-governance, thesis-alignment -->
That split is the one this Part turns on. A prompt can align behavior without creating authority. MAGE is
concerned with the transition from guidance to enforceable obligation: the move from soft conditioning,
which aims the reasoner, to hard authority, which binds it.

Security practice draws the same boundary. Once agents act before commit time, the repository is too late
to be the security boundary — the tools, permissions, and execution environment that produce a change join
the trusted base, so agentic security must secure the process that creates the artifact, not only the
artifact [cite:snyk2026agenticlifecycle].

<!-- point: agent-stack-has-four-injection-layers | The agent stack has four layers, each an injection point. | terms: agent-stack, injection-point -->
<!-- index-def: agent-stack -->
If governing an agent means conditioning where it reaches, the question follows: *where do you reach in?*
Four places stack one atop another, each a different grip. Once you see the stack, every mechanism in this
book resolves into one move: pick a layer, inject a mechanism. [ref:stack-layers] draws it; this chapter
walks it from the bottom up.

## The four layers

<!-- section-terms: foundation-model, agentic-harness, engineering-environment -->

<!-- point: foundation-layer-spares-the-model-reasoning-cost | Tell the model where to look; spare its reasoning. | terms: foundation-model -->
<!-- index-def: foundation-model -->
**At the bottom sits the foundation model** — a general language reasoner from a vendor or an open-weight
release. It can *induce* an understanding of your environment, but that induction is expensive and happens
fresh every time. The grip here is to spare the model that cost: tell it, up front, where to look — with an
executable program, a written-down playbook, or a hybrid. Every re-derivation you hand it for free is one
it need not reconstruct. You run the model as it ships and steer it through what you place in its window,
not by bending its weights. (How far your system sits from what the model has already seen sets how hard
you must condition it — [a later chapter](5.1-the-problem-and-the-bar.html) treats that distance as the
novelty axis.)

<!-- point: the-window-is-packed-not-widened | The window is a bound you pack denser, not one you widen. | terms: context-window, thesis-modeling -->
<!-- index-def: context-window -->
The one thing you cannot change mid-task is the **context window**, the fixed token budget the model holds.
You do not widen it; you decide what meaning fills it — and a model packs more system per token. That is the
Modeling Thesis aimed at this bound, which Part 2 built in full.

<!-- point: harness-manages-the-context-window-and-holds-two-mechanism-points | The harness manages the context window and holds two mechanisms. | terms: agentic-harness, context-window, hook-hard-control, skill-soft-control -->
<!-- index-def: agentic-harness -->
<!-- index-def: skill-soft-control -->
<!-- index-def: hook-hard-control -->
<!-- index-def: tool-deterministic-action -->
**On top of the model sits the agentic harness** — the runtime that feeds prompts to the model, manages
the window, and compacts when it overflows. Two mechanism points live here, and the line between them is
sharp: a **hook** is a thing the agent *has* to do; a **skill** is a thing it *can choose* to do. A skill
carries soft guidance and, in its code half, a **tool** that lets the model take a *deterministic* action
instead of guessing; a hook runs a deterministic program before or after an action and can forbid it —
refuse an outbound call, block a send — or, run after the fact, log it. One aims; the other binds, at the
moment the agent acts.

Permissions harden the same layer: an alert-triage agent that can shift maintenance windows but cannot
create a cluster or touch networking has its blast radius bounded by its service-account permissions, not
by the quality of its prompt — the API just returns a clean 403 [cite:cockroachlabs2026agents].

<!-- point: engineering-environment-must-be-written-down-and-offers-git-and-ci-hooks | Write down the engineering environment; it offers git hooks. | terms: engineering-environment, injection-point, hook-hard-control -->
<!-- index-def: engineering-environment -->
**Above the harness sits the engineering environment** — the tools and conventions the team already uses.
Git holds the code, a tracker the tickets, named hosts the deploys; the standard procedures for a bug
report or an incident live here too. Engineers carry this in their heads; an agent arrives with none of it,
so for agents it *must* be written down. The injection point is concrete: git has hooks on every command,
and the classic one runs a fast quality check before a change enters the tree — feedback moved as far left
as it goes. Above that, CI is another set of stages where mechanisms attach.

> Learn more about this governance mechanism: [pre-commit hook](appendix-a-pre-commit-hook.html).

<!-- point: application-layer-makes-mistakes-structurally-impossible-via-static-analysis | Static analysis makes a mistake class structurally impossible. | terms: static-analysis, ban-lint -->
**At the top sits your application** — the product code, which carries governance of its own: models of how
it is meant to work, and static analyses that check the code against them. Here a whole class of mistakes
becomes structurally impossible. The catalogue's sharpest example is a **ban-lint that routes every
mutation of a document format through one structured model**, so no agent can reach the raw library and
corrupt a file. A protection seam is useful only if every relevant path actually crosses it — so the rule
sits at the one gateway every path must pass, and it holds for every agent that ever touches that code.

> Learn more about this governance mechanism: [one structured model per format](appendix-c-pdf-model.html).

## Softest to hardest

<!-- section-terms: injection-point, soft-vs-hard-governance -->

<!-- point: authority-sits-on-a-spectrum-from-soft-to-hard | Authority can be placed at any boundary, softest to hardest. | terms: injection-point, soft-vs-hard-governance -->
The four layers are not four strengths of grip; they are four *boundaries* at which the same intent can be
bound, at a chosen distance from the act. Read them as a spectrum. At the soft end, authority acts on the
agent's **reasoning** through the context you supply — it conditions a probability. Harden a step and it
acts on a **harness action** through a hook or tool; harden again and it acts on the **workflow** through
git and CI; at the hard end it acts on the **accepted artifact** through types and lints, where the wrong
output is not discouraged but impossible to write. [ref:authority-spectrum] lays it out. The lesson is not
that one boundary is best — it is that intent can be placed at any of them, and the placement decides how
binding it becomes.

Authority hardens left to right: context conditions a probability; a type makes the wrong artifact impossible to write. The same obligation can be attached at any of them. -->

## Every layer is a place to steer

<!-- section-terms: injection-point, agent-stack -->

<!-- point: read-each-layer-as-an-injection-opportunity | Read each layer as an injection opportunity. | terms: injection-point, context-window -->
<!-- index-def: injection-point -->
Read the stack as a list of opportunities, because that is what it is. The harness writing a reliable state
summary before a lossy compaction helps the model reconstruct less. The pre-commit hook catches a defect
while everything that produced it is still fresh in the window, not three compactions later. CI turning a
failure into a message the agent can read points it back toward the fix. Each layer, done well, narrows the
agent's search — the goal Part 1 named — and every mechanism you place there is structure the model would
otherwise induce on the fly, burning window on the rules of the road instead of the work. Autonomy wants to
sit amid its evidence-producing tools, "never limited by missing context or tools, but only by model
intelligence" [cite:ramp2026inspect].

<!-- point: mechanisms-interact-and-the-interplay-is-its-own-problem | Mechanisms interact; the interplay is its own problem. | terms: injection-point -->
One thing the stack does not show: the mechanisms you install do not act in isolation. Two that touch the
same thing at the same moment pull against each other and confuse the very agent they were meant to steer.
The interplay is its own problem, and it grows as the agents multiply — enough that managing the topology
*among* agents becomes governed infrastructure in its own right, lest unmanaged "agent sprawl" exhaust
resources and open security holes [cite:ericsson2026agentfabric]. [A later
chapter](3.5-when-guardrails-collide.html) takes the interplay up.

<!-- point: the-stack-grounds-both-theses | The stack grounds both the Modeling and Alignment theses. | terms: thesis-modeling, thesis-alignment -->
Governance is a posture at every layer, not one gate bolted on at the end. The stack is where the two
theses get their footing: a model handed to a layer enacts the Modeling Thesis; a hook or lint installed at
a layer enacts the Alignment Thesis. The stack gives the slots; it does not say what to put in them.

<!-- index-def: thesis-alignment -->
This is the Part's governing claim, stated whole. **The Alignment Thesis:** give engineering intent
authority over autonomous work by encoding obligations into authoritative mechanisms that constrain
actions, produce evidence, evaluate that evidence, and control admission. Where the Modeling Thesis makes
intent explicit, the Alignment Thesis makes that intent binding on what the fleet can do and what the
environment will accept. *In other words:* once you have decided how the system should behave, stop asking
every future agent to remember that decision — teach the environment to enforce it instead. The four verbs — constrain,
observe, evaluate, control admission — are the four mechanism archetypes this Part builds: Constraint,
Sensor, Validator, Gate.

The Alignment Thesis — authority installed at a layer rather than asked for in a prompt — is easiest to see
in systems already running it.

<!-- worked-examples: thesis-alignment -->
### Example — Docker
Docker places an agent's authority in the environment, not its instructions: the agent acts only through a
constrained tool seam, and the platform — not the prompt — decides what that seam permits. A move outside
the boundary is refused, not merely discouraged. It is the grip the stack names at the harness layer,
hardened into a permission the agent cannot talk its way past.

### Example — Zenseact
Zenseact's platform hands each domain team an agent that is little more than a config file and a skill,
while a central team owns the runtime, the permissions, and the context routing. Authority lives in a
per-tool, per-role permission table the environment enforces, so an agent's reach is a property of where
it sits in the platform rather than of how it was asked. The control sits at the engineering-environment
layer, one rung above the harness.

### Example — Spotify
Spotify's migration agents touch the code only through a restricted API and a narrow Git interface, and
every change must clear a merge gate fed by static linters and a semantic reviewer before it lands. The
gate, not the agent's confidence, admits the work. That is the Alignment Thesis installed at the top of
the stack, where CI decides what becomes the system.

### Example — DocAble
DocAble's sharpest alignment control is a ban-lint that routes every mutation of a document format through
one structured model, enforced at the application layer so no agent can reach the raw library and silently
corrupt a file. One rule at one gateway holds for every agent that ever touches that code. The same
posture recurs down the stack — a skill in the harness, a pre-commit hook in the environment — so the
authority is spread across layers, not concentrated in one.

<!-- takeaway -->
The shared move is the **Alignment Thesis**: authority placed in the environment at some layer of the
stack — a permission, a gate, a lint — so a probabilistic instruction becomes a control the agent cannot
opt out of.
