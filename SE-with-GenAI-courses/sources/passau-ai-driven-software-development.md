## A. Explicit course content (quoted / cited)

### Identity
University of Passau (Germany) · Faculty of Computer Science and Mathematics, Chair of Software Engineering II · module 5487 ("5487UE") · "AI-Driven Software Development" · first run summer semester 2025 ("we conducted it at the University of Passau in the summer semester of 2025 with 68 students participating"; "2 Bachelor, 66 Master"; 63 completed); repeated SoSe 2026 · instructors: Benedikt Fein, Prof. Dr. Gordon Fraser, Prof. Dr. Steffen Herbold ("Thanks to Marko Ivanković and Philipp Straubinger for contributing to the course ideation and design") · level: master's ("We evaluate the course concept at master's level with 68 students") · format: weekly 90-minute lectures + exercise sessions, then an individual project ("even though we ran two instances of the course in parallel to accept more participants, many more would have joined if possible") · taught in English (paper: "the course is taught in English"; participants "were international").

### Stated learning objectives
No enumerated objective list is published; the paper states the aim:
- "we need to educate our students not only in classical software development, but in the new paradigm of AI-Driven Software Development."
- "It becomes important that students are explicitly educated in the different approaches to AI tools and how these can be used to enhance different phases and tasks of software development. They furthermore need to understand the downsides and limitations of AI tools, and how to overcome them."
- "A central problem becomes how to grade the student's learning and critical thinking, not the generative capabilities of the LLMs they use."
- Conclusion: "the course indeed achieved its aim to teach students how to effectively use AI tools for software engineering."

### Organizing sequence
Two phases (Figure 1: "Weekly Lectures and Assignments" then "Independent Project"):
1. **Scaffolded phase — six interactive lectures**, one per classical SDLC step: "requirements engineering, prototyping, coding, unit and integration testing, system testing, and an overall quality-driven process (e.g., continuous integration with static analysis tools and automated tests, merge requests with code reviews)." In each lecture "we first introduce the tasks and outcomes and how they can be achieved using non-AI-based methods, to ensure students are familiar with core software engineering concepts," then "examples for AI-based tools suitable for the respective task" and "strategies on how to use the tool by highlighting potential challenges and how to overcome them." Each SDLC step is crossed with four AI-integration modes (Figure 1 rows): Chat, IDE, Agent, API.
2. **Independent final project — five weeks** ("in our case, end of June to end of July"), individual: build "a calendar application" (JVM server, browser-based UI) "over two iterations with changing requirements": "we publish additional requirements two weeks after the initial ones. The addition of new requirements also requires the AI tools to be able to support maintenance and evolution, rather than only generating the code of an initial prototype."

### Assignments and project structure
- **Weekly assignments (phase 1):** "the students are tasked to iteratively develop a small Todo-notes app" with "a JVM-based (e.g., using Java or Kotlin) server connected to a database and providing the API for a user interface developed using Java- or TypeScript running in the browser." Students choose their own features ("let them develop their own in the initial requirements engineering phase") so they "collect experience with their preferred tools in preparation for the final project."
- **Final project:** calendar app with specified initial functional requirements ("event creation/update/deletion, user management, reminders for events, recurring events, and tagging events with user-defined tags") which students "extend into full user stories with corresponding acceptance criteria before integrating them into their application." Changed requirements at the midpoint: three self-chosen features plus two specified features that "might contain subtle challenges for AI tools" (secure event-sharing links; per-user preferred time zones).
- **Process requirements:** "we require them to create issues in their GitHub project with descriptions in the user story format and task them to develop the application iteratively by small merge requests or commits that implement one feature or refactoring at a time. Furthermore, they should add unit and integration tests to both server and client of the system with at least 90 % statement coverage and develop automatic system tests that simulate the interactive interaction via the browser with the full application. They should add a CI pipeline to their project that verifies the feature integrity after each commit by running automatic tests, automatic linters (e.g., CheckStyle, ESLint), and static analysis tools."

### AI tools and agent frameworks used
- Demonstrated/provided: GitHub Copilot ("all students had free access via the GitHub students pack to GitHub Copilot both in the GitHub web interface and as plugin to their IDE"); the open-source agent aider with "a local instance of Ollama for API-based access to self-hosted LLMs like Mistral, Devstral, Llama 3.1, CodeLlama, and Gemma 3" on a university server; Playwright (Java API) for system tests; automatic code-review tools "like Copilot as integrated into the GitHub website and CodeRabbit."
- Free tool choice: "the students are free to also use other tools not presented in the lectures, including commercial ones like Cursor in case they already have a subscription."
- Observed usage (survey, n=40): models GPT-4o (29), Claude Sonnet 4 (30), Claude Sonnet 3.5 (13), Gemini 2.5 Pro (11), GPT-4o-mini (9); tools GitHub Copilot (30), Cursor (13), JetBrains Junie (6), aider (4). "Notably, all of these tools have agentic capabilities."

### Treatment of: conventional SE activities
Each lecture leads with the non-AI method: "we first introduce the tasks and outcomes and how they can be achieved using non-AI-based methods, to ensure students are familiar with core software engineering concepts." The course spine is the classical SDLC (requirements, prototyping, coding, unit/integration testing, system testing, quality process), and the conclusion argues this makes the design durable: "since the course is organised around core software engineering phases rather than AI aspects, the overall structure can remain stable" even as tools churn.

### Treatment of: human responsibility and judgment
- "while the AI can support many development tasks, the human developer ultimately needs to retain both control over the tools and an understanding of the developed system to be able to remediate issues in AI-generated work."
- Quality-process lecture: "while many tasks can be automated by AI, ultimately the developer still has to retain responsibility for the produced system and has to ensure consistency throughout the development process, e.g., consistency between user stories and user requirements, implementation and user stories, or expected and tested behaviour."
- Lecture demos deliberately show failure: "We use the demonstration to highlight that the LLMs may sometimes generate generic, too complex, or even nonsensical requirements. Similar demonstrations of limitations continue throughout all lectures."

### Treatment of: evaluation/verification of AI-produced work
- Testing is a graded backbone: unit + integration tests for server and client (rubric: ≥80 % coverage scores 3, ≥90 % scores 4), plus browser-driving system tests, plus a CI pipeline running "code formatters, linters, and the test suite so that core consistency and quality checks are always enforced even without AI support."
- Anti-vibe-coding by construction: "The high coverage requirement as communicated as part of the final project description can unlikely be achieved by 'vibe coding', but instead requires conscious use of AI tools to obtain tests for edge-cases."
- The report's paired sections "Where did the AI tools work well?" / "Where did the AI tools not work as intended?" require students to evidence both, with worked examples and adaptations; rubric level 4 requires "specific, well-explained examples where AI tools failed or underperformed" and how they "adapted their approach."
- Vibe-coding/verification issues taught explicitly in the coding lecture: "we focus on possible issues with a pure 'vibe coding' approach, e.g., the introduction of maintenance burden, subtle bugs, or security issues in the generated code due to even the original developer not fully understanding it. We then present prompt strategies to mitigate such issues."

### Treatment of: persistent engineering knowledge beyond source code
- Required issue tracker in user-story form, small PRs/commits referencing issues, and a report that "should link relevant issues, merge requests, or commits when explaining features or AI tool usage."
- "The development in self-contained steps is important because it allows both us and students to revisit the development process and allows the students to refer to the commit history in the report when describing how they used the AI tools."
- The graded report sections: "System architecture and design decisions," "Design decisions for custom features," "Used LLMs and AI-based tools," "Where did the AI tools work well?", "Where did the AI tools not work as intended?", "Missing AI tools (optional)."

### Treatment of: controls, constraints, governance, enforcement
- **Assessment model as the control:** "To assess student learning rather than the capabilities of LLMs, the grading is based not only on submitted code." Grading sums weekly assignments (0–2 each), final-project feature implementation (0–2 per requirement, verified executable "on our machines"), a five-subcategory development-process rubric (Issues, Pull Requests/Commits, CI Pipeline, Unit Tests, System Tests; 0–4 each; Table 1), and a five-subcategory report rubric (Table 2). "The grading for these two categories [assignments + features] is intentionally coarse and limited in points, since the work of the students and the AI is directly mixed. The main focus of the grading therefore is on the development process and the final report, since these are not directly the result of the AI, but instead show whether the students used a suitable AI-based process and then explicitly reflected on how they used the tools."
- Report grading rewards reflection over description: "the students achieve higher marks by showing a thorough reflection on why and how they made their design decisions and used the AI tools, rather than only describing what they used."
- Mandatory CI with linters/static analysis as a standing quality gate independent of AI.
- Budget governance: tools restricted to ones "available for free for all students, either by being open-source or by offering a special student discount"; self-hosted LLMs via a university Ollama server; "we had no budget to cover costly subscriptions and tokens for all students across multiple AI providers."

## B. Surveyor notes (interpretation, labeled)
- **Coverage gaps in the public record:** lecture slides, assignment handouts, and the module-catalogue entry are not public; learning objectives must be reconstructed from the paper's prose; no public course website or repo was found. The paper is unusually complete for assessment design (both rubrics printed in full) but thin on the lecture-by-lecture materials.
- **Organizing logic (interpretation):** the course is organized as a matrix — classical SDLC phases (stable axis) × AI-integration modes (Chat/IDE/Agent/API, volatile axis) — with the assessment deliberately displaced off the artifact onto process + reflection because "the work of the students and the AI is directly mixed." Of the courses surveyed, this is the most explicit published answer to the grading problem: grade the audit trail (issues, PR granularity, CI, coverage) and the student's calibrated judgment about the tools (paired worked-well/failed sections), not the code the AI can produce. The anti-vibe-coding move is structural (a coverage bar chosen to be unreachable without deliberate tool use) rather than policy-based.
- **First-run evidence (interpretation):** the evaluation (63 finishers; unit testing rated most AI-helped, system testing hardest with 54 % not implementing it; documented agent rewrite-loops and deprecated-API failures) functions as an empirical map of where student judgment is still required — the paper feeds this back as tool-design implications (agent 'modes', context indexing), which marks the course as also a research instrument.
