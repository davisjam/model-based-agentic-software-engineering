The engineering case

On 2 July 2019 Cloudflare deployed a new rule to its Web Application Firewall. The rule contained a regular expression whose matching cost grew explosively on some inputs. As the rule was evaluated against live traffic it exhausted CPU across Cloudflare's network, and for roughly 27 minutes the company's core proxy, CDN, and WAF services returned errors globally. The required reading is Cloudflare's own postmortem, “Details of the Cloudflare outage on July 2, 2019”.

Two things this page will not claim. (1) The outage was not an attack. The pathological rule was written and deployed by Cloudflare itself; no adversary was involved. The underlying algorithmic weakness is nevertheless exploitable as a denial-of-service vulnerability, which is exactly why it belongs in a security lecture rather than only a performance one. (2) The demonstration below does not reproduce Cloudflare's production behaviour. Different regex engines use different matching algorithms and different optimisations, and your browser's engine is not the one Cloudflare was running. What the demonstration reproduces is the same class of algorithmic vulnerability. Cloudflare supplies the real engineering case; the browser supplies a real measurement of the class.

The expression, before the outcome

Work through the construct before reading what happened. The postmortem identifies this fragment inside the much larger rule:

.*(?:.*=.*)

Two unbounded .* repetitions in sequence, with nothing between them that forces a unique division of the input. When the overall match fails, the engine must try the ways of dividing the text between them before it can conclude failure. Predict which inputs are expensive before you run anything.

The same shape appears in Experiment 2 below, in a smaller expression you can read in one glance: /^.*\s+$/ — an unbounded .* followed by an unbounded \s+, with no forced division between them.

Experiments

The four experiments form a 2×2. Experiments 1 and 2 run the same expression on different inputs, so the only thing that changes is what the adversary supplies. Experiments 2 and 4 run different expressions on byte-identical input, so the only thing that changes is what the engineer wrote. Holding one variable fixed at a time is what makes each comparison an experiment rather than an anecdote.

Why a worker, and why that is not enough

The match runs in a Web Worker, on its own thread, so the interface stays responsive while the engine is occupied. Watch the frame counter during an expensive run: it keeps climbing.

A worker does not make an expensive regular expression interruptible. There is no way to ask a matching engine to stop. So the page keeps a wall-clock timer the matching thread cannot block, and when a run overruns the deadline the page destroys the worker and creates a fresh one for the next experiment. Destroying it is the only available remedy, and the counters above record how often it was needed.

Note what this does and does not buy. Moving the computation into a worker protects the interface; it does nothing to make the regular expression efficient. The same holds for the server-side analogue in the mitigation list below: isolating the match bounds the damage, not the cost.

Measured execution time

Choosing the axes is part of the analysis. On a linear axis a quadratic curve and an exponential one both just look “steep”. On log y an exponential series straightens into a line, because each extra character multiplies the work by a constant. On log–log a polynomial series straightens, and its slope is the exponent — a slope near 2 is quadratic, near 1 linear. Running all four experiments also puts two input ranges three orders of magnitude apart on one axis; log–log is the mode that shows both at once.

Why the work grows — a model of backtracking

This is a conceptual model of backtracking, not a trace of your engine. It enumerates candidates a backtracking matcher could be obliged to consider. The actual engine may optimise some away, order them differently, or never attempt them at all — and V8, SpiderMonkey, and JavaScriptCore do not agree with each other about which. The threat model

The measurements above are a performance observation. What makes this a security finding is that the expensive input is chosen by someone else. Name the elements:

Model elementReDoS example

A threat is a possible course of harmful action; a vulnerability is the weakness that may let it succeed; an attack is an attempt to exploit that weakness. Here the vulnerability is superlinear matching, the threat is resource exhaustion, and the attack is one HTTP request carrying a long run of spaces.

The distinction from Performance Engineering. A performance model assumes a service-time distribution chosen by the engineer — the Performance Knee simulator asks what happens when many ordinary requests compete for finite capacity. This demonstration shows an adversary influencing that distribution by selecting inputs. Experiments 1 and 2 differ in nothing an engineer controls: same expression, same code path, same deployment. Only the input changed.

Choose a mitigation

The security objective is bound computation per request. Select what you would do, then read how the selection is judged against that objective.

Using this in class — the intended sequence
  1. Read the Cloudflare postmortem. A real outage, at a company whose core competence is operating this kind of infrastructure. Establish that the question matters before introducing any synthetic expression.
  2. Examine the regular expression. Find .*(?:.*=.*) in the rule. Two unbounded repetitions in sequence, nothing forcing a unique division between them.
  3. Predict. Which inputs are expensive, and why? Commit to an answer before measuring. The prediction is the part that is graded by the measurement.
  4. Run the demonstration. Experiments 1 and 2 first, because they isolate the adversary's variable. Then 3, for what a nested quantifier costs. Then 4, which is the fix, on byte-identical input to 2.
  5. Identify the threat. Fill in the threat model: who supplies the input, through which entry point, and what resource is exhausted.
  6. Propose controls. Choose mitigations and defend the choice against the objective — including why a rate limit is not sufficient on its own.

Exercises

  1. Experiments 1 and 2 run the same expression. Experiment 1 is fast. Explain the difference using the structure of /^.*\s+$/ and the structure of the two inputs — not the measured numbers.
  2. Set the time axis to log–log and read the slope of experiment 2. What value would you expect from n(n+1)/2, and does your run agree? If it does not, name a reason that is about the engine rather than about the expression.
  3. Experiment 3 runs out of budget somewhere in the twenties. Each extra character doubles the modelled work. If a service capped its input at 100 characters, would that cap bound the cost for experiment 3? For experiment 2?
  4. Experiment 4 decides exactly the same question as experiment 2 on exactly the same bytes. Read both expressions and say which construct removed the cost.
  5. The page runs the match in a worker and destroys it at a deadline. Name what that protects and what it does not. Then say which of the two the server-side analogue protects.

The engineering question to leave with

What input can an adversary control, and what resource can it exhaust?

Asked of every component that accepts input from outside the trust boundary, this question finds algorithmic complexity vulnerabilities well beyond regular expressions: parsers, decompressors, hash tables, sorting, image decoders, and anything whose cost depends on the shape of its input rather than only on its size.

About this instrument

What it measures

Each experiment runs one curated regular expression against generated inputs of increasing length, using the browser's own RegExp engine, and reports the measured execution time. Nothing here plots a theoretical complexity curve and calls it a measurement: the numbers come from running the matcher. The model of why the numbers grow is reported separately and labelled as a model.

Fixed, curated patterns. The page executes no user-supplied expression.

Correctness of the curated patterns

A demonstration that mis-states what its expressions mean teaches the wrong thing, so the match behaviour is pinned rather than asserted in prose. Each expression is checked against a table of small inputs, and the safe alternative is checked for exact language equivalence with the pathological expression by exhaustive enumeration of short strings — the claim “same decision, far less work” is only worth making if it is true.

Self-tests

The engine carries its own suite so the instrument can be checked in the room it is being used in. The repository's Node suite under course/interactive/redos/tests/ extracts this page's engine script element and evaluates it, so the tested code and the shipped code are the same text.
