Changing parameters while running. A change to λ affects future arrivals only — the arrival already scheduled is not regenerated, and no past arrival is altered. A request already in service keeps the completion time it was given; only requests that start service afterwards use the new μ or the new service distribution. Setting λ = 0 cancels the pending arrival: at rate zero there is no arrival process.

This chart answers a different question from the one beside the queue: not what happened but what does the model predict at every load? It is a static curve. It moves only when you change μ or the service-time distribution — changing λ just slides the vertical marker along it.

A precision point worth insisting on. Strictly speaking there is no mathematically distinguished knee in this curve. Response time diverges as utilization approaches 100%; the curve is smooth, and every point on it has a well-defined slope. “The knee” is an engineering choice, not a mathematical feature. Engineers pick an operational threshold from latency requirements and workload variability — which is why Experiment 2 asks you to look for a universal threshold and then explains why you will not find one.

Little's Law

L = λW — the time-average number of requests in a system equals the rate at which they pass through it times the average time each one spends in it. It is a general relationship among occupancy, throughput, and response time. It assumes no particular arrival process, no particular service distribution, and no particular queue discipline.

Little's Law does not predict the knee. It is an identity, and it holds just as well at ρ = 0.1 as at ρ = 0.99. What predicts the sharp rise in response time near capacity is the queueing model — M/M/1 or M/D/1 — which adds assumptions Little's Law does not make.

The consistency check, computed over a compatible window

A finite measurement window breaks the naive arithmetic: requests that arrived before the window opened, or that are still in the system when it closes, contribute to one side of L = λW and not the other. The resulting mismatch is a window artefact, not a violation of the law. So the check below is computed over an empty-to-empty cohort: an interval that begins and ends with the system empty. Every request counted arrived and departed inside it, so the identity holds exactly — the residual you see is floating-point noise and nothing else.

Classroom experiments

Five short experiments. Each one asks you to predict first. The explanations are deliberately hidden until you ask for them — reading the answer before running the experiment converts a prediction task into a recall task.

1. Predict utilization

Set up: λ = 30, μ = 100, exponential service.

  1. Before running: what fraction of the time will the server be busy? Write it down.
  2. What will the mean response time be? Is it more or less than the mean service time 1/μ = 10 ms?
  3. Run for at least 60 simulated seconds and compare against the measured utilization.
Reveal explanation

Utilization is ρ = λ/μ = 0.30. The server is busy 30% of the time. Notice what this does not say: it says nothing about response time. The model predicts W = 1/(μ−λ) = 1/70 s ≈ 14.3 ms, which is already 43% above the 10 ms service time even at a load most engineers would call comfortable. Queueing delay is not something that switches on at some high load; it is present at every positive load and merely small here.

2. Find the knee

Set up: μ = 100, exponential service. Step λ through 50, 70, 90, 95, 99.

  1. Record the predicted and observed mean response time at each setting.
  2. By what factor does response time grow from ρ = 0.5 to 0.9? From 0.9 to 0.99?
  3. Is there a universal utilization threshold above which performance is unacceptable?
Reveal explanation

W = 1/(μ(1−ρ)). At ρ = 0.5, W = 20 ms; at 0.9, 100 ms; at 0.99, 1000 ms. Each halving of the headroom 1−ρ doubles the response time. The growth is driven by the headroom, not by the utilization figure itself.

There is no universal threshold. The curve is smooth and has no distinguished point — no inflection, no discontinuity, no maximum of curvature that survives a change of axis scaling. “70% utilization” is a rule of thumb, not a property of queues. The threshold you should choose depends on your latency requirement, how variable your service times are (compare Experiment 5), and how much your arrival rate fluctuates. An engineer who quotes a universal number has substituted a slogan for the model.

3. Exceed capacity

Set up: λ = 110, μ = 100, exponential service.

  1. Run at 100× and watch the queue length and the response-time chart.
  2. What does the model predict for mean response time? Why does the panel refuse to print a number?
  3. The utilization measurement approaches 1.00 but never exceeds it. Why is offered load ρ = 1.10 not the same thing as utilization?
Reveal explanation

With λ > μ there is no steady state. The queue does not settle around some large average; it grows without bound at approximately λ − μ = 10 requests per second. Mean response time is not large — it is undefined, because the limit the mean would be taken over does not exist. Printing a big number here would be a lie dressed as a measurement, so the panel prints the reason instead.

Offered load and utilization are different quantities that coincide only when λ < μ. Offered load λ/μ can be any non-negative number; utilization is a fraction of time and cannot exceed 1. A saturated server runs at utilization 1 and throughput μ, not throughput λ. The excess λ − μ goes into the backlog, which is exactly why the real-world symptom of overload is growing latency rather than falling throughput.

4. Restore capacity

Set up: run Experiment 3 until the queue has several hundred requests in it, then raise μ to 150 without resetting.

  1. Before pressing the second button: note the queue length N. How long should the backlog take to drain?
  2. Run and time it. Compare with your estimate.
  3. Once the queue has drained, what is the mean response time — and why is the measured mean still far above the model's prediction?
Reveal explanation

While the backlog drains, the system removes work at μ and receives it at λ, so it shrinks at μ − λ = 40 requests per second. A backlog of N requests therefore takes about N/40 seconds. With N = 600 that is 15 seconds — a fast recovery, and a useful number to be able to produce on a whiteboard during an incident.

Afterwards the system is stable at ρ = 110/150 ≈ 0.73, so the model predicts W = 1/40 s = 25 ms. The measured mean stays far higher for a long time because it still averages in the enormous response times of requests that queued during the overload. This is the measurement-window problem in its most practical form: a mean over a window that spans a regime change describes neither regime. Press Reset after recovery, or use a warm-up, and the measurement converges on the prediction.

5. Change variability

Set up: λ = 90, μ = 100 (ρ = 0.9). Compare exponential and deterministic service times.

  1. Both settings have the same mean service time, 10 ms, and the same offered load, 0.9. Predict the two mean response times.
  2. Run each for at least 200 simulated seconds and record the measurements.
  3. Why does identical mean service demand not imply identical latency?
Reveal explanation

M/M/1 predicts W = 100 ms. M/D/1 predicts Wq = ρ/(2μ(1−ρ)) = 45 ms, so W = 55 ms. Removing service-time variability cuts the queue wait exactly in half (90 ms → 45 ms) while the mean service demand is unchanged.

Queueing delay is produced by variability, not by average demand. A long service time delays everything behind it, and under an exponential distribution long services are common enough to dominate the average wait. Pollaczek–Khinchine makes this precise: Wq scales with the second moment of the service distribution, so halving the coefficient of variation to zero halves the wait. This is the modelling reason that reducing tail latency — making slow requests less slow — often buys more than adding capacity, and it is invisible to anyone reasoning only about averages.

Changing the seed or the warm-up resets the run — both are properties of the whole experiment, not of a moment in it. The display settings (max displayed requests, chart history, reduced motion) touch only rendering and never the simulation.

Not offered, deliberately. Finite queue capacity, admission rejection, client timeouts, and retry policy belong to the Reliability lecture's extension of this same instrument. The engine already distinguishes a logical request from a physical attempt and reserves a timeout event kind in its ordering policy, so retries can be added without rewriting the queue. Controls for mechanisms that are not implemented are not shown, because a knob that does nothing is worse than a missing knob.

About the models, the engine, and this page

Three different things, kept apart on purpose

WhatStatementWhat it does and does not do
Little's Law L = λW A general relationship among average occupancy, throughput, and response time. Needs almost no assumptions. Does not predict the knee, and cannot: it has no notion of capacity.
M/M/1 W = 1/(μ−λ), λ<μ Predicts how mean response time rises as utilization approaches capacity. Assumes Poisson arrivals, exponential service, one server, FCFS, unlimited waiting room.
Simulation the event trace Empirical evidence about those predictions, under assumptions you can violate on purpose to see what breaks.

Little's Law relates throughput, latency, and concurrency. Queueing theory predicts why latency rises near capacity. Simulation shows what those relationships mean for an operating system.

How the engine works

  • Discrete-event, not frame-based. The engine advances from one event to the next in nondecreasing simulation-time order. Simulated time is wholly independent of wall-clock time: the 1×, 10×, and 100× speeds change only how much simulated time each animation frame is asked to cover, so the same seed produces the same event trace at every speed. Rendering observes the state; it never determines it.
  • Tie-break policy. Events at an identical timestamp are processed in the order service completion → timeout → arrival. Completion first means a request never queues behind a server that is, at that same instant, becoming free. The timeout rung is reserved for the Reliability extension and is never scheduled here; it is in the ordering now so that adding it later cannot silently change the trace of a scenario that does not use it.
  • Seeded randomness. A 32-bit mulberry32 generator; Math.random is not reachable from the engine. Arrivals and service times draw from two independent streams, so changing μ cannot perturb the arrival sequence. Deterministic service consumes no random draw at all, which is why switching the service distribution leaves the arrival trace untouched.
  • Interarrival times. Δt = −ln U / λ with U uniform on the open interval (0,1), so every sample is strictly positive and finite. λ = 0 is handled explicitly: no arrival is ever scheduled.
  • Queue discipline. FCFS, one server, unlimited waiting room. Nothing is discarded, ever. There is no loss, no balking, and no admission control in this version.
  • Statistics. Before each event at time t the engine accumulates N(t⁻)·Δt into the occupancy integral and the busy indicator into the busy time, then advances the clock. Utilization is busy time over observation time. Throughput counts completions, not offered arrivals.
  • Falling behind rather than skipping. Each frame has an event budget. At extreme settings the simulated clock advances more slowly than the requested multiple of real time, but no event is ever dropped or reordered to keep up.

Keyboard

Space run / pause · S step one event · R reset · D defaults. Every control is reachable with Tab; sliders respond to the arrow keys, Home, and End. The shortcut keys stand down while a text field or <select> has focus, so typing a value never starts the simulation.

Accessibility

No state is signalled by colour alone: the stability badge carries a word and a glyph as well as a colour and a border style, the backlog-preserving preset is marked both by a dashed border and by the words “keeps backlog”, and the three chart series are distinguished by dash pattern (dots, solid, dashed) as well as by hue. Each canvas is exposed to assistive technology as an image with a live text description of what it currently shows. A reduced-motion mode is offered under Advanced and is switched on automatically when the operating system asks for it.

Running the model from the console

The engine is a pure module published as window.QueueSim with no DOM dependency: createSimulation, advanceSimulation, calculateMM1, calculateMD1, and runSelfTests, plus the event-ordering policy and the preset table. The repository's test suite under course/interactive/performance-knee/tests/ extracts this very script element from this very file and evaluates it in Node, so the tested code and the shipped code are the same text. Nothing in the interface depends on the test harness.
