What the cache is. “Cache on” means an ORM identity map or application cache that remembers a room within this request: the first access to a room issues a query, and every later access to the same room is served from memory. It starts empty on every page load, so nothing is carried over between configurations. It never changes which rooms the loop needs — all three strategies return the same reservations and the same room names.

Classroom presets

The first preset is the configuration the lecture notes describe. Step through the rest in order: each one changes exactly one decision, and the last one is the counter-example — a cache that cannot help.

The application code

This is the whole program. It does not change when you change the strategy or the cache — there is one version of it, and it is the same text under every configuration. 

reservations = load_reservations()
for r in reservations:
    print(r.room.name)

All four configurations, same N, D and latency

  

  

  

    All four return the same reservations and the same room names. Nothing here is a correctness
    difference. Eager usually wins on time and loses on bytes: a join repeats the
    room columns on every reservation row, while the batched query sends each room once. Which of
    those you care about depends on where the constraint is.
  







  
The cost model, in full

  

    Nothing on this page executes SQL. There is no database, no connection, no engine, and no
    measurement. Every number is computed from the constants below, which is why the same controls
    always produce the same answer. The query counts are exact arithmetic; the
    times and byte counts are a model, and a real engine would differ.
  


  
Query counts — exact

  

    
StrategyCacheQueriesWhy

    
      
LazyOff1 + N
          One query for the reservations, then one per reservation. Nothing remembers that two reservations share a room.

      
LazyOn1 + Deff
          One query for the reservations, then one per distinct room. Later accesses to a room already loaded are served from the identity map.

      
Eagereither1
          A single join returns reservations and their rooms together. The cache changes nothing: the room columns already arrived.

      
Batchedeither2
          One query for the reservations, then one WHERE id IN (…) for the rooms the loop will need.

    
  

  

    N+1 is a consequence of a configuration, not a property of lazy loading. Lazy
    loading executes N additional queries only when every room access misses. Set the cache on and
    point 200 reservations at 10 rooms and lazy loading issues 11 queries. Point them at 200
    different rooms and the cache cannot help: 201 again. The exercise is to find that boundary
    yourself.
  


  
Deff — the clamp, and why there is one

  

    A reservation references exactly one room, so N reservations can reference at most N distinct
    rooms. When the distinct rooms control exceeds the reservation count, the model uses
    Deff = min(D, N) and says so above the results rather than reporting a
    configuration that cannot exist. Your control keeps the value you set.
  

  

    Reservations are assigned to rooms round-robin — reservation i takes room
    i mod Deff — so every distinct room is used and the assignment is
    deterministic. The assignment changes which accesses miss, and therefore where the
    misses sit on the timeline. It does not change how many there are: with the cache on, each
    distinct room is fetched exactly once however the reservations are spread.

    What the model leaves out, stated so it is not mistaken for a benchmark: no
    connection-pool waiting, no lock contention, no index choice, no concurrency, no network
    variance, no server-side caching between requests, and no application CPU. Response time here is
    round-trip overhead plus database processing, nothing else. A real system has all of those, and
    this page would mislead anyone who read its milliseconds as a prediction about one.
