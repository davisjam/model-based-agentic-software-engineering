The Release Factory

Delivery policies, release risk, and the Four Keys — an interactive experiment.

Engineering problem How do the engineer's release policies affect delivery performance and the consequences of defects?

Five policies govern this factory and each trades something away: deeper testing buys evidence with delay, a blocking gate buys correctness with throughput, a larger batch buys fewer releases with a wider blast radius.

Model assumptions

  • Every probability and duration is an illustrative simulation assumption, not a measured industrial value. Defect rate, coverage factors, rework hours and monitoring quality are printed on this page and chosen for teaching.
  • This instrument measures delivery performance and release risk. Its four measures are the Four Keys — deployment frequency, lead time for changes, change failure rate, time to restore service — the four the course reading names, and not an account of current DORA measurement practice, which has moved on.
  • They describe selected outcomes of the delivery process. They do not establish whether the organisation is producing valuable or correct software. A factory can ship ten times a day, restore in minutes, and build the wrong thing perfectly.
  • Changing a policy resets the factory, and the seed does not change. The same team commits the same changes carrying the same defects, so switching one policy is a controlled experiment rather than a fresh draw.

No figure here measures any real organisation. Read each comparison as the consequence of a stated model — and argue with the model.

The factory’s policies

Your experiment

  1. 1 · Predict With changes arriving 44 a day, write down what you expect thorough testing behind a required gate to do to deployment frequency and to change failure rate — and which of the two you expect to move more. Commit it before you run.
  2. 2 · Run Run 90 days on the defaults. Then change exactly one policy at a time: test depth to smoke, admission to advisory, strategy to canary, batch size to 10. The seed is unchanged across resets, so each run is the same team committing the same defects.
  3. 3 · Explain Which policy moved delivery performance, and which moved the consequences of a defect — users exposed, time to detect, time to restore? Name one policy that improved a Four-Keys measure while making the factory worse, and say what you would recommend.

Work in the factory, over time (observations)

Three series, each labelled on the chart and drawn with its own line style, so the picture reads without colour. A queue that climbs and never comes back down is a stage past its capacity — the same shape as the Performance Knee simulator’s response-time curve, in a release pipeline instead of a server.

The defect ledger — five separate events

A defect is tracked as five events, never collapsed into one: introduced, detected before release, exposed in production, detected after release, service restored. Two rows sit beside them because collapsing those would hide a policy: the tests’ signal is recorded separately from the gate’s block (so an advisory policy is visible as a signal that shipped anyway), and a defect removed by someone else’s rollback is counted as removed, not restored — nobody ever knew it was there.

Hold capacity fixed, raise the arrival rate

Step 4 of the experiment, measured rather than asserted: the same policies, the same two build–test lanes and one release slot, run independently at each arrival rate on the chart. Every point is a full seeded simulation.

The sweep holds everything except the arrival rate, including the seed offsets, so the curve is a function of load alone. A pipeline has two capacities — the build–test lanes and the release channel — and whichever one the policies make scarcer is the one that bends first. A one-hour canary soak at one change per release caps the factory near twenty-four deployments a day however fast the tests run.

Two things to read carefully. The curve usually bends well to the left of the dashed capacity lines, because those lines count only the first pass through each stage: a rollback sends its whole batch back, so a factory that fails often spends real capacity recovering from itself. And beyond the knee the measured lead time flattens — an artefact, not a recovery. A queue past its capacity has no steady state, so the average wait is bounded by how long the simulation ran. Run each point for longer and the right-hand side keeps climbing. In an unstable system, the number you measure depends on how long you watch.

Classroom experiments

1 · Thorough tests, required checks, immediate deployment

Load preset 1 and run to about thirty days. Changes arrive at forty-four a day; a thorough suite takes two and a half hours and there are two lanes, so the stage can serve about nineteen a day.

What to look for

The build–test queue climbs without bound and the mean lead time runs into weeks. No single change is slow; the queue is. Utilisation reads above two, and the state badge says ▲ over capacity in words as well as colour.

Notice what the Four Keys say about this factory. Change failure rate is low and time to restore is fast. Two of the four measures look healthy while the organisation cannot ship.

2 · Reduce the test depth

Preset 2 changes one control: standard tests instead of thorough. Everything else is identical, and the seed is the same, so the same changes arrive carrying the same defects.

What to look for

Lead time collapses from weeks to hours and deployment frequency triples: the stage now serves about sixty-nine changes a day against forty-four arriving. That is the whole case for a shallower suite.

Now read the ledger. The signal rate falls from about 59% of defects to about 45%, so more defects reach users — and requests exposed per day rises by roughly an order of magnitude. The cost did not disappear; it moved from the pipeline to production, where the people paying it are users rather than engineers.

The honest reading of step 1 versus step 2 is not “shallower is better”. It is that the two configurations spend the same risk in different currencies.

3 · Enable the canary

Preset 3 changes one control again: a canary at five per cent of traffic, soaked for an hour, before the whole fleet.

What to look for

Four things move, and they do not move together.

  • Change failure rate barely changes. A canary does not stop a deployment being classified as failed — real users were exposed, and the rollback happened.
  • Median exposure per failed deployment falls by a large factor — roughly the traffic share. This is the consequence a canary actually buys, and it is why the fifth measure is on the page at all.
  • Lead time rises, because every release now holds the release channel for the length of its soak.
  • Some defects are caught inside the soak and some are not. The ledger splits them: caught in the canary versus reached the whole fleet.

Nothing in the model says a canary helps. Detection in production is a Poisson process whose rate is affected requests/hour × distinguishability × monitoring quality; a canary lowers the first term by the traffic share, so the chance of catching a defect inside the soak is 1 − e−rate × soak. Try the Obvious defects only and Rare defects, quiet service presets back to back: the first makes the canary look like a triumph, the second like a tax. Both are the same code.

4 · Hold capacity fixed and raise the arrival rate

Preset 4 keeps step 3’s policies and raises arrivals to a hundred and twenty changes a day. Then run the sweep above.

What to look for

Lead time does not rise in proportion to the load. It is flat, then it bends, then it runs away — a release pipeline develops its own performance knee, for exactly the reason a server does: arrivals are random, service takes time, and a queue in front of a stage near its capacity grows faster than the load that feeds it.

This is the bridge to the Performance Knee simulator and to the agentic-software-factory lecture. If an agent fleet raises the arrival rate tenfold and the pipeline’s capacity is unchanged, the fleet has not made the organisation faster. It has made the queue longer.

5 · Make the checks advisory

What to look for

The ledger now shows a gap between two rows that were previously identical: the tests signalled a defect and the change shipped anyway. That gap is the policy. Required checks close it and charge for it in lead time — including on the changes that were never broken, because a flaky suite blocks those too.

6 · Ten changes per release

What to look for

Deployment frequency falls, lead time rises — and the change failure rate rises with them, because the rate is computed per deployment. A release carrying ten changes fails if any one of them does. The same defects, the same tests, a worse-looking metric: the denominator moved.

Blue-green makes the batch cost concrete. A verification failure holds the whole batch, so one bad change delays nine good ones.

Advanced controls

Everything the five primary controls hold fixed. Changing any of these resets the factory.

Warm-up excludes the first days from every aggregate. It is zero by default and that is deliberate: a factory past its capacity has no steady state to warm up into, and hiding the transient would hide the finding. Raise it when you want a settled measurement of a configuration that settles.

About the model, the engine, and this page

What the model is

A seeded discrete-event simulation of one delivery pipeline. Changes arrive as a Poisson process; each is tested in one of a fixed number of lanes; an admission policy decides whether a failing change proceeds; admitted changes are batched into releases; a release strategy decides how the batch meets users; production monitoring may notice a defect, after which the release is rolled back and its changes return through the pipeline.

Every number on this page comes from that one engine. Nothing is a lookup table, and no outcome is predetermined — which is why two policies can swap places when you change the defect population or the traffic volume.

The five events, and why they are kept apart

A defect is an object with its own lifecycle. Collapsing any two of these would make a policy question unanswerable:

EventFires whenWhat it lets you ask
1 · introduceda defective change is committed how many defects does this team produce?
2 · detected before release a pre-production control found it and the change did not ship what did the gate actually keep out?
3 · exposed in productionthe change first served real traffic what reached users, whatever the tests said?
4 · detected after releasemonitoring or a user report noticed it what did we find, and how fast?
5 · service restoredthe rollback finished how long did users carry it?
signalled by teststhe suite failed on this defect the signal, separate from the block — which is how an advisory policy becomes measurable
removed from production a rollback triggered by a different defect took it away not a restoration: nobody knew it was there

Events 2 and 3 are mutually exclusive. Event 4 implies event 3. Event 5 implies event 4. A defect can be exposed and never detected, in which case it is never restored and never appears in the change failure rate. The test suite checks every one of these on every release strategy.

How a defect behaves

Each defect draws three attributes from a four-class mixture at the moment it is committed, independently of every policy. The classes are teaching-scale assumptions, not measurements of any real population, and they are printed here so you can see what the simulator believes:

ClassShareTest detectability Manifests onDistinguishableCharacter

Test detectability is the probability a fully thorough suite signals it. The configured depth multiplies that by a coverage factor — and the deepest suite's factor is 0.92, not one, so thorough testing never eliminates all defects. There is no branch anywhere that sets the escape probability to zero.

Detection in production

Detection is a Poisson process. Its rate is built from affected traffic, not from the release strategy: 

affected/hour = requests/hour × exposed fraction × manifest rate

rate = affected/hour × distinguishability × monitoring quality   (instruments)
     + affected/hour × reports per affected request                  (bug reports)

So the chance of catching a defect inside a canary soak of length S is 1 − e−rate×S. A canary enters only through the exposed fraction. That is the whole of its effect, and it is why the answer depends on the defect: at twenty thousand requests an hour a defect manifesting on 30% of them is caught in the soak essentially always, and one manifesting on 1 request in 100,000 essentially never. Nothing hard-codes that a canary improves the change failure rate.

The bug-report channel is proportional to affected users rather than a flat background rate, because a user can only report what they experienced. A flat rate would quietly guarantee that every defect is eventually found, which would delete the “exposed but never detected” case the model exists to show.

Blue-green verification uses the same defect attributes against a fixed number of synthetic requests, so it misses a rare defect for the same reason a canary does — not enough requests exercise it. What it does differently is expose nobody while it looks.

How the four measures are computed

MeasureDefinition used here
Deployment frequency releases that reached real users, per measured day. A blue-green release aborted at verification never reached users, so it is not a deployment.
Lead time for changes first commit to first arrival in production, including any rework. One observation per change: a rolled-back change shipped again does not produce a second, or the mean would depend on how often the factory fails.
Change failure rate failed deployments ÷ deployments — not changes. A deployment fails if a defect it carries is detected in production.
Time to restore service detection to rollback complete. The clock starts when somebody noticed, not when the defect was exposed.
User impact requests served by a defective release while it is live, integrated over the exposed traffic share. Reported as a total, a per-day rate, and the median per failed deployment — the last because the total is dominated by the long tail of slowly-detected defects, so a canary moves the median far more than the mean.

What is deliberately not modelled

  • Feature flags. They decouple deploy from release, which would need a separate exposure control; the 3-1 lecture covers them and this instrument does not.
  • Partial rollback. A rollback here reverts the whole batch.
  • Supersession. A later release does not fix an earlier defect, so an undetected defect keeps accruing exposure until somebody finds it. That is deliberate: it is the honest answer, and it is where most of the user impact comes from.
  • Dependencies between changes, review time, and anything about whether the change was worth making.

Reproducibility

The engine is a pure module published as window.ReleaseFactory with no reference to the page. It uses six independent seeded generators — arrivals, defect attributes, rework regressions, test verdicts, durations, production detection — and no unseeded random source and no clock, so the same seed and parameters replay the same event trace exactly, and switching one policy leaves the others’ draws where they were. Its test suite extracts this element from the published file, so the tested code and the code you are running are the same bytes.
