The Architecture Workbench

One reservation service, three candidate structures, and a cost model whose implementation term you can drive to a hundredth.

Teach with MAGE
ECE 30861 · Act III
(Agentic) Technical Debt, Architecture and Dependencies

Engineering problem When implementation becomes cheap, which architectural boundaries remain worth maintaining?

The campus reservation service works, and the university now wants laboratory reservations with their own approval and booking policies. A coding agent makes any of the three structures below cheap to write, and makes establishing that the result still satisfies the system's obligations no cheaper at all. Which term decides is the exercise.

Model assumptions

  • One reservation application, six components at most, one new requirement.
  • Must-modify is an assumption each scenario declares per architecture: stated, not derived from the graph, and not measured.
  • Potentially impacted is derived — a dependency path exists, towards dependents (a moved interface may reach a caller) or towards dependencies (the change may need something new). A path makes an effect possible, never certain.
  • Costs are unitless points, so only ratios mean anything; future changes are expected counts, not rates. The multiplier scales implementation only, the assurance level validation only.

The cost estimates are illustrative. Graph structure alone does not predict change cost. Nothing on this page was measured, and no figure here describes any real system. Wherever a number below comes from an assumption it is written in this ochre — ▲ assumed — so an assumed cost never reads like a measured one.

Two further controls sit lower down: the change scenario, which selects the question the impact panel answers, and the architectural rules, which you edit to state what the structure must permit or prohibit.

Your experiment

  1. 1 · Predict For twenty future policy changes and one engineer, which of the three structures costs least? Now answer again for implementation a hundred times cheaper. Commit both before you read a number — the three conditions in The experiment below stay locked until you do.
  2. 2 · Run Hold the horizon fixed and move the implementation multiplier from 1× to 0.01×. Put it back, and move the assurance level instead. Then switch the scenario to Change the persistence mechanism and compare the must-modify counts across the three architectures.
  3. 3 · Explain Which control moved the ranking, and which only moved the totals? Extracting services never leads on modelled cost here — find what does make it the answer, and say whether that is an economic argument or a requirement. What would you recommend to the engineer, and what measurement would change your mind?

Architectural obligations

  

    An architecture is not what a diagram shows; it is what the system is held to. State the
    obligations as rules, then read whether the selected structure satisfies them. Introduce a
    violation deliberately and watch the graph mark it.

Obligations a dependency rule cannot settle

      

      

        Three of the five obligations are invisible to topology. A graph can show that
        LabPolicy does not reference RoomPolicy; it cannot show that both preserve
        the reservation invariants, that neither mutates shared state without coordinating, or that
        two independently deployed services tolerate each other's versions. Those need tests and
        review. Reading a clean rule report as a clean architecture is the error this panel exists
        to prevent.

What this instrument does and does not establish

  
    
    
  • It does not predict change costs from topology. The costs are declared
      coefficients; the graph contributes impact paths, not prices.
    • 
    
  • It does not establish which components must change. The must-modify set is
      an assumption attached to each scenario, stated per architecture and labelled as such. A
      dependency edge is not evidence that both ends change.
    • 
    
  • It does establish two things firmly, within this model. A hundredfold
      implementation discount never makes extracting services preferable, at any horizon, under any
      setting of the other controls. And where it does change the answer, it moves in one direction
      only — from retaining the structure to modularizing it — at a horizon of one or two
      changes, or from a gap the model already could not separate. So it lowers the threshold at
      which drawing a boundary repays without changing which boundary is worth drawing. Both are
      properties of the arithmetic, and the sweep below walks the whole parameter space to confirm
      them.
